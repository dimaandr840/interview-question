## Тема 2. Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров

### 61. Что такое образ контейнера и чем он принципиально отличается от запущенного контейнера?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Образ — это неизменяемый шаблон (файловая система и метаданные), а контейнер — это запущенный на его основе процесс со своим тонким writable-слоем и изоляцией через namespaces/cgroups.

**Разбор**

Как это работает: образ Docker собирается из последовательности read-only слоёв по инструкциям Dockerfile. При запуске (`docker run`) Docker добавляет сверху тонкий writable-слой и создаёт для процесса изолированные Linux namespaces (PID, network, mount и др.) и ограничения через cgroups — это и есть контейнер.

На практике: один и тот же образ можно запустить сколько угодно раз — каждый запуск создаёт отдельный контейнер со своим состоянием и ID. Удаление контейнера (`docker rm`) не удаляет образ, из которого он был создан; а образ нельзя удалить (`docker rmi`), пока существует хотя бы один контейнер (даже остановленный), созданный из него.

Частые ошибки: путают ID образа и ID контейнера при чтении вывода команд; ожидают, что изменения файлов внутри контейнера автоматически попадут в образ — это не так, нужен либо `docker commit` (редко применяется в проде), либо правильный путь — пересобрать образ через обновлённый Dockerfile.

**Пример / кейс**

```
$ docker images
REPOSITORY   TAG       IMAGE ID       SIZE
ubuntu       22.04     3b418d7b466a   77.8MB

$ docker run -d --name test1 ubuntu:22.04 sleep 300
$ docker run -d --name test2 ubuntu:22.04 sleep 300
$ docker ps
CONTAINER ID   IMAGE          NAMES
...            ubuntu:22.04   test1
...            ubuntu:22.04   test2
```

Из одного образа `ubuntu:22.04` создано два независимых контейнера с разными ID; `docker rmi ubuntu:22.04` завершится ошибкой "image is being used", пока `test1` и `test2` существуют.

### 62. Что такое слои (layers) образа и как они формируются при сборке Dockerfile?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Каждая инструкция Dockerfile, изменяющая файловую систему (`RUN`, `COPY`, `ADD`), создаёт новый неизменяемый слой с диффом относительно предыдущего; слои накладываются друг на друга union/overlay-файловой системой.

**Разбор**

Как это работает: сборщик выполняет инструкции Dockerfile последовательно, и после каждой такой инструкции фиксирует результат как отдельный слой с собственным хешем содержимого. Готовый образ — это упорядоченный список ссылок на такие слои плюс метаданные (команда запуска, переменные окружения и т.п.).

На практике: слои можно посмотреть командой `docker history <image>` — там видны размер и команда, создавшая каждый слой. Одинаковые слои (по хешу) могут переиспользоваться разными образами на одном хосте, что экономит место на диске и трафик при `docker pull`.

Частые ошибки: думают, что удаление файла в более позднем слое (`RUN rm large_file`) уменьшает итоговый размер образа — на самом деле файл физически остаётся в предыдущем слое и продолжает занимать место, просто становится невидимым в финальной файловой системе. Для реального уменьшения размера нужно либо не создавать файл в отдельном слое, либо использовать multi-stage build.

**Пример / кейс**

```
$ docker history myapp:1.0
IMAGE          CREATED BY                                      SIZE
<missing>      RUN apt-get update && apt-get install -y curl   42MB
<missing>      COPY . /app                                     1.2MB
<missing>      FROM ubuntu:22.04                                77.8MB
```

Видно, что установка `curl` добавила отдельный слой в 42MB независимо от того, что происходило до или после — удаление пакета в последующем `RUN` не уберёт эти 42MB из образа.

### 63. Из каких основных инструкций обычно состоит Dockerfile и что делает каждая (FROM, RUN, COPY, CMD)?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

`FROM` задаёт базовый образ, `RUN` выполняет команду во время сборки и фиксирует результат новым слоем, `COPY` копирует файлы с хоста в образ, `CMD` задаёт команду, выполняемую по умолчанию при запуске контейнера.

**Разбор**

Как это работает: `FROM` указывает стартовую файловую систему и наследуемые метаданные; всё, что идёт после, добавляется слоями сверху. `RUN` выполняется в процессе `docker build`, то есть влияет только на содержимое образа, а не на поведение при запуске. `COPY` переносит файлы из контекста сборки (папки, переданной в `docker build`) в файловую систему образа. `CMD` не выполняется при сборке — она просто записывается в метаданные образа и запускается, когда создаётся контейнер, если не переопределена явно.

На практике: в одном Dockerfile обычно одна инструкция `FROM` (без multi-stage), несколько `RUN`/`COPY` и одна итоговая `CMD` (или `ENTRYPOINT`). Порядок инструкций важен для кэширования слоёв: то, что меняется редко, должно идти раньше.

Частые ошибки: пишут бизнес-логику в `RUN` там, где она должна выполняться при старте контейнера (`CMD`), либо наоборот ожидают, что `CMD` выполнится во время сборки и проверит результат — это не так, `CMD` только декларируется.

**Пример / кейс**

```dockerfile
FROM python:3.12-slim
RUN pip install --no-cache-dir flask==3.0.0
COPY app.py /app/app.py
WORKDIR /app
CMD ["python", "app.py"]
```

`docker build -t myflask .` выполнит `RUN pip install` на этапе сборки один раз; `CMD ["python", "app.py"]` выполнится только при `docker run myflask`.

### 64. В чём разница между COPY и ADD в Dockerfile, и когда предпочтительнее использовать COPY?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

`COPY` копирует локальные файлы и папки без дополнительной логики; `ADD` умеет дополнительно автоматически распаковывать локальные tar-архивы и скачивать файлы по URL, что делает её менее предсказуемой — поэтому по умолчанию рекомендуют `COPY`.

**Разбор**

Как это работает: обе инструкции копируют содержимое из контекста сборки (или, для `ADD`, из внешнего URL) в указанный путь внутри образа, создавая новый слой. `ADD` дополнительно проверяет, является ли источник локальным tar/tar.gz/tar.bz2-архивом — если да, автоматически распаковывает его в целевую директорию.

На практике: `COPY` предсказуема и явна — что скопировали, то и получили; `ADD` стоит использовать только когда осознанно нужна автораспаковка локального архива. Скачивание файлов через `ADD <url>` по URL в современных Dockerfile не рекомендуется — лучше явный `RUN curl -o ... && ...`, потому что так можно проверить контрольную сумму и управлять кэшированием слоя точнее.

Частые ошибки: используют `ADD` "по привычке" для обычного копирования файлов, из-за чего поведение сборки для других членов команды становится менее очевидным; не замечают, что `ADD` с архивом неожиданно распаковывает файлы там, где ожидалось просто скопировать архив целиком.

**Пример / кейс**

```dockerfile
# ADD автоматически распакует архив в /app
ADD app-dist.tar.gz /app/

# COPY скопирует архив как есть, без распаковки
COPY app-dist.tar.gz /app/
```

После первой инструкции в `/app` окажутся распакованные файлы из `app-dist.tar.gz`; после второй — сам файл архива, без изменений.

### 65. В чём разница между CMD и ENTRYPOINT в Dockerfile?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

`CMD` задаёт аргументы/команду по умолчанию, которые легко целиком переопределить аргументами `docker run`; `ENTRYPOINT` задаёт основную исполняемую команду, которая по умолчанию не заменяется — аргументы `docker run` добавляются к ней или заменяют `CMD`.

**Разбор**

Как это работает: если задан только `CMD`, то любые аргументы после имени образа в `docker run` полностью заменяют `CMD`. Если задан `ENTRYPOINT` в exec-форме (`["executable"]`), а `CMD` задаёт аргументы по умолчанию, то аргументы из `docker run` заменяют именно `CMD`, а не `ENTRYPOINT` — то есть исполняемый файл остаётся фиксированным, меняются только его флаги.

На практике: `ENTRYPOINT` удобен, когда образ должен вести себя как "обёртка" над конкретной программой (например, CLI-утилита), а `CMD` используют для образов общего назначения, где запуск произвольной команды — ожидаемый сценарий (например, базовые образы `ubuntu`/`alpine`).

Частые ошибки: задают `ENTRYPOINT` в shell-форме (`ENTRYPOINT command`) вместо exec-формы — тогда сигналы (например, `SIGTERM` при `docker stop`) доставляются обёртывающему `/bin/sh -c`, а не самому процессу, и контейнер может не завершаться штатно по таймауту `docker stop`, уходя в `SIGKILL`.

**Пример / кейс**

```dockerfile
ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]
```

`docker run myimage` выполнит `nginx -g "daemon off;"`; `docker run myimage -v` заменит `CMD` и выполнит `nginx -v`, не трогая `ENTRYPOINT`.

### 66. Что такое .dockerignore и для чего он нужен при сборке образа?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

`.dockerignore` — файл в корне контекста сборки, который задаёт шаблоны файлов и папок, исключаемых из контекста перед отправкой демону Docker, аналогично `.gitignore`.

**Разбор**

Как это работает: перед выполнением `docker build` клиент Docker упаковывает всю директорию контекста (обычно `.`) и отправляет её демону; `.dockerignore` фильтрует, какие пути не попадают в этот архив, а значит не могут быть скопированы `COPY`/`ADD` и не влияют на инвалидацию кэша слоёв.

На практике: в `.dockerignore` обычно исключают `node_modules`, `.git`, временные файлы сборки, большие дата-файлы и локальные секретные файлы (`.env`). Это ускоряет отправку контекста демону, уменьшает риск случайно скопировать ненужные или чувствительные файлы в образ и снижает вероятность лишней инвалидации кэша слоёв из-за неважных изменений (например, в `.git`).

Частые ошибки: забывают добавить `.git` и локальные `.env`/файлы с секретами в `.dockerignore`, из-за чего они случайно попадают в контекст, а затем (если ещё и скопированы инструкцией с широкой маской, например `COPY . .`) — прямо в слои образа, откуда их потом трудно удалить.

**Пример / кейс**

```
# .dockerignore
.git
node_modules
*.log
.env
Dockerfile
```

После добавления такого файла команда `COPY . .` не скопирует `.git`, `node_modules` и `.env`, даже если они присутствуют в рабочей директории.

### 67. Как посмотреть вывод (логи) работающего или уже завершившегося контейнера?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Команда `docker logs <container>` выводит stdout/stderr контейнера; флаг `-f` переключает в режим постоянного чтения (follow), `--tail N` ограничивает вывод последними N строками.

**Разбор**

Как это работает: по умолчанию Docker перехватывает stdout и stderr главного процесса контейнера через драйвер логирования (по умолчанию `json-file`) и сохраняет их на диске хоста; `docker logs` читает эти сохранённые записи, независимо от того, работает контейнер сейчас или уже остановлен (если он не был удалён).

На практике: `docker logs -f --tail 100 myapp` — типичная команда для live-наблюдения за последними записями при диагностике; для контейнеров, уже упавших (`docker ps -a` показывает `Exited`), `docker logs` всё равно покажет накопленный вывод, что часто первый шаг диагностики причины падения.

Частые ошибки: ожидают увидеть логи приложения, которое пишет не в stdout/stderr, а в файл внутри контейнера — `docker logs` их не покажет, нужно либо `docker exec`/`docker cp` для чтения файла, либо перенастроить приложение писать в stdout.

**Пример / кейс**

```
$ docker logs --tail 20 -f myapp
2024-05-01T10:00:01Z INFO  starting server on :8080
2024-05-01T10:00:05Z ERROR failed to connect to db: connection refused
```

Видно, что приложение не может подключиться к БД — следующий шаг диагностики: проверить сеть и доступность контейнера с БД.

### 68. Что такое том (volume) в Docker и для чего он используется?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Volume — управляемая Docker область хранения данных, находящаяся вне writable-слоя конкретного контейнера, которая переживает удаление контейнера и может быть подключена к другим контейнерам.

**Разбор**

Как это работает: writable-слой контейнера удаляется вместе с самим контейнером (`docker rm`), поэтому данные, записанные только в него, теряются навсегда. Volume создаётся отдельно (явно через `docker volume create` или неявно при первом использовании) и хранится Docker-ом в собственной управляемой области на хосте (обычно `/var/lib/docker/volumes/...`), не зависящей от жизненного цикла контейнера.

На практике: volume используют для всего, что должно сохраняться между пересозданиями контейнера — данных БД, загруженных пользователями файлов, кэшей. Volume можно подключить сразу к нескольким контейнерам одновременно для обмена данными.

Частые ошибки: хранят важные данные приложения только внутри writable-слоя контейнера (без volume), а затем теряют их при обычном обновлении версии образа (`docker rm old && docker run new`), потому что не связали с конкретным volume заранее.

**Пример / кейс**

```
$ docker volume create pgdata
$ docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:16
$ docker rm -f db
$ docker run -d --name db2 -v pgdata:/var/lib/postgresql/data postgres:16
```

Несмотря на удаление контейнера `db`, данные БД сохраняются в volume `pgdata` и доступны новому контейнеру `db2`.

### 69. Чем отличается bind mount от named volume в Docker?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Bind mount монтирует конкретный, заранее известный путь файловой системы хоста внутрь контейнера; named volume — это область хранения, полностью управляемая самим Docker, физическое расположение которой не нужно знать пользователю.

**Разбор**

Как это работает: при bind mount (`-v /host/path:/container/path`) пользователь сам указывает и контролирует путь на хосте — файлы там видны и редактируемы обычными средствами ОС вне Docker. При named volume (`-v myvolume:/container/path`) Docker сам создаёт и обслуживает хранилище, абстрагируя пользователя от реального расположения на диске; доступ к содержимому идёт только через Docker-команды или сам контейнер.

На практике: bind mount удобен для разработки (например, монтирование исходного кода проекта для live-перезагрузки) и для доступа к специфическим файлам хоста (сертификаты, сокеты). Named volume предпочтителен для production-данных приложений (БД, очереди), так как не зависит от конкретной структуры файловой системы хоста и лучше переносится между хостами через backup/restore драйверов volume.

Частые ошибки: используют bind mount на production для данных БД, жёстко привязывая развёртывание к конкретному пути конкретного хоста, что усложняет миграцию на другой сервер или оркестратор.

**Пример / кейс**

```
# bind mount: путь на хосте должен существовать и известен заранее
docker run -v /srv/app/config:/app/config myapp

# named volume: Docker сам управляет хранилищем
docker run -v app_config:/app/config myapp
```

`docker volume ls` покажет `app_config` в списке управляемых volume, тогда как `/srv/app/config` в этом списке не появится — это просто директория хоста.

### 70. Какие базовые сетевые режимы (drivers) есть у Docker и чем отличаются bridge, host и none?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

`bridge` (режим по умолчанию) создаёт изолированную виртуальную сеть с NAT на хост; `host` отключает сетевую изоляцию, и контейнер напрямую использует сетевой стек хоста; `none` отключает сеть вовсе, кроме локального loopback-интерфейса.

**Разбор**

Как это работает: `bridge` создаёт виртуальный сетевой мост на хосте, к которому подключаются контейнеры, получая собственный IP во внутренней подсети; доступ снаружи требует явной публикации портов (`-p`). `host` убирает сетевой namespace контейнера — он напрямую слушает порты хоста, без NAT и без изоляции портов от других процессов хоста. `none` не подключает контейнер ни к одному сетевому интерфейсу, кроме loopback — используется для процессов, которым сеть вовсе не нужна, либо для максимальной изоляции.

На практике: `bridge` — безопасный выбор по умолчанию для большинства сервисов; `host` иногда применяют там, где критична сетевая производительность или нужен доступ к сетевым интерфейсам хоста напрямую (с пониманием, что контейнер теряет изоляцию портов); `none` используют редко, для batch-задач без сетевого взаимодействия.

Частые ошибки: используют `--network host` "для простоты", не осознавая, что это открывает контейнеру те же порты и сетевые возможности, что есть у самого хоста, и ломает возможность запустить несколько одинаковых контейнеров на разных портах одновременно.

**Пример / кейс**

```
$ docker run -d --network host --name web nginx
$ docker run -d --network none --name isolated alpine sleep 1000
```

В первом случае nginx слушает порт 80 прямо на хосте (без `-p`); во втором контейнер вообще не имеет сетевого доступа — `docker exec isolated ping 8.8.8.8` завершится ошибкой.

### 71. Как опубликовать порт контейнера на хост и зачем это нужно?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Флаг `-p <host_port>:<container_port>` команды `docker run` настраивает переадресацию трафика с порта хоста на порт внутри контейнера через правила iptables/NAT, делая сервис контейнера доступным снаружи.

**Разбор**

Как это работает: контейнер в режиме `bridge` находится в изолированной подсети и по умолчанию недостижим снаружи хоста. Публикация порта создаёт правило трансляции адресов (DNAT) на хосте: обращения на `host_port` перенаправляются на IP контейнера и `container_port` внутри виртуальной сети.

На практике: можно опубликовать порт на все интерфейсы хоста (`-p 8080:80`) или только на конкретный IP (`-p 127.0.0.1:8080:80`, чтобы сервис был доступен только локально); флаг `-P` (заглавная) публикует все `EXPOSE`-порты образа на случайные свободные порты хоста.

Частые ошибки: путают `EXPOSE` в Dockerfile с реальной публикацией порта — `EXPOSE` лишь документирует, какой порт слушает приложение внутри образа, и не публикует его автоматически; забывают, что при публикации на все интерфейсы (`0.0.0.0`) порт может стать доступен из внешней сети, если хост не защищён файрволом.

**Пример / кейс**

```
$ docker run -d -p 8080:80 nginx
$ curl http://localhost:8080
<!DOCTYPE html><html>... Welcome to nginx! ...
```

Запрос на `localhost:8080` хоста успешно долетает до nginx, слушающего порт 80 внутри контейнера.

### 72. Что такое реестр образов (registry) и какую роль играет Docker Hub?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Registry — сервис хранения и распространения образов по именам и тегам/дайджестам (поддерживает `docker push`/`docker pull`); Docker Hub — крупнейший публичный registry, но в компаниях часто используют приватные реестры (Harbor, ECR, GCR, GitLab Registry и др.).

**Разбор**

Как это работает: образ идентифицируется полным именем вида `[registry-host/]namespace/repository:tag`; если хост реестра не указан, по умолчанию используется Docker Hub. `docker pull` скачивает слои образа из реестра, `docker push` — загружает их туда, если у пользователя есть права на репозиторий.

На практике: публичные образы с Docker Hub удобны для готовых инструментов (базовые образы, популярные сервисы), но для внутренних приложений компании обычно нужен приватный реестр — с контролем доступа, сканированием на уязвимости и нередко географической близостью к инфраструктуре для быстрого `pull`.

Частые ошибки: тянут неизвестные образы из публичных реестров без проверки источника (официальный образ или произвольный пользовательский) — произвольные образы могут содержать уязвимости или вредоносный код; не указывают явно реестр в имени образа, из-за чего не очевидно, откуда реально приходит артефакт.

**Пример / кейс**

```
$ docker pull nginx:1.25
$ docker tag nginx:1.25 registry.example.com/team/nginx:1.25
$ docker push registry.example.com/team/nginx:1.25
```

Образ скачан с Docker Hub, затем помечен новым именем и загружен в приватный реестр `registry.example.com`.

### 73. Почему использование тега latest считается плохой практикой в production?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

`latest` — обычный текстовый тег, который может в разное время указывать на совершенно разные версии образа, поэтому он не даёт воспроизводимости развёртывания и затрудняет точный откат на известную рабочую версию.

**Разбор**

Как это работает: тег в Docker — просто указатель (как ветка в Git) на конкретный digest образа; при каждой публикации новой сборки с тем же тегом `latest` указатель переставляется на новый digest, а старый остаётся доступен только по digest, если его явно не сохранили.

На практике: для воспроизводимых развёртываний используют конкретные версии (`myapp:1.4.2`) или ещё надёжнее — digest (`myapp@sha256:...`), которые однозначно фиксируют содержимое образа. Это позволяет точно знать, какая версия кода работает в каждом окружении, и безопасно откатываться.

Частые ошибки: деплоят `myapp:latest` в проде и через время не могут понять, какая именно версия кода сейчас запущена, потому что каждый `docker pull myapp:latest` после новой сборки меняет фактическое содержимое без изменения имени; при откате пытаются "откатить latest", хотя по факту нужно просто передеплоить предыдущий зафиксированный тег.

**Пример / кейс**

```
День 1: docker push myapp:latest   (digest sha256:aaa...)
День 2: docker push myapp:latest   (digest sha256:bbb...)

# на проде всё это время крутится "myapp:latest",
# но фактическое содержимое образа сменилось без явной сигнализации об этом
```

Без явного тега версии невозможно по имени образа понять, какой код реально выполняется на проде в день 1 и день 2.

### 74. Как посмотреть текущее потребление ресурсов (CPU, память) запущенными контейнерами?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Команда `docker stats` показывает live-метрики по контейнерам: CPU%, использование памяти относительно лимита, сетевой I/O и дисковый I/O; с флагом `--no-stream` выводится однократный снимок, а не постоянно обновляемая таблица.

**Разбор**

Как это работает: `docker stats` читает метрики напрямую из cgroups хоста, в которых запущен каждый контейнер (CPU time, memory.usage, I/O счётчики), и периодически обновляет вывод в терминале.

На практике: `docker stats` — первый инструмент для быстрой проверки, не "съедает" ли какой-то контейнер аномально много CPU или памяти; для разового снимка (например, в скриптах) используют `docker stats --no-stream --format "{{.Name}}: {{.CPUPerc}} {{.MemUsage}}"`.

Частые ошибки: путают `MEM USAGE / LIMIT` из `docker stats` с реальным лимитом ядра ОС — если лимит контейнеру явно не задан (`--memory`), в колонке показывается общая память хоста, что может ввести в заблуждение о "лимите" контейнера.

**Пример / кейс**

```
$ docker stats --no-stream
CONTAINER   NAME   CPU %   MEM USAGE / LIMIT     MEM %
a1b2c3d4    web    145.3%  510MiB / 512MiB        99.6%
```

Контейнер `web` почти вплотную подошёл к лимиту памяти 512MiB — высокий риск скорого OOM kill, нужно разобраться в причине и/или повысить лимит.

### 75. Какими флагами можно ограничить потребление памяти и CPU контейнером при его запуске?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Флаг `--memory` (и опционально `--memory-swap`) ограничивает объём памяти контейнера, флаг `--cpus` ограничивает долю процессорного времени (например, `1.5` ядра); при превышении лимита памяти процесс в контейнере получает OOM kill.

**Разбор**

Как это работает: оба флага транслируются в настройки Linux cgroups для контейнера. `--memory=512m` задаёт жёсткий верхний предел использования RAM — при его превышении ядро посылает OOM killer сигнал процессу внутри контейнера. `--cpus=1.5` задаёт квоту CPU-времени за период, ограничивая максимальную долю процессора, которую может использовать контейнер, независимо от того, сколько ядер физически доступно на хосте.

На практике: лимиты обязательно нужны на production-хостах с несколькими контейнерами, чтобы один "прожорливый" сервис не мог положить остальные (noisy neighbor); значения лимитов стоит подбирать на основе реального профиля нагрузки приложения, а не произвольно.

Частые ошибки: задают лимит памяти заметно ниже реальных потребностей приложения "на всякий случай", что приводит к частым OOM kill и перезапускам; путают лимит CPU с лимитом числа ядер — `--cpus=2` не "привязывает" контейнер строго к 2 физическим ядрам, а ограничивает суммарную долю CPU-времени, эквивалентную двум ядрам.

**Пример / кейс**

```
$ docker run -d --name limited --memory=512m --cpus=1.5 myapp
$ docker inspect limited --format '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}'
536870912 1500000000
```

`docker inspect` подтверждает, что лимиты применены: 512MiB памяти и 1.5 CPU в виде NanoCpus.

### 76. Как выполнить команду внутри уже работающего контейнера, например для диагностики?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Команда `docker exec -it <container> sh` (или `bash`, если он есть в образе) запускает новый процесс в тех же namespaces, что и уже работающий контейнер, не перезапуская и не останавливая его.

**Разбор**

Как это работает: `docker exec` не создаёт новый контейнер, а добавляет ещё один процесс в существующие Linux namespaces уже запущенного контейнера (тот же сетевой стек, та же файловая система на момент выполнения). Флаги `-i` и `-t` обеспечивают интерактивный терминал.

На практике: типичный способ диагностики "живого" контейнера — зайти внутрь и проверить процессы, переменные окружения, содержимое файлов, сетевую доступность (`ps aux`, `env`, `curl localhost:...`, `cat /etc/resolv.conf`). Это работает только если в образе есть исполняемый shell; для минимальных/distroless образов такой shell может отсутствовать.

Частые ошибки: путают `docker exec` с `docker attach` — `attach` подключается к основному процессу (PID 1) контейнера и может случайно его завершить при `Ctrl+C`, тогда как `exec` создаёт отдельный независимый процесс и безопаснее для диагностики.

**Пример / кейс**

```
$ docker exec -it web sh
/ # ps aux
PID   USER     COMMAND
1     root     nginx: master process
7     root     sh
/ # curl -s -o /dev/null -w "%{http_code}" http://localhost:80
200
```

Внутри контейнера подтверждено, что nginx отвечает кодом 200 на локальный запрос — проблема, если она есть, скорее всего не в самом приложении, а на уровне сети/публикации портов.

### 77. В чём принципиальная разница между Dockerfile и образом, который он описывает?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Dockerfile — текстовый рецепт сборки (исходный код, который можно хранить в Git), а образ — это бинарный артефакт, полученный в результате выполнения этого рецепта командой `docker build`.

**Разбор**

Как это работает: `docker build` читает Dockerfile, последовательно выполняет инструкции и производит набор слоёв с метаданными — это и есть образ, сохранённый локально и идентифицируемый по digest. Dockerfile сам по себе не запускается и ничего не хранит — это только инструкция для сборщика.

На практике: один и тот же Dockerfile, собранный в разное время (например, при изменившемся базовом образе или зависимостях без фиксации версий), может дать разные по содержимому образы — поэтому важно различать "код инфраструктуры" (Dockerfile в репозитории) и конкретный "артефакт" (собранный и протегированный образ), который реально развёртывается.

Частые ошибки: хранят только Dockerfile без зафиксированного и опубликованного в реестре образа и пытаются "пересобрать то же самое" на каждом окружении — это не гарантирует идентичность артефакта между dev/staging/prod, если за это время изменились внешние зависимости.

**Пример / кейс**

```dockerfile
FROM node:20
COPY . /app
RUN npm install
CMD ["npm", "start"]
```

```
$ docker build -t myapp:1.0 .
$ docker image inspect myapp:1.0 --format '{{.Id}}'
sha256:9f8e7d6c5b4a...
```

Dockerfile — это текст выше; `myapp:1.0` с конкретным digest `sha256:9f8e7d6c...` — это уже образ, артефакт одной конкретной сборки.

### 78. Что такое multi-stage build в Docker и для чего он применяется на базовом уровне?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Multi-stage build — это Dockerfile с несколькими инструкциями `FROM`, где промежуточные стадии (например, со средой компиляции) используются только для сборки артефакта, а в финальный образ через `COPY --from=` копируются только нужные готовые файлы — без инструментов сборки.

**Разбор**

Как это работает: каждая `FROM` начинает новую именованную или нумерованную стадию со своим набором слоёв; инструкция `COPY --from=<stage>` позволяет взять файл из предыдущей стадии в текущую, не перенося остальное содержимое той стадии. Финальным образом становится только последняя стадия Dockerfile.

На практике: типичный пример — компилируемые языки (Go, Java, C++): первая стадия содержит компилятор и зависимости сборки (большой образ), вторая стадия — минимальный базовый образ (например, `alpine` или `scratch`), в который копируется только скомпилированный бинарник. Итоговый образ получается значительно меньше и не содержит инструментов сборки, что также снижает поверхность атаки.

Частые ошибки: забывают именовать стадии (`AS builder`) и затем путаются при ссылках `--from=0` в сложных Dockerfile; копируют из builder-стадии больше файлов, чем нужно (например, весь `/root` вместе с кэшами), раздувая итоговый образ без необходимости.

**Пример / кейс**

```dockerfile
FROM golang:1.22 AS builder
WORKDIR /src
COPY . .
RUN go build -o app .

FROM alpine:3.19
COPY --from=builder /src/app /usr/local/bin/app
CMD ["/usr/local/bin/app"]
```

Итоговый образ на базе `alpine` не содержит ни исходного кода, ни компилятора Go — только готовый бинарник `app`, что проверяется размером образа (`docker images`) заметно меньшим, чем промежуточная стадия `builder`.

### 79. Как удалить неиспользуемые образы, контейнеры и сети, занимающие место на диске хоста?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Команда `docker system prune` удаляет остановленные контейнеры, неиспользуемые пользовательские сети, "висячие" (dangling) образы и build-кэш; флаг `-a` дополнительно удаляет все неиспользуемые образы (не только dangling), а `--volumes` — неиспользуемые тома.

**Разбор**

Как это работает: со временем на хосте накапливаются остановленные контейнеры, промежуточные (dangling, без тега) образы от пересборок и неиспользуемые тома/сети — всё это продолжает занимать место на диске, даже если активно не используется. `docker system prune` проходит по этим категориям объектов и удаляет те, что не привязаны ни к одному работающему или даже остановленному (в зависимости от флагов) контейнеру.

На практике: команду часто запускают на CI-раннерах и build-серверах, где регулярно накапливается большой объём build-кэша и промежуточных слоёв; перед добавлением `--volumes` стоит убедиться, что нет важных данных только в неиспользуемых на вид volume.

Частые ошибки: запускают `docker system prune -a --volumes` на production-хосте без предварительной проверки, что именно будет удалено — команда может безвозвратно удалить volume с данными, которые не были подключены ни к одному контейнеру в момент запуска, но формально ещё нужны.

**Пример / кейс**

```
$ docker system prune -a --volumes
WARNING! This will remove:
  - all stopped containers
  - all networks not used by at least one container
  - all volumes not used by at least one container
  - all images without at least one container associated to them
  - all build cache
Are you sure you want to continue? [y/N]
```

Явное предупреждение перед удалением — перед ответом `y` нужно убедиться, что не затронуты нужные данные в volumes.

### 80. Какая команда покажет список всех образов на хосте, и что означают основные колонки её вывода?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Junior

**Короткий ответ**

Команда `docker images` (синоним `docker image ls`) показывает список образов на хосте; колонка `REPOSITORY:TAG` — человекочитаемое имя и версия, `IMAGE ID` — уникальный идентификатор содержимого образа, `SIZE` — суммарный размер его уникальных слоёв.

**Разбор**

Как это работает: `docker images` читает локальную метаинформацию о скачанных и собранных образах. `IMAGE ID` — это укороченный хеш (производный от digest манифеста образа), однозначно определяющий содержимое; несколько разных `REPOSITORY:TAG` могут указывать на один и тот же `IMAGE ID`, если это фактически один и тот же собранный образ, просто с разными именами/тегами.

На практике: эту команду используют, чтобы проверить, что сборка действительно создала новый образ с ожидаемым тегом, оценить размер образов перед публикацией в реестр, найти "висячие" (без тега, `<none>`) образы от незавершённых или перезаписанных сборок.

Частые ошибки: путают `SIZE` в выводе `docker images` с реальным приростом места на диске при добавлении нового образа — если образы делят общие нижние слои (например, один и тот же базовый `FROM`), фактический прирост на диске будет меньше суммы отображаемых размеров, так как общие слои хранятся один раз.

**Пример / кейс**

```
$ docker images
REPOSITORY   TAG       IMAGE ID       CREATED        SIZE
myapp        1.0       9f8e7d6c5b4a   2 days ago     128MB
myapp        latest    9f8e7d6c5b4a   2 days ago     128MB
<none>       <none>    a1b2c3d4e5f6   5 days ago     130MB
```

`myapp:1.0` и `myapp:latest` имеют одинаковый `IMAGE ID` — это один и тот же образ под двумя именами; строка с `<none>` — результат предыдущей сборки, на которую больше не ссылается ни один тег.

### 81. Как устроено кэширование слоёв при docker build и как правильно упорядочить инструкции Dockerfile для ускорения пересборки?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Docker кэширует каждый слой по хешу инструкции и её входных данных; если слой и все предыдущие совпадают с кэшем, сборка переиспользует готовый слой без повторного выполнения — поэтому редко меняющиеся шаги (установку зависимостей) нужно располагать раньше часто меняющегося кода.

**Разбор**

Как это работает: для каждой инструкции сборщик вычисляет ключ кэша на основе самой команды и (для `COPY`/`ADD`) содержимого копируемых файлов. Если ключ совпадает с ранее сохранённым слоем и все предыдущие слои тоже были взяты из кэша, инструкция не выполняется повторно — используется готовый слой. Как только один слой в цепочке меняется, все последующие слои инвалидируются и пересобираются с нуля, даже если их входные данные не менялись.

На практике: классический паттерн для Node.js/Python/Go — сначала копировать только файл с описанием зависимостей (`package.json`, `requirements.txt`, `go.mod`), выполнить установку зависимостей, и только потом копировать весь исходный код. Тогда изменение кода приложения не инвалидирует дорогой шаг установки зависимостей.

Частые ошибки: пишут `COPY . .` сразу в начале Dockerfile перед установкой зависимостей — любое изменение любого файла в репозитории (даже README) инвалидирует кэш установки зависимостей, и она выполняется заново при каждой сборке; используют BuildKit cache mount некорректно, полагая, что он заменяет правильный порядок инструкций.

**Пример / кейс**

```dockerfile
# Плохо: любое изменение кода пересобирает npm install
FROM node:20
COPY . .
RUN npm install
CMD ["npm", "start"]

# Хорошо: npm install кэшируется, пока не меняется package*.json
FROM node:20
COPY package*.json ./
RUN npm install
COPY . .
CMD ["npm", "start"]
```

Во втором варианте `docker build` при изменении только `src/index.js` переиспользует кэш слоя `RUN npm install`, что проверяется по надписи `CACHED` в выводе сборки для этого шага.

### 82. Контейнер приложения постоянно перезапускается, и docker ps показывает код выхода 137 почти сразу после старта. Как диагностировать причину?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Код выхода 137 = 128+9, то есть процесс получил сигнал `SIGKILL`; чаще всего это OOM kill от cgroup при превышении лимита `--memory`, что подтверждается полем `OOMKilled: true` в `docker inspect`.

**Разбор**

Как это работает: когда процесс внутри контейнера превышает лимит памяти cgroup, ядро Linux принудительно завершает его сигналом `SIGKILL` (OOM killer), и Docker фиксирует соответствующий код выхода и флаг в метаданных контейнера. Если при этом задана политика restart (`--restart=on-failure` или `always`), Docker сразу перезапускает контейнер, который снова упирается в тот же лимит и падает — внешне это выглядит как бесконечный цикл перезапусков.

На практике: первым шагом смотрят `docker inspect --format '{{json .State}}' <container>` — наличие `"OOMKilled": true` подтверждает причину. Далее нужно понять, действительно ли приложению не хватает заданного лимита (тогда разумно его увеличить и профилировать потребление памяти), либо это утечка памяти в самом приложении (тогда увеличение лимита лишь отложит проблему).

Частые ошибки: сразу увеливают `--memory` "чтобы заработало", не проверив, не является ли рост потребления памяти утечкой; путают OOM kill ядра cgroup с ошибкой уровня приложения (например, необработанным исключением), хотя код 137 специфично указывает именно на внешний `SIGKILL`.

**Пример / кейс**

```
$ docker inspect app --format '{{json .State}}' | jq
{
  "Status": "exited",
  "ExitCode": 137,
  "OOMKilled": true,
  "Error": ""
}

$ dmesg | grep -i "killed process"
[12345.678] Memory cgroup out of memory: Killed process 4821 (node) ...
```

Оба источника подтверждают: процесс убит именно из-за превышения лимита памяти cgroup, а не из-за сбоя самого приложения.

### 83. Чем отличается принцип copy-on-write в overlay2 storage driver от простого копирования файлов между слоями образа?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

OverlayFS объединяет несколько read-only слоёв (`lowerdir`) с одним writable-слоем (`upperdir`) через union filesystem; при первой попытке изменить файл, унаследованный из нижнего слоя, он целиком копируется в `upperdir` (copy-up) перед модификацией, а не копируется весь образ.

**Разбор**

Как это работает: overlay2 (стандартный storage driver Docker на современных ядрах Linux) показывает процессу контейнера объединённый вид файловой системы, "просвечивая" верхние изменения над нижними неизменяемыми слоями. Чтение файла, который не менялся, идёт прямо из соответствующего `lowerdir`. Как только контейнер пытается изменить такой файл, ядро выполняет copy-up — копирует файл целиком в `upperdir`, и дальнейшие изменения применяются уже к этой копии, не трогая оригинальный слой.

На практике: copy-up для очень больших файлов (например, больших лог-файлов или архивов внутри образа) может ощутимо замедлить первую операцию записи — поэтому для часто изменяемых больших файлов разумнее использовать volume, а не писать прямо в файловую систему writable-слоя контейнера.

Частые ошибки: считают, что overlay2 копирует весь образ при запуске контейнера — на самом деле копируются только отдельные файлы, и только в момент первой записи в них; не учитывают задержку copy-up при профилировании операций записи в приложениях с большими файлами внутри слоёв образа.

**Пример / кейс**

```
$ docker inspect app --format '{{.GraphDriver.Data.UpperDir}}'
/var/lib/docker/overlay2/abcdef.../diff

$ docker exec app sh -c "echo test >> /etc/config/large-file.conf"
# ядро выполнит copy-up large-file.conf в upperdir перед дозаписью
```

После первой записи в `large-file.conf`, изначально принадлежавший слою образа, его полная копия появится в `UpperDir` контейнера, что можно проверить размером и временем изменения файла там.

### 84. Как использовать multi-stage build, чтобы существенно уменьшить размер production-образа компилируемого приложения?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Стадия сборки использует полнофункциональный образ с компилятором и зависимостями, а финальная стадия строится на минимальном base image (`alpine`, `distroless`, `scratch`), в который копируется только скомпилированный бинарник через `COPY --from=`, без инструментов сборки и промежуточных артефактов.

**Разбор**

Как это работает: промежуточная стадия (`builder`) может весить сотни мегабайт за счёт компилятора, системных заголовков и зависимостей сборки, но в финальный образ эти слои не попадают — копируется только явно указанный путь. Для статически линкуемых языков (Go, Rust) финальной стадией может быть даже `scratch` — полностью пустой базовый образ, содержащий только бинарник.

На практике: это значительно сокращает размер итогового образа (с сотен мегабайт до единиц–десятков), ускоряет `docker pull` в production и уменьшает поверхность атаки — в финальном образе физически отсутствуют компиляторы, пакетные менеджеры и build-инструменты, которые могли бы быть использованы при компрометации.

Частые ошибки: забывают скопировать вспомогательные файлы, нужные бинарнику в runtime (например, сертификаты CA для TLS-соединений при использовании `scratch`, которые обычно берутся из builder-стадии через `COPY --from=builder /etc/ssl/certs/ca-certificates.crt ...`); используют слишком "толстый" финальный базовый образ (например, полный `golang` вместо `alpine`/`scratch`) и теряют выгоду multi-stage build.

**Пример / кейс**

```dockerfile
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app .

FROM scratch
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=builder /app /app
ENTRYPOINT ["/app"]
```

`docker images` покажет размер builder-стадии (сотни MB за счёт Go toolchain) и финального образа — обычно единицы-десятки MB, так как в нём остался только бинарник и сертификаты.

### 85. Два контейнера, запущенные через docker run без явной сети, не могут обратиться друг к другу по имени контейнера. Как это объяснить и исправить?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

В сети `bridge` по умолчанию (docker0) встроенный DNS Docker не резолвит имена контейнеров — обращаться можно только по IP; нужно создать пользовательскую bridge-сеть (`docker network create`) и подключить к ней оба контейнера, тогда Docker DNS начнёт резолвить имена.

**Разбор**

Как это работает: сеть `bridge` по умолчанию существует для обратной совместимости и не включает встроенный DNS-сервер Docker (127.0.0.11), который резолвит имена контейнеров и сервисов. Пользовательские (user-defined) сети, созданные через `docker network create`, автоматически получают этот встроенный DNS, и каждый подключённый контейнер может обращаться к другим по их имени или заданному через `--network-alias` псевдониму.

На практике: в большинстве реальных сценариев (включая docker-compose, который всегда создаёт пользовательскую сеть по умолчанию для проекта) контейнеры одного логического приложения нужно явно объединять в одну пользовательскую сеть. Диагностика начинается с проверки, в какой сети находится каждый контейнер (`docker inspect --format '{{.NetworkSettings.Networks}}'`), и проверки DNS-резолва внутри контейнера.

Частые ошибки: пытаются использовать имя контейнера как hostname в default bridge сети и считают это багом Docker, не зная про ограничение встроенного DNS именно для сети по умолчанию; создают пользовательскую сеть, но забывают подключить к ней один из двух контейнеров (`docker network connect`), из-за чего связь всё равно не работает.

**Пример / кейс**

```
$ docker network create app-net
$ docker run -d --name db --network app-net postgres:16
$ docker run -it --rm --name api --network app-net alpine sh -c "nslookup db"
Name:      db
Address 1: 172.19.0.2 db
```

В пользовательской сети `app-net` имя `db` успешно резолвится встроенным Docker DNS; в сети `bridge` по умолчанию та же команда `nslookup db` вернула бы ошибку резолва.

### 86. Как организовать сохранение данных приложения между пересозданием контейнера (например, при обновлении образа), не теряя данные?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Данные приложения должны находиться в named volume (или, при необходимости, bind mount), а не в writable-слое контейнера; при пересоздании контейнера с новым образом нужно подключить тот же volume по имени — тогда данные автоматически доступны новому контейнеру.

**Разбор**

Как это работает: writable-слой уничтожается вместе с контейнером при `docker rm`, независимо от того, по какой причине он пересоздаётся (обновление версии образа, смена конфигурации). Если каталог с данными приложения внутри контейнера подключён как volume, сам volume существует отдельно от жизненного цикла контейнера и переживает его удаление.

На практике: типичный безопасный процесс обновления версии stateful-сервиса — `docker stop old`, `docker rm old`, затем `docker run --name new -v same_volume:/data new_image`; важно убедиться, что новая версия образа совместима по формату данных с тем, что лежит в volume (например, при мажорном обновлении БД иногда требуется отдельная миграция формата перед переключением).

Частые ошибки: при обновлении меняют путь монтирования volume внутри контейнера между версиями образа без переноса данных на новый путь, из-за чего приложение в новой версии "не видит" старые данные, хотя volume физически не потерян; не делают backup volume перед обновлением версии stateful-сервиса, рискуя потерять данные при несовместимом обновлении.

**Пример / кейс**

```
$ docker volume create pgdata
$ docker run -d --name pg15 -v pgdata:/var/lib/postgresql/data postgres:15
# ... время работы, накоплены данные ...
$ docker stop pg15 && docker rm pg15
$ docker run -d --name pg15 -v pgdata:/var/lib/postgresql/data postgres:15.5
```

После пересоздания контейнера с уточнённым тегом `postgres:15.5` данные из `pgdata` остаются доступны — это проверяется запросом к БД сразу после старта нового контейнера.

### 87. Зачем нужен HEALTHCHECK в Dockerfile или health check в docker-compose, и как Docker использует его результат?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

`HEALTHCHECK` периодически выполняет заданную команду внутри контейнера и на основе её кода выхода определяет статус `healthy`/`unhealthy`/`starting`, который виден в `docker ps` и может использоваться для оркестрации (условия `depends_on` в compose, политика restart, внешние балансировщики).

**Разбор**

Как это работает: Docker запускает указанную команду с заданным интервалом (`--interval`), таймаутом (`--timeout`) и числом допустимых неудачных попыток (`--retries`) перед сменой статуса на `unhealthy`. В отличие от обычного статуса "процесс запущен/остановлен", healthcheck проверяет, что приложение внутри контейнера реально отвечает на уровне своей бизнес-логики (например, HTTP-эндпоинт `/health` возвращает 200), а не просто что процесс PID 1 существует.

На практике: healthcheck особенно важен для сервисов, у которых процесс может "висеть" живым, но фактически не обрабатывать запросы (deadlock, потеря соединения с зависимостью); в docker-compose условие `depends_on: condition: service_healthy` позволяет не запускать зависимый сервис, пока его зависимость не стала healthy, что снижает число ошибок на старте из-за гонки условий.

Частые ошибки: делают healthcheck слишком "тяжёлым" (например, полный прогон интеграционных проверок), создавая дополнительную нагрузку при частом интервале; не разделяют readiness (готовность принимать трафик) и liveness (процесс жив) смысл внутри одной команды healthcheck, что в сложных случаях приводит к неверной интерпретации статуса.

**Пример / кейс**

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1
```

```
$ docker ps
CONTAINER ID   STATUS
abc123         Up 2 minutes (healthy)
```

Статус `(healthy)` в `docker ps` подтверждает, что последние проверки curl успешно завершились кодом 0.

### 88. Почему рекомендуется запускать процесс в контейнере не от root, и как это настроить в Dockerfile?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Если процесс внутри контейнера работает от root и злоумышленник найдёт способ выйти за пределы изоляции (уязвимость runtime, неверно настроенные mounts/capabilities), последствия для хоста будут значительно серьёзнее, чем при непривилегированном пользователе; инструкция `USER` в Dockerfile создаёт и переключает выполнение на обычного пользователя.

**Разбор**

Как это работает: по умолчанию, если `USER` не указан, процессы контейнера выполняются от root внутри его user namespace; без дополнительной настройки user namespace remapping (`userns-remap` на демоне) root внутри контейнера по UID соответствует root на хосте (UID 0), хотя и ограничен изоляцией контейнера. Инструкция `USER appuser` переключает контекст выполнения последующих инструкций и финального процесса на указанного непривилегированного пользователя.

На практике: для обслуживающих процессов (веб-сервер приложения, воркер) обычно создают выделенного системного пользователя в образе и переключаются на него перед `CMD`/`ENTRYPOINT`; некоторые официальные базовые образы (например, `node`, `postgres`) уже содержат готового непривилегированного пользователя, которого достаточно указать в `USER`.

Частые ошибки: добавляют `USER appuser`, но забывают выдать этому пользователю права на директории, в которые приложение пишет файлы (логи, временные файлы, volume), из-за чего контейнер падает с ошибками доступа; путают изоляцию контейнера с полноценной изоляцией виртуальной машины — не-root пользователь внутри контейнера снижает, но не исключает риски при компрометации ядра или runtime.

**Пример / кейс**

```dockerfile
FROM python:3.12-slim
RUN addgroup --system app && adduser --system --ingroup app appuser
WORKDIR /app
COPY --chown=appuser:app . .
USER appuser
CMD ["python", "server.py"]
```

`docker exec container whoami` вернёт `appuser`, а не `root`, что подтверждает корректное применение непривилегированного пользователя.

### 89. Как и зачем сканировать образы на известные уязвимости (CVE) перед публикацией в registry?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Сканеры образов (Trivy, Grype, Docker Scout и аналоги) анализируют установленные пакеты во всех слоях образа и сверяют их версии с базами известных уязвимостей (CVE), позволяя обнаружить и заблокировать публикацию образов с критическими проблемами ещё в CI, до попадания в production.

**Разбор**

Как это работает: сканер разбирает слои образа, строит список установленных пакетов ОС и, часто, зависимостей уровня языка (npm, pip, go modules), затем сопоставляет версии с публичными базами данных уязвимостей (NVD и производные источники) и выдаёт отчёт с уровнями критичности (CRITICAL, HIGH, MEDIUM, LOW).

На практике: сканирование включают прямо в CI-пайплайн сборки образа, с правилом "сборка не проходит" (`exit code != 0`), если найдены уязвимости выше заданного уровня критичности; важно также периодически пересканировать уже опубликованные образы, так как новые CVE для тех же версий пакетов обнаруживаются постоянно, даже без изменения самого образа.

Частые ошибки: сканируют образ лишь однократно при публикации и больше не возвращаются к нему, хотя новые уязвимости для тех же версий пакетов появляются со временем; блокируют весь пайплайн при любой найденной уязвимости без разделения по критичности, что на практике приводит либо к постоянным "красным" сборкам, либо к массовому игнорированию отчётов командой.

**Пример / кейс**

```
$ trivy image --severity CRITICAL,HIGH myapp:1.0
myapp:1.0 (debian 12.4)
=======================
Total: 3 (CRITICAL: 1, HIGH: 2)

┌──────────┬────────────────┬──────────┬───────────────┐
│ Library  │ Vulnerability  │ Severity │ Fixed Version │
├──────────┼────────────────┼──────────┼───────────────┤
│ openssl  │ CVE-2024-XXXXX │ CRITICAL │ 3.0.13-1      │
└──────────┴────────────────┴──────────┴───────────────┘
```

CI-шаг с таким вызовом и проверкой кода выхода `trivy` не даст образу с CRITICAL-уязвимостью попасть дальше в пайплайне до обновления версии `openssl`.

### 90. Как настроить аутентификацию для pull/push образов из приватного registry, и какие есть варианты хранения учётных данных?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

`docker login <registry>` сохраняет учётные данные (токен) в `~/.docker/config.json`; для безопасного хранения вместо явного пароля в этом файле нужно использовать credential helper (например, `docker-credential-pass`/облачный helper), а в Kubernetes для pull образов используется отдельный объект `imagePullSecrets`.

**Разбор**

Как это работает: после `docker login` Docker CLI либо сохраняет (обычно в закодированном, но не зашифрованном виде) токен авторизации прямо в `config.json`, либо, если настроен credential helper, делегирует хранение секрета специализированному хранилищу ОС (keychain, pass, облачный secret manager) и сохраняет в `config.json` только ссылку на него. При каждом `docker pull`/`docker push` клиент автоматически подставляет сохранённые данные для соответствующего хоста реестра.

На практике: в CI-пайплайнах учётные данные для реестра передают через секреты самой CI-системы (а не хранят в репозитории или прямо в Dockerfile), логинясь перед операциями `push`; в облачных managed registry (ECR, GCR, ACR) обычно используется краткоживущий токен, получаемый через облачный CLI, а не статический пароль.

Частые ошибки: хранят `~/.docker/config.json` с незашифрованным паролем в образе для "удобства" автоматизации или коммитят его в репозиторий; передают логин/пароль registry через `ARG`/`ENV` в Dockerfile — такие значения могут остаться видимыми в истории слоёв или в метаданных образа.

**Пример / кейс**

```
$ docker login registry.example.com -u ci-bot
Password: ********
Login Succeeded

$ cat ~/.docker/config.json
{
  "auths": {
    "registry.example.com": { "auth": "base64-encoded-creds" }
  }
}
```

Без credential helper значение `auth` — это просто base64 (не шифрование) от `user:password`, поэтому такой файл нужно защищать правами доступа и не коммитить в систему контроля версий.

### 91. Как Linux cgroups ограничивают CPU контейнера, и как понять, что контейнер throttling'ится по CPU?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Лимит `--cpus` транслируется в cgroup-параметры CFS-квоты (`cpu.cfs_quota_us`/`cpu.cfs_period_us` в cgroup v1 или `cpu.max` в cgroup v2); превышение квоты за период не убивает процесс, а принудительно приостанавливает его (throttling) до следующего периода, что видно по росту счётчика `nr_throttled` в `cpu.stat`.

**Разбор**

Как это работает: CFS (Completely Fair Scheduler) делит время на периоды (обычно 100ms) и выделяет контейнеру квоту CPU-времени внутри каждого периода пропорционально лимиту (например, `--cpus=0.5` даёт квоту в половину периода). Если контейнер исчерпал квоту раньше конца периода, ядро приостанавливает (throttle) его потоки до начала следующего периода — приложение не падает, но ощутимо замедляется, даже если на хосте формально есть свободные ядра.

На практике: throttling диагностируют через `cpu.stat` соответствующей cgroup контейнера: растущий `nr_throttled` относительно `nr_periods` и накопленный `throttled_time` указывают на то, что лимит CPU слишком жёсткий для фактической нагрузки приложения, что может объяснять скачки латентности, не видимые в среднем значении `docker stats`.

Частые ошибки: смотрят только на среднее значение CPU% в `docker stats` и не замечают кратковременный throttling, который проявляется именно в хвостовых задержках (p99 latency), а не в средней загрузке; ставят лимит CPU "как получится" без профилирования реального пикового потребления приложения.

**Пример / кейс**

```
$ cat /sys/fs/cgroup/system.slice/docker-<id>.scope/cpu.stat
usage_usec 123456789
nr_periods 45000
nr_throttled 1800
throttled_usec 950000
```

Соотношение `nr_throttled`/`nr_periods` ≈ 4% говорит о заметном throttling — стоит пересмотреть значение `--cpus` или профиль нагрузки приложения.

### 92. Чем отличается сеть, создаваемая docker-compose по умолчанию для проекта, от docker network create вручную, и как настроить несколько изолированных сетей для сервисов одного compose-файла?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

По умолчанию docker-compose автоматически создаёт для проекта одну пользовательскую bridge-сеть и подключает к ней все сервисы, давая им DNS-резолв по имени сервиса "из коробки"; для изоляции отдельных сервисов друг от друга (например, чтобы фронтенд не мог напрямую обращаться к БД) нужно явно объявить несколько сетей в секции `networks` и назначить сервисам только нужные.

**Разбор**

Как это работает: без явной секции `networks` compose создаёт сеть с именем вида `<project>_default` и добавляет туда все описанные сервисы — поведение по сути эквивалентно ручному `docker network create` плюс подключение каждого контейнера. Если же в compose-файле заданы несколько сетей и у каждого сервиса явно указано, к каким из них он подключён, сервисы, не состоящие в общей сети, не смогут резолвить и достигать друг друга.

На практике: типичная схема — сеть `frontend` для веб-сервера и API, и отдельная сеть `backend` для API и БД, где веб-сервер в `backend` не присутствует и физически не может напрямую обратиться к БД, даже зная её имя. Это дополнительный слой defense-in-depth на уровне сети, не заменяющий, но дополняющий авторизацию на уровне самой БД.

Частые ошибки: добавляют сервис во все сети "на всякий случай", из-за чего задуманная изоляция не работает; ожидают, что разделение на сети само по себе защищает от эксплуатации через уязвимость в сервисе, который всё же находится в обеих сетях (сеть снижает поверхность атаки, но не исключает риски внутри уже разрешённых соединений).

**Пример / кейс**

```yaml
services:
  web:
    image: myweb
    networks: [frontend]
  api:
    image: myapi
    networks: [frontend, backend]
  db:
    image: postgres:16
    networks: [backend]

networks:
  frontend:
  backend:
```

`docker exec web ping db` завершится ошибкой резолва имени — `web` не состоит в сети `backend`, где находится `db`, в отличие от `api`, у которого есть доступ в обе сети.

### 93. На хосте с множеством контейнеров внезапно заканчивается место на диске, хотя образы и volumes небольшие. Как диагностировать и какие причины наиболее вероятны?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Частая причина — неограниченный рост лог-файлов контейнеров при драйвере логирования `json-file` по умолчанию без настроенной ротации; диагностируется через `du -sh /var/lib/docker/containers/*/*.json.log`, лечится настройкой `log-opts` с `max-size`/`max-file` или сменой log driver.

**Разбор**

Как это работает: по умолчанию Docker пишет весь stdout/stderr контейнера в файл `*-json.log` на хосте без ограничения размера, если явно не настроены опции ротации. Приложение, которое интенсивно логирует (особенно в debug-уровне или при цикле ошибок с повторными попытками), может за короткое время накопить гигабайты в одном лог-файле, незаметные через обычный просмотр `docker images`/`docker system df`, который не всегда явно выделяет логи как отдельную категорию.

На практике: диагностику начинают с `docker system df` для общей картины, затем смотрят `du -sh` по директориям `/var/lib/docker/containers/`, `/var/lib/docker/overlay2/`, `/var/lib/docker/volumes/` отдельно, чтобы понять, какая категория реально расходует место. Для предотвращения повторения настраивают ротацию логов на уровне демона (`daemon.json`) или конкретного контейнера.

Частые ошибки: включают избыточное debug-логирование в production без настроенной ротации; считают, что `docker system prune` решит проблему растущих логов активных (не остановленных) контейнеров — prune не трогает логи работающих контейнеров, только неиспользуемые образы/сети/остановленные контейнеры.

**Пример / кейс**

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

После добавления такой конфигурации в `/etc/docker/daemon.json` и перезапуска демона каждый лог-файл контейнера будет автоматически ротироваться и ограничен 3 файлами по 10MB — суммарно не более 30MB логов на контейнер.

### 94. Как уменьшить количество слоёв образа и почему это иногда важно, но не должно быть самоцелью?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Объединение нескольких связанных команд в одну инструкцию `RUN` через `&&` (например, установку пакетов и очистку кэша пакетного менеджера в одной команде) уменьшает промежуточные артефакты, попадающие в финальный размер образа; но превращение всего Dockerfile в одну гигантскую команду ухудшает читаемость и кэшируемость — важнее группировать логически связанные шаги.

**Разбор**

Как это работает: если `apt-get install` и `rm -rf /var/lib/apt/lists/*` выполнить в двух разных `RUN`, временные файлы пакетного менеджера будут зафиксированы в слое после `install` и останутся там физически (как в вопросе про слои и удаление файлов), даже если следующий слой их "скрывает". Объединение в одну `RUN`-команду гарантирует, что очистка произойдёт до фиксации слоя, и временные файлы не попадут в финальный образ вовсе.

На практике: разумный баланс — объединять то, что логически представляет один шаг (установка + очистка кэша одного пакетного менеджера), но не сливать совершенно разные этапы (установка зависимостей и копирование кода приложения) в одну инструкцию, так как это ломает возможность переиспользовать кэш отдельно для каждого шага при последующих пересборках.

Частые ошибки: радикально минимизируют число слоёв ценой читаемости и кэшируемости, из-за чего любое изменение требует пересборки одного огромного шага; либо наоборот — оставляют установку и очистку в разных `RUN`, искренне считая, что последующая очистка в отдельном слое уменьшает итоговый размер образа.

**Пример / кейс**

```dockerfile
# Плохо: кэш apt остаётся зафиксированным в отдельном слое
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# Хорошо: очистка попадает в тот же слой, что и установка
RUN apt-get update && \
    apt-get install -y curl && \
    rm -rf /var/lib/apt/lists/*
```

Сравнение размеров образов (`docker images`) после каждого варианта покажет заметно меньший итоговый размер у второго варианта при прочих равных.

### 95. Как комбинация ENTRYPOINT в exec-форме и CMD позволяет передавать аргументы по умолчанию, которые можно переопределить при запуске?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

При `ENTRYPOINT ["executable"]` в exec-форме и `CMD ["--default-flag"]`, `docker run image` без дополнительных аргументов выполнит `executable --default-flag`, а `docker run image --other-flag` заменит именно `CMD`, выполнив `executable --other-flag`, не трогая сам `ENTRYPOINT`.

**Разбор**

Как это работает: Docker собирает финальную команду контейнера как конкатенацию массива `ENTRYPOINT` и массива аргументов — либо `CMD` из образа (если явных аргументов в `docker run` нет), либо аргументов, переданных после имени образа в `docker run` (если они есть, они целиком заменяют `CMD`, но не `ENTRYPOINT`). Это работает предсказуемо только при exec-форме (`["..."]`) обоих инструкций — shell-форма ломает эту механику, так как оборачивает команду в `/bin/sh -c`.

На практике: такой паттерн используют для образов-утилит, где `ENTRYPOINT` фиксирует саму программу, а `CMD` задаёт "разумные значения по умолчанию" флагов, которые пользователь образа может переопределить без необходимости переопределять весь `ENTRYPOINT` через `--entrypoint`.

Частые ошибки: задают `ENTRYPOINT` в shell-форме (`ENTRYPOINT executable`) и затем недоумевают, почему `CMD` с аргументами не подхватывается ожидаемым образом — в shell-форме Docker игнорирует `CMD` как аргументы в привычном смысле, так как вся команда уже единая строка, выполняемая через shell.

**Пример / кейс**

```dockerfile
ENTRYPOINT ["python", "cli.py"]
CMD ["--mode=default"]
```

```
$ docker run myimage
# выполнится: python cli.py --mode=default

$ docker run myimage --mode=debug
# выполнится: python cli.py --mode=debug
```

Второй вызов подтверждает, что переданный аргумент `--mode=debug` заменил `CMD`, но `ENTRYPOINT` (`python cli.py`) остался неизменным в обоих случаях.

### 96. Как отладить проблему в контейнере, построенном на distroless/минимальном образе без shell и пакетного менеджера?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Обычный `docker exec sh` не сработает, так как shell отсутствует; можно извлечь файлы через `docker cp`, либо запустить отдельный debug-контейнер (например, на базе `busybox`), разделяющий сетевые и/или PID namespaces с целевым контейнером через `--network container:<id>` и `--pid container:<id>`.

**Разбор**

Как это работает: `docker run --network=container:<target> --pid=container:<target> busybox sh` создаёт новый, полноценный контейнер с инструментами внутри, но подключает его к тем же namespaces, что у целевого — в результате из debug-контейнера видно те же процессы (`ps aux` покажет процессы целевого контейнера) и ту же сетевую конфигурацию (можно сделать `curl localhost:PORT`, как если бы запрос шёл из самого целевого контейнера).

На практике: такой подход позволяет диагностировать сетевые проблемы (слушает ли приложение порт, отвечает ли локально) и процессный статус, не устанавливая никаких дополнительных инструментов в сам production-образ и не раздувая его ради редких случаев отладки. Файловую систему целевого контейнера при этом так просмотреть не получится — для конкретных файлов используют `docker cp <container>:/path ./local-path`.

Частые ошибки: пытаются временно пересобрать и задеплоить debug-версию образа с установленным shell прямо в production ради одной диагностики, что рискованно и медленно; забывают, что `docker cp` работает и для остановленных (но не удалённых) контейнеров, и пытаются искать более сложные пути для простого извлечения файла.

**Пример / кейс**

```
$ docker run -it --rm --network=container:app --pid=container:app busybox sh
/ # ps aux
PID   USER     COMMAND
1     65532    /app
/ # wget -qO- http://localhost:8080/health
{"status":"ok"}
```

Debug-контейнер подтверждает, что приложение внутри target-контейнера `app` отвечает на `/health`, хотя сам образ `app` не содержит ни shell, ни `wget`.

### 97. Чем Docker secrets (в составе Swarm) или аналогичные механизмы отличаются от передачи чувствительных данных через переменные окружения, и в чём риск последних?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Переменные окружения контейнера видны через `docker inspect`, попадают в логи ошибок и иногда в системы мониторинга процессов, а Docker secrets монтируются как файлы в tmpfs только тем сервисам, которым явно разрешён доступ, не отображаясь в обычном `docker inspect` сервиса.

**Разбор**

Как это работает: любая переменная, заданная через `-e`/`environment`, хранится в метаданных контейнера в открытом виде и доступна любому, кто может выполнить `docker inspect` по этому контейнеру, а также наследуется всеми дочерними процессами внутри контейнера. Docker secrets (в режиме Swarm) передаются зашифрованными через Raft log менеджерам кластера и монтируются только в tmpfs конкретных сервисов, которым явно назначен секрет — после остановки сервиса файл секрета исчезает вместе с tmpfs.

На практике: для production-данных (пароли БД, API-ключи) предпочтительнее механизмы, монтирующие секрет как файл, доступный только внутри контейнера и не отображаемый в общих метаданных — это могут быть Docker secrets, внешние secret-менеджеры (Vault, облачные Secrets Manager) с монтированием через volume/init-контейнер, но не обычные переменные окружения.

Частые ошибки: передают пароли БД через `-e DB_PASSWORD=...` и считают это достаточно безопасным, не учитывая, что значение будет видно через `docker inspect` любому, у кого есть доступ к Docker API на хосте; логируют весь набор переменных окружения при старте приложения в целях диагностики, случайно публикуя секреты в логи.

**Пример / кейс**

```
$ docker inspect app --format '{{.Config.Env}}'
[PATH=/usr/bin DB_PASSWORD=SuperSecret123]
```

Пароль БД виден в открытом виде любому, кто может выполнить `docker inspect` для этого контейнера — при использовании secrets такого поля в выводе `inspect` сервиса просто не будет, секрет доступен только изнутри контейнера как файл.

### 98. В чём разница между named volume и tmpfs mount, и когда стоит использовать tmpfs?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Named volume хранится на диске хоста и переживает перезапуск/удаление контейнера, а tmpfs mount существует только в оперативной памяти хоста, никогда не пишется на диск и полностью исчезает при остановке контейнера — подходит для временных чувствительных данных и ускорения операций ввода-вывода.

**Разбор**

Как это работает: tmpfs — это файловая система, полностью размещённая в RAM (и, в зависимости от настроек, swap), поэтому операции чтения/записи в ней заметно быстрее дисковых, но весь объём ограничен доступной памятью и может быть явно лимитирован флагом `size`. Named volume, напротив, задействует постоянное хранилище хоста через выбранный volume-драйвер и гарантирует сохранность данных между перезапусками.

На практике: tmpfs применяют для временных файлов сессий, кэшей, расшифрованных секретов, которые не должны попасть на диск ни при каких обстоятельствах (например, по требованиям безопасности), а также для существенного ускорения I/O-интенсивных временных операций. Named volume остаётся стандартным выбором для всего, что должно сохраняться — данных БД, пользовательских загрузок, персистентных очередей.

Частые ошибки: используют tmpfs для данных, которые критично не потерять (например, принимая её по ошибке за "просто ещё один volume"), и теряют всё при рестарте контейнера или хоста; не ограничивают размер tmpfs явно (`size=`), рискуя исчерпать память хоста при неожиданном росте временных файлов.

**Пример / кейс**

```
$ docker run -d --name cache --tmpfs /app/cache:size=256m,mode=1777 myapp
$ docker restart cache
$ docker exec cache ls /app/cache
# директория пуста — все временные файлы исчезли после перезапуска
```

После перезапуска контейнера содержимое `/app/cache` полностью утрачено, в отличие от того, что произошло бы, если `/app/cache` был бы named volume.

### 99. Пайплайн CI иногда собирает образ, который ведёт себя иначе, чем вчера, хотя Dockerfile не менялся. Какая частая причина связана с тегами базового образа и как её устранить?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

`FROM node:20` (без уточнения патч-версии или digest) указывает на изменяемый тег: издатель образа может опубликовать обновлённую минорную/патч-версию под тем же именем, и новая сборка молча подтянет другое содержимое базового образа — решение — фиксировать базовый образ по digest либо по максимально точному тегу и обновлять его осознанно.

**Разбор**

Как это работает: теги в реестрах (кроме неизменяемого digest) — это просто указатели, которые владелец репозитория может переставить на новый манифест в любой момент; `node:20` на практике означает "последняя опубликованная версия ветки 20.x" и со временем начинает указывать на другой набор слоёв, с другими версиями системных библиотек и npm/node patch-релизом.

На практике: для воспроизводимости сборки закрепляют базовый образ по digest (`FROM node:20@sha256:...`), либо как минимум по максимально точной версии (`node:20.11.1-slim`), и обновляют эту фиксацию сознательно через отдельный процесс (например, автоматический PR от Dependabot/Renovate), который проходит обычный ревью и тестирование, а не подтягивается незаметно при каждой пересборке.

Частые ошибки: закрепляют только major-версию (`node:20`), считая, что этого достаточно для стабильности, и получают "случайные" различия между сборками в разные дни; закрепляют digest один раз и больше никогда не обновляют образ, из-за чего со временем накапливается разрыв с патчами безопасности — фиксация по digest требует отдельного процесса регулярного обновления.

**Пример / кейс**

```dockerfile
# Нестабильно во времени: один и тот же тег = разное содержимое в разные дни
FROM node:20

# Воспроизводимо: зафиксированный digest, обновляется явным PR
FROM node:20.11.1-slim@sha256:1a2b3c4d5e6f...
```

`docker build` с первым вариантом в разные дни может давать образы с разным `IMAGE ID` даже при идентичном Dockerfile и коде приложения; со вторым вариантом содержимое базового слоя гарантированно одно и то же, пока явно не обновлён digest в коде.

### 100. Как диагностировать, что контейнер не может установить соединение с внешним сервисом, если проблема не в самом приложении, а в сетевой настройке Docker (DNS, firewall, MTU)?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Middle

**Короткий ответ**

Диагностику ведут последовательно: сначала проверяют DNS-резолв внутри контейнера и конфигурацию встроенного Docker DNS (`127.0.0.11`), затем правила iptables на хосте (цепочка `DOCKER`), и отдельно — параметр MTU сети, который часто является причиной обрывов соединений именно в overlay/VPN-окружениях.

**Разбор**

Как это работает: контейнер по умолчанию использует встроенный DNS-резолвер Docker, который проксирует запросы либо к DNS-серверам хоста, либо резолвит имена других контейнеров в той же пользовательской сети; сбой на этом уровне проявляется как ошибка резолва конкретного имени при рабочей сети в целом. Отдельно от DNS, Docker управляет сетевой связностью через динамически создаваемые правила iptables (цепочки `DOCKER`, `DOCKER-USER` и др.) — их конфликт с другими правилами файрвола хоста может блокировать исходящий или входящий трафик контейнера. Третий слой — несовпадение MTU между виртуальным сетевым интерфейсом контейнера/сети Docker и реальным сетевым путём (особенно при VPN или overlay-сетях между хостами), что проявляется как успешное установление соединения, но обрывы на крупных пакетах.

На практике: диагностику начинают с внутренней проверки (`nslookup`/`getent hosts`, `curl -v`), затем переходят на хост (`iptables -L -n`, `tcpdump` на соответствующем bridge-интерфейсе), и только затем проверяют MTU (`ip link show docker0`, тестовые пакеты большого размера через `ping -M do -s <size>`).

Частые ошибки: сразу подозревают код приложения при сетевых проблемах, хотя симптом ("connection refused"/таймаут только для определённых размеров пакетов") явно сетевой; меняют правила iptables вручную без понимания, что Docker сам управляет значительной частью своих цепочек и может перезаписать изменения при перезапуске демона.

**Пример / кейс**

```
$ docker exec -it app sh -c "cat /etc/resolv.conf; nslookup api.example.com"
nameserver 127.0.0.11
Name:      api.example.com
Address 1: 93.184.216.34

$ docker exec -it app sh -c "curl -v --max-time 5 https://api.example.com"
* Connected to api.example.com (93.184.216.34) port 443
* TLS handshake failed: timeout
```

DNS резолв успешен, но TLS handshake зависает — это указывает на проблему ниже DNS, вероятно на уровне firewall/MTU, а не в самом приложении или его конфигурации имени хоста.

### 101. Как спроектировать стратегию реестров образов для организации с несколькими командами и регионами: один глобальный registry, несколько региональных с репликацией, или managed-сервис облачного провайдера? Единственно верного решения здесь нет.

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Senior

**Короткий ответ**

Выбор зависит от требований к latency `pull` в разных регионах, ограничений по размещению данных (data residency), бюджета на managed-сервис против операционных затрат на self-hosted реестр и критичности доступности registry для процесса деплоя; единственно верного ответа нет — решение нужно обсуждать с учётом конкретных критериев организации.

**Разбор**

Как это работает: любой вариант реализует одну и ту же базовую функцию (хранение и раздача слоёв образов по тегам/digest), различия — в операционной модели. Managed-реестр облачного провайдера (ECR, GCR, ACR) снимает с команды задачи HA, патчинга и backup самого реестра, но привязывает к конкретному облаку и тарифицирует трафик/хранение по модели провайдера. Self-hosted решение (например, Harbor) даёт полный контроль, мультиоблачность и возможность репликации между регионами на своих условиях, но требует отдельной команды/процесса поддержки его отказоустойчивости, обновлений безопасности и backup'ов хранилища слоёв.

На практике: для глобально распределённых команд часто комбинируют подходы — один "источник правды" (центральный реестр с строгим контролем доступа и сканированием) и региональные read-through кэши/реплики ближе к кластерам, чтобы деплой не зависел от сетевой доступности центрального реестра при каждом `pull`.

Частые ошибки: выбирают единственный централизованный реестр без региональных реплик для глобально распределённой инфраструктуры, из-за чего деплой в дальнем регионе зависит от сетевого пути через весь мир; либо наоборот — разворачивают независимые нерепликруемые реестры в каждом регионе без единого источника правды, из-за чего теряется контроль версий и аудит.

Компромисс: managed-сервис снижает операционную нагрузку и ускоряет запуск, но увеличивает зависимость от провайдера и может быть дороже при большом объёме трафика между регионами; self-hosted с репликацией даёт контроль и независимость от облака, но требует инвестиций в HA, мониторинг и обновления самого registry — решение нужно принимать на основе реальных SLA по деплою, бюджета и готовности команды нести операционную ответственность, а не по умолчанию.

**Пример / кейс**

```yaml
# Harbor replication policy (пример): репликация образов
# из центрального registry в региональный read-only кэш
replication:
  name: eu-to-apac
  src_registry: harbor-eu.internal
  dest_registry: harbor-apac.internal
  trigger: event_based
  filters:
    - type: tag
      value: "release-*"
```

Нужно явно продумать и протестировать сценарий: что произойдёт с деплоями в APAC-регионе, если центральный `harbor-eu.internal` временно недоступен — будет ли региональный кэш содержать актуальные образы, или деплой заблокируется до восстановления связи.

### 102. Как выстроить безопасность цепочки поставки образов (supply chain): подписание образов, SBOM, admission-контроль недоверенных образов — какие компоненты обязательны, а какие опциональны в зависимости от зрелости организации?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Senior

**Короткий ответ**

Единого обязательного набора нет: минимальная база — это pull образов только из доверенных реестров по digest и генерация SBOM в CI; подписание образов (например, cosign/Notation) и admission-политики, блокирующие неподписанные/непроверенные образы, добавляются по мере роста требований безопасности и compliance организации.

**Разбор**

Как это работает: SBOM (Software Bill of Materials) — машиночитаемый список всех пакетов и версий внутри образа, который можно сверять с базами уязвимостей даже после публикации образа, не пересканируя его заново каждый раз вручную. Подписание образов криптографически связывает конкретный digest с издателем — admission-контроллер в оркестраторе может проверять подпись перед запуском контейнера и отклонять образы без валидной подписи от доверенного издателя.

На практике: внедрение обычно идёт поэтапно: сначала фиксация по digest и базовое сканирование на CVE в CI, затем генерация и хранение SBOM для каждой сборки, и только на зрелом этапе — подписание и enforcement-режим admission-политики (сначала в режиме audit/dry-run, чтобы не заблокировать легитимные деплои из-за ошибок в самой политике).

Частые ошибки: включают enforcement-политику подписания сразу во всех окружениях без предварительного audit-периода, что приводит к массовым сбоям деплоя из-за образов, собранных старыми пайплайнами без подписи; считают наличие SBOM равноценным гарантии безопасности, хотя SBOM — это только инвентарь, а не автоматическая защита без процесса регулярной проверки его на уязвимости.

Компромисс: полный набор supply chain security (подписание + SBOM + enforcement admission policy) даёт сильные гарантии целостности и происхождения образов, но увеличивает сложность пайплайнов, время сборки и риск заблокировать легитимный деплой при сбое инфраструктуры верификации (например, недоступности key management сервиса); решение о глубине внедрения и скорости перехода от audit к enforce зависит от требований compliance, зрелости команды и допустимого риска блокировки релизов — здесь нет единственно правильного баланса.

**Пример / кейс**

```
$ cosign sign --key cosign.key registry.example.com/team/app@sha256:abcd...
$ cosign verify --key cosign.pub registry.example.com/team/app@sha256:abcd...

Verification for registry.example.com/team/app@sha256:abcd... --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - The signatures were verified against the specified public key
```

Admission-контроллер кластера, настроенный на обязательную проверку подписи, должен заблокировать запуск любого образа, для которого `cosign verify` не проходит — этот сценарий стоит явно протестировать в режиме audit перед включением строгого enforcement на проде.

### 103. Как спроектировать политику тегирования и retention в образном реестре при росте числа образов и затрат на хранение, не теряя возможность откатиться на старую версию?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Senior

**Короткий ответ**

Универсальной схемы нет: как правило комбинируют immutable-теги (например, git SHA или семантическая версия) для релизных сборок с политикой автоматического удаления непромотированных/временных тегов (CI-сборки, dev-ветки) по возрасту, и отдельно — явно согласованный срок хранения релизных тегов, достаточный для возможных откатов.

**Разбор**

Как это работает: retention/garbage collection политика реестра обычно оперирует правилами вида "удалить образы старше N дней, не соответствующие шаблону тега `release-*`" или "оставить только последние K тегов для репозитория X". Такая политика безопасна для временных артефактов (сборки для feature-веток, ночные CI-образы), но рискованна для релизных образов, если не учитывает, какие окружения в принципе могут откатываться на старые версии и на какой горизонт времени.

На практике: разделяют репозитории или префиксы тегов на категории с разной политикой — например, `myapp:ci-<sha>` с retention 7-14 дней, и `myapp:v1.4.2` (соответствует релизу) с retention на порядок дольше или вовсе без автоматического удаления, с явным процессом архивации в холодное хранилище после истечения активного окна.

Частые ошибки: применяют одинаковую агрессивную retention-политику ко всем тегам без разделения на временные и релизные, из-за чего случайно удаляется образ, нужный для hotfix-откату редко обновляемого окружения (например, у отдельного крупного клиента на устаревшей версии); не учитывают, что удаление тега без удаления самого слоя (если на него ссылается другой тег) не освобождает реально много места — нужно понимать модель дедупликации конкретного реестра.

Компромисс: агрессивная retention экономит расходы на хранение, но увеличивает риск потери возможности откатиться на нужную версию в редком, но критичном сценарии; консервативная retention (хранить почти всё) снижает этот риск, но линейно наращивает расходы на storage со временем — правильный баланс зависит от того, как часто в организации реально происходят откаты на образы старше условных 30-90 дней, и это стоит оценивать по фактическим инцидентам, а не произвольно.

**Пример / кейс**

```yaml
# Пример политики жизненного цикла (концептуально, под Harbor/ECR-подобный реестр)
rules:
  - name: keep-releases
    tag_pattern: "release-*"
    action: keep
    retention: unlimited
  - name: clean-ci-builds
    tag_pattern: "ci-*"
    action: delete
    older_than_days: 14
```

Перед включением такой политики в production реестре стоит сначала прогнать её в режиме "dry-run"/отчёта без реального удаления и сверить список образов, которые будут удалены, с текущими развёрнутыми версиями во всех окружениях, включая редко обновляемые.

### 104. При высокой плотности контейнеров на хосте нужно выбрать сетевой режим (пользовательские bridge-сети, host networking, overlay для нескольких хостов) с учётом требований к производительности и изоляции. Единственно верного ответа здесь нет — как подойти к выбору?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Senior

**Короткий ответ**

Host networking даёт минимальные накладные расходы на пакет, но ломает изоляцию портов между контейнерами и усложняет multi-tenancy; user-defined bridge изолирует сервисы друг от друга при умеренном NAT-оверхеде; overlay-сети (для связи между хостами, например в Swarm) добавляют ещё больший оверхед ради мультихостовой связности — выбор зависит от конкретных требований к latency/throughput и допустимой сложности, а не от общей рекомендации.

**Разбор**

Как это работает: каждый дополнительный уровень сетевой абстракции (NAT в bridge, VXLAN-инкапсуляция в overlay) добавляет вычислительные накладные расходы на обработку каждого пакета и потенциально увеличивает latency, но в обмен даёт изоляцию адресного пространства и упрощает маршрутизацию между множеством контейнеров/хостов без конфликтов портов.

На практике: для latency-критичных нагрузок (например, высокочастотная обработка сообщений, где каждая микросекунда на пакет важна) host networking может быть осознанным выбором, принятым с пониманием, что контейнеры такого сервиса не могут использовать одинаковые порты на одном хосте и теряют сетевую изоляцию друг от друга. Для большинства обычных сервисов умеренный NAT-оверхед user-defined bridge незначим по сравнению с выгодой простой изоляции и многотенантности на одном хосте.

Частые ошибки: переходят на host networking "для производительности" без измерения фактической разницы в своей нагрузке, теряя изоляцию портов без реальной необходимости; выбирают overlay-сеть для связи контейнеров на одном хосте, хотя там достаточно обычного bridge, добавляя ненужный оверхед инкапсуляции.

Компромисс: нет универсально "правильного" сетевого режима — решение нужно принимать на основе измеренных метрик (throughput, latency, jitter) именно для профиля нагрузки конкретного сервиса, числа тенантов, которым требуется изоляция на одном хосте, и операционной сложности поддержки выбранного режима; при неопределённости стоит начинать с user-defined bridge как безопасного базового варианта и переходить на host/overlay только при подтверждённой измерениями необходимости.

**Пример / кейс**

```
# Сравнение throughput между bridge и host networking для одной и той же нагрузки
$ docker run --network bridge --rm networkstatic/iperf3 -c target_bridge
$ docker run --network host --rm networkstatic/iperf3 -c target_host
```

Перед принятием решения стоит провести такой тест именно с профилем нагрузки целевого приложения (размер пакетов, частота соединений), а не ориентироваться на общие цифры из документации, так как разница заметна по-разному в зависимости от паттерна трафика.

### 105. Как распределять CPU и память между контейнерами на одном хосте, чтобы избежать noisy neighbor эффекта, учитывая разницу между cgroups v1 и v2 в поведении лимитов? Однозначного рецепта нет.

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Senior

**Короткий ответ**

Нет единственно верной схемы лимитов: нужно сочетать `--cpus`/`--memory` с мониторингом фактического throttling и OOM-событий, а переход на cgroups v2 (единая иерархия контроллеров, `cpu.max` вместо раздельных quota/period, встроенная поддержка PSI-метрик) меняет точность и гранулярность контроля по сравнению с cgroups v1.

**Разбор**

Как это работает: cgroups v1 исторически имел раздельные, не всегда согласованные между собой иерархии для разных контроллеров (cpu, memory, blkio), что иногда приводило к неожиданным взаимодействиям при сложных схемах лимитирования; cgroups v2 унифицирует иерархию и добавляет PSI (Pressure Stall Information) — метрики, показывающие, какую долю времени процессы реально простаивают из-за нехватки CPU/памяти/IO, что даёт более точный сигнал о реальном дефиците ресурсов, чем просто процент использования.

На практике: калибровка лимитов должна основываться на профилировании фактических пиковых паттернов нагрузки приложения (а не фиксированных "дефолтных" значений), с последующим мониторингом throttling (`nr_throttled`) и PSI-метрик в проде, и итеративной донастройкой; переход на cgroups v2 (где поддерживается дистрибутивом и версией Docker) даёт более точные инструменты диагностики noisy neighbor, но требует проверки совместимости со всем используемым стеком мониторинга и оркестрации.

Частые ошибки: копируют лимиты ресурсов "по шаблону" из документации или соседнего проекта без профилирования конкретного приложения, получая либо постоянный throttling легитимно "взрывной" нагрузки, либо, наоборот, недостаточную защиту соседних контейнеров; смешивают интерпретацию метрик cgroups v1 и v2 при миграции, что приводит к неверным выводам о степени ограничения ресурсов.

Компромисс: слишком жёсткие лимиты защищают соседей по хосту, но деградируют легитимно пульсирующую нагрузку того же сервиса (throttling в моменты пиков); слишком мягкие лимиты снижают риск self-throttling, но допускают noisy neighbor, способный повлиять на остальные контейнеры хоста; правильная точка баланса — результат итеративного профилирования под реальный трафик и мониторинга PSI/throttling, а не фиксированное число "по умолчанию", и она может со временем меняться вместе с профилем нагрузки.

**Пример / кейс**

```
$ cat /sys/fs/cgroup/system.slice/docker-<id>.scope/cpu.pressure
some avg10=12.50 avg60=8.30 avg300=4.10 total=98765432
full avg10=2.10  avg60=1.50 avg300=0.80 total=12345678
```

Высокое значение `avg10` в строке `some` говорит, что процессы контейнера заметную часть времени (12.5% за последние 10 секунд) простаивают из-за нехватки CPU — это более точный сигнал для пересмотра лимита, чем просто средний `CPU%` из `docker stats`.

### 106. Данные в named volumes на одном Docker-хосте не защищены от отказа диска/хоста. Как спроектировать резервное копирование и восстановление (DR) для контейнерных данных, и какие варианты существуют?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Senior

**Короткий ответ**

Единого решения нет: варианты — от периодических файловых снапшотов volume (например, через временный контейнер с `tar`) до репликации на уровне самого приложения/СУБД, либо использования внешнего распределённого хранилища (сетевое хранилище, объектное хранилище, блочное хранилище облака) со встроенными снапшотами — выбор зависит от требований RPO/RTO и объёма данных.

**Разбор**

Как это работает: простой файловый backup volume достаточно сделать временным контейнером, который монтирует тот же volume в режиме только для чтения и упаковывает его содержимое в архив, сохраняемый вне хоста. Для баз данных такой подход без координации с самим приложением (например, без `pg_dump`/аналогичного механизма "горячего" снапшота или краткой паузы записи) может дать несогласованный на уровне транзакций снимок, если файлы менялись во время архивации. Внешние распределённые хранилища (сетевой блочный диск со снапшотами на уровне облака, Ceph и т.п.) решают эту проблему на уровне инфраструктуры, но добавляют сетевую зависимость и обычно более высокую latency по сравнению с локальным диском хоста.

На практике: для stateful-сервисов в Docker нужно явно выбрать и зафиксировать целевые RPO (сколько данных допустимо потерять) и RTO (сколько времени допустимо на восстановление), и подобрать механизм backup исходя из этих цифр — для некритичных данных периодический файловый снапшот может быть достаточен, для БД с жёсткими требованиями обычно нужен специализированный механизм резервного копирования самой СУБД плюс репликация.

Частые ошибки: считают репликацию (если она настроена на уровне приложения) полноценной заменой бэкапа — репликация защищает от отказа одного узла, но не от логической ошибки (например, ошибочного `DELETE` или повреждения данных), которая мгновенно реплицируется на все узлы; никогда не тестируют процедуру восстановления из backup, обнаруживая проблему с самим архивом только в момент реального инцидента.

Компромисс: простые файловые бэкапы дёшевы и просты в реализации, но рискуют несогласованностью данных и требуют остановки записи на момент снятия снимка для полной надёжности; внешние распределённые хранилища со встроенными снапшотами дают более надёжную консистентность и HA, но повышают сложность инфраструктуры, стоимость и сетевую зависимость — решение нужно принимать по фактическим требованиям RPO/RTO конкретного сервиса, а не универсально для всей инфраструктуры.

**Пример / кейс**

```
# Снапшот named volume во внешний архив через временный контейнер
$ docker run --rm -v pgdata:/data:ro -v /backup:/backup \
    busybox tar czf /backup/pgdata-$(date +%F).tar.gz -C /data .

# Критично: перед восстановлением на проде нужно
# явно проверить окружение, наличие свежего бэкапа и план отката
$ docker run --rm -v pgdata_restored:/data -v /backup:/backup \
    busybox tar xzf /backup/pgdata-2024-05-01.tar.gz -C /data
```

После восстановления обязательно нужно поднять тестовый контейнер с СУБД на `pgdata_restored` и проверить целостность данных запросом, а не считать восстановление успешным только по коду выхода команды `tar`.

### 107. Команда рассматривает миграцию с Docker Engine на containerd/nerdctl или Podman в части рабочих нагрузок. На что нужно обратить внимание при принятии решения, если единственно верного ответа тут нет?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Senior

**Короткий ответ**

Нужно оценить совместимость существующих Dockerfile/compose-файлов и привычек команды с новым CLI, зависимость CI/CD от docker-специфичных API/сокета, требования к rootless-запуску (сильная сторона Podman) и поддержку нужных сетевых/storage-плагинов в целевом runtime — универсального ответа, что "лучше", здесь нет.

**Разбор**

Как это работает: containerd и Podman реализуют во многом совместимый с Docker интерфейс для базовых операций (сборка, запуск, управление образами по OCI-стандарту), но отличаются архитектурно. Podman по умолчанию не требует постоянно работающего привилегированного daemon (в отличие от классического Docker Engine) и изначально поддерживает полностью rootless-запуск контейнеров, что снижает поверхность атаки. containerd же часто используют не как замену Docker CLI напрямую, а как container runtime уровня ниже, на котором и так работает Docker Engine и Kubernetes (через CRI) — переход к containerd/nerdctl обычно означает отказ от daemon-слоя Docker в пользу более тонкой интеграции с оркестратором.

На практике: миграция требует аудита всей цепочки инструментов — не только самого `docker run`, но и build-системы (некоторые buildkit-фичи, volume-плагины, сетевые драйверы могут отличаться по доступности), CI-раннеров (которые могут напрямую зависеть от docker socket), и привычек разработчиков, использующих `docker-compose` (для которого у Podman есть частично совместимый, но не идентичный аналог).

Частые ошибки: мигрируют только часть окружений (например, только CI) без полной картины, из-за чего команда поддерживает два параллельных стека инструментов с разным поведением edge-кейсов; ожидают 100% поведенческой идентичности с Docker CLI и сталкиваются с неожиданными отличиями в деталях (networking defaults, обработка volume-плагинов) уже в проде.

Компромисс: переход на containerd/Podman может снизить площадь атаки (особенно при отказе от постоянно работающего привилегированного daemon) и упростить интеграцию с Kubernetes, но ломает привычные рабочие процессы и требует переобучения команды и миграции сопутствующих инструментов; частичная миграция снижает немедленный риск, но увеличивает долгосрочную сложность поддержки двух параллельных экосистем — решение должно явно взвешивать выигрыш в безопасности/архитектуре против стоимости переходного периода для конкретной команды.

**Пример / кейс**

```
# Podman: запуск того же контейнера rootless, без daemon
$ podman run -d --name web -p 8080:80 nginx:1.25

# Для CI, ожидающего docker-совместимый socket:
$ podman system service --time=0 unix:///run/user/1000/podman.sock &
export DOCKER_HOST=unix:///run/user/1000/podman.sock
```

Перед полной миграцией CI стоит явно протестировать весь существующий пайплайн именно через такой совместимый socket, а не предполагать идентичное поведение всех используемых docker-команд и плагинов.

### 108. Как построить multi-environment стратегию сборки образов (build once, promote everywhere), чтобы один и тот же артефакт шёл от dev до prod, и как при этом безопасно передавать build-time секреты без их утечки в слои образа?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Senior

**Короткий ответ**

Образ нужно собирать один раз, а окружение-специфичную конфигурацию внедрять при запуске (через переменные окружения, конфигурационные файлы/ConfigMap), а не пересобирать образ для каждого окружения; build-time секреты (например, токен приватного npm registry) передавать через механизм временного монтирования секрета в BuildKit (`--secret`), а не через `ARG`, значения которого остаются в истории слоёв образа.

**Разбор**

Как это работает: `ARG`, даже если не зафиксирован явной инструкцией `ENV`, всё равно виден в метаданных промежуточных слоёв образа и может быть восстановлен через `docker history` с флагом, показывающим полные команды, либо через анализ самого манифеста — то есть секрет, переданный через `ARG`, нельзя считать надёжно удалённым из артефакта. BuildKit secret mount (`RUN --mount=type=secret,id=...`) предоставляет секрет процессу сборки только во время выполнения конкретной `RUN`-инструкции, через файл, который не фиксируется в итоговом слое.

На практике: "build once, promote everywhere" подразумевает, что один и тот же digest образа тестируется в dev/staging и затем продвигается (promote) в prod без пересборки — это даёт сильную гарантию, что протестированный артефакт и есть то, что работает в проде; вся разница между окружениями должна быть вынесена за пределы образа, в runtime-конфигурацию.

Частые ошибки: пересобирают образ отдельно для каждого окружения с разными переменными, "зашитыми" через `ARG`/`ENV` на этапе сборки, теряя гарантию, что в проде работает именно тот артефакт, который тестировался в staging; передают секреты сборки через `ARG`, считая, что `.dockerignore` или удаление файла после `RUN` решает проблему — метаданные слоя всё равно могут хранить переданное значение.

Компромисс: строгий "build once promote" даёт сильную трассируемость и гарантию идентичности артефакта между окружениями, но требует, чтобы абсолютно всё окружение-специфичное (включая иногда и build-time фичи, которые легаси-приложения ожидают увидеть на этапе компиляции) было вынесено в runtime — для некоторых унаследованных систем это может требовать существенного рефакторинга; это архитектурное решение команды, и в переходный период возможен гибридный подход с постепенным выносом конфигурации из build-time в runtime.

**Пример / кейс**

```dockerfile
# syntax=docker/dockerfile:1.4
RUN --mount=type=secret,id=npmrc \
    cp /run/secrets/npmrc /root/.npmrc && \
    npm install && \
    rm /root/.npmrc
```

```
$ DOCKER_BUILDKIT=1 docker build --secret id=npmrc,src=.npmrc -t myapp:1.0 .
$ docker history myapp:1.0 --no-trunc | grep -i npmrc
# секрет не должен обнаруживаться в истории слоёв
```

Проверка `docker history` после сборки с `--secret` подтверждает, что содержимое `.npmrc` не зафиксировано ни в одном слое итогового образа, в отличие от передачи того же значения через `ARG`.

### 109. Нужно диагностировать проблему производительности в production-контейнере (высокая латентность) без влияния на обслуживание трафика и без установки дополнительных инструментов внутрь минимального/distroless образа. Какие подходы возможны и какие у них издержки?

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Senior

**Короткий ответ**

Единственного правильного инструмента нет: можно подключать временный debug-контейнер с общими namespaces к целевому, использовать `nsenter` с хоста для захода прямо в namespaces процесса, либо заранее внедрённую систему continuous profiling (например, на основе eBPF), если экстренная точечная отладка на проде недопустима в принципе.

**Разбор**

Как это работает: debug-контейнер, запущенный с `--network=container:<target>` и `--pid=container:<target>`, получает видимость процессов и сетевого стека целевого контейнера без его остановки, но не имеет доступа к его файловой системе, если она не смонтирована отдельно. `nsenter -t <pid> -n ...`, выполненный прямо на хосте с правами root, даёт более полный доступ (включая возможность работать с инструментами хоста напрямую в контексте namespaces процесса), но требует root-доступа к самому хосту, что расширяет поверхность риска при ошибке оператора. Continuous profiling системы (например, eBPF-based профилировщики) собирают данные постоянно в фоне с относительно низким оверхедом, устраняя необходимость экстренной точечной диагностики, но требуют заранее внедрённой инфраструктуры и добавляют постоянную (хоть и небольшую) нагрузку на все контейнеры, а не только проблемный.

На практике: выбор инструмента зависит от того, насколько критичен сервис (можно ли рискнуть доступом root на хосте в моменте инцидента), насколько часто повторяются подобные проблемы (разово — debug-контейнер достаточен, систематически — стоит внедрить постоянный профилировщик) и от зрелости observability-практик команды.

Частые ошибки: используют `nsenter` с хоста как "универсальный быстрый способ" без оценки риска повышенных прав в момент инцидента на критичном проде; откладывают внедрение continuous profiling до тех пор, пока проблема производительности не стала хронической, теряя время на повторяющуюся экстренную отладку вместо системного решения.

Компромисс: debug-контейнер с shared namespaces безопаснее по правам доступа, но ограничен в возможностях (нет файловой системы приложения); `nsenter` с хоста мощнее, но требует root и повышает риск человеческой ошибки прямо на проде; continuous profiling убирает экстренность, но добавляет постоянный операционный оверхед и сложность поддержки самой системы профилирования — правильный выбор зависит от критичности сервиса, частоты повторения проблемы и зрелости команды, и его стоит явно обсуждать, а не предполагать единственно верный инструмент.

**Пример / кейс**

```
# Доступ к сетевому стеку процесса контейнера прямо с хоста,
# без установки инструментов внутрь самого образа
$ PID=$(docker inspect -f '{{.State.Pid}}' app)
$ sudo nsenter -t $PID -n ss -tlnp
State   Recv-Q  Send-Q  Local Address:Port   Process
LISTEN  0       128     0.0.0.0:8080         users:(("app",pid=12345,fd=9))
```

Перед таким вмешательством на production-хосте стоит явно зафиксировать, что действие выполняется под наблюдением (например, в рамках открытого инцидента) и не меняет состояние процесса, только считывает информацию.

### 110. При масштабировании инфраструктуры расходы на хранение образов и слоёв в registry заметно выросли. Как подойти к управлению этой статьёй расходов без потери возможности откатов и аудита? Однозначного решения здесь нет.

**Направление:** DevOps Engineer
**Тема:** Контейнеры и Docker: образы, слои, Dockerfile, сети и тома контейнеров, реестры образов, ограничение ресурсов, безопасность образов, отладка контейнеров
**Уровень:** Senior

**Короткий ответ**

Нет единственного решения: обычно сочетают дедупликацию за счёт единых базовых образов между сервисами, garbage collection непромотированных/временных тегов, перенос редко используемых архивных образов в более дешёвое холодное хранилище, и явный аудит того, какие образы реально нужны по требованиям compliance, а не только по текущему бюджету.

**Разбор**

Как это работает: большая часть затрат на хранение образов в реестре обычно приходится не на уникальный код приложений, а на повторяющиеся базовые слои (системные библиотеки, runtime языка), если разные команды используют разные версии или источники базовых образов — унификация базовых образов снижает количество уникальных крупных слоёв, которые реестр должен хранить отдельно. Garbage collection непромотированных тегов (временных CI-сборок, dev-веток) убирает заведомо ненужный со временем объём. Холодное хранилище (например, объектное хранилище с более низким классом доступности/стоимости) подходит для образов, которые должны формально сохраняться для аудита/compliance, но практически никогда не используются для реального `pull`.

На практике: перед любой оптимизацией стоимости нужно провести инвентаризацию — какие образы и теги реально тянутся за последние N месяцев (метрики реестра обычно это показывают), какие обязаны храниться по требованиям безопасности/compliance независимо от частоты использования, и только после этого проектировать многоуровневую политику хранения.

Частые ошибки: сокращают расходы агрессивной единой retention-политикой без разделения на категории, рискуя удалить образ, нужный аудитору или для восстановления легаси-версии у конкретного клиента; переносят в холодное хранилище образы, для которых время восстановления (retrieval time) холодного класса хранения неприемлемо долго в случае реального экстренного rollback.

Компромисс: агрессивная очистка и перенос в холодное хранилище снижают текущие расходы, но увеличивают время восстановления редко используемых образов и риск случайно затронуть что-то, нужное для compliance; консервативное хранение всего "как есть" предсказуемо по доступности, но затраты растут линейно вместе с числом образов — правильный баланс между "горячими" релизными образами (быстрый доступ, более долгий стандартный retention) и "холодными" архивными (дешевле, дольше восстановление) зависит от фактических требований аудита и допустимого RTO при редких откатах, и должен быть явно согласован с владельцами compliance, а не выбран только по статье расходов.

**Пример / кейс**

```yaml
# Пример многоуровневой lifecycle-политики (концептуально)
rules:
  - name: archive-old-non-release
    tag_pattern: "*"
    exclude_pattern: "release-*"
    action: move_to_cold_storage
    older_than_days: 90
  - name: delete-unreferenced
    action: delete
    condition: "no_tag_references"
    older_than_days: 180
```

Перед применением такой политики стоит явно сверить список кандидатов на перенос/удаление с перечнем образов, за которые отвечает команда compliance, и зафиксировать согласованный минимальный срок хранения релизных образов отдельно от общей политики экономии места.
