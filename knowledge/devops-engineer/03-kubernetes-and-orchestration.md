### 111. Что такое Pod в Kubernetes и почему это минимальная единица развёртывания, а не отдельный контейнер?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Pod — это группа из одного или нескольких контейнеров, которые разделяют сетевое пространство имён (один IP, один localhost) и могут разделять volume; Kubernetes планирует, масштабирует и перезапускает именно Pod, а не отдельный контейнер.

**Разбор**

Как это работает: контейнеры внутри одного Pod запускаются в общем network namespace и, опционально, в общих volume, что позволяет им общаться через localhost и обмениваться файлами. Kubernetes управляет жизненным циклом Pod целиком: планирование на узел, перезапуск контейнеров при сбое, остановка происходят на уровне Pod.

На практике: чаще всего Pod содержит один основной контейнер приложения; дополнительные контейнеры (sidecar, init) добавляют, когда нужна тесная связь по сети или диску — например, сборщик логов рядом с приложением. Для масштабирования и обновлений Pod почти никогда не создают напрямую, а используют Deployment или StatefulSet, которые управляют набором Pod через ReplicaSet.

Частые ошибки: путать термины "контейнер" и "Pod" как взаимозаменяемые; пытаться создавать Pod вручную для прод-нагрузки вместо Deployment, из-за чего при сбое узла Pod не пересоздаётся автоматически; не учитывать, что все контейнеры Pod всегда планируются на один и тот же узел.

**Пример / кейс**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: demo-pod
spec:
  containers:
    - name: app
      image: nginx:1.25
      ports:
        - containerPort: 80
```

После `kubectl apply -f pod.yaml` команда `kubectl get pod demo-pod -o wide` покажет один под с одним IP-адресом; `kubectl exec -it demo-pod -- hostname -i` подтвердит, что сетевой стек общий для всех контейнеров пода.

### 112. Чем Deployment отличается от создания Pod напрямую и зачем он нужен?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Deployment — это декларативный контроллер, который через ReplicaSet поддерживает заданное число реплик Pod, пересоздаёт их при сбоях и управляет обновлениями версии приложения; одиночный Pod такого самовосстановления не имеет.

**Разбор**

Как это работает: Deployment описывает желаемое состояние (образ, число реплик, стратегию обновления), а контроллер в control plane постоянно сверяет фактическое состояние с желаемым и создаёт/удаляет Pod через ReplicaSet, чтобы их совпасть.

На практике: Deployment используют для stateless-приложений, которым не важны порядок запуска и устойчивые идентификаторы. Обновление образа через `kubectl set image` или изменение манифеста запускает rolling update по заданной стратегии, а при проблеме можно откатиться командой `kubectl rollout undo`.

Частые ошибки: создавать "голый" Pod в проде и удивляться, что после падения узла он не восстанавливается; редактировать Pod, созданный Deployment'ом, напрямую — изменения будут перезаписаны контроллером при следующей сверке состояния; не указывать `resources` и стратегию обновления, полагаясь на значения по умолчанию.

**Пример / кейс**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: nginx:1.25
```

`kubectl get rs,pods -l app=web` покажет один ReplicaSet и три Pod; если удалить один Pod вручную (`kubectl delete pod <name>`), Deployment пересоздаст его автоматически.

### 113. Какие основные статусы Pod показывает `kubectl get pods` и что каждый из них означает?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Основные статусы: `Pending` (под создан, но ещё не запущен — ждёт планирования или скачивания образа), `Running` (контейнеры запущены), `Succeeded`/`Failed` (контейнеры завершили работу), `CrashLoopBackOff` (контейнер постоянно падает и перезапускается с нарастающей задержкой).

**Разбор**

Как это работает: статус в колонке `STATUS` агрегирует фазу Pod и состояние его контейнеров; например, `CrashLoopBackOff` — это не фаза Pod, а состояние конкретного контейнера, которое Kubernetes отображает на верхнем уровне для удобства диагностики.

На практике: при `Pending` стоит смотреть `kubectl describe pod` на события планировщика (нехватка ресурсов, taints, отсутствие подходящего узла); при `CrashLoopBackOff` — логи и exit code последнего завершения (`kubectl logs --previous`); `ImagePullBackOff` отдельно сигнализирует о проблеме с реестром образов или правами доступа.

Частые ошибки: путать `Pending` с зависанием приложения внутри контейнера — на самом деле контейнер ещё не стартовал; игнорировать `kubectl describe` и пытаться диагностировать проблему только по `kubectl get pods`; считать `Completed` ошибкой, хотя это нормальное завершение для Job.

**Пример / кейс**

```
NAME         READY   STATUS             RESTARTS   AGE
web-7f9c8    0/1     CrashLoopBackOff   5          3m
web-7f9c9    1/1     Running            0          3m
```

`kubectl describe pod web-7f9c8` покажет секцию `Events` с причиной последнего рестарта и код выхода контейнера, что указывает направление дальнейшей диагностики.

### 114. Что такое ReplicaSet и как он связан с Deployment?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

ReplicaSet — это контроллер, который поддерживает заданное число одинаковых Pod по селектору меток; Deployment не управляет Pod напрямую, а создаёт и переключает ReplicaSet при каждом обновлении шаблона.

**Разбор**

Как это работает: при изменении `template` в Deployment создаётся новый ReplicaSet с новым хэшем версии шаблона, после чего Deployment постепенно переносит реплики со старого ReplicaSet на новый согласно стратегии обновления, оставляя старый ReplicaSet с нулём реплик для возможного отката.

На практике: `kubectl rollout history deployment/<name>` и список ReplicaSet (`kubectl get rs`) позволяют увидеть историю версий; откат (`kubectl rollout undo`) фактически масштабирует предыдущий ReplicaSet обратно вверх, а текущий — вниз.

Частые ошибки: создавать ReplicaSet напрямую вместо Deployment, теряя удобное управление rolling update и историю ревизий; удивляться накоплению старых ReplicaSet с нулевыми репликами — это ожидаемо и регулируется параметром `revisionHistoryLimit`; путать селектор ReplicaSet с метками самого Deployment.

**Пример / кейс**

```
kubectl get rs -l app=web
NAME             DESIRED   CURRENT   READY   AGE
web-5d7c9f9b7    0         0         0       2h
web-6b8d7a6c5    3         3         3       5m
```

Два ReplicaSet с одинаковым селектором `app=web` соответствуют старой и новой версии Deployment; ненулевой `DESIRED` имеет только актуальный ReplicaSet.

### 115. Зачем нужен Service в Kubernetes, если у Pod уже есть IP-адрес?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Service даёт стабильный сетевой адрес (имя и/или виртуальный IP) и балансировку нагрузки для группы Pod, чьи IP-адреса меняются при каждом пересоздании — без Service клиентам пришлось бы вручную отслеживать актуальные IP подов.

**Разбор**

Как это работает: Service выбирает Pod по `selector` с метками и формирует список endpoint'ов (объект Endpoints/EndpointSlice), на который kube-proxy настраивает правила перенаправления трафика (iptables или IPVS) на уровне узла; DNS внутри кластера (CoreDNS) резолвит имя Service в его ClusterIP.

На практике: приложения обращаются к другим сервисам по доменному имени вида `service-name.namespace.svc.cluster.local`, а не по IP конкретного Pod; при масштабировании или пересоздании Pod список endpoint'ов обновляется автоматически, и клиенту не нужно ничего менять.

Частые ошибки: обращаться к Pod напрямую по IP в коде приложения; забывать, что Service балансирует только между Pod, у которых есть хотя бы один прошедший readiness probe; несовпадение меток в `selector` Service и `labels` в шаблоне Pod — самая частая причина "сервис не находит под".

**Пример / кейс**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector: { app: web }
  ports:
    - port: 80
      targetPort: 8080
```

`kubectl get endpoints web` должен показать список IP:порт реальных подов; если список пуст, в первую очередь нужно сверить `selector` сервиса и `labels` подов.

### 116. В чём разница между типами Service ClusterIP, NodePort и LoadBalancer?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

`ClusterIP` (по умолчанию) доступен только внутри кластера; `NodePort` дополнительно открывает один и тот же порт на всех узлах кластера наружу; `LoadBalancer` запрашивает у облачного провайдера внешний балансировщик, который направляет трафик на NodePort.

**Разбор**

Как это работает: `ClusterIP` создаёт виртуальный IP, маршрутизируемый только внутри кластерной сети. `NodePort` включает в себя `ClusterIP` и дополнительно резервирует порт (по умолчанию из диапазона 30000–32767) на каждом узле, перенаправляя внешний трафик на сервис. `LoadBalancer` — надстройка над `NodePort`: облачный контроллер создаёт внешний балансировщик (например, AWS ELB), который слушает публичный адрес и шлёт трафик на NodePort узлов.

На практике: `ClusterIP` используют для внутренних сервисов (базы данных, внутренние API); `NodePort` — редко напрямую, чаще как механизм для Ingress-контроллера или в кластерах без облачного балансировщика (bare-metal); `LoadBalancer` — для публичного входа в облаке, но каждый такой сервис обычно создаёт отдельный платный балансировщик у провайдера.

Частые ошибки: создавать `LoadBalancer` для каждого внутреннего микросервиса, что приводит к лишним расходам — для внешнего трафика к множеству сервисов обычно нужен один Ingress; забывать, что `NodePort` открывает порт на всех узлах независимо от того, где физически работает под; путать `LoadBalancer` с Ingress, хотя это разные уровни (L4 vs L7).

**Пример / кейс**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-public
spec:
  type: LoadBalancer
  selector: { app: web }
  ports:
    - port: 80
      targetPort: 8080
```

После применения `kubectl get svc web-public` покажет `EXTERNAL-IP` после того, как облачный провайдер выделит балансировщик — это может занять одну-две минуты.

### 117. Для чего нужен ConfigMap и как передать его данные в контейнер?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

ConfigMap хранит некритичные конфигурационные данные (переменные окружения, файлы настроек) отдельно от образа контейнера и может быть подключён к Pod как переменные окружения или как смонтированный том с файлами.

**Разбор**

Как это работает: ConfigMap — это объект Kubernetes с набором пар ключ-значение или целых файлов; он хранится в etcd в открытом виде (без шифрования по умолчанию) и не предназначен для секретов. При монтировании как volume каждый ключ становится отдельным файлом в указанной директории.

На практике: ConfigMap позволяет использовать один и тот же образ контейнера в разных окружениях (dev/staging/prod), подставляя разную конфигурацию снаружи образа, что соответствует принципу "один артефакт — много окружений". Для горячей перезагрузки конфигурации приложение должно само отслеживать изменения файла, Kubernetes не перезапускает Pod автоматически.

Частые ошибки: хранить пароли и токены в ConfigMap вместо Secret — Secret тоже не шифрует данные по умолчанию, но разделение облегчает контроль доступа и аудит; ожидать, что изменение ConfigMap мгновенно применится к переменным окружения уже запущенного контейнера — переменные окружения читаются только при старте процесса.

**Пример / кейс**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
---
apiVersion: v1
kind: Pod
metadata: { name: demo }
spec:
  containers:
    - name: app
      image: myapp:1.0
      envFrom:
        - configMapRef: { name: app-config }
```

`kubectl exec demo -- env | grep LOG_LEVEL` должен вывести `LOG_LEVEL=info`, подтверждая, что переменная подхватилась из ConfigMap.

### 118. Чем Secret принципиально отличается от ConfigMap?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Secret предназначен для чувствительных данных (пароли, токены, сертификаты) и по умолчанию хранится в etcd в кодировке base64 (это не шифрование), но Kubernetes ограничивает его отображение в `kubectl get` и поддерживает шифрование at rest при соответствующей настройке кластера, чего ConfigMap не предусматривает.

**Разбор**

Как это работает: значения Secret кодируются в base64 при хранении в манифесте, но это лишь способ представления бинарных данных в YAML, а не защита — любой, кто имеет доступ к etcd или право на чтение Secret через API, может декодировать значение. Реальная защита обеспечивается RBAC-ограничениями на чтение Secret и опциональным шифрованием etcd at rest (encryption provider).

На практике: Secret монтируют как файлы или переменные окружения аналогично ConfigMap; для продакшена часто используют внешние системы управления секретами (Vault, облачные Secret Manager) с синхронизацией в Kubernetes Secret через оператор, чтобы не хранить настоящие секреты в Git и получить аудит доступа.

Частые ошибки: считать base64 шифрованием и хранить реальные пароли в публичном репозитории в виде манифеста Secret; давать широким группам пользователей право `get`/`list` на Secret через RBAC; передавать секрет через переменную окружения в случаях, где он может попасть в логи при падении приложения — монтирование файлом безопаснее для части сценариев.

**Пример / кейс**

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  password: cGFzc3dvcmQxMjM=
```

`echo cGFzc3dvcmQxMjM= | base64 -d` выведет `password123` — это демонстрирует, что base64 полностью обратим и не заменяет шифрование или контроль доступа.

### 119. Какую проблему решают liveness и readiness probe и чем они отличаются на базовом уровне?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Liveness probe проверяет, что процесс в контейнере жив и работоспособен — при провале Kubernetes перезапускает контейнер; readiness probe проверяет, готов ли контейнер принимать трафик — при провале под временно убирается из endpoints Service, но не перезапускается.

**Разбор**

Как это работает: обе проверки выполняются kubelet на узле по расписанию (HTTP-запрос, TCP-соединение или команда внутри контейнера) и имеют независимые пороги успеха/неудачи. Liveness влияет на решение "перезапустить контейнер", readiness — на решение "включать ли под в балансировку трафика Service".

На практике: readiness особенно важна при старте приложения, которому нужно время на прогрев кэша или подключение к базе — без неё трафик пойдёт на под раньше, чем он реально готов отвечать. Liveness нужна для восстановления после зависаний (deadlock), когда процесс жив, но не отвечает.

Частые ошибки: использовать одну и ту же проверку для liveness и readiness без понимания разницы последствий; настраивать liveness слишком строго (короткий таймаут) для приложения с медленным стартом, что вызывает бесконечные перезапуски ещё до того, как приложение успело подняться — для этого случая нужен startup probe, рассматриваемый отдельно на уровне Middle.

**Пример / кейс**

```yaml
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
```

Если `/ready` временно возвращает 503 во время прогрева кэша, `kubectl get pod` покажет `READY 0/1`, при этом `RESTARTS` останется `0`, так как liveness при этом продолжает отвечать успешно.

### 120. Что произойдёт, если не указать requests и limits для контейнера, и зачем они вообще нужны?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Без `requests`/`limits` планировщик не знает, сколько ресурсов резервировать для Pod, и под получает низший приоритет QoS (`BestEffort`) — он будет выселен первым при нехватке ресурсов на узле и может бесконтрольно потреблять CPU и память, мешая соседним подам.

**Разбор**

Как это работает: `requests` — это объём ресурсов, который планировщик резервирует для Pod при выборе узла; `limits` — верхняя граница, которую контейнер не может превысить (для CPU — через throttling, для памяти — через убийство процесса, OOMKilled). Если не задать ни то, ни другое, под может занять сколько угодно свободных ресурсов узла, пока их хватает.

На практике: для предсказуемой работы прод-нагрузки желательно явно задавать и requests, и limits, ориентируясь на реальное потребление приложения под нагрузкой (через мониторинг), а не на произвольные числа. Слишком заниженные requests ведут к избыточному размещению подов на узле и конкуренции за ресурсы; слишком высокие — к неэффективному использованию кластера.

Частые ошибки: указывать limits без requests (Kubernetes в части версий автоматически приравнивает requests к limits, что может неожиданно повлиять на планирование); ставить лимит памяти намного ниже реального пикового потребления, что приводит к регулярным OOMKilled; не пересматривать значения после изменения нагрузки на сервис.

**Пример / кейс**

```yaml
resources:
  requests: { cpu: "250m", memory: "256Mi" }
  limits: { cpu: "500m", memory: "512Mi" }
```

Если контейнер попытается использовать больше 512Mi памяти, `kubectl describe pod` покажет `Last State: Terminated, Reason: OOMKilled` — это признак того, что приложению нужно либо больше памяти, либо исправление утечки.

### 121. Что такое namespace в Kubernetes и зачем его использовать?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Namespace — это логическая область видимости внутри одного кластера, позволяющая разделять ресурсы (Pod, Service, ConfigMap и т.д.) между командами, окружениями или проектами и независимо применять к ним квоты и права доступа.

**Разбор**

Как это работает: большинство объектов Kubernetes (кроме, например, Node и PersistentVolume, которые кластерного уровня) существуют внутри namespace; имена объектов должны быть уникальны только в пределах одного namespace, а не всего кластера. RBAC, ResourceQuota и NetworkPolicy можно применять именно на уровне namespace.

На практике: namespace часто используют для разделения окружений (`dev`, `staging`, `prod`) в одном кластере или для изоляции команд/продуктов в общем кластере, сочетая с RBAC и квотами ресурсов. DNS-имя сервиса включает namespace (`svc.namespace.svc.cluster.local`), что позволяет иметь одноимённые сервисы в разных namespace.

Частые ошибки: полагать, что namespace обеспечивает полную сетевую изоляцию "из коробки" — без NetworkPolicy поды из разных namespace по умолчанию могут общаться друг с другом; забывать указывать `-n <namespace>` в командах kubectl и случайно работать не с тем окружением; создавать слишком мелкое дробление на namespace без реальной необходимости в изоляции.

**Пример / кейс**

```
kubectl create namespace staging
kubectl config set-context --current --namespace=staging
kubectl get pods
```

После установки namespace по умолчанию для контекста все последующие команды `kubectl get/apply` будут выполняться в `staging`, пока контекст не переключат обратно — это частый источник путаницы при работе с несколькими окружениями.

### 122. Как посмотреть логи контейнера и что делать, если под уже перезапустился?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Команда `kubectl logs <pod> [-c <container>]` показывает логи текущего работающего контейнера; для логов контейнера, который уже упал и был перезапущен, нужно добавить флаг `--previous`, чтобы получить вывод предыдущего завершившегося экземпляра.

**Разбор**

Как это работает: kubelet собирает stdout/stderr контейнера в локальный лог-файл на узле, а `kubectl logs` читает его через API сервер. Когда контейнер перезапускается (например, из-за `CrashLoopBackOff`), новый процесс стартует "с нуля" и его логи не содержат информации о причине предыдущего падения — для этого нужен именно `--previous`.

На практике: для Pod с несколькими контейнерами обязательно указывать `-c <container-name>`, иначе kubectl либо запросит уточнение, либо покажет логи первого контейнера. Для потокового просмотра в реальном времени используют флаг `-f`, а для агрегации логов со всех реплик — внешние системы логирования (не встроенная функция kubectl).

Частые ошибки: пытаться смотреть логи только текущего запуска после `CrashLoopBackOff`, не находя причину падения, хотя она была в предыдущем запуске; не указывать `-c` в multi-container Pod и анализировать логи не того контейнера; путать `kubectl logs` (логи приложения) с `kubectl describe pod` (события Kubernetes, включая причины рестартов).

**Пример / кейс**

```
kubectl logs app-7d9f -c worker --previous --tail=100
```

Вывод покажет последние 100 строк из упавшего до перезапуска процесса контейнера `worker`, что обычно содержит трассировку исключения или сообщение об ошибке, объясняющее причину `CrashLoopBackOff`.

### 123. Чем StatefulSet отличается от Deployment на базовом уровне?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

StatefulSet даёт каждому Pod устойчивый порядковый номер и имя (например, `db-0`, `db-1`), сохраняет привязку к своему персистентному хранилищу между перезапусками и управляет запуском/остановкой в строгом порядке, тогда как Deployment создаёт взаимозаменяемые Pod со случайными именами.

**Разбор**

Как это работает: StatefulSet использует шаблон имени `<имя>-<порядковый номер>` и, при указании `volumeClaimTemplates`, создаёт отдельный PersistentVolumeClaim для каждого Pod, который сохраняется даже при удалении и пересоздании конкретного Pod с тем же номером. Это нужно приложениям, где порядок запуска или устойчивость идентичности и данных имеют значение (базы данных, очереди сообщений с кворумом).

На практике: StatefulSet обычно используют вместе с headless Service (`clusterIP: None`), что даёт каждому Pod собственное DNS-имя вида `db-0.db.namespace.svc.cluster.local` для прямой адресации конкретного экземпляра — это важно для кластерных СУБД, где роли узлов (primary/replica) привязаны к конкретному инстансу.

Частые ошибки: использовать Deployment для кластеризуемой базы данных, ожидая, что каждый под сохранит "свои" данные при пересоздании — у Deployment нет устойчивой привязки тома к конкретной реплике; разворачивать в Kubernetes сложную stateful-систему без понимания, что это требует дополнительной экспертизы по сравнению с управляемым внешним сервисом базы данных.

**Пример / кейс**

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: db }
spec:
  serviceName: db
  replicas: 3
  selector: { matchLabels: { app: db } }
  template:
    metadata: { labels: { app: db } }
    spec:
      containers:
        - name: db
          image: postgres:16
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: ["ReadWriteOnce"]
        resources: { requests: { storage: 10Gi } }
```

`kubectl get pods -l app=db` покажет `db-0`, `db-1`, `db-2` в строго возрастающем порядке создания, а `kubectl get pvc` — отдельный том для каждого из них.

### 124. Зачем нужен Ingress, если у Service уже есть тип LoadBalancer?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Ingress работает на уровне HTTP/HTTPS (L7) и позволяет одним внешним точкой входа маршрутизировать трафик к разным сервисам по доменному имени или пути URL, а также централизованно управлять TLS, тогда как `Service type: LoadBalancer` создаёт отдельный балансировщик на каждый сервис и работает на уровне TCP/UDP (L4).

**Разбор**

Как это работает: Ingress — это набор правил маршрутизации (host/path → Service), который читает Ingress-контроллер (например, NGINX Ingress Controller, Traefik), работающий как отдельный под или набор подов с собственным Service типа LoadBalancer или NodePort. Сам объект Ingress без установленного контроллера ничего не делает.

На практике: вместо десяти сервисов с типом `LoadBalancer` (и, соответственно, десяти облачных балансировщиков) можно развернуть один Ingress-контроллер с одним внешним IP и описать правила маршрутизации по доменам/путям для всех сервисов — это снижает расходы и упрощает управление TLS-сертификатами в одном месте.

Частые ошибки: ожидать, что создание объекта Ingress само по себе откроет внешний доступ без установленного в кластере Ingress-контроллера; путать Ingress (L7, HTTP-маршрутизация) с Service LoadBalancer (L4, проброс портов); не учитывать, что для нескольких Ingress-контроллеров в одном кластере нужно явно указывать `ingressClassName`.

**Пример / кейс**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: app-ingress }
spec:
  ingressClassName: nginx
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: shop, port: { number: 80 } }
```

После настройки DNS-записи `shop.example.com` на внешний IP Ingress-контроллера запрос `curl http://shop.example.com` будет направлен на Service `shop`, при этом сам контроллер физически слушает один общий внешний адрес.

### 125. Что такое labels и selectors и как они связывают объекты Kubernetes между собой?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Labels — это произвольные пары ключ-значение, прикреплённые к объектам (например, `app: web`), а selector — это запрос, который по значениям labels выбирает набор объектов; через эту связь Service находит свои Pod, а Deployment — управляемые им Pod.

**Разбор**

Как это работает: labels не имеют встроенного смысла для Kubernetes — это просто метаданные, которые становятся значимыми только тогда, когда другой объект ссылается на них через `selector`. Selector поддерживает равенство (`app=web`) и наборные выражения (`in`, `notin`, `exists`) для более гибкой фильтрации.

На практике: labels используют для группировки по приложению, окружению, версии (`app`, `tier`, `env`, `version`), а selectors Service/Deployment/NetworkPolicy опираются именно на них для определения "своих" подов. Хорошая схема меток с самого начала экономит время на диагностике и позволяет гибко фильтровать ресурсы командой `kubectl get pods -l`.

Частые ошибки: менять labels у уже запущенных Pod, управляемых Deployment, что может вывести их из-под управления контроллера (он их просто не узнает и создаст новые); несовпадение `selector` Service и `labels` шаблона Pod по регистру или лишнему пробелу — приводит к пустому списку endpoints без явной ошибки; путать `labels` (для выбора) с `annotations` (для произвольных метаданных без функции выбора).

**Пример / кейс**

```
kubectl get pods --show-labels
kubectl get pods -l app=web,tier=frontend
```

Вторая команда вернёт только те поды, у которых одновременно выставлены обе метки — это тот же механизм, который использует `selector` в Service и Deployment внутри манифеста.

### 126. Как выполнить обновление версии образа в Deployment и как это выглядит "под капотом"?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Обновление образа выполняется командой `kubectl set image deployment/<name> <container>=<new-image>` или изменением поля `image` в манифесте с последующим `kubectl apply`; Deployment создаёт новый ReplicaSet и постепенно переносит трафик с старых Pod на новые по стратегии RollingUpdate.

**Разбор**

Как это работает: при изменении шаблона Pod Deployment генерирует новый ReplicaSet, затем поочерёдно увеличивает число реплик в новом ReplicaSet и уменьшает в старом, соблюдая параметры `maxSurge` и `maxUnavailable`, пока не произойдёт полный переход. На каждом шаге новые Pod должны пройти readiness probe, прежде чем старые будут удалены.

На практике: прогресс обновления можно отслеживать командой `kubectl rollout status deployment/<name>`, а историю версий — `kubectl rollout history`. Для безопасного обновления важно, чтобы readiness probe действительно отражала готовность приложения — иначе Kubernetes может посчитать недостаточно прогретый под "готовым" и начать направлять на него трафик раньше времени.

Частые ошибки: менять образ напрямую через `kubectl edit` без понимания, что это создаёт новую ревизию и запускает rollout; не следить за `kubectl rollout status` и считать деплой успешным сразу после выполнения команды, хотя новые Pod могут не подняться; забывать про readiness probe, из-за чего "успешный" rollout на деле отправляет трафик на не готовые к работе поды.

**Пример / кейс**

```
kubectl set image deployment/web web=myapp:2.0
kubectl rollout status deployment/web
```

Если новая версия образа содержит ошибку и поды не проходят readiness, `kubectl rollout status` зависнет с сообщением о ожидании готовности, и администратор может выполнить `kubectl rollout undo deployment/web` для отката к предыдущей рабочей версии.

### 127. Какие типичные причины у статуса Pod `Pending` и как их отличить друг от друга?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

`Pending` чаще всего означает, что планировщик ещё не нашёл подходящий узел: типичные причины — нехватка ресурсов (CPU/память) на узлах, отсутствие узла, снимающего taints через соответствующие tolerations, незакреплённый PersistentVolumeClaim, или под ещё ждёт скачивания образа.

**Разбор**

Как это работает: до момента, пока планировщик не назначит Pod на конкретный узел (или назначил, но контейнеры ещё не запущены), Pod остаётся в фазе `Pending`. Причина всегда фиксируется в секции `Events` объекта Pod, доступной через `kubectl describe pod`.

На практике: сообщение вида `0/5 nodes are available: insufficient cpu` прямо указывает на нехватку ресурсов; `node(s) had taint that the pod didn't tolerate` — на несовпадение taints/tolerations; `pod has unbound immediate PersistentVolumeClaims` — на проблему с хранилищем. Каждая из этих причин требует разных действий: добавить узлы/снизить requests, настроить toleration, или разобраться со StorageClass.

Частые ошибки: сразу перезапускать под командой `kubectl delete pod`, не посмотрев причину в `describe` — это не решает первопричину и под снова зависнет в `Pending`; путать нехватку ресурсов кластера с ограничением ResourceQuota конкретного namespace, которые дают похожий внешний эффект, но требуют разных решений.

**Пример / кейс**

```
kubectl describe pod web-9f8c7
...
Events:
  Warning  FailedScheduling  30s  default-scheduler  0/3 nodes are available: 3 Insufficient memory.
```

Такое сообщение означает, что ни на одном из трёх узлов нет достаточного свободного объёма памяти под `requests.memory` этого Pod — решение: снизить requests, освободить ресурсы или добавить узлы.

### 128. Для чего используется `kubectl describe` и чем он отличается от `kubectl get`?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

`kubectl get` выводит краткий табличный список объектов и их основные поля, а `kubectl describe` показывает подробную информацию по одному объекту, включая историю событий (`Events`), что критично для диагностики проблем планирования, рестартов и ошибок конфигурации.

**Разбор**

Как это работает: `describe` агрегирует данные объекта (спецификацию, статус, связанные события из API) в читаемый человеком формат, тогда как `get -o yaml`/`-o json` выводит сырое представление ресурса без истории событий. События хранятся в etcd ограниченное время (обычно около часа по умолчанию) и привязаны к конкретному объекту.

На практике: диагностику проблемы с Pod почти всегда начинают с `kubectl describe pod <name>`, обращая внимание на секции `Conditions` (готовность, планирование) и `Events` (последние действия системы и ошибки). Для Deployment `describe` покажет статус rollout и связанные ReplicaSet.

Частые ошибки: пытаться найти причину сбоя только в `kubectl get pods`, где видно лишь итоговый статус без контекста; игнорировать, что `Events` может быть уже "прокручен" (старые события удалены), если с момента инцидента прошло много времени — в этом случае логи и внешний мониторинг надёжнее.

**Пример / кейс**

```
kubectl describe deployment web
...
Conditions:
  Type           Status  Reason
  Available      True    MinimumReplicasAvailable
  Progressing    True    NewReplicaSetAvailable
```

Такой вывод подтверждает, что rollout завершился успешно и новый ReplicaSet полностью доступен — при проблемах здесь же появится `Progressing: False` с указанием причины.

### 129. Что такое volume в Kubernetes на базовом уровне и зачем он нужен контейнеру?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Volume — это каталог с данными, доступный контейнерам внутри Pod, который может переживать перезапуск контейнера (в отличие от файловой системы самого контейнера) и позволяет нескольким контейнерам одного Pod обмениваться файлами.

**Разбор**

Как это работает: файловая система контейнера по умолчанию эфемерна — при перезапуске контейнера (не Pod) все изменения в ней теряются. Volume монтируется в один или несколько контейнеров Pod по указанному пути и живёт столько, сколько живёт сам Pod (для эфемерных типов, например `emptyDir`) или дольше (для `PersistentVolume`, подключаемого через `PersistentVolumeClaim`).

На практике: `emptyDir` часто используют для временного обмена данными между основным контейнером и sidecar (например, логи или кэш); для данных, которые должны пережить пересоздание Pod, используют `PersistentVolumeClaim`, подключённый к реальному сетевому или облачному хранилищу.

Частые ошибки: рассчитывать, что `emptyDir` сохранит данные после удаления Pod — он удаляется вместе с Pod; путать перезапуск контейнера внутри Pod (файлы `emptyDir` сохраняются) с пересозданием самого Pod (эфемерные volume теряются); монтировать один и тот же `ReadWriteOnce` том в поды на разных узлах одновременно, что для большинства типов хранилищ невозможно.

**Пример / кейс**

```yaml
spec:
  containers:
    - name: app
      image: myapp:1.0
      volumeMounts:
        - name: cache
          mountPath: /tmp/cache
  volumes:
    - name: cache
      emptyDir: {}
```

Если контейнер `app` упадёт и перезапустится в том же Pod, содержимое `/tmp/cache` сохранится; но при удалении и пересоздании всего Pod каталог `cache` будет создан заново пустым.

### 130. Чем Deployment отличается от DaemonSet и когда стоит выбрать DaemonSet?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Deployment поддерживает заданное число реплик, размещаемых планировщиком по любым подходящим узлам, а DaemonSet гарантирует ровно один экземпляр Pod на каждом (или на выбранном подмножестве) узле кластера — число реплик определяется числом узлов, а не задаётся вручную.

**Разбор**

Как это работает: DaemonSet автоматически добавляет Pod при появлении нового узла и удаляет при выводе узла из кластера, минуя обычный процесс планирования по ресурсам в привычном смысле — по умолчанию он игнорирует часть ограничений, чтобы гарантированно разместиться на каждом узле (с учётом taints/tolerations).

На практике: DaemonSet используют для инфраструктурных агентов, которые должны работать на каждом узле: сборщики логов (Fluentd/Fluent Bit), экспортеры метрик (node-exporter), сетевые плагины (CNI), агенты безопасности. Обычное приложение с бизнес-логикой почти никогда не разворачивают через DaemonSet.

Частые ошибки: использовать DaemonSet для масштабирования обычного веб-приложения вместо Deployment — это привязывает число реплик к числу узлов и не даёт независимо управлять масштабированием; забывать, что DaemonSet по умолчанию размещается в том числе на управляющих (control-plane) узлах, если явно не настроены исключающие toleration/affinity.

**Пример / кейс**

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata: { name: node-exporter }
spec:
  selector: { matchLabels: { app: node-exporter } }
  template:
    metadata: { labels: { app: node-exporter } }
    spec:
      containers:
        - name: node-exporter
          image: prom/node-exporter:v1.7.0
```

`kubectl get daemonset node-exporter` покажет колонки `DESIRED`/`CURRENT`, равные числу узлов кластера, подходящих под условия размещения — при добавлении нового узла число автоматически увеличится без ручного вмешательства.

### 131. Как выполнить вход в работающий контейнер для диагностики и какие есть ограничения у этого подхода?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Команда `kubectl exec -it <pod> -- /bin/sh` (или `bash`) открывает интерактивную сессию внутри указанного контейнера; ограничение в том, что это работает только если в образе вообще есть соответствующая оболочка, а изменения внутри контейнера не сохранятся после его перезапуска.

**Разбор**

Как это работает: `kubectl exec` отправляет запрос через API сервер на kubelet узла, где запущен контейнер, и запускает указанную команду внутри пространства имён контейнера — это не похоже на SSH, а использует механизм container runtime (exec в namespace процесса).

На практике: внутри контейнера можно посмотреть переменные окружения, проверить сетевую доступность (`curl`, `nslookup`, если утилиты установлены в образе), посмотреть содержимое смонтированных ConfigMap/Secret. Для минимальных образов (distroless, scratch) без оболочки используют `kubectl debug` с эфемерным контейнером отладки, подключаемым к тому же namespace процессов.

Частые ошибки: вносить ручные правки конфигурации прямо внутри контейнера через `exec` как "постоянное" решение — они исчезнут при следующем перезапуске или пересоздании Pod; пытаться выполнить `exec -it` в контейнер, который уже находится в `CrashLoopBackOff` и не успевает стартовать достаточно долго для подключения; забывать указывать `-c <container>` в multi-container Pod.

**Пример / кейс**

```
kubectl exec -it web-7d9f -- /bin/sh
# внутри контейнера
curl -sv http://backend:8080/health
```

Если команда `curl` возвращает `Connection refused`, это говорит о сетевой проблеме или недоступности backend-сервиса, а не об ошибке самого приложения в этом контейнере — направление дальнейшей диагностики смещается в сторону Service/сети.

### 132. Что означает `imagePullPolicy` и чем отличаются значения `Always`, `IfNotPresent`, `Never`?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

`imagePullPolicy` управляет тем, когда kubelet скачивает образ контейнера: `Always` — каждый раз перед запуском проверяет реестр и скачивает образ заново; `IfNotPresent` — использует локально закэшированный образ, если он уже есть на узле; `Never` — запрещает скачивание, используя только локальный образ.

**Разбор**

Как это работает: по умолчанию Kubernetes выбирает `Always`, если тег образа — `latest` или не указан, и `IfNotPresent` для любого другого явного тега. Это поведение по умолчанию можно переопределить явно в манифесте.

На практике: `IfNotPresent` ускоряет запуск и снижает нагрузку на реестр образов, но требует, чтобы тег образа был уникальным и неизменяемым (immutable) — то есть при каждом новом релизе должен использоваться новый тег, а не повторное использование старого с другим содержимым. `Never` применяют в основном в локальной разработке (minikube/kind), где образ собран прямо на узле.

Частые ошибки: использовать тег `latest` в продакшене — это заставляет Kubernetes каждый раз скачивать образ (`Always`) и, что хуже, делает невозможным точно знать, какая именно версия кода запущена на конкретном поде; переиспользовать один и тот же тег для разных версий образа при `IfNotPresent` — узел может не скачать обновлённую версию, если локально уже есть образ с этим тегом.

**Пример / кейс**

```yaml
containers:
  - name: app
    image: registry.example.com/app:2.3.1
    imagePullPolicy: IfNotPresent
```

Если на узле уже закэширован `app:2.3.1`, повторный деплой с тем же тегом не скачает образ заново — для гарантии обновления нужно использовать новый тег при каждом релизе (например, с хэшем коммита).

### 133. Как Pod становится частью списка endpoints Service, и что должно быть верно для этого?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Pod попадает в endpoints Service, когда его метки совпадают с `selector` сервиса и его readiness probe (если она задана) проходит успешно; если readiness не настроена, под считается готовым сразу после того, как все контейнеры перешли в состояние `Running`.

**Разбор**

Как это работает: контроллер Endpoints (или EndpointSlice-контроллер в новых версиях) постоянно следит за подами, подходящими под selector Service, и добавляет в список только те, у которых статус `Ready` в условиях (`Conditions`) Pod равен `True`. kube-proxy на каждом узле обновляет правила маршрутизации на основе этого списка.

На практике: это механизм, который позволяет безопасно выкатывать обновления — новый под не получает трафик, пока не пройдёт readiness, а под, который перестал отвечать на readiness во время работы (например, временная перегрузка), автоматически и временно исключается из балансировки без перезапуска.

Частые ошибки: не задавать readiness probe вовсе, из-за чего трафик может прийти на под до того, как приложение реально готово (например, не успело подключиться к базе данных); считать, что исключение из endpoints равносильно падению пода — это лишь временное исключение из балансировки, сам под продолжает работать и может вернуться в список при восстановлении готовности.

**Пример / кейс**

```
kubectl get endpointslice -l kubernetes.io/service-name=web
```

Если под не проходит readiness, его IP не появится в выводе `kubectl get endpoints web`, даже если `kubectl get pods` показывает его как `Running` — несовпадение между этими двумя командами типично для диагностики "сервис не видит часть подов".

### 134. Что такое ServiceAccount и для чего он используется?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

ServiceAccount — это идентификатор, от имени которого процессы внутри Pod обращаются к Kubernetes API; каждый Pod использует какой-либо ServiceAccount (по умолчанию — `default` в своём namespace), и права этого аккаунта определяются через RBAC.

**Разбор**

Как это работает: при создании Pod в него автоматически монтируется токен ServiceAccount (JWT), который приложение может использовать для аутентификации при обращении к Kubernetes API сервера. Сами по себе права не предоставляются ServiceAccount автоматически — их нужно явно выдать через Role/RoleBinding или ClusterRole/ClusterRoleBinding.

На практике: ServiceAccount нужен, когда приложению внутри кластера требуется взаимодействовать с Kubernetes API — например, оператору, который следит за ресурсами, или CI-агенту, разворачивающему манифесты. Для приложений, которым не нужен доступ к API Kubernetes, лучше явно отключить автомонтирование токена (`automountServiceAccountToken: false`), чтобы снизить площадь атаки.

Частые ошибки: давать `default` ServiceAccount широкие права через ClusterRoleBinding "на всякий случай", что делает любой под в namespace потенциально опасным, если у него есть доступ к API; не отключать automount токена у подов, которым он не нужен, оставляя неиспользуемые учётные данные внутри каждого контейнера.

**Пример / кейс**

```yaml
apiVersion: v1
kind: ServiceAccount
metadata: { name: ci-deployer }
---
apiVersion: v1
kind: Pod
metadata: { name: deployer-pod }
spec:
  serviceAccountName: ci-deployer
  containers:
    - name: app
      image: bitnami/kubectl:1.29
```

`kubectl exec deployer-pod -- cat /var/run/secrets/kubernetes.io/serviceaccount/token` покажет смонтированный токен именно ServiceAccount `ci-deployer`, права которого определяются отдельным RoleBinding.

### 135. Как безопасно откатить неудачный Deployment и что при этом происходит с ReplicaSet?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Команда `kubectl rollout undo deployment/<name>` возвращает Deployment к предыдущей (или указанной через `--to-revision`) ревизии: Kubernetes масштабирует вверх старый ReplicaSet, соответствующий этой ревизии, и масштабирует вниз текущий, повторяя логику rolling update в обратную сторону.

**Разбор**

Как это работает: каждая ревизия Deployment хранится как отдельный ReplicaSet (до тех пор, пока не превышен `revisionHistoryLimit`), и `rollout undo` просто переключает "активный" ReplicaSet на тот, что соответствует нужной ревизии, не требуя пересборки образа или повторного применения старого манифеста вручную.

На практике: перед откатом полезно посмотреть `kubectl rollout history deployment/<name>` и при необходимости `kubectl rollout history deployment/<name> --revision=N` для просмотра деталей конкретной версии. Откат — это быстрый способ вернуть известное рабочее состояние, пока команда разбирается с причиной проблемы в новой версии.

Частые ошибки: полагаться на откат как на единственную меру безопасности без мониторинга и readiness probe — если проблемная версия уже успела полностью заменить старую и нанести ущерб (например, испортить данные), откат кода не отменяет последствий; не устанавливать `revisionHistoryLimit`, из-за чего в кластере годами копится множество неиспользуемых ReplicaSet.

**Пример / кейс**

```
kubectl rollout history deployment/web
kubectl rollout undo deployment/web --to-revision=3
kubectl rollout status deployment/web
```

После отката `kubectl get rs -l app=web` покажет, что ReplicaSet, соответствующий ревизии 3, снова имеет ненулевое число реплик, а предыдущий активный ReplicaSet — ноль.

### 136. Чем Job отличается от CronJob и для каких задач их используют?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

Job запускает Pod для выполнения разовой задачи до её успешного завершения (а не бесконечно, как Deployment), а CronJob создаёт Job по расписанию в формате cron, то есть это механизм повторяющихся по времени задач.

**Разбор**

Как это работает: Job следит за тем, чтобы заданное число Pod успешно завершилось (`completions`), и при сбое может пересоздать Pod согласно `backoffLimit`; после успешного завершения Pod не перезапускается. CronJob на основе расписания создаёт новый объект Job в нужный момент времени, делегируя ему фактическое выполнение.

На практике: Job используют для разовых задач — миграции базы данных, пакетная обработка данных, обучение модели; CronJob — для регулярных задач, например ночного бэкапа или ротации отчётов. Важно учитывать политику `concurrencyPolicy` (Allow/Forbid/Replace) на случай, если предыдущий запуск ещё не завершился к моменту следующего.

Частые ошибки: использовать Deployment для разовой задачи вместо Job — Deployment будет бесконечно перезапускать завершившийся Pod, воспринимая завершение как сбой; не задавать `backoffLimit` и `activeDeadlineSeconds`, из-за чего зависшая задача может выполняться или перезапускаться неограниченно долго; не учитывать `concurrencyPolicy` для CronJob, что приводит к параллельному выполнению нескольких экземпляров долгой задачи.

**Пример / кейс**

```yaml
apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly-backup }
spec:
  schedule: "0 2 * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: backup-tool:1.4
```

`kubectl get jobs --watch` в районе 2 часов ночи покажет создание нового Job этим CronJob'ом; при `concurrencyPolicy: Forbid` новый запуск будет пропущен, если предыдущий ещё выполняется.

### 137. Что такое PersistentVolume и PersistentVolumeClaim и как они связаны между собой?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

PersistentVolume (PV) — это объект, описывающий конкретный ресурс хранения в кластере (диск, NFS-шару и т.п.), а PersistentVolumeClaim (PVC) — это запрос приложения на хранилище с нужным объёмом и режимом доступа; Kubernetes связывает (`bind`) PVC с подходящим PV, а Pod монтирует именно PVC.

**Разбор**

Как это работает: администратор кластера (или StorageClass с динамическим provisioning) создаёт PV, а разработчик описывает PVC с требованиями (размер, `accessMode`, класс хранилища); контроллер находит подходящий PV и связывает его с PVC один к одному. При динамическом provisioning (через `StorageClass`) PV создаётся автоматически в момент создания PVC, без ручного шага.

На практике: приложения в манифестах ссылаются только на PVC, оставаясь независимыми от конкретной реализации хранилища (облачный диск, NFS, Ceph) — это абстракция, позволяющая переносить манифесты между средами. Режим доступа `ReadWriteOnce` означает, что том можно монтировать на чтение-запись только на одном узле одновременно, что важно учитывать при проектировании StatefulSet.

Частые ошибки: путать PV (ресурс кластера, создаёт администратор или StorageClass) и PVC (запрос приложения) — это разные уровни абстракции; пытаться смонтировать один и тот же PVC с `ReadWriteOnce` в поды на разных узлах одновременно и получать ошибку монтирования; не указывать `storageClassName`, полагаясь на класс по умолчанию, который может отличаться между кластерами.

**Пример / кейс**

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: data-claim }
spec:
  accessModes: ["ReadWriteOnce"]
  resources: { requests: { storage: 5Gi } }
  storageClassName: standard
```

`kubectl get pvc data-claim` после создания покажет статус `Bound` и имя автоматически созданного PV, если в кластере настроен динамический provisioning для StorageClass `standard`; статус `Pending` будет говорить о проблеме с provisioning.

### 138. Что такое kubeconfig и контекст, и как это влияет на то, с каким кластером работает kubectl?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Junior

**Короткий ответ**

kubeconfig — это файл с данными для подключения к одному или нескольким кластерам (адрес API сервера, учётные данные, сертификаты), а контекст внутри него — именованная комбинация "кластер + пользователь + namespace по умолчанию"; переключение контекста определяет, к какому кластеру и под каким пользователем будут выполняться команды kubectl.

**Разбор**

Как это работает: по умолчанию kubectl читает файл `~/.kube/config` (или путь из переменной `KUBECONFIG`), который может содержать несколько записей `clusters`, `users` и `contexts`; активный контекст (`current-context`) определяет, какая комбинация используется при выполнении команд без явного указания `--context`.

На практике: при работе с несколькими кластерами (например, dev и prod) критично перед выполнением потенциально опасной команды проверять текущий контекст (`kubectl config current-context`), чтобы случайно не применить изменения не в том окружении. Для автоматизации (CI/CD) обычно используют отдельный ServiceAccount с ограниченными правами и отдельный kubeconfig, а не личные учётные данные инженера.

Частые ошибки: выполнить деструктивную команду (`kubectl delete`, `kubectl apply` с неверным манифестом), не проверив активный контекст, и затронуть продакшен вместо тестового кластера; хранить kubeconfig с правами полного администратора в общедоступном месте или в репозитории с кодом; не использовать `kubectl config get-contexts` для ревизии накопившихся за долгое время контекстов.

**Пример / кейс**

```
kubectl config get-contexts
kubectl config current-context
kubectl config use-context prod-cluster
```

Вывод `kubectl config current-context` перед важной операцией — простая, но критичная привычка: если там неожиданно оказался `prod-cluster` вместо `dev-cluster`, следующую команду стоит остановить и перепроверить.

### 139. Как последовательно диагностировать под, застрявший в `CrashLoopBackOff`?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Диагностику ведут по шагам: смотрят `kubectl describe pod` на код завершения и причину (`Last State`, `Reason`), затем логи предыдущего запуска (`kubectl logs --previous`), и только после этого делают вывод — упало ли приложение само (ошибка кода/конфигурации) или его убил Kubernetes (например, по failed liveness probe или OOM).

**Разбор**

Как это работает: `CrashLoopBackOff` — это состояние, в котором kubelet увеличивает интервал между попытками перезапуска контейнера экспоненциально после повторных сбоев. Причина сбоя всегда одна из: ненулевой exit code процесса приложения, провал liveness probe (Kubernetes сам убивает контейнер), либо OOMKilled (убийство ядром из-за превышения лимита памяти).

На практике: `exit code 1` обычно означает необработанное исключение или ошибку конфигурации на старте — приложение не смогло подключиться к зависимости (БД, очередь) или получило некорректные переменные окружения; `exit code 137` указывает на SIGKILL, что характерно для OOMKilled или ручного убийства; провал liveness виден в `Events` как `Liveness probe failed`. Для медленно стартующих приложений нужно проверить, не слишком ли агрессивны пороги liveness/startup probe относительно реального времени старта.

Частые ошибки: сразу увеличивать `backoffLimit`/лимиты ресурсов "на всякий случай", не выяснив первопричину; путать `OOMKilled` (контроллер памяти ядра) с провалом liveness (решение Kubernetes) — это разные проблемы с разными решениями; не проверять зависимые сервисы (БД, DNS), к которым приложение не может подключиться при старте.

**Пример / кейс**

```
kubectl describe pod payments-7f9c8
...
Last State:  Terminated
  Reason:    OOMKilled
  Exit Code: 137
```

Такой вывод однозначно указывает на нехватку `limits.memory` относительно реального потребления приложения — следующий шаг: посмотреть графики потребления памяти в мониторинге и аккуратно повысить лимит или найти утечку памяти в коде.

### 140. Как подтвердить, что контейнер действительно страдает от CPU throttling при заданных limits, и что с этим делать?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

CPU throttling подтверждается ростом метрики `container_cpu_cfs_throttled_periods_total` (или доли throttled-времени) относительно `container_cpu_cfs_periods_total` в cAdvisor/Prometheus, при одновременном наблюдении, что приложение упирается в `limits.cpu`, хотя по логике не перегружено; решение — поднять `limits.cpu`, либо убрать CPU limit вовсе (оставив только requests) с учётом компромиссов для шумных соседей.

**Разбор**

Как это работает: Linux CFS (Completely Fair Scheduler) квотирует CPU контейнера долями времени за период (обычно 100 мс); если за период контейнер исчерпал квоту, соответствующую `limits.cpu`, ядро принудительно "замораживает" процесс до следующего периода — это и есть throttling, который проявляется как задержки и рост латентности без видимой перегрузки по `usage`.

На практике: throttling особенно коварен при многопоточных приложениях (Java, Go с большим GOMAXPROCS), где кратковременные всплески параллельной работы быстро исчерпывают квоту CPU даже при невысоком среднем потреблении. Решение зависит от контекста: можно увеличить `limits.cpu`, настроить `GOMAXPROCS`/размер пула потоков в соответствии с лимитом, либо для некритичных сервисов вообще не ставить `limits.cpu`, полагаясь только на `requests` и QoS.

Частые ошибки: смотреть только на среднее использование CPU (`usage`) без метрики throttling и не видеть проблему; устанавливать `limits.cpu` равным `requests.cpu` "для простоты", что гарантированно создаёт throttling при любом всплеске; игнорировать, что отсутствие CPU limit повышает риск "шумного соседа", отбирающего ресурсы у других подов на узле — здесь нет универсально правильного выбора без учёта архитектуры узла.

**Пример / кейс**

```promql
rate(container_cpu_cfs_throttled_periods_total{pod="checkout-7d9f"}[5m])
/
rate(container_cpu_cfs_periods_total{pod="checkout-7d9f"}[5m])
```

Значение, стабильно превышающее 0.2–0.3 (20–30% периодов throttled), при нормальной бизнес-нагрузке — сигнал к пересмотру `limits.cpu` или настроек параллелизма приложения.

### 141. Что такое QoS-классы Pod (Guaranteed, Burstable, BestEffort) и как они влияют на поведение при нехватке ресурсов узла?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

QoS-класс вычисляется автоматически из соотношения requests и limits: `Guaranteed` (requests = limits по CPU и памяти для всех контейнеров), `Burstable` (requests заданы и отличаются от limits, либо только частично заданы), `BestEffort` (requests/limits не заданы вовсе); при нехватке памяти на узле kubelet выселяет (evict) поды в порядке BestEffort → Burstable → Guaranteed.

**Разбор**

Как это работает: QoS влияет на порядок OOM-killer внутри узла (через `oom_score_adj`, который Kubernetes выставляет по классу) и на порядок принудительного выселения подов при node pressure (нехватка памяти/диска). Guaranteed-поды удаляются последними и только при действительно критическом состоянии узла.

На практике: для критичных stateful-компонентов (базы данных, очереди) стремятся к классу Guaranteed, чтобы минимизировать риск неожиданного выселения при давлении на узел; для менее критичных batch-задач допустим Burstable или даже BestEffort, если это осознанный компромисс ради более плотного использования кластера. Важно понимать, что Guaranteed не защищает от CPU throttling — это два разных механизма.

Частые ошибки: считать, что Guaranteed гарантирует отсутствие проблем в принципе — он лишь снижает приоритет выселения при node pressure, но не отменяет OOMKilled при превышении собственного лимита памяти пода; не замечать, что под случайно попал в BestEffort из-за отсутствия `requests` хотя бы у одного контейнера в multi-container Pod.

**Пример / кейс**

```
kubectl get pod db-0 -o jsonpath='{.status.qosClass}'
Guaranteed
```

Если в манифесте `requests.memory` и `limits.memory` отличаются хотя бы на один контейнер в Pod, класс станет `Burstable`, даже если остальные контейнеры настроены как Guaranteed — класс вычисляется по Pod целиком, а не по отдельному контейнеру.

### 142. Как правильно настроить startup, liveness и readiness probe вместе для приложения с медленным и непредсказуемым временем старта?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Для приложения с долгим и непредсказуемым стартом нужно добавить startup probe с достаточным суммарным временем ожидания (`failureThreshold * periodSeconds`), чтобы liveness и readiness не начинали действовать, пока startup не подтвердит готовность процесса — это предотвращает преждевременные перезапуски из-за "медленного" старта.

**Разбор**

Как это работает: пока startup probe не завершится успехом, kubelet не выполняет ни liveness, ни readiness проверки вообще; после успеха startup probe управление переходит к обычным liveness/readiness с их собственными интервалами. Это решает проблему, когда единая liveness probe с коротким таймаутом убивает контейнер ещё до завершения инициализации (прогрев кэша, миграции схемы, подключение к зависимостям).

На практике: `failureThreshold` у startup probe стоит рассчитывать с запасом относительно p95/p99 времени старта по данным мониторинга, а не по "обычному" времени — иначе под будет случайно убиваться именно в моменты аномально медленного старта (например, при холодном кэше JVM). Readiness при этом может отдельно проверять готовность конкретно к приёму трафика (например, прогрета ли in-memory карта), даже после того как startup уже подтвердил сам факт живого процесса.

Частые ошибки: пытаться решить проблему медленного старта только за счёт увеличения `initialDelaySeconds` у liveness — это фиксированная задержка, которая либо избыточна для быстрого старта, либо недостаточна для редкого медленного; не разделять startup и liveness, из-за чего приходится делать liveness слишком "мягкой" (большой таймаут), что замедляет обнаружение реальных зависаний уже после старта.

**Пример / кейс**

```yaml
startupProbe:
  httpGet: { path: /healthz, port: 8080 }
  failureThreshold: 30
  periodSeconds: 10
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
```

Startup probe даёт приложению до 300 секунд (30×10с) на инициализацию; после этого liveness со своим, более строгим порогом, начинает следить за "жизнью" уже запущенного процесса, не мешая долгому старту.

### 143. Зачем StatefulSet используют вместе с headless Service и для чего нужны `volumeClaimTemplates`?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Headless Service (`clusterIP: None`) даёт каждому Pod StatefulSet собственную стабильную DNS-запись вместо единого виртуального IP с балансировкой, что нужно для прямой адресации конкретного экземпляра (например, primary в кластере БД); `volumeClaimTemplates` обеспечивает каждому порядковому Pod свой персональный PVC, который сохраняется и переподключается при пересоздании Pod с тем же именем.

**Разбор**

Как это работает: обычный Service скрывает индивидуальные Pod за балансировкой, что не подходит, когда клиенту важно обратиться именно к конкретному экземпляру (например, к primary узлу репликации). Headless Service вместо виртуального IP возвращает через DNS список A-записей (или SRV) на все Pod, а в сочетании со StatefulSet каждый Pod получает дополнительно отдельное стабильное имя вида `<pod>.<service>.<namespace>.svc.cluster.local`. `volumeClaimTemplates` гарантирует, что при пересоздании `db-1` (например, после удаления) новый под снова подключит тот же PVC `data-db-1`, а не получит пустой том.

На практике: эта комбинация — основа для развёртывания кластеризованных систем (etcd, Kafka, Postgres с репликацией), где identity и данные конкретного узла должны сохраняться между перезапусками. Приложение-клиент или sidecar обычно сам реализует логику поиска текущего primary через DNS-запросы ко всем Pod или через механизм выбора лидера.

Частые ошибки: использовать обычный (не headless) Service со StatefulSet и удивляться, что нельзя обратиться к конкретной реплике напрямую; удалять StatefulSet с параметром, который также удаляет PVC (в зависимости от версии и настроек `persistentVolumeClaimRetentionPolicy`), теряя данные, которые предполагалось сохранить.

**Пример / кейс**

```yaml
apiVersion: v1
kind: Service
metadata: { name: kafka }
spec:
  clusterIP: None
  selector: { app: kafka }
  ports: [{ port: 9092 }]
```

`nslookup kafka.default.svc.cluster.local` внутри кластера вернёт отдельную A-запись на каждый под (`kafka-0`, `kafka-1`, `kafka-2`), а не один балансирующий IP — это и используется клиентскими библиотеками Kafka для подключения к конкретным брокерам.

### 144. Чем отличаются стратегии обновления Deployment RollingUpdate и Recreate, и как `maxSurge`/`maxUnavailable` влияют на процесс?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

`RollingUpdate` (стратегия по умолчанию) постепенно заменяет старые Pod новыми без полного простоя, регулируя скорость через `maxSurge` (на сколько реплик сверх нормы можно временно превысить) и `maxUnavailable` (сколько реплик может быть временно недоступно); `Recreate` сначала полностью останавливает все старые Pod и только потом запускает новые, что гарантированно создаёт простой.

**Разбор**

Как это работает: при `RollingUpdate` с `maxSurge: 1, maxUnavailable: 0` Deployment сначала поднимает один дополнительный под новой версии, дожидается его readiness, и только потом гасит один под старой версии, повторяя цикл — это минимизирует риск простоя ценой временного превышения числа реплик. При `maxUnavailable: 1, maxSurge: 0` вместо этого сначала гасится один старый под, и лишь после его удаления поднимается новый — это экономит ресурсы, но временно снижает мощность обслуживания.

На практике: `Recreate` оправдан, когда одновременная работа старой и новой версии недопустима — например, при несовместимых изменениях схемы данных в stateful-приложении с единственной репликой, или при эксклюзивном доступе к ресурсу, который не поддерживает параллельный доступ двух версий. Для большинства stateless веб-сервисов используют `RollingUpdate` с ненулевым `maxSurge`, чтобы избежать простоя при деплое.

Частые ошибки: выбирать `RollingUpdate` для приложения, где старая и новая версия не могут работать одновременно (например, из-за несовместимого формата сообщений в очереди), что приводит к ошибкам в проде во время самого обновления; устанавливать `maxUnavailable: 0` и `maxSurge: 0` одновременно — это некорректная комбинация, блокирующая прогресс rollout.

**Пример / кейс**

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

При 3 репликах в процессе обновления временно будет до 4 Pod одновременно (3 старых + 1 новый, затем постепенно наоборот), но доступность не опустится ниже 3 реплик — такой выбор предпочтителен для сервисов с жёсткими требованиями к доступности, ценой временного увеличения потребления ресурсов.

### 145. Pod долго висит в `Pending` на нагруженном кластере — как системно продиагностировать причину за пределами банальной нехватки ресурсов?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Кроме явной нехватки CPU/памяти, нужно проверить: taints на узлах без соответствующих tolerations у Pod, несовместимые nodeAffinity/nodeSelector требования, превышение ResourceQuota в namespace, нехватку доступных IP-адресов в сети подов, и недоступность запрошенного PersistentVolume/StorageClass — всё это видно в `kubectl describe pod` в секции Events, но формулировки сообщений нужно уметь различать.

**Разбор**

Как это работает: планировщик перебирает все узлы и отфильтровывает неподходящие по множеству предикатов (ресурсы, taints, affinity, топология); если ни один узел не прошёл фильтрацию, Pod остаётся `Pending`, а причина агрегируется в одном сообщении `FailedScheduling`, которое может скрывать сразу несколько факторов (например, "insufficient cpu" на одних узлах и "node(s) had taint" на других).

На практике: при сложном сообщении об ошибке стоит проверять по отдельности каждое условие: `kubectl get nodes -o json | jq '.items[].spec.taints'` для taints, `kubectl describe node <node>` для текущей аллокации ресурсов, `kubectl get resourcequota -n <namespace>` для ограничений namespace. ResourceQuota — частая неочевидная причина: кластер в целом может иметь свободные ресурсы, но namespace уже исчерпал выделенную ему квоту.

Частые ошибки: сразу делать вывод "не хватает ресурсов кластера" и добавлять узлы, когда реальная причина — ResourceQuota namespace или taint, который просто забыли toleration'ить при переносе workload на новый пул узлов; не проверять топологические ограничения (`topologySpreadConstraints`), которые тоже могут сделать Pod непланируемым при недостаточном числе доступных зон.

**Пример / кейс**

```
kubectl describe pod batch-job-9f8
...
Warning  FailedScheduling  default-scheduler  0/8 nodes are available:
  5 Insufficient cpu, 3 node(s) had taint {dedicated: gpu} that the pod didn't tolerate.
```

Это сообщение говорит о двух независимых проблемах одновременно: пяти узлам не хватает CPU, а три узла зарезервированы под GPU-нагрузку — решение требует либо снизить requests, либо добавить общие узлы, а GPU-узлы здесь не являются решением без соответствующей toleration.

### 146. Для чего нужен PodDisruptionBudget и как он взаимодействует с добровольными сбоями (voluntary disruptions)?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

PodDisruptionBudget (PDB) ограничивает, сколько реплик приложения может быть одновременно недоступно из-за добровольных действий (эвакуация узла, обновление кластера, ручной `kubectl drain`), не затрагивая непредвиденные сбои вроде падения узла или OOMKilled, которые PDB предотвратить не может.

**Разбор**

Как это работает: PDB задаёт `minAvailable` или `maxUnavailable` для набора Pod по селектору; при попытке добровольного выселения (через Eviction API, который используют `kubectl drain` и Cluster Autoscaler) Kubernetes проверяет, не нарушит ли это условие PDB, и если нарушит — операция блокируется до тех пор, пока ситуация не изменится (например, пока не поднимется замещающий под в другом месте).

На практике: PDB критичен при плановом обслуживании узлов (patching, upgrade) в кластере — без него `kubectl drain` может единовременно вывести из строя все реплики критичного сервиса, если они случайно оказались на одном узле. PDB не защищает от аппаратного сбоя узла или от OOM — это принципиальное ограничение, которое нужно явно понимать при проектировании отказоустойчивости.

Частые ошибки: считать, что PDB гарантирует доступность при любом сбое, включая аварийные; выставлять `minAvailable`, равный общему числу реплик (например, `minAvailable: 3` при 3 репликах), что полностью блокирует любую добровольную эвакуацию и мешает плановому обслуживанию кластера; не учитывать PDB при планировании upgrade узлов, из-за чего `drain` неожиданно "зависает".

**Пример / кейс**

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: web-pdb }
spec:
  minAvailable: 2
  selector: { matchLabels: { app: web } }
```

При `kubectl drain node-3` для сервиса с тремя репликами и `minAvailable: 2` один под будет эвакуирован и пересоздан на другом узле, но drain не станет одновременно выселять второй под того же приложения, пока первый не окажется снова готов.

### 147. Как с помощью NetworkPolicy ограничить трафик между подами разных namespace, и что произойдёт, если NetworkPolicy не поддерживается CNI-плагином?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

NetworkPolicy описывает разрешённый входящий и/или исходящий трафик для подов по селектору меток, namespace и портам; но сам по себе объект NetworkPolicy ничего не делает, если сетевой плагин (CNI) кластера не реализует его поддержку — в этом случае правила принимаются API сервером, но фактически игнорируются, создавая ложное чувство защищённости.

**Разбор**

Как это работает: по умолчанию в Kubernetes весь трафик между подами разрешён; как только к поду применяется хотя бы одна NetworkPolicy с типом `Ingress`, для этого пода начинает действовать модель "запрещено всё, что не разрешено явно" только для входящего трафика (аналогично для `Egress`). Правила могут ссылаться на `podSelector`, `namespaceSelector` и `ipBlock`, комбинируя их для точечного разрешения.

На практике: для реализации "default deny" в namespace сначала создают пустую политику, блокирующую весь трафик, а затем — отдельные политики, явно разрешающие нужные соединения (например, только от frontend к backend на конкретном порту). Поддержка NetworkPolicy зависит от CNI: Calico, Cilium и некоторые другие её реализуют, тогда как часть простых плагинов (например, базовый flannel в режиме vxlan без Calico) — нет.

Частые ошибки: внедрять NetworkPolicy на кластере с CNI, который её не поддерживает, и считать систему защищённой, хотя трафик по факту ничем не ограничен — это нужно проверять документацией конкретного CNI заранее; забывать, что добавление Ingress-политики не блокирует Egress automatически, и наоборот — для полной изоляции нужно управлять обоими направлениями.

**Пример / кейс**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-frontend-to-backend, namespace: prod }
spec:
  podSelector: { matchLabels: { app: backend } }
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector: { matchLabels: { app: frontend } }
      ports: [{ port: 8080 }]
```

После применения политики под с меткой, отличной от `app: frontend` (например, случайно развёрнутый отладочный под), не сможет установить соединение с `backend` на порту 8080 — это можно проверить через `kubectl exec` и `curl` с таймаутом вместо ответа.

### 148. В чём разница между Role/RoleBinding и ClusterRole/ClusterRoleBinding в RBAC Kubernetes?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Role и RoleBinding ограничены одним namespace и дают права только на ресурсы внутри него; ClusterRole определяет права, применимые на уровне всего кластера (включая кластерные ресурсы вроде Node), но может быть связан как ClusterRoleBinding (права во всём кластере), так и RoleBinding (права только в конкретном namespace, хотя сам набор прав переиспользуемый).

**Разбор**

Как это работает: RBAC в Kubernetes состоит из двух частей — определение прав (`Role`/`ClusterRole`, набор правил "что можно делать с какими ресурсами") и привязка этих прав к субъекту (`RoleBinding`/`ClusterRoleBinding`, "кому выданы эти права и где"). ClusterRole часто используют для переиспользуемых наборов прав (например, "read-only доступ к Pod и Service"), которые затем привязываются к разным namespace через отдельные RoleBinding, чтобы не дублировать одинаковые правила.

На практике: для прав, которые должны действовать везде одинаково и затрагивают кластерные ресурсы (Node, PersistentVolume, сами CRD), используют ClusterRole + ClusterRoleBinding; для ограничения команды только её собственным namespace — Role + RoleBinding (или переиспользуемый ClusterRole + RoleBinding именно в этом namespace). Принцип наименьших привилегий означает выдачу максимально узких прав, необходимых для задачи, и регулярный аудит через `kubectl auth can-i`.

Частые ошибки: выдавать ClusterRoleBinding там, где достаточно RoleBinding в одном namespace, расширяя права на весь кластер без необходимости; путать "ClusterRole можно привязать через RoleBinding" с "ClusterRole всегда даёт права на весь кластер" — область действия определяется типом binding, а не только типом role.

**Пример / кейс**

```
kubectl auth can-i delete pods --as=system:serviceaccount:prod:ci-deployer -n prod
```

Эта команда проверяет, разрешено ли конкретному ServiceAccount удалять Pod в namespace `prod`, не выполняя реального удаления — полезный способ проверить корректность настроенного RBAC перед тем, как давать команде доступ в проде.

### 149. Как настроить Ingress с TLS-терминацией и маршрутизацией по путям для нескольких сервисов?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

TLS-сертификат подключается через поле `tls` в манифесте Ingress со ссылкой на Secret типа `kubernetes.io/tls`, а маршрутизация по путям задаётся списком `rules[].http.paths` с указанием `pathType` и backend-сервиса для каждого пути; сам Ingress-контроллер терминирует TLS и далее обычно общается с backend по HTTP внутри кластера.

**Разбор**

Как это работает: Ingress-контроллер слушает порт 443, использует сертификат и ключ из указанного Secret для TLS handshake, после чего расшифрованный HTTP-запрос маршрутизируется согласно правилам `host`/`path`. `pathType: Prefix` сопоставляет по префиксу пути, `Exact` — только точное совпадение, что важно для корректной работы нескольких правил с пересекающимися путями.

На практике: для автоматического выпуска и обновления сертификатов обычно используют cert-manager, который сам создаёт и обновляет Secret с TLS-сертификатом (например, через Let's Encrypt), избавляя от ручного управления сроком действия. При нескольких `host` в одном Ingress каждый может указывать на разные сервисы, что позволяет обслуживать несколько доменов одним контроллером и одним внешним IP.

Частые ошибки: указывать в `tls.hosts` домен, не совпадающий с доменом в сертификате Secret — TLS handshake завершится ошибкой несоответствия имени; не учитывать порядок правил при пересекающихся путях разных `pathType`, что может привести к неожиданной маршрутизации; забывать, что backend-сервис должен существовать и иметь готовые endpoints — иначе Ingress-контроллер вернёт 502/503 несмотря на корректно настроенный TLS.

**Пример / кейс**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: shop }
spec:
  ingressClassName: nginx
  tls:
    - hosts: ["shop.example.com"]
      secretName: shop-tls
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend: { service: { name: api, port: { number: 8080 } } }
          - path: /
            pathType: Prefix
            backend: { service: { name: frontend, port: { number: 80 } } }
```

`curl -v https://shop.example.com/api/health` должен показать корректный TLS-сертификат для `shop.example.com` и ответ от сервиса `api`, а запрос к `/` — ответ от `frontend`, подтверждая правильность и TLS, и маршрутизации.

### 150. Почему изменение ConfigMap не применяется автоматически к уже запущенным подам, и какие есть способы решить эту проблему?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Переменные окружения, переданные из ConfigMap, читаются процессом только один раз при старте контейнера и не обновляются без перезапуска; файлы, смонтированные как volume из ConfigMap, обновляются на диске автоматически (с задержкой синхронизации kubelet), но приложение должно само отслеживать изменение файла, чтобы подхватить новую конфигурацию без перезапуска.

**Разбор**

Как это работает: при использовании `envFrom`/`env.valueFrom.configMapKeyRef` значения подставляются в переменные окружения процесса на старте контейнера операционной системой — после этого никакая синхронизация с Kubernetes API не происходит. При монтировании ConfigMap как volume kubelet периодически (обычно за время, близкое к TTL кэша kubelet, порядка минуты) обновляет содержимое файлов в уже запущенном контейнере, но само приложение должно реализовать механизм отслеживания изменений файла (например, через inotify или периодический опрос).

На практике: для конфигурации, которая должна меняться "на лету" без простоя, предпочтительно монтирование как файл с логикой горячей перезагрузки в приложении; если приложение не поддерживает это, распространённый паттерн — добавить в манифест аннотацию с хэшем содержимого ConfigMap, которая меняется при каждом обновлении конфигурации и тем самым провоцирует rolling update Deployment (пересоздание подов с новой конфигурацией).

Частые ошибки: менять ConfigMap и ожидать, что переменные окружения в уже работающих подах обновятся без их перезапуска — это невозможно архитектурно; не предусматривать механизм управляемого перезапуска/rollout после изменения конфигурации, из-за чего часть подов работает со старой, а часть — с новой конфигурацией в неопределённый период.

**Пример / кейс**

```yaml
spec:
  template:
    metadata:
      annotations:
        checksum/config: "{{ sha256sum-of-configmap }}"
```

Такой паттерн часто применяют в Helm-чартах: при изменении ConfigMap меняется и чек-сумма в аннотации шаблона Pod, что Kubernetes воспринимает как изменение шаблона и запускает обычный rolling update, гарантированно пересоздавая поды с новой конфигурацией.

### 151. Как работает HorizontalPodAutoscaler и какие ограничения нужно учитывать при его настройке?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

HPA периодически опрашивает метрики (по умолчанию — средний процент использования CPU/памяти относительно `requests`, либо кастомные метрики через Metrics API) и изменяет число реплик Deployment/StatefulSet, чтобы приблизить фактическое значение метрики к целевому; ограничение в том, что HPA требует корректно заданных `requests` и не реагирует мгновенно — есть задержка на сбор метрик и период стабилизации.

**Разбор**

Как это работает: формула масштабирования примерно такая — `желаемые реплики = текущие реплики × (текущее значение метрики / целевое значение)`, с округлением и ограничениями `minReplicas`/`maxReplicas`. Для метрики CPU используется не абсолютное потребление, а процент от `requests.cpu`, поэтому без заданных requests автоскейлинг по CPU вообще не будет работать корректно.

На практике: для плавного масштабирования без "дребезга" (постоянных колебаний числа реплик) настраивают `behavior.scaleDown.stabilizationWindowSeconds`, чтобы не схлопывать реплики сразу после кратковременного снижения нагрузки. Для приложений с нагрузкой, не связанной с CPU (например, зависящей от длины очереди сообщений), нужны кастомные метрики через Prometheus Adapter или внешние метрики (External Metrics API).

Частые ошибки: настраивать HPA по CPU без заданных `requests.cpu` у контейнеров — метрика "процент от requests" в этом случае не определена; ставить слишком узкий диапазон `minReplicas`/`maxReplicas`, не учитывающий время, необходимое новым подам на прохождение readiness (между решением HPA и реальной готовностью пода к трафику есть задержка); не учитывать, что частое резкое масштабирование вниз может преждевременно убивать поды, всё ещё обрабатывающие длительные запросы.

**Пример / кейс**

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: web-hpa }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: web }
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
```

При росте среднего CPU выше 70% от `requests.cpu` HPA начнёт постепенно увеличивать число реплик `web`, что можно наблюдать командой `kubectl get hpa web --watch` вместе с изменением `REPLICAS`.

### 152. Как с помощью affinity/anti-affinity распределить поды приложения по разным узлам или зонам доступности для отказоустойчивости?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

`podAntiAffinity` с правилом по топологическому ключу (`topologyKey: kubernetes.io/hostname` или `topology.kubernetes.io/zone`) запрещает или не предпочитает планировать несколько реплик одного приложения на один и тот же узел/зону, снижая риск одновременной потери всех реплик при сбое одного узла или зоны.

**Разбор**

Как это работает: `requiredDuringSchedulingIgnoredDuringExecution` — жёсткое правило, под которое не удовлетворяющее условие вообще не будет запланировано; `preferredDuringSchedulingIgnoredDuringExecution` — мягкое предпочтение с весом, которое планировщик учитывает, но может нарушить, если нет другого выбора. "IgnoredDuringExecution" означает, что правило проверяется только при планировании и не приводит к выселению уже запущенного Pod при последующем изменении условий.

На практике: жёсткая anti-affinity гарантирует распределение, но может привести к тому, что часть реплик останется в `Pending`, если подходящих узлов/зон физически не хватает (например, 5 реплик при anti-affinity "один под на узел" и только 3 узлах); мягкая anti-affinity безопаснее с точки зрения доступности размещения, но не даёт строгой гарантии распределения. Для распределения по зонам также можно использовать `topologySpreadConstraints`, который даёт более гибкий контроль над максимальным перекосом (`maxSkew`).

Частые ошибки: использовать жёсткую (`required`) anti-affinity без учёта реального числа доступных узлов/зон, что приводит к незапланированным Pod в периоды пиковой нагрузки при масштабировании; путать `podAffinity` (стремление к размещению рядом, например с кэшем) и `podAntiAffinity` (стремление к размещению порознь, для отказоустойчивости) — у них противоположные цели.

**Пример / кейс**

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector: { matchLabels: { app: web } }
        topologyKey: "kubernetes.io/hostname"
```

При такой конфигурации `kubectl get pods -l app=web -o wide` покажет, что каждая реплика размещена на отдельном узле; при попытке запланировать больше реплик, чем доступно узлов, лишние поды останутся в `Pending` с сообщением о нарушении anti-affinity.

### 153. Для какого практического сценария используют taints и tolerations, и как они соотносятся с affinity?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Taint на узле отталкивает все поды, у которых нет соответствующей toleration (например, резервирование узлов с GPU только под нагрузку, которая их реально использует), тогда как affinity работает в обратную сторону — это предпочтение/требование со стороны Pod к определённым узлам; для гарантированного выделения пула узлов под конкретную нагрузку обычно комбинируют taint+toleration с nodeAffinity.

**Разбор**

Как это работает: taint состоит из ключа, значения и эффекта (`NoSchedule` — не планировать новые поды без toleration; `PreferNoSchedule` — мягкое избегание; `NoExecute` — дополнительно выселяет уже запущенные поды без toleration). Toleration на Pod лишь "разрешает" планирование на узел с таким taint, но не обязывает планировщик выбрать именно этот узел — для принудительного направления на нужный пул узлов toleration дополняют nodeAffinity/nodeSelector.

На практике: типичный сценарий — выделенный пул GPU-узлов с taint `nvidia.com/gpu=true:NoSchedule`; только поды с явной toleration под этот taint (обычно ML-нагрузка) могут туда попасть, а GPU-узлы не засоряются случайными обычными workload. Аналогично используют для узлов под конкретные команды/тарифные пулы в мультиарендных кластерах или для исключения control-plane узлов из обычного планирования.

Частые ошибки: добавлять toleration без nodeAffinity, ожидая, что под обязательно попадёт именно на нужный выделенный узел — toleration лишь снимает запрет, но не создаёт предпочтение, и планировщик может разместить под на любом другом подходящем узле без этого taint; использовать `NoExecute` без понимания, что это может неожиданно выселить уже работающие поды при добавлении taint на уже занятый узел.

**Пример / кейс**

```yaml
tolerations:
  - key: "nvidia.com/gpu"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - { key: "nvidia.com/gpu", operator: In, values: ["true"] }
```

Такая комбинация гарантирует, что под и будет допущен на GPU-узел (toleration снимает запрет), и будет размещён именно там (nodeAffinity требует этого), а не на произвольном узле без GPU.

### 154. Как диагностировать проблемы с DNS внутри Kubernetes-кластера, если приложение не может резолвить имя другого сервиса?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Диагностику начинают с проверки, резолвится ли имя вообще из отладочного пода (`nslookup`/`dig` на `<service>.<namespace>.svc.cluster.local`), затем проверяют статус подов CoreDNS (`kube-system`), их логи на ошибки, и конфигурацию `/etc/resolv.conf` внутри проблемного пода — несовпадение search domain или временная перегрузка CoreDNS часто остаются незамеченными при поверхностной проверке.

**Разбор**

Как это работает: каждый под по умолчанию получает `resolv.conf` с `nameserver`, указывающим на ClusterIP сервиса CoreDNS, и `search`-путями, достраивающими короткие имена до полного FQDN (`svc.cluster.local` и т.п.). Если CoreDNS перегружен, его поды падают, либо NetworkPolicy блокирует трафик к порту 53 — резолвинг начинает сбоить случайным образом, что внешне похоже на "нестабильную сеть".

На практике: полезно сравнить поведение короткого имени (`backend`) и полного FQDN (`backend.prod.svc.cluster.local`) — если полное имя резолвится, а короткое нет, проблема в `search`-путях или в том, что под запущен не в том namespace, где ожидается. Для перегруженного CoreDNS проверяют метрики задержки и количество реплик — при большом числе подов в кластере может требоваться горизонтальное масштабирование CoreDNS или включение NodeLocal DNSCache для снижения нагрузки.

Частые ошибки: считать любую проблему с подключением "сетевой проблемой" и не проверять именно DNS отдельно от TCP-соединения; не учитывать, что NetworkPolicy, разрешающая доступ к backend-сервису, но блокирующая egress на порт 53 в `kube-system`, ломает резолвинг имени этого же сервиса; игнорировать логи CoreDNS, где могут быть прямые сообщения о таймаутах upstream DNS или перегрузке.

**Пример / кейс**

```
kubectl run -it --rm debug --image=busybox:1.36 -- sh
/ # nslookup backend.prod.svc.cluster.local
/ # nslookup backend
```

Если первая команда успешна, а вторая — нет, проблема локализована в `search`-путях `resolv.conf` текущего namespace отладочного пода, а не в самом CoreDNS или сервисе `backend`.

### 155. Приложение не получает трафик через Service, хотя поды в статусе Running — как системно найти причину?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Нужно последовательно проверить: совпадают ли `selector` Service и `labels` подов, есть ли endpoints у сервиса (`kubectl get endpoints`), проходят ли поды readiness probe, совпадает ли `targetPort` с реальным портом, на котором слушает приложение внутри контейнера, и не блокирует ли трафик NetworkPolicy.

**Разбор**

Как это работает: Service — это абстракция поверх реального списка endpoint, который формируется автоматически только при точном совпадении меток и успешном readiness; даже один неверный символ в значении метки или в имени порта полностью разрывает эту цепочку без явной ошибки в логах приложения — проблема проявляется только на уровне сетевого взаимодействия.

На практике: первый диагностический шаг — `kubectl get endpoints <service>`: пустой список сразу сужает проблему до selector/labels/readiness, тогда как непустой список переключает фокус на `targetPort`, сетевые политики или на само приложение (слушает ли оно действительно указанный порт и интерфейс, например `0.0.0.0`, а не только `127.0.0.1`). Проверку порта внутри контейнера можно сделать через `kubectl exec` и `curl localhost:<port>` непосредственно в самом поде.

Частые ошибки: сразу подозревать Ingress или внешний балансировщик, не проверив базовый слой Service/Endpoints; путать `port` (порт самого Service) и `targetPort` (порт контейнера) — несовпадение targetPort с реальным портом приложения даёт непустые endpoints, но соединения всё равно будут обрываться; забывать, что приложение, слушающее только `127.0.0.1` внутри контейнера, недоступно даже при идеально настроенном Service.

**Пример / кейс**

```
kubectl get endpoints backend
NAME      ENDPOINTS   AGE
backend   <none>      10m
```

Пустой список `ENDPOINTS` при наличии подов в статусе `Running` почти всегда означает несовпадение `selector` сервиса с `labels` подов либо провал readiness probe — проверка `kubectl get pods -l <selector-из-сервиса>` и `kubectl describe pod` для readiness подтвердит конкретную причину.

### 156. Для чего используются initContainers и чем они принципиально отличаются от обычных контейнеров приложения в Pod?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

initContainers запускаются последовательно до старта основных контейнеров Pod и должны полностью и успешно завершиться (exit code 0), прежде чем Kubernetes начнёт запускать обычные контейнеры; их используют для подготовительных задач — ожидания готовности зависимости, миграции данных, загрузки конфигурации или секретов перед стартом приложения.

**Разбор**

Как это работает: в отличие от обычных контейнеров (которые запускаются параллельно и работают постоянно), initContainers выполняются строго по очереди, один за другим; если какой-то initContainer завершается с ошибкой, Kubernetes перезапускает именно его (согласно `restartPolicy` Pod), не переходя к следующему и не запуская основные контейнеры, пока проблема не будет решена.

На практике: типичные примеры — init-контейнер, который ждёт доступности базы данных перед стартом приложения (`until pg_isready; do sleep 1; done`), или который клонирует репозиторий конфигурации во временный volume, используемый затем основным контейнером. Это позволяет не усложнять образ основного приложения логикой ожидания и подготовки, вынося её в отдельный переиспользуемый шаг.

Частые ошибки: пытаться использовать initContainer для фоновой задачи, которая должна работать параллельно с приложением — для этого нужен sidecar (обычный дополнительный контейнер), а не init; не задавать разумный таймаут ожидания зависимости в init-контейнере, из-за чего под бесконечно висит в состоянии `Init:0/1` без явной ошибки, если зависимость так и не становится доступной.

**Пример / кейс**

```yaml
initContainers:
  - name: wait-for-db
    image: busybox:1.36
    command: ["sh", "-c", "until nc -z db 5432; do echo waiting; sleep 2; done"]
containers:
  - name: app
    image: myapp:1.0
```

`kubectl get pod app-7f9c` в статусе `Init:0/1` указывает, что основной контейнер ещё не запущен, потому что `wait-for-db` не завершился; логи `kubectl logs app-7f9c -c wait-for-db` покажут, сколько раз выполнялась проверка доступности базы данных.

### 157. Какие ключевые настройки securityContext стоит применять к Pod/контейнеру на практике, и зачем нужен `runAsNonRoot`?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Базовый набор для большинства приложений: `runAsNonRoot: true` (запрещает запуск процесса от root внутри контейнера), `readOnlyRootFilesystem: true` (файловая система контейнера доступна только для чтения, кроме явно смонтированных writable volume), и `allowPrivilegeEscalation: false` — вместе они существенно снижают ущерб от компрометации приложения внутри контейнера.

**Разбор**

Как это работает: `runAsNonRoot` не запускает процесс от конкретного пользователя сам по себе — он лишь запрещает Kubernetes стартовать контейнер, если итоговый UID процесса (из образа или из `runAsUser`) равен 0; поэтому его обычно комбинируют с явным `runAsUser: <non-zero>`. `readOnlyRootFilesystem` предотвращает запись вредоносного или случайного кода в файловую систему контейнера во время выполнения, вынуждая явно объявлять нужные для записи volume (например, `/tmp`).

На практике: эти настройки снижают поверхность атаки при эксплуатации уязвимости в приложении — если злоумышленник получит RCE, но процесс работает не от root и файловая система доступна только на чтение, возможности закрепления и дальнейшего продвижения существенно ограничены. Для кластерного применения единых правил используют Pod Security Admission (стандарты `baseline`/`restricted`) или сторонние политики (Kyverno/OPA Gatekeeper), которые в принудительном порядке требуют такие настройки для всех подов namespace.

Частые ошибки: настраивать `runAsNonRoot: true` без проверки, что образ приложения вообще поддерживает работу не от root (многие базовые образы по умолчанию root) — под просто не запустится с ошибкой `CreateContainerConfigError`; включать `readOnlyRootFilesystem` без добавления необходимых writable volume для временных файлов приложения, что ломает его работу в рантайме.

**Пример / кейс**

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false
volumes:
  - name: tmp
    emptyDir: {}
volumeMounts:
  - { name: tmp, mountPath: /tmp }
```

Если образ приложения по умолчанию пишет временные файлы в `/tmp`, добавление writable `emptyDir` именно под этот путь позволяет сохранить `readOnlyRootFilesystem: true` для всей остальной файловой системы без поломки функциональности.

### 158. Что происходит с подами при `kubectl cordon` и `kubectl drain` узла, и чем это отличается от простого удаления узла?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

`cordon` помечает узел как непланируемый (`Unschedulable`), не трогая уже работающие на нём поды, тогда как `drain` дополнительно корректно выселяет (evict) существующие поды через Eviction API, уважая PodDisruptionBudget, graceful shutdown и terminationGracePeriod, в отличие от аварийного удаления узла, при котором поды просто теряются и пересоздаются только после истечения таймаута обнаружения недоступности узла.

**Разбор**

Как это работает: `cordon` — это декларативное изменение `spec.unschedulable: true` у объекта Node, после которого планировщик просто не рассматривает этот узел для новых Pod, но ничего не делает с текущими. `drain` сначала выполняет cordon, а затем вызывает Eviction API для каждого пода на узле (кроме управляемых DaemonSet и ряда системных), ожидая, что каждый под корректно завершится и будет пересоздан контроллером (Deployment/StatefulSet) на другом узле, при этом соблюдая ограничения PodDisruptionBudget.

На практике: перед плановым обслуживанием узла (патчинг ОС, замена инстанса) правильная последовательность — `cordon`, затем `drain`, затем обслуживание и, при необходимости, удаление узла из кластера; это даёт управляемый, "вежливый" процесс вывода без одновременного исчезновения всех реплик критичного сервиса, если PDB настроен корректно. При аварийной потере узла (например, отказ оборудования) ничего из этого не происходит добровольно — Kubernetes обнаруживает недоступность узла только по истечении `node-monitoring-grace-period` и дальнейших таймаутов, после чего поды помечаются к пересозданию.

Частые ошибки: удалять узел из кластера (`kubectl delete node`) без предварительного drain, из-за чего под не получает штатного сигнала graceful shutdown; не учитывать, что `drain` может "зависнуть", если PDB не позволяет выселить под без нарушения `minAvailable`, и требовать либо ручного вмешательства, либо ожидания, пока не появится возможность безопасной эвакуации.

**Пример / кейс**

```
kubectl cordon node-3
kubectl drain node-3 --ignore-daemonsets --delete-emptydir-data
```

Флаг `--ignore-daemonsets` необходим, так как поды DaemonSet не предназначены для эвакуации (они и так пересоздадутся на узле при его возвращении), а `--delete-emptydir-data` явно разрешает потерю данных в `emptyDir`-томах, которые не персистентны по своей природе.

### 159. Какие есть распространённые паттерны multi-container Pod (sidecar, ambassador, adapter) и для каких задач их применяют?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Sidecar дополняет функциональность основного контейнера (сбор логов, синхронизация файлов, proxy service mesh), ambassador проксирует исходящие соединения основного контейнера к внешним сервисам, упрощая ему сетевую логику, а adapter нормализует выходные данные основного контейнера (например, формат логов или метрик) к единому виду, ожидаемому внешней системой мониторинга.

**Разбор**

Как это работает: все три паттерна используют общую инфраструктуру Pod — разделяемую сеть (localhost) и, при необходимости, общие volume — чтобы дополнительный контейнер мог взаимодействовать с основным без сетевых издержек и сложной конфигурации обнаружения сервисов. Разница между паттернами — не в механизме, а в роли: sidecar расширяет возможности, ambassador упрощает исходящий трафик, adapter — приводит данные к общему формату на выходе.

На практике: самый распространённый пример sidecar — proxy service mesh (Envoy в Istio/Linkerd), который прозрачно перехватывает весь входящий/исходящий трафик пода для телеметрии, mTLS и маршрутизации, не требуя изменений в коде приложения. Adapter часто встречается там, где legacy-приложение пишет логи в нестандартном формате, а adapter-контейнер преобразует их в формат, понятный централизованной системе логирования.

Частые ошибки: добавлять sidecar без учёта его собственного потребления ресурсов (CPU/память), которое суммируется с основным контейнером при планировании и влияет на итоговый QoS Pod; не предусматривать независимый жизненный цикл sidecar при завершении основного контейнера — в версиях Kubernetes до появления нативной поддержки "sidecar containers" (restartPolicy на уровне initContainer, начиная с 1.28) порядок остановки sidecar мог приводить к преждевременному обрыву соединений основного приложения.

**Пример / кейс**

```yaml
containers:
  - name: app
    image: myapp:1.0
  - name: log-shipper
    image: fluent-bit:2.2
    volumeMounts:
      - { name: logs, mountPath: /var/log/app }
volumes:
  - name: logs
    emptyDir: {}
```

Основной контейнер `app` пишет логи в общий `emptyDir`, а sidecar `log-shipper` читает их оттуда и отправляет во внешнюю систему — это разделяет ответственность без изменения кода приложения для прямой интеграции с системой логирования.

### 160. Почему base64-кодирование в Kubernetes Secret не является шифрованием, и какие есть практические способы защитить секреты в кластере?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Base64 — это обратимая кодировка без ключа, а не шифрование; реальная защита Secret в Kubernetes складывается из нескольких независимых слоёв: шифрования etcd at rest (encryption provider), строгого RBAC на чтение Secret, и, при более высоких требованиях, внешних систем управления секретами (Vault, облачный Secret Manager) с синхронизацией в кластер.

**Разбор**

Как это работает: по умолчанию Kubernetes хранит Secret в etcd в виде base64 без какого-либо шифрования на диске — доступ к файлам etcd или снапшоту бэкапа даёт прямой доступ к значениям секретов. Encryption at rest (настраивается через `EncryptionConfiguration` на API сервере) шифрует значения Secret перед записью в etcd, но не защищает от легитимного доступа через Kubernetes API — для этого нужен именно RBAC.

На практике: минимальный защищённый контур включает: включённое шифрование etcd at rest, RBAC-правила, ограничивающие `get`/`list` на Secret только необходимым сервисным аккаунтам и людям, и отключение automountServiceAccountToken там, где он не нужен. Для организаций с повышенными требованиями к аудиту и ротации секретов используют внешние хранилища (HashiCorp Vault, AWS/GCP Secret Manager) с оператором (External Secrets Operator) или CSI-драйвером Secrets Store, который подтягивает секреты напрямую в под, минуя постоянное хранение в etcd.

Частые ошибки: считать base64 достаточной защитой и хранить Secret-манифесты с реальными значениями в Git без дополнительного шифрования (например, sealed-secrets, SOPS); включать шифрование etcd at rest, но забывать ограничить RBAC — зашифрованные на диске данные всё равно доступны через API любому, у кого есть права на чтение Secret.

**Пример / кейс**

```
kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d
```

Эта команда демонстрирует, что любой пользователь с правом `get` на конкретный Secret получает значение в открытом виде одной командой — значит, именно контроль прав доступа (RBAC), а не кодировка, является реальной защитой на уровне Kubernetes API.

### 161. Liveness probe настроена неправильно и вызывает каскадные перезапуски сервиса под нагрузкой — как это диагностировать и исправить?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Каскадные рестарты по liveness обычно возникают, когда проверка завязана на тот же ресурс (CPU, пул соединений), что и обработка обычных запросов: под нагрузкой приложение не успевает ответить на liveness-запрос вовремя, Kubernetes убивает под как "неживой", оставшийся трафик перераспределяется на другие поды, увеличивая их нагрузку и провоцируя тот же сбой по цепочке — решение в том, чтобы сделать liveness лёгкой и независимой от текущей нагрузки, в отличие от readiness, которая может быть строже.

**Разбор**

Как это работает: liveness probe должна отвечать на вопрос "жив ли процесс и не завис ли он", а не "может ли сервис сейчас обработать дополнительный запрос" — если endpoint liveness выполняет тяжёлую проверку (запрос к базе данных, полный health-check всех зависимостей) и использует тот же thread pool, что и основная нагрузка, под высокой нагрузкой именно эта проверка первой не успевает уложиться в timeout, хотя процесс полностью работоспособен.

На практике: правильная практика — liveness проверяет минимальный внутренний признак жизни (например, что HTTP-сервер отвечает на простой запрос без обращения к внешним зависимостям), тогда как readiness может быть строже и учитывать зависимости, потому что провал readiness не убивает под, а лишь временно исключает его из трафика, что безопаснее при перегрузке. Также стоит увеличить `timeoutSeconds`/`failureThreshold` liveness с запасом относительно p99 задержки самого простого ответа под пиковой нагрузкой.

Частые ошибки: использовать один и тот же "тяжёлый" health-check endpoint для liveness и readiness; ставить слишком агрессивный `timeoutSeconds` (например, 1 секунда) для liveness на сервисе, где GC-паузы или временные пики нагрузки регулярно превышают это значение; не смотреть на корреляцию между ростом нагрузки, ростом рестартов и падением readiness других подов при расследовании инцидента.

**Пример / кейс**

```yaml
livenessProbe:
  httpGet: { path: /livez, port: 8080 }
  timeoutSeconds: 3
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /readyz, port: 8080 }
  timeoutSeconds: 2
  periodSeconds: 5
  failureThreshold: 2
```

Эндпоинт `/livez` в этом примере должен быть реализован так, чтобы отвечать мгновенно без обращения к БД, а `/readyz` может проверять реальные зависимости — при перегрузке именно `/readyz` начнёт отказывать первым, временно убирая под из балансировки без разрушительного перезапуска.

### 162. Как работает rolling update у StatefulSet и для чего нужен параметр `partition`?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

По умолчанию StatefulSet обновляет поды строго в порядке убывания номера (от самого большого индекса к нулевому), по одному, дожидаясь готовности предыдущего, прежде чем перейти к следующему; параметр `partition` в стратегии `RollingUpdate` позволяет обновить только поды с индексом больше или равным указанному значению, оставляя остальные на старой версии — это используют для канареечного обновления stateful-приложений.

**Разбор**

Как это работает: в отличие от Deployment, где порядок замены подов не гарантирован и может идти параллельно (в пределах `maxSurge`/`maxUnavailable`), StatefulSet по умолчанию работает строго последовательно и в обратном порядке индексов, что важно для приложений, где, например, под с наибольшим индексом — это нереплицированный узел, безопасный для обновления первым. Установка `partition: N` "замораживает" обновление для подов с индексом меньше N, позволяя вручную проконтролировать, когда продолжать раскатку дальше.

На практике: `partition` используют для осторожного обновления кластеризованной БД — сначала обновляют только один под с самым высоким индексом (например, реплику), проверяют его работоспособность под реальным трафиком некоторое время, и только затем постепенно понижают `partition`, продолжая обновление оставшихся подов. Также существует `OrderedReady` (по умолчанию, строгий порядок) и `Parallel` (`podManagementPolicy: Parallel`) — последний запускает/останавливает все поды одновременно, что ускоряет операции, но отказывается от гарантий порядка, важных для некоторых систем при первом запуске кластера.

Частые ошибки: забывать вернуть `partition` обратно к 0 после тестирования канареечной версии, из-за чего обновление застревает на полпути неопределённо долго; применять `podManagementPolicy: Parallel` к системе, которая зависит от строгого порядка инициализации узлов (например, кворумным системам, где первый узел должен быть готов раньше остальных).

**Пример / кейс**

```yaml
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 2
```

При трёх репликах (`db-0`, `db-1`, `db-2`) и `partition: 2` обновится только `db-2`; `db-0` и `db-1` останутся на предыдущей версии образа до тех пор, пока `partition` не будет понижен, что даёт контролируемое окно для проверки новой версии на единственном узле.

### 163. Зачем нужны ResourceQuota и LimitRange на уровне namespace, и чем они отличаются друг от друга?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

ResourceQuota ограничивает суммарное потребление ресурсов (CPU, память, число объектов определённого типа) всем namespace целиком, а LimitRange задаёт ограничения и значения по умолчанию для отдельных Pod/контейнеров внутри namespace (минимум, максимум, значения requests/limits по умолчанию, если они не указаны явно) — это защита от разных проблем: ResourceQuota от исчерпания ресурсов кластера одной командой, LimitRange от подов без явных requests/limits.

**Разбор**

Как это работает: если в namespace установлена ResourceQuota с лимитом на суммарные `requests.cpu`, то любое создание Pod, которое привело бы к превышению этой суммы, будет отклонено API сервером ещё на этапе создания объекта, независимо от реальной свободной ёмкости кластера. LimitRange, в свою очередь, применяется к каждому отдельному Pod/контейнеру при его создании: если в манифесте нет `resources`, LimitRange может подставить значение по умолчанию, а также заблокировать создание объекта, если указанные значения выходят за допустимый диапазон (`min`/`max`).

На практике: ResourceQuota обычно настраивают при выделении namespace под команду или проект в мультиарендном кластере, чтобы одна команда не могла случайно (или намеренно) занять все ресурсы кластера; LimitRange дополняет это, гарантируя, что в принципе каждый под будет иметь хоть какие-то requests/limits, даже если разработчик забыл их указать — это снижает риск появления "незапланированных" BestEffort-подов в namespace с квотами.

Частые ошибки: устанавливать ResourceQuota без LimitRange, из-за чего при отсутствии явных requests в манифестах Pod квота по `requests.cpu`/`requests.memory` может быть внезапно исчерпана несколькими "незаметными" объектами, если квота считает по другим полям, или наоборот — поды без requests вовсе не создадутся, если ResourceQuota требует явного указания ресурсов; устанавливать значения LimitRange по умолчанию, не соответствующие реальным потребностям большинства приложений namespace, что приводит к массовым OOMKilled после включения политики.

**Пример / кейс**

```yaml
apiVersion: v1
kind: ResourceQuota
metadata: { name: team-quota, namespace: team-a }
spec:
  hard: { requests.cpu: "10", requests.memory: 20Gi, pods: "50" }
```

Если суммарные `requests.cpu` всех подов namespace `team-a` уже равны 10, попытка создать ещё один под будет отклонена с ошибкой `exceeded quota`, даже если в кластере в целом достаточно свободных ресурсов на других узлах.

### 164. PVC приложения завис в статусе `Pending` — как системно найти причину, связанную со StorageClass?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Чаще всего причина — несуществующий или неверно указанный `storageClassName`, отсутствие provisioner'а для динамического создания томов в этом классе, недоступность запрошенного объёма/режима доступа у облачного хранилища, либо `WaitForFirstConsumer` binding mode, при котором PVC намеренно остаётся `Pending` до тех пор, пока соответствующий Pod не будет запланирован на конкретный узел/зону.

**Разбор**

Как это работает: при создании PVC контроллер admission и provisioning смотрит на `storageClassName`; если такого StorageClass не существует в кластере, PVC останется `Pending` без автоматического создания PV. Если класс существует, но использует `volumeBindingMode: WaitForFirstConsumer` (распространено для облачных дисков, привязанных к зоне), PVC нормально остаётся в `Pending` до момента, когда планировщик определит зону для использующего его Pod — это не ошибка, а штатное поведение, которое легко спутать с проблемой.

На практике: диагностику начинают с `kubectl describe pvc`, где в `Events` обычно прямо указана причина — "waiting for first consumer", "no persistent volumes available", или ошибка provisioner'а (например, недостаточно квоты в облаке на создание диска). Проверка `kubectl get storageclass` подтверждает, что указанный класс вообще существует и какой у него `provisioner` и `volumeBindingMode`.

Частые ошибки: сразу считать зависший PVC багом хранилища, не проверив банальную опечатку в имени `storageClassName`; не знать про `WaitForFirstConsumer` и пытаться "чинить" PVC, который на самом деле корректно ждёт привязки к Pod — реальная проблема в этом случае может быть не в PVC, а в том, что сам Pod не может быть запланирован.

**Пример / кейс**

```
kubectl describe pvc data-claim
...
Events:
  Warning  ProvisioningFailed  1m  Failed to provision volume: rpc error: ... quota exceeded
```

Такое сообщение прямо указывает на исчерпание квоты на создание дисков у облачного провайдера, а не на ошибку в манифесте Kubernetes — решение лежит на стороне облачного аккаунта (запрос увеличения квоты), а не в изменении YAML.

### 165. Для чего в кластере может понадобиться несколько Ingress-контроллеров и как `ingressClassName` помогает их разграничить?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

Несколько Ingress-контроллеров в одном кластере нужны, когда разным группам трафика требуются разные возможности или изоляция — например, отдельный публичный внешний контроллер и отдельный внутренний для служебных сервисов, или разные вендоры (NGINX и облачный ALB-контроллер) для разных типов нагрузки; поле `ingressClassName` в объекте Ingress явно указывает, какой контроллер должен обрабатывать именно это правило.

**Разбор**

Как это работает: каждый Ingress-контроллер при запуске слушает (через механизм `watch`) только те объекты Ingress, у которых `ingressClassName` совпадает с его собственным `IngressClass`, либо, если `IngressClass` помечен как `default`, обрабатывает Ingress без явно указанного класса. Без явного указания класса при наличии нескольких контроллеров поведение становится неоднозначным — в зависимости от конфигурации либо ни один контроллер не возьмёт объект, либо он будет случайно обработан "дефолтным".

На практике: разделение на внешний и внутренний Ingress-контроллер позволяет держать внутренние административные интерфейсы (Grafana, внутренние API) полностью отделёнными от публичного внешнего адреса с собственными правилами безопасности, сертификатами и, возможно, более мягкими настройками rate-limiting. Использование двух разных реализаций (например, NGINX Ingress Controller и облачный контроллер, интегрированный с managed балансировщиком) оправдано, когда разным классам трафика нужны разные возможности — но это увеличивает операционную сложность поддержки двух разных систем.

Частые ошибки: не указывать `ingressClassName` в кластере с несколькими контроллерами и получать непредсказуемое поведение маршрутизации (правило либо не подхватывается никем, либо подхватывается не тем контроллером); помечать несколько IngressClass как `default` одновременно, что в части реализаций приводит к конфликту или непредсказуемому выбору.

**Пример / кейс**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: internal-grafana }
spec:
  ingressClassName: nginx-internal
  rules: [...]
```

`kubectl get ingressclass` покажет список зарегистрированных классов (`nginx-internal`, `nginx-external` и т.п.); только контроллер, настроенный на класс `nginx-internal`, будет обрабатывать именно это правило, оставляя внешний контроллер незатронутым.

### 166. Что происходит на уровне Kubernetes, когда Pod получает SIGTERM при обычном (не аварийном) завершении, и как это влияет на проектирование graceful shutdown приложения?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Middle

**Короткий ответ**

При удалении Pod Kubernetes параллельно отправляет контейнеру сигнал SIGTERM и начинает исключать под из endpoints Service; у приложения есть время до истечения `terminationGracePeriodSeconds` (по умолчанию 30 секунд), чтобы корректно завершить текущие запросы и закрыть соединения, после чего, если процесс ещё жив, отправляется SIGKILL.

**Разбор**

Как это работает: удаление из списка endpoints Service и отправка SIGTERM контейнеру происходят практически одновременно, но не атомарно — из-за распределённой природы системы (kube-proxy на разных узлах, разная задержка синхронизации) часть входящих соединений может прийти на под уже после получения им SIGTERM, но до того, как все узлы обновили свои правила маршрутизации. Поэтому приложению недостаточно просто мгновенно завершиться по SIGTERM — ему нужно продолжать обрабатывать уже начатые запросы (и желательно ещё немного новых) в течение короткого окна.

На практике: типичная правильная стратегия — по получении SIGTERM сразу перестать сообщать о готовности на readiness-эндпоинте (если он не завязан на то же самое), продолжить обработку уже принятых соединений, отклонять или закрывать новые медленно (не разрывая их грубо), и завершиться явно до истечения `terminationGracePeriodSeconds`, не дожидаясь принудительного SIGKILL. Для приложений с длительными запросами стоит явно увеличить `terminationGracePeriodSeconds` относительно значений по умолчанию.

Частые ошибки: игнорировать SIGTERM в коде приложения и полагаться только на SIGKILL по истечении grace period — это обрывает соединения резко и может приводить к ошибкам на стороне клиента; задавать слишком короткий `terminationGracePeriodSeconds` для сервиса с долгими запросами (например, стриминг или батч-обработка), из-за чего корректные запросы прерываются принудительно ещё до завершения.

**Пример / кейс**

```yaml
spec:
  terminationGracePeriodSeconds: 60
  containers:
    - name: app
      image: myapp:1.0
      lifecycle:
        preStop:
          exec: { command: ["sh", "-c", "sleep 5"] }
```

Хук `preStop` с небольшой задержкой здесь — распространённый практический приём: он даёт время на распространение обновлённого списка endpoints по всем узлам кластера, прежде чем приложение внутри контейнера реально начнёт завершать уже установленные соединения.

### 167. Как спроектировать отказоустойчивое размещение приложения в Kubernetes на несколько зон доступности или регионов, и какие здесь есть принципиальные компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Единственно верного решения нет: мульти-зональный кластер с `topologySpreadConstraints`/anti-affinity решает большинство сценариев отказа зоны при умеренной сложности, тогда как мульти-региональная (или мульти-кластерная) архитектура даёт устойчивость к отказу целого региона ценой значительно большей операционной сложности, задержек репликации данных и затрат — выбор зависит от требуемого RTO/RPO, характера состояния приложения и бюджета.

**Разбор**

Как это работает: один кластер, растянутый на несколько зон доступности в одном регионе, решает проблему отказа узла/стойки/зоны при относительно низкой сложности — control plane управляемого кластера (EKS/GKE/AKS) обычно уже мульти-зонален, а worker-узлы распределяют через `topologySpreadConstraints` и зональные node pools. Для защиты от отказа всего региона нужен либо активный мульти-региональный кластер (сложная синхронизация stateful-компонентов, глобальный DNS/балансировка), либо отдельные кластеры на регион с репликацией данных и механизмом переключения трафика (failover).

На практике: для большинства бизнес-приложений без жёстких регуляторных требований достаточно мульти-зональной отказоустойчивости в рамках одного региона — это покрывает подавляющее большинство реальных инцидентов (отказ ЦОД/зоны) при разумной стоимости. Мульти-региональная архитектура оправдана, когда бизнес явно требует непрерывности при отказе целого облачного региона (финансовые сервисы, критическая инфраструктура) — но тогда нужно отдельно решать вопрос консистентности данных между регионами (синхронная репликация увеличивает задержку, асинхронная создаёт риск потери данных при failover).

Частые ошибки: кандидаты часто приравнивают простое увеличение числа реплик к реальной отказоустойчивости, забывая про `topologySpreadConstraints`/anti-affinity, из-за чего все реплики могут случайно оказаться в одной зоне; также нередко называют мульти-регион "просто ещё одним кластером", не упоминая проблему консистентности данных и необходимость явного RTO/RPO.

Компромисс: мульти-зональность внутри региона — разумный баланс стоимости и отказоустойчивости для большинства команд; мульти-регион нужно обсуждать предметно, оценивая реальную вероятность отказа целого региона у конкретного провайдера, стоимость поддержки второго полноценного окружения, сложность data-слоя (можно ли вообще синхронно реплицировать используемую БД между регионами с приемлемой задержкой) и то, кто и как тестирует failover на практике, а не только на бумаге.

**Пример / кейс**

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector: { matchLabels: { app: checkout } }
```

Такая конфигурация гарантирует примерно равномерное распределение реплик `checkout` по зонам; при отказе одной зоны оставшиеся реплики в других зонах продолжают обслуживать трафик — но для оценки пригодности этого решения нужно обсудить с командой, допустимо ли для бизнеса временное снижение мощности на время, пока не поднимутся новые реплики взамен потерянных.

### 168. Как спроектировать RBAC-модель для крупной организации с множеством команд и кластеров (multi-tenancy), и какие здесь компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Единого правильного шаблона нет: модель обычно строится вокруг пространства имён на команду/продукт с переиспользуемыми ClusterRole и RoleBinding в каждом namespace, но конкретная степень изоляции (shared-кластер с namespace-мультиарендностью vs отдельные кластеры на команду) зависит от требований к безопасности, зрелости команд и готовности нести операционные издержки.

**Разбор**

Как это работает: типовой подход — определить небольшой набор переиспользуемых ClusterRole ("viewer", "developer", "admin-namespace") с чётко описанными правами, затем привязывать их к конкретным группам пользователей через RoleBinding в namespace каждой команды, избегая создания уникальных ролей под каждую команду. Группы пользователей обычно синхронизируются из внешней IdP (через OIDC), а не управляются вручную внутри Kubernetes, чтобы избежать рассинхронизации при увольнениях/переходах сотрудников между командами.

На практике: namespace-мультиарендность в общем кластере дешевле в эксплуатации и быстрее в развёртывании, но требует дисциплины в NetworkPolicy, ResourceQuota, Pod Security Admission и RBAC, чтобы одна команда не могла случайно или намеренно повлиять на другую; она также несёт риск "шумного соседа" и более широкий blast radius при компрометации control plane. Отдельные кластеры на команду/окружение дают более сильную изоляцию и меньший blast radius, но кратно увеличивают операционную нагрузку (patching, upgrade, мониторинг каждого кластера) и могут приводить к дублированию инфраструктуры.

Частые ошибки: частая ошибка — создавать уникальную Role под каждую команду вместо переиспользуемых ClusterRole, что приводит к разрастанию прав и усложняет аудит; также кандидаты иногда путают namespace-уровневый RoleBinding с ClusterRoleBinding (действующим на весь кластер) или забывают упомянуть синхронизацию групп доступа с внешним IdP.

Компромисс: решение зависит от зрелости платформенной команды (способна ли она поддерживать десятки кластеров на одном уровне качества) и требований безопасности конкретных workload (например, PCI DSS или работа с особо чувствительными данными могут требовать физической изоляции кластера); разумный средний путь — несколько кластеров по уровню доверия/критичности (например, prod/non-prod отдельно), а не один кластер на каждую команду и не один кластер на всю организацию.

**Пример / кейс**

```yaml
kind: ClusterRole
metadata: { name: namespace-developer }
rules:
  - apiGroups: ["apps", ""]
    resources: ["deployments", "services", "configmaps", "pods"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
```

Эта же ClusterRole переиспользуется для разных команд через отдельные RoleBinding в их namespace (`team-a`, `team-b`), что при аудите позволяет легко увидеть единый источник прав вместо десятков похожих, но не идентичных ролей — обсуждение с заказчиком нужно, когда команде требуется что-то за пределами этого стандартного набора (например, доступ к CRD конкретного оператора).

### 169. Как спланировать upgrade control plane и узлов крупного production-кластера Kubernetes с минимальным риском простоя, и какие здесь компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Единого безопасного пути нет: upgrade обычно выполняют поэтапно — сначала control plane (с учётом version skew policy, допускающей control plane не более чем на несколько минорных версий новее kubelet), затем узлы партиями с drain и PodDisruptionBudget, предварительно проверив совместимость API-версий используемых манифестов и операторов в тестовом окружении — конкретная стратегия зависит от допустимого окна обслуживания, критичности workload и зрелости CI/CD для инфраструктуры.

**Разбор**

Как это работает: Kubernetes поддерживает ограниченный version skew между компонентами (control plane может быть новее kubelet на worker-узлах на определённое число минорных версий, точное значение зависит от версии проекта), поэтому апгрейд должен идти в определённом порядке и нельзя пропускать несколько минорных версий сразу без промежуточных шагов, если это не поддерживается явно. Managed-кластеры (EKS/GKE/AKS) частично автоматизируют control plane upgrade, но ответственность за совместимость workload (устаревшие `apiVersion`, снятые с поддержки в новой версии API) остаётся на команде.

На практике: перед апгрейдом нужно проверить `kubectl deprecations`/сторонние инструменты (например, `kubent`/`pluto`) на использование удаляемых API-версий, протестировать апгрейд на некритичном окружении, обновлять узлы постепенно партиями (node pool за node pool) с PDB и `drain`, следя за метриками ошибок и латентности между партиями, и иметь чёткий план отката (для managed control plane откат может быть невозможен, тогда план отката — это откат на уровне workload/конфигурации, а не самого control plane).

Частые ошибки: частая ошибка — пытаться перескочить через несколько минорных версий kubelet за один шаг, нарушая version skew policy, или не проверить устаревшие `apiVersion` в манифестах перед апгрейдом control plane, из-за чего объекты перестают приниматься после обновления.

Компромисс: более частые, мелкие апгрейды (например, каждую минорную версию) снижают риск каждого отдельного шага, но увеличивают операционную нагрузку на команду; редкие большие скачки версий проще спланировать по времени, но риск несовместимости и объём необходимого тестирования в каждом таком апгрейде выше. Выбор зависит от размера платформенной команды, количества и разнородности workload в кластере, и от того, насколько критичен простой для бизнеса в конкретном окне обслуживания — обсуждение этих факторов с заинтересованными сторонами должно предшествовать выбору конкретного расписания апгрейдов.

**Пример / кейс**

```
kubectl get deployments -A -o json | pluto detect -o wide -
```

Такая проверка перед апгрейдом кластера с версии, например, 1.24 на 1.26 покажет все манифесты с `apiVersion`, снятыми с поддержки между этими версиями (например, старые версии `PodSecurityPolicy` или `batch/v1beta1` для CronJob) — их нужно обновить до апгрейда control plane, иначе соответствующие объекты перестанут приниматься API сервером.

### 170. Как спроектировать сетевую изоляцию multi-tenant кластера при выборе между разными CNI-решениями (например, Calico и Cilium), и какие здесь компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Однозначно лучшего CNI нет: оба решения поддерживают NetworkPolicy и расширенные возможности (Calico — через собственный `GlobalNetworkPolicy` и опциональный eBPF dataplane, Cilium — изначально построен на eBPF с L7-политиками и встроенной сетевой телеметрией), выбор зависит от требуемой глубины видимости и контроля трафика, существующей экспертизы команды и совместимости с остальной инфраструктурой (service mesh, облачный провайдер).

**Разбор**

Как это работает: базовый Kubernetes NetworkPolicy API ограничен L3/L4 (IP, порты, namespace/pod selector); для более тонкого контроля (L7, например "разрешить только HTTP GET на /api, запретить DELETE") нужны расширения конкретного CNI — у Cilium это `CiliumNetworkPolicy` с L7-правилами на основе eBPF, у Calico — собственные Calico-специфичные политики с похожими, но не идентичными возможностями. eBPF-решения (Cilium, а также режим eBPF у Calico) дают более детальную наблюдаемость трафика на уровне ядра без классического iptables, что снижает накладные расходы на больших кластерах с большим числом Service/правил.

На практике: при миграции между CNI в уже работающем production-кластере возникает значительный риск — нет "горячей" миграции без простоя для большинства CNI, так как смена dataplane требует пересоздания сетевого стека узлов, что обычно означает поэтапный вывод узлов из кластера, их переконфигурацию и возврат (аналог rolling upgrade, но на уровне инфраструктуры, а не приложений), либо полное пересоздание кластера с переносом workload. Выбор CNI для multi-tenant окружения также должен учитывать, насколько команды сами способны писать и поддерживать специфичные для CNI политики, или стоит ограничиться базовым NetworkPolicy API для простоты.

Частые ошибки: частая ошибка — считать, что смену CNI в работающем кластере можно сделать "на горячую" без пересоздания узлов; также кандидаты нередко путают возможности базового NetworkPolicy (ограниченного L3/L4) с L7-фильтрацией, которая доступна только через CNI-специфичные CRD вроде `CiliumNetworkPolicy`.

Компромисс: eBPF-решения дают больше возможностей и часто лучшую производительность на масштабе, но требуют более новых версий ядра Linux и специфичной экспертизы для диагностики проблем (отладка eBPF сложнее классического iptables для большинства инженеров); выбор конкретного CNI также может диктоваться облачным провайдером (некоторые managed-сервисы ограничивают поддерживаемые CNI) — это стоит явно обсуждать с учётом текущей инфраструктуры, а не выбирать CNI изолированно от остального стека.

**Пример / кейс**

```yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata: { name: restrict-api-methods }
spec:
  endpointSelector: { matchLabels: { app: api } }
  ingress:
    - toPorts:
        - ports: [{ port: "8080", protocol: TCP }]
          rules:
            http: [{ method: "GET", path: "/public/.*" }]
```

Такая политика возможна только в CNI с поддержкой L7 (например, Cilium) и демонстрирует разницу с базовым NetworkPolicy — решение о переходе на подобный уровень контроля стоит обсуждать, взвешивая выгоду для безопасности против возросшей сложности эксплуатации и диагностики.

### 171. Как спланировать архитектуру автомасштабирования узлов кластера (Cluster Autoscaler vs Karpenter) с учётом стоимости и скорости появления ёмкости, и какие здесь компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Однозначно лучшего решения нет: классический Cluster Autoscaler работает поверх заранее сконфигурированных groups/node pools с фиксированными типами инстансов и относительно консервативной логикой масштабирования, тогда как Karpenter (и аналогичные bin-packing-ориентированные решения) динамически выбирает оптимальный тип и размер инстанса под конкретные незапланированные поды, потенциально снижая стоимость и ускоряя появление ёмкости, но требуя более тщательной настройки ограничений (какие типы инстансов разрешены, лимиты по стоимости) и несёт свои риски.

**Разбор**

Как это работает: Cluster Autoscaler добавляет/убирает узлы, масштабируя существующие managed node groups (с заранее заданным типом инстанса на группу), реагируя на Pod в статусе `Pending` из-за нехватки ресурсов и на недогруженные узлы для consolidation. Karpenter устраняет посредника в виде node group, напрямую запрашивая у облачного провайдера инстанс нужного размера и типа под конкретный набор незапланированных Pod, что позволяет точнее подбирать ёмкость (bin packing) и быстрее реагировать на спайки нагрузки за счёт прямого API облака вместо шаблонных групп.

На практике: Karpenter особенно выгоден в средах с разнородной и непредсказуемой нагрузкой (много разных по требованиям workload), где заранее нарезанные node pools фиксированного размера приводят либо к избыточным расходам (переразмеренные узлы под мелкие поды), либо к задержкам масштабирования; Cluster Autoscaler проще для команд с относительно однородной и предсказуемой нагрузкой, где уже есть устоявшаяся схема node groups и не требуется такая гибкость. Оба решения требуют осознанной настройки consolidation/scale-down, чтобы не допустить ни избыточных расходов на простаивающие узлы, ни агрессивного удаления узлов, вызывающего частые перепланирования Pod.

Частые ошибки: частая ошибка — развернуть Karpenter без ограничений на допустимые семейства инстансов и лимиты по стоимости, что создаёт риск неконтролируемого запуска дорогих инстансов при спайке нагрузки; также кандидаты иногда преподносят Karpenter как безусловную замену Cluster Autoscaler, не упоминая зависимость от поддержки конкретным облачным провайдером.

Компромисс: более динамичный и гибкий подход (Karpenter) добавляет операционную сложность — нужно явно ограничивать допустимые типы/семейства инстансов и лимиты по стоимости (`limits.cpu`/`limits.memory` на уровне NodePool), иначе есть риск неконтролируемого выбора дорогих инстансов под спайк нагрузки; выбор между решениями также зависит от поддерживаемости конкретным облачным провайдером и готовности команды разбираться с новым инструментом вместо более устоявшегося и широко задокументированного Cluster Autoscaler — обсуждение этого выбора должно включать реальные цифры по паттернам нагрузки конкретной платформы, а не абстрактное предпочтение "более нового" решения.

**Пример / кейс**

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: default }
spec:
  limits: { cpu: "1000", memory: "4000Gi" }
  template:
    spec:
      requirements:
        - { key: "karpenter.k8s.aws/instance-category", operator: In, values: ["c", "m"] }
```

Явный `limits` на уровне NodePool здесь — обязательная мера защиты от неконтролируемого роста расходов; без него резкий всплеск незапланированных Pod с высокими requests может спровоцировать запуск непропорционально большого числа дорогих инстансов за короткое время.

### 172. Как спроектировать стратегию disaster recovery для stateful-приложений, работающих в Kubernetes (включая etcd и персистентные тома), и какие здесь компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Единого рецепта нет: полноценный DR-план должен отдельно покрывать резервное копирование etcd (состояние самого кластера Kubernetes) и резервное копирование/репликацию данных persistent-томов приложений (которые etcd не включает), с конкретными RTO/RPO, определяемыми бизнес-требованиями, а также регулярным тестированием восстановления — выбор между снапшотами тома, приложенческой репликацией и кросс-региональным резервированием зависит от характера данных и допустимого окна потери данных.

**Разбор**

Как это работает: etcd хранит только описание состояния объектов Kubernetes (манифесты, статусы) — его снапшот (`etcdctl snapshot save`) позволяет восстановить конфигурацию кластера, но не содержит данные, физически находящиеся на персистентных томах (базы данных, файлы). Поэтому DR для stateful-приложений требует отдельного механизма резервного копирования самих данных — снапшотов облачных дисков, встроенной репликации СУБД, или инструментов уровня Kubernetes (Velero с интеграцией CSI snapshot) для согласованного бэкапа и PV, и сопутствующих манифестов одновременно.

На практике: важно различать репликацию (защищает от отказа узла/зоны в реальном времени, но не от логической порчи данных — ошибочный DELETE реплицируется мгновенно) и бэкапы (защищают от логической порчи ценой задержки восстановления и потенциальной потери данных за период между бэкапами); DR-план stateful-системы должен включать оба механизма, а не полагаться на один из них. Для кросс-регионального DR нужно решить, насколько синхронной должна быть репликация данных между регионами, явно принимая компромисс между задержкой записи (при синхронной репликации) и риском потери данных при failover (при асинхронной).

Частые ошибки: частая ошибка — считать, что снапшот etcd восстанавливает и данные на персистентных томах; также кандидаты нередко путают репликацию с резервным копированием, ошибочно полагая, что репликация сама по себе защищает от логической порчи данных (например, ошибочного `DELETE`).

Компромисс: частота снапшотов и бэкапов напрямую определяет RPO (сколько данных потенциально потеряется), а сложность и стоимость инфраструктуры восстановления — RTO (как быстро можно восстановиться); более частые бэкапы и горячий резерв в другом регионе снижают оба показателя, но кратно увеличивают стоимость и сложность поддержки. План должен прямо обсуждаться с владельцами бизнеса в терминах конкретных цифр RTO/RPO для каждой системы, а не приниматься инженерами в одностороннем порядке, и обязательно проверяться регулярными учениями восстановления, а не только документироваться.

**Пример / кейс**

```
etcdctl snapshot save /backup/etcd-snapshot-$(date +%F).db --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=... --key=...
velero backup create nightly-prod --include-namespaces prod --snapshot-volumes
```

Снапшот etcd восстанавливает конфигурацию кластера, а `velero backup` с `--snapshot-volumes` дополнительно захватывает состояние персистентных томов через CSI snapshot — без обеих частей план DR будет неполным: восстановленный кластер поднимет манифесты, но подключит либо пустые, либо устаревшие данные.

### 173. Как выстроить безопасность цепочки поставок контейнерных образов в Kubernetes-платформе (от сборки до запуска), и какие здесь компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Единого обязательного стандарта нет, но типовая зрелая цепочка включает: сканирование образов на уязвимости в CI, подпись образов (например, cosign/Sigstore) с проверкой подписи через admission-контроллер (Kyverno/OPA Gatekeeper) перед запуском в кластере, запрет на использование нефиксированных тегов и образов из непроверенных реестров, и регулярное обновление базовых образов — степень строгости каждого из этих шагов зависит от критичности workload и зрелости команд разработки.

**Разбор**

Как это работает: admission-контроллер (валидирующий webhook) перехватывает запросы на создание Pod и может отклонить образ, если его подпись не проходит проверку доверенным ключом, либо если образ происходит не из разрешённого реестра — это переносит контроль "сдвинутым влево" (shift-left) и одновременно обеспечивает enforcement непосредственно в runtime, не полагаясь только на дисциплину CI. Подпись образа (например, через Sigstore/cosign с keyless-подписью на основе OIDC identity CI-системы) даёт криптографическую гарантию, что образ собран именно ожидаемым пайплайном и не был подменён между сборкой и развёртыванием.

На практике: внедрение полной цепочки (сканирование + подпись + enforcement + SBOM) требует согласованных изменений в CI всех команд, что может существенно замедлить миграцию существующих пайплайнов и первое время создавать трение (ложные блокировки легитимных деплоев из-за найденных уязвимостей в зависимостях, которые разработчик не может сразу исправить). Поэтому внедрение часто проходит поэтапно: сначала режим аудита (audit/dry-run у admission-политик, без реальной блокировки), сбор статистики нарушений, коммуникация с командами, и только потом включение принудительного блокирующего режима.

Частые ошибки: частая ошибка — сразу включать блокирующий `Enforce`-режим admission-политик без предварительного прогона в режиме аудита, что останавливает легитимные деплои; также кандидаты часто путают сканирование образов на уязвимости с криптографической подписью образов, считая одно достаточной заменой другого.

Компромисс: более строгий enforcement (блокировка любого образа с критическими уязвимостями или без подписи) повышает безопасность, но может замедлить скорость поставки и потребовать exception-процесса для легитимных случаев (например, временная уязвимость без доступного патча в стороннем образе); более мягкий подход (только предупреждения и дашборды) безопаснее для скорости разработки, но не даёт реальной гарантии защиты от компрометации цепочки поставок — выбор конкретного баланса должен явно обсуждаться с заинтересованными сторонами, с учётом регуляторных требований и реальной зрелости процессов конкретной организации.

**Пример / кейс**

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: require-image-signature }
spec:
  validationFailureAction: Enforce
  rules:
    - name: verify-signature
      match: { resources: { kinds: ["Pod"] } }
      verifyImages:
        - imageReferences: ["registry.example.com/*"]
          attestors:
            - entries:
                - keyless: { issuer: "https://token.actions.githubusercontent.com", subject: "https://github.com/org/repo/*" }
```

Такая политика Kyverno в режиме `Enforce` отклонит создание Pod с образом из `registry.example.com`, если он не подписан ожидаемым CI-пайплайном GitHub Actions — перед включением `Enforce` стоит прогнать политику в режиме `Audit` и обсудить с командами найденные несоответствия, чтобы не остановить легитимные деплои внезапно.

### 174. Как readiness probe, liveness probe и PodDisruptionBudget влияют на достижение SLO сервиса, и как обсуждать эти настройки в терминах error budget?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Единого "правильного" порога probe и PDB не существует — их нужно настраивать исходя из конкретного SLO сервиса (например, допустимой доли ошибок за период) и бюджета ошибок: слишком агрессивные probe увеличивают число ложных исключений из трафика и расходуют error budget на ровном месте, а слишком мягкие probe/PDB позволяют реальным сбоям дольше оставаться незамеченными или допускают избыточные одновременные добровольные нарушения доступности.

**Разбор**

Как это работает: каждое срабатывание readiness-провала временно убирает под из трафика, что при недостаточном числе оставшихся готовых реплик может повысить нагрузку на них и увеличить латентность или долю ошибок — то есть сами механизмы защиты (probe) при неверной настройке могут стать источником нарушения SLO, а не только средством его защиты. PodDisruptionBudget ограничивает, сколько реплик может быть недоступно одновременно из-за плановых операций (апгрейд узлов, автоскейлинг вниз), что напрямую связано с тем, сколько "бюджета" доступности команда готова потратить на плановое обслуживание в течение отчётного периода SLO.

На практике: обсуждение этих настроек должно начинаться с вопроса "какой SLO у этого сервиса и сколько error budget уже израсходовано в этом периоде", а не с универсальных рекомендаций по таймаутам; например, сервис с SLO 99.9% и почти исчерпанным error budget за месяц должен консервативнее подходить к плановым операциям (более строгий PDB, перенос необязательных апгрейдов узлов на начало следующего периода), тогда как сервис с большим запасом бюджета может позволить себе более агрессивное плановое обслуживание. Также стоит учитывать, что SLO обычно измеряется с точки зрения клиента (доля успешных запросов, задержка), а probe и PDB — это внутренние механизмы Kubernetes, корреляция которых с клиентским опытом требует отдельной проверки (например, через синтетические проверки снаружи кластера).

Частые ошибки: частая ошибка — настраивать таймауты probe и `maxUnavailable` у PDB по универсальным "best practice" значениям без привязки к конкретному SLO сервиса; также кандидаты часто не замечают, что сами слишком агрессивные probe могут расходовать error budget, рассматривая их только как защитный механизм, а не как потенциальный источник нарушений.

Компромисс: нет единого ответа, насколько строгим должен быть PDB или насколько агрессивны должны быть probe — это всегда результат переговоров между надёжностью (меньше риск простоя от плановых операций) и операционной гибкостью (возможность быстро проводить апгрейды и масштабирование); команда должна явно формализовать эти пороги в терминах SLO/error budget и пересматривать их по мере изменения критичности сервиса или истории инцидентов, а не оставлять как статичную "настройку по умолчанию".

**Пример / кейс**

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: checkout-pdb }
spec:
  maxUnavailable: 1
  selector: { matchLabels: { app: checkout } }
```

Если у `checkout` SLO 99.95% и команда видит по дашборду, что бюджет ошибок почти исчерпан на этой неделе из-за недавнего инцидента, разумным решением будет временно ужесточить PDB (например, `maxUnavailable: 0` при достаточном запасе реплик) и отложить плановые node upgrade в этом namespace — такое решение стоит явно зафиксировать и обсудить с владельцем сервиса, а не принимать автоматически.

### 175. Когда оправдано хранить stateful-нагрузку (например, базу данных) в Kubernetes через StatefulSet, а когда лучше использовать managed-сервис вне кластера, и какие здесь компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Однозначного правила нет: StatefulSet в Kubernetes даёт больше контроля и может снизить стоимость/избежать vendor lock-in, но перекладывает на команду всю операционную сложность (бэкапы, репликация, failover, патчинг, мониторинг специфичных метрик СУБД), тогда как managed-сервис (RDS, Cloud SQL и т.п.) стоит дороже и может иметь свои ограничения, но снимает значительную часть этой операционной нагрузки — выбор зависит от зрелости команды в эксплуатации конкретной технологии БД, требований к контролю и бюджета.

**Разбор**

Как это работает: Kubernetes StatefulSet решает только часть задач эксплуатации БД — устойчивую идентичность и привязку хранилища к конкретному поду; но сама логика failover, резервного копирования с проверкой восстановимости, обновления минорных/мажорных версий без потери данных, мониторинга репликационного лага и прочих специфичных для конкретной СУБД операций либо должна быть реализована через Kubernetes-оператор (например, для PostgreSQL — Zalando/CloudNativePG, для Kafka — Strimzi), либо вручную. Managed-сервис берёт эту ответственность на себя, предоставляя SLA на доступность и часто встроенные инструменты для point-in-time recovery, но ограничивает возможность тонкой настройки и может быть дороже при большом объёме данных или интенсивном трафике.

На практике: для команд без глубокой экспертизы в конкретной технологии (например, нет опыта эксплуатации Kafka-кластера под нагрузкой) запуск в Kubernetes без зрелого оператора создаёт реальный риск потери данных или длительных простоев при первом же серьёзном инциденте; наличие качественного оператора для конкретной технологии существенно снижает этот риск, но не устраняет его полностью — оператор не заменяет понимание, как работает сама СУБД под капотом. Managed-сервис также не освобождает от ответственности полностью: команде всё равно нужно настраивать правильные параметры, мониторинг использования и собственные процессы восстановления на уровне приложения (например, тестирование процедуры восстановления из бэкапа managed-сервиса).

Частые ошибки: частая ошибка — считать наличие зрелого Kubernetes-оператора достаточной гарантией безопасной эксплуатации без понимания внутреннего устройства самой СУБД; также кандидаты нередко переоценивают managed-сервис, забывая, что он не избавляет команду от необходимости собственного мониторинга и тестирования процедур восстановления.

Компромисс: решение должно явно взвешивать стоимость managed-сервиса против стоимости времени инженеров на поддержку self-hosted решения (включая риск редких, но дорогостоящих инцидентов), доступность зрелого Kubernetes-оператора именно для нужной технологии и версии, требования к задержке и совместному размещению с остальными компонентами в том же кластере, и регуляторные ограничения (например, требование физического размещения данных, которое managed-сервис может не поддерживать в нужном регионе) — это решение стоит принимать совместно с владельцами продукта и архитекторами, а не как изолированный выбор DevOps-команды.

**Пример / кейс**

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata: { name: orders-db }
spec:
  instances: 3
  storage: { size: 100Gi }
```

Использование зрелого оператора (здесь — CloudNativePG) снижает часть рисков self-hosted PostgreSQL в Kubernetes (автоматический failover, управление репликацией), но команда всё равно должна явно обсудить и протестировать сценарии восстановления из бэкапа, обновления мажорной версии PostgreSQL и поведение при полном отказе зоны, прежде чем доверять этому решению данные, критичные для бизнеса.

### 176. Как спроектировать стратегию zero-downtime деплоя (blue-green или canary) поверх примитивов Kubernetes, и какие здесь компромиссы по сравнению с обычным RollingUpdate?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Однозначно лучшей стратегии нет: обычный RollingUpdate Deployment достаточен для большинства случаев и прост в эксплуатации, canary (постепенный перевод небольшой доли трафика на новую версию с метриками до полного переключения) снижает blast radius ошибки ценой дополнительной инфраструктуры (service mesh или специализированный контроллер вроде Argo Rollouts/Flagger), а blue-green (две полностью параллельные версии с мгновенным переключением трафика) даёт самый быстрый откат ценой удвоенного потребления ресурсов на время деплоя.

**Разбор**

Как это работает: RollingUpdate постепенно подменяет поды одной версии на другую без возможности тонко контролировать долю трафика на новую версию отдельно от доли подов — на практике доля трафика примерно пропорциональна доле подов новой версии, и нет встроенного механизма автоматической остановки по метрикам ошибок. Canary и blue-green требуют дополнительного уровня управления трафиком независимо от количества подов (через service mesh с weighted routing, Ingress с canary-аннотациями, или специализированный контроллер), что позволяет, например, направить всего 5% трафика на новую версию, автоматически анализировать метрики ошибок/латентности, и либо продолжить раскатку, либо автоматически откатиться при аномалии.

На практике: canary particularly полезен для сервисов с высоким трафиком и историей проблем, не ловящихся в staging (где нагрузка и данные отличаются от прод); blue-green особенно ценен, когда критична скорость отката (мгновенное переключение трафика обратно на полностью готовую старую версию) и когда можно себе позволить временно удвоенное потребление ресурсов. Оба подхода усложняют конфигурацию и требуют дополнительных инструментов и экспертизы команды (например, Argo Rollouts с анализом метрик через Prometheus), что увеличивает когнитивную нагрузку и поверхность отказа самой платформы деплоя.

Частые ошибки: частая ошибка — путать canary и blue-green или считать, что RollingUpdate даёт точный контроль доли трафика на новую версию независимо от доли подов; также кандидаты нередко предлагают canary/blue-green как универсальное решение для всех сервисов, не упоминая стоимость дополнительной инфраструктуры и экспертизы.

Компромисс: усложнение пайплайна деплоя должно быть оправдано реальной частотой проблемных релизов и стоимостью инцидента при плохом деплое — для внутреннего низконагруженного сервиса обычный RollingUpdate с хорошими readiness probe и мониторингом может быть достаточен, тогда как для высоконагруженного customer-facing сервиса с историей проблемных релизов инвестиция в canary-инфраструктуру может окупиться; это решение стоит обсуждать предметно для каждого сервиса, а не внедрять одну стратегию деплоя универсально для всей платформы.

**Пример / кейс**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: checkout }
spec:
  strategy:
    canary:
      steps:
        - setWeight: 5
        - pause: { duration: 10m }
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 100
```

Такая конфигурация Argo Rollouts постепенно увеличивает долю трафика на новую версию с паузами для наблюдения за метриками; при настроенном автоматическом анализе (`AnalysisTemplate`) аномальный рост ошибок на шаге 5% может автоматически остановить раскатку и откатить трафик — но внедрение этого механизма требует отдельного обсуждения, какие именно метрики и пороги считать признаком проблемы для конкретного сервиса.

### 177. Как выбрать между Ingress API и Gateway API для крупной мультиарендной платформы, и какие здесь компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Однозначно лучшего выбора нет: Ingress API проще, широко поддержан и достаточен для базовой HTTP-маршрутизации, тогда как Gateway API даёт более выразительную ролевую модель (разделение ответственности между администратором инфраструктуры, владельцем Gateway и командами, управляющими маршрутами) и более богатые возможности маршрутизации (включая TCP/UDP, продвинутый traffic splitting), но требует перехода на новую, менее давно устоявшуюся экосистему и зависит от зрелости её поддержки у выбранного Ingress-контроллера/провайдера.

**Разбор**

Как это работает: Ingress API исторически ограничен HTTP/HTTPS-маршрутизацией и полагается на нестандартизированные аннотации конкретного контроллера для любой продвинутой функциональности (rate limiting, canary, rewrite правила), что делает конфигурацию менее портируемой между разными реализациями контроллеров. Gateway API вводит отдельные ресурсы с чётким разделением ролей (`GatewayClass`/`Gateway` — управляется платформенной командой, `HTTPRoute`/`TCPRoute` и т.п. — управляется командами приложений), стандартизируя продвинутые возможности маршрутизации без необходимости в proprietary-аннотациях.

На практике: для мультиарендной платформы с чётким разделением "платформенная команда управляет точкой входа, продуктовые команды управляют своими маршрутами" ролевая модель Gateway API концептуально точнее отражает реальное разделение ответственности, чем плоская модель Ingress, где подобное разделение приходится имитировать через RBAC и соглашения. Переход, однако, требует, чтобы используемый Ingress-контроллер (или отдельный Gateway-контроллер) поддерживал Gateway API на нужном уровне зрелости, и может потребовать параллельной поддержки обоих API на время миграции существующих маршрутов.

Частые ошибки: частая ошибка — называть Gateway API безусловно лучшим выбором только потому, что он новее стандарт, не проверив уровень его поддержки у конкретного используемого контроллера; также кандидаты иногда путают роли `Gateway`/`GatewayClass` и `HTTPRoute` с обычным объектом Ingress, не видя заложенного разделения ответственности.

Компромисс: внедрение Gateway API оправдано, когда реальная сложность платформы (много команд, много разных типов трафика, потребность в продвинутой маршрутизации) уже упирается в ограничения Ingress и proprietary-аннотаций; для меньших платформ с простыми требованиями к маршрутизации переход может добавить сложность без ощутимой выгоды — решение стоит принимать с учётом конкретной зрелости используемого контроллера, стоимости миграции существующих Ingress-манифестов и реальной потребности в ролевом разделении, а не исходя из того, что Gateway API "более новый" стандарт.

**Пример / кейс**

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: checkout-route, namespace: team-checkout }
spec:
  parentRefs: [{ name: shared-gateway, namespace: platform }]
  rules:
    - matches: [{ path: { type: PathPrefix, value: "/checkout" } }]
      backendRefs: [{ name: checkout, port: 8080 }]
```

Здесь команда `team-checkout` управляет только своим `HTTPRoute`, ссылаясь на общий `Gateway`, которым владеет платформенная команда в своём namespace — такое разделение ответственности снижает риск, что команда приложения случайно изменит общую конфигурацию точки входа, но требует предварительного согласования модели владения между командами.

### 178. Как спланировать распределение ресурсов и приоритетов в мультиарендном кластере, чтобы снизить проблему "шумного соседа", и какие здесь компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Единого решения нет: комбинация корректно заданных requests/limits, ResourceQuota/LimitRange на namespace, PriorityClass с возможностью preemption для критичных workload и, при необходимости, физического разделения узлов по критичности (через node pools с taints) снижает риск шумного соседа, но каждая мера имеет свою цену — от избыточного резервирования ресурсов до усложнения эксплуатации кластера.

**Разбор**

Как это работает: "шумный сосед" возникает, когда один workload (например, batch-задача с высоким потреблением CPU/диска/сети) деградирует производительность соседних подов на том же узле, особенно если requests занижены относительно реального потребления или лимиты не заданы вовсе. PriorityClass позволяет при нехватке ресурсов на узле вытеснять (preempt) поды с низким приоритетом в пользу подов с высоким, что защищает критичные сервисы, но означает, что workload с низким приоритетом должен быть спроектирован так, чтобы безопасно переживать подобное вытеснение (идемпотентность, возможность повторного запуска).

На практике: для действительно критичных по изоляции рабочих нагрузок (например, PCI-compliance workload или задачи с предсказуемой латентностью) может потребоваться выделенный node pool с taint, куда допускаются только эти поды, что устраняет шумного соседа ценой менее эффективного использования кластера (выделенные узлы не разделяются с остальной нагрузкой). Для менее критичных случаев обычно достаточно корректных requests/limits (QoS Guaranteed для чувствительных к задержке сервисов) вместе с PriorityClass и мониторингом фактического потребления ресурсов по сравнению с запрошенным.

Частые ошибки: частая ошибка — пытаться решить проблему шумного соседа только через requests/limits, не используя PriorityClass и preemption для защиты критичных workload; также кандидаты нередко путают ResourceQuota (ограничение суммарных ресурсов namespace) с LimitRange (значения по умолчанию и границы на один контейнер).

Компромисс: более строгая изоляция (выделенные node pools, строгий Guaranteed QoS везде) повышает предсказуемость, но снижает эффективность использования кластера и повышает стоимость; более мягкий подход (общие узлы, Burstable QoS) эффективнее по затратам, но создаёт риск деградации при неудачном соседстве workload — решение должно явно обсуждаться для каждого класса критичности workload, с учётом того, что не все сервисы в организации одинаково чувствительны к шумному соседству, и единая политика для всех не всегда оправдана.

**Пример / кейс**

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: business-critical }
value: 1000000
preemptionPolicy: PreemptLowerPriority
```

Поды с этим PriorityClass при нехватке ресурсов на узле могут вытеснить поды с более низким приоритетом (например, batch-аналитику); перед внедрением такой политики стоит явно обсудить с владельцами низкоприоритетных workload, что их поды могут быть принудительно остановлены, и убедиться, что их архитектура это переживает без потери данных.

### 179. Как спланировать миграцию с одного CNI или service mesh на другой в работающем production-кластере без простоя, и какие здесь риски и компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Единого безопасного рецепта нет: миграция CNI обычно требует поэтапного вывода узлов из кластера, их переконфигурации с новым CNI и возврата (либо полного параллельного кластера с переносом workload), тогда как миграция service mesh чаще допускает более плавное сосуществование двух mesh на время перехода — в обоих случаях ключевой риск в недооценке связности между компонентами, которая может обнаружиться только в проде, и решение требует тщательного поэтапного плана с возможностью отката на каждом шаге.

**Разбор**

Как это работает: большинство CNI-плагинов конфигурируют сетевой стек на уровне узла при его инициализации, поэтому смена CNI на уже работающем узле без его пересоздания обычно не поддерживается штатно — типичный безопасный путь представляет собой постепенный вывод узлов партиями (cordon/drain), их переконфигурацию или замену новыми узлами с новым CNI, и контролируемый перенос workload, похожий на процесс апгрейда кластера, но потенциально более рискованный из-за различий в реализации NetworkPolicy, MTU, или производительности между CNI. Миграция service mesh (например, с Linkerd на Istio) обычно идёт через постепенное добавление sidecar нового mesh рядом со старым для части namespace, проверку метрик и поведения, и последующее отключение старого mesh — но при этом нужно явно управлять тем, как трафик между подами с разными mesh (или без mesh) будет себя вести в переходный период, особенно если используется mTLS.

На практике: перед любой такой миграцией нужен прогон полного плана на отдельном, максимально похожем на прод тестовом кластере, включая сценарии отказа на середине миграции (что произойдёт, если процесс прервётся после перевода половины узлов/namespace); также критично заранее явно задокументировать и протестировать план отката для каждого промежуточного шага, а не только для миграции целиком. Для организаций с низкой толерантностью к риску часто предпочтительнее поднять полностью новый кластер с целевым CNI/mesh и постепенно переносить workload через внешний балансировщик трафика между старым и новым кластером, чем мигрировать "на месте".

Частые ошибки: частая ошибка — предполагать, что CNI можно сменить без пересоздания узлов, или недооценивать поведение mTLS и связности между подами с разными service mesh в переходный период; также кандидаты часто не планируют откат для каждого промежуточного шага, считая план отмены нужным только для миграции целиком.

Компромисс: миграция "на месте" дешевле по инфраструктуре, но несёт более высокий риск для существующего кластера и требует простоя или деградации на время замены узлов; миграция через параллельный новый кластер безопаснее с точки зрения изоляции риска, но требует дополнительных ресурсов на существование двух кластеров одновременно и решения задачи постепенного переноса трафика между ними — выбор должен явно обсуждаться с учётом критичности сервисов в кластере, доступного бюджета на временное дублирование инфраструктуры и зрелости команды в управлении подобными миграциями.

**Пример / кейс**

```
kubectl cordon node-old-1
kubectl drain node-old-1 --ignore-daemonsets --delete-emptydir-data
# узел переустанавливается с новым CNI или заменяется новым инстансом
kubectl label node node-new-1 cni-version=cilium-v2
```

Такой поэтапный процесс позволяет мигрировать CNI node pool за node pool, но требует, чтобы между партиями узлов с разными CNI поды могли корректно взаимодействовать (что не всегда гарантировано) — это должно быть явно проверено в тестовом окружении до начала миграции прод-кластера, иначе переходный период может привести к труднодиагностируемым сетевым сбоям.

### 180. Как выбрать архитектуру управления секретами на уровне платформы (нативные Kubernetes Secret vs Vault/External Secrets Operator), и какие здесь компромиссы?

**Направление:** DevOps Engineer
**Тема:** Kubernetes и оркестрация
**Уровень:** Senior

**Короткий ответ**

Однозначно лучшего варианта нет: нативные Kubernetes Secret с включённым шифрованием etcd at rest и строгим RBAC достаточны для многих команд и просты в эксплуатации, тогда как внешняя система управления секретами (Vault, облачный Secret Manager) с синхронизацией через External Secrets Operator даёт централизованный аудит, ротацию и единую точку управления секретами для нескольких кластеров ценой дополнительной инфраструктуры и зависимости от доступности этой внешней системы.

**Разбор**

Как это работает: External Secrets Operator периодически синхронизирует значения из внешнего хранилища во внутренние Kubernetes Secret (или альтернативно секрет монтируется напрямую через CSI-драйвер Secrets Store без постоянного хранения в etcd вовсе), что позволяет централизованно управлять жизненным циклом секрета (создание, ротация, отзыв) в одном месте независимо от числа кластеров, которые его используют. Это также даёт единый аудиторский след обращений к секретам, который нативный Kubernetes RBAC предоставляет менее детально (видно, кто имеет право на доступ, но не всегда так же детально — кто и когда реально обратился к конкретному значению, в зависимости от настройки audit log).

На практике: для одного кластера с небольшим числом команд и нормально настроенным RBAC и encryption at rest нативных Secret может быть достаточно — добавление Vault создаёт дополнительную точку отказа (при недоступности Vault новые поды могут не получить нужный секрет при старте, если не предусмотрено кэширование) и требует экспертизы по эксплуатации самого Vault (unsealing, политика доступа, высокая доступность). Для организаций с несколькими кластерами, строгими требованиями комплаенса к аудиту и ротации секретов, или уже существующим Vault для других целей — централизация через External Secrets Operator снижает дублирование процессов управления секретами и повышает согласованность политик между кластерами.

Частые ошибки: частая ошибка — считать, что синхронизация через External Secrets Operator сама обеспечивает применение новых значений в приложении, забывая, что многим приложениям требуется перезапуск или reload для подхватывания обновлённого секрета; также кандидаты нередко защищают доступ к Kubernetes Secret через RBAC, но не продумывают контроль доступа к самому внешнему хранилищу.

Компромисс: добавление внешней системы управления секретами увеличивает операционную сложность и вводит новую критичную зависимость (доступность Vault становится частью critical path при старте подов, если не настроено кэширование или graceful degradation), но даёт выгоды масштаба при множестве кластеров/команд; для единственного или малого числа кластеров эти выгоды могут не оправдывать добавленную сложность — решение должно явно обсуждаться с учётом числа кластеров, требований комплаенса конкретной организации и готовности команды нести ответственность за ещё одну критичную систему.

**Пример / кейс**

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata: { name: db-credentials }
spec:
  secretStoreRef: { name: vault-backend, kind: SecretStore }
  target: { name: db-credentials }
  data:
    - secretKey: password
      remoteRef: { key: prod/db, property: password }
```

Такая конфигурация синхронизирует значение из Vault в обычный Kubernetes Secret `db-credentials`, который приложение монтирует привычным способом — но команда должна явно продумать поведение при временной недоступности Vault (например, что произойдёт при создании нового пода, если `ExternalSecret` не может обновить значение) и протестировать этот сценарий до переноса критичных секретов на эту схему.
