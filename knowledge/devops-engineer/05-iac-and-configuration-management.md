## Тема 5. Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize

### 241. Что такое Infrastructure as Code и чем системный подход Terraform принципиально отличается от ручного создания ресурсов через веб-консоль облачного провайдера ("ClickOps")?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

IaC описывает инфраструктуру декларативным кодом, который хранится в репозитории, проходит review и применяется автоматически; при ClickOps инженер вносит изменения вручную через UI, и эти изменения нигде не зафиксированы как код.

**Разбор**

Как это работает: Terraform читает конфигурацию в HCL, строит граф зависимостей ресурсов, запрашивает текущее состояние через API провайдера и вычисляет план изменений, необходимых для перехода к описанному в коде состоянию.

На практике: код хранится в git, его можно просмотреть в Pull Request, повторно применить для создания идентичного окружения (например, staging как копия prod) и восстановить инфраструктуру после потери. ClickOps подходит для быстрых экспериментов, но не оставляет истории изменений и не гарантирует повторяемость.

Частые ошибки: считать, что после внедрения Terraform ручные правки в консоли становятся технически невозможны — это не так, их просто не стоит делать, иначе возникнет расхождение (drift) между кодом и реальностью. Вторая ошибка — хранить .tf файлы только локально на ноутбуке инженера без системы контроля версий.

**Пример / кейс**

```hcl
resource "aws_s3_bucket" "logs" {
  bucket = "my-app-logs-bucket"
  tags = {
    Environment = "dev"
  }
}
```

Этот бакет описан в коде и может быть пересоздан в любом аккаунте командой `terraform apply`. Если тот же бакет создать вручную через консоль AWS, `terraform plan` в следующий раз покажет этот ресурс как отсутствующий в state и предложит создать дубликат — явный признак того, что ручные изменения не синхронизированы с кодом.

### 242. Из каких основных строительных блоков состоит типовая конфигурация Terraform (provider, resource, variable, output, data source), и за что отвечает каждый из них?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

provider подключает Terraform к конкретному API (облако, SaaS), resource описывает управляемый объект инфраструктуры, variable параметризует конфигурацию, output возвращает значения после apply, а data source читает уже существующие данные без управления ими.

**Разбор**

Как это работает: каждый блок — декларативная единица: provider задаёт эндпоинт и учётные данные, resource маппится на конкретный API-объект и хранится в state, data source выполняет "только чтение" (например, узнать id текущего VPC), variable и output формируют интерфейс конфигурации для передачи значений снаружи и наружу.

На практике: provider обычно настраивается один раз на корень конфигурации; resource-блоки группируют по файлам (main.tf, network.tf); data source удобен, когда ресурс создан вне Terraform (например, существующий VPC, созданный другой командой); output используют для передачи значений между модулями или для вывода в CI/CD.

Частые ошибки: пытаться "управлять" ресурсом через data source (он read-only и не создаёт/не меняет объект); забывать объявить provider с нужной версией, из-за чего в команде у разных людей применяются разные версии провайдера с разным поведением.

**Пример / кейс**

```hcl
provider "aws" {
  region = "eu-west-1"
}

data "aws_vpc" "default" {
  default = true
}

resource "aws_subnet" "app" {
  vpc_id     = data.aws_vpc.default.id
  cidr_block = "10.0.1.0/24"
}

output "subnet_id" {
  value = aws_subnet.app.id
}
```

После `terraform apply` вывод `subnet_id` покажет id созданной подсети, а `aws_vpc.default` не появится как управляемый ресурс в state — только как прочитанные данные.

### 243. Что такое файл состояния (state) Terraform, и почему Terraform не может работать без него?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

state — это JSON-файл (terraform.tfstate), в котором Terraform хранит соответствие между ресурсами в коде и реальными объектами в инфраструктуре (их ID и атрибуты); без него Terraform не может понять, что уже создано, и будет пытаться создать всё заново или потеряет контроль над существующими ресурсами.

**Разбор**

Как это работает: после каждого apply Terraform записывает в state реальные атрибуты ресурсов (ID, ARN и т.д.), и при следующем plan сравнивает три источника: конфигурацию кода, данные state и реальное состояние API, вычисляя разницу.

На практике: на локальной машине state по умолчанию лежит в файле terraform.tfstate рядом с кодом; в команде такой подход опасен (конфликты, потеря файла), поэтому используют удалённый backend. Состояние может содержать чувствительные данные (пароли, ключи) в открытом виде — это нужно учитывать при настройке доступа.

Частые ошибки: удалять или редактировать state файл вручную текстовым редактором; неправильно настраивать .gitignore — либо случайно коммитить terraform.tfstate в репозиторий (раскрывая секреты и создавая конфликты при параллельной работе), либо терять его без резервной копии.

**Пример / кейс**

```bash
$ cat terraform.tfstate | jq '.resources[0].type'
"aws_s3_bucket"
```

Пример показывает, что state хранит структурированные данные о ресурсе. Потеря этого файла без резервной копии означает, что Terraform "забывает" про уже созданные ресурсы, хотя они продолжают существовать в облаке.

### 244. В чём разница между командами `terraform plan` и `terraform apply`, и почему рекомендуется всегда сначала смотреть план перед применением изменений в важном окружении?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

`terraform plan` только вычисляет и показывает, какие изменения будут внесены, не трогая реальную инфраструктуру, а `terraform apply` выполняет эти изменения (и по умолчанию сам формирует план перед выполнением, запрашивая подтверждение).

**Разбор**

Как это работает: plan строит граф различий между кодом/state и реальным состоянием ресурсов через API-запросы к провайдеру и выводит список действий (create / update in-place / destroy and re-create / destroy) без побочных эффектов, кроме, иногда, обновления данных state при чтении.

На практике: в CI/CD план обычно сохраняется в файл (`terraform plan -out=plan.tfplan`) и прикладывается к Pull Request для review, а затем именно этот сохранённый план применяется (`terraform apply plan.tfplan`), чтобы между просмотром и применением инфраструктура не успела измениться.

Частые ошибки: запускать `apply` без предварительного `plan` в проде "чтобы быстрее"; не замечать в выводе плана строку с destroy для важного ресурса (например, базы данных) из-за невнимательного чтения длинного вывода.

**Пример / кейс**

```text
  # aws_instance.web must be replaced
-/+ resource "aws_instance" "web" {
      ami           = "ami-0123" -> "ami-0456" # forces replacement
      instance_type = "t3.micro"
    }

Plan: 1 to add, 0 to change, 1 to destroy.
```

Символ `-/+` и пометка "forces replacement" означают, что инстанс будет не обновлён на месте, а пересоздан — важно заметить это перед apply, если на инстансе есть несохранённые данные.

### 245. Что такое модуль Terraform, и зачем выносить повторяющиеся блоки resource в отдельный модуль вместо копирования одного и того же кода в нескольких местах?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Модуль — это набор .tf файлов с собственными input-переменными и output-значениями, который можно вызывать (module-блоком) многократно с разными параметрами, что избавляет от копипасты и делает инфраструктуру единообразной и проще в поддержке.

**Разбор**

Как это работает: модуль — обычная папка с конфигурацией, у которой есть "интерфейс" (variables.tf — входы, outputs.tf — выходы); корневая конфигурация вызывает его через `module "name" { source = "./modules/x" ... }`, передавая значения переменных, а Terraform встраивает ресурсы модуля в общий граф.

На практике: типичные модули — "сеть" (VPC/подсети), "кластер БД", "сервис приложения"; при изменении логики внутри модуля достаточно поднять версию и обновить всех потребителей, а не редактировать копии кода в десяти местах.

Частые ошибки: делать модуль слишком узким (на один resource без добавленной логики) или слишком широким (один модуль "на всё"), из-за чего он становится негибким; забывать, что переменные без значения по умолчанию обязательны для вызывающего кода, и не документировать интерфейс модуля.

**Пример / кейс**

```hcl
module "web_bucket" {
  source = "./modules/s3-bucket"
  name   = "web-assets-prod"
  tags   = { Env = "prod" }
}

module "logs_bucket" {
  source = "./modules/s3-bucket"
  name   = "logs-prod"
  tags   = { Env = "prod" }
}
```

Один и тот же модуль `s3-bucket` переиспользуется для двух разных бакетов с разными именами — логика создания бакета (политики, версии, шифрование) описана один раз.

### 246. Что делает команда `terraform init`, и почему её нужно запускать заново после добавления нового provider или модуля в конфигурацию?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

`terraform init` скачивает и устанавливает указанные providers и модули, инициализирует backend для state и подготавливает рабочую директорию (.terraform) к выполнению plan/apply; без неё Terraform не знает, какие плагины использовать.

**Разбор**

Как это работает: Terraform читает блоки `required_providers` и `module.source`, скачивает нужные версии плагинов провайдеров в `.terraform/providers`, а модули — в `.terraform/modules`, и настраивает подключение к backend (например, S3) для хранения state.

На практике: init нужно повторять при клонировании репозитория на новую машину, при добавлении/обновлении провайдера или модуля, при смене backend. В CI/CD это всегда первый шаг пайплайна перед plan.

Частые ошибки: забывать перезапустить init после изменения блока backend (Terraform может продолжать использовать старую конфигурацию до явного `terraform init -reconfigure` или `-migrate-state`); коммитить папку `.terraform` в git, что раздувает репозиторий и может привести к конфликтам версий плагинов.

**Пример / кейс**

```bash
$ terraform init
Initializing the backend...
Initializing provider plugins...
- Finding hashicorp/aws versions matching "~> 5.0"...
- Installing hashicorp/aws v5.31.0...
Terraform has been successfully initialized!
```

После этого вывода появляется папка `.terraform` с установленным провайдером нужной версии, и можно запускать `terraform plan`.

### 247. Какие меры предосторожности нужно предпринять перед выполнением `terraform destroy` на реальном окружении, и как можно удалить только один конкретный ресурс, не затрагивая остальные?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Перед destroy нужно проверить, на каком именно окружении/workspace выполняется команда, посмотреть план удаления и убедиться в наличии актуального бэкапа данных для stateful-сервисов; для удаления одного ресурса лучше удалить его блок из кода и выполнить обычный apply, либо временно использовать `terraform destroy -target=<адрес_ресурса>`.

**Разбор**

Как это работает: `terraform destroy` строит план, в котором каждый управляемый ресурс помечен на удаление, и выполняет его в порядке, обратном зависимостям; флаг `-target` ограничивает план конкретным адресом ресурса, но Terraform всё равно может затронуть зависимые от него ресурсы.

На практике: перед запуском стоит явно проверить переменную окружения/workspace (`terraform workspace show`) и backend-конфигурацию, чтобы не удалить прод вместо dev; для продовых БД нужен подтверждённый недавний снапшот; команду стоит запускать интерактивно с ручным подтверждением, а не в автоматическом non-interactive режиме.

Частые ошибки: использовать `-target` как постоянный способ частичных изменений (HashiCorp рекомендует это только для экстренных ситуаций, так как это может рассинхронизировать state); запускать destroy в CI без ручного approve-шага для прод-окружения.

**Пример / кейс**

```bash
$ terraform plan -destroy -target=aws_instance.worker
$ terraform destroy -target=aws_instance.worker
```

План покажет только `aws_instance.worker` и зависимые от него ресурсы (например, присоединённый EBS том) как помеченные на удаление — перед подтверждением нужно убедиться, что среди них нет ничего, что нужно сохранить.

### 248. Что означает идемпотентность операции в контексте инструментов управления конфигурацией, и почему команда `mkdir /opt/app` не идемпотентна, а Ansible-модуль `ansible.builtin.file` с `state: directory` идемпотентен?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Идемпотентная операция при повторном запуске с теми же параметрами приводит систему к тому же результату без ошибки и без лишних изменений; `mkdir` завершится ошибкой, если папка уже существует, а модуль `file` сначала проверяет текущее состояние и ничего не делает, если каталог уже соответствует описанному.

**Разбор**

Как это работает: идемпотентные инструменты (Ansible-модули, Terraform resource) реализуют логику "сначала проверить текущее состояние, затем применить только недостающие изменения", в отличие от императивных команд, которые просто выполняют действие без проверки состояния.

На практике: идемпотентность позволяет безопасно перезапускать playbook или `terraform apply` многократно (например, после сбоя сети в середине выполнения) и получать предсказуемый результат; это основа для автоматизации без ручного контроля "а что уже сделано".

Частые ошибки: использовать модуль `command`/`shell` в Ansible для действий, у которых есть специализированный идемпотентный модуль, из-за чего playbook при повторном запуске либо падает, либо каждый раз выполняет ненужное действие и помечается как "changed".

**Пример / кейс**

```yaml
- name: Создать директорию приложения
  ansible.builtin.file:
    path: /opt/app
    state: directory
    mode: "0755"
```

При первом запуске Ansible покажет `changed`, при повторном запуске без изменений в системе — `ok` (без изменений), что и является признаком идемпотентности.

### 249. Что такое inventory-файл в Ansible, и как описать в нём статическую группировку хостов по ролям (например, web и db)?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Inventory — это файл (INI или YAML), в котором перечислены управляемые хосты и их группировка, используемая для нацеливания playbook на нужный набор серверов; в простом варианте это статический список IP/имён, сгруппированных по заголовкам секций.

**Разбор**

Как это работает: Ansible читает inventory и строит внутреннее представление хостов и групп с переменными (host_vars/group_vars); playbook указывает целевую группу в поле `hosts:`, и Ansible подключается к каждому хосту из неё по SSH (или WinRM) для выполнения задач.

На практике: статический inventory подходит для небольших и стабильных окружений; группы можно вкладывать друг в друга (`[prod:children]`), а переменные, общие для группы, выносить в `group_vars/<имя_группы>.yml`, чтобы не повторять их в playbook.

Частые ошибки: хранить пароли или ключи прямо в inventory в открытом виде; забывать, что имя хоста в inventory должно быть разрешаемым (DNS/hosts-файл), или явно не указывать `ansible_host` с IP-адресом, когда имя не резолвится.

**Пример / кейс**

```ini
[web]
web1.example.com
web2.example.com

[db]
db1.example.com ansible_host=10.0.0.5

[prod:children]
web
db
```

Playbook с `hosts: web` выполнится только на web1 и web2, а `hosts: prod` — на всех четырёх хостах благодаря группе-родителю `prod`.

### 250. В чём разница между ad-hoc командой Ansible (`ansible ... -m ...`) и playbook, и когда уместно использовать каждый из этих способов?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Ad-hoc команда выполняет одно разовое действие на выбранных хостах прямо из командной строки без сохранения в файл, а playbook — декларативный YAML-файл с последовательностью задач, который можно версионировать, переиспользовать и review-ить; ad-hoc хорош для быстрой диагностики или разовой операции, playbook — для повторяемой автоматизации.

**Разбор**

Как это работает: ad-hoc команда вызывает ровно один модуль с заданными аргументами на указанной группе хостов и сразу выводит результат; playbook описывает набор "play", каждый из которых применяет список задач (каждая — вызов модуля) к группе хостов, с поддержкой handlers, условий, переменных и тегов.

На практике: ad-hoc удобен для проверки состояния ("узнать uptime на всех веб-серверах"), перезапуска одного сервиса в экстренной ситуации или быстрой проверки факта; для всего, что должно повторяться регулярно или быть частью процесса, нужен playbook в git.

Частые ошибки: использовать ad-hoc команды для продовых изменений конфигурации без фиксации того, что было сделано (никакой истории изменений не остаётся); пытаться засунуть сложную логику с условиями и хендлерами в ad-hoc-вызов, хотя это явный признак того, что нужен playbook.

**Пример / кейс**

```bash
$ ansible web -m ansible.builtin.service -a "name=nginx state=restarted" -b
```

Эта команда разово перезапускает nginx на всех хостах группы `web` с повышением привилегий (`-b`), но результат никуда не сохраняется как код — для регулярного использования такое действие стоит оформить задачей в playbook.

### 251. Какова базовая структура playbook в Ansible (play, hosts, tasks), и как выглядит простой playbook, устанавливающий и запускающий nginx?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Playbook — это список одного или нескольких "play", каждый из которых задаёт целевые хосты (`hosts`), опционально режим повышения привилегий (`become`) и список задач (`tasks`), где каждая задача вызывает конкретный модуль с параметрами.

**Разбор**

Как это работает: Ansible выполняет play последовательно сверху вниз, а внутри play — задачи по порядку на всех целевых хостах параллельно (с учётом `forks`); каждая задача — пара "имя модуля + аргументы", и её результат (changed/ok/failed) влияет на то, сработают ли связанные handlers.

На практике: play обычно группируют по логическому назначению (например, отдельный play для настройки firewall, отдельный — для деплоя приложения); имена задач (`name:`) важны для читаемости вывода и логов выполнения.

Частые ошибки: смешивать в одном play задачи, относящиеся к разным ролям серверов, без разделения по `hosts:`; забывать `become: true` там, где модулю нужны root-права, из-за чего задача падает с ошибкой доступа.

**Пример / кейс**

```yaml
- name: Установить и запустить nginx
  hosts: web
  become: true
  tasks:
    - name: Установить пакет nginx
      ansible.builtin.apt:
        name: nginx
        state: present

    - name: Убедиться, что nginx запущен
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

При запуске `ansible-playbook` на хостах без nginx обе задачи покажут `changed`; при повторном запуске на том же хосте — `ok`, подтверждая идемпотентность.

### 252. Какова стандартная структура директорий роли Ansible (`tasks/`, `handlers/`, `templates/`, `defaults/`, `vars/`), и зачем выносить логику в роль вместо одного большого playbook?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Роль — это переиспользуемый пакет автоматизации со стандартизированной структурой папок (tasks, handlers, templates, files, defaults, vars, meta), который можно подключать к разным playbook и окружениям; вынесение логики в роль избавляет от дублирования и упрощает повторное использование между проектами.

**Разбор**

Как это работает: Ansible автоматически подхватывает файлы роли по соглашению об именах — `tasks/main.yml` выполняется при подключении роли, `handlers/main.yml` содержит обработчики уведомлений, `templates/` хранит Jinja2-шаблоны конфигов, `defaults/main.yml` задаёт переменные с низким приоритетом (легко переопределить), `vars/main.yml` — с высоким.

На практике: роли публикуют и переиспользуют через Ansible Galaxy или приватный репозиторий; типичный playbook сводится к списку ролей, применяемых к группе хостов, что делает его компактным и декларативным.

Частые ошибки: путать `defaults` и `vars` по приоритету переопределения, из-за чего переменная из `group_vars` неожиданно не переопределяет значение из `vars/main.yml` роли; складывать все задачи проекта в одну "универсальную" роль вместо логического разделения.

**Пример / кейс**

```text
roles/
  nginx/
    tasks/main.yml
    handlers/main.yml
    templates/nginx.conf.j2
    defaults/main.yml
```

Playbook подключает роль так: `roles: [ nginx ]` — вся логика установки и настройки nginx переиспользуется для любого проекта, где достаточно этой роли.

### 253. Как работают handlers и директива `notify` в Ansible, и почему перезапуск сервиса стоит оформлять через handler, а не как обычную задачу после изменения конфига?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Handler — это задача, которая запускается только тогда, когда её явно "уведомила" (notify) другая задача, помеченная как changed, и выполняется один раз в конце play даже если уведомлений было несколько; это позволяет перезапускать сервис только при реальном изменении конфигурации, а не при каждом запуске playbook.

**Разбор**

Как это работает: задача с `notify: <имя handler>` добавляет handler в очередь только если её статус — changed; в конце play (или раньше, если явно вызван flush_handlers) Ansible выполняет каждый уникальный handler из очереди ровно один раз, независимо от того, сколько задач его вызвали.

На практике: типичный паттерн — задача шаблонирования конфига (`template`) уведомляет handler "restart service"; если конфиг не изменился, handler не сработает, и сервис не будет перезапущен без необходимости, что снижает downtime при частых прогонах playbook.

Частые ошибки: ставить обычную задачу `service: state=restarted` сразу после задачи шаблонирования без notify — тогда сервис будет перезапускаться при каждом запуске playbook независимо от того, изменился ли конфиг; забывать, что handlers по умолчанию выполняются в конце play, а не сразу в месте notify.

**Пример / кейс**

```yaml
tasks:
  - name: Обновить конфиг nginx
    ansible.builtin.template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify: Перезапустить nginx

handlers:
  - name: Перезапустить nginx
    ansible.builtin.service:
      name: nginx
      state: restarted
```

Если шаблон не изменился, задача вернёт `ok` и handler не выполнится — nginx продолжит работать без перезапуска.

### 254. Для чего используется Ansible Vault, и как зашифровать файл с переменными, содержащими пароли, чтобы безопасно хранить его в git?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Ansible Vault шифрует файлы (или отдельные строки) с чувствительными данными симметричным шифрованием по паролю/ключу, позволяя безопасно хранить секреты в репозитории рядом с остальным кодом и расшифровывать их только во время выполнения playbook.

**Разбор**

Как это работает: команда `ansible-vault encrypt` шифрует YAML-файл целиком (AES256) под паролем, который хранится отдельно (менеджер секретов, файл с ограниченным доступом, переменная окружения); при запуске playbook Ansible расшифровывает файл "на лету", получив пароль через `--ask-vault-pass`, `--vault-password-file` или интеграцию с внешним менеджером секретов.

На практике: распространённый паттерн — хранить обычные переменные в `vars.yml`, а секреты в `vault.yml`, зашифрованном Vault, и подключать оба файла; для разных окружений можно использовать разные vault-пароли (`vault-id`), чтобы доступ к prod-секретам был ограничен.

Частые ошибки: закоммитить расшифрованный файл по ошибке из-за отсутствия pre-commit/CI проверки на незашифрованные секреты; хранить vault-пароль в том же репозитории, что полностью обесценивает шифрование.

**Пример / кейс**

```bash
$ ansible-vault encrypt group_vars/prod/vault.yml
$ ansible-playbook site.yml --vault-password-file ~/.vault_pass.txt
```

После шифрования файл в git выглядит как `$ANSIBLE_VAULT;1.1;AES256` и бинарный блоб — без пароля его содержимое прочитать невозможно, а playbook расшифровывает его только во время выполнения.

### 255. Что такое Helm chart, файл `values.yaml` и папка `templates/` — за что отвечает каждая из этих частей при развёртывании приложения в Kubernetes?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Helm chart — это упакованный набор шаблонов Kubernetes-манифестов с метаданными; `values.yaml` задаёт настраиваемые параметры по умолчанию (например, количество реплик, образ), а `templates/` содержит Go-шаблоны манифестов, которые Helm рендерит, подставляя значения из values, в итоговые YAML для применения в кластер.

**Разбор**

Как это работает: при `helm install`/`helm upgrade` Helm объединяет значения из `values.yaml` чарта, файлов `-f custom-values.yaml` и флагов `--set` (по возрастанию приоритета), рендерит шаблоны из `templates/` с этими значениями через Go template engine и применяет получившиеся манифесты в кластер, сохраняя релиз как отдельный объект (Secret) для истории.

На практике: один и тот же chart переиспользуется для разных окружений за счёт разных values-файлов (`values-dev.yaml`, `values-prod.yaml`), без изменения самих шаблонов; это аналог "модуля" в Terraform, но для Kubernetes-манифестов.

Частые ошибки: хардкодить значения прямо в templates вместо вынесения их в values (это убивает переиспользуемость); не указывать значения по умолчанию для обязательных параметров, из-за чего chart ломается при install без явного `-f`.

**Пример / кейс**

```yaml
# values.yaml
replicaCount: 2
image:
  repository: myapp
  tag: "1.4.0"
```

```yaml
# templates/deployment.yaml (фрагмент)
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

`helm template .` покажет итоговый YAML с `replicas: 2` и образом `myapp:1.4.0` — именно это будет применено в кластер.

### 256. В чём разница между `helm install` и `helm upgrade`, и что произойдёт, если по ошибке запустить `helm install` для релиза, который уже существует?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

`helm install` создаёт новый релиз в кластере, а `helm upgrade` применяет изменения (новую версию chart или values) к уже существующему релизу, сохраняя историю ревизий; повторный `helm install` с тем же именем релиза завершится ошибкой "cannot re-use a name that is still in use".

**Разбор**

Как это работает: Helm хранит метаданные каждого релиза (включая отрендеренные манифесты каждой ревизии) как Kubernetes Secret в namespace релиза; `upgrade` сравнивает текущую (последнюю) ревизию с новой и применяет diff через серверный apply, увеличивая номер ревизии, что и даёт возможность `helm rollback`.

На практике: для идемпотентного деплоя из CI/CD часто используют `helm upgrade --install`, которая создаёт релиз, если его нет, или обновляет, если есть — это избавляет от необходимости различать первый и последующие деплои в пайплайне.

Частые ошибки: использовать `helm install` в CI/CD без флага `--install` на upgrade, из-за чего второй и последующие запуски пайплайна падают с ошибкой "already exists"; не указывать `--namespace` явно, из-за чего релиз неожиданно попадает в namespace `default`.

**Пример / кейс**

```bash
$ helm upgrade --install myapp ./chart -f values-prod.yaml -n prod
```

Команда создаст релиз `myapp`, если он отсутствует в namespace `prod`, или обновит его до новой ревизии, если уже существует — такой вызов безопасно повторять в пайплайне при каждом деплое.

### 257. Что такое Kustomize, и как устроена базовая структура "base + overlay" для генерации немного различающихся манифестов под разные окружения без Helm?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Kustomize — встроенный в kubectl инструмент для декларативной настройки "чистых" Kubernetes-манифестов без шаблонизации: есть базовый набор манифестов (`base`) и оверлеи (`overlays/dev`, `overlays/prod`), которые ссылаются на base и применяют к нему патчи без копирования и редактирования всего YAML.

**Разбор**

Как это работает: каждая папка содержит файл `kustomization.yaml`, перечисляющий входные ресурсы (`resources:`) и патчи/генераторы; оверлей указывает `base` как один из resources и добавляет свои патчи, а команда `kubectl kustomize` (или `kustomize build`) рекурсивно собирает финальный YAML, объединяя base и патчи оверлея.

На практике: Kustomize удобен, когда манифесты в целом одинаковы, а различия между окружениями минимальны (реплики, лимиты ресурсов, namespace, суффиксы имён); в отличие от Helm, здесь нет шаблонного языка и условной логики — только декларативные патчи поверх валидного YAML.

Частые ошибки: пытаться засунуть сложную условную логику в Kustomize (для этого больше подходит Helm); забывать, что оверлей не "наследует" base автоматически без явного указания его в `resources:` своего kustomization.yaml.

**Пример / кейс**

```yaml
# base/kustomization.yaml
resources:
  - deployment.yaml

# overlays/prod/kustomization.yaml
resources:
  - ../../base
patches:
  - target:
      kind: Deployment
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 5
```

`kubectl kustomize overlays/prod` выведет итоговый Deployment с `replicas: 5`, при этом сам base-файл остаётся неизменным и общим для всех окружений.

### 258. Что такое drift (расхождение) конфигурации в контексте IaC, и как он может возникнуть, даже если никто не редактировал .tf или Ansible-код?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Drift — это расхождение между описанным в коде желаемым состоянием и фактическим состоянием инфраструктуры; он возникает, когда кто-то (человек или другой процесс) меняет ресурс напрямую — через консоль, CLI облака, автомасштабирование или другой инструмент — минуя Terraform/Ansible.

**Разбор**

Как это работает: Terraform узнаёт о реальном состоянии только во время plan/apply (запрашивая его через API провайдера) — между запусками инфраструктура может измениться незаметно для инструмента; Ansible, в отличие от Terraform, обычно не хранит state и просто применяет задачи заново, поэтому drift там проявляется иначе — как "незапланированные" changed-задачи при следующем прогоне.

На практике: типичные причины drift — инженер вручную поправил security group "на скорую руку" во время инцидента; автомасштабирование изменило количество инстансов; другой инструмент изменил тег ресурса; drift обнаруживают регулярным запуском `terraform plan` (без apply) и сравнением вывода.

Частые ошибки: игнорировать непустой `terraform plan` в CI как "шум"; не фиксировать в процессе, что любое экстренное ручное изменение должно быть как можно скорее отражено в коде, из-за чего drift накапливается и со временем план становится нечитаемым.

**Пример / кейс**

```text
  # aws_security_group.app has changed outside of Terraform
  ~ resource "aws_security_group" "app" {
      ~ ingress = [
          + { from_port = 22, to_port = 22, cidr_blocks = ["0.0.0.0/0"] },
        ]
    }
```

Такой вывод `terraform plan` означает, что кто-то вручную открыл порт 22 для всех — Terraform предложит либо откатить это изменение при apply, либо нужно явно внести его в код, если оно легитимно.

### 259. Для чего нужны файлы `*.tfvars` в Terraform, и каким образом можно передать в конфигурацию значения переменных для разных окружений (dev/prod)?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

`.tfvars`-файлы содержат значения входных переменных конфигурации в формате `имя = значение` и подключаются через флаг `-var-file`, что позволяет использовать одну и ту же конфигурацию с разными наборами значений для разных окружений без изменения кода.

**Разбор**

Как это работает: Terraform собирает значения переменных из нескольких источников с определённым приоритетом: значения по умолчанию в `variable` блоке, файлы `terraform.tfvars`/`*.auto.tfvars` (подключаются автоматически), явно указанные `-var-file`, флаги `-var` и переменные окружения `TF_VAR_*` — более специфичный источник переопределяет более общий.

На практике: типичный паттерн — `environments/dev.tfvars` и `environments/prod.tfvars` с одинаковым набором имён переменных, но разными значениями (размер инстанса, количество реплик, CIDR), и один и тот же код применяется с флагом `-var-file=environments/prod.tfvars`.

Частые ошибки: хранить чувствительные значения (пароли) прямо в `.tfvars` и коммитить файл в git; путать приоритет источников и удивляться, почему значение из `-var` не применилось, хотя на самом деле более приоритетный `*.auto.tfvars` его перекрыл.

**Пример / кейс**

```hcl
# environments/prod.tfvars
instance_type  = "m5.large"
instance_count = 4
```

```bash
$ terraform apply -var-file=environments/prod.tfvars
```

Та же самая конфигурация с `environments/dev.tfvars` (например, `instance_type = "t3.micro"`, `instance_count = 1`) создаст заметно более дешёвое и маленькое окружение без единой правки .tf файлов.

### 260. Для чего используется блок `output` в Terraform, и как получить значение output уже применённой конфигурации без повторного apply?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

`output` возвращает значения атрибутов ресурсов после apply (например, IP адрес, ARN, URL) для использования человеком, CI/CD-пайплайном или другим модулем/конфигурацией; посмотреть их повторно можно командой `terraform output` без необходимости что-либо применять заново.

**Разбор**

Как это работает: значения outputs сохраняются в state вместе с ресурсами; `terraform output` просто читает их оттуда, а `terraform output -json` отдаёт их в машиночитаемом формате для скриптов.

На практике: outputs часто используют для передачи данных между слоями инфраструктуры (например, сетевой модуль выводит `vpc_id`, а конфигурация приложения читает его через `terraform_remote_state` data source или напрямую как output родительского модуля); в CI/CD output с адресом балансировщика можно подставить в smoke-тест после деплоя.

Частые ошибки: пытаться получить output до первого успешного apply (значения просто отсутствуют в state); выводить чувствительные данные (пароли) в output без флага `sensitive = true`, из-за чего они светятся в логах CI/CD в открытом виде.

**Пример / кейс**

```hcl
output "db_endpoint" {
  value     = aws_db_instance.main.endpoint
  sensitive = true
}
```

```bash
$ terraform output db_endpoint
"<sensitive>"
$ terraform output -json db_endpoint
"mydb.abc123.eu-west-1.rds.amazonaws.com:5432"
```

Пометка `sensitive = true` скрывает значение в обычном выводе CLI, но не блокирует доступ к нему через `-json` — это не замена нормального секрет-менеджмента.

### 261. Прочитайте фрагмент вывода `terraform plan` ниже и объясните, что означают символы `+`, `-`, `~` и `-/+`, а также итоговую строку с количеством действий.

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

`+` означает создание нового ресурса, `-` — удаление существующего, `~` — изменение атрибутов на месте без пересоздания, а `-/+` означает удаление и создание нового ресурса взамен (replacement); итоговая строка суммирует количество ресурсов по каждому типу действия.

**Разбор**

Как это работает: Terraform вычисляет эти символы, сравнивая желаемую конфигурацию с данными из state (и опционально свежим refresh реального состояния); "updated in-place" означает, что провайдер поддерживает изменение этого атрибута без простоя и пересоздания ресурса (как в случае с тегами).

На практике: перед apply важно просматривать не только итоговую строку с числами, а каждый блок изменений — особенно обращая внимание на `-` (destroy) и `-/+` (replace), так как они могут означать потерю данных или простой сервиса, если ресурс содержит state (например, EBS-том, база данных).

Частые ошибки: считать, что раз итоговая строка выглядит компактно, то можно не читать детали; не замечать удаление ресурса, если он на самом деле ещё используется приложением и его удаление вручную убрали из кода по ошибке, а не намеренно.

**Пример / кейс**

```text
Terraform will perform the following actions:

  # aws_instance.cache will be created
  + resource "aws_instance" "cache" {
      + ami           = "ami-0abc"
      + instance_type = "t3.small"
    }

  # aws_s3_bucket.old will be destroyed
  - resource "aws_s3_bucket" "old" {
      - bucket = "legacy-bucket"
    }

  # aws_instance.web will be updated in-place
  ~ resource "aws_instance" "web" {
      ~ tags = {
          ~ "Owner" = "alice" -> "bob"
        }
    }

Plan: 1 to add, 1 to change, 1 to destroy.
```

Ожидаемая проверка: перед `terraform apply` в важном окружении нужно явно подтвердить, что бакет `legacy-bucket` действительно предназначен для удаления, иначе остановить apply и скорректировать код.

### 262. Что делает режим `--check` (и `--diff`) в Ansible, и почему прогон playbook в check mode не всегда на 100% точно предсказывает результат обычного запуска?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

`--check` выполняет playbook в "сухом" режиме, показывая, какие задачи считались бы `changed`, без реального применения изменений, а `--diff` дополнительно показывает построчное различие для изменяемых файлов/шаблонов; точность ограничена тем, что не все модули полностью поддерживают check mode, а некоторые задачи зависят от результата предыдущих (ещё не реально выполненных) задач.

**Разбор**

Как это работает: в check mode каждый модуль, поддерживающий этот режим, выполняет только проверку текущего состояния системы и сравнение с желаемым, не выполняя реального изменения; модули без явной поддержки check mode либо пропускаются, либо могут вести себя непредсказуемо.

На практике: `--check --diff` используют как предварительный просмотр перед применением playbook к продовым серверам, аналогично `terraform plan`; это особенно полезно перед массовым раскатом изменений конфигурации на большую группу хостов.

Частые ошибки: полностью доверять check mode для playbook с большим количеством задач `command`/`shell`, которые не умеют нормально работать в режиме проверки и либо помечаются как "always changed", либо пропускаются, искажая картину; не использовать `--diff` и упускать, что именно изменится внутри шаблона конфигурации.

**Пример / кейс**

```bash
$ ansible-playbook site.yml --check --diff --limit web1
```

Вывод покажет для задачи `template` построчный diff будущего `nginx.conf` без реального изменения файла на web1 — удобно для review перед реальным запуском на всю группу `web`.

### 263. Чем принципиально отличается подход Helm (шаблонизация с values) от подхода Kustomize (патчи поверх чистых манифестов), и в какой ситуации новичку будет проще выбрать Kustomize, а не Helm?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

Helm использует шаблонный язык (Go templates) и подстановку значений из values.yaml в заготовки манифестов с версионируемыми "релизами", а Kustomize работает без шаблонов, просто накладывая декларативные патчи на валидные YAML-манифесты; Kustomize проще выбрать, когда манифесты почти одинаковы между окружениями и нет необходимости в пакетировании/версионировании чарта как отдельного артефакта.

**Разбор**

Как это работает: в Helm шаблоны содержат конструкции `{{ .Values.x }}`, `{{ if }}`, `{{ range }}`, что даёт гибкость, но требует понимания шаблонного языка и усложняет чтение "сырых" манифестов до рендера; Kustomize хранит сами манифесты в валидном YAML и описывает только дельту (патчи, генераторы ConfigMap/Secret, смену namespace/префиксов), что проще читать напрямую.

На практике: Kustomize встроен в `kubectl` (`kubectl apply -k`) и не требует установки дополнительного CLI, что снижает порог входа для небольших проектов; Helm предпочтительнее, когда нужно публиковать приложение как переиспользуемый артефакт с зависимостями, хуками и системой релизов/rollback.

Частые ошибки: думать, что Kustomize и Helm взаимоисключающие — на практике их комбинируют (Kustomize как post-processing над `helm template`); выбирать Helm "по умолчанию" для простого внутреннего сервиса с двумя окружениями, где хватило бы пары патчей Kustomize, и получать лишнюю сложность шаблонов без реальной потребности в ней.

**Пример / кейс**

```bash
$ kubectl apply -k overlays/dev
```

Для небольшого внутреннего сервиса с двумя окружениями (dev/prod), отличающимися только количеством реплик и лимитами ресурсов, такой overlay читается как обычный YAML с одним патчем — без необходимости изучать синтаксис шаблонов Helm.

### 264. Что проверяют команды `terraform fmt` и `terraform validate`, и почему успешный `terraform validate` не гарантирует, что `terraform apply` пройдёт без ошибок?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Junior

**Короткий ответ**

`terraform fmt` приводит код к единому стилю форматирования (отступы, выравнивание), а `terraform validate` проверяет синтаксическую корректность и внутреннюю согласованность конфигурации без обращения к реальному API провайдера — поэтому ошибки, зависящие от реального состояния облака (квоты, права доступа, занятые имена), validate не отловит.

**Разбор**

Как это работает: `validate` работает локально, разбирая HCL и проверяя схему ресурсов из уже установленных провайдеров (после `terraform init`), но не выполняет сетевые запросы к облаку и не знает о внешних ограничениях; `fmt` просто переформатирует файлы по канонизированным правилам HCL и ничего не проверяет по смыслу.

На практике: оба инструмента полезно запускать в CI как самый быстрый и дешёвый первый шаг pipeline (до plan), отбраковывая явные ошибки раньше, чем кто-либо начнёт ждать результат plan; `fmt -check` в CI (без изменения файлов) используют, чтобы требовать единообразного стиля в Pull Request.

Частые ошибки: считать прохождение `validate` достаточной гарантией успешного apply и пропускать этап `plan`/review; не настраивать `fmt -check` в CI, из-за чего в репозитории копится разнородно отформатированный код, усложняющий diff в Pull Request.

**Пример / кейс**

```bash
$ terraform fmt -check -recursive
$ terraform validate
Success! The configuration is valid.
```

Даже получив "Success", `terraform apply` может упасть с ошибкой вроде "BucketAlreadyExists" или "InvalidClientTokenId", так как такие проблемы видны только при реальном обращении к API во время plan/apply.

### 265. Два CI-джоба почти одновременно запустили `terraform apply` на один и тот же remote state, и второй завис с ошибкой `Error acquiring the state lock`, а первый после этого аварийно упал по таймауту раннера, не освободив лок. Что такое state locking в Terraform, зачем он нужен и как безопасно разблокировать state в этой ситуации?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

State locking — это механизм, которым Terraform блокирует state в remote backend на время `plan`/`apply`, чтобы два процесса не писали в него параллельно и не повредили данные; если лок «подвис» из-за аварийного завершения процесса, нужно убедиться, что никакой apply реально не выполняется, и снять именно этот лок командой `terraform force-unlock <LOCK_ID>`, а не трогать state вручную.

**Разбор**

Как это работает: backend с поддержкой locking (например, S3 backend с таблицей DynamoDB для блокировок, или Terraform Cloud/Consul) перед изменением state создаёт отдельную запись-лок с идентификатором операции, временем и информацией о том, кто её запустил; любой другой процесс, пытающийся получить тот же лок, получает отказ и сообщение с LOCK ID, пока запись не удалена.

На практике: перед `force-unlock` нужно проверить в самой системе хранения лока (например, в таблице DynamoDB или в логах CI) статус первого джоба и убедиться, что его процесс действительно завершён, а не просто «долго думает»; после подтверждения выполняется `terraform force-unlock <LOCK_ID>` с указанием точного идентификатора, а не массовая очистка; в команде это стоит сопровождать алертом в CI, чтобы зависшие локи не оставались незамеченными.

Частые ошибки: частая ошибка — снимать лок «на всякий случай», пока первый apply физически ещё работает, из-за чего два apply одновременно пишут в один state и он повреждается; другая ошибка — хранить state локально без backend с locking при работе нескольких инженеров или CI-джобов, из-за чего блокировки вообще не возникает и гонка состояний остаётся незамеченной до тех пор, пока не испортится реальная инфраструктура.

**Пример / кейс**

```bash
$ terraform apply
Error acquiring the state lock

Lock Info:
  ID:        7c4d1a2e-91f3-4b2a-9a7e-1a2b3c4d5e6f
  Path:      env/prod/terraform.tfstate
  Operation: OpenTofu/Terraform apply
  Who:       ci-runner-42
  Created:   2026-10-04 12:01:03 UTC

# после подтверждения, что ci-runner-42 действительно мёртв:
$ terraform force-unlock 7c4d1a2e-91f3-4b2a-9a7e-1a2b3c4d5e6f
```

Ожидаемое поведение: после подтверждённого `force-unlock` следующий `terraform plan`/`apply` должен успешно получить лок; если же процесс-владелец лока на самом деле ещё жив, после снятия лока оба процесса начнут писать в state параллельно, что видно по конфликтующим изменениям в последующем `plan`.


### 266. Команда несколько месяцев хранила `terraform.tfstate` локально в git-репозитории, и теперь нужно перейти на remote backend (например, S3 + DynamoDB) без потери истории ресурсов и без простоя инфраструктуры. Какие шаги нужно выполнить для безопасной миграции state, и почему просто скопировать файл в S3 недостаточно?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Нужно описать новый backend в конфигурации, выполнить `terraform init -migrate-state`, которая скопирует существующий state в новое хранилище и подтвердит это, а также немедленно удалить `terraform.tfstate` из git и добавить файл в `.gitignore`; просто скопировать файл в S3 вручную недостаточно, потому что Terraform должен сам обновить метаданные backend и включить locking, а ручное копирование не гарантирует согласованность и не настраивает блокировки.

**Разбор**

Как это работает: блок `backend` в конфигурации описывает, где Terraform хранит state и как блокирует его; при смене backend Terraform сравнивает текущий (locally known) state с целевым хранилищем и при `-migrate-state` переносит содержимое, сохраняя serial-номер версии state, чтобы не создать рассинхронизацию между старым и новым источником истины.

На практике: перед миграцией стоит сделать резервную копию текущего state (`terraform state pull > backup.tfstate`), выполнить миграцию на некритичном окне, когда никто не запускает apply, и сразу после миграции проверить `terraform plan` — он должен показать отсутствие изменений (no-op), что подтверждает успешный перенос; также нужно включить versioning на S3-бакете и таблицу DynamoDB для locking, чтобы получить защиту от конкурентной записи.

Частые ошибки: частая ошибка — вручную загрузить файл state в S3 через CLI/консоль без `terraform init -migrate-state`, из-за чего локальный backend продолжает считаться активным и следующий apply создаёт ресурсы заново или теряет связь с реальными; ещё одна ошибка — не включить versioning на бакете, из-за чего при случайной порче state нет возможности откатиться к предыдущей версии.

**Пример / кейс**

```hcl
terraform {
  backend "s3" {
    bucket         = "acme-tfstate-prod"
    key            = "env/prod/terraform.tfstate"
    region         = "eu-central-1"
    dynamodb_table = "acme-tf-locks"
    encrypt        = true
  }
}
```
```bash
$ terraform init -migrate-state
Terraform detected that the backend type changed from "local" to "s3"...
Do you want to copy existing state to the new backend? yes
```

Ожидаемое поведение: после миграции `terraform plan` должен сообщить `No changes. Your infrastructure matches the configuration.`; файл `terraform.tfstate` локально больше не должен обновляться, а новые записи должны появляться в S3-бакете с включённым versioning.


### 267. Как использовать `terraform state mv` и `terraform import` для этих задач, и в чём риск, если пропустить этот шаг?

**Направление:** DevOps Engineer

**Уровень:** Middle

**Короткий ответ**

`terraform state mv` меняет адрес ресурса внутри state без обращения к облачному API, что позволяет переименовать или переместить ресурс в конфигурации без его пересоздания; `terraform import` добавляет в state привязку между уже существующим реальным ресурсом и адресом ресурса в конфигурации (начиная с Terraform 1.5 то же можно делать декларативно через блок `import`); если просто переименовать ресурс в коде без `state mv`, Terraform решит, что старый ресурс нужно удалить, а новый создать, что может вызвать простой.

**Разбор**

Как это работает: Terraform сопоставляет блоки конфигурации с объектами в state по адресу ресурса (`тип.имя` или с учётом модуля); если адрес в коде не совпадает с адресом в state, Terraform считает старый объект «удалённым из конфигурации» и планирует destroy, а новый блок — созданием нового ресурса, даже если по факту это один и тот же облачный объект.

На практике: перед `state mv` и `import` обязательно делается backup state (`terraform state pull > backup.tfstate`), затем выполняется команда, после чего обязательно запускается `terraform plan`, который должен показать `No changes` (для mv) или минимальные изменения, связанные с доведением атрибутов до соответствия конфигурации (для import, где часть атрибутов может быть не указана в коде); для множества ресурсов в Terraform 1.1+ удобнее декларативный блок `moved`, который фиксирует переименования в самой конфигурации и не требует ручных команд при каждом apply.

Частые ошибки: частая ошибка — переименовать ресурс в `.tf`-файле и сразу запустить `apply`, не проверив план, что приводит к неожиданному destroy/create на проде; при `import` — забыть прописать в конфигурации все атрибуты, которые реально заданы у существующего ресурса, из-за чего следующий `plan` попытается привести ресурс к дефолтным/неверным значениям.

**Пример / кейс**

```bash
# переименование ресурса без пересоздания
$ terraform state mv aws_instance.web aws_instance.app

# привязка уже существующего ресурса (id из облака) к конфигурации
$ terraform import aws_instance.app i-0abcd1234ef567890
```
```hcl
# альтернатива в Terraform 1.1+ прямо в конфигурации
moved {
  from = aws_instance.web
  to   = aws_instance.app
}
```

Ожидаемое поведение: после `state mv`/`import` команда `terraform plan` должна показывать `No changes` (если конфигурация точно описывает текущие атрибуты ресурса), а не план на удаление и создание.


### 268. В команде спорят, как организовать окружения dev/staging/prod в Terraform: через встроенные workspaces (`terraform workspace new prod`) с одной и той же конфигурацией, или через отдельные директории/state-файлы на каждое окружение. В чём разница этих подходов и какие практические проблемы возникают при использовании workspaces для окружений с разным набором ресурсов?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Workspaces дают один и тот же код конфигурации с разными state-файлами, переключаемыми командой `terraform workspace select`, что удобно для небольших различий (например, разный `count`/`var.environment`), но плохо подходит, когда окружения должны отличаться структурно (разные ресурсы, разные провайдеры, разный доступ), — для таких случаев лучше отдельные директории (или отдельные корневые модули) с явно разным backend key на каждое окружение.

**Разбор**

Как это работает: workspace — это просто именованный префикс для state внутри одного backend (например, отдельный файл или путь в S3 на каждый workspace), конфигурация `.tf`-файлов остаётся общей, а различия между окружениями выражаются через `terraform.workspace` в выражениях или через переменные, подставляемые отдельно для каждого workspace.

На практике: workspaces хорошо работают, когда окружения действительно похожи (например, несколько feature-веток одного и того же набора ресурсов для review), но для prod/staging/dev с разным уровнем доступа и разными политиками безопасности рекомендуют отдельные корневые конфигурации с общими модулями, чтобы можно было применять разные права IAM, разные approval-процессы и избегать ситуации, когда разработчик по ошибке применяет prod-конфигурацию, забыв переключить workspace.

Частые ошибки: частая ошибка — положиться только на `terraform workspace select prod` как единственную защиту от применения кода к прод-окружению, без отдельного backend/разных учётных данных, из-за чего забытый `workspace select` приводит к применению тестовых изменений к production state; ещё одна ошибка — использовать `terraform.workspace` в именах ресурсов без проверки, что это не приводит к превышению лимитов на длину имён у облачного провайдера.

**Пример / кейс**

```bash
$ terraform workspace new staging
$ terraform workspace select staging
$ terraform apply -var-file=staging.tfvars
```
```hcl
resource "aws_s3_bucket" "logs" {
  bucket = "acme-logs-${terraform.workspace}"
}
```

Ожидаемое поведение: `terraform workspace list` показывает текущий активный workspace звёздочкой; для prod лучше дополнительно проверять в CI, что переменная окружения/backend соответствуют ожидаемому workspace, прежде чем разрешать `apply`.


### 269. Несколько команд в организации используют общий модуль Terraform из внутреннего Git-репозитория для создания виртуальных машин. После обновления модуля без изменения версии в коде потребителей у части команд внезапно поменялось поведение `apply`. Как правильно фиксировать версию модуля при подключении, и какие риски создаёт отсутствие версионирования модулей?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Версию модуля нужно явно указывать через параметр `version` (для модулей из Terraform Registry) или через ref на конкретный тег/коммит Git (`?ref=v1.4.0`) в source, а не на `main`/`master`; без фиксированной версии любое обновление кода модуля немедленно и незаметно влияет на всех потребителей при следующем `terraform init -upgrade` или даже при обычном `init`, если источник модуля не закреплён на неизменяемый коммит.

**Разбор**

Как это работает: Terraform скачивает код модуля из source при `terraform init` и кладёт его в `.terraform/modules`; если source указывает на изменяемую ссылку (ветку), содержимое модуля может отличаться при каждой переустановке, а сам Terraform не хранит версию модуля в своём state как отдельную проверяемую величину — он просто применяет то, что скачал.

На практике: в организации стоит вести модули в отдельных репозиториях с семантическим версионированием и CHANGELOG, публиковать их либо во внутренний Terraform Registry, либо фиксировать `ref` на git-тег; обновление версии модуля в конфигурациях-потребителях должно проходить через обычный `plan`/review, чтобы видеть эффект изменений до применения, а не как побочный эффект чужого коммита.

Частые ошибки: частая ошибка — ссылаться на `ref=main` «для простоты», из-за чего любое изменение модуля сразу раскатывается на всех потребителей без code review на их стороне; другая ошибка — не вести CHANGELOG и breaking-change политику для внутренних модулей, из-за чего потребители не понимают, что при переходе с v1 на v2 изменились обязательные переменные.

**Пример / кейс**

```hcl
module "vm" {
  source  = "git::https://git.acme.local/infra/terraform-modules.git//vm?ref=v1.4.0"
}

# или модуль из приватного registry:
module "vm" {
  source  = "app.terraform.io/acme/vm/aws"
  version = "~> 1.4"
}
```

Ожидаемое поведение: `terraform init` должен скачивать ровно тот код модуля, что соответствует зафиксированному тегу/версии; изменение версии в коде конфигурации — единственный способ получить новое поведение модуля, и это изменение видно в diff Pull Request.


### 270. Переменная `instance_count` в Terraform-модуле должна принимать только значения от 1 до 10, а переменная `environment` — только одно из строк `dev`, `staging`, `prod`. Как добиться того, чтобы некорректное значение отбраковывалось ещё на этапе `terraform plan`, а не приводило к ошибке облачного API или к созданию ресурса с неожидаемым именем?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Нужно задать в объявлении переменной блок `validation` с условием (`condition`) и понятным сообщением об ошибке (`error_message`), а также по возможности ограничить тип через `type` (например, `number`, `string`) — тогда при передаче недопустимого значения Terraform остановится с явной ошибкой ещё до обращения к provider, а не при `apply` с малопонятным сообщением от API.

**Разбор**

Как это работает: блок `validation` выполняется Terraform локально на этапе обработки конфигурации (во время `plan`/`apply`, до построения графа ресурсов), вычисляя булево выражение `condition` для значения переменной; если оно ложно, Terraform прерывает выполнение с заданным `error_message`, что происходит гораздо раньше и понятнее, чем ошибка от облачного провайдера при попытке создать ресурс с недопустимым параметром.

На практике: стоит добавлять валидацию для всех переменных, значения которых ограничены бизнес-правилами или возможностями провайдера (диапазоны, допустимые enum-строки, формат CIDR и т.п.), а также писать `error_message` так, чтобы разработчик сразу понимал, что и как исправить; для модулей, используемых несколькими командами, это существенно снижает число обращений в поддержку из-за непонятных ошибок API.

Частые ошибки: частая ошибка — полагаться только на тип переменной (`type = string`) и не добавлять `validation`, из-за чего опечатка типа `environmant = "prod"` в значении (а не в имени) незаметно создаёт ресурсы в несуществующем окружении или с дефолтным поведением; другая ошибка — писать `error_message` без указания, какое значение на самом деле ожидается, что не помогает диагностике.

**Пример / кейс**

```hcl
variable "instance_count" {
  type = number
  validation {
    condition     = var.instance_count >= 1 && var.instance_count <= 10
    error_message = "instance_count должен быть от 1 до 10."
  }
}

variable "environment" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment должен быть одним из: dev, staging, prod."
  }
}
```

Ожидаемое поведение: при `terraform plan -var="environment=prodd"` выполнение должно остановиться с ошибкой `environment должен быть одним из: dev, staging, prod.` ещё до построения плана ресурсов.


### 271. Роль Ansible `webserver` должна при каждом использовании сначала гарантировать, что на хосте уже настроен общий `common`-профиль (пользователи, firewall, часовой пояс). Как оформить эту зависимость через `meta/main.yml`, и почему такие зависимости стоит объявлять явно, а не просто указывать обе роли подряд в плейбуке?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Зависимость оформляется в файле `roles/webserver/meta/main.yml` в секции `dependencies`, где указывается роль `common` (при необходимости с параметрами); Ansible автоматически выполнит зависимые роли перед основной, так что порядок гарантирован даже если кто-то в будущем подключит `webserver` в плейбуке без явного упоминания `common`, в отличие от простого перечисления ролей в `roles:`, которое легко случайно нарушить при рефакторинге плейбука.

**Разбор**

Как это работает: при выполнении плейбука Ansible разворачивает список ролей в плоский список задач, и для каждой роли с объявленными `dependencies` сначала подставляет задачи зависимых ролей (в порядке их перечисления, с дедупликацией по умолчанию, если роль уже была выполнена с теми же параметрами); это обрабатывается до начала основного прогона плейбука, то есть зависимости выполняются раньше, а не «по требованию» посреди задач.

На практике: зависимости в `meta/main.yml` удобны для ролей, которые переиспользуются в нескольких плейбуках и командах (в том числе подключаемых через `ansible-galaxy` из общего каталога), потому что гарантируют инвариант независимо от того, кто и как вызывает роль; для более сложных случаев (например, нужно передать разные параметры зависимости в разных плейбуках) иногда предпочитают явные `include_role`/`import_role` с параметрами вместо `meta`-зависимостей, чтобы логика была нагляднее.

Частые ошибки: частая ошибка — продублировать логику `common` внутри `webserver`, вместо того чтобы объявить зависимость, из-за чего при изменении базовой настройки нужно помнить про несколько мест; другая ошибка — не учитывать, что по умолчанию Ansible выполняет зависимую роль только один раз за прогон (если не указано `allow_duplicates: true` в её `meta`), и неожиданно получить пропущенное повторное применение при намеренной необходимости выполнить роль с другими параметрами.

**Пример / кейс**

```yaml
# roles/webserver/meta/main.yml
dependencies:
  - role: common
    vars:
      timezone: "Europe/Moscow"
```
```bash
$ ansible-playbook -i inventory site.yml
PLAY [all] *************************************************
TASK [common : Set timezone] *******************************
changed: [web01]
TASK [webserver : Install nginx] ***************************
changed: [web01]
```

Ожидаемое поведение: роль `common` выполняется автоматически перед `webserver`, даже если в `site.yml` указана только роль `webserver`.


### 272. Нужно сгенерировать на хостах конфиг nginx, где список upstream-серверов и включение/выключение gzip зависят от переменных инвентаря, при этом для разных групп хостов список серверов разный. Как использовать модуль Ansible `template` с Jinja2 (циклы и условия) для этой задачи, и как диагностировать ситуацию, когда сгенерированный файл оказался не таким, как ожидалось?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Нужно создать `.j2`-шаблон с циклом `{% for %}` по списку переменной (например, `upstream_servers`) и условием `{% if gzip_enabled %}` для опциональных блоков, подключить его через модуль `ansible.builtin.template` с указанием `src`/`dest`; для диагностики используется `ansible-playbook --check --diff` (покажет построчный diff без применения) или прогон модуля `template` в режиме с `-vvv`, а также точечная проверка конкретных значений переменных через `ansible -m debug -a "var=upstream_servers"`.

**Разбор**

Как это работает: модуль `template` рендерит Jinja2-шаблон на управляющей машине (control node), подставляя значения переменных, доступных для конкретного хоста (из inventory, group_vars, host_vars, facts), и копирует результат на целевой хост, сравнивая содержимое с уже существующим файлом для определения `changed`/`ok`; то есть вся логика выбора данных решается до копирования файла, а не на самом хосте.

На практике: при отладке шаблона полезно временно вывести промежуточное значение через `{{ upstream_servers | to_nice_json }}` в комментарии шаблона или прогнать `ansible-playbook --check --diff --limit host1`, чтобы увидеть точный diff без изменения продакшен-хоста; также стоит держать тестовые значения переменных в отдельном inventory для проверки edge-кейсов (пустой список upstream, один сервер, много серверов).

Частые ошибки: частая ошибка — использовать неопределённую переменную в шаблоне без дефолта (`{{ gzip_enabled }}` вместо `{{ gzip_enabled | default(false) }}`), из-за чего на хостах без явного значения рендер падает с ошибкой `undefined variable`; другая ошибка — забыть, что группировка переменных в Ansible имеет приоритет (host_vars выше group_vars выше defaults роли), и не проверить, что нужное значение не перекрывается более специфичной переменной.

**Пример / кейс**

```jinja
{# roles/nginx/templates/nginx.conf.j2 #}
upstream backend {
{% for srv in upstream_servers %}
    server {{ srv }};
{% endfor %}
}
{% if gzip_enabled | default(false) %}
gzip on;
{% endif %}
```
```bash
$ ansible-playbook site.yml --check --diff --limit web01
--- before: /etc/nginx/nginx.conf
+++ after: /etc/nginx/nginx.conf
+upstream backend {
+    server 10.0.1.10:8080;
+    server 10.0.1.11:8080;
+}
```

Ожидаемое поведение: `--diff` показывает именно тот набор upstream-серверов, который задан для группы данного хоста, без применения изменений до подтверждения.


### 273. Playbook разворачивает список пакетов через `loop` по переменной `packages_to_install`, и выполнение задачи, обёрнутой в `when: ansible_facts['os_family'] == 'Debian'`, неожиданно падает в середине цикла на одном из элементов с ошибкой "no package matching 'foo-tools'". Как диагностировать, на каком именно элементе цикла и на каких хостах произошёл сбой, и как сделать так, чтобы один неудачный пакет не прерывал обработку остальных хостов из плейбука?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Нужно смотреть вывод `ansible-playbook` с `-v`: для каждой итерации цикла Ansible печатает результат с ключом `item`, что сразу показывает, на каком элементе списка и на каком хосте произошёл сбой; чтобы ошибка на одном хосте не останавливала выполнение задачи на остальных хостах, используется `ignore_errors: true` в сочетании с явной проверкой результата (`register` + последующий `when: result is failed`) или стратегия `free` вместо `linear`, а для одного «плохого» элемента внутри списка — `loop_control: { label: "{{ item }}" }` для читаемости и, при необходимости, отдельная задача-обработчик неудачных элементов.

**Разбор**

Как это работает: при `linear` strategy (дефолтной) Ansible выполняет задачу на всех хостах пакетного батча параллельно, но следующая задача не начнётся, пока предыдущая не завершится на всех хостах; при ошибке без `ignore_errors` хост, на котором она произошла, исключается из дальнейшего выполнения плейбука (хотя другие хосты батча продолжают текущую задачу), а `loop` внутри задачи выполняется последовательно по списку элементов для данного хоста, и по умолчанию падение на одном элементе останавливает весь `loop` для этого хоста.

На практике: для некритичных элементов списка (например, опциональный инструмент, который есть не во всех репозиториях) стоит явно обрабатывать ожидаемые сбои через `ignore_errors: true` + `register` + отдельный шаг логирования/уведомления, а не глушить все ошибки одинаково; для диагностики на проде полезно сразу прогонять с `--limit` на упавшем хосте и `-vvv`, чтобы увидеть точную команду `apt`/`yum`, которая не сработала.

Частые ошибки: частая ошибка — ставить `ignore_errors: true` на весь плейбук или на все задачи подряд «чтобы не падало», из-за чего реальные критичные сбои (например, недоступность сети) тоже тихо игнорируются; другая ошибка — не использовать `loop_control: label`, из-за чего в длинном списке переменных сложного типа (словари) вывод ошибки превращается в нечитаемую стену текста без понимания, какой именно элемент сломался.

**Пример / кейс**

```yaml
- name: Install optional packages
  ansible.builtin.package:
    name: "{{ item }}"
    state: present
  loop: "{{ packages_to_install }}"
  loop_control:
    label: "{{ item }}"
  register: pkg_result
  ignore_errors: true
  when: ansible_facts['os_family'] == 'Debian'

- name: Report failed packages
  ansible.builtin.debug:
    msg: "Package {{ item.item }} failed on {{ inventory_hostname }}"
  loop: "{{ pkg_result.results }}"
  when: item is failed
```

Ожидаемое поведение: вывод явно показывает `failed: [web03] => (item=foo-tools)`, выполнение продолжается для остальных пакетов и хостов, а финальная задача собирает список реально сломавшихся пакетов.


### 274. Playbook для инвентаря из 300 хостов стал заметно медленнее после того, как в начало каждого плейбука добавили несколько задач, читающих `ansible_facts` (например, версию ОС и список сетевых интерфейсов). Что делает `gather_facts`, почему он ощутимо влияет на время выполнения при большом инвентаре, и как ускорить повторные прогоны с помощью кэширования фактов?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

`gather_facts: true` (по умолчанию) заставляет Ansible перед выполнением задач подключиться к каждому хосту и собрать факты через модуль `setup` (информация об ОС, сети, дисках и т.п.), что при сотнях хостов создаёт заметную задержку на каждый прогон; ускорить повторные запуски можно включив fact caching (например, backend `jsonfile` или `redis` в `ansible.cfg`) с разумным `fact_caching_timeout`, либо собирая факты один раз в отдельном playbook и переиспользуя кэш в последующих прогонах, не опрашивая все хосты заново при каждом плейбуке.

**Разбор**

Как это работает: модуль `setup` выполняется на каждом целевом хосте при первом обращении к play, если `gather_facts` не выключен, и результат живёт в памяти текущего процесса `ansible-playbook`; при включённом fact caching Ansible дополнительно сохраняет собранные факты во внешнее хранилище (файл/Redis/Memcached) с TTL, и при следующих запусках (если TTL не истёк) не переопрашивает хост заново, а берёт факты из кэша, экономя время на сетевое подключение и выполнение модуля `setup`.

На практике: для больших инвентарей стоит явно выставлять `gather_facts: false` там, где факты не нужны (например, playbook только вызывает один модуль без условий по ОС), и включать `gather_facts: true` только там, где это необходимо; также полезно увеличивать `forks` в `ansible.cfg` для параллельного сбора фактов и использовать `gather_subset` для сбора только нужных категорий фактов (например, `!hardware,!facter`), если полный набор не требуется.

Частые ошибки: частая ошибка — держать fact caching включённым с большим TTL (например, сутки) для динамической инфраструктуры, из-за чего playbook принимает решения (например, по IP-адресу) на основе устаревших фактов после пересоздания инстанса; другая ошибка — выключать `gather_facts` глобально без проверки, что никакая задача ниже по плейбуку не зависит от `ansible_facts`, из-за чего задачи с `when: ansible_facts['os_family'] == ...` молча не выполняются, потому что факт пуст.

**Пример / кейс**

```ini
# ansible.cfg
[defaults]
gathering = smart
fact_caching = jsonfile
fact_caching_connection = /tmp/ansible_facts_cache
fact_caching_timeout = 3600
forks = 50
```
```yaml
- hosts: all
  gather_facts: false
  tasks:
    - name: Deploy config without needing OS facts
      ansible.builtin.copy:
        src: app.conf
        dest: /etc/app/app.conf
```

Ожидаемое поведение: при `gathering = smart` и валидном кэше повторный прогон в пределах `fact_caching_timeout` заметно быстрее первого, так как Ansible не выполняет модуль `setup` повторно на каждом хосте.


### 275. Фронтенд-сервис развёрнут в auto scaling group, количество EC2-инстансов постоянно меняется в течение дня, и статический inventory-файл с фиксированным списком IP регулярно оказывается рассинхронизирован с реальным набором хостов. Чем динамический inventory отличается от статического, и как настроить плагин `aws_ec2` для автоматического обнаружения хостов по тегам?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Динамический inventory получает список хостов и их группировку не из статического файла, а опросом внешнего источника (облачного API, CMDB) в момент запуска плейбука, поэтому он всегда отражает текущий набор инстансов; для AWS это настраивается YAML-файлом инвентаря с `plugin: amazon.aws.aws_ec2`, фильтрами по тегам и правилами `keyed_groups` для автоматической группировки, вместо того чтобы вручную поддерживать список IP при каждом масштабировании ASG.

**Разбор**

Как это работает: при запуске `ansible-playbook -i inventory_aws_ec2.yml` плагин инвентаря обращается к EC2 API, получает список инстансов по заданным фильтрам (регион, теги, состояние `running`), и на основе `keyed_groups`/`hostnames` строит группы и имена хостов динамически на каждый прогон, то есть источником правды становится сам облак, а не файл в репозитории.

На практике: такой инвентарь стоит ограничивать фильтрами по тегам и регионам, чтобы не захватывать чужие или неожиданные ресурсы, и кэшировать результат опроса API (`cache: yes` с TTL) при частых прогонах, чтобы не упираться в лимиты API; для гибридных случаев (часть хостов статична — например, bare-metal, часть динамична — облако) используют несколько источников инвентаря одновременно, передавая директорию с несколькими inventory-файлами через `-i`.

Частые ошибки: частая ошибка — не указывать фильтр по состоянию инстанса, из-за чего в inventory попадают и остановленные/terminated инстансы, к которым playbook не может подключиться, что выглядит как случайные сбои подключения; другая ошибка — полагаться на динамический inventory без кэша в playbook, который запускается очень часто, и упираться в rate limit облачного API.

**Пример / кейс**

```yaml
# inventory_aws_ec2.yml
plugin: amazon.aws.aws_ec2
regions:
  - eu-central-1
filters:
  instance-state-name: running
  tag:Environment: prod
keyed_groups:
  - key: tags.Role
    prefix: role
```
```bash
$ ansible-inventory -i inventory_aws_ec2.yml --graph
@all:
  |--@role_web:
  |  |--ec2-10-0-1-11
  |  |--ec2-10-0-1-27
```

Ожидаемое поведение: при добавлении нового инстанса в ASG с тегом `Role=web` он автоматически появляется в группе `role_web` при следующем прогоне, без ручного редактирования inventory-файла.


### 276. В роли Ansible задача `shell: mkdir -p /opt/app/releases/{{ release_id }} && chown app:app /opt/app/releases/{{ release_id }}` при каждом прогоне плейбука помечается как `changed`, даже если директория уже создана и владелец уже верный. Почему модуль `shell` в этом случае не идемпотентен, и как переписать задачу так, чтобы статус `changed` отражал реальное изменение?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Модули `shell`/`command` по умолчанию не умеют определять, изменилось ли что-то на самом деле — Ansible просто помечает их как `changed`, если команда завершилась с кодом 0, независимо от того, создала ли она что-то новое; правильное решение — заменить shell-команду на специализированные модули `ansible.builtin.file` (для создания директории и смены владельца) и, если команда необходима, использовать параметры `creates`/`removes` или явный `changed_when` на основе анализа вывода.

**Разбор**

Как это работает: специализированные модули (`file`, `copy`, `template`, `package` и т.п.) перед действием проверяют текущее состояние системы (есть ли файл, какой у него владелец, какое содержимое) и сообщают `changed` только если реальное состояние отличается от желаемого; у `shell`/`command` такой проверки нет, потому что Ansible не умеет заранее знать семантику произвольной команды, поэтому по умолчанию он консервативно считает любой успешный запуск изменением.

На практике: использовать `shell`/`command` стоит только когда нет подходящего модуля, и в этом случае обязательно задавать `creates: /opt/app/releases/{{ release_id }}` (задача не выполнится повторно, если путь уже существует) или `changed_when: false`/кастомное условие по `stdout`, если команда действительно безопасно перезапускаемая, но сама по себе не меняет состояние на повторных запусках; для создания директорий и прав всегда предпочтительнее `ansible.builtin.file`, который нативно идемпотентен.

Частые ошибки: частая ошибка — оставлять задачи `shell`/`command` помеченными как `changed` на каждом прогоне и игнорировать это, из-за чего handlers, завязанные на `notify` от такой задачи, срабатывают при каждом запуске плейбука (например, лишний перезапуск сервиса); другая ошибка — добавлять `changed_when: false` там, где команда действительно может что-то менять, что маскирует реальные изменения и усложняет аудит.

**Пример / кейс**

```yaml
# было: неидемпотентно
- name: Create release dir
  ansible.builtin.shell: >
    mkdir -p /opt/app/releases/{{ release_id }} &&
    chown app:app /opt/app/releases/{{ release_id }}

# стало: идемпотентно
- name: Create release dir
  ansible.builtin.file:
    path: "/opt/app/releases/{{ release_id }}"
    state: directory
    owner: app
    group: app
    mode: "0755"
```

Ожидаемое поведение: повторный прогон плейбука на уже настроенном хосте должен показывать `ok=1 changed=0` для этой задачи вместо `changed=1` на каждом запуске.


### 277. Инфраструктура управляется через Terraform, но инженеры иногда вручную меняют параметры ресурсов через веб-консоль облачного провайдера «чтобы быстро починить прод», и такие изменения долго остаются незамеченными до следующего планового `apply`. Как организовать регулярное обнаружение drift в CI (например, по расписанию) и оповещение о нём, не выполняя автоматический `apply` на найденные расхождения?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Нужно настроить отдельный CI-джоб по расписанию (cron), который выполняет только `terraform plan -detailed-exitcode` (без `apply`) для каждого важного окружения, разбирает код выхода (0 — нет изменений, 2 — есть расхождения, 1 — ошибка) и при коде 2 отправляет уведомление команде с содержимым плана, оставляя решение о применении человеку, а не автоматизируя `apply` на обнаруженный drift.

**Разбор**

Как это работает: `terraform plan -detailed-exitcode` сравнивает текущее реальное состояние ресурсов (через обращение к API провайдера) с тем, что записано в state и описано в конфигурации, и возвращает отличающийся от обычного `plan` код выхода, который легко разобрать скриптом в CI; сам факт расхождения между желаемым (конфигурация) и фактическим состоянием — это и есть drift, независимо от того, кто и как его внёс.

На практике: план с обнаруженным drift стоит отправлять в Slack/почту/issue-трекер с диффом и ссылкой на job, а не просто логировать «где-то в CI»; для критичных ресурсов можно добавить политику, что любое ручное изменение через консоль обязано сопровождаться последующим PR с обновлением Terraform-кода (например, через `terraform import`/`moved`) в течение фиксированного времени, чтобы state и реальность не расходились постоянно.

Частые ошибки: частая ошибка — настраивать автоматический `terraform apply` сразу после обнаружения drift без участия человека, из-за чего намеренное экстренное ручное исправление на проде может быть откатано автоматизацией в худший момент; другая ошибка — запускать drift-detection слишком редко (например, раз в неделю) для часто меняющейся инфраструктуры, из-за чего накопленный drift сложнее анализировать построчно.

**Пример / кейс**

```bash
#!/usr/bin/env bash
set -euo pipefail
terraform init -input=false
set +e
terraform plan -detailed-exitcode -input=false -out=plan.out
code=$?
set -e
if [ "$code" -eq 2 ]; then
  terraform show -no-color plan.out | tee drift.txt
  ./notify_slack.sh "#infra-alerts" "Drift detected in prod" drift.txt
elif [ "$code" -eq 1 ]; then
  exit 1
fi
```

Ожидаемое поведение: при отсутствии расхождений джоб завершается без уведомлений (код 0); при наличии drift в канал приходит сообщение с конкретным диффом ресурсов, но инфраструктура не меняется автоматически.


### 278. Модуль Terraform использует `data "aws_ami" "latest"` с фильтром по имени для получения ID последнего образа, который публикует другая команда вне этого Terraform-проекта, и несколько месяцев всё работало, а затем один `terraform apply` неожиданно пересоздал все инстансы. Какой риск создаёт зависимость resource от внешнего data source, и как снизить вероятность неожиданного пересоздания ресурсов при обновлении внешних данных?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Data source каждый раз запрашивает текущее состояние у провайдера при `plan`/`apply`, поэтому если внешняя команда опубликовала новый AMI, подходящий под тот же фильтр, значение `data.aws_ami.latest.id` меняется без единого изменения в самом Terraform-коде, и ресурс, использующий этот id (например, `aws_instance` с `ami = data.aws_ami.latest.id` без `lifecycle.create_before_destroy`/`ignore_changes`), будет пересоздан при следующем apply, что и произошло — изменение пришло «снаружи» конфигурации.

**Разбор**

Как это работает: data source в Terraform не версионируется и не фиксируется в конфигурации так, как явный resource: он выполняет live-запрос к API на этапе plan и подставляет свежий результат в граф зависимостей; если результат отличается от предыдущего apply, Terraform видит разницу в значении атрибута, который использует зависимый resource, и планирует соответствующее действие (в данном случае replace, если `ami` требует пересоздания).

На практике: если нужна предсказуемость, стоит либо зафиксировать конкретный ID образа как явную переменную/значение (а обновление версии образа делать осознанным PR), либо явно задать `ignore_changes = [ami]` в `lifecycle`, если автоматическое обновление образа нежелательно для уже работающих инстансов, либо, наоборот, осознанно спроектировать `create_before_destroy` и rolling-замену, если обновление образа — ожидаемое поведение; выбор зависит от того, управляется ли жизненный цикл образа тем же процессом релиза, что и инфраструктура.

Частые ошибки: частая ошибка — использовать `data` с фильтром "последний/latest" для production-ресурсов без понимания, что это делает apply недетерминированным во времени (результат одного и того же кода меняется сам по себе); другая ошибка — добавить `ignore_changes` «чтобы не пересоздавалось» без отдельного процесса обновления образа, из-за чего инстансы годами работают на устаревшем, неисправленном образе.

**Пример / кейс**

```hcl
data "aws_ami" "latest" {
  most_recent = true
  owners      = ["self"]
  filter {
    name   = "name"
    values = ["app-*"]
  }
}

resource "aws_instance" "app" {
  ami           = data.aws_ami.latest.id
  instance_type = "t3.medium"
  lifecycle {
    ignore_changes = [ami]
  }
}
```

Ожидаемое поведение: после публикации новой версии AMI командой-владельцем образов `terraform plan` больше не должен молча планировать replace инстанса — изменение `ami` игнорируется до осознанного отдельного шага ротации инстансов.


### 279. В Terraform-модуле переменная `db_password` помечена как `sensitive = true`, а в Ansible playbook пароль читается из Ansible Vault и используется в задаче подключения к БД. Команда считает, что после этих мер пароль нигде не виден в открытом виде. Что на самом деле скрывает `sensitive` в Terraform и `no_log` в Ansible, а что они не скрывают, и где пароль всё равно может оказаться в читаемом виде?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

`sensitive = true` в Terraform скрывает значение переменной/output только в консольном выводе `plan`/`apply` (заменяет его на `(sensitive value)`), но само значение в открытом виде всё равно сохраняется в state-файле; аналогично `no_log: true` в Ansible скрывает значение из лога конкретной задачи, но не шифрует его — если значение передаётся через переменную, попадающую в другие незащищённые места (debug-задачи, артефакты CI, факты), оно может «утечь» в другом месте, поэтому обе меры дополняют, а не заменяют реальное шифрование секрета (Vault, Terraform state encryption, внешнее secret-хранилище).

**Разбор**

Как это работает: механизм маскировки в обоих инструментах работает на уровне вывода/логирования: Terraform помечает конкретный атрибут как sensitive в своей внутренней модели и фильтрует его при рендере человеко-читаемого вывода, а Ansible для задачи с `no_log: true` просто не печатает параметры и результат этой задачи в лог; ни то, ни другое не меняет, как и где значение физически хранится (state на диске/в S3, временные файлы, память процесса).

На практике: для реальной защиты секретов state необходимо хранить в backend с шифрованием at rest (например, S3 с SSE) и ограниченным доступом, рассматривать вариант интеграции с внешним хранилищем секретов (Vault, AWS Secrets Manager) и подстановкой значения в момент apply, а не хранением «как есть»; в Ansible пароли лучше получать динамически (lookup в HashiCorp Vault/AWS Secrets Manager) вместо постоянного хранения в зашифрованном vault-файле в репозитории, если нужна ротация без изменения кода.

Частые ошибки: частая ошибка — считать, что `sensitive = true` защищает значение в state-файле так же, как шифрование, и хранить незашифрованный state в общедоступном месте; другая ошибка — выводить sensitive-значение в Terraform через `output` без `sensitive = true` у самого output (тогда маскировка переменной не распространяется автоматически), либо в Ansible логировать результат задачи, использующей секрет, в отдельной debug-задаче без `no_log`, из-за чего пароль всё равно попадает в лог CI.

**Пример / кейс**

```hcl
variable "db_password" {
  type      = string
  sensitive = true
}

output "db_password" {
  value     = var.db_password
  sensitive = true
}
```
```yaml
- name: Connect to DB
  community.mysql.mysql_user:
    login_password: "{{ vault_db_password }}"
  no_log: true
```

Ожидаемое поведение: в CI-логе и в консольном выводе `terraform apply`/`ansible-playbook` пароль не отображается, но файл state (если не зашифрован отдельно) и Vault-файл (если расшифрован или скомпрометирован ключ) всё ещё содержат значение.


### 280. После того, как кто-то вручную отредактировал файл `terraform.tfstate` текстовым редактором (пытаясь "быстро исправить" устаревший атрибут) и сохранил его с опечаткой в JSON, следующий `terraform plan` начал падать с ошибкой парсинга state. Как восстановить работоспособность state, если используется backend с versioning (например, S3 с включённым object versioning), и какие промежуточные шаги нужно выполнить, чтобы не потерять изменения, случившиеся после последней валидной версии?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Нужно скачать предыдущую валидную версию объекта state из versioning-истории бакета (например, через AWS CLI `aws s3api list-object-versions`/`get-object` с нужным `VersionId`), проверить её локально (`terraform show -json` на загруженном файле, не на активном backend), и если с момента этой версии были реальные изменения в инфраструктуре мимо Terraform — аккуратно сверить их через `terraform plan` после восстановления, прежде чем аплайдить; саму восстановленную версию нужно загрузить обратно как текущий объект state (или через `terraform state push`), а не редактировать JSON вручную повторно.

**Разбор**

Как это работает: S3 object versioning хранит каждую предыдущую версию объекта (включая state) как отдельный `VersionId`, то есть повреждение последней версии не удаляет предыдущие, и committed история state физически доступна для восстановления; Terraform CLI команда `state push` принимает локальный файл state и перезаписывает remote state целиком, что и используется для возврата к валидной версии как к новому текущему state.

На практике: перед любым восстановлением стоит сохранить повреждённую версию (на случай, если в ней были правки, которые всё же нужно перенести вручную), восстановление делать на изолированной копии (`terraform state pull`/локальный файл), проверять план на отсутствие неожиданных действий, и только после этого делать `state push`; на будущее — запретить прямое редактирование state-файла организационно и технически (права доступа), и обучать команду использовать только `terraform state ...` подкоманды.

Частые ошибки: частая ошибка — продолжать редактировать state вручную текстовым редактором даже для «исправления» уже возникшей проблемы, что рискует сломать JSON ещё сильнее; другая ошибка — восстановить старую версию state и сразу выполнить `apply` без предварительного `plan`, не проверив, что между повреждённой и восстановленной версией не было легитимных изменений инфраструктуры, которые теперь будут выглядеть как drift или будут случайно перезаписаны.

**Пример / кейс**

```bash
$ aws s3api list-object-versions     --bucket acme-tfstate-prod     --prefix env/prod/terraform.tfstate
$ aws s3api get-object     --bucket acme-tfstate-prod     --key env/prod/terraform.tfstate     --version-id 3HL4kqtJlcpXroDTDmjVBH     restored.tfstate

$ terraform state push restored.tfstate
$ terraform plan
```

Ожидаемое поведение: после `state push` командой `terraform plan` должен выполниться без ошибки парсинга; план покажет либо `No changes`, либо конкретные расхождения, возникшие за время, пока state был повреждён, — их нужно разобрать вручную перед `apply`.


### 281. В репозитории с Terraform-модулями и ролями Ansible до сих пор единственной проверкой в CI был `terraform validate`/`ansible-lint`. Как выстроить более основательное тестирование IaC для этого репозитория, включая проверку логики ролей Ansible в изолированном окружении (Molecule) и проверку, что модуль Terraform действительно создаёт ожидаемые ресурсы (например, через `terraform test` в Terraform 1.6+ или Terratest)?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Для Ansible-ролей используется Molecule: она поднимает временное окружение (контейнер/VM), прогоняет роль, затем прогоняет её повторно для проверки идемпотентности (`idempotence` сценарий ожидает `changed=0` на втором прогоне) и может выполнять verifier-тесты (например, Testinfra/Ansible assert) для проверки итогового состояния; для Terraform — встроенный `terraform test` (с файлами `.tftest.hcl`, доступен с версии 1.6) или внешний Terratest на Go позволяют реально применить модуль в тестовом окружении (или sandbox-аккаунте), проверить атрибуты созданных ресурсов и корректно уничтожить их после теста.

**Разбор**

Как это работает: Molecule оборачивает полный цикл `create -> converge -> idempotence -> verify -> destroy`, запуская роль Ansible против эфемерного драйвера (чаще всего Docker), что даёт быструю обратную связь без необходимости реальных облачных ресурсов; `terraform test`/Terratest, напротив, обычно выполняют реальные `apply`/`destroy` против тестового облачного окружения, потому что поведение провайдера нельзя полностью эмулировать локально, поэтому такие тесты дороже и медленнее и обычно запускаются не на каждый commit, а на PR в основную ветку или по расписанию.

На практике: практичная пирамида для такого репозитория: быстрые статические проверки (`terraform fmt/validate`, `ansible-lint`, `tflint`) на каждый push; Molecule-сценарии для ролей на PR; Terraform-тесты с реальным apply/destroy в изолированном sandbox-аккаунте — реже (PR в main или nightly), с обязательной очисткой ресурсов даже при сбое теста; важно также проверять idempotence (повторный прогон без изменений) как отдельный обязательный шаг, а не полагаться на единичный успешный прогон.

Частые ошибки: частая ошибка — ограничиваться только статическими линтерами и считать это достаточным тестированием, из-за чего логические ошибки (роль работает, но не идемпотентна, или модуль создаёт ресурс не с тем параметром) обнаруживаются только в проде; другая ошибка — не предусмотреть гарантированную очистку (`destroy`) тестовых ресурсов при сбое теста посреди выполнения, из-за чего в тестовом аккаунте копится забытая инфраструктура и растут расходы.

**Пример / кейс**

```yaml
# molecule/default/molecule.yml (фрагмент)
driver:
  name: docker
scenario:
  test_sequence:
    - create
    - converge
    - idempotance
    - verify
    - destroy
```
```hcl
# tests/vm.tftest.hcl
run "creates_instance_with_tag" {
  command = apply
  assert {
    condition     = aws_instance.app.tags["Environment"] == "test"
    error_message = "Тег Environment не установлен"
  }
}
```

Ожидаемое поведение: `molecule test` завершается успешно только если второй прогон роли (idempotence) показывает `changed=0`; `terraform test` создаёт реальные ресурсы в тестовом окружении, проверяет assert-условия и гарантированно уничтожает их по завершении.


### 282. После `helm upgrade` с ошибочным значением в `values.yaml` релиз Kubernetes-приложения застрял в состоянии `pending-upgrade`, и повторные попытки `helm upgrade` с исправленными значениями завершаются ошибкой `another operation (install/upgrade/rollback) is in progress`. Что означает это состояние, как из него безопасно выйти, и как работает `helm rollback` для возврата к последней рабочей версии?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Состояние `pending-upgrade` означает, что Helm начал операцию upgrade, записал в свою историю релиза (Secrets/ConfigMaps в кластере) новую ревизию как "в процессе", но сама операция не была доведена до конца (например, упал pre/post-upgrade hook или процесс был прерван); чтобы выйти из застрявшего состояния, в современных версиях Helm 3 используется `helm rollback <release> <revision>`, который переводит релиз на конкретную прошлую ревизию, либо (если rollback невозможен из-за битой истории) аккуратно правится статус релиза в secret Helm вручную — но такой ручной способ рискованный и используется только как последнее средство.

**Разбор**

Как это работает: Helm хранит историю релизов как отдельные объекты (по умолчанию Kubernetes Secrets) с манифестом и статусом каждой ревизии; при `upgrade` создаётся новая ревизия со статусом `pending-upgrade`, и только по завершении применения манифестов и всех хуков статус меняется на `deployed`, а предыдущая ревизия — на `superseded`; если процесс прерывается до этого перехода, статус `pending-upgrade` остаётся висеть и блокирует новые операции до тех пор, пока явно не выполнить `rollback` (который создаёт новую ревизию с манифестом старой) или не вмешаться вручную.

На практике: перед следующим `upgrade` после сбоя полезно посмотреть `helm history <release>` и `helm status <release>`, чтобы понять, какая ревизия последняя рабочая, и явно откатиться на неё, а не пытаться сразу накатить новый upgrade поверх зависшего состояния; для критичных релизов стоит использовать `--atomic` (автоматический rollback при неудачном upgrade) и `--timeout`, чтобы Helm сам откатывался при сбое, не оставляя релиз в подвешенном состоянии.

Частые ошибки: частая ошибка — пытаться повторно запустить `helm upgrade` многократно, игнорируя сообщение о блокировке, вместо того чтобы сначала разобраться в причине (сбойный hook, таймаут) и выполнить `rollback`; другая ошибка — не использовать `--atomic`/`wait` в CI-пайплайне деплоя, из-за чего пайплайн считает деплой успешным сразу после отправки манифестов, не дождавшись реальной готовности подов, и пропускает момент, когда upgrade фактически завис.

**Пример / кейс**

```bash
$ helm upgrade myapp ./chart -f values.yaml
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress

$ helm history myapp
REVISION  STATUS           CHART        
3         pending-upgrade  myapp-1.4.0  
2         deployed         myapp-1.3.0  

$ helm rollback myapp 2
Rollback was a success! Happy Helming!

$ helm upgrade myapp ./chart -f values-fixed.yaml --atomic --timeout 5m
```

Ожидаемое поведение: после `rollback` статус релиза возвращается к `deployed` на ревизии 2; последующий `upgrade --atomic` при повторном сбое сам откатится, не оставляя релиз в `pending-upgrade`.


### 283. Главный Helm-чарт приложения подключает в качестве зависимости (subchart) стандартный чарт `postgresql` из публичного репозитория, и нужно переопределить его параметры (размер диска, имя базы) из родительского `values.yaml`, не редактируя сам subchart. Как объявляется зависимость в `Chart.yaml` и как правильно передавать значения в subchart через секцию в values родительского чарта?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Зависимость объявляется в `Chart.yaml` секцией `dependencies` с именем, версией (диапазоном) и репозиторием чарта, после чего выполняется `helm dependency update`, которая скачивает subchart в папку `charts/`; значения для subchart передаются из родительского `values.yaml` в виде вложенного ключа с именем subchart'а (`postgresql: { ... }`), а если subchart поддерживает global-значения — общие для нескольких subchart'ов параметры можно вынести в секцию `global`, которая видна во всех уровнях.

**Разбор**

Как это работает: Helm при рендере объединяет values по иерархии: значения из `values.yaml` родителя под ключом `<имя subchart>` переопределяют дефолтные `values.yaml` самого subchart'а для этого уровня вложенности, а секция `global` доступна и родителю, и всем subchart'ам одновременно; команда `helm template`/`helm install --dry-run` позволяет увидеть итоговый результат слияния до реального применения в кластер.

На практике: перед переопределением стоит посмотреть `helm show values <repo>/postgresql` (или файл `charts/postgresql/values.yaml` после `dependency update`), чтобы использовать точные имена ключей, ожидаемые subchart'ом, а не угадывать структуру; версии зависимостей в `Chart.yaml` лучше фиксировать диапазоном с ограничением (например, `~12.1.0`), чтобы `dependency update` не подтягивал breaking-change версию незаметно.

Частые ошибки: частая ошибка — редактировать файлы внутри `charts/postgresql` напрямую вместо передачи значений через родительский `values.yaml`, из-за чего правки затираются при следующем `helm dependency update`; другая ошибка — перепутать структуру вложенности ключей (например, положить параметры subchart'а на верхний уровень `values.yaml` без обёртки его именем), из-за чего Helm просто игнорирует эти значения при рендере subchart'а.

**Пример / кейс**

```yaml
# Chart.yaml
dependencies:
  - name: postgresql
    version: "~12.1.0"
    repository: "https://charts.bitnami.com/bitnami"
```
```yaml
# values.yaml родительского чарта
postgresql:
  auth:
    database: appdb
  primary:
    persistence:
      size: 20Gi
```
```bash
$ helm dependency update ./mychart
$ helm template mychart ./mychart | grep -A2 "size:"
```

Ожидаемое поведение: в отрендеренном манифесте PVC для postgresql размер диска должен быть `20Gi`, а не дефолтное значение из `charts/postgresql/values.yaml`.


### 284. Overlay Kustomize для окружения `prod` должен увеличить количество реплик Deployment и добавить один дополнительный label на все ресурсы, но после `kustomize build overlays/prod` в итоговом манифесте реплики не изменились, хотя label появился. В чём разница между strategic merge patch и JSON6902 patch в Kustomize, и как диагностировать, почему конкретный патч не применился так, как ожидалось?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Strategic merge patch (`patches` с фрагментом YAML того же вида, что целевой ресурс) объединяется с базовым манифестом по известным Kubernetes-правилам слияния полей, и если в патче допущена ошибка — неверный `kind`/`name`/`apiVersion` для таргетинга ресурса, или патч описан как часть списка без совпадающего селектора, — Kustomize может просто не найти, к какому ресурсу применить патч, и тихо его пропустить; JSON6902 patch (`patches` с `target` + списком операций `op/path/value`) применяется по точному JSON-пути, и ошибка в `path` (например, неверный индекс массива контейнеров) приведёт либо к явной ошибке, либо к применению не туда, куда ожидалось — для диагностики нужно запускать `kustomize build` локально и явно сверять итоговый YAML, а не полагаться только на применение в кластер.

**Разбор**

Как это работает: strategic merge patch требует, чтобы верхнеуровневые поля-идентификаторы (`apiVersion`, `kind`, `metadata.name`) в файле патча точно совпадали с таргетируемым ресурсом — Kustomize ищет ресурс по этим полям и сливает оставшиеся поля по map-подобным правилам Kubernetes (например, список контейнеров сливается по имени `name`, а не по индексу); JSON6902 patch, напротив, адресует изменения по `target` (group/version/kind/name) и точным JSON path, что мощнее для точечных изменений (например, поменять один элемент массива по индексу), но более хрупко при изменении структуры базового манифеста.

На практике: для надёжной диагностики стоит всегда прогонять `kustomize build overlays/prod > /tmp/out.yaml` локально перед `kubectl apply`, и явно сверять нужные поля (`grep -A3 replicas`), а не доверять интуиции о том, что патч точно применился; при частых сложных патчах полезно разбивать overlay на несколько явных файлов (`patch-replicas.yaml`, `patch-labels.yaml`) с понятными именами, чтобы проще находить, какой конкретно патч за что отвечает.

Частые ошибки: частая ошибка — указать в strategic merge patch неверный `metadata.name`, отличающийся от реального имени Deployment в base (например, из-за добавленного Kustomize `namePrefix`), из-за чего патч не находит цель и молча не применяется; другая ошибка — смешивать strategic merge и JSON6902 патчи на один и тот же ресурс в одном overlay без понимания порядка их применения, что приводит к неожиданному финальному результату.

**Пример / кейс**

```yaml
# overlays/prod/kustomization.yaml
resources:
  - ../../base
patches:
  - path: patch-replicas.yaml
    target:
      kind: Deployment
      name: web
commonLabels:
  tier: prod
```
```yaml
# overlays/prod/patch-replicas.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 5
```
```bash
$ kustomize build overlays/prod | grep -A1 "replicas:"
  replicas: 5
```

Ожидаемое поведение: если имя Deployment в base отличается от указанного в патче (например, `web-app` вместо `web`), `kustomize build` выполнится без ошибки, но поле `replicas` останется со значением из base — это и есть признак того, что патч не нашёл цель.


### 285. Небольшая команда поддерживает три окружения (dev, staging, prod) на Terraform и хочет избежать копипасты кода между ними, но при этом не наступить на подводные камни workspaces из предыдущего вопроса. Как на практике организовать структуру репозитория с отдельными директориями на каждое окружение и общими модулями, чтобы различия между окружениями были явными, а повторение кода — минимальным?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Практичная структура — директория `modules/` с переиспользуемыми модулями (сеть, кластер, база данных) и отдельная директория на каждое окружение (`envs/dev`, `envs/staging`, `envs/prod`), где у каждого окружения свой `backend` (свой state), свой `*.tfvars` с конкретными значениями (размер инстансов, CIDR, количество реплик) и один и тот же вызов общих модулей с разными параметрами; это даёт явную изоляцию state и прав доступа между окружениями при минимальном дублировании самой логики ресурсов.

**Разбор**

Как это работает: каждая директория окружения — это самостоятельный корневой модуль Terraform со своим `terraform init`/`plan`/`apply` и своим backend key, а общий код (модули) подключается через относительный путь `source = "../../modules/network"`, поэтому изменения в логике ресурса делаются один раз в модуле и переиспользуются во всех окружениях при следующем `plan`, а различия (размеры, количество, включённые фичи) остаются только в `tfvars`/вызовах модуля конкретного окружения.

На практике: для минимизации дублирования самого кода-обёртки (повторяющийся блок `module "network" { source = ... }` в каждом env) можно использовать generate-инструменты (Terragrunt или свой скрипт), но для небольшой команды из 3 окружений часто дешевле принять небольшое дублирование вызовов модулей, чем вносить ещё один инструмент и его кривую обучения — выбор зависит от того, сколько окружений и как часто меняется сама структура вызовов.

Частые ошибки: частая ошибка — пытаться сделать один универсальный корневой модуль с условиями `count = var.environment == "prod" ? 1 : 0` внутри самого корневого кода вместо разделения на директории, из-за чего один state содержит вперемешку логику всех окружений и риск случайного влияния на prod из dev-ветки кода растёт; другая ошибка — держать все `tfvars` в одном файле с комментариями «для prod раскомментировать это», что провоцирует человеческую ошибку при ручном редактировании перед apply.

**Пример / кейс**

```
envs/
  dev/
    main.tf        # module "network" { source = "../../modules/network" ... }
    backend.tf      # key = "env/dev/terraform.tfstate"
    dev.tfvars
  prod/
    main.tf
    backend.tf      # key = "env/prod/terraform.tfstate"
    prod.tfvars
modules/
  network/
  database/
```
```bash
$ cd envs/prod && terraform init && terraform plan -var-file=prod.tfvars
```

Ожидаемое поведение: изменение в `modules/network` подхватывается в plan каждого окружения независимо, но `apply` для dev и prod выполняются раздельно, против разных state и, как правило, с разными правами доступа CI.


### 286. Нужно спроектировать CI/CD пайплайн для Terraform-репозитория так, чтобы `terraform plan` автоматически запускался и публиковался как комментарий в каждом Pull Request, а `terraform apply` на prod выполнялся только после merge в основную ветку и с обязательным ручным подтверждением. Как построить такой пайплайн и как предотвратить одновременный запуск двух `apply` на один state из параллельных merge?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Пайплайн на PR должен выполнять `terraform init` + `terraform plan -out=plan.tfplan`, сохранять читаемый вывод (`terraform show -no-color plan.tfplan`) и публиковать его как комментарий к PR через API системы CI/VCS; после merge в main отдельный job выполняет `terraform apply` с ручным approval-гейтом (environment protection rule в GitHub Actions/manual gate в GitLab CI) и обязательно используя именно тот план, что был проверен (или заново сгенерированный план с тем же содержимым); одновременный запуск двух `apply` предотвращается как самим state locking backend'а (второй apply будет ждать/упадёт на занятом локе), так и организационно — настройкой очереди/конкурентности на уровне CI (например, `concurrency group` на имя окружения), чтобы не запускать два job параллельно на один и тот же state вообще.

**Разбор**

Как это работает: CI-система видит каждый PR и merge как отдельное событие и по умолчанию может запускать job'ы параллельно; ограничение конкурентности (named concurrency group / environment lock в CI) заставляет job'ы, относящиеся к одному и тому же окружению, выполняться строго по очереди, а backend state locking Terraform — это второй, более низкоуровневый уровень защиты, срабатывающий даже если конкурентность в CI настроена неверно.

На практике: план, применяемый в `apply`, в идеале должен быть ровно тем артефактом, что проверяли люди в PR (а не новый `plan`, сгенерированный в момент apply, который теоретически может отличаться, если кто-то успел смержить что-то ещё между review и apply) — для этого план сохраняют как CI-артефакт и передают в job apply; approval-гейт должен требовать подтверждения конкретным человеком/ролью, а не автоматического прохождения, особенно для prod.

Частые ошибки: частая ошибка — давать возможность запускать `apply` вручную из любой ветки в обход пайплайна «в экстренном случае», что обходит review и approval-процесс и со временем становится обычной практикой; другая ошибка — не ограничивать конкурентность на уровне CI и полагаться только на state locking, из-за чего второй job просто падает по таймауту лока вместо аккуратной постановки в очередь, создавая ложные сбои в пайплайне.

**Пример / кейс**

```yaml
# .github/workflows/terraform.yml (фрагмент)
on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: terraform-prod
  cancel-in-progress: false

jobs:
  plan:
    if: github.event_name == 'pull_request'
    steps:
      - run: terraform plan -out=plan.tfplan
      - run: terraform show -no-color plan.tfplan > plan.txt
      - uses: actions/github-script@v7   # публикует plan.txt как комментарий к PR

  apply:
    if: github.ref == 'refs/heads/main'
    environment: prod   # требует manual approval в настройках окружения
    steps:
      - run: terraform apply -auto-approve plan.tfplan
```

Ожидаемое поведение: в PR появляется комментарий с планом до merge; `apply` на prod запускается только после merge и только после подтверждения approver'ом, а параллельный запуск второго apply на тот же state блокируется concurrency group.


### 287. Playbook, который раньше выполнялся на 20 хостах за минуту, после расширения инвентаря до 400 хостов стал выполняться почти 40 минут, хотя сами задачи не изменились. Какие настройки Ansible (`forks`, `pipelining`, стратегия выполнения) влияют на время прогона при большом количестве хостов, и как диагностировать, что именно является узким местом?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Ключевые параметры — `forks` (сколько хостов обрабатывается параллельно за раз, по умолчанию всего 5, что при 400 хостах означает 80 последовательных батчей), `pipelining` (отключает отдельную передачу модуля файлом по SSH, уменьшая число SSH-подключений на задачу) и `strategy` (дефолтная `linear` ждёт завершения задачи на всех хостах батча перед следующей задачей, тогда как `free` позволяет каждому хосту идти по плейбуку в своём темпе); диагностировать узкое место помогает профилирование через `ANSIBLE_CALLBACKS_ENABLED=timer,profile_tasks` или встроенный плагин `profile_tasks`, который показывает время каждой задачи и помогает понять, SSH-overhead это или реально долгая задача.

**Разбор**

Как это работает: при `forks = 5` Ansible делит 400 хостов на 80 последовательных групп по 5, и каждая задача внутри плейбука выполняется этими батчами, так что даже быстрая задача (1 секунда на хосте) на 400 хостах с такими forks растягивается на значимое время просто из-за количества батчей; `pipelining` убирает лишний шаг копирования скрипта модуля на хост через SFTP/SCP перед выполнением, что при высокой задержке сети или большом количестве мелких задач даёт заметный выигрыш.

На практике: для большого инвентаря стоит поднять `forks` до разумного числа, соответствующего возможностям control node и целевой инфраструктуры (сотни, если control node и сеть это выдерживают), включить `pipelining = True` в `ansible.cfg` (требует отсутствия `requiretty` в sudoers на хостах), и для плейбуков без строгих межзадачных зависимостей между хостами переключиться на `strategy: free`; также полезно разбивать очень большие прогоны на `serial` батчи, если цель — не скорость, а контролируемый rollout (например, canary-раскатка конфигурации).

Частые ошибки: частая ошибка — увеличивать только `forks`, не включая `pipelining` и не проверяя профиль задач, из-за чего настоящим узким местом остаётся, например, одна конкретная медленная задача (скачивание большого файла), которую параллелизация по хостам не ускоряет; другая ошибка — включить `strategy: free` для плейбука, где поздние задачи реально зависят от того, что все хосты прошли более ранний шаг (например, миграция схемы БД перед деплоем кода), что приводит к состоянию гонки между хостами.

**Пример / кейс**

```ini
# ansible.cfg
[defaults]
forks = 50
strategy = linear
callback_whitelist = profile_tasks

[ssh_connection]
pipelining = True
```
```bash
$ ANSIBLE_STDOUT_CALLBACK=profile_tasks ansible-playbook -i inventory site.yml
Sunday 04 October 2026  15:10:02 +0000 (0:00:28.311)  Install packages ------- 28.31s
Sunday 04 October 2026  15:10:30 +0000 (0:00:02.014)  Copy config ------------  2.01s
```

Ожидаемое поведение: после увеличения `forks` и включения `pipelining` общее время прогона на 400 хостов должно заметно снизиться; вывод `profile_tasks` указывает, какая конкретная задача доминирует по времени, если ускорение не произошло.


### 288. Нужно отрефакторить Terraform-конфигурацию: вынести ресурс `aws_security_group.app`, который раньше был объявлен прямо в корневом модуле, внутрь нового переиспользуемого модуля `modules/security`, сохранив тот же реальный security group в AWS без его удаления и пересоздания. Как оформить это перемещение ресурса между модулями безопасно, используя блок `moved` или `terraform state mv`, и как проверить, что переезд прошёл без побочных эффектов?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Middle

**Короткий ответ**

Нужно физически перенести код ресурса в файлы нового модуля, подключить модуль в корневой конфигурации, и либо добавить в конфигурацию блок `moved { from = aws_security_group.app, to = module.security.aws_security_group.app }` (Terraform 1.1+, предпочтительный декларативный способ), либо выполнить эквивалентную команду `terraform state mv aws_security_group.app module.security.aws_security_group.app` вручную; в обоих случаях реальный ресурс в AWS не удаляется и не создаётся — меняется только адрес ресурса внутри state, после чего `terraform plan` должен показать `No changes`.

**Разбор**

Как это работает: Terraform сопоставляет ресурсы конфигурации с объектами state по полному адресу, включающему путь модуля (`module.security.aws_security_group.app` отличается от `aws_security_group.app`); блок `moved` фиксирует переименование прямо в конфигурации и применяется автоматически при каждом `plan`/`apply`, что удобнее для командной работы, чем разовая ручная команда `state mv`, которую нужно не забыть выполнить каждому, у кого есть доступ к этому state (включая CI), прежде чем он впервые применит новую конфигурацию.

На практике: после переноса обязательно нужно прогнать `terraform plan` и убедиться, что единственное отображаемое действие (если есть) — ожидаемое, а не неожиданный destroy/create; также стоит проверить, что вместе с самим ресурсом не потерялись связанные с ним атрибуты/зависимости (например, если на security group ссылались другие ресурсы через `aws_security_group.app.id`, эти ссылки нужно обновить на `module.security.aws_security_group.app.id`), иначе план может показать изменения в зависимых ресурсах.

Частые ошибки: частая ошибка — перенести код ресурса в модуль, забыв добавить `moved`/выполнить `state mv`, из-за чего Terraform планирует удалить старый ресурс и создать новый внутри модуля, что для security group means временное окно без нужных правил доступа; другая ошибка — выполнить `state mv` локально у одного инженера, но не донести это изменение до CI/остальной команды до их следующего `plan`, из-за чего они получают неожиданный destroy/create, потому что их state ещё не содержит нового адреса.

**Пример / кейс**

```hcl
# root main.tf
module "security" {
  source = "./modules/security"
  vpc_id = aws_vpc.main.id
}

moved {
  from = aws_security_group.app
  to   = module.security.aws_security_group.app
}
```
```bash
$ terraform plan
# ожидаем: Terraform will perform the following actions: (пусто/No changes)
# либо явное сообщение о применении move без destroy/create для security group
```

Ожидаемое поведение: `terraform plan` после рефакторинга не должен планировать `-/+ destroy and then create replacement` для security group; реальный ресурс в AWS (и его ID) остаётся тем же самым.


### 289. Компания выросла до нескольких десятков AWS-аккаунтов в разных регионах, и весь Terraform-код сейчас живёт в одном монорепозитории с несколькими крупными state-файлами на каждый регион. Один инцидент (повреждённый state в одном регионе) парализовал deploy везде, потому что CI-пайплайн для всех регионов использовал общий модуль с жёсткой последовательной зависимостью. Как спроектировать изоляцию state и границы blast radius для мультирегиональной/мультиаккаунтной архитектуры, и какие компромиссы есть между монорепо и полирепо для организации такого кода?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Нужно разделить state по естественным границам отказа — отдельный state (а лучше отдельный backend/учётные данные) на каждую комбинацию аккаунт+регион+слой (сеть, платформа, приложения), чтобы повреждение или лок одного state не блокировал остальные, и убрать жёсткие последовательные зависимости между регионами в пайплайне, заменив их на параллельные независимые пайплайны с явными точками синхронизации только там, где это действительно необходимо (например, глобальный DNS); при этом однозначно лучшего выбора между монорепо и полирепо нет — решение зависит от размера команды, частоты изменений шаблонов и зрелости tooling, и кандидату стоит обсудить критерии выбора, а не выбрать один вариант как универсально правильный.

**Разбор**

Как это работает: при текущей архитектуре один большой state на регион означает, что любая операция (включая просто `plan`) в этом state блокируется локом, а ошибка в общем модуле, подключаемом последовательно во всех регионах, распространяет сбой по цепочке; разбиение на более мелкие, слабо связанные state снижает blast radius (сбой/лок одного state не парализует остальные), но увеличивает количество независимых state-файлов, которые нужно отслеживать, и может усложнить сквозные изменения, затрагивающие сразу несколько слоёв.

На практике: на практике подход зависит от зрелости организации: небольшая платформенная команда может поддерживать монорепо с общими модулями и явной матрицей CI (параллельные джобы по аккаунт×регион), тогда как при росте числа команд-потребителей монорепо начинает создавать contention на review и общий CI, и часть организаций переходит на полирепо с чётко версионированными модулями, публикуемыми во внутренний registry, жертвуя удобством сквозного рефакторинга ради независимости команд.

Частые ошибки: None

Компромисс: Монорепо проще для сквозного рефакторинга общих модулей и даёт единый обзор всей инфраструктуры, но при росте числа команд создаёт очередь на review и общий CI, а также риск, что один сломанный pipeline-файл влияет на всех; полирепо с версионированными модулями изолирует команды и блокировки, но требует зрелого внутреннего registry модулей, процесса релизов и сложнее для атомарных изменений, затрагивающих сразу много репозиториев — выбор должен опираться на реальную частоту межкомандных изменений и зрелость платформенной команды, а не на моду.

**Пример / кейс**

```
monorepo (пример):
infra/
  modules/           # общие версионированные модули
  live/
    eu-west-1/
      network/   (отдельный state)
      platform/  (отдельный state)
    us-east-1/
      network/   (отдельный state)
      platform/  (отдельный state)
```
```yaml
# CI: независимые параллельные джобы вместо одной последовательной цепочки
jobs:
  eu-west-1-network: {...}
  us-east-1-network: {...}   # не зависит от eu-west-1-network
```

Ожидаемое поведение/обсуждение на интервью: кандидат должен объяснить, что критерии выбора — размер команды, частота изменений, зрелость CI/registry, стоимость координации — важнее самого ярлыка «монорепо vs полирепо», и предложить конкретную метрику для пересмотра решения (например, время восстановления после инцидента, время на сквозной рефакторинг).


### 290. В организации 15 команд пишут собственные Terraform-модули с дублирующейся и местами небезопасной логикой (например, разные команды по-своему настраивают шифрование S3-бакетов, где-то забывая его включить). Платформенная команда предлагает ввести внутренний registry обязательных модулей. Как спроектировать governance модулей так, чтобы обеспечить базовые гарантии безопасности и консистентности, не превратив платформенную команду в блокирующее бутылочное горлышко для остальных 15 команд?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Нужно разделить модули на уровни обязательности: небольшой набор "golden" модулей с жёстко зафиксированными небезопасными-по-умолчанию настройками (например, S3-бакет с обязательным шифрованием и блокировкой публичного доступа) — обязателен и проходит через централизованный review и SLA на обновления; остальная логика остаётся в свободном использовании командами, с возможностью прислать свой модуль в общий каталог через стандартизированный, но лёгковесный процесс (CI-проверки + review от платформенной команды, а не ручное одобрение каждой мелочи); единственно верного баланса между контролем и автономией нет, и выбор нужно явно обсуждать с учётом размера организации, зрелости команд и регуляторных требований.

**Разбор**

Как это работает: governance здесь означает комбинацию технического контроля (policy as code, проверяющая, что критичные ресурсы созданы только через одобренные модули/с одобренными настройками) и процесса (кто может публиковать и обновлять модуль, как версионируется breaking change, как потребители узнают об устаревших версиях); без этого каждая из 15 команд предсказуемо воспроизводит свою версию одних и тех же решений с разным уровнем качества, потому что для них это не основная экспертиза.

На практике: на практике работает модель "тонкой талии": платформенная команда владеет малым числом модулей, покрывающих реальные риски (secrets, сетевой периметр, хранение данных), публикует их в registry с версионированием и явным deprecation-процессом, а для остальной логики даёт командам шаблоны и lint-правила, но не блокирует их решения; важно иметь обратную связь от команд-потребителей в roadmap платформенных модулей, иначе платформенная команда начинает навязывать решения, не подходящие под реальные кейсы использования.

Частые ошибки: None

Компромисс: Жёсткий централизованный контроль всех модулей снижает риск небезопасных конфигураций, но масштабируется плохо: платформенная команда становится бутылочным горлышком, а команды-потребители обходят процесс через shadow-IaC; полностью децентрализованный подход быстр для команд, но воспроизводит разнородные и местами небезопасные решения. Разумный компромисс — малый обязательный набор policy-as-code правил и golden-модулей для реальных рисков, и самообслуживание (self-service) с лёгким review для всего остального, пересматриваемое по метрикам нагрузки на платформенную команду и числу инцидентов безопасности.

**Пример / кейс**

```hcl
# пример "golden" модуля с безопасным дефолтом, который нельзя обойти
module "secure_bucket" {
  source  = "registry.acme.local/platform/secure-s3-bucket"
  version = "2.3.0"
  name    = "team-orders-bucket"
  # encryption и public access block зашиты внутри модуля без возможности отключить
}
```
```rego
# policy as code (Conftest/OPA): блокирует bucket, созданный не через golden-модуль
deny[msg] {
  input.resource_type == "aws_s3_bucket"
  not input.module_source_matches_approved_list
  msg := "S3-бакеты должны создаваться через platform/secure-s3-bucket"
}
```

Ожидаемое поведение/обсуждение: кандидат должен назвать конкретные сигналы перегрузки платформенной команды (время на review, число открытых запросов на новые модули) и предложить, что делать при их превышении — например, расширять self-service без обязательного ручного review для низкорисковых изменений.


### 291. Остановка платформы в результате сценария "потеряна таблица DynamoDB с локами и повреждена последняя версия S3-бакета со всеми production state-файлами" (из-за человеческой ошибки с правами удаления) привела бы к тому, что компания не может ни посмотреть, ни безопасно изменить реальную production-инфраструктуру через Terraform. Как спроектировать disaster recovery именно для самого Terraform state на уровне платформы (не для приложений), и какие регулярные проверки должны подтверждать, что восстановление реально работает?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Нужен отдельный DR-план именно для state: versioning и MFA delete на S3-бакете со state, репликация бакета в другой регион/аккаунт (cross-region replication), отдельное резервное копирование DynamoDB-таблицы локов (point-in-time recovery), строгое разграничение прав (отдельная роль с правом удаления объектов state, недоступная по умолчанию даже администраторам), и, главное, регулярные тренировки восстановления (game day) в изолированном окружении, которые подтверждают, что восстановленный state реально проходит `terraform plan` без неожиданных действий, а не просто существует как файл.

**Разбор**

Как это работает: state — это единственный источник истины о том, что Terraform считает управляемой инфраструктурой; его потеря не разрушает саму инфраструктуру немедленно, но делает её неуправляемой через IaC (любой следующий apply либо не пройдёт, либо попытается создать ресурсы заново), а повреждение бэкапов (а не только "живой" копии) означает отсутствие реального restore path, даже если на бумаге DR-план существует.

На практике: регулярные game day упражнения должны включать реальное восстановление state из резервной копии в изолированный аккаунт/окружение и прогон `terraform plan`/`import` на восстановленной копии, с измерением фактического RTO; также стоит вести отдельный, независимо хранимый export критичных идентификаторов ресурсов (ID VPC, ARN ключей и т.п.) вне самого Terraform state, чтобы в худшем случае (state действительно утрачен полностью) можно было восстановить управление через `terraform import`/`moved`, а не только воссоздавать инфраструктуру с нуля.

Частые ошибки: None

Компромисс: Полная репликация state в реальном времени в другой регион/аккаунт и жёсткая изоляция прав удаления снижают риск катастрофической потери, но увеличивают операционную сложность и стоимость (отдельные роли, мониторинг репликации, регулярные game day); более лёгкий подход (только versioning без репликации в другой аккаунт) дешевле, но не защищает от компрометации/ошибки на уровне всего аккаунта. Выбор зависит от критичности управляемой через этот state инфраструктуры и регуляторных требований, и должен быть явно обсуждён с бизнесом, а не решён только инженерами.

**Пример / кейс**

```bash
# пример регулярной проверки DR (game day), а не однократной настройки
$ aws s3api get-bucket-versioning --bucket acme-tfstate-prod-replica
$ aws dynamodb describe-continuous-backups --table-name acme-tf-locks-replica

# восстановление в изолированный аккаунт и проверка
$ terraform init -backend-config=dr-backend.hcl
$ terraform plan   # ожидаем: план объясним, без массового destroy/create
```

Ожидаемое поведение/обсуждение: кандидат должен явно назвать метрику успеха DR-упражнения (например, восстановленный state проходит plan с объяснимым результатом за X минут) и обсудить, что чисто технические меры (versioning, replication) без регулярной тренировки восстановления не дают реальной уверенности в работоспособности DR.


### 292. Платформенная команда хочет внедрить policy as code (OPA/Conftest или Sentinel) поверх Terraform plan, чтобы автоматически блокировать опасные изменения (например, открытие security group на 0.0.0.0/0 для SSH) до apply. После пилота несколько команд жалуются, что строгие политики блокируют легитимные edge-кейсы и замедляют релизы. Как спроектировать систему policy as code, которая реально снижает риск, не превращаясь в источник постоянного трения с командами-разработчиками?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Нужно разделить политики по уровню строгости: небольшой набор hard-блокирующих правил только для однозначно недопустимых и дорого обходящихся рисков (публичный SSH/RDP, отключённое шифрование секретных данных), и более широкий набор warn-only/advisory правил, которые требуют явного подтверждения (например, обязательного объяснения в PR или approval второй командой) вместо автоматической блокировки; также необходим управляемый процесс исключений (exception process) с временным approved override и сроком действия, а не постоянные ручные обходы политики через отключение проверки целиком.

**Разбор**

Как это работает: policy as code работает, анализируя план (JSON-вывод `terraform show -json`) или итоговые манифесты до их применения, и возвращает allow/deny на основе правил; жёсткая блокировка без пути легитимного исключения заставляет команды искать обходные пути (например, вручную редактировать ресурс после apply, что создаёт drift), поэтому важно не только писать правила, но и спроектировать процесс работы с их нарушениями.

На практике: метрика успеха такой системы — не количество заблокированных plan'ов, а соотношение реально предотвращённых инцидентов к количеству ложных блокировок легитимных кейсов; для этого полезно вести лог решений (allow/deny/override) и периодически пересматривать правила с участием команд-разработчиков, а не только силами платформенной/security-команды, чтобы правила отражали реальные ограничения бизнеса, а не только теоретические риски.

Частые ошибки: None

Компромисс: Чем шире список hard-блокирующих правил, тем выше гарантированный уровень безопасности, но тем больше трения с командами и тем выше риск, что команды начнут искать обходные пути (ручные правки после apply, параллельные неуправляемые ресурсы), что хуже с точки зрения общего риска, чем сам исходный edge-кейс. Узкий набор строгих правил плюс управляемый процесс исключений даёт более медленное, но устойчивое повышение зрелости, тогда как агрессивный подход быстрее формально закрывает риски, но создаёт скрытый технический долг в виде обходов. Решение должно учитывать требования compliance и реальную частоту легитимных edge-кейсов.

**Пример / кейс**

```rego
# пример: hard-block только для явно недопустимого риска
deny[msg] {
  input.resource_type == "aws_security_group_rule"
  input.cidr_blocks[_] == "0.0.0.0/0"
  input.from_port <= 22
  input.to_port >= 22
  msg := "SSH не может быть открыт на 0.0.0.0/0"
}

# пример: advisory-правило, требующее подтверждения, а не блокировки
warn[msg] {
  input.resource_type == "aws_db_instance"
  not input.multi_az
  msg := "БД без multi-AZ: подтвердите, что это осознанный выбор для этого окружения"
}
```

Ожидаемое поведение/обсуждение: кандидат должен разграничить, какие категории правил достойны hard-block, а какие — advisory, и предложить конкретный процесс временного исключения (кто одобряет, какой срок действия, как это логируется для аудита).


### 293. Секреты (пароли БД, API-ключи сторонних сервисов) сейчас хранятся в зашифрованных Ansible Vault файлах в git и в Terraform-переменных, помеченных `sensitive`, но недавний аудит обнаружил, что несколько секретов не менялись три года и известны бывшим подрядчикам. Как спроектировать архитектуру управления секретами для связки Terraform + Ansible + Kubernetes/Helm, которая обеспечивает ротацию и минимизирует распространение секретов в state/git, и какие компромиссы это создаёт по сравнению с текущим подходом?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Нужно перейти от статичного хранения секретов в зашифрованных файлах к централизованному secret-хранилищу (например, HashiCorp Vault или облачный аналог) с динамической выдачей короткоживущих секретов: Terraform получает секреты через `data` source к Vault в момент apply (не храня их постоянно в конфигурации), Ansible — через `community.hashicorp_vault` lookup вместо расшифровки статичного vault-файла, а Kubernetes/Helm — через внешний secret-оператор (например, External Secrets Operator), синхронизирующий секреты из Vault в Kubernetes Secrets во время выполнения, а не зашитый в values чарта; это не устраняет полностью присутствие секрета в state (многие ресурсы всё равно требуют записи значения в state провайдером), но резко снижает время жизни скомпрометированного значения за счёт ротации.

**Разбор**

Как это работает: динамические секреты в Vault выдаются с ограниченным TTL и привязаны к конкретной роли/политике доступа, поэтому даже утечка значения ограничена по времени его действия, а не живёт годами, как статичный пароль в зашифрованном файле; интеграция на уровне Terraform/Ansible/Kubernetes через единый источник означает, что ротация настраивается и аудируется в одном месте, а не в трёх разных местах с разными процессами, как сейчас.

На практике: такой переход требует значимых инвестиций: разворачивание и эксплуатация самого Vault (или выбор managed-альтернативы), миграция существующих секретов и процессов, обучение команд новым инструментам, и для части legacy-систем, не поддерживающих динамическую выдачу, всё равно потребуется какой-то статичный секрет с процессом ручной ротации; поэтому миграцию стоит вести поэтапно, начиная с самых критичных и самых старых (как в аудите) секретов.

Частые ошибки: None

Компромисс: Статичные зашифрованные секреты проще внедрить и не требуют поддержки дополнительного сервиса, но не решают проблему ротации и долгоживущего доступа бывших сотрудников/подрядчиков; динамическая выдача через Vault даёт ротацию и централизованный аудит, но добавляет операционную нагрузку (ещё один критичный сервис, который сам нуждается в HA и DR) и не покрывает legacy-компоненты без доработки. Решение должно соответствовать реальной критичности секретов и зрелости команды эксплуатировать дополнительный сервис, а не внедряться как разовая "модная" миграция без плана поддержки.

**Пример / кейс**

```hcl
# Terraform: получение секрета из Vault в момент apply, без хранения пароля в коде
data "vault_generic_secret" "db" {
  path = "database/creds/app-role"
}

resource "aws_db_instance" "app" {
  password = data.vault_generic_secret.db.data["password"]
}
```
```yaml
# External Secrets Operator: секрет синхронизируется в Kubernetes Secret из Vault
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: app-db-credentials
spec:
  secretStoreRef:
    name: vault-backend
  target:
    name: app-db-credentials
  data:
    - secretKey: password
      remoteRef:
        key: database/creds/app-role
        property: password
```

Ожидаемое поведение/обсуждение: кандидат должен признать, что значение секрета всё равно может оказаться в state Terraform или в памяти Pod'а, и обсудить, какие дополнительные меры (шифрование state, короткий TTL, аудит доступа к Vault) снижают остаточный риск, а не заявлять, что переход на Vault полностью убирает секреты из всех промежуточных хранилищ.


### 294. В компании несколько сотен Terraform-репозиториев/workspace использует один и тот же провайдер облака, и назрело обновление с мажорной версии провайдера, где часть аргументов ресурсов переименована и изменено поведение дефолтных значений. Массовое одновременное обновление версии во всех репозиториях рискованно и неконтролируемо. Как спроектировать процесс обновления версии провайдера/Terraform в масштабе всей организации, минимизируя риск масштабного инцидента?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Нужен поэтапный, измеримый rollout: сначала обновление и тестирование в небольшом наборе низкорисковых/некритичных репозиториев (canary), с обязательным прогоном `terraform plan` (а в идеале и `apply` в тестовом окружении) для выявления breaking changes из changelog провайдера; затем публикация внутреннего руководства по миграции (какие аргументы переименованы, как обновить код) и постепенное расширение на следующие волны репозиториев по владению командами, с мониторингом результатов каждой волны перед переходом к следующей, а не одновременное обновление версии во всех `.tf` файлах через глобальный find-and-replace.

**Разбор**

Как это работает: мажорное обновление провайдера часто меняет не только имена аргументов, но и то, какие значения Terraform считает дефолтными, что может привести к незаметному для автора кода плану на изменение/пересоздание ресурса даже без изменений в самом `.tf`-файле; поэтому "план без видимых diff в коде" не гарантирует безопасность — обязательно нужен реальный `terraform plan` против обновлённого провайдера для каждого репозитория перед принятием изменения.

На практике: для организации с сотнями repo полезно централизованно отследить, кто уже обновился (например, через сканирование `required_providers` во всех репозиториях), установить дедлайн для перехода на новую мажорную версию (так как провайдеры тоже имеют EOL старых версий), и иметь canary-группу, которая получает обновления провайдера раньше остальных и сигнализирует о проблемах, прежде чем остальная организация обновится.

Частые ошибки: None

Компромисс: Быстрое синхронное обновление версии во всех репозиториях сокращает время нахождения организации на устаревшей, потенциально небезопасной версии провайдера, но резко увеличивает площадь одновременного риска, если changelog содержит неочевидный breaking change. Поэтапный canary-rollout безопаснее, но означает, что часть организации дольше остаётся на старой версии, что может быть неприемлемо при наличии security-фикса именно в новой версии. Выбор темпа миграции должен явно учитывать, обновление вызвано security-патчем (быстрее) или плановым апгрейдом фич (медленнее, тщательнее).

**Пример / кейс**

```hcl
# шаг миграции: временно разрешить обе версии через constraint,
# чтобы команды мигрировали не одновременно
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = ">= 4.0, < 6.0"   # временное широкое ограничение на время миграции
    }
  }
}
```
```bash
# централизованная проверка, кто ещё не обновился
$ grep -rl 'version = "~> 4' */required_providers.tf
```

Ожидаемое поведение/обсуждение: кандидат должен предложить конкретные критерии перехода между волнами (нет новых инцидентов за X дней в canary-группе) и объяснить, почему не стоит просто зафиксировать точную версию провайдера везде одной командой без поэтапной проверки.


### 295. Платформенная команда обсуждает переход с текущей модели (CI-пайплайн выполняет `helm upgrade`/`kubectl apply` при каждом merge) на GitOps-модель, где Flux или ArgoCD в кластере сами непрерывно приводят состояние кластера в соответствие с Git-репозиторием манифестов/чартов. Какие архитектурные различия и последствия для drift-reconciliation и безопасности нужно обсудить при выборе между этими подходами, и почему нельзя просто сказать, что GitOps однозначно лучше?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

В пайплайн-модели CI имеет прямой push-доступ к кластеру и применяет изменения только в момент деплоя, то есть drift между деплоями не исправляется автоматически; в GitOps-модели pull-агент (Flux/ArgoCD) внутри кластера постоянно сверяет текущее состояние с Git и самостоятельно выполняет reconciliation, включая откат ручных изменений кем-то через `kubectl`, что даёт более сильную гарантию соответствия Git состоянию кластера, но требует, чтобы агент имел широкие права внутри кластера на изменение ресурсов, и смещает вопрос безопасности с "кто может запускать deploy pipeline" на "кто может мержить в Git-репозиторий манифестов" и "насколько защищён сам GitOps-агент".

**Разбор**

Как это работает: при push-модели секреты для доступа к кластеру должны быть у CI-системы (внешней по отношению к кластеру), что создаёт риск утечки учётных данных кластера через CI; при pull-модели агент работает внутри кластера с учётными данными, не покидающими его, но сам агент становится высокопривилегированной целью атаки, и компрометация репозитория манифестов (а не только CI) становится прямым путём к изменению продакшена, поэтому для GitOps особенно критичен code review и защита веток в самом Git.

На практике: непрерывный reconciliation в GitOps означает, что ручные экстренные изменения через `kubectl` (hotfix во время инцидента) будут автоматически откатаны агентом при следующей синхронизации, если их не внести также в Git — это дисциплинирует процесс, но может застать команду врасплох во время инцидента, если она не знает об этом поведении и ожидаемо использует `kubectl edit` как при push-модели.

Частые ошибки: None

Компромисс: GitOps даёт более сильную гарантию соответствия Git и снижает риск несанкционированного push-доступа к кластеру, но требует зрелого процесса защиты самого Git-репозитория манифестов (review, защищённые ветки, подписанные коммиты) и обучения команды его поведению при инцидентах; пайплайн-модель проще для команд, привыкших к push-деплоям, и даёт более предсказуемое поведение во время ручных hotfix, но не устраняет drift автоматически и требует доверенного доступа CI к кластеру. Выбор зависит от зрелости команды в работе с Git-процессами и от того, насколько критичен автоматический откат неучтённых ручных изменений именно для этой организации.

**Пример / кейс**

```yaml
# пример ArgoCD Application: продолжает синхронизировать кластер с Git непрерывно,
# в том числе откатывая ручные изменения, не зафиксированные в Git
apiVersion: argoproj.io/v1alpha1
kind: Application
spec:
  source:
    repoURL: https://git.acme.local/infra/manifests.git
    path: apps/web
  syncPolicy:
    automated:
      selfHeal: true   # именно этот флаг откатывает ручной kubectl-дрифт
      prune: true
```

Ожидаемое поведение/обсуждение: кандидат должен объяснить, что `selfHeal: true` — это одновременно и защита от неконтролируемого drift, и операционный риск при незнании об этом поведении во время инцидента, и предложить, как обучить (runbook, обучение) команду дежурных, прежде чем включать автоматический selfHeal на критичных приложениях.


### 296. Финансовый отдел сообщает, что облачные расходы выросли на 40% за квартал, и причина — несколько Terraform-модулей, которые по умолчанию создают избыточно большие инстансы БД и забытые NAT Gateway в каждом dev-окружении, которые никто не удаляет после экспериментов. Как спроектировать governance расходов на уровне IaC-платформы (теги, политики, алерты), чтобы предотвращать подобный рост затрат заранее, а не обнаруживать его постфактум через финансовый отчёт?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Нужна комбинация превентивных и обнаруживающих мер: обязательное тегирование всех ресурсов (команда, окружение, владелец, срок жизни) через policy as code, проверяющую plan до apply; политики, ограничивающие дорогие типы ресурсов/размеры инстансов в неprod-окружениях без явного approval; автоматическое уничтожение временных dev-окружений по TTL (например, через scheduled job, который по тегу `expiry` удаляет ресурсы старше N дней); и алерты по аномальному росту расходов, привязанные к тегам команды/проекта, а не только общий биллинг-дэшборд, который кто-то должен регулярно и добровольно смотреть.

**Разбор**

Как это работает: без обязательных тегов стоимость в биллинге облачного провайдера агрегируется плохо и не позволяет понять, какая команда/окружение несёт ответственность за рост, а без политик на этапе plan дорогой ресурс обнаруживается только постфактум, когда расход уже понесён за месяц; TTL-механизм для dev-окружений работает, потому что временные эксперименты по своей природе не нуждаются в бессрочном существовании, а их забывают удалить именно потому, что это не автоматизировано.

На практике: превентивные политики (запрет создания NAT Gateway/instance определённого размера в dev без approval) должны быть сформулированы так, чтобы не блокировать легитимные случаи, когда dev-окружению действительно нужен более мощный ресурс (например, нагрузочное тестирование) — для этого нужен быстрый процесс временного исключения, а не постоянный запрет; также полезно считать стоимость прямо в CI на основе plan (например, через Infracost) и показывать её в PR до merge, чтобы автор видел финансовые последствия своего изменения до, а не после того, как оно попало в прод.

Частые ошибки: None

Компромисс: Жёсткие предварительные ограничения по стоимости (запрет дорогих типов ресурсов без approval) предотвращают рост расходов надёжнее, но замедляют легитимные эксперименты и требуют поддерживать процесс исключений; чисто обнаруживающий подход (дэшборды и алерты постфактум) не мешает разработчикам, но реагирует с задержкой и уже понесёнными расходами. Разумный баланс — дёшево внедряемые превентивные меры для самых частых ошибок (забытые NAT Gateway, TTL для dev) плюс обнаруживающие алерты для менее предсказуемых случаев, с пересмотром порогов по фактической статистике инцидентов с расходами.

**Пример / кейс**

```hcl
# Policy as code: требование тегов + ограничение размера БД в dev
deny[msg] {
  input.resource_type == "aws_db_instance"
  input.tags.Environment == "dev"
  input.instance_class != "db.t3.small"
  not input.tags.cost_exception_approved
  msg := "БД в dev должна быть db.t3.small без явного cost_exception_approved"
}
```
```bash
# Infracost в CI: показывает стоимостной эффект PR до merge
$ infracost diff --path=.
Monthly cost will increase by $412 (NAT Gateway x3 added)
```

Ожидаемое поведение/обсуждение: кандидат должен предложить конкретный порог/процесс для cost-алертов (например, рост более X% за команду за неделю триггерит уведомление владельцу) и объяснить, почему одного только финансового отчёта постфактум недостаточно — обратная связь должна приходить в момент принятия решения (PR), а не через месяц.


### 297. Нужно внести изменение в общий Terraform-модуль сетевого слоя (например, поменять схему маршрутизации/security group на уровне VPC), которое затрагивает десятки сервисов в нескольких регионах одновременно, и ошибка в этом изменении способна вызвать масштабный сетевой сбой. Как спроектировать безопасный rollout такого изменения, ограничивая blast radius, если инфраструктура организована как набор похожих, но не идентичных окружений/регионов?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Нужно применять изменение поэтапно по заранее определённым волнам риска: сначала в изолированном тестовом окружении с синтетической нагрузкой, затем в одном наименее критичном production-регионе/окружении с усиленным мониторингом сетевых метрик в течение достаточного окна наблюдения, и только после подтверждения отсутствия регрессии — расширять на следующие волны по одному региону/окружению за раз, с возможностью немедленно остановить раскатку и откатить изменение в конкретной волне, не трогая уже не затронутые регионы; одновременное применение ко всем регионам сразу максимизирует скорость, но делает blast radius равным всей инфраструктуре.

**Разбор**

Как это работает: при поэтапном rollout критично, чтобы Terraform-state и пайплайн применения были организованы так, чтобы волны были физически независимы (отдельные state на регион/окружение, как в вопросе про мультирегиональную изоляцию), иначе "поэтапность" существует только на бумаге, а реальный apply всё равно идёт по одному общему state сразу на всё; мониторинг во время каждой волны должен покрывать именно те метрики, которые способно повредить это изменение (например, связность между подсетями, количество отбрасываемых пакетов на SG), а не общий uptime.

На практике: критерии перехода между волнами должны быть заранее определены и измеримы (например, отсутствие новых сетевых алертов в течение фиксированного окна после применения), а не субъективное "кажется, всё в порядке"; также нужен заранее готовый и проверенный план отката для сетевых изменений именно такого типа, потому что откат сетевой конфигурации может быть сложнее обычного `terraform destroy`/`apply` предыдущей версии, если изменение затронуло живые соединения.

Частые ошибки: None

Компромисс: Быстрый одновременный rollout во все регионы минимизирует время, в течение которого окружения находятся в разных версиях сетевой конфигурации (что само по себе может быть источником путаницы), но делает худший сценарий сбоя максимально широким; поэтапный rollout по волнам снижает blast radius и даёт время на обнаружение проблемы, но увеличивает общее время миграции и временно оставляет инфраструктуру в неоднородном состоянии, что тоже нужно учитывать (например, при отладке проблем, специфичных для переходного периода). Темп волн должен определяться критичностью сервисов и зрелостью мониторинга, способного быстро обнаружить именно сетевую регрессию.

**Пример / кейс**

```
Волна 0: sandbox с синтетическим трафиком        -> проверка базовой логики
Волна 1: staging, 1 регион                        -> окно наблюдения 24ч
Волна 2: prod, наименее критичный регион          -> окно наблюдения 48ч
Волна 3: prod, оставшиеся регионы (параллельно)   -> только после волн 1-2 без инцидентов
```
```promql
# пример метрики для критерия перехода между волнами
sum(rate(vpc_flow_logs_rejected_total[5m])) by (region)
```

Ожидаемое поведение/обсуждение: кандидат должен явно сформулировать измеримый критерий остановки/перехода между волнами и объяснить, почему для сетевых изменений план отката нужно проверить заранее, а не придумывать в момент инцидента.


### 298. Legacy-часть инфраструктуры компании представляет собой долгоживущие серверы, конфигурация которых поддерживается регулярными прогонами Ansible playbook (каждую ночь "подгоняющими" состояние серверов к желаемому), и команда рассматривает переход к иммутабельной модели (пересборка образов и замена серверов целиком вместо точечного исправления). Какие риски и выгоды несёт такой переход, и почему для части legacy-системы полный переход может быть неоправдан?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Иммутабельная модель (сборка нового образа при каждом изменении и замена инстансов, а не патчинг на месте) устраняет накопленный configuration drift между серверами и делает откат предсказуемым (просто разворачивается предыдущий образ), но требует, чтобы приложение переносило потерю локального состояния при пересоздании инстанса (externalized state, graceful shutdown, время на прогрев), и плохо подходит для систем, где локальное состояние на сервере тяжело или невозможно извлечь (например, старые монолиты с файловым хранилищем на диске без плана миграции на внешнее хранилище) без дополнительной архитектурной работы.

**Разбор**

Как это работает: при текущей модели Ansible playbook выполняется регулярно и приводит состояние к желаемому "по верху" уже работающего сервера, что со временем накапливает незамеченный drift в местах, не покрытых playbook (вручную поставленные пакеты, файлы, оставленные при инцидентах), и этот drift обнаруживается только когда playbook случайно это трогает или происходит инцидент; иммутабельная замена целиком устраняет такой накопленный drift просто потому, что новый инстанс собирается с нуля из зафиксированного образа.

На практике: для части legacy-системы стоимость рефакторинга приложения под stateless/иммутабельную модель (вынос состояния, доработка graceful shutdown, пересмотр процедур бэкапа) может быть выше, чем выгода от устранения drift, особенно если система стабильна и близка к концу жизненного цикла; в этом случае разумнее продолжать модель с continuous configuration management, но усилить именно обнаружение drift (периодические отчёты Ansible в check-mode, алерты на незапланированные изменения) вместо полного архитектурного перехода.

Частые ошибки: None

Компромисс: Полный переход на иммутабельную модель даёт сильную гарантию отсутствия drift и предсказуемый откат, но стоит дорого для систем с тяжёлым локальным состоянием и требует архитектурных изменений в самом приложении; сохранение модели continuous configuration management дешевле в моменте, но несёт риск накопленного drift и более сложного disaster recovery (нужно восстанавливать состояние сервера, а не просто разворачивать образ). Решение должно оцениваться по остаточному жизненному циклу системы и стоимости рефакторинга state-зависимых частей, а не по общей моде на иммутабельность.

**Пример / кейс**

```
Было:  server (живёт месяцы/годы) --(каждую ночь)--> ansible-playbook приводит к желаемому состоянию
Стало: image build (CI) --(pipeline)--> новый instance --(health check OK)--> переключение трафика
                                                     --> старый instance удаляется
```
```yaml
# compromise-шаг: усилить обнаружение drift без полного перехода на immutable
- hosts: legacy_app
  gather_facts: false
  tasks:
    - name: Report drift without changing anything
      ansible.builtin.command: true
      check_mode: true
```

Ожидаемое поведение/обсуждение: кандидат должен явно сформулировать критерий, по которому конкретная legacy-система является (не)хорошим кандидатом для иммутабельного перехода (наличие externalized state, частота изменений, остаточный жизненный цикл системы), а не рекомендовать иммутабельность как универсально правильный следующий шаг.


### 299. Платформенная команда хочет выстроить зрелую стратегию тестирования для всей IaC-платформы (десятки Terraform-модулей и Ansible-ролей), но ограничена бюджетом инженерного времени и не может покрыть всё одинаково глубоко тестами с реальным apply/destroy в облаке. Как спроектировать многоуровневую пирамиду тестирования IaC (статические проверки, unit/contract-тесты, интеграционные тесты с реальными ресурсами, policy-тесты) с учётом ограниченного бюджета, и по каким критериям решать, куда инвестировать тестирование глубже?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Нужно распределить инвестиции по пирамиде обратно пропорционально стоимости и прямо пропорционально риску: дешёвые статические проверки (`fmt`, `validate`, `tflint`, `ansible-lint`, policy-as-code) — на 100% модулей при каждом коммите; более дорогие contract/unit-тесты (`terraform test`, Molecule) — на модули с наибольшим количеством потребителей или наибольшей историей инцидентов; самые дорогие end-to-end тесты с реальным apply/destroy в облаке — только на самые критичные модули (сеть, права доступа, хранение данных), где цена дефекта в проде значительно превышает стоимость поддержки такого теста, а не равномерно на все модули.

**Разбор**

Как это работает: стоимость теста растёт от статического анализа (секунды, без внешних зависимостей) к unit/contract-тестам (минуты, изолированное окружение) к полноценным интеграционным тестам с реальными ресурсами (минуты-часы, реальные облачные затраты и необходимость надёжной очистки), поэтому попытка дать всем модулям одинаково глубокое покрытие либо непропорционально дорога, либо снижает глубину тестирования критичных модулей, размазывая бюджет тонким слоем по всем.

На практике: критерии приоритизации должны быть измеримыми: число команд-потребителей модуля, количество прошлых инцидентов, связанных с этим модулем, критичность управляемого ресурса (например, модуль, управляющий правами IAM или сетевым периметром, приоритетнее модуля для тестового S3-бакета); эти критерии нужно периодически пересматривать, потому что состав самых используемых/самых рискованных модулей меняется со временем, и бюджет тестирования должен следовать за этим изменением, а не оставаться статично закреплённым за исходным списком.

Частые ошибки: None

Компромисс: Равномерное неглубокое тестирование всех модулей даёт широкое, но поверхностное покрытие и оставляет самые критичные модули недотестированными на реальных сценариях; сфокусированное глубокое тестирование только самых рискованных модулей оставляет остальные модули защищёнными лишь статическими проверками, что может пропустить логические ошибки в редко используемых, но потенциально важных модулях. Баланс должен определяться явным, периодически пересматриваемым списком критичности модулей, а не универсальным правилом "тестируем всё одинаково" или "тестируем только самое важное" навсегда.

**Пример / кейс**

```
Уровень 1 (все модули, каждый commit):      fmt, validate, tflint, ansible-lint, policy-as-code
Уровень 2 (широко используемые модули):     terraform test / Molecule, на PR
Уровень 3 (самые критичные модули,          реальный apply/destroy в sandbox-аккаунте,
           network/IAM/data):               на merge в main / nightly, с гарантированной очисткой
```
```bash
# пример метрики для приоритизации: число потребителей модуля
$ grep -rl 'source = "registry.acme.local/platform/secure-s3-bucket"' */*.tf | wc -l
```

Ожидаемое поведение/обсуждение: кандидат должен привести конкретный числовой или качественный критерий (не просто "важные модули") для решения, какие модули получают дорогие интеграционные тесты, и признать, что часть модулей сознательно останется без уровня 3 тестирования при ограниченном бюджете.


### 300. Один из первых Terraform-репозиториев компании превратился за годы в монолитный state на три с половиной тысячи ресурсов без модулей, и любой `plan`/`apply` занимает 20+ минут и регулярно приводит к конфликтам между командами, одновременно меняющими разные части этой инфраструктуры. Нужно разбить этот state на модульную структуру с несколькими независимыми state без простоя production-сервисов. Как спроектировать безопасную поэтапную миграцию такого масштаба, и какие риски нужно явно проговорить с бизнесом перед началом?

**Направление:** DevOps Engineer
**Тема:** Infrastructure as Code и управление конфигурацией: Terraform, Ansible, модули, state, drift, идемпотентность, управление окружениями, тестирование IaC, Helm и Kustomize
**Уровень:** Senior

**Короткий ответ**

Миграцию нужно вести поэтапно, выделяя из монолитного state логически независимые группы ресурсов (например, по владению командой или по слою — сеть, данные, приложения) и перенося каждую группу через `terraform state mv`/блоки `moved` в новый отдельный state, с обязательной проверкой `plan` (ожидается `No changes`) после каждого переноса и с паузой/проверкой стабильности перед переносом следующей группы, а не попыткой разбить всё одним большим изменением; перед началом важно явно проговорить с бизнесом, что сама миграция не меняет инфраструктуру, но несёт операционный риск человеческой ошибки при переносе state и требует временного замораживания параллельных изменений в мигрируемой части во время самого переноса (окно изменений), а также что полная миграция на три с половиной тысячи ресурсов — это проект на недели/месяцы, а не на один спринт.

**Разбор**

Как это работает: при переносе ресурса в другой state через `state mv` сам ресурс в облаке не трогается, но если в момент переноса кто-то параллельно выполняет `apply` на исходном монолитном state, затрагивающий тот же ресурс, возникает race condition между миграцией и обычной работой — поэтому на время переноса конкретной группы ресурсов нужно либо временно ограничить доступ к apply этой части монолитного state, либо выполнять миграцию в окне с минимальной активностью и явным оповещением команд.

На практике: порядок выделения групп должен начинаться с наименее связанных и наименее критичных ресурсов (чтобы отработать процесс и инструментарий на низком риске), и только затем двигаться к более связанным и критичным частям; для каждой группы нужен задокументированный и протестированный на менее критичной группе rollback-план (как вернуть ресурсы обратно в монолитный state, если перенос пошёл не так), потому что отсутствие проверенного пути назад на ресурсах такого масштаба само по себе неприемлемый риск.

Частые ошибки: None

Компромисс: Быстрая миграция большими кусками сокращает общее время проекта и число раз, когда команда переключает контекст на эту работу, но резко повышает риск крупной ошибки с трудным откатом на масштабе тысяч ресурсов; медленная поэтапная миграция маленькими группами безопаснее и даёт возможность откатиться на каждом шаге, но растягивает проект на месяцы и требует длительной координации между командами, продолжающими одновременно вносить изменения в мигрируемую инфраструктуру. Темп миграции должен быть явно согласован с бизнесом как компромисс между риском инцидента и скоростью получения выгоды (параллельная работа команд без конфликтов state).

**Пример / кейс**

```bash
# пример переноса одной группы ресурсов в новый state, шаг за шагом
$ terraform state mv -state=monolith.tfstate -state-out=network.tfstate     module.network aws_vpc_endpoint_route_table_association.x

$ terraform plan   # в новом state network: ожидаем No changes
$ terraform plan   # в оставшемся монолитном state: ожидаем No changes для перенесённых ресурсов
```
```
Этап 1: перенос некритичных/изолированных ресурсов (теги, вспомогательные бакеты)
Этап 2: перенос сетевого слоя (с окном изменений, координация со всеми командами)
Этап 3: перенос слоя данных/IAM (самый высокий риск, в последнюю очередь)
```

Ожидаемое поведение/обсуждение: кандидат должен явно назвать, что нужно согласовать с бизнесом перед началом — допустимое окно изменений, кто принимает риск, какой горизонт по времени у всего проекта, и объяснить, почему попытка сделать перенос всех 3500 ресурсов одним изменением неприемлема независимо от объёма доступного времени на эту работу.
