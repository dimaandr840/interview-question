## Тема 1. SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)

### 1. [Q-04-01-0001] Как вывести только уникальные значения столбца «страна» из таблицы клиентов?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно выполнить `SELECT DISTINCT country FROM customers;` — `DISTINCT` удаляет из результата повторяющиеся строки по выбранным столбцам.

**Разбор**
- **Как это работает:** `DISTINCT` применяется к готовой строке результата после вычисления списка столбцов в `SELECT`; если указать несколько колонок, уникальность проверяется по их комбинации, а не по каждой отдельно.
- **На практике:** перед тем как «лечить» дубликаты через `DISTINCT`, стоит проверить, не являются ли они следствием ошибки — например, задвоения строк из-за некорректного JOIN. На больших таблицах `DISTINCT` требует сортировки или хеширования и может быть медленнее, чем `GROUP BY` с тем же набором столбцов — план выполнения стоит проверять через EXPLAIN.
- **Частые ошибки:** путают `DISTINCT country, city` (уникальные пары значений) с «отдельно уникальные country и отдельно уникальные city»; забывают, что все NULL-значения в столбце схлопываются в одну строку результата.

**Пример / кейс**
```sql
SELECT DISTINCT country
FROM customers;
```
Если в таблице 10000 строк и 12 различных стран, результат — 12 строк (плюс одна строка NULL, если есть клиенты без указанной страны). Проверка: сравнить с `SELECT country, COUNT(*) FROM customers GROUP BY country` — число строк должно совпасть.

### 2. [Q-04-01-0002] Чем отличается фильтрация в WHERE от фильтрации в HAVING и когда какую использовать?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`WHERE` фильтрует отдельные строки до группировки, `HAVING` фильтрует уже готовые группы после агрегации, поэтому в `HAVING` можно использовать агрегатные функции (`SUM`, `COUNT`), а в `WHERE` — нет.

**Разбор**
- **Как это работает:** логический порядок выполнения запроса — `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY`. `WHERE` отсекает строки ещё до формирования групп, поэтому агрегаты там недоступны; `HAVING` работает над результатом `GROUP BY`.
- **На практике:** если условие можно проверить до агрегации (например, «только заказы за 2024 год»), его лучше ставить в `WHERE` — так СУБД отфильтрует строки раньше и обработает меньше данных, что экономит время. `HAVING` нужен только для условий на агрегат, например «сумма заказов клиента больше 1000».
- **Частые ошибки:** пытаются написать `WHERE SUM(amount) > 1000` и получают ошибку; либо, наоборот, ставят в `HAVING` условие, которое можно было вычислить в `WHERE`, из-за чего СУБД агрегирует больше строк, чем нужно, и запрос работает медленнее.

**Пример / кейс**
```sql
SELECT customer_id, SUM(amount) AS total_amount
FROM orders
WHERE order_date >= '2024-01-01'
GROUP BY customer_id
HAVING SUM(amount) > 1000;
```
Результат — только клиенты 2024 года, суммарно потратившие больше 1000. Проверка: для одного customer_id вручную просуммировать его заказы за 2024 год и сравнить с выводом запроса.

### 3. [Q-04-01-0003] В чём разница между INNER JOIN и LEFT JOIN и как она влияет на итоговое количество строк?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`INNER JOIN` оставляет только строки, у которых есть совпадение в обеих таблицах, а `LEFT JOIN` сохраняет все строки левой таблицы, заполняя NULL там, где совпадения в правой таблице не нашлось.

**Разбор**
- **Как это работает:** оба соединения сопоставляют строки по условию в `ON`. `INNER JOIN` отбрасывает «несовпавшие» строки с обеих сторон, `LEFT JOIN` гарантирует, что ни одна строка левой таблицы не потеряется, даже если для неё нет пары справа.
- **На практике:** `LEFT JOIN` используют, когда важно не потерять «пустые» случаи — например, список всех клиентов, включая тех, кто ещё не сделал ни одного заказа. После `LEFT JOIN` стоит проверять поля правой таблицы на `NULL`, чтобы отличить «нет заказов» от «заказ с нулевой суммой».
- **Частые ошибки:** используют `INNER JOIN`, когда нужно посчитать «всех клиентов», и случайно теряют тех, у кого нет заказов — это незаметно искажает метрику (например, процент клиентов без покупок просто исчезает из отчёта).

**Пример / кейс**
```sql
SELECT c.customer_id, COUNT(o.order_id) AS orders_cnt
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id;
```
Клиенты без заказов получат `orders_cnt = 0`. Если заменить на `INNER JOIN`, такие клиенты вообще не попадут в результат — проверить это можно, сравнив количество строк в выводе с `SELECT COUNT(*) FROM customers`.

### 4. [Q-04-01-0004] Почему COUNT(*) и COUNT(column_name) могут давать разные числа на одной и той же таблице?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`COUNT(*)` считает все строки независимо от содержимого, а `COUNT(column_name)` считает только строки, где значение этого столбца не `NULL`.

**Разбор**
- **Как это работает:** `COUNT(*)` — это подсчёт строк в наборе данных, он не смотрит на значения столбцов. `COUNT(column)` сначала проверяет каждую строку на `NULL` в указанном столбце и игнорирует такие строки.
- **На практике:** эта разница часто используется осознанно: например, `COUNT(email)` покажет, сколько клиентов указали email, а `COUNT(*)` — общее число клиентов; разница между ними — количество клиентов без email. Это удобный способ быстро оценить полноту данных по конкретному полю.
- **Частые ошибки:** считают, что `COUNT(column)` всегда равен `COUNT(*)`, и не замечают, что часть данных отсутствует; либо путают `COUNT(DISTINCT column)`, который дополнительно убирает дубликаты значений, с обычным `COUNT(column)`.

**Пример / кейс**
```sql
SELECT COUNT(*) AS total_rows, COUNT(email) AS rows_with_email
FROM customers;
```
Если `total_rows = 1000`, а `rows_with_email = 940`, значит у 60 клиентов email не указан. Проверка: `SELECT COUNT(*) FROM customers WHERE email IS NULL;` должно дать 60.

### 5. [Q-04-01-0005] Почему сравнение `email = NULL` в WHERE никогда не отбирает строки, даже если в таблице есть пустые email?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`NULL` означает «значение неизвестно», поэтому любое сравнение с `NULL` через `=` или `!=` возвращает `NULL` (не `TRUE`), и строка не проходит фильтр; для проверки на пустоту нужно использовать `IS NULL` / `IS NOT NULL`.

**Разбор**
- **Как это работает:** SQL использует трёхзначную логику — `TRUE`, `FALSE` и `UNKNOWN`. Операция `x = NULL` всегда даёт `UNKNOWN`, а `WHERE` пропускает в результат только строки, где условие даёт `TRUE`. Поэтому `UNKNOWN` отбрасывается так же, как `FALSE`.
- **На практике:** для поиска пустых значений всегда используют `IS NULL`/`IS NOT NULL`. Если нужно отобрать строки «email не заполнен или пустая строка», стоит явно писать `email IS NULL OR email = ''`, потому что это два разных случая в данных.
- **Частые ошибки:** пишут `WHERE email != NULL`, ожидая получить все заполненные email, и получают пустой результат; также забывают, что `NOT IN` с подзапросом, содержащим `NULL`, тоже из-за той же логики может вернуть пустой результат целиком.

**Пример / кейс**
```sql
SELECT * FROM customers WHERE email IS NULL;
```
Вернёт все строки с незаполненным email. Проверка — сравнить с результатом `SELECT COUNT(*) FROM customers WHERE email = NULL;`, который всегда равен 0, даже если пустые email есть.

### 6. [Q-04-01-0006] Как заменить NULL на значение по умолчанию при выводе отчёта, не меняя исходные данные?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно использовать функцию `COALESCE(column, 'значение по умолчанию')`, которая возвращает первый не-NULL аргумент из списка, не изменяя данные в таблице.

**Разбор**
- **Как это работает:** `COALESCE` принимает список выражений и возвращает первое из них, которое не равно `NULL`; если все аргументы `NULL`, результат — тоже `NULL`. Это чисто вычисление на уровне вывода запроса, таблица не меняется.
- **На практике:** `COALESCE` часто используют для отчётов («Нет данных» вместо пустой ячейки), а также для безопасных вычислений — например, `COALESCE(discount, 0)`, чтобы `NULL` не «съедал» сумму при арифметике, ведь любое выражение с `NULL` обычно тоже даёт `NULL`.
- **Частые ошибки:** подменяют `NULL` на `0` в метриках типа «средний чек» без понимания, что это меняет смысл — «не было скидки» (0) и «скидка неизвестна» (NULL) — разные ситуации, и слепая замена искажает агрегаты типа `AVG`.

**Пример / кейс**
```sql
SELECT customer_id, COALESCE(email, 'не указан') AS email_display
FROM customers;
```
Все строки с `NULL` в email в выводе покажут «не указан», но в самой таблице `customers` значение останется `NULL`. Проверка: повторный `SELECT email FROM customers` без `COALESCE` всё ещё покажет `NULL`.

### 7. [Q-04-01-0007] Как выбрать клиентов, которые совершили хотя бы один заказ, с помощью подзапроса?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Можно использовать подзапрос в `WHERE ... IN (SELECT customer_id FROM orders)`, который возвращает список id клиентов, встречающихся в таблице заказов.

**Разбор**
- **Как это работает:** подзапрос выполняется (логически) первым и возвращает набор значений `customer_id`; внешний запрос затем проверяет, входит ли `customer_id` каждой строки таблицы `customers` в этот набор через `IN`.
- **На практике:** такой подзапрос — независимый (не коррелированный), то есть не обращается к внешней таблице построчно, поэтому обычно выполняется один раз и может быть эффективным. Альтернатива — `JOIN` с `DISTINCT` или `EXISTS`; на практике результат одинаковый, но план выполнения и читаемость могут отличаться.
- **Частые ошибки:** если в подзапросе `customer_id` может быть `NULL`, то `NOT IN` с таким подзапросом даст неожиданно пустой результат (из-за трёхзначной логики с NULL), хотя обычный `IN` на это не так чувствителен.

**Пример / кейс**
```sql
SELECT *
FROM customers
WHERE customer_id IN (SELECT customer_id FROM orders);
```
Вернёт только клиентов, у которых есть хотя бы одна запись в `orders`. Проверка: количество строк результата должно совпадать с `SELECT COUNT(DISTINCT customer_id) FROM orders WHERE customer_id IN (SELECT customer_id FROM customers)`.

### 8. [Q-04-01-0008] Как посчитать количество заказов и общую сумму продаж по каждому месяцу?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно округлить дату заказа до месяца функцией типа `DATE_TRUNC('month', order_date)` и сгруппировать по этому значению с агрегатами `COUNT` и `SUM`.

**Разбор**
- **Как это работает:** `DATE_TRUNC('month', order_date)` в PostgreSQL (в BigQuery — `DATE_TRUNC(order_date, MONTH)`, в ClickHouse — `toStartOfMonth(order_date)`) приводит дату к первому числу месяца, после чего строки с разными днями, но одним месяцем, попадают в одну группу.
- **На практике:** важно группировать именно по усечённой дате, а не по `EXTRACT(MONTH FROM order_date)`, иначе январь 2023 и январь 2024 схлопнутся в одну группу «месяц 1». Также стоит сразу сортировать результат по дате, а не по алфавиту текстового представления месяца.
- **Частые ошибки:** группируют по текстовому названию месяца («Январь», «Февраль») без года — данные за несколько лет смешиваются; забывают `ORDER BY`, из-за чего строки выводятся в произвольном порядке.

**Пример / кейс**
```sql
SELECT DATE_TRUNC('month', order_date) AS month, COUNT(*) AS orders_cnt, SUM(amount) AS total_amount
FROM orders
GROUP BY 1
ORDER BY 1;
```
Результат — одна строка на каждый календарный месяц, присутствующий в данных. Проверка: сумма всех `total_amount` по месяцам должна совпасть с `SELECT SUM(amount) FROM orders`.

### 9. [Q-04-01-0009] Чем отличается UNION от UNION ALL и когда разница важна для правильного подсчёта метрики?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`UNION` объединяет результаты двух запросов и убирает полностью одинаковые строки, а `UNION ALL` объединяет их без удаления дублей, поэтому для корректного подсчёта количества событий почти всегда нужен `UNION ALL`.

**Разбор**
- **Как это работает:** оба оператора требуют одинакового числа и типа столбцов в объединяемых запросах. `UNION` дополнительно делает операцию, аналогичную `DISTINCT`, по всем строкам результата, что требует сортировки/хеширования и дополнительных ресурсов.
- **На практике:** если две разные по смыслу строки случайно совпадают по всем столбцам (например, два разных события с одинаковыми значениями), `UNION` «съест» одно из них, что приведёт к недосчёту. Поэтому при объединении таблиц событий/логов обычно используют `UNION ALL`.
- **Частые ошибки:** используют `UNION` «по привычке» везде, не задумываясь, что это может незаметно уменьшить количество строк и исказить метрику типа «количество событий»; не проверяют, что порядок и типы столбцов в обоих SELECT совпадают.

**Пример / кейс**
```sql
SELECT customer_id, 'web' AS source FROM web_orders
UNION ALL
SELECT customer_id, 'app' AS source FROM app_orders;
```
Результат содержит все заказы из обоих источников без потерь. Проверка: `COUNT(*)` объединённого запроса должен равняться сумме `COUNT(*)` по каждой таблице отдельно.

### 10. [Q-04-01-0010] Как с помощью CASE WHEN разбить клиентов на возрастные группы прямо в SELECT?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно использовать конструкцию `CASE WHEN условие THEN значение ... ELSE значение END`, которая последовательно проверяет условия и возвращает соответствующую метку для каждой строки.

**Разбор**
- **Как это работает:** `CASE` проверяет условия `WHEN` по порядку сверху вниз и возвращает результат первого истинного условия; если ни одно не сработало, используется `ELSE` (а если `ELSE` не указан — результат `NULL`).
- **На практике:** такие группировки по диапазонам удобно выносить в `CASE`, а затем использовать как обычный столбец в `GROUP BY` или `ORDER BY`. Важно продумать границы диапазонов без пропусков и перекрытий, иначе часть строк попадёт не туда или не попадёт никуда.
- **Частые ошибки:** оставляют «дырки» между условиями (например, `age < 18` и `age > 18`, забывая про `age = 18`); не предусматривают `ELSE`, из-за чего строки, не подошедшие ни под одно условие, тихо превращаются в `NULL` и выпадают из последующей группировки, если она делается не по NULL-совместимой логике.

**Пример / кейс**
```sql
SELECT customer_id,
       CASE
         WHEN age < 18 THEN 'до 18'
         WHEN age BETWEEN 18 AND 34 THEN '18-34'
         WHEN age BETWEEN 35 AND 54 THEN '35-54'
         ELSE '55+'
       END AS age_group
FROM customers;
```
Каждый клиент получает одну из четырёх групп. Проверка: сумма количества строк по всем группам (включая возможный NULL-возраст, если не учтён отдельно) должна равняться общему числу клиентов.


### 11. [Q-04-01-0011] Как с помощью простого CTE разбить сложный запрос на читаемые шаги?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно использовать конструкцию `WITH имя_cte AS (SELECT ...)`, которая объявляет временный именованный результат запроса, доступный в основном запросе ниже как обычная таблица.

**Разбор**
- **Как это работает:** CTE (Common Table Expression) — это именованный подзапрос, объявленный перед основным `SELECT`. Он вычисляется (логически) один раз и затем используется по имени, что делает длинный запрос похожим на последовательность шагов «вычислили промежуточный результат → используем его дальше».
- **На практике:** CTE особенно полезен, когда нужно сначала агрегировать данные, а потом отфильтровать или присоединить их к другой таблице — без CTE пришлось бы вкладывать подзапросы друг в друга, что хуже читается. В большинстве современных СУБД (PostgreSQL 12+) оптимизатор может «встроить» (inline) простой CTE в основной план, поэтому использование `WITH` обычно не обязывает к материализации и не всегда замедляет запрос.
- **Частые ошибки:** считают, что CTE — это всегда отдельная временная таблица, которая один раз считается и кэшируется для многократного использования в одном запросе; в большинстве диалектов это не гарантировано, и при нескольких обращениях к CTE расчёт может повториться.

**Пример / кейс**
```sql
WITH monthly_sales AS (
  SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS total_amount
  FROM orders
  GROUP BY 1
)
SELECT month, total_amount
FROM monthly_sales
WHERE total_amount > 100000
ORDER BY month;
```
Результат — только месяцы с продажами выше 100000. Проверка: убрать `WHERE` из основного запроса и сравнить полный список сумм по месяцам с отфильтрованным.

### 12. [Q-04-01-0012] Как отобрать 10 клиентов с наибольшей суммой покупок?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно сгруппировать заказы по клиенту, посчитать сумму покупок, отсортировать по убыванию суммы и ограничить вывод конструкцией `LIMIT 10` (в PostgreSQL/ClickHouse) или `LIMIT 10` / `TOP 10` в зависимости от диалекта.

**Разбор**
- **Как это работает:** `GROUP BY customer_id` формирует одну строку на клиента с агрегатом `SUM(amount)`, `ORDER BY total_amount DESC` располагает клиентов от наибольшей суммы к наименьшей, а `LIMIT 10` отсекает все строки после десятой.
- **На практике:** без `ORDER BY` перед `LIMIT` результат недетерминирован — СУБД не обязана возвращать строки в каком-то конкретном порядке, если он явно не задан, поэтому «топ-10» без сортировки — это фактически случайные 10 строк. При равенстве сумм у нескольких клиентов на границе топ-10 нужно явно решить, как обрабатывать «ничьи» (например, добавить вторичный критерий сортировки).
- **Частые ошибки:** ставят `LIMIT` до `ORDER BY` по смыслу (хотя синтаксически `ORDER BY` должен идти перед `LIMIT`) или вовсе забывают `ORDER BY`; не учитывают, что при равных суммах граница топ-10 может быть произвольной и меняться между запусками.

**Пример / кейс**
```sql
SELECT customer_id, SUM(amount) AS total_amount
FROM orders
GROUP BY customer_id
ORDER BY total_amount DESC
LIMIT 10;
```
Результат — 10 строк, отсортированных по убыванию суммы. Проверка: для клиента на 1-й позиции вручную просуммировать его заказы и сравнить с выводом.

### 13. [Q-04-01-0013] В чём разница между WHERE-фильтром на правой таблице и условием в ON при LEFT JOIN?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Условие в `ON` применяется в момент соединения строк и не убирает строки левой таблицы при `LEFT JOIN`, а условие в `WHERE` применяется после соединения и может отфильтровать (убрать) строки левой таблицы, если правая часть оказалась `NULL`.

**Разбор**
- **Как это работает:** при `LEFT JOIN` СУБД сначала пытается найти пары по условию в `ON`; если пары нет, строка левой таблицы всё равно остаётся, а столбцы правой заполняются `NULL`. Если затем в `WHERE` стоит условие на столбец правой таблицы (например, `status = 'paid'`), то строки с `NULL` в этом столбце не проходят фильтр и теряются — результат фактически превращается в `INNER JOIN`.
- **На практике:** если нужно оставить все строки левой таблицы и при этом ограничить, какие строки правой таблицы учитывать при соединении (например, только оплаченные заказы), условие на правую таблицу нужно переносить в `ON`, а не в `WHERE`.
- **Частые ошибки:** пишут `LEFT JOIN orders o ON o.customer_id = c.customer_id WHERE o.status = 'paid'`, ожидая увидеть всех клиентов, но на деле получают только тех, у кого есть оплаченный заказ — это классическая скрытая ошибка, которая выглядит как рабочий запрос.

**Пример / кейс**
```sql
SELECT c.customer_id, o.order_id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id AND o.status = 'paid';
```
Все клиенты останутся в результате, а `order_id` будет `NULL` у тех, у кого нет оплаченных заказов. Проверка: количество строк в результате должно быть не меньше `SELECT COUNT(*) FROM customers`.

### 14. [Q-04-01-0014] Как посчитать разницу в днях между датой регистрации и датой первого заказа клиента?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно вычесть одну дату из другой; в PostgreSQL результат вычитания двух `date` — целое число дней, а для дат с временем точнее использовать функции вроде `DATE_PART`/`EXTRACT(EPOCH FROM ...)` или `DATEDIFF` в зависимости от диалекта.

**Разбор**
- **Как это работает:** в PostgreSQL `order_date - registration_date` для типа `date` сразу даёт `integer` — количество дней; для `timestamp` результат — интервал, который может включать часы и минуты, и для получения целых дней его нужно явно привести, например через `EXTRACT(DAY FROM ...)` или приведение к `date`. В BigQuery для этого есть `DATE_DIFF(date1, date2, DAY)`, в ClickHouse — `dateDiff('day', date1, date2)`.
- **На практике:** перед вычислением важно убедиться, что обе даты в одном часовом поясе и одном типе (date vs timestamp), иначе разница может «съехать» на день из-за времени суток. Также нужно решить, что делать, если дата первого заказа раньше даты регистрации (ошибка в данных) — такие случаи стоит проверять отдельно, а не слепо включать в статистику.
- **Частые ошибки:** вычитают `timestamp`-значения и интерпретируют результат как целое число дней без учёта часов; не проверяют отрицательные разницы, которые обычно означают проблему в данных, а не реальный бизнес-кейс.

**Пример / кейс**
```sql
SELECT customer_id,
       first_order_date - registration_date AS days_to_first_order
FROM customer_first_order;
```
Если `registration_date = '2024-01-01'`, `first_order_date = '2024-01-05'`, результат — 4. Проверка: отрицательные значения `days_to_first_order` стоит вывести отдельно и проверить вручную по первичным данным.

### 15. [Q-04-01-0015] Как привести текстовое поле с датой в формате '2024-05-01' к типу date и отфильтровать по нему?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно явно привести строку к типу `date`, например `CAST(column AS DATE)` или через `column::date` (синтаксис PostgreSQL), после чего её можно сравнивать с другими датами или использовать в условиях `WHERE`.

**Разбор**
- **Как это работает:** `CAST` проверяет, соответствует ли текст ожидаемому формату даты, и преобразует значение в настоящий тип `date`; если формат не распознан, запрос завершится ошибкой (в отличие от «мягких» функций типа `TRY_CAST` в некоторых диалектах, которые при ошибке вернут `NULL`).
- **На практике:** если формат дат в данных нестандартный (например, `01.05.2024` вместо `2024-05-01`), прямой `CAST` может сработать неверно или с ошибкой — тогда нужно сначала явно распарсить строку функцией вида `TO_DATE(column, 'DD.MM.YYYY')`. Хранение дат как текста в принципе создаёт риск: сортировка и сравнение такого текста не совпадают с сортировкой реальных дат.
- **Частые ошибки:** сравнивают текстовые «даты» как строки без приведения типа — тогда '2024-2-1' и '2024-02-01' считаются разными значениями, а сортировка по тексту даёт неверный хронологический порядок (например, '2024-10-01' окажется раньше '2024-2-01' при лексикографическом сравнении).

**Пример / кейс**
```sql
SELECT *
FROM events
WHERE CAST(event_date_text AS DATE) >= '2024-05-01';
```
Результат — только события с датой от 1 мая 2024 и позже. Проверка: выполнить `SELECT DISTINCT event_date_text FROM events WHERE CAST(event_date_text AS DATE) IS NULL` — если есть строки, значит часть данных не парсится и требует отдельной обработки.

### 16. [Q-04-01-0016] Как объединить имя и фамилию клиента в одно поле и аккуратно обработать случай, когда фамилия не указана?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно использовать `CONCAT(first_name, ' ', COALESCE(last_name, ''))` или оператор `||` в PostgreSQL, сначала заменив возможный `NULL` в фамилии на пустую строку через `COALESCE`.

**Разбор**
- **Как это работает:** оператор конкатенации `||` в PostgreSQL возвращает `NULL`, если хотя бы один из операндов `NULL`, из-за чего всё итоговое поле «пропадает»; функция `CONCAT` в PostgreSQL устроена мягче и обычно трактует `NULL` как пустую строку, но поведение может отличаться между диалектами, поэтому надёжнее явно обезопасить себя `COALESCE`.
- **На практике:** перед склеиванием текстовых полей стоит всегда продумывать: что должно получиться, если одно из полей пустое? Для отчётов обычно хотят увидеть «Иван» вместо пустой строки или `NULL`, а не терять всю запись.
- **Частые ошибки:** используют `first_name || ' ' || last_name` без `COALESCE` и удивляются, почему часть строк в итоговом поле полностью пустая (`NULL`), хотя имя точно было указано.

**Пример / кейс**
```sql
SELECT customer_id,
       CONCAT(first_name, ' ', COALESCE(last_name, '')) AS full_name
FROM customers;
```
Для клиента с `first_name = 'Анна'`, `last_name = NULL` результат — `'Анна '` (с пробелом, который можно дополнительно обработать `TRIM`). Проверка: сравнить количество непустых `full_name` с `COUNT(*)` клиентов.

### 17. [Q-04-01-0017] Как найти всех клиентов, у которых email содержит домен "@gmail.com"?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно использовать оператор `LIKE` с шаблоном `WHERE email LIKE '%@gmail.com'`, где `%` обозначает любую последовательность символов до искомой подстроки.

**Разбор**
- **Как это работает:** `LIKE` сравнивает строку с шаблоном, где `%` заменяет любое количество (в том числе ноль) произвольных символов, а `_` — ровно один символ. По умолчанию в большинстве СУБД `LIKE` чувствителен к регистру (в PostgreSQL для нечувствительного поиска есть `ILIKE`).
- **На практике:** шаблон `'%@gmail.com'` найдёт email, заканчивающиеся именно на этот домен, но не отличит реальный домен от строки, которая просто содержит эту подстроку в другом месте, если убрать `%` в конце. Для больших таблиц поиск с `%` в начале шаблона (`LIKE '%gmail%'`) обычно не может использовать обычный B-tree индекс эффективно и может быть медленным.
- **Частые ошибки:** используют `LIKE 'gmail.com%'` (без `%` в начале), что ищет email, начинающиеся с «gmail.com», а не заканчивающиеся на него; не учитывают регистр букв в доменах, если СУБД чувствительна к регистру.

**Пример / кейс**
```sql
SELECT *
FROM customers
WHERE email ILIKE '%@gmail.com';
```
Результат — все клиенты с почтой на gmail.com независимо от регистра. Проверка: вручную просмотреть 5-10 строк результата и убедиться, что домен действительно gmail.com, а не похожая подстрока.

### 18. [Q-04-01-0018] Чем RIGHT JOIN отличается от LEFT JOIN и почему RIGHT JOIN на практике используют реже?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`RIGHT JOIN` сохраняет все строки правой таблицы (а не левой, как при `LEFT JOIN`), заполняя `NULL` для несовпавших строк левой таблицы; на практике его используют реже, потому что тот же результат проще получить, переставив таблицы местами и используя привычный `LEFT JOIN`.

**Разбор**
- **Как это работает:** `A RIGHT JOIN B ON ...` логически эквивалентен `B LEFT JOIN A ON ...` с тем же условием — просто меняются «главная» и «подчинённая» таблицы в соединении.
- **На практике:** большинство аналитиков договариваются о стиле, где «главная» таблица (та, чьи строки точно нужно сохранить) всегда пишется первой с `LEFT JOIN` — это облегчает чтение сложных запросов с несколькими соединениями, потому что не нужно удерживать в голове направление `RIGHT JOIN`.
- **Частые ошибки:** в запросах с несколькими соединениями смешивают `LEFT` и `RIGHT JOIN`, из-за чего становится трудно понять, какая строка в итоге должна быть «обязательно сохранена», и легко случайно потерять нужные строки при добавлении нового условия.

**Пример / кейс**
```sql
-- Эквивалентные запросы
SELECT * FROM orders o RIGHT JOIN customers c ON o.customer_id = c.customer_id;
SELECT * FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id;
```
Оба запроса вернут одинаковый набор строк (возможно, в разном порядке столбцов). Проверка: сравнить количество строк и набор значений `customer_id` в обоих результатах — они должны совпадать.

### 19. [Q-04-01-0019] Как проверить таблицу на дубликаты строк по комбинации «email + дата заказа»?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно сгруппировать таблицу по этим двум столбцам, посчитать количество строк в каждой группе через `COUNT(*)` и отобрать группы с `HAVING COUNT(*) > 1` — это и есть дубликаты.

**Разбор**
- **Как это работает:** `GROUP BY email, order_date` объединяет все строки с одинаковой комбинацией этих значений в одну группу; `COUNT(*)` в каждой группе показывает, сколько исходных строк туда попало, а `HAVING` отфильтровывает только те группы, где это число больше 1.
- **На практике:** перед любой агрегацией метрик (суммы, средние) полезно сначала явно проверить данные на дубликаты именно таким запросом — это быстрый и наглядный способ понять масштаб проблемы до того, как строить отчёт. Дубликаты могут появляться из-за повторной выгрузки данных, сбоя в ETL или неправильного JOIN на предыдущем шаге.
- **Частые ошибки:** находят дубликаты, но сразу удаляют их все без анализа причины — иногда «дубликаты» на самом деле разные события с одинаковыми значениями полей (например, два разных товара, купленных в одну секунду), и бездумное удаление искажает данные.

**Пример / кейс**
```sql
SELECT email, order_date, COUNT(*) AS cnt
FROM orders
GROUP BY email, order_date
HAVING COUNT(*) > 1
ORDER BY cnt DESC;
```
Если результат пустой — дубликатов по этой комбинации нет. Проверка: для одной найденной пары email+дата вручную просмотреть все строки через `SELECT * FROM orders WHERE email = ... AND order_date = ...` и понять, действительно ли это задвоение.

### 20. [Q-04-01-0020] В чём разница между EXISTS и IN при проверке наличия связанных записей в другой таблице?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`IN` сравнивает значение с готовым списком результатов подзапроса, а `EXISTS` просто проверяет, вернул ли коррелированный подзапрос хотя бы одну строку, без интереса к конкретным значениям — для простых случаев они дают одинаковый результат, но ведут себя по-разному при NULL и в сложных подзапросах.

**Разбор**
- **Как это работает:** `WHERE x IN (SELECT y FROM t)` требует, чтобы `x` совпало с одним из значений `y`; если подзапрос — коррелированный (обращается к внешней таблице), `EXISTS` просто возвращает `TRUE`/`FALSE` по факту существования подходящей строки, что для СУБД часто проще оптимизировать, особенно если внутри нет необходимости строить весь список значений.
- **На практике:** `EXISTS` обычно предпочтительнее, когда подзапрос коррелированный и таблицы большие, потому что движок может остановиться на первой найденной подходящей строке. `IN` удобнее для короткого, явного списка значений или независимого подзапроса.
- **Частые ошибки:** используют `NOT IN (SELECT ... )`, где подзапрос может вернуть `NULL`-значения — это приводит к тому, что весь `NOT IN` неожиданно не находит ни одной строки; `NOT EXISTS` этой проблемы не имеет, поэтому для «отсутствия записи» он надёжнее.

**Пример / кейс**
```sql
SELECT c.customer_id
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);
```
Результат — клиенты, у которых есть хотя бы один заказ. Проверка: количество строк должно совпасть с `SELECT COUNT(DISTINCT customer_id) FROM orders`.


### 21. [Q-04-01-0021] Как сравнить среднее время обработки заказа только для заказов со статусом «доставлен» и «отменён», используя условную агрегацию?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Можно посчитать два отдельных агрегата в одном `SELECT`, используя `AVG(CASE WHEN status = 'delivered' THEN processing_time END)` и аналогично для `cancelled`, без необходимости делать два отдельных запроса или `GROUP BY status`.

**Разбор**
- **Как это работает:** `CASE` внутри агрегатной функции возвращает значение только для строк, удовлетворяющих условию, а для остальных — `NULL` (если `ELSE` не задан); агрегатные функции (`AVG`, `SUM`, `COUNT`) по умолчанию игнорируют `NULL`, поэтому в расчёт попадают только нужные строки.
- **На практике:** такой подход удобен, когда нужно вывести несколько «разрезов» метрики в одной строке результата — например, для сравнения в одной таблице отчёта, а не в нескольких строках после `GROUP BY status`. В PostgreSQL для той же задачи есть более короткий синтаксис `AVG(processing_time) FILTER (WHERE status = 'delivered')`.
- **Частые ошибки:** забывают, что `CASE WHEN ... THEN ... END` без `ELSE` даёт `NULL`, а не `0`, из-за чего при использовании `SUM` вместо `AVG` результат может получиться верным случайно, а при `AVG` — наоборот, не учитывать несовпадающие строки в знаменателе, что и нужно, но иногда ожидания у аналитика другие.

**Пример / кейс**
```sql
SELECT
  AVG(CASE WHEN status = 'delivered' THEN processing_time END) AS avg_delivered,
  AVG(CASE WHEN status = 'cancelled' THEN processing_time END) AS avg_cancelled
FROM orders;
```
Результат — одна строка с двумя числами для сравнения. Проверка: сравнить `avg_delivered` с результатом отдельного запроса `SELECT AVG(processing_time) FROM orders WHERE status = 'delivered'`.

### 22. [Q-04-01-0022] Как выбрать заказы, сделанные в диапазоне дат с 1 по 31 марта 2024 года включительно, без риска случайно упустить последний день?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Безопаснее использовать полуоткрытый интервал `order_date >= '2024-03-01' AND order_date < '2024-04-01'`, чем `BETWEEN '2024-03-01' AND '2024-03-31'`, особенно если `order_date` хранится как `timestamp`, а не как чистая дата.

**Разбор**
- **Как это работает:** `BETWEEN a AND b` эквивалентно `>= a AND <= b`. Если поле — `date`, `BETWEEN '2024-03-01' AND '2024-03-31'` действительно включает весь март. Но если поле — `timestamp`, то `'2024-03-31'` интерпретируется как полночь `2024-03-31 00:00:00`, и заказы, сделанные позже полуночи 31 марта (например, в 15:00), в диапазон не попадут.
- **На практике:** полуоткрытый интервал `[начало месяца, начало следующего месяца)` работает одинаково надёжно независимо от того, `date` это или `timestamp`, и его проще обобщить на произвольный период, вычисляя границы динамически.
- **Частые ошибки:** используют `BETWEEN` с текстовой датой конца периода без времени для `timestamp`-столбца и теряют часть дня; либо жёстко прописывают `'2024-03-31 23:59:59'`, что технически работает, но ломается при наличии долей секунды или при смене типа столбца.

**Пример / кейс**
```sql
SELECT *
FROM orders
WHERE order_date >= '2024-03-01' AND order_date < '2024-04-01';
```
Результат — все заказы марта 2024, включая сделанные в последнюю секунду 31 марта. Проверка: сравнить максимум `order_date` в результате с максимумом `order_date` по всей таблице за март, отфильтрованной вручную через `EXTRACT`.

### 23. [Q-04-01-0023] Как сгруппировать продажи сразу по региону и по категории товара, чтобы увидеть сумму по каждой паре?

**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)

Нужно перечислить оба столбца в `GROUP BY region, category` — тогда каждая уникальная пара «регион + категория» станет отдельной группой со своим агрегатом.

**Разбор**
- **Как это работает:** при группировке по нескольким столбцам СУБД формирует группы по уникальным комбинациям значений всех указанных столбцов, а не отдельно по каждому. Количество итоговых строк равно числу различных сочетаний «регион + категория», встречающихся в данных.
- **На практике:** перед интерпретацией такой таблицы стоит проверить, что в данных нет пропущенных комбинаций (например, региона без какой-то категории) — это может быть реальным отсутствием продаж, а может быть проблемой данных, если такая комбинация ожидалась.

```sql
SELECT region, category, SUM(amount) AS total_amount
FROM sales
GROUP BY region, category
ORDER BY region, category;
```
Результат — по одной строке на каждую встретившуюся пару. Проверка: сумма `total_amount` по всем строкам должна совпасть с `SELECT SUM(amount) FROM sales`.

### 24. [Q-04-01-0024] Как с помощью самосоединения (self-join) найти пары сотрудников, работающих в одном отделе?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно присоединить таблицу `employees` к самой себе по условию совпадения `department_id`, добавив условие `e1.employee_id < e2.employee_id`, чтобы не получить пары-дубликаты и пары сотрудника с самим собой.

**Разбор**
- **Как это работает:** self-join — это обычный `JOIN`, где обе стороны указывают на одну и ту же таблицу, но с разными алиасами (`e1`, `e2`); СУБД рассматривает это как соединение двух независимых копий данных по заданному условию.
- **На практике:** условие `e1.employee_id < e2.employee_id` (а не `!=`) одновременно решает две проблемы: убирает пары вида «сотрудник сам с собой» и убирает зеркальные дубликаты вида (A, B) и (B, A), оставляя только одну версию каждой пары.
- **Частые ошибки:** используют `e1.employee_id != e2.employee_id` без строгого неравенства порядка, из-за чего каждая пара сотрудников появляется в результате дважды, в обоих направлениях, и это раздувает последующие агрегаты (например, «количество пар») вдвое.

**Пример / кейс**
```sql
SELECT e1.employee_id AS emp1, e2.employee_id AS emp2, e1.department_id
FROM employees e1
JOIN employees e2
  ON e1.department_id = e2.department_id AND e1.employee_id < e2.employee_id;
```
Для отдела из 3 сотрудников результат — ровно 3 уникальные пары (а не 6). Проверка: для отдела с N сотрудниками количество пар должно равняться N*(N-1)/2.

### 25. [Q-04-01-0025] Как отобрать 2-ю «страницу» результатов по 20 строк при постраничном выводе списка клиентов?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно отсортировать результат по стабильному критерию и использовать `LIMIT 20 OFFSET 20`, где `OFFSET` пропускает первые 20 строк, а `LIMIT` возвращает следующие 20.

**Разбор**
- **Как это работает:** `OFFSET n` указывает СУБД пропустить первые `n` строк отсортированного результата перед тем, как начать отдавать строки согласно `LIMIT`. Без явного и однозначного `ORDER BY` порядок строк не гарантирован, а значит «страницы» могут перекрываться или задваиваться между запросами.
- **На практике:** постраничный вывод обязательно нужно сортировать по уникальному или хотя бы детерминированному ключу (например, `customer_id`), иначе при наличии одинаковых значений в сортируемом столбце строки могут «перетасоваться» между вызовами, и часть клиентов будет показана два раза или не показана вовсе.
- **Частые ошибки:** сортируют только по неуникальному полю (например, по дате регистрации без вторичного критерия) — тогда при одинаковых датах порядок внутри группы не гарантирован, и постраничная навигация становится нестабильной; также `OFFSET` на больших таблицах может быть неожиданно медленным, так как СУБД фактически вычисляет и отбрасывает все предыдущие строки.

**Пример / кейс**
```sql
SELECT customer_id, full_name
FROM customers
ORDER BY customer_id
LIMIT 20 OFFSET 20;
```
Результат — клиенты с 21-го по 40-й в порядке возрастания customer_id. Проверка: первая строка этой «страницы» должна совпадать с 21-й строкой полного списка, отсортированного тем же образом.

### 26. [Q-04-01-0026] Как получить и общее количество заказов, и суммарную выручку по каждому статусу заказа в одном запросе?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно сгруппировать таблицу заказов по статусу и в одном `SELECT` перечислить сразу несколько агрегатных функций — `COUNT(*)` и `SUM(amount)` — они вычисляются параллельно для каждой группы.

**Разбор**
- **Как это работает:** при наличии `GROUP BY status` СУБД формирует группы строк с одинаковым статусом, а затем для каждой группы независимо вычисляет все агрегатные функции, указанные в `SELECT`; это не требует отдельных проходов по данным для каждой метрики.
- **На практике:** такой подход эффективнее, чем писать два отдельных запроса и затем вручную сопоставлять результаты — СУБД читает таблицу один раз и сразу считает всё необходимое. Это базовый паттерн для большинства сводных отчётов.
- **Частые ошибки:** пытаются добавить третью метрику с другой логикой фильтрации (например, «выручка только по заказам старше недели») в тот же `GROUP BY status` без условной агрегации (`CASE WHEN`/`FILTER`), что требует либо дополнительного столбца в условии, либо отдельного запроса.

**Пример / кейс**
```sql
SELECT status, COUNT(*) AS orders_cnt, SUM(amount) AS total_amount
FROM orders
GROUP BY status
ORDER BY orders_cnt DESC;
```
Результат — по одной строке на каждый статус с двумя метриками. Проверка: сумма `orders_cnt` по всем строкам должна равняться `SELECT COUNT(*) FROM orders`.

### 27. [Q-04-01-0027] Какая разница между типами данных для хранения цены товара — INTEGER (в копейках), NUMERIC и FLOAT — и почему это важно для аналитика?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`FLOAT`/`DOUBLE` хранят числа с приблизительной точностью и могут давать мелкие ошибки округления при суммировании денежных значений, тогда как `NUMERIC`/`DECIMAL` (или целые копейки в `INTEGER`) хранят точное значение — поэтому для денег предпочтительны `NUMERIC` или целочисленное хранение в минимальных единицах.

**Разбор**
- **Как это работает:** `FLOAT`/`DOUBLE PRECISION` — это числа с плавающей точкой по стандарту IEEE 754, они не могут точно представить многие десятичные дроби (например, 0.1), из-за чего при множестве сложений может накопиться заметная погрешность. `NUMERIC(p, s)` хранит точное десятичное значение с заданной точностью, хоть и немного медленнее в вычислениях.
- **На практике:** для сумм в отчётах, особенно при проверке «сходится ли общая выручка до копейки» с бухгалтерией, разница между `FLOAT` и `NUMERIC` может стать заметной на больших объёмах операций. Хранение цены как целого числа копеек — ещё один надёжный способ избежать проблем с округлением вообще.
- **Частые ошибки:** сравнивают денежные `FLOAT`-значения на точное равенство (`price = 19.99`) и получают неожиданный `FALSE` из-за погрешности представления; не замечают, что `SUM` по множеству `FLOAT`-строк слегка «не бьётся» с ожидаемым контрольным числом.

**Пример / кейс**
```sql
SELECT SUM(price) FROM order_items; -- price NUMERIC(10,2)
```
Если все 10000 позиций по 19.99, результат должен быть ровно 199900.00. Проверка: пересчитать вручную `COUNT(*) * 19.99` и сравнить с результатом `SUM`.

### 28. [Q-04-01-0028] Как вывести топ-3 самых дорогих товара в каждой категории, используя только базовые средства (без оконных функций)?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Можно использовать коррелированный подзапрос, который для каждого товара считает, сколько товаров в той же категории дороже него, и оставляет только те, где таких не больше двух (то есть товар входит в топ-3).

**Разбор**
- **Как это работает:** для каждой строки внешнего запроса подзапрос пересчитывает количество товаров той же категории с ценой строго больше текущей; если это количество меньше 3 (0, 1 или 2 более дорогих товара), значит текущий товар находится в первой, второй или третьей позиции по цене внутри своей категории.
- **На практике:** это рабочий, но не самый эффективный способ — коррелированный подзапрос выполняется для каждой строки заново, что на больших таблицах может быть медленным; на уровне Middle для этой задачи обычно используют оконную функцию `RANK()`/`ROW_NUMBER()`, которая решает её за один проход.
- **Частые ошибки:** не учитывают одинаковые цены — при использовании строгого «меньше 3 товаров дороже» два товара с одинаковой максимальной ценой оба попадут в топ-1, из-за чего итоговое количество строк на категорию может быть больше 3, и это нужно сознательно допустить или обработать отдельно.

**Пример / кейс**
```sql
SELECT p1.category, p1.product_name, p1.price
FROM products p1
WHERE (
  SELECT COUNT(*) FROM products p2
  WHERE p2.category = p1.category AND p2.price > p1.price
) < 3
ORDER BY p1.category, p1.price DESC;
```
Результат — до 3 (или больше при ничьих) товаров на категорию. Проверка: для одной категории вручную отсортировать все товары по цене и сверить с выводом.

### 29. [Q-04-01-0029] Чем CROSS JOIN отличается от обычного JOIN и в каком безопасном сценарии он действительно нужен?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`CROSS JOIN` соединяет каждую строку одной таблицы с каждой строкой другой без какого-либо условия, образуя декартово произведение; он полезен, когда нужно специально построить все комбинации, например, все пары «дата × товар» для последующего заполнения пропусков.

**Разбор**
- **Как это работает:** если в первой таблице M строк, а во второй N, результат `CROSS JOIN` содержит M×N строк — каждая строка первой таблицы сочетается с каждой строкой второй. Обычный `JOIN` с условием в `ON` — это, по сути, `CROSS JOIN` с последующей фильтрацией только совпадающих пар.
- **На практике:** осознанный `CROSS JOIN` часто используют вместе с календарной таблицей дат, чтобы получить «все дни × все товары» и затем через `LEFT JOIN` подставить реальные продажи, явно показывая дни без продаж как 0, а не как отсутствие строки.
- **Частые ошибки:** случайно получают декартово произведение, забыв условие `ON` в обычном `JOIN` или перепутав названия столбцов при соединении — это резко увеличивает число строк и искажает последующие суммы (например, SUM удваивается или умножается в разы).

**Пример / кейс**
```sql
SELECT d.calendar_date, p.product_id
FROM calendar d
CROSS JOIN products p;
```
Для 30 дней и 10 товаров результат — ровно 300 строк. Проверка: `SELECT COUNT(*)` результата должен равняться произведению количества строк в `calendar` и `products`.

### 30. [Q-04-01-0030] Как с помощью GROUP BY и HAVING найти клиентов, которые делали заказы хотя бы в 3 разных месяцах?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно сгруппировать заказы по клиенту, посчитать количество уникальных месяцев через `COUNT(DISTINCT DATE_TRUNC('month', order_date))` и отфильтровать группы, где это число больше или равно 3, через `HAVING`.

**Разбор**
- **Как это работает:** `COUNT(DISTINCT ...)` внутри группы считает не общее количество заказов, а число уникальных значений выражения — в данном случае уникальных «месяцев» заказа у этого клиента. `HAVING` затем сравнивает это число с порогом.
- **На практике:** такой запрос — простой способ отличить «активного» клиента, который возвращается в разные месяцы, от клиента, сделавшего много заказов за один день. Важно использовать именно `DATE_TRUNC` (или аналог), а не просто `order_date`, иначе каждая отдельная дата будет считаться отдельным «месяцем».
- **Частые ошибки:** считают `COUNT(DISTINCT order_date)` вместо `COUNT(DISTINCT DATE_TRUNC('month', order_date))` — это покажет число уникальных дней, а не месяцев, что отвечает на другой вопрос; не осознают, что клиент с заказами в январе 2023 и январе 2024 — это 2 разных месяца, а не один.

**Пример / кейс**
```sql
SELECT customer_id
FROM orders
GROUP BY customer_id
HAVING COUNT(DISTINCT DATE_TRUNC('month', order_date)) >= 3;
```
Результат — только клиенты с заказами в 3+ разных месяцах. Проверка: для одного найденного клиента вывести `SELECT DISTINCT DATE_TRUNC('month', order_date) FROM orders WHERE customer_id = ...` и убедиться, что их действительно 3 или больше.

### 31. [Q-04-01-0031] Как проверить, что столбец order_id действительно уникален и может служить первичным ключом?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно сравнить общее количество строк в таблице с количеством уникальных значений этого столбца: `SELECT COUNT(*), COUNT(DISTINCT order_id) FROM orders;` — если числа совпадают, столбец уникален.

**Разбор**
- **Как это работает:** `COUNT(*)` считает все строки, а `COUNT(DISTINCT order_id)` — только уникальные значения столбца; если `order_id` действительно не повторяется, оба числа будут равны. Если второе число меньше первого, значит есть повторяющиеся значения.
- **На практике:** эту проверку стоит делать перед тем, как использовать столбец как ключ соединения (`JOIN`) — если ожидаемый уникальный ключ на самом деле содержит дубликаты, `JOIN` по нему может незаметно размножить строки («fan-out») и искажённо увеличить последующие суммы.
- **Частые ошибки:** проверяют уникальность только «на глаз», просматривая первые несколько строк, или полагаются на документацию/название столбца («id» в названии не гарантирует реальную уникальность в данных, особенно если это не настоящий первичный ключ в БД, а просто поле из выгрузки).

**Пример / кейс**
```sql
SELECT COUNT(*) AS total_rows, COUNT(DISTINCT order_id) AS unique_ids
FROM orders;
```
Если `total_rows = 5000` и `unique_ids = 4980`, значит есть 20 «лишних» дублирующихся строк, которые нужно расследовать отдельным запросом с `GROUP BY order_id HAVING COUNT(*) > 1`.

### 32. [Q-04-01-0032] Как посчитать возраст клиента в полных годах на основе даты рождения?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
В PostgreSQL можно использовать `EXTRACT(YEAR FROM AGE(CURRENT_DATE, birth_date))`, где `AGE` возвращает интервал между двумя датами, а `EXTRACT(YEAR FROM ...)` берёт из него количество полных лет с учётом того, был ли уже день рождения в этом году.

**Разбор**
- **Как это работает:** `AGE(end_date, start_date)` в PostgreSQL корректно учитывает календарные месяцы и дни, а не просто делит разницу в днях на 365 — поэтому результат точнее для расчёта «полных лет». Простое вычисление `(CURRENT_DATE - birth_date) / 365` даёт приблизительный и иногда неверный на один год результат из-за високосных лет.
- **На практике:** для возрастной сегментации важно явно зафиксировать точку отсчёта — «на сегодня» (`CURRENT_DATE`) или «на момент события» (например, на дату заказа), особенно если отчёт строится не в реальном времени, а на исторических данных.
- **Частые ошибки:** делят разницу в днях на 365 без учёта високосных годов и месяцев, что на границе дня рождения может показать на единицу неверный возраст; считают возраст от `CURRENT_DATE`, когда в контексте отчёта нужен возраст на момент конкретного события в прошлом.

**Пример / кейс**
```sql
SELECT customer_id, EXTRACT(YEAR FROM AGE(CURRENT_DATE, birth_date)) AS age
FROM customers;
```
Для `birth_date = '2000-05-01'` и текущей даты `2024-04-20` результат — 23 (день рождения ещё не наступил). Проверка: вручную посчитать возраст для нескольких граничных дат рождения (сегодня, вчера, завтра относительно текущей даты минус N лет).

### 33. [Q-04-01-0033] Почему при объединении данных из разных систем сумма заказов «не бьётся», если в одной системе время хранится в UTC, а в другой — в локальном часовом поясе?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Если одна таблица хранит время в UTC, а другая — в локальном часовом поясе, группировка «по дню» без приведения к единому часовому поясу сдвигает часть событий в соседние календарные сутки, из-за чего суммы по дням в двух системах расходятся даже на одинаковых исходных данных.

**Разбор**
- **Как это работает:** календарный день (`DATE`) зависит от часового пояса — событие, случившееся в 23:30 UTC, в часовом поясе UTC+3 уже относится к следующему дню. Если группировать по дате без явного приведения обеих таблиц к одному часовому поясу, границы «дня» в двух источниках будут отличаться.
- **На практике:** перед объединением данных из разных систем важно явно узнать (не предполагать), в каком часовом поясе хранится каждая временная метка, и привести все значения к единому поясу (например, через `AT TIME ZONE` в PostgreSQL) прежде, чем группировать по дате.
- **Частые ошибки:** считают, что раз в базе указан `timestamp`, то часовой пояс «не важен» и сравнение корректно само по себе; расследуют расхождение сумм как ошибку логики запроса, хотя на самом деле проблема — в несогласованных исходных данных.

**Пример / кейс**
```sql
SELECT DATE(event_time AT TIME ZONE 'UTC' AT TIME ZONE 'Europe/Moscow') AS local_day,
       COUNT(*) AS events_cnt
FROM events
GROUP BY 1;
```
Проверка: для события на границе суток (например, `2024-05-01 23:50:00 UTC`) результат `local_day` должен быть `2024-05-02` при пересчёте в московское время — сверить вручную на нескольких примерах.

### 34. [Q-04-01-0034] Что показывает план запроса EXPLAIN и зачем аналитику смотреть на него хотя бы на базовом уровне?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`EXPLAIN` показывает, какой план выполнения СУБД выбрала для запроса — какие таблицы и в каком порядке читаются, используются ли индексы или полное сканирование таблицы — и помогает понять, почему запрос работает медленно, до того как его запустят на полных данных.

**Разбор**
- **Как это работает:** `EXPLAIN` (без `ANALYZE`) строит предполагаемый план на основе статистики таблиц без фактического выполнения запроса, а `EXPLAIN ANALYZE` реально выполняет запрос и добавляет к плану фактическое время и количество обработанных строк на каждом шаге.
- **На практике:** на базовом уровне аналитику достаточно уметь заметить признаки проблемы — например, «Seq Scan» (полное сканирование таблицы) на очень большой таблице там, где ожидался индексный поиск, или то, что оценка числа строк на одном из шагов плана сильно расходится с фактической.
- **Частые ошибки:** запускают `EXPLAIN ANALYZE` на запросе с `INSERT`/`UPDATE`/`DELETE` в проде, не понимая, что `ANALYZE` фактически выполняет запрос (и, соответственно, реально меняет данные), а не только показывает план «в сухую».

**Пример / кейс**
```sql
EXPLAIN SELECT * FROM orders WHERE customer_id = 12345;
```
Если в плане видно «Seq Scan on orders», а таблица на миллионы строк, это сигнал задуматься об индексе на `customer_id`. Проверка: после создания индекса повторный `EXPLAIN` должен показать «Index Scan» вместо «Seq Scan».

### 35. [Q-04-01-0035] Чем FULL JOIN отличается от LEFT JOIN и в каком практическом случае он нужен аналитику?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
`FULL JOIN` сохраняет все строки из обеих таблиц независимо от того, нашлось ли совпадение, заполняя `NULL` там, где пары нет с любой стороны, — это полезно, например, при сверке двух источников данных, когда нужно увидеть записи, которые есть только в одном из них.

**Разбор**
- **Как это работает:** `FULL JOIN` можно представить как объединение результатов `LEFT JOIN` и `RIGHT JOIN` — ни одна строка ни из левой, ни из правой таблицы не теряется, даже если для неё нет пары на другой стороне.
- **На практике:** типичный сценарий — сверка данных из двух систем учёта (например, «заказы в CRM» и «заказы в биллинге»): `FULL JOIN` по идентификатору заказа с последующей проверкой `WHERE a.order_id IS NULL OR b.order_id IS NULL` сразу покажет записи, которые есть только в одной из систем — это именно те случаи, которые нужно расследовать.
- **Частые ошибки:** используют `FULL JOIN`, когда на самом деле достаточно `LEFT JOIN` (то есть интересуют только «потери» с одной конкретной стороны) — это не ошибка по сути, но усложняет запрос без необходимости; забывают, что после `FULL JOIN` оба набора ключевых столбцов (`a.order_id` и `b.order_id`) нужно проверять на `NULL` отдельно, а не как единое поле.

**Пример / кейс**
```sql
SELECT a.order_id AS crm_id, b.order_id AS billing_id
FROM crm_orders a
FULL JOIN billing_orders b ON a.order_id = b.order_id
WHERE a.order_id IS NULL OR b.order_id IS NULL;
```
Результат — заказы, расходящиеся между системами. Проверка: вручную найти один заказ из этого списка в обеих исходных таблицах и убедиться, что он действительно отсутствует в одной из них.

### 36. [Q-04-01-0036] Как получить только строки с максимальной суммой заказа на каждого клиента, используя подзапрос с агрегацией (без оконных функций)?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Junior

**Короткий ответ**
Нужно сначала посчитать максимальную сумму заказа на каждого клиента в отдельном подзапросе (`GROUP BY customer_id`), а затем присоединить исходную таблицу заказов к этому подзапросу по `customer_id` и совпадению суммы с максимумом.

**Разбор**
- **Как это работает:** подзапрос `SELECT customer_id, MAX(amount) AS max_amount FROM orders GROUP BY customer_id` возвращает одну строку на клиента с его максимальной суммой; соединение этого результата с исходной таблицей по `customer_id` и `amount = max_amount` оставляет только те строки заказов, которые действительно равны этому максимуму.
- **На практике:** если несколько заказов одного клиента имеют одинаковую максимальную сумму, такой подход вернёт их все — это нужно явно учитывать и решать, что требуется в задаче: «все заказы с максимальной суммой» или «ровно один, самый ранний/последний из них».
- **Частые ошибки:** пытаются добавить другие столбцы заказа (например, `order_date`) напрямую в `SELECT` рядом с `MAX(amount)` без `GROUP BY` по ним — это либо вызывает ошибку, либо (в некоторых СУБД) возвращает несогласованную комбинацию полей из разных строк одной группы.

**Пример / кейс**
```sql
SELECT o.*
FROM orders o
JOIN (
  SELECT customer_id, MAX(amount) AS max_amount
  FROM orders
  GROUP BY customer_id
) m ON o.customer_id = m.customer_id AND o.amount = m.max_amount;
```
Результат — для каждого клиента одна или несколько строк с максимальной суммой заказа. Проверка: для одного клиента вручную найти максимум среди его заказов и сверить со значением в результате.


### 37. [Q-04-01-0037] Чем ROW_NUMBER(), RANK() и DENSE_RANK() отличаются друг от друга при одинаковых значениях сортировки?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
`ROW_NUMBER()` всегда присваивает уникальные последовательные номера даже при равных значениях, `RANK()` даёт одинаковый ранг «ничьим», но пропускает следующие номера, а `DENSE_RANK()` даёт одинаковый ранг «ничьим» без пропусков в нумерации.

**Разбор**
- **Как это работает:** все три функции работают над окном, заданным `PARTITION BY`/`ORDER BY`. При трёх строках с одинаковым значением на 2-й позиции: `ROW_NUMBER()` даст 1,2,3,4 произвольно (в зависимости от порядка «ничьих», который без дополнительного критерия сортировки недетерминирован); `RANK()` даст 1,2,2,4 (пропускает 3); `DENSE_RANK()` даст 1,2,2,3.
- **На практике:** выбор функции зависит от задачи: для «каждому ряду — свой уникальный номер» (например, для дедупликации или пагинации) нужен `ROW_NUMBER()`; для «официального» рейтинга, где важно показать настоящее место с учётом ничьих (как в спорте), — `RANK()`; для рейтинга без «дырок» в номерах — `DENSE_RANK()`.
- **Частые ошибки:** используют `ROW_NUMBER()` для дедупликации без достаточно детерминированного `ORDER BY` (без вторичного уникального критерия), из-за чего при повторном запуске может удалиться другая строка из пары дублей; путают `RANK()` и `DENSE_RANK()` при объяснении бизнес-пользователю разницы в итоговых номерах мест.

**Пример / кейс**
```sql
SELECT customer_id, amount,
       ROW_NUMBER() OVER (ORDER BY amount DESC) AS rn,
       RANK() OVER (ORDER BY amount DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY amount DESC) AS drnk
FROM orders;
```
Если два заказа имеют одинаковую максимальную сумму, `rnk` у обоих будет 1, у `drnk` — тоже 1, а следующий заказ получит `rnk = 3`, `drnk = 2`. Проверка: количество уникальных значений `rn` должно равняться количеству строк.

### 38. [Q-04-01-0038] Как посчитать накопительную (кумулятивную) сумму выручки по дням с начала периода?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно использовать оконную функцию `SUM(daily_amount) OVER (ORDER BY day)`, которая по умолчанию считает сумму от первой строки окна до текущей, формируя накопительный итог.

**Разбор**
- **Как это работает:** при наличии `ORDER BY` внутри `OVER(...)` без явного указания рамки (`ROWS BETWEEN`) большинство СУБД по умолчанию применяют рамку `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` — то есть суммируют все строки от начала до текущей по порядку сортировки.
- **На практике:** перед накопительной суммой по дням данные обычно сначала агрегируют до одной строки на день (через `GROUP BY` в CTE), а затем оконную функцию применяют уже к агрегированным дневным суммам — иначе при RANGE-рамке строки с одинаковой датой «сольются» в одну точку накопления, что может быть неожиданным.
- **Частые ошибки:** не агрегируют данные до одного дня предварительно и получают кумулятивную сумму на уровне отдельных транзакций, где все транзакции одного дня (из-за RANGE по умолчанию) получают одинаковое накопленное значение — равное сумме за весь день, а не частичной сумме внутри дня; забывают, что без `ORDER BY` в `OVER()` сумма считается по всему окну сразу, то есть это обычный `SUM`, а не накопительный.

**Пример / кейс**
```sql
WITH daily AS (
  SELECT DATE_TRUNC('day', order_date) AS day, SUM(amount) AS daily_amount
  FROM orders
  GROUP BY 1
)
SELECT day, daily_amount,
       SUM(daily_amount) OVER (ORDER BY day) AS cumulative_amount
FROM daily
ORDER BY day;
```
Последняя строка `cumulative_amount` должна совпадать с общей суммой за весь период. Проверка: сравнить это значение с `SELECT SUM(amount) FROM orders`.

### 39. [Q-04-01-0039] Как с помощью LAG посчитать изменение выручки месяц к месяцу в процентах?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно получить значение предыдущего месяца функцией `LAG(revenue) OVER (ORDER BY month)` и вычислить `(revenue - prev_revenue) / prev_revenue * 100`, аккуратно обработав случай, когда предыдущего месяца нет или его выручка равна нулю.

**Разбор**
- **Как это работает:** `LAG(column, n)` возвращает значение этого столбца из строки, которая находится на `n` позиций раньше в заданном порядке окна (по умолчанию `n = 1`); для первой строки окна результат `LAG` — `NULL`, так как «предыдущей» строки не существует.
- **На практике:** перед делением обязательно нужно защититься от деления на ноль или на `NULL` — например, через `NULLIF(prev_revenue, 0)`, иначе запрос либо упадёт с ошибкой деления на ноль, либо (при NULL в знаменателе) просто тихо вернёт `NULL`. Также важно убедиться, что ряд месяцев не содержит пропущенных месяцев — иначе `LAG` «перепрыгнет» через отсутствующий месяц, не заметив разрыва.
- **Частые ошибки:** не проверяют наличие пропущенных периодов в данных (например, если в каком-то месяце не было продаж и строка отсутствует) — тогда `LAG` сравнит не соседние, а произвольно удалённые по времени месяцы, и расчёт % роста будет формально верным, но содержательно обманчивым.

**Пример / кейс**
```sql
WITH monthly AS (
  SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS revenue
  FROM orders
  GROUP BY 1
)
SELECT month, revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS diff,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 1) AS pct_change
FROM monthly
ORDER BY month;
```
Проверка: для второго месяца в выборке вручную вычислить `(revenue2 - revenue1) / revenue1 * 100` и сравнить с `pct_change`.

### 40. [Q-04-01-0040] Как посчитать долю выручки каждого товара от общей выручки его категории, не теряя строк отдельных товаров?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно использовать оконную функцию с `PARTITION BY category`: `SUM(revenue) OVER (PARTITION BY category)` даёт сумму по всей категории в каждой строке товара, после чего легко посчитать долю `revenue / category_total`, не теряя детализацию по товарам.

**Разбор**
- **Как это работает:** `PARTITION BY` делит все строки на независимые группы (аналогично `GROUP BY`), но, в отличие от `GROUP BY`, оконная функция не сворачивает строки в одну — каждая исходная строка сохраняется, и к ней просто «пристёгивается» агрегат по её группе.
- **На практике:** это ключевое отличие оконных функций от обычной агрегации — можно одновременно видеть детальный уровень (товар) и контекст уровня группы (категория) в одной строке, что удобно для отчётов типа «вклад каждого товара в выручку категории».
- **Частые ошибки:** пытаются решить эту задачу через `GROUP BY category` с подзапросом и `JOIN` обратно к товарам — это тоже работает, но требует двух проходов и соединения, тогда как оконная функция решает задачу за один проход и без явного `JOIN`; забывают, что без `PARTITION BY` оконная функция посчитает сумму по всей таблице, а не по категории.

**Пример / кейс**
```sql
SELECT category, product_name, revenue,
       SUM(revenue) OVER (PARTITION BY category) AS category_total,
       ROUND(100.0 * revenue / SUM(revenue) OVER (PARTITION BY category), 1) AS pct_of_category
FROM product_revenue;
```
Сумма `pct_of_category` внутри одной категории должна быть примерно равна 100%. Проверка: `SELECT category, SUM(pct_of_category) FROM (...) GROUP BY category` — для каждой категории около 100.

### 41. [Q-04-01-0041] Чем отличается оконная рамка ROWS BETWEEN 2 PRECEDING AND CURRENT ROW от обычного PARTITION BY без указания рамки, и зачем нужно скользящее среднее?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` ограничивает окно тремя строками (текущей и двумя предыдущими по порядку сортировки) для расчёта, например, скользящего среднего, тогда как без указания рамки при наличии `ORDER BY` по умолчанию используется расширяющееся окно «от начала до текущей строки».

**Разбор**
- **Как это работает:** явная рамка `ROWS BETWEEN n PRECEDING AND CURRENT ROW` задаёт скользящее окно фиксированного размера, которое «едет» вместе с текущей строкой, тогда как без рамки (но с `ORDER BY`) окно растёт с каждой следующей строкой — это принципиально разные вычисления, хотя обе используют одну и ту же функцию, например `AVG`.
- **На практике:** скользящее среднее (например, за последние 7 дней) сглаживает дневные колебания и шум, помогая увидеть тренд, но важно явно договориться о размере окна и о том, что для первых N-1 строк ряда окно будет «неполным» (содержать меньше точек, чем задано), если не предусмотреть это отдельно.
- **Частые ошибки:** путают `ROWS` и `RANGE` — при `RANGE` несколько строк с одинаковым значением сортировки считаются «на одной границе» и могут попасть в окно все сразу, что для скользящего среднего по дням с дублирующимися датами даёт иной результат, чем ожидалось; не проверяют, что в ряду нет пропущенных дат, из-за чего «скользящее среднее за 7 дней» на самом деле может усреднять данные за более длинный календарный период при наличии пропусков.

**Пример / кейс**
```sql
SELECT day, daily_amount,
       AVG(daily_amount) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma_7d
FROM daily_sales
ORDER BY day;
```
Проверка: для 8-й по порядку строки вручную усреднить `daily_amount` этой и 6 предыдущих строк и сравнить с `ma_7d`.

### 42. [Q-04-01-0042] Как с помощью рекурсивного CTE построить полный список дат от начала до конца периода, если отдельной календарной таблицы нет?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно написать рекурсивный `WITH RECURSIVE`, где «якорная» часть задаёт стартовую дату, а рекурсивная часть добавляет по одному дню, пока не достигнута конечная дата; в BigQuery для той же задачи проще использовать встроенную функцию `GENERATE_DATE_ARRAY`.

**Разбор**
- **Как это работает:** рекурсивный CTE состоит из двух частей, объединённых `UNION ALL`: «базовый случай» (одна начальная строка) и «рекурсивный шаг», который ссылается на сам CTE и добавляет следующий день; СУБД выполняет рекурсивный шаг многократно, пока условие в `WHERE` не остановит рекурсию.
- **На практике:** сгенерированный список дат обычно используют как «скелет» для `LEFT JOIN` к фактическим данным, чтобы явно увидеть дни без событий как 0, а не как отсутствующие строки — это важно для корректных графиков временных рядов и расчёта средних по дням.
- **Частые ошибки:** не ограничивают глубину рекурсии явным условием или забывают увеличить `max_recursion` (в некоторых СУБД рекурсия по умолчанию ограничена небольшим числом шагов, например 100 в PostgreSQL без `OPTION`), из-за чего генерация длинного диапазона дат обрывается или требует дополнительной настройки.

**Пример / кейс**
```sql
WITH RECURSIVE date_series AS (
  SELECT DATE '2024-01-01' AS day
  UNION ALL
  SELECT day + INTERVAL '1 day'
  FROM date_series
  WHERE day + INTERVAL '1 day' <= DATE '2024-01-31'
)
SELECT day FROM date_series ORDER BY day;
```
Результат — ровно 31 строка. Проверка: `SELECT COUNT(*) FROM date_series` должен совпасть с числом дней между начальной и конечной датой включительно.

### 43. [Q-04-01-0043] Как использовать несколько последовательных CTE, чтобы сначала очистить данные, а затем посчитать на них метрику?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно объявить несколько CTE через запятую в одном блоке `WITH`, где каждый следующий CTE может ссылаться на предыдущие, формируя цепочку шагов «очистка → дедупликация → агрегация → финальный отбор».

**Разбор**
- **Как это работает:** в блоке `WITH cte1 AS (...), cte2 AS (SELECT ... FROM cte1 ...), cte3 AS (...)` каждый следующий CTE может использовать результат предыдущего по имени, как обычную таблицу; основной `SELECT` в конце обычно обращается к последнему CTE.
- **На практике:** такой подход делает сложную логику читаемой и тестируемой по шагам — можно временно заменить финальный `SELECT` на `SELECT * FROM cte2` и проверить промежуточный результат, не переписывая весь запрос. Это особенно полезно, когда данные перед агрегацией нужно почистить (убрать дубликаты, отфильтровать тестовые записи, привести типы).
- **Частые ошибки:** нагромождают слишком много логики в одном CTE вместо разделения на понятные шаги, из-за чего сложно отследить, на каком этапе появилась ошибка; забывают, что в большинстве диалектов (кроме рекурсивных CTE) CTE не может ссылаться на CTE, объявленный после него — порядок объявления важен.

**Пример / кейс**
```sql
WITH cleaned_orders AS (
  SELECT * FROM orders WHERE amount > 0 AND customer_id IS NOT NULL
),
deduped_orders AS (
  SELECT DISTINCT * FROM cleaned_orders
),
monthly_revenue AS (
  SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS revenue
  FROM deduped_orders
  GROUP BY 1
)
SELECT * FROM monthly_revenue ORDER BY month;
```
Проверка: временно выполнить `SELECT COUNT(*) FROM cleaned_orders` и `SELECT COUNT(*) FROM deduped_orders`, чтобы увидеть, сколько строк отсеялось на каждом шаге.

### 44. [Q-04-01-0044] Как написать запрос для когортного анализа удержания пользователей по месяцу первой покупки?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно для каждого клиента определить месяц первой покупки (когорту), затем для каждой его покупки посчитать «номер месяца жизни» относительно когорты, и сгруппировать по когорте и номеру месяца, посчитав количество уникальных активных клиентов.

**Разбор**
- **Как это работает:** шаг 1 — CTE с `MIN(order_date)` по клиенту для определения когорты; шаг 2 — присоединение этой когорты к каждой покупке и вычисление разницы в месяцах между покупкой и датой когорты (например, через `DATE_PART` или `DATE_DIFF` в зависимости от диалекта); шаг 3 — `GROUP BY cohort_month, month_number` с `COUNT(DISTINCT customer_id)`.
- **На практике:** удержание обычно представляют как таблицу «когорта × номер месяца» с процентом от исходного размера когорты (`месяц 0` = 100%). Важно явно решить, что считается «активностью» — любая покупка, определённое действие, вход в приложение — и зафиксировать это определение, так как оно сильно влияет на итоговые цифры.
- **Частые ошибки:** считают просто количество покупок, а не количество уникальных клиентов в месяце, что задваивает удержание для клиентов с несколькими покупками в одном месяце; не учитывают, что последние когорты (например, когорта текущего месяца) ещё физически не могли «дожить» до месяца 3, 6 и т.д. — их нужно явно исключать из сравнения, а не трактовать как «0% удержания».

**Пример / кейс**
```sql
WITH cohorts AS (
  SELECT customer_id, DATE_TRUNC('month', MIN(order_date)) AS cohort_month
  FROM orders GROUP BY customer_id
),
activity AS (
  SELECT o.customer_id, c.cohort_month,
         DATE_PART('year', o.order_date) * 12 + DATE_PART('month', o.order_date)
         - (DATE_PART('year', c.cohort_month) * 12 + DATE_PART('month', c.cohort_month)) AS month_number
  FROM orders o JOIN cohorts c ON o.customer_id = c.customer_id
)
SELECT cohort_month, month_number, COUNT(DISTINCT customer_id) AS active_customers
FROM activity
GROUP BY cohort_month, month_number
ORDER BY cohort_month, month_number;
```
Проверка: для `month_number = 0` количество активных клиентов должно равняться полному размеру когорты.

### 45. [Q-04-01-0045] Как эффективно удалить дубликаты строк, оставив только одну (самую последнюю) версию по уникальному бизнес-ключу?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно пронумеровать дубликаты внутри каждой группы бизнес-ключа функцией `ROW_NUMBER() OVER (PARTITION BY business_key ORDER BY updated_at DESC)` и оставить (или удалить все, кроме) строки с номером 1.

**Разбор**
- **Как это работает:** `PARTITION BY business_key` делит строки на группы дублей, `ORDER BY updated_at DESC` внутри каждой группы ставит самую свежую запись первой, и `ROW_NUMBER()` присваивает ей номер 1; все остальные строки группы получают номера 2, 3 и так далее и считаются «лишними» дублями.
- **На практике:** в PostgreSQL для реального удаления обычно оборачивают это в CTE и используют `DELETE ... WHERE id IN (SELECT id FROM ranked WHERE rn > 1)`; важно сначала выполнить только `SELECT`, чтобы визуально проверить, какие строки будут удалены, прежде чем запускать `DELETE`. В ClickHouse для таблиц с движком `ReplacingMergeTree` похожая задача решается через `FINAL` или `OPTIMIZE ... DEDUPLICATE`, что работает принципиально иначе.
- **Частые ошибки:** сортируют без вторичного детерминированного критерия при равенстве `updated_at` у нескольких строк — тогда «какая строка окажется первой» не гарантировано и может отличаться между запусками; забывают, что `DELETE` нужно явно ограничить тем же набором строк, что и проверочный `SELECT`, иначе можно случайно удалить больше данных.

**Пример / кейс**
```sql
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY business_key ORDER BY updated_at DESC, id DESC) AS rn
  FROM raw_table
)
SELECT * FROM ranked WHERE rn = 1;
```
Проверка: количество строк с `rn = 1` должно равняться `COUNT(DISTINCT business_key)` в исходной таблице.

### 46. [Q-04-01-0046] Как посчитать медиану суммы заказа по каждому региону с помощью оконной или агрегатной функции percentile?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
В PostgreSQL можно использовать `PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY amount)` как агрегатную функцию с `GROUP BY region`; в BigQuery — аналог `PERCENTILE_CONT(amount, 0.5) OVER (PARTITION BY region)` как оконную функцию, в ClickHouse — `quantile(0.5)(amount)`.

**Разбор**
- **Как это работает:** медиана — это 50-й перцентиль, значение, относительно которого ровно половина наблюдений меньше и половина больше (с интерполяцией для `PERCENTILE_CONT` при чётном количестве наблюдений). В отличие от среднего, медиана устойчива к выбросам — один аномально большой заказ не сдвинет медиану так, как сдвинет среднее.
- **На практике:** медиану стоит приводить рядом со средним, когда в данных есть выбросы (крупные корпоративные заказы на фоне розничных) — иначе среднее может создать ложное впечатление о «типичном» заказе. Разные СУБД по-разному называют и реализуют функции перцентиля, и важно проверить, какая именно интерполяция используется (`PERCENTILE_CONT` интерполирует, `PERCENTILE_DISC` берёт реальное значение из данных).
- **Частые ошибки:** путают медиану со средним или считают, что они должны быть близки — при сильно скошенном распределении (например, доходы, суммы заказов) они могут заметно отличаться, и это нормально, а не признак ошибки в расчёте.

**Пример / кейс**
```sql
SELECT region,
       PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY amount) AS median_amount,
       AVG(amount) AS avg_amount
FROM orders
GROUP BY region;
```
Проверка: для небольшого региона с нечётным числом заказов вручную отсортировать суммы и взять среднее значение — оно должно совпасть с `median_amount`.

### 47. [Q-04-01-0047] Почему запрос с SELECT * и несколькими JOIN на таблице в сотни миллионов строк работает медленно, и какие простые шаги могут это ускорить?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Основные причины — чтение ненужных столбцов и строк, отсутствие или неиспользование индексов на ключах соединения и фильтрации, а также джойны до фильтрации; базовые шаги — выбирать только нужные столбцы, фильтровать как можно раньше, проверять индексы на столбцах JOIN/WHERE и смотреть план выполнения через EXPLAIN.

**Разбор**
- **Как это работает:** `SELECT *` заставляет СУБД читать и передавать все столбцы, включая возможно крупные текстовые/JSON поля, которые не нужны для анализа — это увеличивает объём I/O и сетевого трафика. Если JOIN выполняется на столбце без индекса, СУБД может быть вынуждена делать полное сканирование одной из таблиц для каждой строки другой (вложенный цикл), что на больших объёмах крайне медленно.
- **На практике:** полезная последовательность диагностики — (1) посмотреть `EXPLAIN ANALYZE` и найти самый дорогой шаг по времени/числу строк; (2) проверить, есть ли индекс на столбцах `JOIN`/`WHERE`; (3) перенести фильтры как можно раньше (в подзапрос/CTE до JOIN), чтобы уменьшить объём данных, участвующих в соединении; (4) убрать ненужные столбцы из `SELECT`.
- **Частые ошибки:** добавляют индексы «на всё подряд» без анализа реальных запросов — это ускоряет чтение, но замедляет запись и расходует место; оптимизируют один медленный запрос, не проверив, что изменения не ухудшили другие частые запросы к той же таблице.

**Пример / кейс**
```sql
EXPLAIN ANALYZE
SELECT o.order_id, c.region
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE o.order_date >= '2024-01-01';
```
Проверка: сравнить время выполнения (`Execution Time` в выводе `EXPLAIN ANALYZE`) до и после добавления индекса на `orders.customer_id` и `orders.order_date`.

### 48. [Q-04-01-0048] Как читать EXPLAIN ANALYZE и понять, где именно «узкое место» в запросе с несколькими соединениями?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно читать план выполнения «снизу вверх» (от самых глубоких узлов к верхним), сравнивать оценку числа строк (`rows`) с фактическим числом (`actual rows`) на каждом шаге и искать узел с наибольшим фактическим временем — это и есть основная точка замедления.

**Разбор**
- **Как это работает:** PostgreSQL выполняет план как дерево операций (сканирование таблиц, соединения, сортировки, агрегации); каждый узел в `EXPLAIN ANALYZE` показывает `actual time` (включает время всех дочерних узлов) и `actual rows`. Большое расхождение между оценкой (`rows=...` в плане) и фактическим числом строк часто говорит об устаревшей статистике таблицы.
- **На практике:** типичные «красные флаги» — `Seq Scan` на крупной таблице там, где ожидался индексный доступ, `Nested Loop` с большим количеством итераций по внешней таблице без индекса на внутренней, а также отдельный заметный по времени узел `Sort` или `Hash`, который может говорить о нехватке `work_mem` и уходе сортировки на диск.
- **Частые ошибки:** оценивают запрос по суммарному времени выполнения всего плана, не разбирая его по узлам, и пытаются «оптимизировать всё подряд»; не обновляют статистику таблицы (`ANALYZE table_name`) перед диагностикой, из-за чего оптимизатор строит план на основе неактуальных данных о распределении значений.

**Пример / кейс**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.region, SUM(o.amount)
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
GROUP BY c.region;
```
Если узел `Hash Join` показывает `actual time=5000..5200` на фоне общего времени запроса 5300 мс — именно это соединение является основным узким местом. Проверка: после добавления индекса или увеличения `work_mem` повторно снять план и сравнить время этого узла.


### 49. [Q-04-01-0049] Почему AVG(amount) по заказам может не совпадать со "средним чеком", если часть заказов имеет NULL в amount из-за ошибки интеграции?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
`AVG(amount)` игнорирует строки с `NULL` и делит сумму только на количество заказов с заполненной суммой, поэтому при наличии «битых» заказов с `NULL` вместо суммы средний чек окажется завышен или занижен по сравнению с ожиданием «сумма всех заказов / общее число заказов».

**Разбор**
- **Как это работает:** агрегатные функции в SQL по умолчанию пропускают `NULL`-значения при вычислении; то есть `AVG` фактически считает `SUM(ненулевых значений) / COUNT(ненулевых значений)`, а не делит на общее количество строк в группе (`COUNT(*)`).
- **На практике:** перед доверием к `AVG` важно явно проверить, сколько строк имеют `NULL` в этом поле (`COUNT(*) - COUNT(amount)`), и понять причину — технический сбой интеграции, легитимный «пустой» заказ (например, отменённый до оплаты) или что-то ещё. Если `NULL` на самом деле должен означать 0, нужно явно привести это через `COALESCE(amount, 0)` до агрегации, а не полагаться на поведение `AVG` по умолчанию.
- **Частые ошибки:** интерпретируют высокий `AVG(amount)` как рост среднего чека, когда на самом деле просто увеличилась доля заказов с `NULL` (например, из-за сбоя одного из источников данных), которые `AVG` просто не учитывает, искажая знаменатель.

**Пример / кейс**
```sql
SELECT COUNT(*) AS total_orders,
       COUNT(amount) AS orders_with_amount,
       AVG(amount) AS avg_amount,
       SUM(amount) / COUNT(*) AS avg_amount_strict
FROM orders;
```
Если `total_orders = 1000`, `orders_with_amount = 900`, две версии среднего будут отличаться. Проверка: расследовать 100 заказов с `NULL` через выборку `SELECT * FROM orders WHERE amount IS NULL LIMIT 20` и понять их природу.

### 50. [Q-04-01-0050] Как построить полный ряд дат по дням для графика, даже если в некоторые дни не было ни одной продажи?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно сгенерировать полный список дат (через `generate_series` в PostgreSQL или аналог в другом диалекте) и сделать `LEFT JOIN` к агрегированным по дням продажам, заменив `NULL` в сумме на 0 через `COALESCE`.

**Разбор**
- **Как это работает:** `generate_series(start_date, end_date, interval '1 day')` в PostgreSQL возвращает по одной строке на каждый день периода; `LEFT JOIN` сохраняет все эти даты независимо от того, нашлась ли для них продажа, и `COALESCE(SUM(amount), 0)` явно превращает отсутствие продаж в 0, а не в пропущенную точку графика.
- **На практике:** без этого шага график временного ряда просто «перескочит» через дни без продаж, что может визуально искажать тренд (линия на графике соединит соседние по данным, но не по времени точки) и затруднить расчёт корректных средних за период, включающих нулевые дни.
- **Частые ошибки:** строят график прямо по результату `GROUP BY order_date` без досоздания пропущенных дат, из-за чего дни без продаж просто отсутствуют на графике вместо явного нуля — это особенно критично для низкочастотных событий (например, продажи редкого товара).

**Пример / кейс**
```sql
WITH days AS (
  SELECT generate_series('2024-01-01'::date, '2024-01-31'::date, interval '1 day')::date AS day
)
SELECT d.day, COALESCE(SUM(o.amount), 0) AS daily_amount
FROM days d
LEFT JOIN orders o ON o.order_date = d.day
GROUP BY d.day
ORDER BY d.day;
```
Результат — ровно 31 строка, включая дни с `daily_amount = 0`. Проверка: `SELECT COUNT(*)` должен быть 31 независимо от того, были ли продажи каждый день.

### 51. [Q-04-01-0051] Как рассчитать SRM-проверку (sample ratio mismatch) по данным A/B-теста прямо в SQL?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно посчитать количество пользователей в каждой группе эксперимента через `GROUP BY variant` и сравнить фактическое соотношение с ожидаемым (например, 50/50) — SQL даёт только сырые числа, а формальную проверку (например, хи-квадрат) обычно делают уже вне SQL, хотя сами наблюдаемые и ожидаемые частоты можно посчитать запросом.

**Разбор**
- **Как это работает:** `SELECT variant, COUNT(DISTINCT user_id) FROM experiment_assignments GROUP BY variant` даёт фактическое число пользователей в каждой ветке; дальше это сравнивают с ожидаемым распределением (обычно пропорциональным доле трафика, заданной в конфигурации эксперимента) — большое отклонение сигнализирует о проблеме в рандомизации или в логировании, а не о реальном эффекте теста.
- **На практике:** SRM нужно проверять до анализа основной метрики — если группы разъехались по размеру сильнее, чем можно объяснить случайностью, доверять результатам теста в целом нельзя, независимо от того, насколько «красивой» выглядит разница по конверсии. Причины SRM часто лежат не в статистике, а в технических деталях: разное время старта логирования для групп, фильтры ботов, которые по-разному задевают группы, или ошибки в самом механизме рандомизации.
- **Частые ошибки:** смотрят только на итоговые пропорции («49.8% vs 50.2% — это нормально») без формальной проверки значимости отклонения и без учёта размера выборки — при очень больших выборках даже небольшое на вид отклонение может быть статистически значимым и указывать на реальную проблему.

**Пример / кейс**
```sql
SELECT variant, COUNT(DISTINCT user_id) AS users_cnt
FROM experiment_assignments
WHERE experiment_id = 'checkout_redesign'
GROUP BY variant;
```
Если ожидалось 50/50, а получили 51200 и 48700 — разницу стоит прогнать через тест на соответствие пропорций вне SQL, а не оценивать «на глаз». Проверка: пересчитать по дням старта эксперимента отдельно — не появилась ли проблема после конкретного релиза.

### 52. [Q-04-01-0052] Как посчитать конверсию по вариантам A/B-теста и сразу увидеть численность каждой группы в одном запросе?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно соединить таблицу назначений в эксперимент с таблицей целевых событий через `LEFT JOIN`, сгруппировать по варианту и посчитать и общее число пользователей, и число совершивших целевое действие, чтобы конверсия (`converted / total`) и размер выборки были видны вместе.

**Разбор**
- **Как это работает:** `LEFT JOIN` от назначений к событиям гарантирует, что пользователи без целевого действия тоже учтутся (с `NULL` в поле события), и `COUNT(DISTINCT CASE WHEN event_user_id IS NOT NULL THEN assignment_user_id END)` корректно посчитает только тех, у кого нашлось событие, деля на общее `COUNT(DISTINCT assignment_user_id)`.
- **На практике:** важно всегда показывать рядом с конверсией размер выборки каждой группы — без этого «разница в конверсии 2 п.п.» невозможно правильно интерпретировать: на малой выборке это может быть шумом, на большой — значимым эффектом. SQL может посчитать сырые цифры, но решение о статистической значимости обычно требует дополнительного теста (например, z-теста для пропорций) за пределами SQL.
- **Частые ошибки:** используют `INNER JOIN` вместо `LEFT JOIN` между назначением и событием, из-за чего пользователи без события выпадают из знаменателя, а не остаются там с нулевым числителем — это искусственно завышает конверсию для обеих групп.

**Пример / кейс**
```sql
SELECT a.variant,
       COUNT(DISTINCT a.user_id) AS users_cnt,
       COUNT(DISTINCT e.user_id) AS converted_cnt,
       ROUND(100.0 * COUNT(DISTINCT e.user_id) / COUNT(DISTINCT a.user_id), 2) AS conversion_pct
FROM experiment_assignments a
LEFT JOIN target_events e ON e.user_id = a.user_id AND e.event_time >= a.assigned_at
GROUP BY a.variant;
```
Проверка: `users_cnt` по группам должен быть близок к ожидаемому размеру выборки, а `converted_cnt` не может превышать `users_cnt`.

### 53. [Q-04-01-0053] Как с помощью оконной функции определить первый источник трафика (first touch), приведший каждого пользователя к покупке?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно пронумеровать все касания (визиты/клики) каждого пользователя функцией `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY touch_time)` и оставить только строки с номером 1 — это и будет первое касание (first touch) для атрибуции.

**Разбор**
- **Как это работает:** `PARTITION BY user_id` группирует все касания одного пользователя, `ORDER BY touch_time` сортирует их по времени внутри группы, и `ROW_NUMBER() = 1` однозначно выбирает самое раннее касание, даже если у пользователя их были десятки.
- **На практике:** first-touch — одна из множества моделей атрибуции (есть также last-touch, линейная, с затухающим весом и т.д.), и выбор модели — не технический, а методологический вопрос: разные модели по-разному распределяют «вклад» каждого канала и могут давать очень разные выводы о том, какой канал эффективнее. Перед тем как использовать first-touch, стоит явно обозначить, что это осознанный выбор модели, а не единственно верный способ атрибуции.
- **Частые ошибки:** при равных `touch_time` (например, два события залогированы в одну и ту же секунду) порядок между ними без дополнительного критерия сортировки не детерминирован — это может давать нестабильные результаты «первого касания» при повторных запусках; путают атрибуцию по первому касанию к покупке с первым касанием вообще за всю историю пользователя, если период анализа не ограничен явно.

**Пример / кейс**
```sql
WITH ranked AS (
  SELECT user_id, channel, touch_time,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY touch_time) AS rn
  FROM touchpoints
)
SELECT channel, COUNT(DISTINCT user_id) AS users_cnt
FROM ranked
WHERE rn = 1
GROUP BY channel;
```
Проверка: сумма `users_cnt` по всем каналам должна равняться общему числу уникальных пользователей в `touchpoints`.

### 54. [Q-04-01-0054] Как построить SQL-запрос для медленно меняющегося измерения (SCD Type 2), чтобы получить «актуальный на дату события» статус клиента?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно присоединить таблицу фактов к таблице SCD2 (с полями `valid_from`/`valid_to`) по условию, что дата события попадает в интервал действия версии записи: `fact.event_date BETWEEN scd.valid_from AND scd.valid_to`.

**Разбор**
- **Как это работает:** SCD Type 2 хранит историю изменений атрибута как несколько строк на один бизнес-объект, каждая с периодом действия (`valid_from`, `valid_to`, где `valid_to` может быть `NULL` или датой в будущем для текущей версии). Соединение по интервалу даёт именно ту версию атрибута, которая была актуальна в момент события, а не текущую версию на сегодня.
- **На практике:** частая ошибка в компаниях без SCD2 — соединение факта с «текущим» измерением (например, текущий регион клиента), что искажает исторические отчёты: если клиент переехал из региона A в регион B, все его прошлые заказы в отчёте задним числом «переезжают» в регион B, хотя фактически были сделаны из региона A.
- **Частые ошибки:** забывают обработать открытый интервал (`valid_to IS NULL` для текущей активной версии) отдельным условием (`OR scd.valid_to IS NULL`), из-за чего события после последнего обновления записи не находят подходящую версию и теряются при `INNER JOIN`.

**Пример / кейс**
```sql
SELECT f.order_id, f.event_date, scd.region
FROM orders f
JOIN customer_scd2 scd
  ON scd.customer_id = f.customer_id
  AND f.event_date >= scd.valid_from
  AND (f.event_date < scd.valid_to OR scd.valid_to IS NULL);
```
Проверка: для клиента, сменившего регион, заказы до даты смены должны показывать старый регион, а после — новый.

### 55. [Q-04-01-0055] Как с помощью GROUPING SETS (или ROLLUP) получить в одном запросе и детальные суммы по регион+категория, и подытоги по региону, и общий итог?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно использовать `GROUP BY ROLLUP(region, category)` (или явный `GROUPING SETS ((region, category), (region), ())`), который за один проход выдаёт и детальные группы, и промежуточные подытоги, и общий итог, помечая «свёрнутые» измерения значением `NULL`.

**Разбор**
- **Как это работает:** `ROLLUP(a, b)` строит иерархию подытогов: сначала группы по `(a, b)`, затем по `(a)` с агрегацией по всем `b`, затем общий итог без разбивки вообще — причём на местах «свёрнутых» столбцов в результате появляется `NULL`. `GROUPING SETS` даёт более гибкий контроль, позволяя явно указать произвольный набор нужных комбинаций группировки, не ограничиваясь строгой иерархией.
- **На практике:** такой подход заменяет несколько отдельных запросов (детальный + подытог по региону + общий итог) одним, что удобно для построения сводных таблиц в отчётах, но требует аккуратной функции `GROUPING()` для различения «настоящего» `NULL` в данных от `NULL`, означающего «эта строка — подытог».
- **Частые ошибки:** путают строки-подытоги (с `NULL` от `ROLLUP`) со строками, где `region` или `category` изначально были `NULL` в данных — без `GROUPING(region)` эти два случая неразличимы в результате, что может привести к неверной интерпретации итоговой таблицы.

**Пример / кейс**
```sql
SELECT region, category, SUM(amount) AS total_amount,
       GROUPING(region) AS is_region_subtotal,
       GROUPING(category) AS is_category_subtotal
FROM sales
GROUP BY ROLLUP(region, category);
```
Проверка: строка с `GROUPING(region) = 1 AND GROUPING(category) = 1` — это общий итог, его `total_amount` должен равняться `SELECT SUM(amount) FROM sales`.

### 56. [Q-04-01-0056] Дашборд показывает выручку за март на 8% ниже, чем отчёт из исходной системы. С чего начать расследование на уровне SQL?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно сравнить определения метрики и границы фильтров в обоих местах (период, статусы заказов, включены ли возвраты/отмены, часовой пояс), а затем по шагам сузить расхождение через разбивку по дням/статусам/источникам, а не сразу искать ошибку в коде дашборда.

**Разбор**
- **Как это работает:** расхождение в 8% редко означает «дашборд врёт» — чаще это разные правила агрегации: например, дашборд может фильтровать `status != 'cancelled'`, а отчёт источника считает все заказы; или дашборд использует `order_date`, а отчёт — `payment_date`; или часовой пояс границы месяца отличается (см. вопрос про UTC).
- **На практике:** эффективный порядок проверки: (1) сравнить фильтры WHERE/статусы в обоих запросах построчно; (2) разбить расхождение по дням — если оно сосредоточено у границ месяца, это сигнал про часовой пояс или про дату отсечки; (3) разбить по статусу заказа и источнику — если расхождение сосредоточено в одной категории, искать там; (4) сверить итоговую сумму на уровне нескольких конкретных order_id вручную.
- **Частые ошибки:** сразу предполагают ошибку в формуле дашборда и переписывают его логику без проверки, что определения метрики в двух местах изначально разные; расследуют на агрегированном уровне, не спускаясь до конкретных строк, из-за чего причина остаётся гипотезой, а не подтверждённым фактом.

**Пример / кейс**
```sql
SELECT DATE_TRUNC('day', order_date) AS day, status,
       SUM(amount) AS dashboard_logic,
       SUM(CASE WHEN status != 'cancelled' THEN amount ELSE 0 END) AS source_logic
FROM orders
WHERE order_date >= '2024-03-01' AND order_date < '2024-04-01'
GROUP BY 1, 2
ORDER BY 1;
```
Проверка: если разница в 8% сосредоточена в строках со статусом `cancelled`, причина найдена — это вопрос определения метрики, а не технической ошибки.

### 57. [Q-04-01-0057] В ClickHouse таблица на движке ReplacingMergeTree показывает задвоенные строки при обычном SELECT. Как корректно посчитать метрику, учитывая эту особенность?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно либо использовать модификатор `FINAL` в запросе (`SELECT ... FROM table FINAL`), который принудительно схлопывает дубликаты по ключу сортировки на момент чтения, либо явно дедуплицировать через `ROW_NUMBER()`-подобную логику (`argMax`/`LIMIT 1 BY` в ClickHouse) без `FINAL`, если производительность важнее.

**Разбор**
- **Как это работает:** `ReplacingMergeTree` асинхронно «склеивает» строки с одинаковым ключом сортировки в фоновых слияниях партиций, оставляя версию с наибольшим значением указанного столбца версии; до завершения слияния в таблице физически могут существовать несколько версий одной логической записи, и обычный `SELECT` без `FINAL` увидит их все.
- **На практике:** `FINAL` даёт корректный результат, но может быть существенно медленнее на больших таблицах, так как требует дополнительной работы по слиянию «на лету» во время запроса. Альтернатива — агрегировать с `LIMIT 1 BY id ORDER BY version DESC` или использовать `argMax(column, version)` в `GROUP BY id`, что часто быстрее, но требует более сложного запроса.
- **Частые ошибки:** считают метрики (например, `COUNT(*)`, `SUM`) прямо по таблице `ReplacingMergeTree` без `FINAL` и без ручной дедупликации, получая задвоенные/утроенные значения, которые на первый взгляд выглядят правдоподобно, но фактически неверны.

**Пример / кейс**
```sql
SELECT id, argMax(status, version) AS current_status, argMax(amount, version) AS current_amount
FROM orders_replacing
GROUP BY id;
```
Проверка: сравнить количество строк результата с ожидаемым количеством уникальных `id`, а также сравнить агрегат с результатом `SELECT ... FROM orders_replacing FINAL` на небольшой выборке.

### 58. [Q-04-01-0058] В BigQuery запрос по большой таблице событий стоит дорого в выставленных счетах. Какие изменения в структуре запроса/таблицы снижают стоимость без потери нужной детализации?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
В BigQuery стоимость запроса обычно зависит от объёма прочитанных данных, поэтому главные рычаги — партиционирование таблицы по дате и фильтрация именно по партиционирующему столбцу, кластеризация по часто используемым столбцам фильтра, а также явный выбор нужных столбцов вместо `SELECT *`.

**Разбор**
- **Как это работает:** BigQuery хранит данные колоночно и по умолчанию тарифицирует запрос по объёму прочитанных байт (в модели on-demand); партиционирование по дате позволяет движку физически пропускать партиции, не попадающие под фильтр `WHERE event_date BETWEEN ...`, а кластеризация внутри партиции ускоряет и дешевит фильтрацию по дополнительным столбцам (например, `user_id`, `event_type`).
- **На практике:** перед запуском дорогого запроса стоит использовать режим предварительной оценки (`dry run` / предпросмотр объёма обрабатываемых байт в интерфейсе), чтобы увидеть стоимость до фактического выполнения. Выбор конкретных столбцов вместо `SELECT *` в колоночном хранилище особенно важен — ненужные столбцы вообще не читаются с диска, в отличие от строкового хранения.
- **Частые ошибки:** фильтруют по дате через выражение, скрывающее партиционирующий столбец (например, `CAST(event_timestamp AS DATE) = '2024-03-01'` вместо прямого сравнения с партиционирующим полем), из-за чего движок не может применить partition pruning и читает все партиции целиком, несмотря на внешне «правильный» фильтр.

**Пример / кейс**
```sql
SELECT user_id, event_type
FROM `project.dataset.events`
WHERE event_date BETWEEN '2024-03-01' AND '2024-03-31'
  AND event_type = 'purchase';
```
Проверка: сравнить оценку обрабатываемого объёма (через dry run) для этого запроса и для его варианта без фильтра по `event_date` на полную таблицу — разница должна быть многократной при партиционировании по `event_date`.

### 59. [Q-04-01-0059] Как решить задачу sessionization — сгруппировать события пользователя в сессии, если между событиями прошло больше 30 минут?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно с помощью `LAG` посчитать разницу во времени с предыдущим событием того же пользователя, отметить начало новой сессии там, где разница больше 30 минут, а затем накопительной суммой этих отметок (через `SUM(...) OVER`) получить номер сессии для каждого события — это классический паттерн «gaps and islands».

**Разбор**
- **Как это работает:** на первом шаге `LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time)` даёт время предыдущего события; на втором шаге условие `event_time - prev_event_time > interval '30 minutes'` (или `prev_event_time IS NULL` для самого первого события) помечается как `1` — начало новой сессии, иначе `0`; на третьем шаге `SUM(is_new_session) OVER (PARTITION BY user_id ORDER BY event_time)` превращает эти отметки в растущий номер сессии.
- **На практике:** порог в 30 минут — это условность, принятая во многих продуктовых аналитических системах по умолчанию, но не универсальный стандарт; для конкретного продукта имеет смысл подбирать порог на основе распределения интервалов между событиями, а не слепо копировать общепринятое число.
- **Частые ошибки:** забывают учесть первое событие пользователя (где `LAG` даёт `NULL`) как начало новой сессии; не разбивают расчёт на отдельные CTE-шаги, пытаясь сделать всё в одном выражении, из-за чего получают сложный для проверки и отладки запрос.

**Пример / кейс**
```sql
WITH gaps AS (
  SELECT user_id, event_time,
         CASE WHEN event_time - LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time)
                   > INTERVAL '30 minutes'
              OR LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time) IS NULL
              THEN 1 ELSE 0 END AS is_new_session
  FROM events
)
SELECT user_id, event_time,
       SUM(is_new_session) OVER (PARTITION BY user_id ORDER BY event_time) AS session_id
FROM gaps;
```
Проверка: для пользователя с известной последовательностью событий вручную посчитать ожидаемое число сессий и сравнить с `MAX(session_id)`.

### 60. [Q-04-01-0060] JOIN таблицы заказов с таблицей позиций заказа (order_items) неожиданно увеличил сумму выручки в отчёте в несколько раз. Что произошло и как это исправить?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Скорее всего произошёл «fan-out» — соединение таблицы заказов (одна строка на заказ) с таблицей позиций (несколько строк на заказ) размножило каждую строку заказа на число позиций в нём, и последующий `SUM(orders.total_amount)` просуммировал одно и то же значение несколько раз.

**Разбор**
- **Как это работает:** `JOIN` по своей природе образует по одной строке результата на каждую пару совпавших строк с обеих сторон; если на один `order_id` в `order_items` приходится 3 строки, то после `JOIN` поле `orders.total_amount` окажется повторено 3 раза — и `SUM` по нему будет втрое больше реального.
- **На практике:** правильный способ зависит от задачи: если нужна сумма заказов — считать `SUM(DISTINCT ...)` небезопасно (может отфильтровать легитимные совпадающие суммы у разных заказов), поэтому лучше либо агрегировать `order_items` до одной строки на заказ заранее (в CTE), либо считать сумму `orders.total_amount` из отдельного запроса без JOIN к позициям, а детализацию по товарам получать отдельно.
- **Частые ошибки:** не проверяют соотношение «один-к-одному» или «один-к-многим» перед JOIN (см. вопрос про проверку уникальности ключа) и обнаруживают fan-out только постфактум, когда итоговая цифра выглядит подозрительно большой.

**Пример / кейс**
```sql
-- Неверно: total_amount заказа задваивается на каждую позицию
SELECT SUM(o.total_amount) FROM orders o JOIN order_items i ON i.order_id = o.order_id;

-- Верно: считаем сумму заказов без джойна к позициям
SELECT SUM(total_amount) FROM orders;
```
Проверка: сравнить оба результата — если первый кратно больше второго, это явный признак fan-out, кратность примерно равна среднему числу позиций на заказ.


### 61. [Q-04-01-0061] Как посчитать процентное изменение выручки год к году с учётом сезонности, сравнивая не соседние месяцы, а тот же месяц прошлого года?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно использовать `LAG(revenue, 12) OVER (ORDER BY month)` вместо `LAG(revenue, 1, ...)`, чтобы сравнивать каждый месяц не с предыдущим, а с тем же месяцем год назад — это сравнение год-к-году (YoY) корректно учитывает сезонность.

**Разбор**
- **Как это работает:** параметр `n` в `LAG(column, n)` задаёт, на сколько строк назад по заданному порядку смотреть; если ряд строго помесячный без пропусков, `n = 12` сдвигает на 12 месяцев назад, то есть на тот же календарный месяц предыдущего года.
- **На практике:** сравнение месяц-к-месяцу (MoM) часто вводит в заблуждение для сезонных продуктов (например, продажи ёлочных игрушек в январе логично падают относительно декабря — это не признак проблем с продуктом), поэтому для таких бизнесов сравнение YoY даёт более содержательную картину. Важно убедиться, что ряд действительно непрерывен (нет пропущенных месяцев), иначе `LAG(..., 12)` «сдвинется» не на 12 календарных месяцев, а на 12 существующих строк, что не одно и то же при пропусках.
- **Частые ошибки:** применяют `LAG(revenue, 12)` к ряду с пропущенными месяцами, получая сравнение с неверным историческим периодом без явной ошибки выполнения — запрос «работает», но результат содержательно неверен; не учитывают, что длина месяца и число рабочих/праздничных дней могут отличаться год к году, что тоже влияет на сравнение.

**Пример / кейс**
```sql
WITH monthly AS (
  SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS revenue
  FROM orders GROUP BY 1
)
SELECT month, revenue,
       ROUND(100.0 * (revenue - LAG(revenue, 12) OVER (ORDER BY month))
             / NULLIF(LAG(revenue, 12) OVER (ORDER BY month), 0), 1) AS yoy_pct
FROM monthly ORDER BY month;
```
Проверка: для конкретного месяца вручную найти выручку этого же месяца год назад в исходных данных и сравнить с результатом `LAG`.

### 62. [Q-04-01-0062] В чём разница между QUALIFY (ClickHouse/Snowflake/BigQuery) и подзапросом с ROW_NUMBER в PostgreSQL для фильтрации по результату оконной функции?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
`QUALIFY` позволяет фильтровать строки прямо по значению оконной функции в том же `SELECT`, где она вычислена, тогда как в PostgreSQL (где `QUALIFY` не поддерживается) для этого нужно обернуть оконную функцию в подзапрос или CTE и фильтровать уже внешним `WHERE`, потому что `WHERE` не может напрямую ссылаться на оконные функции, вычисленные в том же уровне запроса.

**Разбор**
- **Как это работает:** логический порядок выполнения запроса — оконные функции вычисляются после `WHERE`, но до финальной проекции `SELECT`; `QUALIFY` — это дополнительный этап фильтрации именно после вычисления оконных функций, аналогичный тому, как `HAVING` работает после `GROUP BY`. В PostgreSQL такого отдельного этапа нет, поэтому оконную функцию нужно материализовать в подзапросе/CTE, чтобы потом сослаться на неё в обычном `WHERE`.
- **На практике:** `QUALIFY` делает запрос короче и нагляднее там, где он поддерживается; в PostgreSQL эквивалентная логика требует дополнительного уровня вложенности, что не хуже по производительности, но многословнее. При переносе SQL-кода между диалектами (например, из BigQuery в PostgreSQL) наличие `QUALIFY` — одна из частых точек, которую нужно переписать.
- **Частые ошибки:** пытаются написать `WHERE ROW_NUMBER() OVER (...) = 1` напрямую в PostgreSQL без оборачивания в подзапрос и получают ошибку синтаксиса, так как оконные функции недопустимы в `WHERE` того же уровня запроса.

**Пример / кейс**
```sql
-- ClickHouse / Snowflake / BigQuery
SELECT customer_id, order_id, amount
FROM orders
QUALIFY ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY amount DESC) = 1;

-- PostgreSQL (эквивалент)
SELECT * FROM (
  SELECT customer_id, order_id, amount,
         ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY amount DESC) AS rn
  FROM orders
) t WHERE rn = 1;
```
Проверка: оба запроса должны вернуть одинаковое количество строк — ровно одну на каждого клиента.

### 63. [Q-04-01-0063] Как в BigQuery «развернуть» столбец с массивом тегов заказа (ARRAY<STRING>) в отдельные строки для подсчёта популярности каждого тега?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно использовать `UNNEST(tags)` в `FROM`/`CROSS JOIN`, что превращает каждый элемент массива в отдельную строку, после чего можно обычным `GROUP BY` посчитать частоту каждого тега.

**Разбор**
- **Как это работает:** `UNNEST` в BigQuery — табличная функция, которая принимает массив (`ARRAY`) и возвращает по одной строке на каждый его элемент; при использовании как `CROSS JOIN UNNEST(tags) AS tag` каждая исходная строка заказа «размножается» на число тегов в её массиве, сохраняя остальные поля заказа неизменными в каждой копии.
- **На практике:** это стандартный паттерн для анализа данных, хранящихся в полуструктурированном/вложенном виде (массивы, структуры) — частый случай в BigQuery для событийных и JSON-подобных данных. Аналогичная операция в PostgreSQL называется `unnest()`, а в ClickHouse — `arrayJoin()`, с похожей, но не идентичной семантикой.
- **Частые ошибки:** не учитывают, что заказ без тегов (пустой массив или `NULL`) при обычном `CROSS JOIN UNNEST` может просто исчезнуть из результата — для его сохранения нужен `LEFT JOIN UNNEST(...)` там, где диалект это поддерживает; забывают, что после разворота `COUNT(*)` считает число пар «заказ-тег», а не число заказов — для числа уникальных заказов с тегом нужен `COUNT(DISTINCT order_id)`.

**Пример / кейс**
```sql
SELECT tag, COUNT(DISTINCT order_id) AS orders_with_tag
FROM orders, UNNEST(tags) AS tag
GROUP BY tag
ORDER BY orders_with_tag DESC;
```
Проверка: сумма `orders_with_tag` по всем тегам должна быть не меньше количества заказов хотя бы с одним тегом (может быть больше, так как у заказа может быть несколько тегов).

### 64. [Q-04-01-0064] Почему `NOT EXISTS` обычно рекомендуют вместо `LEFT JOIN ... WHERE right.id IS NULL` для поиска строк без связанных записей, и есть ли реальная разница в результате?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
При корректных условиях оба запроса дают одинаковый логический результат, но `NOT EXISTS` часто читается яснее по смыслу («не существует связанной записи») и в некоторых СУБД/версиях может эффективнее оптимизироваться, особенно при многостолбцовом условии соединения.

**Разбор**
- **Как это работает:** `LEFT JOIN ... WHERE b.id IS NULL` сначала строит полное соединение со всеми совпадениями и несовпадениями, а затем отфильтровывает только те строки, где совпадения не нашлось; `NOT EXISTS (SELECT 1 FROM b WHERE b.a_id = a.id)` для каждой строки `a` сразу проверяет наличие соответствия без необходимости материализовать полный JOIN.
- **На практике:** современные оптимизаторы PostgreSQL часто превращают оба варианта в похожий физический план (`Anti Join`), поэтому разница в производительности не всегда значима — стоит сравнивать `EXPLAIN ANALYZE` на конкретных данных, а не полагаться на общее правило. Выбор между ними часто определяется читаемостью кода и условиями на множественные столбцы соединения, где `NOT EXISTS` с несколькими условиями в подзапросе часто компактнее.
- **Частые ошибки:** при соединении по нескольким столбцам в `LEFT JOIN ... WHERE col IS NULL` проверяют на `NULL` только один из столбцов соединения, что может дать неверный результат, если именно этот столбец оказался `NULL` в найденной (а не отсутствующей) паре.

**Пример / кейс**
```sql
SELECT c.customer_id
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
```
Проверка: сравнить результат с `SELECT c.customer_id FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id WHERE o.customer_id IS NULL` — наборы `customer_id` должны полностью совпасть.

### 65. [Q-04-01-0065] Почему наивное усреднение дневных конверсий по регионам может давать искажённую общую конверсию (проявление парадокса Симпсона), и как считать правильно?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Простое среднее арифметическое долей по группам (`AVG` долей) игнорирует разный размер этих групп, поэтому правильный способ — считать взвешенную конверсию как `SUM(converted) / SUM(total)` по всем строкам сразу, а не усреднять уже готовые проценты.

**Разбор**
- **Как это работает:** если в регионе A было 10 визитов и 5 конверсий (50%), а в регионе B — 1000 визитов и 300 конверсий (30%), простое среднее долей даст (50%+30%)/2 = 40%, что никак не отражает реальную общую конверсию `(5+300)/(10+1000) ≈ 29.4%` — потому что простое среднее не учитывает, что регион B весит в данных гораздо больше.
- **На практике:** эта разница становится особенно важной (и может приводить к парадоксу Симпсона), когда сравнивают агрегированные группы с сильно разным объёмом — например, конверсия по дням недели, по странам с разным трафиком или по когортам разного размера. Перед усреднением процентных метрик всегда стоит спросить: «веса групп одинаковы или сильно различаются?»
- **Частые ошибки:** усредняют уже посчитанные в отдельных строках проценты (`AVG(conversion_rate)` по регионам) вместо пересчёта от первичных числителя и знаменателя — это распространённая ошибка в сводных дашбордах, собранных из уже агрегированных таблиц без доступа к исходным числителю/знаменателю.

**Пример / кейс**
```sql
SELECT SUM(converted) * 1.0 / SUM(total_visits) AS overall_conversion
FROM region_stats;
-- НЕВЕРНО для сравнения с общим показателем: AVG(converted::float / total_visits) AS naive_avg
```
Проверка: сравнить `overall_conversion` с результатом прямого расчёта по необобобщённым данным `SELECT COUNT(CASE WHEN converted THEN 1 END)::float / COUNT(*) FROM raw_visits` — они должны совпасть, а наивное среднее долей — как правило, нет.

### 66. [Q-04-01-0066] Как найти дни, за которые полностью отсутствуют данные в таблице событий (пропуски в временном ряду), используя календарную таблицу?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно сделать `LEFT JOIN` от полного списка дат периода (сгенерированного или из отдельной календарной таблицы) к агрегированным по дням данным и отобрать те даты, где после соединения не нашлось ни одной строки событий (`COUNT(event) = 0` или `event_id IS NULL`).

**Разбор**
- **Как это работает:** если просто сделать `SELECT DISTINCT date FROM events`, пропущенные дни физически отсутствуют в данных и их невозможно «увидеть» — нужна внешняя точка отсчёта (полный список ожидаемых дат), от которой можно оттолкнуться через `LEFT JOIN`, чтобы явно выявить даты без единой строки в основной таблице.
- **На практике:** такую проверку целесообразно делать частью регулярного мониторинга качества данных (data quality) — например, ежедневная автоматическая проверка «за последние 24 часа данные точно поступили» помогает поймать сбой в пайплайне до того, как искажённый отчёт увидит бизнес.
- **Частые ошибки:** путают «день без единого события» (возможный сбой загрузки данных) с «днём с нулевой активностью пользователей» (легитимный бизнес-факт, например, выходной для B2B-продукта) — расследование должно отличать эти два случая по контексту, а не автоматически считать любой пропуск ошибкой.

**Пример / кейс**
```sql
WITH days AS (
  SELECT generate_series('2024-03-01'::date, '2024-03-31'::date, interval '1 day')::date AS day
),
agg AS (
  SELECT DATE_TRUNC('day', event_time)::date AS day, COUNT(*) AS events_cnt
  FROM events GROUP BY 1
)
SELECT d.day
FROM days d
LEFT JOIN agg a ON a.day = d.day
WHERE a.day IS NULL;
```
Проверка: для каждой найденной «пустой» даты проверить логи загрузки данных (ETL) за этот день, чтобы подтвердить техническую причину, а не бизнес-факт.

### 67. [Q-04-01-0067] Данные о заказах поступают из одного источника повторно (late-arriving events) и иногда дублируются по order_id с разным updated_at. Как агрегировать только последнюю версию каждого заказа?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно пронумеровать строки по `order_id` с сортировкой по `updated_at DESC` через `ROW_NUMBER()`, оставить только строки с номером 1 (последнюю версию каждого заказа) в CTE, и уже на этом «чистом» наборе строить все дальнейшие агрегаты.

**Разбор**
- **Как это работает:** этот паттерн — частный случай дедупликации (аналогичный вопросу про удаление дублей), но применяется систематически как обязательный первый шаг перед любой агрегацией таких данных, а не разово; логика та же: `PARTITION BY order_id ORDER BY updated_at DESC` даёт `rn = 1` для самой свежей версии.
- **На практике:** важно убедиться, что `updated_at` действительно монотонно отражает «более новую» версию записи, а не время технической вставки строки в хранилище — если источник присылает исторические правки с запаздыванием, именно бизнес-метка времени обновления должна использоваться для сортировки, а не момент загрузки в хранилище.
- **Частые ошибки:** агрегируют данные напрямую, не дедуплицируя, из-за чего в финальных метриках учитываются сразу несколько версий одного заказа (например, старая версия со статусом «в обработке» и новая со статусом «доставлен»), что задваивает счётчики и искажает статусную разбивку.

**Пример / кейс**
```sql
WITH latest AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) AS rn
  FROM raw_orders_feed
)
SELECT status, COUNT(*) AS orders_cnt, SUM(amount) AS total_amount
FROM latest
WHERE rn = 1
GROUP BY status;
```
Проверка: `COUNT(DISTINCT order_id)` на `latest WHERE rn = 1` должен равняться `COUNT(*)` того же запроса — то есть ровно одна строка на заказ.

### 68. [Q-04-01-0068] Когда создание промежуточной агрегированной (материализованной) таблицы для дневных метрик оправдано, а когда достаточно обычного запроса "на лету"?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Материализованную таблицу или вью стоит создавать, когда один и тот же тяжёлый расчёт выполняется многократно (например, дашборд, который открывают десятки раз в день) и исходные данные меняются не чаще, чем требуется обновлять агрегат; если запрос выполняется редко или всегда должен быть «в реальном времени», обычный запрос на лету проще и избавляет от риска показать устаревшие данные.

**Разбор**
- **Как это работает:** материализованное представление (`MATERIALIZED VIEW` в PostgreSQL, таблица, обновляемая по расписанию, или материализованная вью в BigQuery) физически сохраняет результат агрегации, избавляя от повторного пересчёта по сырым данным при каждом обращении; обновление такой таблицы требует отдельного процесса (`REFRESH MATERIALIZED VIEW`, scheduled query и т.п.), который должен быть надёжным и мониториться отдельно.
- **На практике:** выбор — это компромисс между скоростью чтения и свежестью данных плюс дополнительной инфраструктурной сложностью (ещё один процесс, который может сломаться, ещё один источник расхождений между «сырыми» и «агрегированными» цифрами, если они временно не синхронизированы). Для не слишком больших объёмов и редких запросов материализация часто избыточна.
- **Частые ошибки:** материализуют агрегаты без чёткого процесса инвалидации/обновления, из-за чего дашборд незаметно показывает устаревшие цифры; либо, наоборот, пересчитывают на лету очень тяжёлый запрос при каждом открытии дашборда, создавая ненужную нагрузку и задержку для пользователей.

**Пример / кейс**
```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT DATE_TRUNC('day', order_date) AS day, SUM(amount) AS revenue
FROM orders
GROUP BY 1;
-- Обновление по расписанию:
REFRESH MATERIALIZED VIEW daily_revenue;
```
Проверка: после `REFRESH` сравнить несколько строк `daily_revenue` с прямым агрегатом по `orders` за те же дни — они должны совпадать на момент обновления.

### 69. [Q-04-01-0069] Как написать один запрос, который одновременно считает количество новых и количество вернувшихся пользователей по дням?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно сначала для каждого пользователя определить дату первой активности (через `MIN(event_date)` в CTE), затем в основном запросе помечать событие как «новый пользователь», если его дата совпадает с датой первой активности, и как «вернувшийся» — если не совпадает, и сгруппировать по дате и этой метке.

**Разбор**
- **Как это работает:** сравнение `event_date = first_seen_date` для каждой строки активности однозначно классифицирует её на «первый визит» (новый пользователь в этот день) или «повторный визит» (вернувшийся пользователь); агрегация `COUNT(DISTINCT user_id)` по дате и метке даёт обе метрики за один проход по данным.
- **На практике:** важно явно договориться об определении «нового» и «вернувшегося» пользователя относительно выбранного события — активность в приложении, покупка, регистрация — разные определения дают разные абсолютные числа, хотя общая логика расчёта одна и та же.
- **Частые ошибки:** считают «новых пользователей» по дате регистрации в системе, а «активность» — по другому событию (например, покупке), без явного разделения этих двух разных понятий, что приводит к путанице в терминологии между командами, обсуждающими один и тот же отчёт.

**Пример / кейс**
```sql
WITH first_seen AS (
  SELECT user_id, MIN(event_date) AS first_date
  FROM activity GROUP BY user_id
)
SELECT a.event_date,
       COUNT(DISTINCT CASE WHEN a.event_date = f.first_date THEN a.user_id END) AS new_users,
       COUNT(DISTINCT CASE WHEN a.event_date != f.first_date THEN a.user_id END) AS returning_users
FROM activity a
JOIN first_seen f ON f.user_id = a.user_id
GROUP BY a.event_date
ORDER BY a.event_date;
```
Проверка: `new_users`, просуммированные по всем дням, должны равняться общему числу уникальных пользователей в `activity`.

### 70. [Q-04-01-0070] Как сравнить производительность двух эквивалентных по результату запросов (с подзапросом и с CTE) и аргументированно выбрать один для продакшена?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно прогнать оба варианта через `EXPLAIN ANALYZE` на представительном объёме данных (близком к продакшену, а не на маленькой тестовой выборке) и сравнить фактическое время выполнения и объём обработанных данных, а не полагаться на общие утверждения вроде «CTE всегда медленнее подзапроса».

**Разбор**
- **Как это работает:** в современных версиях PostgreSQL (начиная с 12) простой, не рекурсивный CTE по умолчанию может быть «встроен» (inlined) оптимизатором в основной запрос точно так же, как подзапрос — то есть различие в производительности, характерное для более старых версий, во многих случаях исчезло. Поведение может отличаться, если CTE явно помечен как материализуемый (`AS MATERIALIZED`) или используется многократно.
- **На практике:** универсального правила «что быстрее» нет — решение зависит от конкретной версии СУБД, объёма данных, наличия индексов и того, насколько сложен план для каждого варианта. Самый надёжный способ — измерить на реалистичных данных, а не делать вывод по теории или по результатам на маленькой тестовой таблице, где различия в плане могут быть не видны.
- **Частые ошибки:** делают вывод о производительности на основе синтетического теста на маленькой таблице, где оба варианта выполняются за миллисекунды независимо от плана, и переносят этот вывод на продакшен-данные без повторной проверки.

**Пример / кейс**
```sql
EXPLAIN ANALYZE
WITH high_value AS (SELECT * FROM orders WHERE amount > 1000)
SELECT customer_id, COUNT(*) FROM high_value GROUP BY customer_id;

EXPLAIN ANALYZE
SELECT customer_id, COUNT(*)
FROM (SELECT * FROM orders WHERE amount > 1000) t
GROUP BY customer_id;
```
Проверка: сравнить строки `Execution Time` в обоих выводах на реальном объёме таблицы `orders`, а не на тестовых 100 строках.

### 71. [Q-04-01-0071] В чём отличие использования LIMIT в PostgreSQL/ClickHouse/MySQL от TOP в T-SQL и FETCH FIRST в стандарте SQL, и почему это важно при переносе запросов между диалектами?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
`LIMIT n` (PostgreSQL, MySQL, ClickHouse, BigQuery) ставится после `ORDER BY` в конце запроса, `TOP n` в T-SQL (SQL Server) ставится сразу после `SELECT`, а `FETCH FIRST n ROWS ONLY` — стандартный ANSI SQL синтаксис, поддерживаемый, например, в PostgreSQL и Oracle как альтернатива `LIMIT`; при переносе запроса между диалектами синтаксис ограничения строк почти всегда нужно переписывать вручную.

**Разбор**
- **Как это работает:** все три конструкции решают одну задачу — ограничить количество возвращаемых строк — но различаются синтаксическим расположением и иногда поведением при наличии «ничьих» на границе отсечки (для которых может потребоваться `WITH TIES` в T-SQL или `FETCH FIRST ... WITH TIES` в ANSI SQL, что не всегда есть в упрощённом `LIMIT`).
- **На практике:** при переносе SQL-логики между системами (например, миграция отчётов с SQL Server на PostgreSQL или с PostgreSQL на BigQuery) стоит явно пройтись по каждому запросу и заменить диалект-специфичный синтаксис, а не надеяться на автоматическую совместимость — в том числе проверить работу `OFFSET`/пагинации, которая тоже оформляется по-разному.
- **Частые ошибки:** копируют запрос с `TOP 10` в PostgreSQL без изменений и получают синтаксическую ошибку; не замечают, что некоторые диалекты (например, старые версии MySQL) не поддерживают `OFFSET` без `LIMIT` или требуют другого порядка аргументов (`LIMIT offset, count` в MySQL против `LIMIT count OFFSET offset` в PostgreSQL).

**Пример / кейс**
```sql
-- PostgreSQL / ClickHouse
SELECT * FROM orders ORDER BY amount DESC LIMIT 10;
-- T-SQL (SQL Server)
SELECT TOP 10 * FROM orders ORDER BY amount DESC;
-- ANSI SQL / Oracle / PostgreSQL
SELECT * FROM orders ORDER BY amount DESC FETCH FIRST 10 ROWS ONLY;
```
Проверка: все три варианта на одних и тех же данных должны вернуть одинаковый набор из 10 строк при отсутствии «ничьих» на границе.

### 72. [Q-04-01-0072] Как аргументированно объяснить стейкхолдеру, почему отчёт, использующий сложные оконные функции, нельзя просто "сделать быстрее" без изменения требований?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Middle

**Короткий ответ**
Нужно показать на конкретном плане выполнения, какая часть логики (например, большое окно `PARTITION BY` на всю историю без ограничения периода, или несколько проходов с разными окнами) требует обработки большого объёма данных, и предложить конкретные альтернативы с явными компромиссами (ограничить период, предрасчитать агрегаты, снизить частоту обновления), а не обещать ускорение без изменения входных условий.

**Разбор**
- **Как это работает:** оконные функции с большим `PARTITION BY`/`ORDER BY` по всей истории данных (например, накопительная сумма с начала всех времён для миллионов пользователей) требуют сортировки/группировки больших объёмов на каждый запуск; без ограничения периода или предагрегации это фундаментально дорогая операция независимо от мелких оптимизаций синтаксиса.
- **На практике:** полезно разделить для стейкхолдера два разных вопроса — «можно ли ускорить этот конкретный запрос техническими средствами» (индексы, материализация, партиционирование) и «можно ли изменить требования так, чтобы задача стала технически легче» (например, показывать агрегаты за последние 90 дней вместо всей истории, или обновлять отчёт раз в час вместо «в реальном времени»). Технический специалист должен явно показать числа (объём данных, фактическое время по EXPLAIN ANALYZE), а не ограничиваться общим «это сложно».
- **Частые ошибки:** соглашаются на нереалистичные сроки «просто оптимизировать запрос», не предъявив сначала диагностику через план выполнения, а затем вынужденно переобещают сроки; не предлагают явную альтернативу с её собственными компромиссами, из-за чего разговор заходит в тупик без решения.

**Пример / кейс**
```sql
EXPLAIN ANALYZE
SELECT user_id, SUM(amount) OVER (PARTITION BY user_id ORDER BY event_date)
FROM all_transactions; -- вся история, десятки миллионов строк
```
Проверка: сравнить фактическое время (`Execution Time`) этого запроса с его версией, ограниченной `WHERE event_date >= CURRENT_DATE - INTERVAL '90 days'` — разница в разы станет наглядным аргументом для обсуждения компромисса с бизнесом.


### 73. [Q-04-01-0073] Как спроектировать единый семантический слой метрик на SQL, чтобы разные команды не получали расходящиеся числа по "выручке" в своих дашбордах?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единого правильного решения нет: можно централизовать определения метрик в общих представлениях/моделях (dbt-подобный слой, вью с зафиксированной логикой) или в семантическом слое BI-инструмента — ключевое требование в обоих случаях — одно место истины для определения метрики, версионирование изменений и явная коммуникация при любом изменении логики.

**Разбор**
- **Как это работает:** семантический слой — это набор согласованных SQL-определений (представлений, моделей), которые инкапсулируют бизнес-логику метрики (что считается «выручкой», какие статусы включены, в какой момент времени признаётся доход) и от которых все дашборды и отчёты наследуют расчёт, а не пишут его заново.
- **На практике:** внедрение такого слоя требует договориться с владельцами разных дашбордов о единых определениях — это organizational, а не только технический вызов, и часто встречает сопротивление, если команды уже привыкли к своим числам. Нужно предусмотреть процесс управления изменениями (changelog, ревью) и миграции существующих отчётов на новые определения без «тихого» скачка в цифрах.
- **Частые ошибки:** строят технически красивый слой метрик, но не документируют и не согласовывают сами определения с бизнес-стейкхолдерами — в результате слой формально есть, но команды продолжают писать собственную логику «по привычке» или из недоверия.
- **Компромисс:** централизация снижает расхождения, но увеличивает связанность — изменение центрального определения метрики теперь влияет на все дашборды сразу, что требует более строгого процесса ревью и тестирования, чем при независимых командных запросах; для небольшой организации с одной командой аналитики этот процесс может быть избыточным, тогда как для крупной организации с десятками дашбордов риск расхождений без него становится неприемлемым.

**Пример / кейс**
```sql
-- Базовая модель "revenue", от которой наследуются все отчёты
CREATE VIEW fct_revenue AS
SELECT order_id, customer_id, order_date,
       amount - COALESCE(refund_amount, 0) AS net_revenue
FROM orders
WHERE status NOT IN ('test', 'fraud_flagged');
```
Проверка: любой дашборд, показывающий выручку, должен ссылаться на `fct_revenue`, а не на `orders` напрямую; регулярный аудит через поиск прямых обращений к `orders.amount` в коде дашбордов помогает находить обходы этого слоя.

### 74. [Q-04-01-0074] Как принять решение между предагрегированными таблицами и расчётом метрик «на лету» для общекомпанейской системы отчётности с растущим объёмом данных?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единственно верного ответа нет: решение зависит от требуемой свежести данных, количества и разнообразия нужных разрезов, объёма данных и стоимости вычислений — предагрегация выигрывает в скорости чтения и предсказуемой стоимости, но жертвует гибкостью разрезов и добавляет инфраструктурную сложность пайплайна обновления.

**Разбор**
- **Как это работает:** предагрегированные таблицы (построенные по расписанию через ETL/ELT) заранее сворачивают детальные данные до нужных измерений, резко уменьшая объём, который читается при каждом запросе отчёта; расчёт «на лету» всегда обращается к детальным данным и пересчитывает агрегаты заново при каждом запуске, что проще поддерживать, но дороже по ресурсам при росте объёма и частоты обращений.
- **На практике:** типичный компромиссный путь — предагрегировать только самые частые и тяжёлые разрезы (например, по дням и по топ-уровню категорий), оставляя редкие ad-hoc разрезы для расчёта на лету по детальным данным; при этом важно явно документировать, какие именно разрезы предрасчитаны, чтобы аналитики не путали «есть только по дням» с «можно получить любой разрез».
- **Частые ошибки:** предагрегируют слишком много разрезов «на будущее», не имея подтверждённого спроса на них, что увеличивает сложность пайплайна без реальной выгоды; либо, наоборот, затягивают с предагрегацией до момента, когда расчёты на лету уже создают заметные проблемы с задержкой и стоимостью, и переход становится болезненным и срочным.
- **Компромисс:** нет universal правильного порога объёма данных или частоты запросов, при котором нужно переходить к предагрегации — решение требует измерения реальной стоимости и задержки текущего подхода и сопоставления с инфраструктурными затратами на поддержку пайплайна обновления, включая риск устаревания данных при сбое обновления.

**Пример / кейс**
```sql
-- Предагрегированная таблица, обновляемая раз в сутки
CREATE TABLE agg_daily_sales AS
SELECT DATE_TRUNC('day', order_date) AS day, region, category, SUM(amount) AS revenue
FROM orders
GROUP BY 1, 2, 3;
```
Проверка: сравнить время ответа дашборда на `agg_daily_sales` против прямого запроса к `orders` на актуальном объёме данных, и явно замерить задержку между событием и его появлением в агрегированной таблице после обновления.

### 75. [Q-04-01-0075] Таблица событий выросла до миллиардов строк и запросы по ней стали непредсказуемо медленными в разные дни. Как спроектировать стратегию партиционирования и кластеризации с учётом разных диалектов (PostgreSQL, ClickHouse, BigQuery)?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единого решения нет: стратегия зависит от типичных фильтров в реальных запросах и от конкретной СУБД — в PostgreSQL это декларативное партиционирование по дате плюс индексы, в ClickHouse — ключ партиционирования (`PARTITION BY`) и ключ сортировки (`ORDER BY`), в BigQuery — партиционирование по дате и кластеризация по часто фильтруемым столбцам; выбор всегда компромисс между скоростью чтения, скоростью записи и операционной сложностью.

**Разбор**
- **Как это работает:** партиционирование физически разделяет таблицу на меньшие сегменты (обычно по диапазону дат), позволяя запросу с фильтром по этому диапазону читать только нужные сегменты (partition pruning); кластеризация/сортировочный ключ внутри сегмента дополнительно упорядочивает данные так, чтобы фильтрация по вторичным столбцам также требовала меньше операций ввода-вывода.
- **На практике:** перед выбором ключей нужно проанализировать реальные паттерны запросов (через логи медленных запросов или метрики BI-инструмента), а не угадывать — например, если 90% запросов фильтруют по `user_id`, кластеризация должна учитывать именно этот столбец, а не произвольно выбранный. Непредсказуемая медленность «в разные дни» часто говорит о неравномерном распределении данных между партициями (data skew) — например, один день с аномально большим количеством событий создаёт «горячую» партицию.
- **Частые ошибки:** выбирают слишком мелкое партиционирование (например, по часам при небольшом суточном объёме), что создаёт избыточное количество маленьких партиций и увеличивает накладные расходы на их обработку метаданными; меняют схему партиционирования без миграции существующих данных, получая «смешанную» таблицу с частью данных в старой схеме.
- **Компромисс:** более мелкое партиционирование и более специфичная кластеризация ускоряют конкретные частые запросы, но увеличивают операционную сложность (больше партиций для мониторинга, больше правил для оптимизатора, возможное удорожание записи) и могут ухудшить производительность запросов с другими, нетипичными паттернами фильтрации; выбор всегда специфичен для фактической нагрузки и должен пересматриваться по мере её изменения.

**Пример / кейс**
```sql
-- BigQuery: партиционирование по дате + кластеризация по user_id
CREATE TABLE events
PARTITION BY event_date
CLUSTER BY user_id
AS SELECT * FROM events_raw;
```
Проверка: сравнить объём обработанных байт (dry run) для типичного запроса с фильтром по `event_date` и `user_id` до и после применения партиционирования/кластеризации — ожидается кратное снижение.

### 76. [Q-04-01-0076] Руководство просит "срочно подтвердить" уже объявленную победу варианта B в A/B-тесте перед отчётом совету директоров через час. Как методологически подойти к такой срочной проверке SQL-запросом, учитывая риски peeking и novelty effect?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единственно правильного пути нет: можно быстро предоставить сырые цифры (SRM, размер выборки, текущая разница метрики) с чёткой оговоркой о методологических ограничениях срочной проверки, но нельзя подменять это формальным «подтверждением» значимости без контроля за временем остановки теста и давностью запуска (риск novelty effect), не предупредив об этом явно тех, кто принимает решение.

**Разбор**
- **Как это работает:** «подтверждение победы» требует как минимум проверки SRM, достаточного размера выборки для задуманной мощности теста, отсутствия признаков peeking (искусственно повышенной вероятности ложноположительного результата, если тест смотрели многократно и остановили в удачный момент) и достаточной давности запуска, чтобы исключить временный эффект новизны, который может угасать уже в первые недели.
- **На практике:** под давлением срочности можно и нужно за ограниченное время выполнить базовые SQL-проверки (SRM, размеры групп, стабильность эффекта по дням) и честно представить результат вместе со списком того, что НЕ было проверено из-за недостатка времени — это профессиональная ответственность аналитика: не подгонять методологию под желаемый быстрый ответ.
- **Частые ошибки:** под давлением сроков выдают «да, подтверждаю» по одному агрегированному числу без проверки SRM и стабильности эффекта по времени, что может привести к стратегическому решению на основе шумового или смещённого результата; либо, наоборот, отказываются дать какой-либо ответ вовсе, что не помогает бизнесу принять обоснованное по времени решение.
- **Компромисс:** баланс между скоростью и методологической строгостью всегда ситуативен — аналитик должен явно обозначить, какие проверки были сделаны за отведённое время, какие не были сделаны и почему, предоставив руководству возможность самостоятельно оценить уровень риска принятия решения на основе неполной проверки, а не скрывая эту неполноту за уверенным «подтверждаю».

**Пример / кейс**
```sql
-- Быстрый набор диагностических проверок за ограниченное время
SELECT variant, COUNT(DISTINCT user_id) AS users_cnt
FROM experiment_assignments WHERE experiment_id = 'checkout_redesign' GROUP BY variant;

SELECT DATE_TRUNC('day', assigned_at) AS day, variant,
       COUNT(DISTINCT user_id) AS users_cnt,
       COUNT(DISTINCT CASE WHEN converted THEN user_id END) AS converted_cnt
FROM experiment_daily WHERE experiment_id = 'checkout_redesign'
GROUP BY 1, 2 ORDER BY 1;
```
Проверка: если эффект «скачет» по дням или появился только в последние 2 дня эксперимента, это сигнал для явной оговорки о риске novelty effect и peeking перед отчётом совету директоров.

### 77. [Q-04-01-0077] Как методологически учить младшего аналитика диагностировать внезапное падение ключевой метрики через последовательную декомпозицию SQL-запросов, а не через угадывание причины?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единого жёсткого алгоритма нет, но полезный каркас — последовательно сужать гипотезу через декомпозицию метрики по сегментам (источник, регион, платформа, статус), по времени (когда именно начался провал) и по этапам воронки/пайплайна данных, причём на каждом шаге формулировать проверяемую гипотезу перед написанием следующего SQL-запроса, а не писать запросы наугад.

**Разбор**
- **Как это работает:** декомпозиция метрики — это представление общего числа как суммы или произведения более детальных составляющих (например, «выручка = количество заказов × средний чек», или «выручка по регионам»), после чего можно проверить запросом, в какой именно составляющей или сегменте сосредоточено падение, вместо того чтобы анализировать агрегированное число целиком.
- **На практике:** эффективная последовательность обучения — сначала просить младшего аналитика чётко сформулировать гипотезу в одно предложение («подозреваю, что падение сосредоточено в одном источнике трафика»), затем написать минимальный SQL-запрос, проверяющий именно эту гипотезу, и только потом двигаться к следующей; это дисциплинирует и предотвращает хаотичный перебор запросов без осмысления результата.
- **Частые ошибки:** младшие аналитики часто сразу подозревают «ошибку в данных» или «баг в трекинге» без проверки более простых и частых причин (сезонность, изменение логики подсчёта, технический сбой загрузки за конкретный день) — наставнику стоит направлять к проверке простых объяснений раньше сложных.
- **Компромисс:** более структурированный процесс декомпозиции занимает больше времени на один инцидент, чем «быстрое угадывание», но снижает риск неверного диагноза и обучает самостоятельности на будущих инцидентах; для разового незначительного колебания метрики полноценная декомпозиция может быть избыточной, и значимость самого падения стоит оценить до начала глубокого расследования.

**Пример / кейс**
```sql
-- Шаг 1: когда начался провал?
SELECT DATE_TRUNC('day', event_date) AS day, SUM(amount) AS revenue
FROM orders GROUP BY 1 ORDER BY 1;

-- Шаг 2: сконцентрировано ли падение в одном сегменте?
SELECT source, DATE_TRUNC('day', event_date) AS day, SUM(amount) AS revenue
FROM orders GROUP BY 1, 2 ORDER BY 2, 1;
```
Проверка: после каждого шага явно сформулировать, какая гипотеза подтвердилась или была отвергнута, и только после этого переходить к следующему запросу — документируя цепочку рассуждений для будущего ревью.

### 78. [Q-04-01-0078] Как спроектировать идемпотентную стратегию дедупликации для событийного пайплайна с доставкой "at-least-once" в хранилище с поддержкой SQL (например, ClickHouse или BigQuery)?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единственно верного решения нет: можно дедуплицировать на уровне запроса (оконные функции/`LIMIT 1 BY`), на уровне хранения (движки типа `ReplacingMergeTree` с ключом версии) или на уровне загрузки (идемпотентный `MERGE`/`UPSERT` по уникальному event_id) — выбор зависит от допустимой задержки, объёма данных и того, нужна ли дедупликация «всегда и везде» или только в конкретных отчётах.

**Разбор**
- **Как это работает:** доставка «at-least-once» гарантирует, что событие точно не потеряется, но может прийти несколько раз; для корректного подсчёта уникальных событий нужен стабильный `event_id` (идемпотентный ключ события, сгенерированный на стороне источника, а не на стороне получателя), по которому можно однозначно определить дубликат независимо от того, сколько раз событие доставлено.
- **На практике:** дедупликация на уровне запроса (`ROW_NUMBER()`/`QUALIFY`/`LIMIT 1 BY`) проста в реализации, но требует повторения логики в каждом запросе, что рискует несогласованностью между отчётами; дедупликация на уровне загрузки (`MERGE INTO target USING staging ON target.event_id = staging.event_id`) решает проблему один раз при записи, но требует поддержки `MERGE`/`UPSERT` в конкретной СУБД и аккуратной обработки конкурентных записей.
- **Частые ошибки:** используют время получения события или автоинкрементный id хранилища как признак дубликата вместо бизнес-идентификатора события, из-за чего реальные дубли (с разным временем получения, но одним и тем же событием) не распознаются как дубли; не учитывают, что некоторые события могут быть «поздними» изменениями одного и того же бизнес-объекта, а не техническими дублями, и бездумная дедупликация по последней версии может скрыть легитимную историю изменений, если она нужна.
- **Компромисс:** дедупликация на уровне загрузки централизует логику и снижает риск расхождений между отчётами, но требует более сложной инфраструктуры загрузки и тщательного тестирования идемпотентности; дедупликация на лету в каждом запросе проще внедрить локально, но создаёт риск, что часть запросов забудет про дедупликацию и покажет задвоенные числа — выбор зависит от зрелости инфраструктуры команды и критичности точности метрики.

**Пример / кейс**
```sql
-- ClickHouse: явная дедупликация по event_id с выбором последней версии
SELECT event_id, argMax(payload, ingested_at) AS payload
FROM raw_events
GROUP BY event_id;
```
Проверка: сравнить `COUNT(DISTINCT event_id)` с `COUNT(*)` после дедупликации — они должны совпасть; дополнительно сверить общее число строк до дедупликации с ожидаемым коэффициентом повторной доставки, зафиксированным в мониторинге пайплайна.

### 79. [Q-04-01-0079] Сложный последовательный анализ пути пользователя (например, определение момента "отвала" в многошаговом процессе) можно реализовать через оконные функции, через self-join или процедурно вне SQL. Как выбрать подход для продакшен-пайплайна?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единственно правильного подхода нет: оконные функции обычно дают лучший баланс читаемости и производительности для последовательностей умеренной сложности внутри одной СУБД, self-join быстро усложняется и плохо масштабируется при росте числа шагов, а вынесение логики за пределы SQL (в Python/Spark) оправдано, когда правила анализа слишком сложны или нестабильны для декларативного SQL, либо требуют интеграции с внешними системами.

**Разбор**
- **Как это работает:** оконные функции (`LAG`/`LEAD`, накопительные суммы, нумерация шагов) эффективно обрабатывают последовательности в один проход по данным средствами самой СУБД; self-join для той же задачи обычно требует соединения таблицы с собой столько раз, сколько шагов в последовательности нужно сравнить, что быстро становится нечитаемым и медленным при увеличении числа шагов. Процедурный подход (построчная обработка в коде) даёт максимальную гибкость логики (произвольные условия, внешние вызовы), но теряет преимущества декларативной оптимизации СУБД и усложняет инфраструктуру (нужен отдельный процесс вычисления, а не просто SQL-запрос).
- **На практике:** решение зависит от того, насколько стабильны правила анализа (если бизнес часто меняет определение «отвала» — гибкость кода может быть важнее), от объёма данных (SQL-движки обычно эффективнее обрабатывают большие объёмы, чем построчный код на одном сервере) и от того, где нужен результат (если он должен попасть обратно в SQL-хранилище для дальнейшего BI, оставаться в SQL часто проще интеграционно).
- **Частые ошибки:** выбирают self-join для последовательности из 10+ шагов «по привычке» (потому что так делали для 2-3 шагов), получая нечитаемый и медленный запрос; либо выносят в код логику, которая прекрасно выражается оконными функциями, усложняя пайплайн без необходимости и теряя возможность быстро проверить промежуточный результат простым SQL-запросом.
- **Компромисс:** оконные функции предпочтительны по умолчанию для производительности и декларативной читаемости внутри экосистемы SQL, но при действительно сложной, часто меняющейся или сильно ветвящейся логике анализа пути пользователя процедурный подход вне SQL может быть оправданным, несмотря на дополнительную инфраструктурную сложность — выбор должен основываться на реальной сложности правил и ожидаемой частоте их изменения, а не на одном лишь предпочтении инструмента.

**Пример / кейс**
```sql
WITH steps AS (
  SELECT user_id, step_name, step_time,
         LEAD(step_name) OVER (PARTITION BY user_id ORDER BY step_time) AS next_step
  FROM funnel_events
)
SELECT step_name, COUNT(*) AS reached, COUNT(next_step) AS proceeded
FROM steps GROUP BY step_name;
```
Проверка: сумма «отвалившихся» (`reached - proceeded`) на каждом шаге должна в точности совпадать с убыванием общего числа пользователей между соседними шагами воронки.

### 80. [Q-04-01-0080] Две команды используют разное определение "активного пользователя" в своих SQL-запросах, что приводит к расходящимся выводам о состоянии продукта. Как выстроить governance-процесс для версионирования и синхронизации определений метрик?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единственно верного процесса нет: можно ввести реестр метрик (каталог с явным владельцем, SQL-определением и версией каждой ключевой метрики), обязательное ревью изменений определения метрики через этот реестр, и явную маркировку, какая версия определения использована в каждом отчёте — конкретная форма процесса зависит от размера организации и зрелости инструментов.

**Разбор**
- **Как это работает:** реестр метрик — это документированный (в коде или в специальном инструменте типа semantic layer / metrics catalog) список согласованных определений с владельцем, ответственным за изменения, и историей версий; при изменении определения метрики процесс ревью требует явно уведомить все команды, использующие эту метрику, прежде чем изменение попадёт в продакшен.
- **На практике:** внедрение такого процесса — это не разовое техническое решение, а изменение рабочих привычек команд, и часто встречает сопротивление, если воспринимается как бюрократическое замедление; успешный governance обычно начинается с 3-5 самых критичных и часто используемых метрик, а не пытается сразу охватить весь каталог показателей компании.
- **Частые ошибки:** создают централизованный каталог метрик, но не делают использование определений из него обязательным (не блокируют создание отчётов с собственной логикой), из-за чего расхождения продолжают накапливаться параллельно с формально существующим «единым источником истины»; меняют определение метрики без уведомления всех потребителей, что создаёт «тихий» скачок в исторических цифрах без объяснения.
- **Компромисс:** более строгий governance снижает расхождения и повышает доверие к данным, но замедляет скорость изменений и добавляет административную нагрузку — командам нужно заранее согласовывать изменения вместо того, чтобы быстро подстраивать свою логику под локальные нужды; для небольшой компании с одной аналитической командой формальный реестр может быть избыточен, тогда как для организации с десятками продуктовых команд отсутствие такого процесса делает расхождения практически неизбежными.

**Пример / кейс**
```sql
-- Версионированное определение метрики с явным указанием версии в комментарии/метаданных
-- metric: active_user, version: 2024-06, owner: data-platform-team
CREATE VIEW metric_active_user_v2 AS
SELECT DISTINCT user_id, activity_date
FROM events
WHERE event_type IN ('login', 'purchase', 'support_ticket');
```
Проверка: провести аудит всех дашбордов, в которых фигурирует метрика «активный пользователь», и зафиксировать, какая версия определения используется в каждом — это даёт отправную точку для согласования.

### 81. [Q-04-01-0081] Разбивка метрики конверсии по сегментам показывает парадокс Симпсона: в каждом отдельном сегменте вариант B лучше, а в целом по всей выборке — хуже. Как это объяснить руководству и что порекомендовать по решению?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единственно правильного ответа «какую цифру показывать» не существует: нужно объяснить руководству, что причина — разный состав сегментов (например, вариант B чаще показывался сегменту с изначально более низкой конверсией) в сравниваемых группах, и явно обсудить, какой уровень агрегации (общий или по сегментам) отражает реальный интерес бизнеса, вместо того чтобы молча выбрать одну «правильную» цифру.

**Разбор**
- **Как это работает:** парадокс Симпсона возникает, когда скрытая переменная (например, платформа, регион, уровень вовлечённости до эксперимента) неравномерно распределена между сравниваемыми группами и при этом сильно влияет на саму метрику; в этом случае агрегированное сравнение смешивает эффект от самого варианта B с эффектом от разного состава аудитории в каждой группе, искажая общий вывод.
- **На практике:** объяснение руководству должно избегать как «технического» языка статистики, так и чрезмерного упрощения — полезно показать конкретные числа по сегментам и объяснить на простом примере (как в случае с конверсией по регионам с разным весом), почему сумма «лучше везде» не гарантирует «лучше в целом», если веса сегментов отличаются между группами теста.
- **Частые ошибки:** выбирают одну «официальную» цифру (либо только общую, либо только по сегментам) без объяснения противоречия, что создаёт у руководства ложное ощущение простоты ситуации; либо, наоборот, приводят слишком много статистических деталей без конкретной рекомендации к действию, оставляя решение полностью на усмотрение нетехнического стейкхолдера.
- **Компромисс:** можно рекомендовать смотреть на сегментированный результат как на более достоверный (если состав трафика в сегментах стабилен и репрезентативен), но это не универсальное правило — если несоответствие состава сегментов между группами теста является следствием ошибки в рандомизации (похоже на SRM на уровне сегментов), правильный шаг — не выбор удобной агрегации, а повторный запуск корректно рандомизированного теста; выбор зависит от того, можно ли доверять текущим данным вообще.

**Пример / кейс**
```sql
SELECT segment, variant,
       COUNT(DISTINCT user_id) AS users_cnt,
       SUM(converted) * 1.0 / COUNT(DISTINCT user_id) AS conversion_rate
FROM experiment_users
GROUP BY segment, variant;
```
Проверка: если доля пользователей из «слабого» сегмента заметно выше в группе B, чем в группе A (`SELECT variant, segment, COUNT(*) FROM experiment_users GROUP BY 1,2`), это подтверждает гипотезу о несбалансированном составе групп как причине парадокса.


### 82. [Q-04-01-0082] В BigQuery дашборды нужно обновлять чаще для "свежести", но каждый лишний запуск увеличивает счёт за обработанные байты. Как принять решение о частоте обновления и донести его до команды?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единого правильного интервала обновления нет: решение должно явно соотносить фактическую скорость принятия решений на основе дашборда (как часто его данные реально используются для действий) со стоимостью каждого обновления, а не выбираться по умолчанию «чем чаще, тем лучше» или «чем реже, тем дешевле».

**Разбор**
- **Как это работает:** стоимость в BigQuery в типичной модели оплаты по объёму обрабатываемых данных растёт пропорционально частоте запуска тяжёлого запроса при неизменном объёме сканируемых данных; при этом «свежесть» данных, не влияющая на фактические решения пользователей дашборда (например, обновление каждые 5 минут для метрики, которую смотрят раз в день), не создаёт ценности, но создаёт постоянные дополнительные расходы.
- **На практике:** полезно явно посчитать и показать команде две цифры рядом: дополнительную стоимость перехода, например, с ежедневного на часовое обновление, и типичный паттерн использования дашборда (как часто его реально открывают и когда); также можно комбинировать подходы — предагрегировать тяжёлую часть расчёта реже, но оставить лёгкий финальный слой агрегации для более частого обновления без пересчёта всего объёма.
- **Частые ошибки:** принимают решение о частоте обновления только на основе «ощущения важности» метрики руководством без реального измерения её использования; не пересматривают частоту обновления по мере роста объёма исходных данных, из-за чего стоимость обновления незаметно вырастает со временем даже без изменения конфигурации.
- **Компромисс:** более частое обновление повышает отзывчивость дашборда к изменениям, но пропорционально увеличивает затраты и инфраструктурную нагрузку; решение о балансе должно явно учитывать специфику конкретного дашборда и его аудитории, а менторская задача аналитика — научить команду формулировать это решение через измеримые величины (стоимость, частота использования), а не интуитивно.

**Пример / кейс**
```sql
-- Оценка стоимости через dry run перед изменением частоты обновления
SELECT COUNT(*) FROM `project.dataset.events`
WHERE event_date BETWEEN CURRENT_DATE() - 1 AND CURRENT_DATE();
```
Проверка: умножить объём обрабатываемых байт одного запуска (из dry run) на планируемую частоту обновления в месяц и сравнить итоговую оценку стоимости с текущей, чтобы перевести решение из «кажется нужным» в конкретные цифры.

### 83. [Q-04-01-0083] Компания использует PostgreSQL как оперативную базу, ClickHouse для аналитики событий и BigQuery для части внешних данных. Как решить, где должны выполняться тяжёлые JOIN между этими источниками — на этапе ETL или на этапе запроса?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единственно верного ответа нет: как правило, тяжёлые межсистемные соединения выгоднее выполнять заранее на этапе ETL, материализуя объединённый результат в одном хранилище, а не выполнять «живые» распределённые JOIN между разными СУБД на каждый запрос, но конкретное решение зависит от требуемой свежести данных, объёма и доступных инструментов федеративных запросов.

**Разбор**
- **Как это работает:** у каждой из перечисленных систем своя модель хранения и исполнения (строковая транзакционная PostgreSQL, колоночная аналитическая ClickHouse, колоночная облачная BigQuery) — «живой» JOIN между ними требует инструмента федеративных запросов (например, внешних таблиц, dblink, или специализированных коннекторов), который обычно не умеет эффективно проталкивать фильтры и индексы между системами, из-за чего такие запросы часто читают намного больше данных, чем кажется по тексту запроса.
- **На практике:** типичный паттерн — регулярно (по расписанию) выгружать нужные срезы данных из PostgreSQL и BigQuery в ClickHouse (или в единое аналитическое хранилище), выполняя соединение там, где данные уже физически рядом и колоночный движок оптимизирован для аналитических JOIN и агрегаций; это добавляет задержку (данные не «живые» в моменте), но резко снижает стоимость и непредсказуемость запросов.
- **Частые ошибки:** пытаются решить задачу «живым» федеративным запросом для часто используемого дашборда, не замечая, что из-за отсутствия проталкивания фильтров каждый запрос читает целые таблицы целиком из удалённой системы, что медленно и дорого; переносят вообще все данные в одно хранилище «на всякий случай», без оценки, какие данные реально нужны для конкретных аналитических задач, создавая ненужную инфраструктурную нагрузку.
- **Компромисс:** предрасчёт на ETL снижает стоимость и нагрузку на операционные системы, но увеличивает задержку актуальности данных и требует поддержки дополнительного пайплайна синхронизации с собственными рисками сбоя; для редких ad-hoc задач «живой» федеративный запрос может быть оправданным даже при его неэффективности, если регулярный пайплайн для этого конкретного соединения не оправдывает затрат на поддержку.

**Пример / кейс**
```sql
-- Пример структуры ETL-шага: выгрузка измерения из PostgreSQL в ClickHouse для последующего локального JOIN
-- (выполняется отдельным процессом синхронизации, не внутри аналитического запроса)
INSERT INTO ch_customers_dim
SELECT customer_id, region, segment FROM postgres_customers_snapshot;
```
Проверка: сравнить время и стоимость аналитического запроса, использующего локальный JOIN внутри ClickHouse после синхронизации, против гипотетического федеративного запроса напрямую к PostgreSQL на том же объёме данных.

### 84. [Q-04-01-0084] Как провести код-ревью SQL-запроса младшего аналитика, который формально работает и даёт правдоподобный результат, но имеет скрытые риски (неявный fan-out, отсутствие проверки SRM, хрупкая логика дат)?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единого чек-листа, покрывающего все случаи, не существует, но системный подход включает: проверку уникальности ключей до каждого JOIN, явную проверку границ дат и часовых поясов, проверку на NULL в ключевых полях, контроль того, что агрегаты считаются от первичных чисел (а не усредняются повторно), и обязательное объяснение автором своей логики своими словами, а не просто «запрос выдал нужное число».

**Разбор**
- **Как это работает:** скрытые риски в SQL часто не проявляются как синтаксические ошибки или даже как явно неправдоподобный результат — запрос с fan-out из-за JOIN один-ко-многим без предварительной агрегации может дать «красивое», но завышенное число, которое пройдёт поверхностную проверку на правдоподобность. Ревью должно целенаправленно искать именно такие тихие ошибки, а не только проверять синтаксис и общую логику.
- **На практике:** эффективный метод ревью — просить автора заранее явно выписать ожидаемые инварианты результата (например, «сумма по сегментам должна совпадать с общим итогом», «число строк на клиента не может быть больше числа его заказов») и показать, что он их проверил, а не просто предъявить финальную цифру; ревьюер должен задавать конкретные уточняющие вопросы («ты проверял, что order_id уникален перед этим JOIN?»), а не полагаться на то, что автор сам заметил бы проблему.
- **Частые ошибки:** ревьюер сосредотачивается на стиле кода (форматирование, именование) и упускает содержательные риски в логике; ревью проходит формально («запрос запускается без ошибок — одобряю»), без воспроизведения расчёта на контрольном примере с известным ожидаемым результатом.
- **Компромисс:** более глубокое и медленное ревью с проверкой инвариантов снижает риск скрытых ошибок, попадающих в продакшен-отчётность, но замедляет скорость поставки отчётов и требует больше времени старшего аналитика; для разового низкорискового ad-hoc запроса такой уровень строгости может быть избыточным, тогда как для запроса, питающего регулярный дашборд для руководства, экономия времени на ревью создаёт неприемлемый риск.

**Пример / кейс**
```sql
-- Вопрос ревьюера к автору: "как ты убедился, что здесь нет fan-out?"
SELECT COUNT(*), COUNT(DISTINCT order_id) FROM order_items; -- проверка перед JOIN к orders
```
Проверка: ревьюер должен воспроизвести итоговую метрику на небольшом контрольном подмножестве данных вручную (например, 3-5 заказов) и сравнить с тем, что выдаёт запрос автора на том же подмножестве.

### 85. [Q-04-01-0085] SQL-анализ показал сильную корреляцию между использованием новой функции продукта и повышенным удержанием пользователей. Руководство хочет на основе этого немедленно сделать функцию обязательной для всех. Как ответить на это предложение?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единственно верного технического ответа нет, но методологически необходимо объяснить руководству, что наблюдательная корреляция из SQL-запроса не доказывает причинно-следственную связь — пользователи, которые сами выбрали использовать функцию, вероятно, систематически отличаются от тех, кто не стал её использовать (смещение самоселекции), и предложить способ получить более причинно-обоснованный ответ, например, контролируемый эксперимент.

**Разбор**
- **Как это работает:** корреляция, найденная агрегирующим SQL-запросом («пользователи функции X удерживаются на Y% лучше»), в равной степени может объясняться тем, что функция действительно помогает удержанию, или тем, что более вовлечённые/мотивированные пользователи и так более склонны оставаться в продукте и попутно более склонны пробовать новые функции — без контроля этого смешивающего фактора эти две причины SQL-запросом неразличимы.
- **На практике:** конструктивный ответ руководству — не просто «это не доказывает причинность» (это правда, но не помогает принять решение), а конкретное предложение: провести A/B-тест, где включение функции рандомизировано, а не выбрано пользователем, что устраняет смещение самоселекции и даёт возможность оценить причинный эффект; если полноценный эксперимент невозможен в срок, можно предложить более слабые, но менее смещённые подходы (например, сравнение по времени до и после принудительного включения функции для случайной подгруппы).
- **Частые ошибки:** аналитик либо соглашается с причинной интерпретацией, чтобы не создавать конфликт с решением руководства, либо категорично отказывается давать любую рекомендацию, ссылаясь на «корреляция не причинность», не предлагая конструктивного пути проверки; оба варианта не помогают бизнесу принять обоснованное решение.
- **Компромисс:** быстрый переход к обязательному включению функции без проверки причинности рискует закрепить неэффективное или даже вредное изменение для части пользователей, тогда как полноценный эксперимент требует времени и инфраструктуры для рандомизации, которой может не быть прямо сейчас — явное обсуждение этого компромисса (скорость решения против надёжности вывода) с руководством уместнее, чем одностороннее решение аналитика.

**Пример / кейс**
```sql
-- Наблюдательное сравнение, которое НЕ доказывает причинность
SELECT used_feature, AVG(retained_90d::int) AS retention_rate
FROM users
GROUP BY used_feature;
```
Проверка: предложить рандомизированный дизайн — `SELECT variant, AVG(retained_90d::int) FROM experiment_users WHERE experiment_id = 'feature_x_rollout' GROUP BY variant` — где `variant` присвоен случайно, а не выбран пользователем, и явно сравнить оба подхода перед руководством.

### 86. [Q-04-01-0086] После изменения логики трекинга событий (например, перехода на новую систему аналитики) временной ряд метрики показывает резкий скачок, не связанный с реальным изменением в продукте. Как реконструировать сопоставимую историю в SQL и задокументировать допущения?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единственно надёжного способа «бесшовно склеить» ряд через разрыв логики трекинга не существует: можно либо держать два параллельных ряда с явной пометкой методологии (до/после) без искусственного сглаживания, либо попытаться оценить и применить корректирующий коэффициент на основе периода параллельного замера обеими системами, если такой период есть — в обоих случаях нужно явно документировать допущение и его неопределённость, а не представлять скорректированный ряд как эквивалентный исходным данным.

**Разбор**
- **Как это работает:** скачок в ряду после смены трекинга обычно означает, что старая и новая система по-разному определяют или фиксируют одно и то же событие (другая логика дедупликации, другой момент фиксации, другой набор фильтруемых ботов); без периода, где обе системы работали параллельно на одних и тех же реальных событиях, невозможно объективно вычислить точный коэффициент пересчёта — любая такая корректировка — лишь оценка с неопределённостью.
- **На практике:** если есть период параллельного запуска (A/B сравнение старой и новой системы на одном трафике), можно в SQL вычислить эмпирическое соотношение между системами на этом периоде и использовать его для грубой реконструкции масштаба старого ряда; если такого периода нет, честнее показывать график с явным визуальным разделением (вертикальная линия на дату смены логики, разные подписи методологии) и избегать расчёта показателей типа «рост год к году», пересекающих эту границу напрямую.
- **Частые ошибки:** применяют единый постоянный коэффициент пересчёта без учёта того, что соотношение старой и новой системы учёта может само меняться со временем (например, доля ботов в трафике не постоянна), выдавая точечную оценку за точный исторический пересчёт; скрывают от стейкхолдеров сам факт разрыва методологии, показывая сглаженный график без пояснений, из-за чего при повторном обнаружении разрыва доверие к аналитике снижается.
- **Компромисс:** корректировка ряда делает графики визуально более читаемыми и упрощает коммуникацию тренда, но вносит дополнительную неопределённость и риск неверной интерпретации, если допущение коэффициента окажется неточным; отказ от корректировки сохраняет честность данных, но требует от аудитории дашборда дополнительного усилия для правильной интерпретации разрыва — выбор зависит от того, для какой аудитории и с какой целью строится отчёт.

**Пример / кейс**
```sql
SELECT DATE_TRUNC('day', event_time) AS day, tracking_version, COUNT(*) AS events_cnt
FROM events
WHERE event_time BETWEEN '2024-05-01' AND '2024-05-14' -- период параллельного трекинга
GROUP BY 1, 2
ORDER BY 1, 2;
```
Проверка: если соотношение `events_cnt` старой к новой системе существенно нестабильно по дням периода параллельного замера, это сигнал, что единый поправочный коэффициент недостаточно надёжен, и нужно явно отразить эту неопределённость в документации к ряду.

### 87. [Q-04-01-0087] Стейкхолдер просит срочный одноразовый SQL-отчёт "прямо сейчас", хотя аналогичные запросы поступают от разных людей еженедельно уже несколько месяцев. Как расставить приоритеты между быстрым ad-hoc ответом и инвестицией в многоразовый дашборд/пайплайн?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единственно правильного решения нет: краткосрочно стоит закрыть срочный запрос, чтобы не блокировать текущую бизнес-потребность, но параллельно нужно явно зафиксировать повторяемость такого типа вопроса и принять осознанное решение о создании многоразового решения на основе накопленной частоты запроса и его стоимости в человеко-часах, а не оставлять это неявным и постоянно повторяющимся источником отвлечения.

**Разбор**
- **Как это работает:** каждый отдельный ad-hoc SQL-запрос может казаться дешёвым («это займёт 20 минут»), но при регулярном повторении одного и того же типа вопроса суммарная стоимость этих 20-минутных ответов за месяцы может легко превысить стоимость разработки одного дашборда или автоматизированного отчёта, который стейкхолдеры смогут обновлять сами без участия аналитика.
- **На практике:** полезная практика — вести лёгкий учёт повторяющихся ad-hoc запросов (хотя бы простым списком: кто спросил, о чём, когда) и периодически (например, раз в месяц) пересматривать его, чтобы выявить кандидатов на автоматизацию по частоте и суммарному затраченному времени, а не принимать решение о приоритизации интуитивно в момент каждого отдельного запроса.
- **Частые ошибки:** аналитик продолжает закрывать один и тот же тип запроса вручную месяцами «потому что сейчас нет времени сделать дашборд», что на деле обходится дороже, чем разовая инвестиция; либо, наоборот, бросается делать полноценный дашборд при первом же повторении запроса, не оценив, действительно ли вопрос будет повторяться регулярно или это было случайное совпадение.
- **Компромисс:** инвестиция в многоразовый дашборд требует отвлечения ресурса от других задач сейчас ради экономии времени в будущем, и это решение оправдано только при достаточной уверенности в повторяемости запроса; если частота или состав вопроса нестабильны (разные стейкхолдеры спрашивают слегка разные вещи под видом «того же отчёта»), инвестиция в негибкий дашборд может оказаться потраченной впустую, и возможно разумнее сделать более общий, параметризуемый запрос, а не узкоспециализированный дашборд.

**Пример / кейс**
```sql
-- Лёгкий лог ad-hoc запросов для последующего анализа повторяемости
INSERT INTO adhoc_request_log (requested_by, topic, requested_at, time_spent_minutes)
VALUES ('head_of_sales', 'monthly_regional_revenue', CURRENT_TIMESTAMP, 20);
```
Проверка: по итогам квартала выгрузить `SELECT topic, COUNT(*), SUM(time_spent_minutes) FROM adhoc_request_log GROUP BY topic ORDER BY 3 DESC` и использовать как объективный аргумент при обсуждении приоритетов с руководством.

### 88. [Q-04-01-0088] Как спроектировать идемпотентный инкрементальный загрузочный паттерн (MERGE/UPSERT) для одной и той же логической таблицы, учитывая различия между PostgreSQL, ClickHouse и BigQuery?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единого кода, работающего одинаково во всех трёх системах, не существует: в PostgreSQL и BigQuery есть относительно прямой `MERGE`/`INSERT ... ON CONFLICT`, тогда как в ClickHouse идемпотентное обновление обычно достигается иначе — через движки типа `ReplacingMergeTree`/`CollapsingMergeTree` с последующим чтением через `FINAL` или явной дедупликацией, а не через классический построчный `UPDATE`; выбор конкретной техники определяется возможностями конкретной СУБД, а не единым паттерном.

**Разбор**
- **Как это работает:** идемпотентность загрузки означает, что повторный запуск одного и того же инкрементального шага загрузки (например, из-за сбоя и повторной попытки) не создаёт дублей и не искажает данные; в PostgreSQL это естественно достигается через `INSERT ... ON CONFLICT (key) DO UPDATE`, который атомарно обновляет существующую строку по уникальному ключу вместо создания новой. ClickHouse оптимизирован для аппенд-записи и не поддерживает эффективные построчные обновления в традиционном смысле — поэтому там идемпотентность достигается записью новой версии строки с последующей дедупликацией на чтении, а не изменением существующей строки на месте.
- **На практике:** при проектировании инкрементального пайплайна важно заранее решить, в какой из систем будет выполняться эта логика, и подбирать технику конкретно под неё, а не пытаться написать «универсальный» SQL, который одинаково хорошо работает везде — попытки абстрагироваться от различий диалектов на таком уровне обычно приводят к неоптимальному или вовсе неработающему решению в одной из систем.
- **Частые ошибки:** переносят паттерн `MERGE`/`UPSERT` из PostgreSQL в ClickHouse буквально, ожидая такого же поведения атомарного обновления строки, и не понимают, почему результат на чтении без `FINAL` показывает задвоенные записи; не предусматривают обработку конкурентных повторных запусков одного и того же инкрементального шага (например, два параллельных ретрая одной загрузки), что может создать состояние гонки даже при формально идемпотентном SQL.
- **Компромисс:** построчный `UPSERT` в PostgreSQL прост и нагляден, но плохо масштабируется на очень большие объёмы частых обновлений; аппенд-подход ClickHouse масштабируется лучше для больших объёмов, но требует либо постоянного использования `FINAL` (с его накладными расходами при чтении), либо явной периодической фоновой дедупликации — выбор зависит от объёма данных, частоты обновлений и допустимой сложности инфраструктуры.

**Пример / кейс**
```sql
-- PostgreSQL: идемпотентный upsert
INSERT INTO customer_dim (customer_id, region, updated_at)
VALUES (123, 'EU', now())
ON CONFLICT (customer_id) DO UPDATE SET region = EXCLUDED.region, updated_at = EXCLUDED.updated_at;

-- ClickHouse: добавление новой версии + дедупликация на чтении
SELECT customer_id, argMax(region, updated_at) AS region
FROM customer_dim_events GROUP BY customer_id;
```
Проверка: повторно выполнить тот же шаг загрузки (имитируя повторную попытку после сбоя) и убедиться, что итоговое количество строк по ключу (`customer_id`) и значения метрик не изменились по сравнению с однократным запуском.

### 89. [Q-04-01-0089] Отдел продаж и отдел продукта по-разному определяют метрику "активная сделка" в своих SQL-запросах к одной и той же таблице CRM, что приводит к конфликту цифр на совместной встрече. Как подойти к стандартизации определения с учётом интересов обоих стейкхолдеров?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единого «правильного» определения метрики, навязанного одной командой другой, обычно не существует: нужно сначала явно выяснить в SQL, в чём конкретно расходятся два определения (разные статусы, разные временные окна, разные фильтры по типу сделки), а затем вместе со стейкхолдерами решить, нужно ли одно общее определение или два осознанно названных разных показателя для разных целей.

**Разбор**
- **Как это работает:** конфликт цифр почти всегда можно декомпозировать до конкретных различий в `WHERE`-условиях двух запросов — например, отдел продаж может считать «активной» любую сделку без финального статуса, а отдел продукта — только те, где было взаимодействие за последние 30 дней; SQL-сравнение двух запросов построчно (через `FULL JOIN` по id сделки с выводом обоих статусов) быстро показывает природу и масштаб расхождения, переводя эмоциональный спор о цифрах в конкретный предметный разговор.
- **На практике:** после выявления технической причины расхождения ключевая работа аналитика — фасилитировать разговор между двумя командами о том, действительно ли им нужна одна и та же метрика (тогда стоит договориться об одном определении и обе команды меняют свои запросы) или они по сути измеряют разные, но похожно называемые вещи (тогда решение — явно переименовать метрики, например, «сделки в работе» для продаж и «вовлечённые сделки» для продукта, чтобы разница была видна из названия, а не обнаруживалась только при сравнении цифр).
- **Частые ошибки:** аналитик пытается единолично решить, какое определение «правильнее», без привлечения обеих команд к обсуждению, что создаёт ощущение несправедливости и подрывает доверие к будущим рекомендациям; ограничивается технической демонстрацией различия в SQL без доведения разговора до конкретного организационного решения (одна метрика или две по-разному названные).
- **Компромисс:** унификация в одно определение снижает путаницу, но требует, чтобы одна (или обе) команды изменили привычный способ измерения, что может плохо отражаться на их внутренней отчётности задним числом; сохранение двух разных метрик с чёткими названиями избегает этого конфликта, но требует дисциплины в коммуникации, чтобы никто не путал и не смешивал эти два похожих, но разных числа в презентациях.

**Пример / кейс**
```sql
SELECT a.deal_id, a.status AS sales_view_status, b.last_activity_date,
       CASE WHEN a.status != 'closed' THEN 'active_sales' END AS sales_flag,
       CASE WHEN b.last_activity_date >= CURRENT_DATE - 30 THEN 'active_product' END AS product_flag
FROM deals a
LEFT JOIN deal_activity b ON b.deal_id = a.deal_id;
```
Проверка: посчитать количество сделок, где `sales_flag` и `product_flag` расходятся (одна из меток пустая, другая заполнена) — это даёт конкретный, обсуждаемый с обеими командами список примеров расхождения, а не абстрактный спор об итоговых числах.

### 90. [Q-04-01-0090] Аналитическая команда растёт с 2 до 15 человек за год, и качество SQL-кода в общих репортах стало неоднородным. Как выстроить практику (шаблоны, тестирование, документация) для масштабирования SQL-культуры без чрезмерной бюрократии?

**Направление:** Data Analyst
**Тема:** SQL и работа с реляционными базами данных: SELECT, JOIN, GROUP BY, оконные функции, CTE, подзапросы, работа с датами и NULL, оптимизация запросов, диалекты (PostgreSQL, ClickHouse, BigQuery и др.)
**Уровень:** Senior

**Короткий ответ**
Единого готового набора правил, подходящего любой команде, нет: обычно работает постепенное введение небольшого числа высокоценных практик (шаблоны частых запросов/CTE, базовые автоматические проверки качества данных, минимальная документация по ключевым метрикам) с приоритетом на то, что реально предотвращает повторяющиеся ошибки в этой конкретной команде, а не на копирование процесса «как положено» из более крупной организации.

**Разбор**
- **Как это работает:** при росте команды неявные договорённости («мы все и так знаем, как тут считать выручку»), работавшие при 2 аналитиках, перестают масштабироваться — новые сотрудники не имеют контекста и воспроизводят типичные ошибки (fan-out, забытый `COALESCE`, несогласованные определения метрик), потому что эти знания никогда не были формализованы. Внедрение шаблонов (переиспользуемые CTE для стандартных сущностей, задокументированные соглашения об обработке NULL и дат) и базовых автоматических тестов данных (проверка уникальности ключей, отсутствия неожиданных NULL, соответствия контрольным суммам) ловит именно эти повторяющиеся классы ошибок на раннем этапе.
- **На практике:** внедрение стоит начинать с 2-3 самых частых и дорогостоящих по последствиям проблем (например, если fan-out через JOIN уже несколько раз приводил к неверным цифрам в отчётах для руководства — начать с обязательной проверки уникальности ключей перед JOIN как часть code review чек-листа), а не пытаться сразу внедрить полный набор практик уровня зрелой data-платформы, который будет восприниматься командой как чрезмерная бюрократия и тормозить повседневную работу.
- **Частые ошибки:** копируют процесс тестирования и документации из статьи или из опыта другой, гораздо более крупной компании без адаптации к текущему размеру и зрелости команды, что создаёт сопротивление и формальное, а не содержательное соблюдение процесса; вводят стандарты только «сверху» без вовлечения самой команды в их формулирование, из-за чего практики воспринимаются как чужеродные и быстро перестают соблюдаться.
- **Компромисс:** более формализованные практики (шаблоны, автотесты, обязательное ревью) снижают частоту ошибок и облегчают онбординг новых сотрудников, но требуют времени на внедрение и поддержку, а также неизбежно немного замедляют скорость поставки отдельных отчётов — правильный баланс зависит от стадии роста команды, критичности отчётов для бизнеса и от того, сколько реальных инцидентов с качеством данных уже произошло; для только начавшей расти команды из 2-3 человек избыточный процесс может принести больше вреда (демотивация, бюрократия), чем пользы.

**Пример / кейс**
```sql
-- Пример минимального автоматического теста качества данных перед публикацией отчёта
SELECT 'duplicate_order_id' AS check_name, COUNT(*) AS failures
FROM (SELECT order_id FROM orders GROUP BY order_id HAVING COUNT(*) > 1) t
UNION ALL
SELECT 'negative_amount', COUNT(*) FROM orders WHERE amount < 0;
```
Проверка: такой запрос можно запускать автоматически перед обновлением ключевых дашбордов — если `failures > 0` хотя бы в одной строке, публикацию отчёта стоит приостановить до расследования, а не выпускать с потенциально искажёнными цифрами.
