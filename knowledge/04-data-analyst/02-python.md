### 91. [Q-04-02-0091] Что такое Series и DataFrame в pandas и чем они отличаются друг от друга?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
Series — одномерный массив значений с индексом (по сути один столбец), а DataFrame — двумерная таблица из нескольких Series, выровненных по общему индексу строк.

**Разбор**
- **Как это работает:** Series хранит однородные (или object) значения плюс метки индекса для доступа по ключу; DataFrame — это набор именованных столбцов-Series, каждый со своим dtype, но с общим индексом строк.
- **На практике:** df['col'] возвращает Series, а df[['col']] — DataFrame из одного столбца; это различие важно при построении цепочек методов, где следующий метод ожидает конкретный тип.
- **Частые ошибки:** путают df['col'] и df[['col']], из-за чего код падает на методах, специфичных для DataFrame; забывают, что арифметика между двумя Series выравнивается по индексу, а не по позиции, и при несовпадающих индексах получаются NaN вместо ожидаемого результата.

**Пример / кейс**
```python
import pandas as pd
s = pd.Series([10, 20, 30], index=['a', 'b', 'c'])
df = pd.DataFrame({'value': s, 'flag': [True, False, True]})
print(type(df['value']))    # <class 'pandas.core.series.Series'>
print(type(df[['value']]))  # <class 'pandas.core.frame.DataFrame'>
```
Проверка: вывод type() подтверждает, что одинарные и двойные скобки дают разные типы объекта.

**Уровень:** Junior

**Короткий ответ**
Файл читают через pd.read_csv(), а первичное знакомство с данными делают через head(), info() и describe(), чтобы увидеть структуру, типы столбцов и наличие пропусков.

**Разбор**
- **Как это работает:** read_csv парсит текстовый файл и пытается автоматически определить типы столбцов; head() показывает первые строки, info() выводит dtype и число непустых значений по каждому столбцу, describe() считает описательную статистику по числовым столбцам.

```python
import pandas as pd
df = pd.read_csv('sales.csv', sep=';', encoding='utf-8')
print(df.shape)
print(df.info())
```
Проверка: df.info() должен показать ожидаемое число столбцов без "Unnamed: 0" и dtype, соответствующий смыслу столбца (даты — не object, суммы — не object).

### 93. [Q-04-02-0093] Как выбрать строки по условию и одновременно нужные столбцы в pandas?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
Для фильтрации по условию используют булеву маску, а для одновременного выбора строк и столбцов по условию и названиям — df.loc[маска, список_столбцов].

**Разбор**
- **Как это работает:** булева маска — это Series True/False той же длины, что и DataFrame; df[mask] оставляет строки с True, а df.loc[mask, cols] дополнительно ограничивает набор столбцов за один проход.
- **На практике:** предпочтительно писать df.loc[df['amount'] > 0, ['id', 'amount']] одной операцией, а не выбирать сначала строки, а потом столбцы через df[mask][['id','amount']] — это избегает цепочечной индексации и связанных с ней предупреждений и неоднозначностей.
- **Частые ошибки:** пытаются присвоить значения через df[mask]['col'] = x и получают SettingWithCopyWarning, потому что неясно, работает ли код с копией или с видом исходных данных; забывают скобки при объединении условий через & и |, из-за чего Python неправильно трактует приоритет операторов.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'id': [1, 2, 3, 4], 'amount': [100, -50, 200, 0]})
positive = df.loc[df['amount'] > 0, ['id', 'amount']]
print(positive)
```
Проверка: результат должен содержать только строки id=1 и id=3, что легко сверить по исходным значениям amount глазами.

### 94. [Q-04-02-0094] В чём разница между loc и iloc в pandas и когда использовать каждый из них?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
loc выбирает данные по меткам индекса и названиям столбцов, а iloc — по целочисленным позициям, независимо от того, какие метки реально стоят в индексе.

**Разбор**
- **Как это работает:** loc[a:b] включает обе границы диапазона, потому что это метки, а не позиции; iloc[a:b] ведёт себя как обычный Python-срез и не включает правую границу.
- **На практике:** loc удобен, когда индекс содержательный (ID, даты), а iloc — когда важна именно позиция строки, например "взять первые N строк" независимо от значений индекса; после фильтрации или сортировки полезно вызывать reset_index(), если дальше планируется позиционный доступ.
- **Частые ошибки:** обращаются к loc[1], думая, что это вторая строка по счёту, хотя после фильтрации метки индекса могут быть произвольными и такой метки может не быть вовсе; путают включительные границы loc и полуоткрытые границы iloc при срезах, получая на одну строку больше или меньше, чем ожидали.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'val': [10, 20, 30, 40]}, index=[5, 6, 7, 8])
print(df.iloc[1])   # вторая строка по позиции: индекс 6, val 20
print(df.loc[6])    # строка с меткой индекса 6: val 20
```
Проверка: df.loc[1] на этом DataFrame вызовет KeyError, так как метки 1 в индексе нет — это наглядно показывает отличие от iloc[1].

### 95. [Q-04-02-0095] Как посчитать базовую описательную статистику для числового столбца в pandas?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
Базовую статистику получают через df['col'].describe() или отдельные методы mean(), median(), std(), min(), max(), которые по умолчанию игнорируют пропуски.

**Разбор**
- **Как это работает:** describe() для числового столбца считает count, mean, std, min, 25/50/75 перцентили и max; count показывает число непустых значений, что сразу даёт понять, есть ли пропуски.
- **На практике:** среднее чувствительно к выбросам, медиана — устойчивее; перед интерпретацией стоит сравнить mean и median, а также посмотреть на min/max, чтобы заметить аномальные значения (отрицательные суммы, нулевые возраста и так далее).
- **Частые ошибки:** считают describe() достаточным анализом без визуализации распределения (гистограммы, boxplot), хотя одинаковые mean/median могут скрывать бимодальное распределение; забывают, что describe() по умолчанию игнорирует NaN, и интерпретируют count как общее число строк в таблице.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'amount': [100, 150, 200, None, 100000]})
print(df['amount'].describe())
```
Проверка: count покажет 4 (не 5, из-за пропуска), а резкий разрыв между 75-м перцентилем и max сигнализирует о потенциальном выбросе 100000.

### 96. [Q-04-02-0096] Что такое NumPy-массив и чем он отличается от обычного списка Python?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
NumPy-массив (ndarray) хранит однородные данные одного типа в непрерывном блоке памяти, что позволяет выполнять векторизованные операции быстрее и компактнее, чем над обычным списком Python.

**Разбор**
- **Как это работает:** список Python хранит ссылки на произвольные объекты, и операции над ним выполняются через интерпретируемый цикл; ndarray хранит значения одного dtype подряд в памяти, а операции (сложение, умножение) реализованы в скомпилированном C-коде и применяются сразу ко всему массиву.
- **На практике:** для числовых расчётов на больших объёмах данных операции с массивами NumPy в разы быстрее, чем цикл for по списку; при этом смешивание типов в массиве (например, числа и строки) приводит к dtype=object и потере преимущества в скорости.
- **Частые ошибки:** складывают списки оператором + и получают конкатенацию вместо поэлементного сложения, в отличие от массивов NumPy, где + складывает поэлементно; не приводят входные данные к числовому dtype и удивляются, почему векторизация не ускоряет код.

**Пример / кейс**
```python
import numpy as np
a = [1, 2, 3]
b = np.array([1, 2, 3])
print(a + a)   # [1, 2, 3, 1, 2, 3]
print(b + b)   # [2 4 6]
```
Проверка: два вывода наглядно различаются — конкатенация списка против поэлементного сложения массива, что и объясняет разницу поведения.

### 97. [Q-04-02-0097] Что такое broadcasting в NumPy и как оно работает на простом примере?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
Broadcasting — это механизм NumPy, который позволяет выполнять поэлементные операции между массивами разной формы, автоматически «растягивая» меньший массив без физического копирования данных.

**Разбор**
- **Как это работает:** NumPy сравнивает формы массивов справа налево; если размерность равна 1 или отсутствует, она расширяется до нужного размера виртуально, без копирования памяти, и только затем выполняется поэлементная операция.
- **На практике:** broadcasting удобен для операций вида "вычесть среднее по столбцу из каждой строки" или "умножить таблицу на вектор коэффициентов"; это избавляет от явных циклов и ускоряет вычисления на больших массивах.
- **Частые ошибки:** путают формы массивов и получают не ту ось broadcasting (например, вычитают построчно вместо постолбцового среднего), получая численно валидный, но содержательно неверный результат; не проверяют shape массивов перед операцией, из-за чего ошибка несовместимости форм падает глубоко в коде.

**Пример / кейс**
```python
import numpy as np
matrix = np.array([[1, 2, 3], [4, 5, 6]])
col_mean = matrix.mean(axis=0)
centered = matrix - col_mean
print(col_mean)    # [2.5 3.5 4.5]
print(centered)
```
Проверка: col_mean имеет форму (3,), а вычитание из матрицы формы (2,3) работает благодаря broadcasting построчно; сумма centered по каждому столбцу должна быть близка к нулю.

### 98. [Q-04-02-0098] Как найти количество и долю пропущенных значений в каждом столбце DataFrame?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
Количество пропусков по столбцам получают через df.isna().sum(), а долю — разделив на df.shape[0] или умножив на 100 для процентов.

**Разбор**
- **Как это работает:** isna() возвращает DataFrame той же формы из True/False, где True означает пропуск (NaN, None, NaT); sum() по умолчанию считает по столбцам (axis=0), складывая True как 1.
- **На практике:** долю пропусков полезно смотреть именно в процентах и сортировать по убыванию, чтобы сразу увидеть самые проблемные столбцы; также стоит проверить isna().sum(axis=1), чтобы понять, есть ли строки с массовыми пропусками сразу по многим полям.
- **Частые ошибки:** считают df.isnull().sum() одинаковым для всех типов "пропусков", хотя пустая строка '' или строка "N/A" не распознаются как NaN и не попадут в счёт без предварительной нормализации значений; делают выводы о пропусках только по общему числу строк, не учитывая, что часть столбцов могла быть пропущена не случайно (например, скидка пустая, если скидки не было).

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'a': [1, None, 3], 'b': [None, None, 'x']})
missing = df.isna().sum()
missing_pct = (missing / len(df) * 100).round(1)
print(missing_pct)
```
Проверка: для столбца 'a' ожидается 33.3%, для 'b' — 66.7%, что соответствует количеству None в исходных данных.

### 99. [Q-04-02-0099] Какие есть способы заполнить пропуски в pandas и когда уместно использовать среднее, медиану или константу?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
Пропуски заполняют через fillna() значением, статистикой (mean, median) или методом распространения соседних значений (ffill/bfill); выбор зависит от природы данных и причины пропуска.

**Разбор**
- **Как это работает:** fillna(value) подставляет заданное значение везде, где NaN; fillna(df['col'].median()) подставляет медиану столбца; ffill/bfill берут последнее известное или следующее значение, что уместно для временных рядов.
- **На практике:** среднее подходит для симметричных распределений без сильных выбросов, медиана устойчивее к выбросам и асимметрии; константу (например, 0 или "unknown") используют, когда пропуск сам по себе содержателен (например, скидки не было); перед выбором метода стоит понять, почему значение отсутствует.
- **Частые ошибки:** автоматически заполняют все числовые пропуски средним без проверки распределения, искажая дисперсию и корреляции; заполняют пропуски до разделения на train/test в задачах моделирования, что приводит к утечке информации; путают, что fillna() без inplace=True не изменяет исходный DataFrame, если результат не сохранён в переменную.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'price': [100, 150, None, 90000, 120]})
median_fill = df['price'].fillna(df['price'].median())
mean_fill = df['price'].fillna(df['price'].mean())
print(median_fill.tolist(), mean_fill.tolist())
```
Проверка: заполнение медианой даст более разумное значение (около 125), тогда как заполнение средним будет сильно искажено выбросом 90000.

### 100. [Q-04-02-0100] Когда уместно просто удалить строки с пропусками (dropna) и какие риски это несёт?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
dropna() уместен, когда пропусков мало и они распределены случайно относительно анализа; если пропусков много или они связаны с конкретным сегментом, удаление строк может сильно искажать выборку.

**Разбор**
- **Как это работает:** dropna() по умолчанию удаляет строку, если хотя бы в одном столбце есть NaN (how='any'); параметр subset ограничивает проверку конкретными столбцами, а how='all' удаляет строку только если все значения пропущены.
- **На практике:** перед удалением стоит посчитать, какую долю строк это затронет, и проверить, не концентрируются ли пропуски в конкретном сегменте (например, в одной стране или у новых пользователей) — тогда удаление введёт систематическое смещение, а не просто уменьшит шум.
- **Частые ошибки:** удаляют все строки с пропуском хотя бы в одном из многих столбцов, хотя для текущего анализа важен только один конкретный столбец, в результате теряется гораздо больше данных, чем необходимо; не документируют, сколько строк и почему были удалены, что затрудняет воспроизведение и объяснение итоговых чисел.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'user_id': [1, 2, 3, 4], 'country': ['RU', None, 'RU', None], 'revenue': [10, 20, 30, 40]})
clean = df.dropna(subset=['country'])
print(clean)
```
Проверка: до удаления 4 строки, после — 2; если удалённые строки относятся к конкретному сегменту (например, все без страны оказались новыми пользователями), стоит явно отметить это ограничение в выводах.

### 101. [Q-04-02-0101] Как найти и удалить полные дубликаты строк в DataFrame?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
Дубликаты находят через df.duplicated(), которая возвращает True для повторяющихся строк, а удаляют через df.drop_duplicates().

**Разбор**
- **Как это работает:** duplicated() по умолчанию сравнивает все столбцы и помечает True для всех повторных вхождений строки, кроме первого (keep='first'); drop_duplicates() использует ту же логику и возвращает DataFrame без повторов.
- **На практике:** перед удалением полезно посчитать df.duplicated().sum(), чтобы понять масштаб проблемы, и посмотреть на сами дубликаты через df[df.duplicated()], чтобы убедиться, что это действительно ошибка, а не легитимные одинаковые записи (например, два одинаковых заказа в один день — если они действительно разные события).
- **Частые ошибки:** удаляют дубликаты сразу без анализа причины их появления (повторная загрузка файла, джойн с размножением), из-за чего настоящая причина ошибки остаётся незамеченной; не указывают keep и не задумываются, какую из дублирующихся строк оставить, если они отличаются во времени обновления.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'order_id': [1, 2, 2, 3], 'amount': [100, 50, 50, 70]})
print(df.duplicated().sum())  # 1
clean = df.drop_duplicates()
print(clean)
```
Проверка: duplicated().sum() равен 1, а итоговый DataFrame содержит 3 строки вместо исходных 4.

### 102. [Q-04-02-0102] Что делает параметр subset в drop_duplicates и почему он важен для бизнес-ключей?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
subset указывает, по каким столбцам искать дубликаты, что критично, когда дубликатом нужно считать совпадение бизнес-ключа (например, order_id), а не полное совпадение всех столбцов.

**Разбор**
- **Как это работает:** без subset drop_duplicates сравнивает все столбцы, и строки, отличающиеся хотя бы в одном поле, не считаются дубликатами; с subset=['order_id'] сравнение идёт только по указанным столбцам, и строки с одинаковым order_id, но разными прочими полями, всё равно будут признаны дубликатами.
- **На практике:** если order_id должен быть уникальным, но у одной записи обновилось, например, поле status, полное сравнение строк не найдёт дубликат — нужен subset по бизнес-ключу; важно явно решить, какую версию оставить (keep='last' для самой свежей, если есть временная метка).
- **Частые ошибки:** проверяют уникальность только полным сравнением строк и делают вывод "дубликатов нет", хотя по бизнес-ключу дубликаты есть, просто отличаются неключевые поля; забывают отсортировать данные по времени обновления перед keep='last', из-за чего "последняя" строка определяется случайным порядком в файле, а не реальной хронологией.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({
    'order_id': [1, 1, 2],
    'status': ['created', 'paid', 'created'],
    'updated_at': ['2024-01-01', '2024-01-02', '2024-01-01']
})
by_key = df.drop_duplicates(subset=['order_id'], keep='last')
print(by_key)
```
Проверка: итоговая таблица содержит по одной строке на order_id, причём для order_id=1 остаётся строка со статусом 'paid' как последняя по порядку в данных.

### 103. [Q-04-02-0103] Как посчитать сумму и среднее по группам в pandas с помощью groupby?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
groupby('col') разбивает DataFrame на группы по значениям столбца, а последующий agg-метод (sum, mean и так далее) считает статистику внутри каждой группы отдельно.

**Разбор**
- **Как это работает:** groupby сам по себе не вычисляет ничего, а создаёт объект-группировку; вызов .sum(), .mean() или .agg(...) применяет функцию к каждой группе независимо и собирает результат в новый DataFrame или Series с группами в индексе.
- **На практике:** для нескольких статистик сразу удобно использовать .agg(['sum', 'mean', 'count']); после группировки результат часто приводят обратно к обычному DataFrame через reset_index(), чтобы было удобнее работать с группировочным столбцом как с обычной колонкой.
- **Частые ошибки:** применяют groupby к столбцам с пропусками в группировочном ключе — такие строки по умолчанию исключаются из результата в более старых версиях pandas (а в более новых есть параметр dropna=False), что может незаметно потерять часть данных; забывают, что среднее по группе также чувствительно к выбросам внутри группы, как и обычное среднее.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'category': ['A', 'A', 'B', 'B'], 'amount': [100, 200, 50, 150]})
summary = df.groupby('category')['amount'].agg(['sum', 'mean']).reset_index()
print(summary)
```
Проверка: для категории A сумма должна быть 300, среднее 150; для B сумма 200, среднее 100 — легко проверить вручную по исходным значениям.

### 104. [Q-04-02-0104] Чем отличается value_counts от groupby(...).size() при подсчёте количества строк по категориям?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
value_counts() — это быстрый способ посчитать частоты значений одного Series с сортировкой по убыванию по умолчанию, а groupby(...).size() — более общий инструмент, который можно использовать при группировке по нескольким столбцам сразу.

**Разбор**
- **Как это работает:** df['col'].value_counts() считает, сколько раз встречается каждое уникальное значение в столбце, и по умолчанию исключает NaN (есть параметр dropna=False, чтобы включить); groupby(['col1','col2']).size() считает количество строк в каждой комбинации значений нескольких столбцов.
- **На практике:** value_counts() удобен для быстрого взгляда на распределение одной категориальной переменной, а groupby+size — когда нужно посчитать количество по пересечению нескольких признаков (например, количество заказов по стране и статусу одновременно).
- **Частые ошибки:** используют value_counts() и забывают, что по умолчанию пропуски не считаются, из-за чего сумма частот меньше общего числа строк; путают size() и count() в groupby — size() считает число строк независимо от пропусков в конкретном столбце, а count() считает непустые значения по каждому столбцу отдельно, и для столбцов с пропусками результаты будут отличаться.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'country': ['RU', 'RU', 'US', None], 'status': ['paid', 'paid', 'paid', 'paid']})
print(df['country'].value_counts())            # RU: 2, US: 1 (без NaN)
print(df.groupby('country').size())             # аналогично, NaN исключён
```
Проверка: сумма value_counts() равна 3, хотя всего в таблице 4 строки — разница в 1 указывает на пропуск, который не попал в подсчёт.

### 105. [Q-04-02-0105] Как объединить две таблицы по общему ключу с помощью merge в pandas?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
pd.merge(df1, df2, on='key', how='inner') объединяет строки двух таблиц по совпадающим значениям ключевого столбца, оставляя по умолчанию только строки, где ключ найден в обеих таблицах.

**Разбор**
- **Как это работает:** merge сопоставляет строки по значениям указанного столбца (или нескольких столбцов в on), а параметр how задаёт тип соединения: inner оставляет только совпадения, left/right/outer управляют тем, что делать со строками без пары.
- **На практике:** перед merge полезно проверить df1['key'].nunique() и df2['key'].nunique() относительно длины таблиц, чтобы понять, ожидается ли связь один-к-одному или один-ко-многим, и сравнить размер результата с ожидаемым.
- **Частые ошибки:** не проверяют тип и регистр ключевого столбца в обеих таблицах (например, int vs str или 'RU' vs 'ru'), из-за чего merge не находит совпадений и теряет строки без видимой ошибки; не указывают явно how и получают inner по умолчанию, теряя строки, которые должны были остаться.

**Пример / кейс**
```python
import pandas as pd
orders = pd.DataFrame({'order_id': [1, 2, 3], 'user_id': [10, 20, 10]})
users = pd.DataFrame({'user_id': [10, 20], 'country': ['RU', 'US']})
merged = pd.merge(orders, users, on='user_id', how='inner')
print(merged)
```
Проверка: итоговая таблица должна содержать 3 строки (все заказы имеют совпадающего пользователя), с добавленным столбцом country.

### 106. [Q-04-02-0106] В чём разница между merge и concat в pandas?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
merge объединяет две таблицы по значению общего ключа (как JOIN в SQL), а concat просто складывает таблицы друг под другом или рядом по индексу, без логики сопоставления по ключу.

**Разбор**
- **Как это работает:** merge ищет соответствия между строками по значениям столбцов и может менять число строк в результате; concat(axis=0) соединяет таблицы по строкам (аналог UNION, но без удаления дублей по умолчанию), а concat(axis=1) — по столбцам, выравнивая по индексу.
- **На практике:** concat уместен, когда нужно просто "склеить" данные за разные периоды с одинаковой структурой столбцов (например, продажи за январь и февраль); merge нужен, когда данные о разных сущностях (заказы и пользователи) нужно связать по ключу.
- **Частые ошибки:** используют concat там, где нужен merge, и получают механическое объединение строк без сопоставления по смыслу; при concat по строкам не используют ignore_index=True, из-за чего в результате появляются повторяющиеся значения индекса, что потом ломает последующий доступ по loc.

**Пример / кейс**
```python
import pandas as pd
jan = pd.DataFrame({'day': [1, 2], 'sales': [100, 150]})
feb = pd.DataFrame({'day': [1, 2], 'sales': [120, 130]})
combined = pd.concat([jan, feb], ignore_index=True)
print(combined)
```
Проверка: итоговый DataFrame должен содержать 4 строки с непрерывным индексом 0..3, а не повторяющийся индекс 0,1,0,1.

### 107. [Q-04-02-0107] Как привести столбец с числами, прочитанными как строки, обратно к числовому типу?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
Столбец приводят через pd.to_numeric(df['col'], errors='coerce') или df['col'].astype(float), предварительно убедившись, что в данных нет нечисловых артефактов вроде пробелов или нестандартных разделителей.

**Разбор**
- **Как это работает:** astype(float) напрямую пытается преобразовать все значения и выбрасывает ошибку, если хотя бы одно значение не парсится как число; pd.to_numeric с errors='coerce' вместо ошибки подставляет NaN для непарсящихся значений, позволяя продолжить анализ и отдельно посчитать, сколько строк не удалось преобразовать.
- **На практике:** перед преобразованием стоит проверить уникальные "странные" значения в столбце (df['col'].unique()), чтобы понять источник проблемы — например, разделитель тысяч, запятая вместо точки или текстовые пометки типа "n/a"; после coerce обязательно считают df['col'].isna().sum(), чтобы не потерять данные незаметно.
- **Частые ошибки:** сразу применяют astype(float) без coerce и получают необработанное исключение на первой проблемной строке, даже не узнав, сколько их всего; применяют coerce и забывают проверить количество получившихся NaN, тихо теряя часть данных в последующих агрегатах.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'amount': ['100', '200', '1,500', 'n/a']})
df['amount_clean'] = pd.to_numeric(df['amount'].str.replace(',', ''), errors='coerce')
print(df)
print(df['amount_clean'].isna().sum())  # 1
```
Проверка: после очистки от запятых успешно преобразуются 3 значения, а 'n/a' превращается в NaN, что подтверждается isna().sum() равным 1.

### 108. [Q-04-02-0108] Чем в pandas отличаются NaN и None и как это важно учитывать при проверке пропусков?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
NaN — это специальное число с плавающей точкой для обозначения отсутствующего числового значения, а None — обычный объект Python для отсутствующего значения; pandas обычно приводит оба к единообразному представлению пропуска в большинстве операций и методов вроде isna().

**Разбор**
- **Как это работает:** в числовом столбце (float64) None автоматически преобразуется в NaN при создании Series; в столбце типа object (например, со строками) None может храниться как есть, но isna() и isnull() всё равно корректно распознают и NaN, и None, и NaT (пропуск в датах) как пропущенные значения.
- **На практике:** для практических целей достаточно пользоваться isna()/notna(), которые унифицированно обрабатывают все виды пропусков, не разбираясь вручную в том, что именно хранится в ячейке; важно не путать пропуск с пустой строкой '' или текстовым "None" — это разные вещи, которые isna() не поймает без предварительной замены.
- **Частые ошибки:** сравнивают значение с None напрямую через == None вместо pd.isna(), что не работает как ожидается для NaN (NaN == NaN даёт False); не замечают, что в столбце есть строковые "NaN"/"null"/"N/A" как текст, а не настоящий пропуск, и isna() их не находит.

**Пример / кейс**
```python
import pandas as pd
import numpy as np
s = pd.Series([1, None, np.nan, 'NaN'])
print(s.isna())
```
Проверка: isna() вернёт True для второго и третьего элементов (None и np.nan), но False для последнего элемента — строки "NaN" как текста, что показывает необходимость явной нормализации текстовых пометок перед проверкой пропусков.

### 109. [Q-04-02-0109] Как отсортировать DataFrame по нескольким столбцам с разным направлением сортировки?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
Сортировка по нескольким столбцам делается через df.sort_values(['col1', 'col2'], ascending=[True, False]), где списки столбцов и направлений должны соответствовать друг другу по порядку.

**Разбор**
- **Как это работает:** sort_values сначала сортирует по первому столбцу списка, а при совпадающих значениях — по следующему, и так далее; ascending принимает список той же длины, где каждый элемент относится к соответствующему столбцу.
- **На практике:** такая сортировка часто нужна для отчётов вида "сначала по категории по алфавиту, внутри категории — по убыванию суммы"; после сортировки полезно вызвать reset_index(drop=True), если дальнейшая логика ожидает последовательный индекс.
- **Частые ошибки:** передают одно значение ascending вместо списка, рассчитывая, что оно применится по-разному к разным столбцам, хотя на самом деле оно применится одинаково ко всем; забывают, что sort_values не меняет DataFrame "на месте" без inplace=True или сохранения результата в переменную.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'category': ['B', 'A', 'A', 'B'], 'amount': [50, 200, 100, 300]})
sorted_df = df.sort_values(['category', 'amount'], ascending=[True, False])
print(sorted_df)
```
Проверка: внутри категории A строки должны идти в порядке 200, затем 100, а внутри категории B — 300, затем 50, при этом категория A идёт раньше B.

### 110. [Q-04-02-0110] Как правильно объединить несколько условий фильтрации в pandas через & и | и какая тут частая синтаксическая ошибка?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
Каждое условие нужно заключать в отдельные скобки перед объединением через & (и) или | (или), иначе Python попытается применить побитовый оператор раньше сравнения и выбросит ошибку или даст неверный результат.

**Разбор**
- **Как это работает:** операторы & и | в Python имеют более высокий приоритет, чем операторы сравнения (>, ==, < и так далее), поэтому без скобок выражение df['a'] > 1 & df['b'] < 2 интерпретируется не так, как ожидает пользователь, и обычно вызывает ошибку.
- **На практике:** правильная запись выглядит как df[(df['a'] > 1) & (df['b'] < 2)]; для булевых условий в pandas нельзя использовать обычные and/or, потому что они ожидают единственное булево значение, а не поэлементный Series.
- **Частые ошибки:** пишут df[df['a'] > 1 and df['b'] < 2] и получают ValueError о неоднозначности истинности Series; забывают скобки вокруг отдельных условий при использовании & и |, получая TypeError или тихо неверный результат из-за иного порядка операций.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'a': [1, 2, 3], 'b': [5, 1, 4]})
filtered = df[(df['a'] > 1) & (df['b'] < 5)]
print(filtered)
```
Проверка: результат должен содержать только строки, где одновременно a>1 и b<5, то есть строки с a=2,b=1 и a=3,b=4; строку a=1 исключает первое условие.

### 111. [Q-04-02-0111] Как быстро получить сводку по пропускам сразу для всех столбцов и отсортировать её по убыванию доли пропусков?

**Короткий ответ**

- **На практике:** такую сводку обычно делают первым шагом при знакомстве с новой таблицей, чтобы сразу расставить приоритеты очистки данных; полезно также вывести её как DataFrame с двумя столбцами (имя столбца и процент), а не как Series, если планируется дальше использовать в отчёте.

```python
summary = (df.isna().mean() * 100).round(1).sort_values(ascending=False)

```

### 112. [Q-04-02-0112] Зачем фиксировать random seed (например, np.random.seed) в аналитическом коде?

**Уровень:** Junior

**Короткий ответ**
Фиксация seed делает результаты операций со случайностью (выборка, перемешивание, разбиение на группы) воспроизводимыми: при повторном запуске кода с тем же seed получаются те же "случайные" числа.

**Разбор**
- **Как это работает:** генераторы псевдослучайных чисел детерминированы относительно внутреннего состояния; seed задаёт стартовое состояние, поэтому последовательность "случайных" чисел полностью определяется значением seed, а не является настоящей случайностью.
- **На практике:** фиксация seed важна при df.sample(), train_test_split, симуляциях для A/B-тестов и любых расчётах, где результат должен быть проверяемым коллегой или воспроизводимым через время; это не делает выборку "правильной", а только повторяемой.
- **Частые ошибки:** фиксируют seed в одном месте кода (например, только для NumPy), но используют случайность одновременно из нескольких источников (встроенный random, NumPy, pandas), получая невоспроизводимый результат, потому что не все источники синхронизированы одним seed; считают, что одинаковый seed гарантирует "правильный" или "репрезентативный" результат, хотя он лишь гарантирует повторяемость.

**Пример / кейс**
```python
import numpy as np
np.random.seed(42)
sample1 = np.random.choice([1, 2, 3, 4, 5], size=3)
np.random.seed(42)
sample2 = np.random.choice([1, 2, 3, 4, 5], size=3)
print(sample1, sample2)
```
Проверка: sample1 и sample2 должны быть идентичны, что подтверждает воспроизводимость при одинаковом seed.

### 116. [Q-04-02-0116] Как простым способом найти потенциальные выбросы в числовом столбце с помощью правила межквартильного диапазона (IQR)?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
По правилу IQR выброс считается значением ниже Q1 минус 1.5×IQR или выше Q3 плюс 1.5×IQR, где IQR — это разница между 75-м и 25-м перцентилем.

**Разбор**
- **Как это работает:** Q1 и Q3 — это 25-й и 75-й перцентили распределения, IQR = Q3 − Q1; границы Q1 − 1.5×IQR и Q3 + 1.5×IQR образуют "нормальный" диапазон, а значения за его пределами помечаются как потенциальные выбросы.
- **На практике:** это простое и устойчивое к асимметрии правило удобно для быстрой разведочной проверки, но коэффициент 1.5 — условность, а не универсальный закон; для сильно скошенных распределений (например, доходы) правило может помечать как "выбросы" много законных значений.
- **Частые ошибки:** применяют правило IQR к явно нечисловому или категориальному распределению, где понятие выброса в принципе не применимо; автоматически удаляют все помеченные значения без содержательной проверки, хотя некоторые "выбросы" могут быть реальными и важными событиями (крупный корпоративный заказ), а не ошибками данных.

**Пример / кейс**
```python
import pandas as pd
s = pd.Series([10, 12, 11, 13, 12, 100])
q1, q3 = s.quantile(0.25), s.quantile(0.75)
iqr = q3 - q1
lower, upper = q1 - 1.5 * iqr, q3 + 1.5 * iqr
outliers = s[(s < lower) | (s > upper)]
print(lower, upper, outliers.tolist())
```
Проверка: значение 100 должно попасть в outliers, так как оно существенно превышает верхнюю границу, рассчитанную по основной массе значений вокруг 10–13.

### 117. [Q-04-02-0117] Зачем в pandas иногда нужно вызывать .copy() и что произойдёт, если забыть это сделать?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Junior

**Короткий ответ**
.copy() создаёт независимую копию данных, чтобы изменения в новом объекте не затрагивали исходный DataFrame; без неё часть операций может вернуть view (вид) на те же данные, и изменения отразятся на оригинале неожиданным образом.

**Разбор**
- **Как это работает:** некоторые операции в pandas (например, простой срез по столбцам) могут возвращать view — объект, ссылающийся на ту же память, что и исходный DataFrame, а не на новую копию; изменение такого view способно изменить и исходные данные, что и вызывает печально известный SettingWithCopyWarning.
- **На практике:** если планируется модифицировать производный DataFrame (добавлять столбцы, менять значения), а исходный должен остаться неизменным для дальнейших сравнений, стоит сразу явно вызвать .copy(); это особенно важно при создании "рабочих" версий таблицы для экспериментов с очисткой.
- **Частые ошибки:** игнорируют предупреждение SettingWithCopyWarning, считая его просто "шумом", хотя оно сигнализирует о реальном риске непредсказуемого поведения; вызывают .copy() избыточно на каждом шаге без необходимости, что расходует память на больших таблицах без реальной пользы.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'a': [1, 2, 3]})
subset = df[df['a'] > 1].copy()
subset['a'] = 0
print(df)       # исходный df не изменился
print(subset)   # а здесь a = 0
```
Проверка: после изменения subset исходный df должен остаться [1, 2, 3], что подтверждает независимость копии от оригинала.

### 119. [Q-04-02-0119] В чём разница между pivot_table и groupby в pandas и когда предпочтительнее каждый из них?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
groupby даёт более общий и гибкий инструмент агрегации с результатом в "длинном" формате, а pivot_table — это надстройка над groupby, сразу разворачивающая одну из группировочных переменных в столбцы, то есть удобна для получения "широкой" сводной таблицы.

**Разбор**
- **Как это работает:** pivot_table(values, index, columns, aggfunc) внутри фактически делает groupby по комбинации index и columns, а затем разворачивает значения columns в отдельные столбцы результата; groupby без columns оставляет результат в виде одного или нескольких уровней индекса без разворота.
- **На практике:** pivot_table удобен для отчётов вида "строки — месяцы, столбцы — категории, значения — сумма продаж", которые удобно читать визуально; groupby лучше подходит, когда результат нужен для дальнейших программных вычислений или объединения с другими таблицами, так как длинный формат проще обрабатывать дальше.
- **Частые ошибки:** забывают указать aggfunc в pivot_table и получают среднее по умолчанию там, где по смыслу нужна сумма или количество; создают широкую сводную таблицу для дальнейшего программного анализа, а не для визуального отчёта, что усложняет последующие join и группировки по сравнению с длинным форматом.

### 120. [Q-04-02-0120] Какие бывают типы merge (inner/left/right/outer) и чем они отличаются по итоговому набору строк?

**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
inner оставляет только строки с совпадением ключа в обеих таблицах, left и right сохраняют все строки соответствующей таблицы (дополняя NaN там, где пары не нашлось), а outer сохраняет все строки из обеих таблиц.

**Разбор**
- **Как это работает:** при каждом типе соединения pandas сначала находит совпадения ключей между таблицами; inner отбрасывает несовпавшие строки с обеих сторон, left добавляет к ним все непарные строки левой таблицы с NaN в столбцах правой, right — симметрично, outer объединяет оба набора непарных строк.
- **На практике:** left join часто используется, когда "главная" таблица — это, например, все заказы, а дополнительная информация о пользователе может отсутствовать для части из них; outer полезен для диагностики, чтобы увидеть все несовпадения сразу с обеих сторон.
- **Частые ошибки:** выбирают inner по умолчанию без явного размышления и теряют строки, которые по смыслу задачи должны были остаться (например, заказы без привязанного пользователя); не проверяют после merge количество новых NaN в добавленных столбцах, из-за чего пропуски, появившиеся из-за отсутствия пары, путают с пропусками, существовавшими изначально.

**Пример / кейс**
```python
import pandas as pd
orders = pd.DataFrame({'order_id': [1, 2, 3], 'user_id': [10, 20, 99]})
users = pd.DataFrame({'user_id': [10, 20], 'country': ['RU', 'US']})
left = pd.merge(orders, users, on='user_id', how='left')
print(left)
```
Проверка: итоговая таблица должна содержать все 3 заказа, при этом для user_id=99 (которого нет в users) столбец country будет NaN.

**Уровень:** Middle

**Короткий ответ**
Рост числа строк после merge почти всегда означает, что ключ объединения не уникален в одной из таблиц (связь один-ко-многим или многие-ко-многим), и для каждой совпадающей строки левой таблицы находится несколько строк правой, что "размножает" результат.

**Разбор**
- **Как это работает:** merge сопоставляет каждую строку левой таблицы со всеми строками правой, где совпал ключ; если ключ в правой таблице повторяется (например, у пользователя несколько адресов доставки), для одного заказа в результате появится несколько строк — по одной на каждый адрес.
- **На практике:** перед merge стоит проверить df2['key'].duplicated().sum() или df2['key'].value_counts(), чтобы понять, сколько раз повторяется ключ; после merge полезно сравнить len(result) с len(df1) — если они не совпадают при ожидаемой связи один-к-одному, это сигнал проблемы.
- **Частые ошибки:** не проверяют уникальность ключа перед merge и узнают о размножении строк только тогда, когда итоговая сумма метрики (например, общая выручка) оказывается больше, чем в источнике; "чинят" проблему добавлением drop_duplicates() после merge без понимания, какую именно дублирующуюся строку правой таблицы нужно оставить, что может привести к потере нужной информации.

**Пример / кейс**
```python
import pandas as pd
orders = pd.DataFrame({'order_id': [1, 2], 'user_id': [10, 20]})
addresses = pd.DataFrame({'user_id': [10, 10, 20], 'address': ['a1', 'a2', 'b1']})
merged = pd.merge(orders, addresses, on='user_id')
print(len(orders), len(merged))
```
Проверка: len(orders) равен 2, а len(merged) равен 3, потому что у user_id=10 два адреса — именно такая проверка числа строк до и после merge и выявляет проблему.

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
apply вызывает функцию отдельно для каждого элемента или строки через интерпретатор Python, тогда как векторизованные операции (например, встроенная арифметика pandas/NumPy) выполняются скомпилированным кодом сразу над всем массивом, что обычно намного быстрее на больших данных.

**Разбор**
- **Как это работает:** векторизованные операции (df['a'] + df['b'], str.contains, np.where) написаны на C и обрабатывают весь столбец за один проход без накладных расходов на вызов функции Python для каждой строки; apply(lambda row: ..., axis=1) для каждой строки создаёт отдельный объект Series и вызывает Python-функцию, что существенно медленнее на больших таблицах.
- **На практике:** apply оправдан, когда логику действительно нельзя выразить встроенными операциями — например, сложная условная логика, зависящая от нескольких столбцов одновременно нестандартным образом, или вызов внешней функции/API; для простых случаев обычно есть векторизованная альтернатива (np.where, np.select, str-методы, map со словарём).
- **Частые ошибки:** используют apply(axis=1) там, где достаточно np.where или простой арифметики, теряя кратный выигрыш в скорости на больших таблицах; не измеряют реальное время выполнения (%timeit) перед оптимизацией, оптимизируя код интуитивно вместо того, чтобы найти настоящее узкое место.

**Пример / кейс**
```python
import pandas as pd
import numpy as np
df = pd.DataFrame({'a': range(100000), 'b': range(100000)})
df['sum_apply'] = df.apply(lambda row: row['a'] + row['b'], axis=1)
df['sum_vec'] = df['a'] + df['b']
print(df['sum_apply'].equals(df['sum_vec']))
```
Проверка: результаты двух подходов должны совпасть (equals вернёт True), при этом замер времени через %timeit покажет, что векторизованная версия выполняется значительно быстрее apply.

**Уровень:** Middle

**Короткий ответ**
SettingWithCopyWarning сигнализирует, что изменение значения происходит на объекте, про который pandas не может гарантировать, является ли он копией или видом исходных данных; правильный способ — выполнять фильтрацию и присвоение в одной операции через .loc.

**Разбор**
- **Как это работает:** при цепочечной индексации вида df[mask]['col'] = value сначала создаётся промежуточный объект (результат df[mask]), а затем в него пытаются записать значение; pandas не гарантирует, что этот промежуточный объект — view на оригинал или отдельная копия, из-за чего присвоение может как сработать, так и не сработать, и выдаётся предупреждение.

- **Частые ошибки:** игнорируют предупреждение и продолжают работу, не проверив, действительно ли изменения применились к нужному объекту; "решают" проблему добавлением pd.options.mode.chained_assignment = None, что просто скрывает предупреждение, а не устраняет источник неоднозначности.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'a': [1, 2, 3], 'b': [10, 20, 30]})
df.loc[df['a'] > 1, 'b'] = 0
print(df)
```
Проверка: после операции строки с a>1 (вторая и третья) должны получить b=0, а строка с a=1 останется с b=10, без предупреждений в выводе.

**Разбор**
- **Как это работает:** category хранит уникальные значения один раз в "словаре" и использует компактные целочисленные коды для самих строк вместо повторения полной строки в каждой ячейке; downcast подбирает наименьший подходящий числовой подтип (например, int8 вместо int64), если диапазон значений это позволяет.
- **На практике:** category особенно эффективен для столбцов вроде страны, статуса заказа или категории товара, где уникальных значений в разы меньше числа строк; перед downcast числовых столбцов стоит убедиться, что в будущем в данные не попадут значения за пределами диапазона уменьшенного типа, иначе возможна потеря данных или переполнение.

```python
import pandas as pd

```

### 125. [Q-04-02-0125] В чём разница между groupby.transform и groupby.apply и когда предпочтительнее каждый из них?

**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
transform возвращает результат той же формы, что и исходные данные (по одному значению на каждую исходную строку, "размноженному" внутри группы), а apply может возвращать результат произвольной формы, включая свёрнутый до одной строки на группу.

**Разбор**
- **Как это работает:** transform применяет функцию к каждой группе и "растягивает" результат обратно на все строки этой группы, что удобно для добавления группового значения (например, среднего по группе) как нового столбца исходной таблицы без явного merge; apply более гибок, но менее предсказуем по форме результата и часто медленнее.

- **Частые ошибки:** используют apply там, где можно обойтись transform, теряя производительность на больших данных; ожидают от transform изменения числа строк (например, возврата одной строки на группу), хотя по определению transform сохраняет исходную форму данных.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'group': ['A', 'A', 'B', 'B'], 'value': [10, 20, 5, 15]})
df['group_mean'] = df.groupby('group')['value'].transform('mean')
print(df)
```
Проверка: для группы A group_mean должен быть 15 в обеих строках, для группы B — 10 в обеих строках, при этом число строк в df не изменилось.

```python
import pandas as pd
df = pd.DataFrame({'day': range(1, 8), 'sales': [10, 12, 9, 15, 20, 18, 22]})
```

### 127. [Q-04-02-0127] Как эффективно обработать csv-файл, который слишком большой, чтобы целиком загрузить в память, с помощью pandas?

**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода

**Короткий ответ**
Файл читают по частям через pd.read_csv(..., chunksize=N), обрабатывая и агрегируя каждый фрагмент отдельно, либо сразу ограничивают используемые столбцы (usecols) и типы данных (dtype), чтобы снизить объём потребляемой памяти.

**Разбор**
- **Как это работает:** chunksize превращает read_csv в итератор, возвращающий DataFrame фиксированного размера по частям; это позволяет обрабатывать файл потоково, сохраняя только промежуточные агрегаты (например, частичные суммы по группам), а не весь файл целиком в памяти.
- **На практике:** если нужна простая агрегация (сумма, количество по категориям), её можно посчитать накопительно по чанкам и объединить в конце; если задача требует операций над всем набором данных сразу (например, глобальная сортировка или сложный merge), чанкование усложняет логику и может потребовать иных инструментов (например, баз данных или движков типа DuckDB/polars).

```python
import pandas as pd
```

Выбор между глобальным средним/медианой, групповым средним (например, по сегменту) и модельной импутацией зависит от того, насколько пропуск связан с другими признаками: более сложные методы точнее, но требуют больше данных и прозрачности для интерпретации.

**Разбор**
- **Как это работает:** глобальное среднее/медиана заполняет все пропуски одним и тем же значением, игнорируя контекст; групповое среднее (df.groupby('segment')['x'].transform('mean')) учитывает, что разные сегменты могут иметь разный типичный уровень метрики; модельная импутация (например, регрессия по другим признакам) пытается предсказать пропущенное значение на основе взаимосвязей в данных.
- **На практике:** групповое среднее — хороший баланс между простотой и точностью, когда есть явный сегмент, объясняющий часть вариации; модельная импутация оправдана при значимой доле пропусков и достаточном объёме данных для обучения, но добавляет сложность и риск переобучения или скрытой утечки целевой переменной.
- **Частые ошибки:** применяют групповое среднее по сегменту с очень малым числом наблюдений, получая нестабильные (переобученные на пару точек) оценки; используют модельную импутацию, обученную на тех же данных, которые затем используются для оценки итоговой метрики, не разделяя обучение и применение, что переоценивает точность импутации.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'segment': ['A', 'A', 'B', 'B'], 'value': [10, None, 100, 120]})
df['value_imputed'] = df.groupby('segment')['value'].transform(lambda x: x.fillna(x.mean()))
print(df)
```
Проверка: пропуск в сегменте A должен быть заполнен значением 10 (единственное известное значение в группе), а не глобальным средним по всей таблице (которое было бы искажено сегментом B).

### 129. [Q-04-02-0129] Как на практике, без строгой статистической проверки, понять, что пропуски в данных не случайны, а связаны с конкретным сегментом?

**Уровень:** Middle

**Короткий ответ**
Нужно сравнить долю пропусков в разных сегментах (по платформе, стране, периоду регистрации и так далее); если пропуски сильно концентрируются в одном сегменте, это сигнал, что пропуск не случаен и напрямую связан с источником или природой данных этого сегмента.

**Разбор**
- **Как это работает:** строят сводную таблицу доли пропусков по каждому сегменту (df.groupby('segment')['col'].apply(lambda x: x.isna().mean())); если доля пропусков заметно различается между сегментами, а не распределена равномерно, пропуски скорее всего связаны с определённым процессом (например, новая версия приложения не отправляла поле, или пользователи одной страны не заполняли анкету).
- **На практике:** такой анализ особенно важен перед принятием решения об удалении строк или заполнении пропусков — если пропуски систематически связаны с, например, менее активными пользователями, удаление строк занизит метрики активности; стоит также проверить, не совпадает ли момент появления пропусков с датой релиза или изменением трекинга.
- **Частые ошибки:** делают вывод о "случайности" пропусков только по общей доле пропусков в таблице, не разбивая по сегментам; увидев связь пропусков с сегментом, сразу удаляют весь сегмент вместо того, чтобы отдельно разобраться, является ли это технической проблемой трекинга или реальной особенностью сегмента.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({
    'platform': ['ios', 'ios', 'android', 'android', 'android'],
    'age': [25, None, 30, None, None]
})
missing_by_segment = df.groupby('platform')['age'].apply(lambda x: x.isna().mean())
print(missing_by_segment)
```
Проверка: доля пропусков для android должна оказаться заметно выше (2 из 3, то есть 0.67), чем для ios (1 из 2, то есть 0.5), что указывает на возможную связь пропуска с платформой и требует дальнейшего разбирательства.

### 130. [Q-04-02-0130] Какие методы обнаружения выбросов (IQR, z-score, перцентили) существуют и в чём ограничения каждого?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
IQR и перцентильные границы устойчивы к асимметричным распределениям и не требуют предположения о нормальности, а z-score основан на среднем и стандартном отклонении и чувствителен к самим выбросам, которые искажают эти оценки.

**Разбор**
- **Как это работает:** IQR-метод использует Q1/Q3 и не зависит от формы распределения; перцентильный метод (например, отрезать значения ниже 1-го и выше 99-го перцентиля) задаёт фиксированную долю "крайних" значений независимо от их абсолютной величины; z-score = (x − mean) / std, и чем больше |z|, тем дальше значение от среднего в единицах стандартного отклонения, но сам std может быть "раздут" выбросами.
- **На практике:** для сильно скошенных метрик (выручка, время на сайте) предпочтительнее IQR или перцентили, так как z-score на таких распределениях будет либо пропускать реальные выбросы, либо помечать нормальные большие значения как аномалии; выбор метода и порогов — это допущение, которое всегда стоит явно проговаривать, а не считать "объективным" стандартом.
- **Частые ошибки:** применяют z-score к явно не нормальному распределению, полагая порог |z|>3 универсальным правилом; обрезают выбросы по фиксированному перцентилю без учёта контекста (например, топовые VIP-клиенты систематически попадают под отсечение, хотя их данные корректны и важны для анализа).

**Пример / кейс**
```python
import pandas as pd
s = pd.Series([10, 12, 11, 13, 12, 14, 500])
z_scores = (s - s.mean()) / s.std()
print(z_scores)
```
Проверка: значение 500 получит заметно больший |z|, чем остальные, но стоит также посчитать IQR-метод на тех же данных и сравнить, насколько по-разному два метода оценивают этот же выброс, особенно если добавить ещё одно умеренно большое значение.

### 131. [Q-04-02-0131] Как искать подстроку или паттерн в текстовом столбце с помощью str-методов pandas и на что обратить внимание при пропусках?

**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода

**Короткий ответ**
Поиск по тексту делают через df['col'].str.contains(pattern) или str.extract(regex) для извлечения части строки по регулярному выражению, при этом параметр na=... нужно задать явно, чтобы контролировать поведение на пропущенных значениях.

- **Как это работает:** str.contains возвращает булев Series, True если совпадение найдено; по умолчанию результат для NaN-значения в исходном столбце тоже становится NaN (не True и не False), что при использовании в качестве фильтра может привести к неожиданному исключению строк; str.extract с группами регулярного выражения возвращает DataFrame с извлечёнными частями или NaN, если совпадение не найдено.

- **Частые ошибки:** используют df[df['col'].str.contains('x')] без na=False на столбце с пропусками и получают ValueError при попытке использовать результат как булеву маску; забывают экранировать специальные символы регулярных выражений (точку, скобки) при поиске буквальной подстроки, получая неверные совпадения.

```python
import pandas as pd
df = pd.DataFrame({'email': ['user@test.com', None, 'another@company.ru']})
has_ru = df['email'].str.contains(r'\.ru$', na=False, regex=True)
print(has_ru)
```
Проверка: результат должен быть [False, False, True] — пропуск корректно трактуется как False благодаря na=False, а не вызывает ошибку при дальнейшей фильтрации.

### 132. [Q-04-02-0132] Как с помощью groupby посчитать разные агрегатные функции для разных столбцов одновременно?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
Для разных функций на разные столбцы используют df.groupby('key').agg({'col1': 'sum', 'col2': 'mean'}) или более явный синтаксис с pd.NamedAgg, который сразу задаёт понятные имена итоговых столбцов.

**Разбор**
- **Как это работает:** agg принимает словарь, где ключ — имя столбца, а значение — функция или список функций, применяемых именно к этому столбцу; синтаксис с NamedAgg (df.groupby('key').agg(total=pd.NamedAgg(column='col1', aggfunc='sum'), avg=pd.NamedAgg(column='col2', aggfunc='mean'))) даёт более читаемые названия результирующих столбцов, особенно если к одному столбцу применяется несколько функций.
- **На практике:** такой подход удобен для построения комплексных сводных отчётов одним вызовом, например "сумма выручки, среднее время доставки и количество уникальных пользователей по региону"; при использовании nunique в качестве одной из функций стоит помнить, что это может быть заметно медленнее на больших данных, чем sum/mean.
- **Частые ошибки:** применяют одну и ту же функцию ко всем столбцам через .agg('sum'), хотя для некоторых столбцов (например, цена за единицу) сумма не имеет смысла и нужна скорее mean; получают многоуровневые названия столбцов (MultiIndex columns) при использовании списка функций и забывают привести их к плоскому виду перед дальнейшей обработкой или экспортом в отчёт.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'region': ['RU', 'RU', 'US'], 'revenue': [100, 150, 200], 'delivery_days': [2, 3, 5]})
summary = df.groupby('region').agg(total_revenue=('revenue', 'sum'), avg_delivery=('delivery_days', 'mean'))
print(summary)
```
Проверка: для region=RU total_revenue должен быть 250, avg_delivery — 2.5, что легко проверить вручную по исходным значениям.

### 133. [Q-04-02-0133] Почему число "дубликатов строк" может отличаться от числа "дубликатов по бизнес-ключу", и как это может объяснить расхождение между дашбордом и источником данных?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
Полное совпадение всех столбцов строки — более строгое условие, чем совпадение бизнес-ключа (например, order_id); если в таблице несколько версий одного заказа с разными статусами, проверка полных дубликатов их не найдёт, и в итоге дашборд, считающий по order_id, и источник, считающий по строкам, дадут разные числа.

**Разбор**
- **Как это работает:** df.duplicated() без параметров сравнивает все столбцы, а df.duplicated(subset=['order_id']) — только указанный ключ; если каждая версия заказа отличается хотя бы одним полем (например, временной меткой обновления), полные дубликаты не обнаруживаются, хотя по бизнес-смыслу должна быть одна запись на заказ.
- **На практике:** при расхождении дашборда и источника стоит первым шагом сравнить df['order_id'].nunique() с len(df) — если они не равны, источник содержит несколько строк на один бизнес-объект, и нужно явно решить, какую версию считать "актуальной" (например, keep='last' по дате обновления) до агрегации.
- **Частые ошибки:** считают общее количество строк "количеством заказов", не проверив уникальность бизнес-ключа, из-за чего дашборд, который правильно дедуплицирует по order_id, показывает меньшее число, которое ошибочно интерпретируют как "дашборд врёт"; дедуплицируют без сортировки по времени обновления, оставляя случайную, а не актуальную версию записи.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({
    'order_id': [1, 1, 2],
    'status': ['created', 'paid', 'paid'],
    'amount': [100, 100, 50]
})
print(len(df), df['order_id'].nunique())
dedup = df.drop_duplicates(subset=['order_id'], keep='last')
print(dedup['amount'].sum())
```
Проверка: len(df) равен 3, а nunique() по order_id — 2; после дедупликации по бизнес-ключу сумма amount равна 150 (100 + 50), а не 250, как если бы считали по всем строкам.

### 134. [Q-04-02-0134] Как заранее проверить тип связи между таблицами (один-к-одному, один-ко-многим) перед merge, чтобы не получить неожиданное размножение строк?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
В pd.merge есть параметр validate (например, '1:1', '1:m', 'm:1', 'm:m'), который проверяет заявленный тип связи и выбрасывает понятную ошибку заранее, если реальные данные ему не соответствуют, вместо того чтобы молча вернуть неожиданный результат.

**Разбор**
- **Как это работает:** validate='one_to_one' проверяет, что ключ объединения уникален в обеих таблицах; validate='one_to_many' проверяет уникальность ключа только в левой таблице, допуская повторы в правой; при нарушении условия merge вместо выполнения операции выбрасывает MergeError с понятным сообщением.
- **На практике:** добавление validate — это дешёвая и полезная защитная проверка перед продакшен-пайплайнами и регулярными отчётами, особенно когда данные могут со временем измениться (появятся дубликаты ключа, которых раньше не было); это особенно важно при автоматизированных регулярных джойнах, где никто не смотрит на результат построчно.
- **Частые ошибки:** считают validate избыточной "страховкой" и не используют её в продакшен-коде, из-за чего проблема с дублированием ключа обнаруживается только постфактум через искажённые бизнес-метрики; неправильно выбирают тип связи в validate (например, ставят '1:1', когда по природе данных связь должна быть '1:m'), получая ложные срабатывания ошибки на корректных данных.

**Пример / кейс**
```python
import pandas as pd
orders = pd.DataFrame({'order_id': [1, 2, 3]})
addresses = pd.DataFrame({'order_id': [1, 1, 2]})
try:
    pd.merge(orders, addresses, on='order_id', validate='one_to_one')
except Exception as e:
    print(type(e).__name__, e)
```
Проверка: вызов должен выбросить MergeError, явно сообщающий, что ключ order_id не уникален в правой таблице, что заранее предотвращает скрытое размножение строк.

### 135. [Q-04-02-0135] Метрика во временном ряду резко изменилась в определённую дату — как в pandas проверить, не связано ли это с изменением логики трекинга, а не с реальным изменением поведения?

Нужно построить ежедневный ряд метрики вместе со вспомогательными показателями (например, долей пропусков, количеством событий по источнику) вокруг подозрительной даты и проверить, совпадает ли разрыв с резким изменением структуры данных, а не только самого значения метрики.

### 137. [Q-04-02-0137] Что меняется в поведении присваиваний в pandas между версией 1.x и 2.x из-за механизма copy-on-write?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
При включённом copy-on-write (режим, ставший поведением по умолчанию с pandas 3.0 и доступный как опция в 2.x) операции, которые раньше могли неявно изменить исходные данные через view, теперь всегда возвращают независимую копию при первой попытке изменения, что делает поведение более предсказуемым, но меняет привычные паттерны кода.

**Разбор**
- **Как это работает:** в классическом режиме часть операций (например, df2 = df[['a','b']]) могла возвращать view, и изменение df2 иногда затрагивало исходный df, иногда — нет, в зависимости от внутренней реализации, что и было источником SettingWithCopyWarning; с copy-on-write любое изменение автоматически создаёт копию "по требованию" именно в момент записи, а не заранее, что устраняет неоднозначность.
- **На практике:** при включении этого режима (pd.set_option('mode.copy_on_write', True) в 2.x) часть кода, ранее опирающегося на побочный эффект изменения через view, перестанет работать как раньше, поэтому перед обновлением версии pandas на продакшен-пайплайнах стоит явно протестировать код; рекомендуется и так писать код в стиле, не зависящем от view/copy (использовать .copy() там, где это нужно по смыслу), чтобы быть независимым от версии.
- **Частые ошибки:** обновляют версию pandas в проекте без проверки поведения SettingWithCopyWarning-подобных мест, из-за чего часть "работавшего" кода начинает давать иной результат без явной ошибки; путают copy-on-write с обычным .copy() — это разные механизмы: один про внутреннюю оптимизацию управления памятью, другой — явный метод в коде пользователя.

**Пример / кейс**
```python
import pandas as pd
print(pd.__version__)
pd.set_option('mode.copy_on_write', True)
df = pd.DataFrame({'a': [1, 2, 3]})
sub = df[['a']]
sub.loc[0, 'a'] = 100
print(df)   # с copy-on-write исходный df не изменится
```
Проверка: при включённом copy-on-write исходный df должен остаться [1, 2, 3], тогда как в классическом режиме на некоторых версиях pandas подобная операция могла (хотя и не гарантированно) изменить df.

### 138. [Q-04-02-0138] Почему перебор строк DataFrame через iterrows считается плохой практикой для производительности, и какие есть альтернативы?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
iterrows создаёт отдельный объект Series для каждой строки и выполняет цикл в интерпретируемом Python-коде, что намного медленнее векторизованных операций; альтернативы — векторизация, np.where/np.select, itertuples (быстрее iterrows, если нужен именно построчный доступ), или groupby/transform для групповой логики.

**Разбор**
- **Как это работает:** iterrows конвертирует каждую строку в Series с приведением типов столбцов к общему dtype, что создаёт накладные расходы на каждой итерации; itertuples возвращает легковесные именованные кортежи и работает быстрее, но всё ещё медленнее, чем полностью векторизованный подход, выполняемый без явного Python-цикла по строкам.
- **На практике:** перед использованием iterrows стоит спросить, можно ли выразить ту же логику через векторизованные операции или np.select для многоусловной логики; если построчный проход действительно необходим (например, сложная stateful-логика, зависящая от предыдущих строк), стоит оценить объём данных и решить, оправдан ли iterrows для конкретного масштаба задачи.
- **Частые ошибки:** используют iterrows по привычке для простых условных преобразований столбца, где достаточно np.where или apply по столбцу; не замеряют время выполнения на реальном объёме данных перед оптимизацией, выбирая "интуитивно более быстрый" метод без проверки.

**Пример / кейс**
```python
import pandas as pd
import numpy as np
df = pd.DataFrame({'amount': [100, -50, 200, 0]})
df['flag_loop'] = [1 if row['amount'] > 0 else 0 for _, row in df.iterrows()]
df['flag_vec'] = np.where(df['amount'] > 0, 1, 0)
print(df['flag_loop'].equals(df['flag_vec']))
```
Проверка: оба способа должны дать идентичный результат (equals вернёт True), при этом замер времени на большом DataFrame покажет кратную разницу в скорости в пользу np.where.

### 139. [Q-04-02-0139] Как построить базовую когортную таблицу в pandas (пользователи по месяцу регистрации и активности в последующие месяцы)?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
Для когортного анализа сначала определяют месяц регистрации каждого пользователя (когорту), затем для каждого события считают номер месяца относительно когорты, после чего строят pivot_table с когортой в строках, номером месяца жизни в столбцах и числом активных пользователей в ячейках.

**Разбор**
- **Как это работает:** когорта обычно определяется как месяц первой активности или регистрации пользователя (df.groupby('user_id')['date'].min()); "номер месяца жизни" = разница в месяцах между датой события и датой когорты пользователя; дальнейший pivot_table с aggfunc='nunique' по user_id даёт число уникальных активных пользователей в каждой ячейке когорта × месяц жизни.
- **На практике:** после построения абсолютных чисел их часто переводят в проценты от размера когорты (retention rate), деля каждую строку на значение в её первом столбце (месяц 0); такую таблицу удобно визуализировать как тепловую карту для наглядного сравнения удержания между когортами.
- **Частые ошибки:** путают дату события и дату когорты при расчёте разницы в месяцах, используя субтракцию календарных дат вместо разницы номеров года-месяца, что даёт неверный результат на границах месяцев; считают "активность" без уникализации по user_id (используя count вместо nunique), что переоценивает когорту при наличии нескольких событий одного пользователя в месяц.

**Пример / кейс**
```python
import pandas as pd
events = pd.DataFrame({
    'user_id': [1, 1, 2, 2, 3],
    'date': pd.to_datetime(['2024-01-10', '2024-02-05', '2024-01-15', '2024-03-01', '2024-02-20'])
})
cohort = events.groupby('user_id')['date'].min().dt.to_period('M').rename('cohort')
events = events.join(cohort, on='user_id')
events['period'] = (events['date'].dt.to_period('M') - events['cohort']).apply(lambda x: x.n)
table = events.pivot_table(index='cohort', columns='period', values='user_id', aggfunc='nunique')
print(table)
```
Проверка: для когорты 2024-01 (пользователи 1 и 2) в period=0 должно быть 2 активных пользователя, а в period=1 — 1 пользователь (user_id=1, вернувшийся в феврале), что проверяется ручным пересчётом по исходным датам.

### 140. [Q-04-02-0140] Как с помощью pandas проверить, что распределение пользователей по группам A/B-теста не нарушено (аналог проверки SRM) прежде чем анализировать результаты?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
Перед анализом эффекта считают количество пользователей в каждой группе теста (value_counts по группе) и сравнивают полученное соотношение с ожидаемым (например, 50/50), а также проверяют, не отличается ли это соотношение по сегментам (платформа, страна, день входа в тест).

- **Как это работает:** df.groupby('variant')['user_id'].nunique() дает фактическое число пользователей в каждой группе; при ожидаемом равном split сильное отклонение (например, 48% против 52% на большой выборке) — явный повод для более строгой статистической проверки SRM (sample ratio mismatch), а не просто "шум".
- **На практике:** проверку стоит делать не только в целом, но и в разрезе по дате входа в тест и по платформе — рассинхрон может возникать не с самого начала теста (например, после правки трекинга в середине эксперимента) или только на одной платформе из-за бага в назначении группы; обнаруженный SRM обычно означает, что сравнивать метрики конверсии по группам до устранения причины некорректно.
- **Частые ошибки:** проверяют общее соотношение групп один раз в конце эксперимента, не замечая, что рассинхрон появился только в середине периода из-за технического сбоя, который искажает лишь часть данных; игнорируют небольшое на первый взгляд отклонение в split, не проверив его статистическую значимость при большом объёме выборки, где даже небольшая разница в процентах может быть неслучайной.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'user_id': range(1, 1001), 'variant': ['A'] * 540 + ['B'] * 460})
counts = df['variant'].value_counts()
ratio = counts / counts.sum()
print(counts)
print(ratio)
```
Проверка: фактическое соотношение 54%/46% вместо ожидаемых 50%/50% на выборке в 1000 пользователей — заметное отклонение, которое стоит проверить статистическим тестом (например, chi-square) и разобраться в причине перед интерпретацией результатов теста.

### 141. [Q-04-02-0141] Что происходит при concat двух DataFrame с несовпадающим набором столбцов, и как контролировать итоговый индекс?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
pd.concat по умолчанию выравнивает таблицы по названиям столбцов, заполняя NaN там, где столбец присутствует только в одной из таблиц, а индексы объединяемых таблиц сохраняются как есть, если не передать ignore_index=True.

**Разбор**
- **Как это работает:** concat(axis=0) объединяет строки по объединению (union) множества столбцов обеих таблиц; столбцы, отсутствующие в одной из таблиц, получают NaN в соответствующих строках; исходные индексы каждой таблицы сохраняются без изменений, из-за чего при одинаковых исходных индексах в результате появляются повторяющиеся метки.
- **На практике:** если таблицы должны иметь одинаковую структуру (например, данные за разные месяцы с одинаковой схемой), стоит заранее проверить набор столбцов (set(df1.columns) == set(df2.columns)), чтобы не получить неожиданные NaN из-за опечатки в названии столбца; ignore_index=True нужен почти всегда, если дальше планируется позиционный доступ или просто чистый диапазон индекса.
- **Частые ошибки:** не замечают, что из-за разного регистра или пробела в названии столбца (Amount vs amount) concat считает их разными столбцами и создаёт два столбца с NaN вместо одного; не используют ignore_index и затем получают неожиданные результаты при join/loc по дублирующимся меткам индекса.

**Пример / кейс**
```python
import pandas as pd
df1 = pd.DataFrame({'id': [1, 2], 'amount': [100, 200]})
df2 = pd.DataFrame({'id': [3, 4], 'Amount': [150, 250]})
combined = pd.concat([df1, df2], ignore_index=True)
print(combined)
```
Проверка: итоговая таблица будет содержать два отдельных столбца amount и Amount с NaN в "чужих" строках — это сразу видно по выводу и сигнализирует об опечатке в названии столбца, а не о реальном отсутствии данных.

### 142. [Q-04-02-0142] Почему важно фиксировать random_state не только в train_test_split, но и во всех других местах кода, где используется случайность?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
Если случайность используется в нескольких местах (разбиение на train/test, df.sample, перемешивание, инициализация модели), а зафиксирован seed только в одном из них, итоговый результат всё равно останется невоспроизводимым, потому что остальные источники случайности будут меняться от запуска к запуску.

**Разбор**
- **Как это работает:** каждый генератор случайных чисел (встроенный random, numpy.random, random_state внутри функций pandas/sklearn) может иметь собственное внутреннее состояние; фиксация seed в одном месте не влияет на остальные, если они не связаны общим источником случайности или не получили свой собственный seed.
- **На практике:** для надёжной воспроизводимости всего пайплайна стоит зафиксировать seed в самом начале скрипта для всех используемых библиотек случайности и передавать random_state явно в каждую функцию, где он поддерживается (train_test_split, sample, shuffle), а не полагаться на глобальный seed, который может быть "израсходован" предыдущими случайными вызовами.
- **Частые ошибки:** фиксируют random_state только в train_test_split, но затем используют df.sample() без параметра random_state где-то ещё в пайплайне, получая разные результаты при каждом перезапуске; переставляют порядок вызовов случайных операций в коде между запусками, из-за чего даже с одинаковым общим seed результат отличается, так как генератор "потребляет" случайные числа в другом порядке.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'id': range(10)})
sample1 = df.sample(n=3, random_state=42)
sample2 = df.sample(n=3, random_state=42)
print(sample1.equals(sample2))
```
Проверка: sample1 и sample2 должны быть идентичны при одинаковом random_state, но если где-то в пайплайне до этого вызова случайность использовалась без фиксированного seed, порядок операций всё равно может влиять на воспроизводимость всего скрипта в целом.

### 143. [Q-04-02-0143] Когда обычный merge по равенству ключа не подходит и нужен merge_asof (объединение по ближайшей дате)?

**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
merge_asof нужен, когда у двух таблиц нет точного совпадения по времени, но логически нужно сопоставить событие с ближайшим по времени (обычно предыдущим) значением из другой таблицы, например событие продажи с последней известной на тот момент ценой или курсом валюты.

**Разбор**
- **Как это работает:** merge_asof сортирует обе таблицы по ключу (обычно временному) и для каждой строки левой таблицы находит последнюю строку правой таблицы, чья временная метка не превышает временную метку левой строки (direction='backward' по умолчанию); обычный merge по равенству требует точного совпадения значений ключа и не умеет искать "ближайшее подходящее".
- **На практике:** типичный пример — сопоставить время транзакции с действовавшим на этот момент тарифом или курсом обмена, который меняется не в момент каждой транзакции, а периодически; перед использованием обе таблицы обязательно должны быть отсортированы по ключу объединения, иначе результат будет неверным или функция выбросит ошибку.
- **Частые ошибки:** пытаются решить задачу обычным merge с последующей сложной постобработкой вместо использования готового merge_asof, усложняя код и рискуя ошибиться в логике "последнего известного значения"; забывают про направление (direction) и получают сопоставление с будущим значением тарифа вместо действовавшего на момент события, если по смыслу нужно backward, а не forward или nearest.

**Пример / кейс**
```python
import pandas as pd
trades = pd.DataFrame({'time': pd.to_datetime(['2024-01-01 10:05', '2024-01-01 10:20']), 'amount': [100, 200]})
rates = pd.DataFrame({'time': pd.to_datetime(['2024-01-01 10:00', '2024-01-01 10:15']), 'rate': [90.0, 91.5]})
merged = pd.merge_asof(trades, rates, on='time', direction='backward')
print(merged)
```
Проверка: для сделки в 10:05 должен применяться курс 90.0 (действовавший с 10:00), а для сделки в 10:20 — курс 91.5 (действовавший с 10:15), что соответствует принципу "последнее известное значение на момент события".

### 144. [Q-04-02-0144] Какие приёмы оптимизации помогают ускорить медленный groupby или merge на большой таблице?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
Типичные приёмы — предварительно отсортировать или проиндексировать данные по ключу объединения/группировки, уменьшить типы данных (category, меньшая разрядность чисел), отфильтровать и выбрать только нужные столбцы до тяжёлой операции, и избегать повторных merge/groupby там, где можно объединить логику в один проход.

**Разбор**
- **Как это работает:** merge и groupby внутри используют хеширование или сортировку по ключу; если ключ имеет тип object (строка) вместо category или числового типа, сравнение и хеширование происходит медленнее; выбор только нужных столбцов (usecols при чтении, или df[['a','b']] до операции) снижает объём данных, которые нужно переставлять в памяти.
- **На практике:** перед тяжёлым merge полезно сначала отфильтровать обе таблицы до нужного подмножества строк (например, только за нужный период), а не объединять всё и фильтровать потом; для повторяющихся по одному и тому же ключу группировок стоит задуматься об установке ключа как индекса (set_index) заранее, что может ускорить последующие операции доступа.
- **Частые ошибки:** оптимизируют типы данных после тяжёлой операции, а не перед ней, теряя весь потенциальный выигрыш; выполняют несколько отдельных groupby по одному и тому же ключу для разных метрик вместо одного groupby с agg по словарю, умножая время выполнения без необходимости.

**Пример / кейс**
```python
import pandas as pd
import time
df = pd.DataFrame({'key': (['A', 'B'] * 500000), 'value': range(1000000)})
df['key_cat'] = df['key'].astype('category')

start = time.time()
df.groupby('key')['value'].sum()
t_object = time.time() - start

start = time.time()
df.groupby('key_cat')['value'].sum()
t_category = time.time() - start

print(t_object, t_category)
```
Проверка: t_category должен быть не больше, а на больших и разнообразных по кардинальности данных обычно заметно меньше t_object, что подтверждает выигрыш от использования category для ключа группировки.

### 145. [Q-04-02-0145] Какие риски связаны с потерей точности float64 при агрегации больших сумм денег, и как их минимизировать в pandas?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Middle

**Короткий ответ**
float64 хранит числа в двоичном формате с конечной точностью, поэтому суммирование большого количества денежных значений может давать крошечные расхождения (например, 0.1 + 0.2 ≠ 0.3 точно), которые накапливаются при множестве операций и могут привести к заметным отклонениям в финансовой отчётности.

**Разбор**
- **Как это работает:** десятичные дробные числа вроде 0.1 не имеют точного представления в двоичной системе, поэтому при хранении в float64 они округляются до ближайшего представимого значения; при суммировании миллионов таких значений ошибки округления накапливаются, и итоговая сумма может немного отличаться от "точной" математической суммы.
- **На практике:** для большинства аналитических отчётов такая погрешность пренебрежимо мала и не влияет на выводы, но для финансовой отчётности, где суммы должны сверяться до копейки с бухгалтерскими системами, стоит либо работать в минимальных неделимых единицах (копейки/центы как целые числа), либо использовать Decimal для критичных расчётов, либо аккуратно округлять результат перед сравнением и выводом.
- **Частые ошибки:** сравнивают два float на точное равенство (sum1 == sum2) вместо сравнения с допустимой погрешностью (abs(sum1 - sum2) < epsilon), получая ложные "несовпадения" из-за микроскопических ошибок округления; смешивают денежные суммы в разных единицах (рубли и копейки) без явного приведения, что усиливает видимые расхождения при округлении.

**Пример / кейс**
```python
import pandas as pd
amounts = pd.Series([0.1] * 1000000)
total = amounts.sum()
print(total)
print(total == 100000.0)
```
Проверка: total может оказаться не точно равным 100000.0 из-за накопленной погрешности округления float64, что видно при точном сравнении через == и требует использования допустимой погрешности при сверке сумм.

### 146. [Q-04-02-0146] В pandas-отчёте метрика резко упала по сравнению с прошлым периодом — какую последовательность проверок стоит сделать, прежде чем сообщать об этом бизнесу?

**Уровень:** Middle

**Короткий ответ**
Перед выводом о реальном падении стоит последовательно проверить: не изменился ли объём и структура исходных данных (дубликаты, пропуски), не "потерялись" ли строки при merge/фильтрации, применяется ли тот же период и та же логика расчёта, что и в прошлый раз, и только после этого делать содержательный вывод.

```python
import pandas as pd

print(current['orders'].pct_change())
```
Проверка: резкий провал на четвёртый день (значение 10 против соседних ~95-100) стоит сначала сверить с количеством строк исходных данных за этот конкретный день — часто такой изолированный провал объясняется неполной выгрузкой данных за день, а не реальным падением заказов.

### 147. [Q-04-02-0147] Как спроектировать переиспользуемый pipeline очистки данных, которым будут пользоваться разные аналитики на разных проектах?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: pipeline можно сделать максимально универсальным (конфигурируемым набором шагов) или специфичным под конкретные данные — выбор зависит от разнообразия источников, частоты изменений схемы и готовности команды поддерживать абстракцию.

**Разбор**
- **Как это работает:** переиспользуемый pipeline обычно строится как последовательность независимых шагов (загрузка → валидация схемы → очистка типов → обработка пропусков/дубликатов → агрегация), каждый из которых можно включать, отключать или настраивать параметрами, а не как монолитная функция с зашитой логикой под один датасет.
- **На практике:** полезно явно разделить "общие" шаги (приведение типов, проверка дубликатов по ключу, базовые инварианты) и "специфичные для проекта" шаги (бизнес-логика конкретной метрики), чтобы общая часть переиспользовалась, а специфичная — настраивалась отдельно; конфигурацию стоит выносить в читаемый формат (словарь/YAML), а не хардкодить внутри функций.
- **Частые ошибки:** делают pipeline настолько гибким и параметризуемым, что его сложнее понять и отладить, чем несколько простых специализированных скриптов; или наоборот — жёстко зашивают предположения одного проекта (названия столбцов, форматы дат) в общий модуль, из-за чего при переносе на другой проект код приходится переписывать, а не конфигурировать.
- **Компромисс:** универсальность снижает дублирование кода и ускоряет запуск нового проекта, но увеличивает сложность, время онбординга новых аналитиков и риск скрытых багов в редко используемых ветках конфигурации; специфичные пайплайны проще для конкретного случая, но плодят дублирование и расхождение логики между проектами со временем. Выбор зависит от того, сколько проектов реально похожи между собой и насколько часто меняются источники данных — единственно верного баланса здесь нет.

**Пример / кейс**
```python
import pandas as pd

def clean_pipeline(df: pd.DataFrame, config: dict) -> pd.DataFrame:
    df = df.drop_duplicates(subset=config.get('dedup_key'))
    for col, dtype in config.get('dtypes', {}).items():
        df[col] = df[col].astype(dtype, errors='ignore')
    for col in config.get('required_columns', []):
        assert df[col].notna().all(), f'Unexpected nulls in {col}'
    return df

config = {'dedup_key': ['order_id'], 'dtypes': {'amount': 'float'}, 'required_columns': ['order_id']}
```
Проверка: такой конфигурируемый pipeline можно прогнать на нескольких разных синтетических таблицах с разными наборами столбцов и проверить, что базовые шаги (дедупликация, проверка на null) срабатывают одинаково, а специфичная логика задаётся только через config.

### 148. [Q-04-02-0148] Как обеспечить воспроизводимость аналитического проекта на уровне версий библиотек и окружения, а не только через фиксацию seed?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: воспроизводимость окружения можно обеспечить через фиксацию версий в requirements/lock-файле, через контейнеризацию (Docker) или через более лёгкие практики вроде записи версий ключевых библиотек в сам отчёт — выбор зависит от критичности результата и ресурсов команды на поддержку инфраструктуры.

**Разбор**
- **Как это работает:** разные версии pandas/numpy могут менять поведение операций (например, copy-on-write, обработка пропусков в groupby, порядок сортировки) даже без изменений в коде проекта; фиксация версий (requirements.txt с точными версиями или lock-файл) гарантирует, что окружение, в котором код тестировался, воспроизводимо на другой машине или через время.

- **Частые ошибки:** фиксируют только seed случайности, игнорируя, что сама логика операций pandas/numpy может незаметно измениться между минорными версиями; тратят непропорционально много времени на выстраивание полной инфраструктуры воспроизводимости для разового исследовательского анализа, который не будет переиспользоваться.
- **Компромисс:** более строгая инфраструктура (контейнеры, lock-файлы, CI-проверки) даёт высокую надёжность воспроизводимости, но требует постоянных вложений в поддержку и замедляет итерации; более лёгкий подход (фиксация seed и версий в документации) быстрее в реализации, но не защищает от расхождений окружения при передаче кода другому человеку или через значительное время. Выбор зависит от того, насколько критичен результат для бизнес-решений и как часто анализ нужно будет воспроизводить.

**Пример / кейс**
```python
import pandas as pd
import numpy as np
import random

SEED = 42
random.seed(SEED)
np.random.seed(SEED)

print('pandas:', pd.__version__)
print('numpy:', np.__version__)
```
Проверка: сравнение зафиксированных в отчёте версий библиотек с версиями в окружении, где отчёт воспроизводится повторно (например, через полгода), помогает быстро выявить расхождение как источник отличий в результате, прежде чем подозревать ошибку в логике расчёта.

### 149. [Q-04-02-0149] Данные перестали помещаться в память одной машины для обработки в pandas — какие есть варианты и по каким критериям выбирать между ними?

Правильный выбор зависит от объёма данных, частоты задачи, квалификации команды и имеющейся инфраструктуры хранения.

```python
import duckdb
```

### 150. [Q-04-02-0150] В финансовом отчёте, построенном на pandas, суммы float64 расходятся с бухгалтерской системой на копейки — как спроектировать расчёт, минимизирующий этот риск?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: можно работать с суммами в минимальных целых единицах (копейках) вместо дробных рублей, использовать тип Decimal для критичных расчётов, либо принять заранее согласованный порог допустимого округления — выбор зависит от требуемой точности сверки и производительности расчётов.

**Разбор**
- **Как это работает:** float64 хранит дробные десятичные числа приближённо в двоичном виде, поэтому последовательное сложение многих денежных значений накапливает мелкие ошибки округления; хранение сумм как целых чисел в минимальных единицах (копейках) полностью устраняет проблему двоичного округления для сложения, а Decimal в Python даёт точную десятичную арифметику ценой меньшей производительности и более сложного кода.
- **На практике:** если отчёт должен сверяться с бухгалтерией "до копейки", стоит привести входные суммы к целым копейкам сразу при загрузке данных и выполнять все промежуточные расчёты в этих единицах, переводя обратно в рубли только для отображения; если расхождения допустимы в пределах, например, рубля на крупные агрегаты, достаточно явного округления итоговых сумм и сравнения с допустимой погрешностью вместо точного равенства.
- **Частые ошибки:** сравнивают суммы, посчитанные в pandas, с суммами из другой системы через точное равенство float без учёта погрешности, делая ложный вывод о "расхождении в данных", хотя разница объясняется исключительно двоичным округлением; переводят всё в Decimal "на всякий случай" даже там, где объём данных и требования к точности этого не оправдывают, сильно замедляя расчёты.
- **Компромисс:** работа в целых копейках быстра и устраняет саму причину ошибки округления, но требует дисциплины при любом вводе/выводе данных (не забыть перевести обратно для отображения); Decimal даёт точность для сложных дробных расчётов (проценты, налоги), но заметно медленнее и менее эргономичен в связке с векторизованными операциями pandas/NumPy. Выбор зависит от того, насколько критична точность до последней копейки и какой объём данных обрабатывается регулярно.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({'amount_rub': [10.10, 20.20, 30.30]})
df['amount_kopecks'] = (df['amount_rub'] * 100).round().astype('int64')
total_kopecks = df['amount_kopecks'].sum()
total_rub = total_kopecks / 100
print(total_rub)
```
Проверка: сумма, посчитанная через целые копейки и затем переведённая обратно в рубли, должна точно совпадать с ожидаемым контрольным значением 60.60, в отличие от потенциальных микрорасхождений при прямом суммировании дробных float.

### 151. [Q-04-02-0151] В продакшен-отчёте merge незаметно размножил строки и исказил итоговую метрику — как выстроить систему проверок, предотвращающую такие случаи в будущем?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: можно добавить явные assert на количество строк до/после merge и validate на тип связи в каждом критичном месте пайплайна, либо выстроить более общий слой автоматических проверок инвариантов данных — выбор зависит от того, сколько таких критичных мест в пайплайне и насколько высока цена ошибки.

**Разбор**
- **Как это работает:** точечная защита — это assert len(result) == len(left) сразу после merge, где ожидается связь один-к-одному или один-ко-многим без изменения числа "главных" записей, плюс validate в самом merge; более общая защита — отдельный модуль проверок данных (data quality checks), который прогоняется после каждого значимого шага пайплайна и логирует/останавливает выполнение при нарушении инварианта.
- **На практике:** для критичных финансовых и управленческих отчётов стоит добавлять проверки в тех местах, где исторически уже случались инциденты, и в местах, где ключ объединения потенциально может перестать быть уникальным (например, справочник пользователей, в который теоретически может попасть дубль); проверки должны явно и громко падать (не просто печатать warning), чтобы ошибка не доходила до бизнес-пользователей незамеченной.
- **Частые ошибки:** добавляют проверки только в том месте пайплайна, где уже был инцидент, игнорируя структурно похожие места, где та же ошибка может повториться с другим ключом объединения; делают проверки настолько строгими и многочисленными, что они начинают ложно срабатывать на легитимные редкие случаи, из-за чего со временем их отключают целиком, а не донастраивают.
- **Компромисс:** точечные assert дёшевы в реализации и понятны, но требуют дисциплины добавлять их вручную в каждое новое критичное место; общая система проверок (аналог unit-тестов для данных) масштабируется лучше, но требует начальных инвестиций в инфраструктуру и поддержку, а также решения, что делать при срабатывании проверки в продакшене (блокировать отчёт или только уведомлять). Выбор зависит от размера пайплайна, частоты изменений схемы данных и цены ошибки для бизнеса.

**Пример / кейс**
```python
import pandas as pd

def safe_merge(left: pd.DataFrame, right: pd.DataFrame, on: str) -> pd.DataFrame:
    before = len(left)
    merged = pd.merge(left, right, on=on, how='left', validate='many_to_one')
    assert len(merged) == before, f'Row count changed after merge: {before} -> {len(merged)}'
    return merged
```
Проверка: safe_merge либо вернёт результат с гарантированно тем же числом строк, что и до merge, либо явно упадёт с понятной ошибкой до того, как искажённые данные попадут в отчёт для бизнеса.

### 152. [Q-04-02-0152] При группировке метрики по сегментам в pandas обнаружен парадокс Симпсона — общий тренд противоположен трендам внутри каждого сегмента. Как объяснить это стейкхолдерам и какие решения стоит предложить дальше?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: можно сообщать бизнесу только сегментированные показатели вместо агрегированного, скорректировать веса сегментов (стандартизацию) или явно показать оба уровня с объяснением причины расхождения — выбор зависит от того, что именно нужно бизнесу для принятия решения.

**Разбор**
- **Как это работает:** парадокс Симпсона возникает, когда соотношение размеров сегментов (весов) меняется между сравниваемыми периодами или группами и само по себе влияет на общий агрегат сильнее, чем изменение показателя внутри каждого сегмента; это легко увидеть в pandas, посчитав метрику через groupby(['period','segment']) и сравнив с метрикой без разбивки на сегмент.
- **На практике:** объяснение для бизнеса должно явно показать таблицу "до/после" с разбивкой по сегментам и их весами, а не только итоговую цифру; дальнейшее решение может быть в пользу взвешенного сравнения с фиксированными весами сегментов (стандартизация), если нужно сравнивать именно "эффективность", а не смесь эффекта и изменения структуры.
- **Частые ошибки:** игнорируют парадокс и продолжают репортить только агрегированную метрику, вводя стейкхолдеров в заблуждение относительно направления тренда; или наоборот — отказываются от агрегированной метрики совсем, хотя для некоторых решений (например, общая выручка компании) агрегат является именно тем, что нужно знать, а разбивка по сегментам — лишь объяснением причины.
- **Компромисс:** показ только сегментированных данных даёт более точную картину причинно-следственной связи, но усложняет коммуникацию и требует от стейкхолдера дополнительной интерпретации; агрегированный показатель проще для коммуникации, но рискует привести к неверным управленческим решениям при изменении структуры сегментов. Обычно разумно показывать оба уровня одновременно с явным объяснением, какой из них на что отвечает, но это требует больше времени на подготовку отчёта и его защиту.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({
    'period': ['before','before','after','after'],
    'segment': ['mobile','desktop','mobile','desktop'],
    'users': [100, 900, 900, 100],
    'converted': [5, 90, 54, 9]
})
df['rate'] = df['converted'] / df['users']
overall = df.groupby('period').apply(lambda g: g['converted'].sum() / g['users'].sum())
print(df[['period','segment','rate']])
print(overall)
```
Проверка: в этом синтетическом примере конверсия внутри каждого сегмента (mobile и desktop) может расти от periода "before" к "after", тогда как общий overall-показатель падает из-за резкой смены веса сегментов — именно это расхождение и нужно явно показать стейкхолдерам, а не только итоговую строку overall.

### 153. [Q-04-02-0153] Доля пропусков в ключевом поле продуктовой метрики существенна и растёт со временем — как выбирать между импутацией, удалением и явным флагом пропуска для принятия решений бизнесом?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: при существенной и растущей доле пропусков предпочтительнее не скрывать их за импутацией, а явно выделить сегмент "неизвестно" отдельной категорией или флагом и отчитываться по нему отдельно, пока не выяснена и не устранена причина роста пропусков.

**Разбор**
- **Как это работает:** когда доля пропусков мала и стабильна, импутация (средним, медианой, модельная) обычно безопасна и мало искажает выводы; когда доля растёт — это сигнал изменяющегося процесса сбора данных (новая версия приложения, новый источник трафика без части полей), и любое "усреднение" пропуска начинает маскировать реальную и меняющуюся проблему, а не просто шум.

- **Частые ошибки:** автоматически увеличивают долю импутированных значений без предупреждения бизнеса, из-за чего отчётная метрика постепенно всё больше опирается на предположения, а не на реальные данные, и это остаётся незамеченным; удаляют растущую долю строк с пропуском, незаметно для себя сокращая выборку и системно смещая отчётную метрику в сторону того сегмента, где данные полнее.
- **Компромисс:** явный флаг пропуска честно показывает ограничения данных, но может "загрязнять" визуализацию дополнительной категорией и требует образования аудитории отчёта, чтобы они не игнорировали эту категорию; импутация даёт более "гладкий" отчёт без явных пробелов, но рискует необоснованно продлить иллюзию уверенности в данных, качество которых реально ухудшается. Решение должно приниматься вместе со стейкхолдерами, а не единолично аналитиком, особенно если метрика используется для серьёзных решений.

**Пример / кейс**
```python
import pandas as pd
df = pd.DataFrame({
    'month': ['2024-01', '2024-02', '2024-03'],
    'total_users': [1000, 1000, 1000],
    'missing_plan': [50, 150, 400]
})
df['missing_share'] = df['missing_plan'] / df['total_users']
print(df)
```
Проверка: явный рост missing_share с 5% до 40% за три месяца — сам по себе важный сигнал, который стоит вынести в отдельный график отчёта, а не просто компенсировать более агрессивной импутацией пропущенного поля "plan".

### 154. [Q-04-02-0154] Как ревьюить pandas-код джуниора на типичные анти-паттерны и что приоритизировать в фидбеке при ограниченном времени на ревью?

**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: при ограниченном времени стоит в первую очередь проверять корректность результата (дедупликация, типы merge, обработка пропусков) и только затем — стиль и производительность, так как ошибка в логике дороже неидиоматичного, но рабочего кода.

**Разбор**
- **Как это работает:** типичные анти-паттерны у джуниоров включают merge без проверки уникальности ключа, использование iterrows там, где можно векторизовать, цепочечную индексацию с риском SettingWithCopyWarning, фильтрацию без скобок вокруг условий, и заполнение пропусков без понимания, почему они возникли; при ограниченном времени ревью стоит выстраивать приоритет по цене ошибки — сначала то, что может незаметно исказить итоговые цифры, потом то, что влияет только на скорость или читаемость.

- **Частые ошибки:** фокусируются на стиле (отступы, имена переменных) и пропускают содержательную ошибку в логике merge или агрегации, которая реально исказит отчёт; дают слишком много замечаний сразу по всем возможным улучшениям, из-за чего джуниор не может выделить, что действительно критично исправить сейчас, а что можно отложить.
- **Компромисс:** глубокое построчное ревью с объяснением каждого нюанса развивает джуниора сильнее, но отнимает много времени ментора и может демотивировать объёмом замечаний; быстрое ревью по чек-листу критичных рисков экономит время, но может пропустить менее очевидные, но реальные проблемы в коде. При дефиците времени разумно явно обозначить, что часть более мелких замечаний отложена "на будущее", а не включать их в тот же цикл ревью.

**Пример / кейс**
```python
import pandas as pd
# пример кода джуниора с анти-паттерном
df = pd.DataFrame({'id': [1, 2], 'country': ['RU', 'US']})
users = pd.DataFrame({'id': [1, 1, 2], 'name': ['a', 'b', 'c']})
result = df.merge(users, on='id')  # нет проверки уникальности ключа в users
print(len(df), len(result))
```
Проверка: len(result) окажется больше len(df) из-за дубликата id=1 в users — это именно тот тип ошибки, который ментору стоит поймать в первую очередь и предложить добавить validate или явную проверку количества строк после merge.

### 155. [Q-04-02-0155] Как спроектировать систему проверок качества данных (аналог unit-тестов) для регулярного pandas-пайплайна, и какие trade-off между полнотой проверок и стоимостью их поддержки нужно учитывать?

**Направление:** Data Analyst

**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: набор проверок можно выстроить вокруг нескольких уровней — структурные инварианты (схема, типы), статистические инварианты (диапазоны значений, доля пропусков) и бизнес-инварианты (сумма метрики не может упасть ниже определённого порога без алерта) — но чем больше проверок, тем выше стоимость их поддержки и риск ложных срабатываний.

**Разбор**
- **Как это работает:** структурные проверки (наличие и тип ожидаемых столбцов, отсутствие дублей по ключу) дёшевы и редко ложно срабатывают; статистические проверки (диапазон значений, резкое изменение доли пропусков день к дню) более информативны, но требуют настройки разумных порогов, которые со временем могут устаревать; бизнес-инварианты (например, "сумма выручки не должна отличаться от вчерашней более чем на X% без видимой причины") самые ценные для раннего обнаружения проблем, но и самые сложные в калибровке.
- **На практике:** разумно начинать с дешёвых структурных проверок на каждом шаге пайплайна и постепенно добавлять статистические/бизнес-проверки только в тех местах, где уже случались или наиболее вероятны реальные инциденты, не пытаясь сразу покрыть все возможные сценарии; результаты проверок стоит логировать отдельно от самого отчёта, чтобы можно было анализировать, какие проверки чаще всего срабатывают и насколько они полезны.
- **Частые ошибки:** строят слишком жёсткие статистические пороги без учёта естественной волатильности метрики (сезонность, выходные), что приводит к частым ложным алертам и постепенному игнорированию всей системы проверок командой; или не инвестируют в проверки вообще, полагаясь на то, что проблемы будут замечены вручную при чтении отчёта, что работает плохо на масштабе и при автоматизации.
- **Компромисс:** более полная система проверок раньше ловит проблемы и снижает риск ошибочных решений на основе плохих данных, но требует постоянных вложений в поддержку порогов и само тестирование проверок; минимальный набор проверок дешевле в поддержке, но оставляет больше пространства для необнаруженных инцидентов. Баланс зависит от критичности пайплайна для бизнеса и от того, насколько часто меняется структура и объём входных данных.

**Пример / кейс**
```python
import pandas as pd

def validate_daily_report(df: pd.DataFrame, prev_total: float) -> list:
    issues = []
    if df['order_id'].duplicated().any():
        issues.append('Duplicate order_id found')
    if df['amount'].isna().mean() > 0.05:
        issues.append('Too many missing amounts')
    current_total = df['amount'].sum()
    if prev_total and abs(current_total - prev_total) / prev_total > 0.3:
        issues.append(f'Total changed too much: {prev_total} -> {current_total}')
    return issues
```
Проверка: функцию можно прогнать на синтетических данных с намеренно внесёнными проблемами (дубликат order_id, резкий скачок amount) и убедиться, что соответствующий issue действительно появляется в списке, а на "нормальных" данных список остаётся пустым.

### 156. [Q-04-02-0156] Руководитель просит срочно подтвердить уже объявленную бизнесу цифру, посчитанную в pandas, и времени на полную перепроверку нет — как действовать ответственно в таких условиях?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: в условиях дефицита времени стоит быстро прогнать несколько самых дешёвых и информативных проверок (число строк, дубликаты по ключу, сверка с независимым контрольным агрегатом), а затем явно сообщить руководителю, что именно проверено, а что осталось за рамками быстрой проверки, вместо того чтобы либо слепо подтверждать цифру, либо требовать полного повторного анализа.

**Разбор**
- **Как это работает:** приоритетные быстрые проверки — это сверка итогового числа с независимым источником (например, грубая оценка через SQL напрямую к источнику данных, в обход всего pandas-пайплайна), проверка на дубликаты по ключевому полю и проверка, что фильтры периода/сегмента применены так же, как в исходном расчёте; такие проверки занимают минуты, но покрывают наиболее вероятные источники грубой ошибки.
- **На практике:** важно явно разграничить для руководителя "быструю проверку на грубые ошибки" и "полный аудит расчёта" — это разные по надёжности уровни уверенности, и смешивать их в одном устном "да, всё верно" рискованно; если быстрая проверка выявляет расхождение, об этом нужно сообщить немедленно, даже если это означает отсрочку публичного подтверждения цифры.
- **Частые ошибки:** под давлением времени просто перечитывают код глазами и подтверждают цифру без фактического пересчёта хотя бы части данных независимым способом, упуская содержательные ошибки, которые не видны по коду; либо, наоборот, отказываются давать какой-либо ответ без "полной" перепроверки, что не соответствует реальной срочности бизнес-ситуации и не даёт руководителю вообще никакой информации для принятия решения здесь и сейчас.
- **Компромисс:** быстрая частичная проверка экономит время, но несёт остаточный риск пропустить более тонкую ошибку, которую выявил бы полный аудит; полный аудит надёжнее, но может быть физически невозможен в требуемые сроки. Ответственный подход — явно обозначить уровень уверенности и объём выполненной проверки, оставив решение о рисках самому руководителю, а не маскировать неопределённость под категоричное "подтверждаю".

**Пример / кейс**
```python
import pandas as pd
report_total = 125000  # цифра, которую нужно подтвердить
raw = pd.DataFrame({'order_id': [1, 2, 2, 3], 'amount': [50000, 40000, 40000, 35000]})
quick_check_total = raw.drop_duplicates(subset=['order_id'])['amount'].sum()
print(quick_check_total, report_total)
```
Проверка: быстрая проверка по дедуплицированным данным даёт 125000 (50000+40000+35000), что совпадает с report_total — такой мини-пересчёт за несколько минут уже даёт разумное основание для осторожного подтверждения, явно указав, что это именно экспресс-проверка, а не полный аудит.

### 157. [Q-04-02-0157] Как спроектировать идемпотентный ETL-процесс на pandas, чтобы повторный запуск на тех же входных данных не портил и не дублировал уже сохранённый результат?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: идемпотентности можно добиться полной перезаписью результата за обрабатываемый период при каждом запуске, либо через upsert-логику по бизнес-ключу с удалением/заменой существующих записей перед вставкой новых — выбор зависит от объёма данных и возможностей хранилища, куда пишется результат.

**Разбор**
- **Как это работает:** неидемпотентный ETL (который просто "дописывает" новые строки при каждом запуске) при повторном запуске на тех же данных создаёт дубликаты; идемпотентный подход либо полностью удаляет и пересчитывает данные за целевой период (например, "удалить все строки за эту дату, затем вставить заново"), либо выполняет upsert по уникальному бизнес-ключу (обновить, если ключ уже существует, иначе вставить).
- **На практике:** полная перезапись периода проще в реализации и легче для отладки (результат всегда детерминирован относительно входных данных), но может быть дороже по времени на больших объёмах; upsert эффективнее для больших таблиц, но требует надёжного уникального ключа и аккуратной обработки случая изменения состава записей (например, строка, которая раньше была в периоде, а теперь должна быть удалена из источника).
- **Частые ошибки:** реализуют ETL через простое append в целевую таблицу без проверки, не запускался ли уже процесс за этот период, что при повторном или параллельном запуске приводит к задвоению данных; при upsert забывают обработать случай удаления записей, которые пропали из источника, из-за чего в целевой таблице остаются "осиротевшие" устаревшие строки.
- **Компромисс:** перезапись всего периода — надёжный и простой в понимании подход, но может быть неприемлемо медленным при больших объёмах и частых запусках; upsert эффективнее по ресурсам, но сложнее реализовать корректно, особенно в части обработки удалённых из источника записей, и сложнее тестировать на предмет скрытых крайних случаев. Выбор зависит от объёма данных, частоты запуска пайплайна и возможностей целевого хранилища по эффективному upsert.

**Пример / кейс**
```python
import pandas as pd

def idempotent_write(new_data: pd.DataFrame, existing_data: pd.DataFrame, period_col: str, period_value: str) -> pd.DataFrame:
    remaining = existing_data[existing_data[period_col] != period_value]
    return pd.concat([remaining, new_data], ignore_index=True)

existing = pd.DataFrame({'date': ['2024-01-01', '2024-01-02'], 'total': [100, 150]})
new_run = pd.DataFrame({'date': ['2024-01-02'], 'total': [160]})
result = idempotent_write(new_run, existing, 'date', '2024-01-02')
print(result)
```
Проверка: при повторном запуске idempotent_write с теми же new_run и existing результат останется тем же самым (одна строка на 2024-01-02 со значением 160), а не превратится в две дублирующиеся строки за одну и ту же дату.

### 158. [Q-04-02-0158] При расчёте метрики через pandas фильтрация только "активных" пользователей вносит смещение выжившего — как спроектировать расчёт метрики так, чтобы избежать этого искажения?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: можно считать метрику по изначальной полной когорте пользователей, включая тех, кто перестал быть активным (явно отражая их как "0" или "отток" в расчёте), либо явно разделять метрику "для оставшихся" и метрику "для исходной когорты" — важно не подменять одно другим незаметно для читателя отчёта.

**Разбор**

- **На практике:** при построении, например, "среднего дохода на пользователя" важно явно определить знаменатель — это все пользователи исходной когорты или только оставшиеся активные; для метрик удержания и роста обычно содержательнее считать от исходного размера когорты, даже если часть пользователей больше не генерирует событий (их вклад тогда равен нулю, а не отсутствует из расчёта).

- **Компромисс:** расчёт от исходной полной когорты честнее отражает общую картину, но может "размывать" метрику нулями от выбывших пользователей и усложнять интерпретацию для узких вопросов об оставшихся активных; расчёт только по оставшимся активным проще интерпретировать применительно к текущему активному сегменту, но рискует ввести в заблуждение относительно общей эффективности продукта, если не сопровождается явным указанием на фильтрацию. Выбор зависит от того, какой именно вопрос бизнеса закрывает метрика.

**Пример / кейс**
```python
import pandas as pd
cohort = pd.DataFrame({'user_id': [1, 2, 3, 4], 'initial_month_revenue': [50, 30, 20, 40]})
active_later = pd.DataFrame({'user_id': [1, 3], 'month3_revenue': [60, 25]})

merged = cohort.merge(active_later, on='user_id', how='left')
merged['month3_revenue'] = merged['month3_revenue'].fillna(0)
avg_all_cohort = merged['month3_revenue'].mean()
avg_only_active = merged.dropna(subset=['month3_revenue'])['month3_revenue'].mean() if False else active_later['month3_revenue'].mean()
print(avg_all_cohort, avg_only_active)
```
Проверка: avg_all_cohort (учитывающий всех 4 пользователей исходной когорты с нулями для выбывших) окажется заметно ниже, чем avg_only_active (только среди 2 оставшихся активных пользователей) — именно эта разница и показывает величину смещения выжившего при неверном выборе знаменателя.

### 159. [Q-04-02-0159] Что выбрать для сложного аналитического расчёта — один большой монолитный pandas-pipeline в памяти или модульные шаги с промежуточным сохранением результатов, и по каким критериям принимать это решение?

**Направление:** Data Analyst
**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода
**Уровень:** Senior

**Короткий ответ**
Единственного правильного решения нет: монолитный pipeline в памяти проще и быстрее для небольших и стабильных расчётов, а модульные шаги с промежуточным сохранением лучше подходят для больших, долго выполняющихся или часто отлаживаемых пайплайнов — выбор зависит от объёма данных, частоты сбоев и потребности в отладке отдельных этапов.

**Разбор**
- **Как это работает:** монолитный подход выполняет все преобразования от сырых данных до финального результата в одном скрипте без сохранения промежуточных состояний, что проще писать и быстрее исполнять за счёт отсутствия лишнего ввода-вывода; модульный подход сохраняет результат каждого значимого шага на диск (parquet/csv), что позволяет перезапускать только упавший или изменившийся шаг, не пересчитывая всё с начала, и облегчает отладку через инспекцию промежуточных файлов.
- **На практике:** для небольших и быстрых расчётов (секунды-минуты) монолитный подход обычно предпочтительнее из-за простоты; для длительных расчётов (десятки минут и часы) или нестабильных источников данных модульность с промежуточным сохранением снижает цену сбоя и упрощает диагностику, на каком именно шаге появилась проблема в данных.
- **Частые ошибки:** делают монолитный pipeline для тяжёлого многочасового расчёта, из-за чего любой сбой в конце требует полного перезапуска с начала; или наоборот — чрезмерно дробят простую и быструю задачу на множество промежуточных файлов, создавая ненужные накладные расходы на ввод-вывод и усложняя понимание общего потока данных.
- **Компромисс:** модульность облегчает отладку, восстановление после сбоев и параллельную разработку разных этапов разными людьми, но увеличивает сложность инфраструктуры, расход дискового пространства и количество мест, где может рассинхронизироваться логика между этапами; монолитный подход проще поддерживать как единое целое, но хуже масштабируется на большие и нестабильные пайплайны. Решение зависит от объёма данных, продолжительности расчёта, частоты сбоев источника и количества людей, одновременно работающих над пайплайном.

**Пример / кейс**
```python
import pandas as pd

# модульный шаг 1: очистка
raw = pd.DataFrame({'id': [1, 2, 2], 'amount': [100, None, 50]})
cleaned = raw.drop_duplicates(subset=['id']).dropna(subset=['amount'])
cleaned.to_parquet('step1_cleaned.parquet')

# модульный шаг 2: агрегация (можно перезапустить отдельно от шага 1)
cleaned_reloaded = pd.read_parquet('step1_cleaned.parquet')
summary = cleaned_reloaded['amount'].sum()
print(summary)
```
Проверка: если шаг агрегации упадёт из-за ошибки в логике, его можно перезапустить заново, читая уже сохранённый step1_cleaned.parquet, не повторяя заново более затратный шаг очистки исходных данных.

### 160. [Q-04-02-0160] Бизнес меняет определение ключевой метрики (например, "активный пользователь") — как методологически обеспечить сопоставимость исторических данных и донести изменение до стейкхолдеров?

**Тема:** Python для анализа данных: pandas, NumPy, очистка и преобразование данных, работа с пропусками и дубликатами, группировки, merge, производительность, воспроизводимость кода

Единственного правильного решения нет: можно пересчитать всю историю по новому определению, оставить два параллельных ряда (старое и новое определение) на переходный период, или ввести явную точку разрыва на графике с пояснением — выбор зависит от того, насколько сильно отличаются определения и насколько критична непрерывность временного ряда для бизнеса.

**Разбор**
- **Как это работает:** смена логики метрики (например, "активный" теперь определяется по действию X за 7 дней вместо 30) при применении только "с сегодняшнего дня" создаёт разрыв сопоставимости: более ранние периоды посчитаны по старой логике, более поздние — по новой, и визуально это может выглядеть как резкий скачок, не связанный с реальным поведением пользователей; пересчёт всей истории по новому определению обеспечивает сопоставимость, но требует доступа к историческим сырым данным в достаточной детализации и может быть ресурсоёмким.
- **На практике:** стоит заранее проверить, достаточно ли гранулярны и доступны исторические сырые данные для пересчёта по новому определению; если да — пересчитать всю историю и явно задокументировать дату и причину изменения методологии в самом отчёте; если нет — вести оба ряда параллельно на переходный период, чтобы стейкхолдеры могли видеть преемственность, прежде чем полностью перейти на новую метрику.
- **Частые ошибки:** меняют логику расчёта метрики "тихо", без коммуникации даты и причины изменения, из-за чего стейкхолдеры интерпретируют технический разрыв ряда как реальное бизнес-событие; пересчитывают только часть истории без явного указания точки, с которой метрика сопоставима, из-за чего разные люди в компании продолжают сравнивать несопоставимые периоды.
- **Компромисс:** полный пересчёт истории даёт самый чистый и сопоставимый ряд, но может быть дорогим или невозможным при недостатке исторических сырых данных нужной детализации; ведение двух параллельных рядов сохраняет прозрачность перехода, но усложняет отчётность и может путать пользователей отчёта, которые видят два значения одной "метрики"; простое обозначение разрыва дешевле всего в реализации, но перекладывает на читателя отчёта задачу интерпретации скачка. Выбор зависит от критичности непрерывности ряда для конкретных решений и доступности исторических данных нужной детализации.

**Пример / кейс**
```python
import pandas as pd
history = pd.DataFrame({
    'month': ['2024-01', '2024-02', '2024-03', '2024-04'],
    'active_users_old_def': [1000, 1050, 1100, None],
    'active_users_new_def': [None, None, 1300, 1400]
})
print(history)
```
Проверка: явное наличие двух параллельных столбцов с перекрытием на переходный месяц (здесь — 2024-03) позволяет стейкхолдерам увидеть масштаб разницы между определениями на одном и том же периоде, прежде чем полностью перейти на новую метрику в будущих отчётах.
