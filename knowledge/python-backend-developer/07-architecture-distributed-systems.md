### 331. [Q-03-07-0331] Что такое монолитная архитектура и когда она подходит проекту?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Монолит — это приложение, собранное и развёрнутое как единый процесс/артефакт, где все модули работают в общей памяти и общей базе данных; подходит на старте проекта, при небольшой команде и неопределённых границах домена.

**Разбор**
- **Как это работает:** Весь код (API, бизнес-логика, доступ к БД) живёт в одном репозитории и деплоится одним артефактом; внутренние вызовы — обычные вызовы функций, а не сетевые запросы.
- **На практике:** Монолит проще разрабатывать, тестировать и деплоить на старте — один процесс CI/CD, одна БД, нет сетевых издержек между модулями; важно поддерживать модульность внутри (слои, пакеты), чтобы монолит не превратился в «big ball of mud».
- **Частые ошибки:** Считать монолит «плохой» архитектурой по умолчанию; разбивать на сервисы слишком рано, когда домен ещё не понят, что увеличивает сложность без пользы.

**Пример / кейс**
```text
myapp/
  orders/
    service.py
    repository.py
  users/
    service.py
  payments/
    service.py
  api/
    routers.py
```
Проверка: статический анализ импортов (например, import-linter) должен показывать, что orders не импортирует внутренние модули payments напрямую, только через публичный интерфейс service.py.

### 332. [Q-03-07-0332] Что такое микросервисная архитектура, в чём отличие от монолита?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Микросервисная архитектура — набор независимо развёртываемых сервисов, каждый со своей БД и границами ответственности, взаимодействующих по сети; в отличие от монолита, масштабирование, деплой и отказы изолированы на уровне отдельного сервиса.

**Разбор**
- **Как это работает:** Каждый сервис владеет своими данными и бизнес-логикой, общение идёт через HTTP/gRPC/сообщения, а не через общую память.
- **На практике:** Позволяет командам независимо деплоить и масштабировать части системы, но добавляет сетевые издержки, сложность мониторинга, распределённые транзакции и необходимость версионирования контрактов.
- **Частые ошибки:** Распределять сервисы по техническим слоям (например, отдельный «DB-сервис»), а не по бизнес-доменам; считать, что микросервисы сами по себе ускоряют разработку.

**Пример / кейс**
```text
Order Service  -- HTTP --> Payment Service
Order Service  -- publish event --> Notification Service (через очередь)
```
Проверка: у каждого сервиса своя схема БД, доступ к данным другого сервиса — только через его API/события, не через прямые SQL-запросы к чужой БД.

### 333. [Q-03-07-0333] Что значит модульность кода, зачем разделять приложение на модули/слои?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Модульность — разбиение кода на независимые по ответственности части с чёткими интерфейсами, что снижает связанность и облегчает изменение одной части без последствий для других.

**Разбор**
- **Как это работает:** Модуль скрывает детали реализации за публичным интерфейсом (функции, классы), остальной код обращается только к этому интерфейсу.
- **На практике:** Типичное разделение — слой API, слой бизнес-логики (use cases), слой доступа к данным (репозитории); это упрощает unit-тестирование (можно подменить репозиторий мок-объектом) и замену реализации (например, смену БД).
- **Частые ошибки:** «Протекание» деталей реализации наружу (например, ORM-модель используется прямо в контроллере), циклические зависимости между модулями, чрезмерное дробление без выгоды для маленького проекта.

**Пример / кейс**
```python
# repository.py — скрывает детали хранения
class OrderRepository:
    def get(self, order_id: int) -> Order: ...

# service.py — бизнес-логика не знает о БД
class OrderService:
    def __init__(self, repo: OrderRepository):
        self.repo = repo

    def cancel_order(self, order_id: int) -> None:
        order = self.repo.get(order_id)
        order.cancel()
```
Проверка: unit-тест OrderService подменяет OrderRepository тестовым дублем — тест бизнес-логики не требует реальной БД.

### 334. [Q-03-07-0334] Что такое API и зачем явно определять границы между сервисами?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
API — формальный контракт взаимодействия (методы, форматы данных, ошибки); явные границы нужны, чтобы сервисы могли меняться внутри независимо, не ломая друг друга.

**Разбор**
- **Как это работает:** Контракт описывает входы/выходы, не детали реализации; потребитель зависит от контракта, а не от кода.
- **На практике:** Используют схемы (OpenAPI, protobuf) для документирования и валидации; изменения проводят через версионирование или обратно совместимые поля.
- **Частые ошибки:** Отсутствие формального контракта («договорились на словах»), прямой доступ к БД другого сервиса вместо вызова его API.

**Пример / кейс**
```yaml
paths:
  /orders/{id}:
    get:
      responses:
        '200':
          description: OK
          content:
            application/json:
              schema:
                type: object
                properties:
                  id: {type: integer}
                  status: {type: string}
```
Проверка: contract-тест проверяет, что реальный ответ сервиса соответствует этой схеме (например, через schemathesis или pact).

### 335. [Q-03-07-0335] В чём разница между синхронным HTTP-вызовом и отправкой сообщения в очередь?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
HTTP-вызов — синхронный, вызывающий ждёт ответ немедленно; отправка в очередь — асинхронная, вызывающий не ждёт обработки, а получает лишь подтверждение постановки сообщения.

**Разбор**
- **Как это работает:** HTTP создаёт прямую временную связанность (сервис-получатель должен быть доступен прямо сейчас); очередь развязывает отправителя и обработчика во времени — сообщение дождётся, пока consumer освободится.
- **На практике:** Синхронный вызов — для операций, где нужен немедленный результат (проверка остатка перед покупкой); очередь — для фоновых задач (отправка email, пересчёт аналитики), где задержка в секунды/минуты допустима.
- **Частые ошибки:** Использовать синхронный вызов для долгих операций (блокирует клиента и поток); использовать очередь там, где нужен немедленный ответ пользователю.

**Пример / кейс**
```python
# синхронно
response = httpx.post("https://payments/charge", json=payload, timeout=5)

# асинхронно через очередь
queue.publish("send_email", {"user_id": 42, "template": "welcome"})
```
Проверка: в логах синхронного вызова видна задержка ответа клиенту; при очереди клиент получает 202 Accepted немедленно, а обработка видна в логах consumer'а позже.

### 336. [Q-03-07-0336] Что такое кеш и зачем он нужен в backend-приложении?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Кеш — промежуточное хранилище часто запрашиваемых данных с быстрым доступом, снижающее нагрузку на основной источник данных (БД, внешний API) и ускоряющее ответ.

**Разбор**
- **Как это работает:** При запросе сначала проверяется кеш; если данных нет (cache miss) — идём в основной источник и кладём результат в кеш; при повторном запросе (cache hit) данные берутся из кеша.
- **На практике:** Типичные хранилища — Redis, Memcached, локальная память процесса; кешируют данные, которые часто читаются и редко меняются либо допускают небольшую задержку свежести.
- **Частые ошибки:** Кешировать данные без плана их обновления/инвалидации; кешировать персональные/чувствительные данные без учёта ограничения доступа.

**Пример / кейс**
```python
def get_product(product_id: int) -> dict:
    cached = redis.get(f"product:{product_id}")
    if cached:
        return json.loads(cached)
    product = db.fetch_product(product_id)
    redis.set(f"product:{product_id}", json.dumps(product), ex=300)
    return product
```
Проверка: метрика cache hit ratio в Redis растёт после прогрева; повторные запросы к одному product_id не создают новых запросов к БД.

### 337. [Q-03-07-0337] Что такое TTL (time-to-live) у записи в кеше?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
TTL — время, после которого запись в кеше автоматически считается устаревшей и удаляется, вынуждая следующий запрос обновить данные из источника.

**Разбор**
- **Как это работает:** При записи в кеш указывается срок жизни (секунды); хранилище (например Redis) само удаляет ключ по истечении TTL.
- **На практике:** Короткий TTL — свежие, но чаще нагружает основной источник; длинный TTL — меньше нагрузки, но данные дольше могут быть устаревшими; TTL выбирают исходя из частоты изменений и критичности свежести.
- **Частые ошибки:** Ставить одинаковый TTL для всех видов данных без учёта частоты изменений; забывать, что TTL не гарантирует согласованность с БД сразу после обновления записи.

**Пример / кейс**
```python
redis.set("session:abc123", token, ex=1800)  # TTL 30 минут
```
Проверка: `redis-cli TTL session:abc123` показывает убывающее значение; после истечения ключ возвращает nil, и обработчик должен заново получить/обновить данные.

### 338. [Q-03-07-0338] Что такое инвалидация кеша и почему это сложно сделать правильно?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Инвалидация кеша — явное удаление или обновление устаревшей записи при изменении исходных данных, чтобы пользователи не видели старые значения дольше необходимого.

**Разбор**
- **Как это работает:** При изменении записи в БД приложение дополнительно удаляет или перезаписывает соответствующий ключ в кеше.
- **На практике:** Простой способ — удалить ключ сразу после успешного обновления БД (invalidate-on-write); сложнее согласовать это при нескольких инстансах приложения и при сбоях (если удаление кеша не выполнилось, данные останутся устаревшими до истечения TTL).
- **Частые ошибки:** Забыть инвалидировать кеш в одном из мест обновления данных; удалять кеш до коммита транзакции в БД, тогда следующий запрос может закешировать всё ещё старое значение.

**Пример / кейс**
```python
def update_product_price(product_id: int, new_price: float):
    db.update_price(product_id, new_price)  # сначала БД
    redis.delete(f"product:{product_id}")   # потом инвалидация кеша
```
Проверка: после вызова update_product_price повторный GET /products/{id} должен вернуть новую цену, а не закешированную старую.

### 339. [Q-03-07-0339] Что такое очередь сообщений (message queue), зачем она нужна между сервисами?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Очередь сообщений — промежуточный сервис, который принимает сообщения от отправителей и хранит их до обработки получателем, развязывая отправителя и обработчика во времени и скорости.

**Разбор**
- **Как это работает:** Producer публикует сообщение в очередь/топик; consumer читает сообщения и подтверждает обработку (ack).
- **На практике:** Используют для фоновых задач, интеграции сервисов, сглаживания пиков нагрузки (буферизация); примеры — RabbitMQ, Kafka, SQS.
- **Частые ошибки:** Считать очередь гарантией мгновенной обработки; не учитывать, что сообщение может быть доставлено повторно (at-least-once).

**Пример / кейс**
```python
# producer
channel.basic_publish(exchange="", routing_key="emails", body=json.dumps(payload))

# consumer
def callback(ch, method, properties, body):
    process_email(json.loads(body))
    ch.basic_ack(delivery_tag=method.delivery_tag)
```
Проверка: в UI RabbitMQ/Kafka видно количество сообщений в очереди/топике и скорость их потребления (consumer lag).

### 340. [Q-03-07-0340] Чем отличаются producer и consumer в очереди сообщений?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Producer — часть системы, которая создаёт и отправляет сообщения в очередь; consumer — часть, которая читает сообщения из очереди и обрабатывает их; это разные роли, часто в разных сервисах.

**Разбор**
- **Как это работает:** Producer не знает, кто и когда обработает сообщение; consumer подписывается на очередь/топик и обрабатывает сообщения в своём темпе.
- **На практике:** Один producer может иметь несколько consumer'ов для масштабирования обработки; в Kafka несколько consumer'ов в одной consumer group делят партиции между собой.
- **Частые ошибки:** Путать широковещательную доставку (каждый consumer получает копию, fanout) с разделением нагрузки (конкурирующие consumer'ы делят сообщения).

**Пример / кейс**
```text
Producer -> Queue "orders.created" -> [Consumer A, Consumer B]  # конкурируют, делят сообщения
```
Проверка: при запуске двух инстансов consumer'а на одной очереди каждое сообщение обрабатывается ровно одним из них (видно по разным worker_id в логах обработки).

### 341. [Q-03-07-0341] Что такое идемпотентность операции? Приведите пример идемпотентного и неидемпотентного HTTP-метода.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Идемпотентная операция — та, повторное выполнение которой с тем же входом даёт тот же результат, что и однократное; пример идемпотентного метода — PUT/DELETE, неидемпотентного — POST создания ресурса.

**Разбор**
- **Как это работает:** Идемпотентность касается эффекта операции на систему, а не ответа — повторный PUT с тем же телом оставит ресурс в том же состоянии.
- **На практике:** GET, PUT, DELETE по HTTP-семантике идемпотентны; POST обычно не идемпотентен, так как повторный вызов может создать второй ресурс.
- **Частые ошибки:** Путать идемпотентность с безопасностью запроса (safe methods); считать, что идемпотентность гарантируется автоматически фреймворком.

**Пример / кейс**
```http
PUT /users/42 HTTP/1.1
Content-Type: application/json

{"name": "Иван"}
```
Повторный такой же PUT оставит пользователя 42 с именем «Иван» — результат не изменится.
Проверка: вызвать запрос дважды подряд и убедиться, что состояние ресурса и количество записей в БД одинаковы после первого и второго вызова.

### 342. [Q-03-07-0342] Что произойдёт, если клиент повторно отправит один и тот же POST-запрос на создание заказа?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Без защиты от дублирования повторный POST с одинаковыми данными создаст второй заказ в БД, так как POST по умолчанию не идемпотентен — сервер просто выполнит вставку ещё раз.

**Разбор**
- **Как это работает:** Каждый POST-запрос интерпретируется сервером как новая команда «создать», независимо от того, что предыдущий запрос уже создал такой же заказ.
- **На практике:** Повтор может произойти из-за сетевого сбоя, ретраев на уровне клиента/балансировщика или двойного клика пользователя; без защиты появляются дублирующиеся заказы и двойное списание денег.
- **Частые ошибки:** Считать эту проблему редкой и игнорировать её при проектировании; решать проблему только на фронтенде (блокировка кнопки), что не защищает от сетевых ретраев.

**Пример / кейс**
```python
@app.post("/orders")
def create_order(data: OrderIn):
    order = Order(**data.dict())
    db.add(order)
    db.commit()
    return order
```
Проверка: отправить этот запрос дважды с одинаковым телом (например, через curl в цикле) — без идемпотентной защиты в БД появятся две строки заказа.

- **Как это работает:** Клиент перехватывает ошибку/таймаут и повторяет запрос через паузу, иногда с ограничением числа попыток.

```python
for attempt in range(3):
```

Проверка: смоделировать временную недоступность сервиса (503) на первые 2 попытки — 3-я попытка должна пройти успешно, логи показывают увеличивающуюся задержку.

### 347. [Q-03-07-0347] Что такое eventual consistency простыми словами? Приведите пример.

**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Eventual consistency — модель, при которой после изменения данных все читатели со временем увидят новое значение, но не гарантируется, что это произойдёт немедленно.

**Разбор**
- **Как это работает:** Обновление сначала применяется в одном узле/реплике, а затем асинхронно распространяется на остальные; в промежутке разные читатели могут видеть разные версии данных.
- **На практике:** Допустимо для данных, где кратковременная несвежесть не критична (счётчик лайков, список комментариев); требует продуманного UX, чтобы пользователь не был сбит с толку расхождениями.
- **Частые ошибки:** Применять eventual consistency там, где бизнес требует немедленной точности (остаток на счёте при переводе денег), без явного решения о допустимости такого риска.

**Пример / кейс**
```text
t0: пользователь обновляет имя профиля в Service A
t0+200ms: Service B (кеш профиля) ещё отдаёт старое имя
t0+2s: Service B получает событие обновления и синхронизируется
```
Проверка: тест, повторяющий чтение профиля сразу после обновления и через несколько секунд, показывает временное расхождение, которое исчезает после задержки репликации.

### 348. [Q-03-07-0348] Что такое strong consistency, чем отличается от eventual?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Strong consistency — гарантия, что после успешного завершения операции обновления любое последующее чтение увидит это обновление немедленно, без промежуточного «старого» состояния.

**Разбор**
- **Как это работает:** Обычно достигается чтением/записью через единственный авторитетный узел (primary) или синхронным согласованием между узлами перед подтверждением записи.
- **На практике:** Даёт предсказуемость, но стоит дороже по латентности и доступности; применяют там, где цена рассинхронизации высока (финансовые балансы, уникальные ограничения).
- **Частые ошибки:** Считать, что «одна БД» автоматически даёт strong consistency при наличии реплик для чтения — чтение с асинхронной read-реплики может вернуть устаревшие данные.

**Пример / кейс**
```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```
Проверка: сразу после COMMIT любой клиент, читающий с primary (или через кворумное чтение), видит обновлённые балансы без исключений.

### 349. [Q-03-07-0349] Чтение кода: найдите проблему в обработчике, который может упасть с 500 при недоступности внешнего сервиса.

**Разбор**
- **Как это работает:** Исключение из httpx.get (например ConnectError, TimeoutException) не перехвачено, значит оно «всплывёт» до обработчика фреймворка, который вернёт generic 500.
- **На практике:** Нужно явно перехватывать ожидаемые сетевые ошибки и возвращать осмысленный ответ клиенту (502/503) либо fallback-значение; также логировать причину сбоя для диагностики.

Код ниже содержит намеренную проблему — нет обработки ошибок:
```python
@app.get("/weather")
def get_weather():
    response = httpx.get("https://weather-api/current")  # может выбросить исключение
    return response.json()
```
Исправление:
```python
@app.get("/weather")
def get_weather():
    try:
        response = httpx.get("https://weather-api/current", timeout=5)
        response.raise_for_status()
        return response.json()
    except httpx.HTTPError:
        raise HTTPException(status_code=503, detail="weather service unavailable")
```
Проверка: смоделировать недоступность weather-api — исправленный обработчик должен вернуть 503 с понятным сообщением, а не упасть с 500.

Service discovery — механизм, с помощью которого сервис находит актуальный сетевой адрес другого сервиса, не используя захардкоженный IP, так как адреса инстансов могут меняться.

- **Как это работает:** Сервис регистрируется в реестре (Consul, Kubernetes Service, Eureka) при старте; вызывающий сервис запрашивает реестр (или DNS) и получает текущий адрес/список адресов.
- **На практике:** В Kubernetes это часто просто DNS-имя Service, которое резолвится в текущие адреса подов через внутренний DNS; реестр избавляет от необходимости вручную обновлять конфигурацию при масштабировании.

```python
response = httpx.get("http://payment-service.default.svc.cluster.local/charge")
```

### 352. [Q-03-07-0352] В чём разница между REST и RPC (общее представление)?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
REST моделирует взаимодействие как операции над ресурсами (GET/POST/PUT/DELETE на URL), а RPC моделирует взаимодействие как вызов удалённой функции/метода с произвольным именем и параметрами (например через gRPC).

**Разбор**
- **Как это работает:** REST опирается на единообразную семантику HTTP-методов и статус-кодов вокруг ресурсов; RPC описывает набор методов-процедур (CreateOrder, CancelOrder), часто через бинарный протокол (protobuf в gRPC).
- **На практике:** REST удобен для публичных/веб-API и браузерных клиентов, легко кешируется по URL; gRPC выгоден для внутреннего взаимодействия сервисов с высокими требованиями к производительности и строгой типизации.
- **Частые ошибки:** Пытаться «причесать» под REST операции, которые по сути — команды, вместо явного RPC-подобного эндпоинта-действия; выбирать gRPC только из-за «модности» без реальной потребности.

**Пример / кейс**
```protobuf
service OrderService {
  rpc CreateOrder (CreateOrderRequest) returns (OrderReply);
}
```
против
```http
POST /orders HTTP/1.1
Content-Type: application/json
```
Проверка: для RPC клиент генерируется из .proto-файла и проверяет типы на этапе компиляции; для REST типы проверяются во время выполнения (валидация JSON-схемы).

### 353. [Q-03-07-0353] Что такое graceful shutdown сервиса и почему это важно?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Graceful shutdown — корректное завершение работы сервиса при сигнале остановки: сервис прекращает принимать новые запросы, дожидается завершения текущих и закрывает ресурсы, чтобы не терять данные и не рвать запросы клиентов.

**Разбор**
- **Как это работает:** Процесс перехватывает сигнал (SIGTERM от Kubernetes перед удалением пода), прекращает приём новых подключений, ждёт завершения активных обработчиков (с ограничением по времени), закрывает ресурсы.
- **На практике:** Важно для consumer'ов очередей (не бросать сообщение в середине обработки) и серверов с долгими запросами; Kubernetes даёт ограниченное время (terminationGracePeriodSeconds) до принудительного kill.
- **Частые ошибки:** Игнорировать SIGTERM и ждать SIGKILL (in-flight запросы теряются); не выставлять под временно «не готовым» перед остановкой, из-за чего балансировщик продолжает слать трафик.

**Пример / кейс**
```python
import signal

def handle_sigterm(signum, frame):
    readiness_flag.set(False)   # перестать принимать новый трафик
    wait_for_inflight_requests(timeout=25)

signal.signal(signal.SIGTERM, handle_sigterm)
```

### 354. [Q-03-07-0354] Что такое circuit breaker в двух словах (концепция без деталей реализации)?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Junior

**Короткий ответ**<br>
Circuit breaker — паттерн, который временно «отключает» вызовы к зависимости после серии сбоев, сразу возвращая ошибку/fallback без реального обращения, давая зависимости время восстановиться.

**Разбор**
- **Как это работает:** Breaker отслеживает частоту ошибок; при превышении порога переходит в состояние «открыт» (вызовы блокируются сразу); после паузы переходит в «полуоткрыт» и пробует тестовые вызовы.
- **На практике:** Защищает вызывающий сервис от долгого ожидания таймаутов к уже деградировавшей зависимости и предотвращает усиление нагрузки на неё.
- **Частые ошибки:** Путать circuit breaker с retry (это разные, дополняющие друг друга механизмы); не предусматривать осмысленный fallback при открытом breaker'е.

**Пример / кейс**
```text
Состояния: CLOSED -> (много ошибок) -> OPEN -> (таймаут) -> HALF_OPEN -> (успех) -> CLOSED
                                                           -> (ошибка) -> OPEN
```
Проверка: смоделировать серию отказов внешнего сервиса — breaker должен перейти в OPEN, и последующие вызовы должны сразу завершаться fallback-ответом без реального сетевого обращения.

```python
def fetch_rate():
```

Проверка: смоделировать зависший fx-rates — исправленная версия должна завершиться ошибкой через ~5 секунд, а не висеть бесконечно.

```text
Клиенты -> [единственный инстанс API] -> БД (с репликой)
```

Проверка: имитировать падение единственного инстанса API — если весь трафик перестаёт обслуживаться, это подтверждает SPOF; после добавления второго инстанса за балансировщиком тест должен проходить без простоя.

### 359. [Q-03-07-0359] Как спроектировать границы сервиса при выделении функциональности из монолита (например, модуля «уведомления»)?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
Границы сервиса следует проводить по бизнес-домену и данным, которыми он владеет (bounded context), а не по техническим слоям; «уведомления» выделяются в отдельный сервис, если у них свой жизненный цикл данных и узкий контракт взаимодействия с остальной системой.

**Разбор**
- **Как это работает:** Сначала определяют, какие данные и операции логически принадлежат домену «уведомления» (шаблоны, история отправок, настройки каналов), затем формализуют интерфейс (отправить уведомление, получить статус) и переносят только эту ответственность.
- **На практике:** Хороший признак готовности — модуль уже внутри монолита слабо связан с остальными (мало взаимных вызовов, собственная таблица/схема данных), и команда может развивать и деплоить notification независимо, не блокируя релизы остальной системы.

**Пример / кейс**
```text
До: OrderService -> notifications_table (общая БД монолита)
После: OrderService -- событие "order.created" --> Notification Service -> своя БД
```
Проверка: после выделения Notification Service должен нормально деплоиться, мигрировать схему и откатываться независимо от деплоя OrderService — это проверяется отдельным pipeline CI/CD.

### 360. [Q-03-07-0360] Какие признаки говорят, что пора разделять монолит на отдельные сервисы, а какие — что пока не стоит?

### 361. [Q-03-07-0361] Чем отличается cache-aside от write-through стратегии кеширования? Когда что выбрать?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
Cache-aside — приложение само читает из кеша, при промахе идёт в БД и кладёт результат в кеш; write-through — запись сразу идёт и в БД, и в кеш синхронно в рамках одной операции обновления.

**Разбор**
- **Как это работает:** При cache-aside кеш заполняется лениво по факту чтения, инвалидация — отдельный шаг при записи; при write-through обновление кеша встроено в транзакцию записи, и кеш никогда не «пустой» для изменённых данных.
- **На практике:** Cache-aside выбирают, когда читаемые данные — лишь часть всех данных; write-through — когда критична согласованность кеша сразу после записи и профиль чтения предсказуем.
- **Частые ошибки:** При cache-aside забывать инвалидировать кеш при записи; при write-through не обрабатывать сбой записи в кеш как некритичную ошибку — запись в БД должна проходить, даже если кеш временно недоступен.

**Пример / кейс**
```python
# cache-aside
def get_user(user_id):
    data = cache.get(key(user_id))
    if data is None:
        data = db.get_user(user_id)
        cache.set(key(user_id), data, ex=300)
    return data

# write-through
def update_user(user_id, fields):
    db.update_user(user_id, fields)
    cache.set(key(user_id), db.get_user(user_id), ex=300)
```
Проверка: для write-through сразу после update_user повторный get_user должен попасть в кеш (cache hit) с новыми данными.

### 362. [Q-03-07-0362] Что такое cache stampede и как его предотвратить?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
Cache stampede — ситуация, когда популярный кешированный ключ истекает, и множество одновременных запросов «проваливаются» в основной источник данных сразу, создавая всплеск нагрузки на БД; предотвращают блокировкой пересчёта, ранним обновлением или джиттером TTL.

**Разбор**
- **Как это работает:** Без защиты каждый из N одновременных запросов, увидевших cache miss, независимо идёт в БД за одними и теми же данными и независимо записывает результат обратно.
- **На практике:** Решения — распределённая блокировка (только один процесс пересчитывает), stale-while-revalidate (отдавать старое значение во время фонового обновления), случайный разброс (jitter) TTL.
- **Частые ошибки:** Ставить одинаковый фиксированный TTL для всех записей, закешированных в один момент (например, при прогреве) — массовое синхронное истечение почти гарантирует stampede под нагрузкой.

**Пример / кейс**
```python
def get_or_lock(key, compute_fn, ttl=300):
    value = cache.get(key)
    if value is not None:
        return value
    lock_acquired = cache.set(f"lock:{key}", "1", ex=10, nx=True)
    if lock_acquired:
        value = compute_fn()
        cache.set(key, value, ex=ttl + random.randint(0, 30))  # jitter
        cache.delete(f"lock:{key}")
        return value
    time.sleep(0.05)
    return cache.get(key) or compute_fn()
```
Проверка: нагрузочный тест с одновременным истечением популярного ключа должен показывать единичный всплеск запросов к БД, а не N-кратный.

### 363. [Q-03-07-0363] Как обеспечить согласованность кеша и БД при обновлении данных (race condition read-after-write)?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
Между записью в БД и обновлением/удалением кеша может вклиниться параллельное чтение, которое закеширует устаревшее значение; надёжнее удалять кеш после коммита БД-транзакции и использовать короткий TTL как страховочную сетку.

**Разбор**
- **Как это работает:** Если порядок — «удалить кеш, затем обновить БД», параллельный читатель между шагами может прочитать из БД старое значение и закешировать его уже после удаления, оставив устаревшие данные до TTL.
- **На практике:** Полностью убрать гонку без блокировок или версионирования сложно; снижают риск коротким TTL, версионированием записи (кешировать с номером версии) либо последовательной обработкой через очередь событий.
- **Частые ошибки:** Считать, что порядок «сначала БД, потом кеш» полностью устраняет гонку — он лишь снижает окно её возникновения; не задавать TTL вообще при invalidate-on-write.

**Пример / кейс**
```python
def update_price(product_id, new_price):
    db.update_price(product_id, new_price)   # 1) обновить БД
    cache.delete(f"product:{product_id}")    # 2) затем инвалидировать кеш
    # окно гонки: read, начавшийся до (1) и завершившийся после (2), может закешировать старое значение
```
Проверка: нагрузочный тест с параллельными чтениями и одним обновлением должен, при коротком TTL, гарантировать, что расхождение кеша и БД не живёт дольше TTL.

### 364. [Q-03-07-0364] Чем отличаются гарантии доставки at-most-once, at-least-once и exactly-once в очередях сообщений?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
At-most-once — сообщение может быть потеряно, но не дублировано; at-least-once — гарантированно доставляется, но может продублироваться; exactly-once на практике достигается не самим брокером, а комбинацией at-least-once доставки и идемпотентной обработки на стороне consumer'а.

**Разбор**
- **Как это работает:** At-most-once — consumer подтверждает (ack) до обработки, и при сбое между ack и обработкой сообщение теряется; at-least-once — ack после успешной обработки, и при сбое до ack брокер повторно доставит сообщение.
- **На практике:** Большинство систем (Kafka, RabbitMQ с manual ack) по умолчанию работают в режиме at-least-once, и ответственность за отсутствие побочных эффектов от дублей перекладывается на consumer.
- **Частые ошибки:** Путать «exactly-once delivery» брокера с «exactly-once processing» — consumer может обработать сообщение дважды из-за собственного сбоя; считать, что включение exactly-once semantics в Kafka решает проблему без идемпотентных внешних side-эффектов.

**Пример / кейс**
```python
# at-least-once: ack после обработки
def callback(ch, method, properties, body):
    process_payment(json.loads(body))      # если упадёт здесь после обработки, но до ack —
    ch.basic_ack(delivery_tag=method.delivery_tag)  # брокер повторит доставку
```
Проверка: смоделировать падение процесса сразу после process_payment, но до basic_ack — при перезапуске брокер должен повторно доставить то же сообщение; идемпотентная обработка должна не допустить повторного списания.

### 365. [Q-03-07-0365] Как реализовать идемпотентный consumer для очереди с гарантией at-least-once?

**Короткий ответ**<br>
Идемпотентный consumer хранит признак уже обработанных сообщений (по уникальному ключу) и, получив дубликат, пропускает повторную обработку, возвращая тот же эффект, что и при первой обработке.

**Разбор**
- **Как это работает:** При получении сообщения consumer сначала проверяет, есть ли запись об обработке message_id; если есть — подтверждает получение без повторного эффекта; если нет — выполняет обработку и атомарно фиксирует факт обработки вместе с результатом.
- **На практике:** Ключ идемпотентности должен быть стабильным и уникальным для бизнес-операции (order_id + event_type), а не техническим delivery tag брокера, который меняется при каждой redelivery.
- **Частые ошибки:** Хранить «обработано» только в памяти процесса (при перезапуске теряется); проверять и фиксировать факт обработки в двух разных нетранзакционных шагах, оставляя окно гонки при параллельной обработке дублей.

**Пример / кейс**
```sql
CREATE TABLE processed_messages (
    message_id UUID PRIMARY KEY,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```
```python
def handle(message):
    with db.transaction():
        inserted = db.execute(
            "INSERT INTO processed_messages (message_id) VALUES (%s) ON CONFLICT DO NOTHING RETURNING message_id",
            [message.id],
        )
        if not inserted:
            return  # уже обработано
        apply_business_effect(message)
```
Проверка: отправить одно и то же сообщение дважды в consumer — бизнес-эффект должен применится ровно один раз.

### 366. [Q-03-07-0366] Что такое паттерн Transactional Outbox и какую проблему он решает?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
Transactional Outbox решает проблему dual write, записывая событие в отдельную таблицу outbox в той же транзакции БД, что и бизнес-изменение, а отдельный процесс затем читает outbox и публикует события в очередь.

**Разбор**
- **Как это работает:** Бизнес-операция и вставка строки в outbox происходят в одной локальной транзакции БД атомарно; relay-процесс (poller или CDC, например Debezium) читает новые строки outbox и публикует их в брокер.
- **На практике:** Избавляет от ситуации, когда БД-транзакция закоммитилась, а публикация в очередь не прошла; relay обеспечивает at-least-once публикацию, и consumer всё равно должен быть идемпотентным.
- **Частые ошибки:** Публиковать событие до коммита транзакции БД (если транзакция откатится — событие о несуществующем изменении уже ушло); публиковать после коммита отдельным не атомарным вызовом без outbox.

**Пример / кейс**
```sql
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 42;
INSERT INTO outbox (id, event_type, payload, created_at)
VALUES (gen_random_uuid(), 'order.paid', '{"order_id": 42}', now());
COMMIT;
```
Проверка: смоделировать сбой relay-процесса сразу после коммита — при перезапуске relay должен найти неотправленную строку outbox и опубликовать событие.

### 367. [Q-03-07-0367] В чём проблема распределённой транзакции между БД и очередью сообщений (dual write problem)?

**Короткий ответ**<br>
При раздельной записи в БД и публикации в очередь без общей транзакции возможна рассинхронизация: БД обновилась, а сообщение не отправлено (или наоборот), поскольку это два независимых ресурса без атомарной гарантии между ними.

**Разбор**

- **На практике:** Двухфазные транзакции (XA) между БД и большинством брокеров почти не используются из-за сложности и блокировок; практическое решение — Transactional Outbox либо change data capture.

**Пример / кейс**
```python
def mark_order_paid(order_id):
    db.update_status(order_id, "paid")  # коммит произошёл
    # --- если процесс упадёт здесь, событие никогда не будет опубликовано ---
    queue.publish("order.paid", {"order_id": order_id})
```
Проверка: смоделировать падение процесса между db.update_status и queue.publish — без outbox событие теряется навсегда, что подтверждает наличие проблемы dual write.

```http
{"amount": 1500, "currency": "RUB"}
```

```sql
CREATE TABLE idempotency_keys (

    status TEXT NOT NULL,

);
```
Проверка: отправить один и тот же запрос с одинаковым Idempotency-Key дважды — второй ответ должен быть идентичен первому, а в БД должна появиться только одна запись платежа.

**Короткий ответ**<br>
Saga — последовательность локальных транзакций в разных сервисах с компенсирующими действиями при сбое; 2PC — протокол, при котором координатор синхронно согласует и либо коммитит, либо откатывает транзакцию во всех участниках атомарно, блокируя ресурсы до завершения голосования.

### 370. [Q-03-07-0370] Как диагностировать каскадный отказ сервисов (cascading failure) при высокой нагрузке?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
Каскадный отказ диагностируют по цепочке деградации: растут задержки/ошибки одной зависимости, затем потоки вызывающего сервиса оказываются заняты ожиданием, что приводит к исчерпанию ресурсов и отказу уже самого вызывающего сервиса для всех клиентов.

**Разбор**
- **Как это работает:** Без таймаутов/circuit breaker медленная зависимость «съедает» воркеры вызывающего сервиса; когда свободных воркеров не остаётся, сервис не может обслуживать вообще никакие запросы, и отказ распространяется дальше по цепочке.
- **На практике:** Диагностика начинается с метрик — рост latency и error rate на конкретной исходящей зависимости, рост использования пула соединений/потоков, затем рост ошибок на сервисе в целом; трассировка помогает увидеть, что все «зависшие» запросы ждут один и тот же downstream-вызов.
- **Частые ошибки:** Лечить симптом (увеличивать размер пула воркеров), не устраняя причину (отсутствие таймаутов и изоляции); не разделять ресурсы (bulkhead) между вызовами к разным зависимостям.

**Пример / кейс**
```text
Метрики при инциденте:
- payment-service p99 latency: 200ms -> 15000ms (деградация зависимости)
- order-service thread pool usage: 40% -> 100% (воркеры заняты ожиданием payment-service)
- order-service error rate (все эндпоинты): 0.1% -> 80% (каскад)
```
Проверка: после добавления таймаута и circuit breaker на вызов к payment-service повторный нагрузочный тест с деградировавшей зависимостью должен показывать, что order-service продолжает обслуживать не связанные запросы с нормальным error rate.

### 371. [Q-03-07-0371] Как реализовать retry с экспоненциальной задержкой и джиттером? Зачем нужен джиттер?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
Экспоненциальная задержка увеличивает паузу между попытками, снижая нагрузку на восстанавливающуюся зависимость; джиттер добавляет случайный разброс, чтобы множество клиентов, начавших ретраить одновременно, не синхронизировались и не создавали повторные волновые всплески нагрузки.

**Разбор**
- **Как это работает:** Базовая задержка умножается на 2 в степени номера попытки и ограничивается максимумом (cap); джиттер — случайное значение, добавляемое или умножаемое к этой задержке (full jitter, equal jitter).
- **На практике:** Без джиттера сотни клиентов, получивших ошибку в один момент, будут ретраить синхронно по одному графику, создавая повторяющиеся пики нагрузки (thundering herd); с джиттером повторные попытки размазываются по времени.
- **Частые ошибки:** Ставить фиксированное количество ретраев без ограничения общего времени ожидания; забывать ограничить максимальную задержку (cap), получая неоправданно долгие паузы на поздних попытках.

**Пример / кейс**
```python
import random

def backoff_delay(attempt, base=1.0, cap=30.0):
    exp = min(cap, base * (2 ** attempt))
    return random.uniform(0, exp)  # full jitter

for attempt in range(5):
    try:
        return call_external()
    except TransientError:
        time.sleep(backoff_delay(attempt))
```
Проверка: нагрузочный тест с временной недоступностью внешнего сервиса для 100 одновременных клиентов должен показывать размазанное во времени распределение повторных попыток, а не синхронные пики.

- **На практике:** При необходимости удалить/изменить поле вводят период deprecation — поле помечается устаревшим, но продолжает поддерживаться параллельно с новым, пока потребители не перейдут; миграцию отслеживают по метрикам использования старого поля.

**Пример / кейс**

```json
{"id": 1, "total": 1500}
// совместимое изменение — добавили поле, не трогая старое
{"id": 1, "total": 1500, "total_formatted": "1 500 ₽"}
```
Проверка: регрессионный тест десериализации старого клиентского кода на новый ответ API должен проходить без изменений — старый код просто не замечает новое поле.

**Короткий ответ**<br>
Bulkhead изолирует ресурсы (пулы соединений, потоки) для разных зависимостей так, чтобы перегрузка/сбой одной зависимости не исчерпывала общий ресурс и не блокировала работу с остальными.

- **Как это работает:** Вместо одного общего пула соединений/потоков на все исходящие вызовы выделяют отдельный пул с ограниченным размером под каждую зависимость; если пул для зависимости A исчерпан, вызовы к B продолжают использовать свой отдельный пул.
- **На практике:** Применяют вместе с таймаутами и circuit breaker — bulkhead ограничивает «ширину» ущерба, а breaker снижает число бесполезных попыток к деградировавшей зависимости.
- **Частые ошибки:** Использовать единственный общий thread pool для вызовов к десяткам внешних сервисов; делать bulkhead слишком маленьким, что искусственно ограничивает throughput даже при здоровой зависимости.

**Пример / кейс**
```python
payment_pool = httpx.Client(limits=httpx.Limits(max_connections=10))
analytics_pool = httpx.Client(limits=httpx.Limits(max_connections=5))
```
Проверка: нагрузочный тест, искусственно замедляющий analytics-сервис, должен показывать, что запросы через payment_pool продолжают обслуживаться с нормальной latency.

### 375. [Q-03-07-0375] Как обеспечить graceful degradation сервиса при недоступности одной из зависимостей?

**Короткий ответ**<br>
Сервис при недоступности опциональной зависимости продолжает отдавать урезанный, но полезный результат (например, без персональных рекомендаций) вместо полного отказа всего запроса, когда деградировавшая часть не критична для основной функции.

**Разбор**
- **Как это работает:** Код явно выделяет «обязательные» и «опциональные» зависимости для запроса; при сбое опциональной используется fallback (кешированное/дефолтное значение), а при сбое обязательной — явная ошибка.
- **На практике:** Решение, какая зависимость опциональна, принимается на уровне бизнес-требований; fallback часто комбинируют с circuit breaker — при открытом breaker сразу используется fallback без попытки реального вызова.
- **Частые ошибки:** Делать весь запрос зависимым от самой нестабильной подсистемы, хотя она лишь дополняет контент; не тестировать сценарий деградации отдельно — fallback-код часто остаётся непроверенным.

**Пример / кейс**
```python
def get_product_page(product_id):
    product = get_product_core(product_id)  # обязательно, без fallback
    try:
        recommendations = get_recommendations(product_id, timeout=1)
    except (TimeoutError, CircuitOpenError):
        recommendations = []  # деградация — страница рендерится без блока рекомендаций
    return render_page(product, recommendations)
```
Проверка: смоделировать недоступность recommendation-сервиса — страница товара должна отрендериться с кодом 200 и пустым блоком рекомендаций, а не вернуть ошибку целиком.

### 376. [Q-03-07-0376] Как отследить и устранить утечку соединений с БД (connection pool exhaustion) в production?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
Исчерпание пула соединений диагностируют по росту времени ожидания свободного соединения и ошибкам «pool exhausted»; типичные причины — соединения не возвращаются в пул, слишком маленький размер пула или долгие транзакции, держащие соединение дольше необходимого.

**Разбор**
- **Как это работает:** Пул хранит ограниченное число открытых соединений; каждый запрос берёт соединение на время работы и должен его вернуть; при ошибке логики без try/finally или context manager пул постепенно исчерпывается.
- **На практике:** Сначала смотрят метрики пула (используемые/свободные соединения), затем ищут в коде места без context manager, долгие транзакции (например, вызов внешнего API внутри открытой транзакции БД) и утечки в обработчиках исключений.
- **Частые ошибки:** Увеличивать размер пула как «быстрое решение» без поиска утечки; держать транзакцию БД открытой во время сетевого вызова к другому сервису.

**Пример / кейс**
Код ниже содержит намеренную проблему — соединение не гарантированно освобождается:
```python
def get_user(user_id):
    conn = pool.get_connection()
    cursor = conn.execute("SELECT * FROM users WHERE id = %s", [user_id])
    return cursor.fetchone()  # conn.close()/release() никогда не вызывается
```
Исправление:
```python
def get_user(user_id):
    with pool.connection() as conn:  # context manager гарантирует возврат в пул
        cursor = conn.execute("SELECT * FROM users WHERE id = %s", [user_id])
        return cursor.fetchone()
```
Проверка: метрика "использованные соединения пула" должна возвращаться к базовому уровню после каждого запроса; до исправления метрика монотонно растёт до исчерпания пула.

### 377. [Q-03-07-0377] Что такое timeout budget при цепочке вызовов A → B → C и как его распределить?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
Timeout budget — распределение общего допустимого времени ответа между последовательными вызовами в цепочке так, чтобы таймаут каждого следующего вызова был меньше оставшегося бюджета вызывающей стороны, а не просто одинаковым фиксированным значением на каждом уровне.

**Разбор**
- **Как это работает:** Если у A таймаут на весь запрос 5 секунд, а внутри A вызывает B с таймаутом 5 секунд, а B внутри вызывает C с таймаутом 5 секунд, то в худшем случае A может ждать существенно дольше 5 секунд суммарно — таймауты должны уменьшаться по цепочке.
- **На практике:** Общий SLA делят так, чтобы каждый следующий вызов получал заведомо меньший таймаут с запасом на собственную обработку, и передают оставшийся бюджет явно (например, через заголовок deadline) там, где это поддерживается.
- **Частые ошибки:** Задавать один и тот же таймаут на каждом уровне цепочки независимо от бюджета вызывающей стороны; не передавать информацию об оставшемся времени вглубь цепочки.

**Пример / кейс**
```text
A (клиентский таймаут 5с)
 -> B (таймаут вызова B из A: 4с)
     -> C (таймаут вызова C из B: 2.5с, с запасом на обработку в B)
```
Проверка: нагрузочный тест с искусственно замедленным C (3с) должен показывать, что B вовремя обрывает вызов по своему таймауту (2.5с) и возвращает A осмысленную ошибку в пределах бюджета A.

### 380. [Q-03-07-0380] Что такое CQRS и в каком случае его применение оправдано?

**Короткий ответ**<br>
CQRS — разделение модели записи (команды) и модели чтения (запросы), часто с отдельным денормализованным хранилищем для чтения; оправдан, когда профиль чтения сильно отличается от профиля записи по нагрузке или структуре данных.

**Разбор**
- **Как это работает:** Команды изменяют «источник правды» (write model) по доменным правилам; события об изменениях асинхронно проецируются в read-модель, заранее денормализованную под конкретные запросы интерфейса.

**Пример / кейс**
```text
Write model: нормализованные таблицы orders, order_items, доменная валидация
Read model: денормализованная таблица order_summary_view (order_id, user_name, total, status),
            обновляется асинхронно по событию "order.changed"
```
Проверка: после создания заказа тест должен учитывать задержку проекции — проверять появление записи в order_summary_view с повторными попытками, а не ожидать её мгновенно.

### 381. [Q-03-07-0381] Как диагностировать проблему «N+1 запросов» на уровне межсервисного взаимодействия?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
Межсервисный N+1 — это когда сервис A, обрабатывая список из N элементов, делает N отдельных вызовов к сервису B вместо одного batch-вызова, что резко увеличивает суммарную латентность и нагрузку на сеть и на сервис B.

**Разбор**
- **Как это работает:** Типичный паттерн — получить список заказов, а затем в цикле для каждого заказа отдельно запросить у User Service данные покупателя, хотя почти все запросы идут к одному и тому же сервису.
- **На практике:** Решения — batch-эндпоинт на стороне B, предварительная денормализация часто нужных полей, или параллельное выполнение вызовов вместо последовательного, если batch невозможен.
- **Частые ошибки:** Распараллелить N вызовов вместо устранения их количества — это ускоряет ответ для A, но не снижает число запросов к B; добавлять batch-эндпоинт без ограничения на размер батча.

**Пример / кейс**
Намеренная проблема — N+1 вызовов:
```python
orders = get_orders(user_id=None, limit=100)
for order in orders:
    order.customer = user_service.get_user(order.user_id)  # 100 отдельных HTTP-вызовов
```
Исправление:
```python
orders = get_orders(user_id=None, limit=100)
user_ids = list({o.user_id for o in orders})
users_by_id = user_service.get_users_batch(user_ids)  # 1 вызов вместо N
for order in orders:
    order.customer = users_by_id[order.user_id]
```
Проверка: профилировщик должен показывать переход от N исходящих HTTP-запросов до 1 запроса на ту же страницу списка заказов.

### 382. [Q-03-07-0382] Как спроектировать dead letter queue (DLQ) и что с ней делать дальше?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
DLQ — отдельная очередь, куда сообщение перемещается после превышения числа неудачных попыток обработки, чтобы не блокировать обработку остальных сообщений и дать возможность разобрать проблемное сообщение отдельно.

**Разбор**
- **Как это работает:** Consumer при повторной ошибке обработки (после N попыток или определённого вида ошибки) явно отправляет сообщение в DLQ вместо бесконечного retry или потери; основная очередь продолжает обрабатывать следующие сообщения.
- **На практике:** Сообщения в DLQ должны сопровождаться метаданными об ошибке; дальше с DLQ работают через мониторинг (алерт при появлении новых сообщений), ручной разбор либо автоматический replay после исправления причины.
- **Частые ошибки:** Не мониторить DLQ вообще — сообщения тихо скапливаются; отправлять в DLQ сообщения с временными ошибками без достаточного числа retry перед этим.

**Пример / кейс**
```python
def callback(ch, method, properties, body):
    try:
        process(json.loads(body))
        ch.basic_ack(delivery_tag=method.delivery_tag)
    except PermanentError:
        channel.basic_publish(exchange="", routing_key="orders.dlq", body=body)
        ch.basic_ack(delivery_tag=method.delivery_tag)
    except TransientError:
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=True)
```
Проверка: сообщение с невалидным форматом должно оказаться в очереди orders.dlq после одной обработки, не блокируя обработку следующих валидных сообщений.

### 383. [Q-03-07-0383] Как обеспечить идемпотентность при обработке платежа с внешним провайдером при повторной доставке webhook?

- **На практике:** Важно отличать event_id конкретного уведомления от бизнес-идентификатора платежа — провайдер может присылать несколько разных событий по одному платежу (created, succeeded, refunded), и каждое обрабатывается идемпотентно по своему event_id.

**Пример / кейс**
```sql
CREATE TABLE webhook_events (
    event_id TEXT PRIMARY KEY,
    payment_id TEXT NOT NULL,
    event_type TEXT NOT NULL,
    received_at TIMESTAMPTZ DEFAULT now()
);
```

```python
def handle_webhook(payload):

        inserted = db.execute(
            "INSERT INTO webhook_events (event_id, payment_id, event_type) VALUES (%s,%s,%s) ON CONFLICT DO NOTHING RETURNING event_id",

        if not inserted:
            return  # дубликат
        apply_payment_event(payload)
```
Проверка: отправить webhook-запрос с одним и тем же event_id дважды подряд — состояние платежа должно измениться только после первого вызова.

### 384. [Q-03-07-0384] В чём разница между синхронной репликацией БД и асинхронной, и как это влияет на consistency при отказе?

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Middle

**Короткий ответ**<br>
При синхронной репликации primary подтверждает запись только после подтверждения реплики(к), гарантируя отсутствие потери данных при отказе primary, но увеличивая латентность; при асинхронной репликации primary подтверждает запись немедленно, и при отказе primary до того, как реплика получила изменения, эти изменения будут потеряны.

**Разбор**
- **Как это работает:** Синхронная репликация добавляет сетевой round-trip до реплики в путь каждой записи; асинхронная применяет изменения на реплике отдельным, не блокирующим процессом, с отставанием.
- **На практике:** Выбор зависит от того, что дороже — потеря последних секунд данных при отказе primary или повышенная латентность/сниженная доступность записи; многие системы используют гибрид (полу-синхронная репликация).
- **Частые ошибки:** Включать строго синхронную репликацию на несколько реплик без учёта, что при недоступности хотя бы одной из них запись может блокироваться; считать, что наличие реплики само по себе защищает от потери данных без синхронности.

**Пример / кейс**
```sql
-- PostgreSQL: синхронная репликация на конкретную реплику
synchronous_standby_names = 'replica_1'
```
Проверка: смоделировать отказ primary сразу после подтверждения записи клиенту при асинхронной репликации — после failover на реплику эта последняя запись должна отсутствовать; при синхронной репликации запись должна присутствовать.

### 385. [Q-03-07-0385] Как выбрать между синхронным вызовом (REST/gRPC) и асинхронным сообщением при интеграции двух сервисов?

Синхронный вызов выбирают, когда вызывающей стороне нужен немедленный результат для продолжения обработки; асинхронное сообщение — когда результат можно получить с задержкой, отправитель не должен блокироваться на доступности получателя, или нужно уведомить несколько независимых подписчиков.

**Разбор**
- **Как это работает:** Синхронный вызов создаёт временную связанность — оба сервиса должны быть доступны одновременно; сообщение развязывает это, но отправитель не может немедленно узнать результат обработки.
- **На практике:** Критерии выбора: нужен ли результат прямо сейчас для ответа пользователю; сколько получателей должны знать о событии; насколько критична доступность получателя прямо в момент отправки.
- **Частые ошибки:** Делать все интеграции синхронными «для простоты», создавая цепочку хрупких зависимостей; делать критичную для пользователя операцию полностью асинхронной без способа дождаться результата.

```text
Синхронно: Checkout Service -> (HTTP, нужен результат сразу) -> Inventory Service: "есть ли товар в наличии?"
Асинхронно: Order Service -> (событие "order.created") -> [Notification, Analytics, Loyalty]
```
Проверка: для синхронного сценария тест подтверждает получение ответа в рамках одного HTTP-запроса; для асинхронного — тест подтверждает, что Order Service отвечает пользователю независимо от скорости обработки события подписчиками.

```text
Лог ошибки на клиенте (старая версия 2.3.0):
```

### 387. [Q-03-07-0387] Как правильно выбирать критерии разбиения монолита на микросервисы по границам доменов, и какие риски несёт неправильное разбиение? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
Границы сервисов стоит проводить по bounded context (устойчивым бизнес-возможностям и владению данными), а не по техническим слоям или текущей оргструктуре; выбор конкретных границ зависит от стабильности домена, профиля нагрузки и зрелости команды — универсального правильного разбиения не существует.

**Разбор**
- **Как это работает:** Домен анализируют через карту бизнес-процессов и данных, ищут «швы» — зоны с низкой связанностью и высокой внутренней согласованностью (например, «каталог» слабо связан с «биллингом» по данным и темпу изменений).
- **На практике:** Критерии выбора: частота совместных изменений (если два модуля почти всегда меняются вместе — граница проведена неверно), различие в требуемом масштабировании/SLA, зрелость команды для операционной сложности отдельного сервиса.
- **Частые ошибки:** Проводить границы по оргструктуре «как есть сейчас» без проверки её устойчивости; разбивать по техническим слоям (отдельный «сервис для БД») вместо бизнес-возможностей.
- **Компромисс:** Слишком крупные границы (мало сервисов) сохраняют часть проблем монолита (совместные деплои, связанность), но проще в эксплуатации; слишком мелкие границы дают высокую автономию команд, но взрывообразно увеличивают операционную сложность (сетевые вызовы, распределённые транзакции, мониторинг) и могут быть избыточны для текущего масштаба. Критерий выбора — соотносить стоимость координации при текущих границах со стоимостью операционной сложности при более мелком разбиении, и пересматривать границы по мере того, как домен и команда созревают.

**Пример / кейс**
```text
Вариант A: Order Service включает заказы + оплату + доставку (крупная граница)
  — меньше сетевых вызовов, но любое изменение оплаты требует релиза всего Order Service
Вариант B: отдельные Order, Payment, Shipping Service (мелкая граница)
  — независимые релизы, но заказ теперь требует Saga между тремя сервисами
  и обработки частичных отказов
```
Обсуждение: нет единственно верного ответа без контекста нагрузки, размера и структуры команд, частоты изменений каждой части и допустимой операционной сложности.

### 388. [Q-03-07-0388] Что выбрать между strong и eventual consistency для остатков товара на складе при высоком параллелизме покупок? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
Выбор между строгой и eventual consistency для остатков зависит от того, что дороже бизнесу — продать товар, которого уже нет (overselling), или искусственно снижать доступность/throughput операции покупки из-за блокировок при строгой согласованности; универсального решения нет.

**Разбор**
- **Как это работает:** Строгая согласованность обычно требует синхронной проверки и резервирования остатка в момент покупки (условное обновление WHERE stock >= qty), что исключает overselling, но ограничивает параллелизм на горячих товарах; eventual consistency допускает локальное/кешированное представление остатка с редким overselling, компенсируемым постфактум.
- **На практике:** Для высокомаржинальных, лимитированных товаров overselling особенно болезненен репутационно — оправдана строгая согласованность даже с потерей throughput; для товаров с большим запасом и низкой вероятностью одновременного исчерпания эвентуальная модель с редкой компенсацией дешевле и быстрее.
- **Частые ошибки:** Применять строгую блокировку остатка для всех товаров независимо от объёма и маржинальности; выбирать eventual consistency без продуманного автоматизированного процесса компенсации overselling.
- **Компромисс:** Строгая согласованность снижает риск overselling, но повышает латентность под нагрузкой на горячих товарах и требует постоянной доступности источника правды (узкое место, например, в «чёрную пятницу»); eventual consistency масштабируется лучше и переживает временную недоступность части системы, но требует спроектированного и протестированного процесса компенсации overselling и готовности бизнеса принимать такие случаи. Критерий выбора — ожидаемая частота конфликтов, стоимость одного случая overselling и готовность инвестировать в автоматическую компенсацию.

**Пример / кейс**
```sql
-- строгий вариант: атомарное условное списание остатка
UPDATE stock SET quantity = quantity - 1
WHERE product_id = 42 AND quantity > 0
RETURNING quantity;
-- если 0 строк затронуто — остатка нет, заказ не создаётся
```
Обсуждение: решение нужно явно принимать с учётом объёма заказов на товар, допустимой задержки ответа покупателю и стоимости компенсации.

### 389. [Q-03-07-0389] Что выбрать — Saga или распределённую транзакцию (2PC/XA) — для мультисервисной бизнес-операции? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
Для большинства мультисервисных операций в микросервисной архитектуре предпочтительнее Saga, так как она не требует долгих блокировок и синхронной доступности всех участников одновременно; 2PC/XA рассматривают только в узких случаях, когда участники — это базы данных под общим контролем и бизнес готов терпеть цену в доступности и масштабируемости.

**Разбор**
- **Как это работает:** Saga выполняет шаги последовательно, коммитя каждый локально и используя компенсации при сбое последующих шагов; 2PC синхронно блокирует ресурсы всех участников на время голосования координатора.
- **На практике:** 2PC плохо сочетается с сетевыми сбоями — при недоступности координатора или участника во время голосования ресурсы остаются заблокированными неопределённо долго; Saga допускает промежуточные eventually consistent состояния, но требует явного проектирования компенсаций, включая случаи их собственного сбоя.
- **Частые ошибки:** Выбирать 2PC из желания «гарантировать строгую атомарность», не оценив доступность и устойчивость участников к блокировкам; реализовывать Saga без механизма восстановления зависших процессов после перезапуска оркестратора.
- **Компромисс:** 2PC даёт более простое концептуальное рассуждение об атомарности, но снижает доступность операции до доступности самого ненадёжного участника и плохо масштабируется; Saga масштабируется и переживает временную недоступность участников, но перекладывает сложность на явное проектирование и поддержку компенсаций, создавая временные окна неконсистентности. Критерий выбора — количество и природа участников, допустимость временной неконсистентности, и готовность команды поддерживать логику компенсаций и мониторинг зависших транзакций.

**Пример / кейс**
```text
Saga-оркестратор хранит состояние шагов:
step1: payment.charge -> succeeded
step2: inventory.reserve -> failed
-> компенсация step1: payment.refund запускается автоматически оркестратором,
   событие логируется для аудита и алертинга при неудаче компенсации
```
Обсуждение: стоит явно проговорить, что происходит, если сама компенсация не срабатывает — это часть архитектурного решения с бизнес-последствиями.

Для часто изменяемых критичных данных типа цен нет единой оптимальной стратегии — выбор между коротким TTL, event-driven инвалидацией и отказом от кеширования зависит от допустимого окна неточности, частоты изменений и последствий показа устаревшей цены для конкретного бизнеса.

**Разбор**
- **Как это работает:** Event-driven инвалидация даёт минимальное окно устаревания, но требует надёжной доставки события во все кеширующие узлы (подвержена тем же проблемам at-least-once/дублей); короткий TTL проще, но гарантирует окно устаревания размером с TTL независимо от того, изменилась цена или нет.
- **На практике:** При высокой частоте изменений (динамическое ценообразование) кеширование может быть неприемлемо вовсе, либо используют push-инвалидацию с коротким TTL как страховку; при редких изменениях подходит более долгий TTL с принудительной инвалидацией при обновлении.
- **Частые ошибки:** Полагаться только на событие инвалидации без TTL-страховки — при потере события устаревшая цена может остаться навечно; показывать покупателю устаревшую цену без финальной сверки перед фактическим списанием денег.
- **Компромисс:** Чисто TTL-подход прост и устойчив к сбоям доставки событий, но создаёт предсказуемое окно устаревания даже без изменений; event-driven подход даёт минимальную задержку обновления, но добавляет инфраструктурную сложность и сам подвержен потере сообщений, поэтому на практике их комбинируют. Независимо от стратегии витрины, критичную точку (подтверждение оплаты) стоит защищать финальной сверкой цены из источника правды, даже если это добавляет дополнительный синхронный вызов.

**Пример / кейс**
```python
# витрина — кешируется с коротким TTL + событие инвалидации
price = cache.get(f"price:{product_id}")  # TTL=10s + invalidate-on-change
# перед фактическим списанием — обязательная сверка с источником правды
actual_price = pricing_service.get_current_price(product_id)
if actual_price != displayed_price:
    raise PriceChangedError(actual_price)
```
Обсуждение: показ цены на витрине и биллинг — разные по критичности операции, и одна стратегия кеширования не обязана применяться к обеим одинаково.

### 391. [Q-03-07-0391] Как спроектировать идемпотентность для платёжной системы при повторной доставке запросов от нескольких клиентов/ретраях? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
Идемпотентность платежа строят на клиентском idempotency key, привязанном к конкретной попытке оплаты, с атомарной резервацией ключа до начала обработки; сложность возникает при одновременных запросах с одним ключом от разных источников — здесь нет единственно верной реализации блокировки «в процессе».

**Разбор**
- **Как это работает:** При получении запроса с idempotency key сервис атомарно регистрирует попытку в статусе «in_progress» перед обращением к провайдеру; при повторном запросе с тем же ключом, пока первая попытка ещё «in_progress», вторая параллельная попытка оплаты не должна начинаться.
- **На практике:** Варианты для конкурентного повтора — заблокировать второй запрос до завершения первого либо вернуть статус «processing» и предложить клиенту опросить результат позже; оба должны корректно обрабатывать случай, когда первая попытка «зависла» без ответа провайдера.
- **Частые ошибки:** Считать, что одного уникального ограничения в БД достаточно — оно защищает от дублирования записи, но не от того, что сервис дважды обратится к провайдеру, если оба запроса прошли проверку до фиксации статуса; не предусматривать путь разрешения «неопределённого» исхода через сверку с провайдером.
- **Компромисс:** Синхронная блокировка второго запроса до завершения первого даёт простую модель согласованности, но увеличивает латентность ответа и риск таймаута у клиента; асинхронная модель «processing + polling» не блокирует клиента надолго, но требует поддержки опроса статуса на стороне потребителей API. Выбор зависит от контроля над клиентским кодом и критичности быстрой обратной связи по результату оплаты.

**Пример / кейс**
```sql
CREATE TABLE payment_attempts (
    idempotency_key UUID PRIMARY KEY,
    status TEXT NOT NULL,          -- in_progress | succeeded | failed
    provider_tx_id TEXT,
    created_at TIMESTAMPTZ DEFAULT now()
);
```
```text
При status = 'in_progress' и повторном запросе -> не начинать новую попытку к провайдеру,
а сверяться с provider_tx_id через API провайдера, если прошло больше N секунд без обновления.
```
Обсуждение: команде стоит явно решить, что происходит в «неопределённом» состоянии — это бизнес-риск, а не только техническая деталь.

### 392. [Q-03-07-0392] Как обрабатывать частичные отказы в цепочке из нескольких сервисов, когда часть шагов выполнилась, а часть — нет, включая компенсирующие транзакции? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
При частичном выполнении цепочки нужно явно спроектировать компенсирующие транзакции для каждого завершённого шага и оркестрацию, которая гарантированно доводит процесс до согласованного финального состояния; единого шаблона компенсации нет — для каждого шага она проектируется индивидуально исходя из его обратимости.

**Разбор**
- **Как это работает:** Компенсация — отдельная бизнес-операция, обратная по смыслу прямому действию; не каждое действие обратимо в строгом смысле, и для таких шагов проектируют смягчающее действие либо откладывают необратимый шаг на конец цепочки.
- **На практике:** Оркестратор должен переживать собственные перезапуски — состояние прогресса Saga хранится персистентно; критичен мониторинг «зависших» процессов и алертинг для ручного вмешательства, когда автоматическая компенсация сама не срабатывает.
- **Частые ошибки:** Проектировать только «счастливый путь» и добавлять компенсации постфактум после инцидента; размещать необратимые побочные эффекты в середине цепочки, а не в её конце.
- **Компромисс:** Полный набор компенсаций повышает надёжность процесса, но требует значительных усилий разработки и тестирования каждой точки отказа; упрощённый подход (алерт дежурному вместо автоматической компенсации) снижает инженерные затраты, но увеличивает operational burden и риск человеческой ошибки. Критерий выбора — частота ожидаемых частичных отказов и стоимость ошибки при неправильной ручной компенсации.

**Пример / кейс**
```text
Цепочка: Payment.charge -> Inventory.reserve -> Shipping.schedule
Отказ на Shipping.schedule после успешных Payment и Inventory:
  компенсация 2: Inventory.release_reservation
  компенсация 1: Payment.refund
Оркестратор выполняет компенсации в обратном порядке и фиксирует финальный статус
заказа как "cancelled_after_partial_failure", с логированием для аудита.
```
Обсуждение: решение о глубине автоматизации компенсаций — архитектурный выбор, зависящий от допустимого операционного риска.

### 393. [Q-03-07-0393] Какие гарантии брокера сообщений (Kafka vs RabbitMQ) выбрать для сценария с высокими требованиями к порядку и консистентности? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
Kafka подходит, когда нужен упорядоченный, воспроизводимый и долгоживущий журнал событий с возможностью перечитывания и масштабированием через партиционирование по ключу; RabbitMQ подходит для сценариев «задача-очередь» с гибкой маршрутизацией, где порядок важен в основном в пределах одной очереди.

**Разбор**
- **Как это работает:** Kafka гарантирует порядок только в пределах одной партиции, поэтому для сохранения порядка связанных событий нужно направлять их в одну партицию через ключ; RabbitMQ гарантирует порядок в пределах одной очереди при единственном consumer'е, а при нескольких конкурирующих consumer'ах порядок обработки не гарантирован.
- **На практике:** При требовании строгого порядка обработки событий одной сущности выбор ключа партиционирования в Kafka — архитектурное решение с последствиями для масштабирования; в RabbitMQ для похожей гарантии нужна либо одна очередь на сущность, либо consistent routing.
- **Частые ошибки:** Предполагать, что Kafka гарантирует глобальный порядок по всему топику; выбирать брокер по общей репутации без проверки, подходит ли его модель гарантий конкретному сценарию.
- **Компромисс:** Kafka даёт долгое хранение истории, replay и масштабируемость через партиции, но требует сложной операционной модели и явного мышления о партиционировании для гарантий порядка; RabbitMQ проще в небольших сценариях маршрутизации задач, но слабее подходит для большого объёма событий с долгим хранением и повторным чтением истории. Критерий выбора — нужен ли replay/аудит, объём и темп сообщений, критичность порядка между независимыми consumer'ами.

**Пример / кейс**
```python
# Kafka: гарантия порядка в пределах партиции через ключ
producer.send("orders.events", key=str(order_id).encode(), value=event_payload)
```
```text
RabbitMQ: для похожей гарантии на сущность — направлять все сообщения по order_id
в одну очередь/consumer через consistent hash exchange,
что ограничивает горизонтальное масштабирование обработки конкретной сущности.
```
Обсуждение: выбор между брокерами стоит обсуждать в терминах конкретных гарантий (порядок, retention, доставка), а не абстрактного "что лучше".

### 394. [Q-03-07-0394] Как вести эволюцию API-контракта в системе с множеством независимых потребителей без breaking changes? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
При множестве независимых потребителей эволюцию контракта ведут через строго аддитивные изменения, явное версионирование при неизбежных breaking changes и длительные периоды параллельной поддержки версий; решение о выводе старой версии зависит от реальной телеметрии использования, а не от предположений.

**Разбор**
- **Как это работает:** Аддитивные изменения (новые необязательные поля) безопасны для потребителей, игнорирующих неизвестные поля; при breaking change вводят новую версию контракта, оставляя старую работающей, и мигрируют потребителей поэтапно.
- **На практике:** Для внешних партнёров период поддержки старой версии может растягиваться на месяцы из-за медленных циклов релиза на их стороне; consumer-driven contract testing (Pact) помогает заранее обнаружить, что изменение ломает известного потребителя.
- **Частые ошибки:** Выводить старую версию по календарному плану без проверки реального трафика на неё; не вести реестр известных потребителей и их версий, что делает невозможным осознанное решение о выводе версии.
- **Компромисс:** Долгая параллельная поддержка нескольких версий даёт потребителям время на миграцию и снижает риск инцидентов, но увеличивает нагрузку на команду и усложняет кодовую базу. Быстрый вывод старой версии снижает эту нагрузку, но повышает риск сломать потребителей, которые не успели мигрировать. Критерий выбора — реальная доля трафика на старой версии, контрактные обязательства перед партнёрами и внутренняя стоимость поддержки нескольких версий одновременно.

**Пример / кейс**
```text
Метрика перед выводом v1 из эксплуатации:
  v1 traffic share: 2% (3 известных партнёра, 1 внутренний сервис)
  -> точечное уведомление оставшихся потребителей с конкретным планом отключения,
     а не общая рассылка "через 3 месяца отключаем v1"
```
Обсуждение: решение о сроках вывода версии должно основываться на фактических данных об использовании, а не только на формальном сроке deprecation policy.

### 395. [Q-03-07-0395] Как применять circuit breaker и bulkhead вместе в системе с высокой нагрузкой и нестабильной внешней зависимостью? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
Bulkhead ограничивает долю ресурсов, которую может занять вызов к нестабильной зависимости, не давая ей исчерпать общий ресурс системы; circuit breaker поверх этого снижает количество бесполезных попыток к уже деградировавшей зависимости внутри изолированного пула — конкретные параметры нужно подбирать под профиль зависимости и нагрузки.

**Разбор**
- **Как это работает:** Bulkhead выделяет, например, 10 из 100 воркеров под вызовы к зависимости X; если X деградирует, максимум 10 воркеров будет занято, остальные 90 продолжают обслуживать остальной трафик; circuit breaker на этом пуле при превышении порога ошибок переходит в OPEN, освобождая даже эти 10 воркеров.
- **На практике:** Размер bulkhead-пула подбирают исходя из ожидаемой доли трафика и допустимой деградации остальной системы; пороги breaker подбирают на основе наблюдаемого нормального уровня ошибок и типичного времени восстановления зависимости.
- **Частые ошибки:** Настраивать breaker глобально на весь сервис, а не на пул конкретной зависимости; выбирать параметры один раз «по интуиции» и не пересматривать их по мере изменения профиля нагрузки.
- **Компромисс:** Чем больше ресурсов выделено под bulkhead, тем выше throughput в нормальном режиме, но тем больше ресурсов теряется при деградации зависимости; чем меньше — тем лучше изоляция, но тем ниже пропускная способность. Агрессивные пороги breaker защищают быстрее, но могут ложно открываться на нормальные всплески ошибок. Критерий выбора — исторические данные о нормальном уровне ошибок/латентности и бизнес-цена как ложного срабатывания, так и задержки в срабатывании.

**Пример / кейс**
```python
payment_bulkhead = ThreadPoolExecutor(max_workers=10)  # изолированный пул
payment_breaker = CircuitBreaker(failure_threshold=5, reset_timeout=30)

def call_payment(request):
    if payment_breaker.is_open():
        return fallback_response()
    future = payment_bulkhead.submit(payment_client.charge, request)
    try:
        return future.result(timeout=3)
    except Exception:
        payment_breaker.record_failure()
        return fallback_response()
```
Обсуждение: значения max_workers, failure_threshold и reset_timeout должны обсуждаться с учётом реальной статистики нагрузки и деградации зависимости.

### 396. [Q-03-07-0396] Какие компромиссы CAP-теоремы стоит выбрать на практике при партиционировании сети для конкретной системы? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
При сетевом партиционировании система должна выбрать между продолжением обслуживания запросов с риском несогласованных данных (AP) или отказом части запросов ради гарантии согласованности (CP) — выбор принимается для конкретной операции и бизнес-контекста, и разные операции одной системы могут выбирать по-разному.

**Разбор**
- **Как это работает:** CAP-теорема утверждает, что при реальном разрыве сети между узлами нельзя одновременно гарантировать полную согласованность и полную доступность для всех операций — нужно выбрать, какую ослабить именно в момент партиционирования.
- **На практике:** Для операций, где показ неверных данных дороже отказа (подтверждение перевода), выбирают CP; для операций, где отказ дороже временной неточности (лента новостей), выбирают AP с последующим сведением.
- **Частые ошибки:** Трактовать CAP как выбор «раз и навсегда» для всей системы, хотя разные операции могут выбирать по-разному; оправдывать постоянно слабую согласованность там, где партиций нет вообще.
- **Компромисс:** Выбор CP означает отказ обслуживания части запросов во время партиционирования, что бьёт по доступности, но исключает несогласованные данные; выбор AP сохраняет видимую доступность, но требует продуманного механизма разрешения конфликтов после восстановления связи, что само по себе источник сложности. Критерий выбора — для каждой конкретной операции нужно явно оценить, что хуже для бизнеса: отказ или несогласованность.

**Пример / кейс**
```text
Сценарий: сеть разделила кластер БД на две группы узлов (partition).
CP-выбор для операции перевода денег: узлы без кворума отклоняют запрос на запись (503),
  пока партиционирование не устранено.
AP-выбор для операции "добавить лайк": узел без кворума принимает запись локально,
  синхронизация и разрешение конфликтов происходит после восстановления связи.
```
Обсуждение: обе стратегии валидны для разных операций одной системы — решение обсуждается для конкретной операции и её цены ошибки.

### 397. [Q-03-07-0397] Как построить устойчивую интеграцию с нестабильным внешним сервисом, комбинируя таймауты, retry, fallback и кеш последнего успешного ответа? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
Устойчивость строят комбинацией таймаутов, ограниченных retry с backoff и джиттером, circuit breaker и осмысленного fallback (включая кеш последнего успешного ответа) — конкретный набор и агрессивность этих механизмов зависят от критичности операции.

**Разбор**
- **Как это работает:** Таймаут ограничивает время ожидания одной попытки; retry даёт шанс на успех при кратковременных сбоях; circuit breaker прекращает бесполезные попытки при затяжной деградации; fallback позволяет не отказывать пользователю полностью.
- **На практике:** Для некритичных дополняющих данных кеш последнего успешного ответа как fallback почти всегда оправдан; для критичных операций (списание денег, проверка доступа) fallback на устаревшие данные может быть опасен, и честная ошибка безопаснее.
- **Частые ошибки:** Применять один и тот же fallback для всех видов интеграций без оценки риска использования устаревших данных; наращивать число retry и уменьшать таймаут бесконтрольно без учёта суммарного времени ожидания.
- **Компромисс:** Более агрессивная защита увеличивает видимую надёжность, но может маскировать реальные проблемы зависимости надолго и увеличивает сложность тестирования; более консервативная защита проще и честнее относительно актуальности данных, но может чаще показывать ошибки при кратковременных сбоях. Критерий выбора — критичность актуальности данных для операции и готовность бизнеса принимать риск устаревшего fallback против риска более частых отказов.

**Пример / кейс**
```python
def get_fx_rate(currency):
    if fx_breaker.is_open():
        return cache.get(f"fx:{currency}") or default_rate(currency)
    try:
        rate = fx_client.get_rate(currency, timeout=2)
        cache.set(f"fx:{currency}", rate, ex=120)
        return rate
    except (TimeoutError, HTTPError):
        fx_breaker.record_failure()
        return cache.get(f"fx:{currency}") or default_rate(currency)
```
Обсуждение: допустимость fallback на кеш для конкретной интеграции (курс валют против проверки лимита платежа) нужно обсуждать по отдельности.

### 398. [Q-03-07-0398] Как обеспечить приемлемую консистентность при чтении с read-реплик с задержкой репликации (replication lag)? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
Чтение с асинхронных read-реплик снижает нагрузку на primary, но может возвращать отстающие данные, особенно заметные сразу после записи самим же пользователем; решение о том, где можно читать с реплики, а где нужен primary, принимается отдельно для разных сценариев использования.

**Разбор**
- **Как это работает:** Запись идёт на primary; реплики применяют изменения асинхронно с задержкой; чтение с реплики сразу после записи тем же пользователем может не увидеть эту запись, если реплика ещё не успела её применить.
- **На практике:** Для сценариев read-your-writes применяют чтение с primary сразу после записи в рамках той же сессии, либо передачу «позиции» записи клиенту для ожидания догона репликой; для чтения чужих давних данных небольшой lag почти не критичен.
- **Частые ошибки:** Читать со случайной реплики без учёта контекста операции сразу после собственной записи пользователя; переводить всё чтение на primary «для надёжности», убивая смысл масштабирования через реплики.
- **Компромисс:** Полный перевод критичных по свежести чтений на primary гарантирует согласованность, но нагружает единственный узел записи; чтение с реплик для всего трафика максимизирует масштабируемость, но создаёт видимые артефакты задержки там, где это критично. Промежуточный вариант (sticky-роутинг на primary после записи) даёт баланс, но требует дополнительной логики роутинга и усложняет инфраструктуру чтения.

**Пример / кейс**
```text
Сценарий: пользователь обновил имя профиля, затем немедленно переходит на страницу профиля.
Без read-your-writes: запрос попадает на реплику с lag 300ms -> видит старое имя.
С read-your-writes: запрос в течение N секунд после записи явно идёт на primary -> видит новое имя.
```
Обсуждение: выбор, для каких операций нужна гарантия read-your-writes, — продуктовое и архитектурное решение, которое стоит явно зафиксировать.

### 399. [Q-03-07-0399] Когда стоит вводить event sourcing, и какие риски и издержки это добавляет команде? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
Event sourcing оправдан, когда бизнесу реально нужна полная история изменений с возможностью восстановления состояния на любой момент и аудита причин изменений; издержки — сложность чтения текущего состояния (нужны проекции), миграция схемы событий и высокий порог входа для команды.

**Разбор**
- **Как это работает:** Вместо обновления строки до нового значения система добавляет запись о событии; текущее состояние — результат применения (reduce) всех событий сущности по порядку, получают через проекции, что сближает event sourcing с CQRS.
- **На практике:** Оправданные случаи — финансовый учёт с требованием полной аудируемой истории, сложные бизнес-процессы, где важно понять «как мы пришли к этому состоянию»; для обычных CRUD-сущностей это создаёт сложность без соразмерной выгоды.
- **Частые ошибки:** Вводить event sourcing целиком для всей системы вместо точечного применения к нужным агрегатам; не продумывать эволюцию схемы событий — старые события навсегда остаются в старом формате.
- **Компромисс:** Event sourcing даёт сильную аудируемость и возможность восстановления состояния на любой момент, но многократно увеличивает сложность разработки (события, проекции, миграция схем) и требует зрелости команды — ошибки в дизайне событий сложно исправить, так как события неизменяемы. Обычное хранение текущего состояния с отдельным audit log проще в поддержке и покрывает большинство практических целей, но не даёт «бесплатного» восстановления состояния на произвольный момент. Критерий выбора — реальная потребность в истории и replay, и готовность нести долгосрочные издержки поддержки схемы событий.

**Пример / кейс**
```text
Agregate "Order" как поток событий:
  OrderCreated{items, total} -> OrderPaid{amount} -> OrderShipped{tracking_id}
Текущее состояние = reduce(events) -> {status: "shipped", total: ..., tracking_id: ...}
```
Обсуждение: решение вводить event sourcing стоит принимать для конкретных агрегатов с явной бизнес-потребностью, а не как стандарт для всей системы.

### 400. [Q-03-07-0400] Какие архитектурные решения принимать при миграции с монолита на микросервисы «вживую» без остановки сервиса (strangler fig pattern), и какие риски и критерии успеха? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Архитектура и распределённые системы: модульность, границы сервисов, монолит и микросервисы, кеширование, очереди, идемпотентность, согласованность и устойчивость к сбоям<br>
**Уровень:** Senior

**Короткий ответ**<br>
Strangler fig постепенно «обрастает» монолит новыми сервисами, перехватывая часть функциональности через прокси/роутер, пока вся нужная функциональность не будет перенесена и старый код не выведен из эксплуатации, без единого «большого взрыва»; критерии успеха и темп миграции определяются конкретным проектом, а не фиксированным планом.

**Разбор**
- **Как это работает:** Перед монолитом ставится роутер, который постепенно перенаправляет отдельные эндпоинты на новые сервисы, оставляя остальной трафик идти в монолит; данные и трафик мигрируют по частям, и на каждом этапе монолит и новые сервисы работают параллельно.
- **На практике:** Успешная миграция определяется контролируемостью риска — на каждом этапе должна быть возможность безопасного откат(а), наблюдаемость, и чёткий критерий «этот кусок полностью перенесён и старый код можно удалить» (отсутствие трафика на старый путь в течение достаточного периода).
- **Частые ошибки:** Переносить сразу большие куски функциональности без промежуточных контрольных точек; не выделять время на удаление старого кода монолита после переноса, из-за чего обе архитектуры годами поддерживаются параллельно.
- **Компромисс:** Быстрая агрессивная миграция сокращает срок и стоимость поддержки двух архитектур одновременно, но повышает риск крупных инцидентов и усложняет откат; медленная поэтапная миграция снижает риск каждого шага и даёт дешёвый откат, но растягивает период параллельной поддержки, что само по себе стоит ресурсов и может никогда не «довестись до конца» без управленческой воли. Критерий выбора темпа — терпимость бизнеса к риску, доступность инженерных ресурсов и готовность выделить время на завершение миграции.

**Пример / кейс**
```text
Gateway routing rule (поэтапный перенос эндпоинта /orders):
  /orders/* -> 10% трафика в Order Service, 90% в монолит (canary)
  -> при отсутствии роста ошибок за 2 недели: 100% в Order Service
  -> мониторинг: error_rate, latency p99, бизнес-метрики сравниваются
     между путём через монолит и через новый сервис на этапе 10%/90%
```
Обсуждение: конкретный темп, пороги canary и критерии полного переключения должны обсуждаться с учётом риск-профиля именно этого домена.
