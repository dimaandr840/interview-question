### 191. [Q-03-04-0191] Чем HTTP-метод GET отличается от POST и когда нужно использовать каждый из них?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
GET запрашивает представление ресурса и не должен менять состояние сервера, параметры передаются в URL; POST отправляет данные для создания ресурса или выполнения действия и обычно изменяет состояние, данные идут в теле запроса.

**Разбор**
- **Как это работает:** GET — безопасный (safe) и идемпотентный метод: повторный вызов с теми же параметрами не меняет данные и возвращает тот же результат (если данные не поменялись извне). POST не является ни безопасным, ни идемпотентным по умолчанию — два одинаковых POST-запроса могут создать два разных ресурса.
- **На практике:** GET используют для получения списков, карточек объектов, поиска с фильтрами через query-параметры. POST — для создания ресурса, отправки форм, выполнения операций без естественного ресурса (например, `/login`, `/orders/{id}/cancel`). GET-запросы можно кэшировать, POST — как правило нет.
- **Частые ошибки:** передавать в GET чувствительные данные в query-параметрах (логируются серверами и проксями); использовать GET для операций с побочными эффектами (например, `/delete-user?id=5`), что ломает идемпотентность и опасно при предзагрузке ссылок ботами/браузером; забывать, что тело GET-запроса не гарантированно поддерживается промежуточными прокси.

**Пример / кейс**
```http
GET /api/v1/users?status=active&page=2 HTTP/1.1
Host: example.com
Accept: application/json

POST /api/v1/users HTTP/1.1
Host: example.com
Content-Type: application/json

{"name": "Иван", "email": "ivan@example.com"}
```
Проверка: вызов GET несколько раз подряд не меняет количество пользователей в базе; повторный вызов POST с одинаковым телом без idempotency-key создаст двух разных пользователей — это можно увидеть по разным `id` в ответах.

### 192. [Q-03-04-0192] В чём разница между PUT и PATCH и какой код вернёт сервер, если ресурс для обновления не существует?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
PUT заменяет ресурс целиком и идемпотентен; PATCH применяет частичное изменение и не обязан быть идемпотентным. Если ресурс не найден, обычно возвращают 404, но PUT иногда допускает создание ресурса по заданному URL (тогда 201).

**Разбор**
- **Как это работает:** PUT ожидает полное представление ресурса — поля, которые не переданы, по спецификации REST должны считаться отсутствующими/сброшенными. PATCH передаёт только изменяемые поля или набор операций (например, JSON Merge Patch или JSON Patch по RFC 6902).
- **На практике:** для простых API часто используют PATCH с частичным JSON-объектом, который мержится с текущими данными в коде обработчика. PUT уместен, когда клиент владеет полным представлением ресурса (например, конфигурация). Решение зависит от соглашений конкретного API — это нужно явно документировать в контракте.
- **Частые ошибки:** реализовывать PATCH так, что непереданные поля интерпретируются как "сбросить в null" (это поведение PUT, а не PATCH); считать PUT автоматически идемпотентным, если сервер генерирует значения на основе текущего времени при каждом обновлении; не возвращать корректный статус при отсутствии ресурса.

**Пример / кейс**
```python
# FastAPI, намеренно показана разница PUT/PATCH
@app.put("/items/{item_id}")
def replace_item(item_id: int, item: Item):
    if item_id not in db:
        return JSONResponse(status_code=404, content={"detail": "not found"})
    db[item_id] = item.dict()  # заменяет ресурс целиком
    return db[item_id]

@app.patch("/items/{item_id}")
def update_item(item_id: int, patch: dict):
    if item_id not in db:
        return JSONResponse(status_code=404, content={"detail": "not found"})
    db[item_id].update(patch)  # частичное обновление
    return db[item_id]
```
Проверка: тест отправляет PUT без поля `price` и убеждается, что `price` стал `None`/значением по умолчанию; тест отправляет PATCH с тем же телом и убеждается, что `price` не изменился.

### 193. [Q-03-04-0193] Какие группы HTTP статус-кодов существуют и чем 401 отличается от 403?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
1xx — информационные, 2xx — успех, 3xx — перенаправление, 4xx — ошибка клиента, 5xx — ошибка сервера. 401 означает, что клиент не прошёл аутентификацию (не предоставил или предоставил неверные учётные данные), 403 — что клиент аутентифицирован, но у него нет прав на действие.

**Разбор**
- **Как это работает:** статус-код — часть HTTP-ответа, которая говорит клиенту, как интерпретировать результат без парсинга тела. 401 Unauthorized по спецификации обязан сопровождаться заголовком `WWW-Authenticate`, указывающим, как авторизоваться.
- **На практике:** 401 возвращают, когда токен отсутствует, просрочен или некорректен; 403 — когда токен валиден, но роли/права не позволяют выполнить операцию (например, обычный пользователь пытается удалить чужой ресурс). Разделение важно для клиентов: при 401 стоит предложить повторный логин, при 403 — показать сообщение об отсутствии прав, а не предлагать перелогиниться.
- **Частые ошибки:** возвращать 401 вместо 403 (или наоборот), что приводит к бесконечным попыткам логина в UI; использовать 500 для ошибок валидации пользовательских данных (должно быть 400/422); возвращать 200 с телом `{"error": "..."}" вместо честного кода ошибки, что ломает автоматическую обработку ошибок на клиенте.

**Пример / кейс**
```python
from fastapi import HTTPException

def get_order(order_id: int, current_user):
    order = find_order(order_id)
    if not order:
        raise HTTPException(status_code=404, detail="Order not found")
    if current_user is None:
        raise HTTPException(status_code=401, detail="Authentication required")
    if order.owner_id != current_user.id and not current_user.is_admin:
        raise HTTPException(status_code=403, detail="Access denied")
    return order
```
Проверка: тест без заголовка `Authorization` получает 401; тест с валидным токеном другого пользователя получает 403; тест владельца ресурса получает 200.

### 194. [Q-03-04-0194] Что такое REST и какие ключевые принципы он предполагает?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
REST — архитектурный стиль для сетевых API, основанный на ресурсах, адресуемых по URL, и операциях над ними через стандартные HTTP-методы; ключевые принципы — клиент-серверность, отсутствие состояния сессии на сервере (statelessness), кэшируемость, единообразный интерфейс и слоистость.

**Разбор**
- **Как это работает:** каждый ресурс (пользователь, заказ) имеет уникальный URL; состояние приложения передаётся клиентом в каждом запросе (например, через токен), а не хранится сервером между запросами — это упрощает масштабирование и отказоустойчивость.
- **На практике:** "RESTful API" на практике часто означает "HTTP API с ресурсами и JSON", без строгого соблюдения всех академических принципов (например, HATEOAS редко реализуют полностью). Важно согласовать с командой, какие принципы обязательны для конкретного API, и зафиксировать это в контракте.
- **Частые ошибки:** хранить состояние сессии в памяти процесса сервера (нарушает statelessness и мешает горизонтальному масштабированию); использовать глаголы в URL вместо существительных-ресурсов (`/getUser` вместо `/users/{id}`); путать RPC-подобный API (действия через POST) с чистым REST и называть любой HTTP API "RESTful" без уточнения.

**Пример / кейс**
```text
Ресурсный подход (REST-стиль):
  GET    /users/42          -> получить пользователя
  PATCH  /users/42          -> обновить пользователя
  DELETE /users/42          -> удалить пользователя

RPC-подобный подход (не REST):
  POST   /getUser?id=42
  POST   /updateUser
  POST   /deleteUser
```
Проверка: код-ревью может проверить, что новые эндпоинты используют существительные-ресурсы и HTTP-методы согласно их семантике, а не глаголы в пути для CRUD-операций.

### 195. [Q-03-04-0195] Зачем нужен заголовок Content-Type и что произойдёт, если сервер отправит JSON без него?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Content-Type сообщает получателю формат и кодировку тела сообщения (например, `application/json; charset=utf-8`); без него клиент может неправильно распарсить тело или библиотека по умолчанию откажется автоматически декодировать JSON.

**Разбор**
- **Как это работает:** заголовок передаётся и в запросе, и в ответе; на основе него сервер решает, как парсить тело запроса (JSON, form-data, multipart), а клиент — как интерпретировать ответ. Многие HTTP-клиенты (например, `requests`) предоставляют метод `.json()`, который сам пытается распарсить тело независимо от заголовка, но это не гарантия — некоторые строгие клиенты и браузеры ориентируются именно на заголовок.
- **На практике:** при отправке JSON нужно явно указывать `Content-Type: application/json`; для форм — `application/x-www-form-urlencoded`; для файлов — `multipart/form-data` с boundary. Фреймворки (FastAPI, Flask) обычно сами выставляют корректный Content-Type в ответе на основе возвращаемого объекта.
- **Частые ошибки:** отправлять JSON-тело с `Content-Type: text/plain`, из-за чего сервер пытается распарсить его как обычный текст и возвращает 400/422; забывать указывать `charset`, что может привести к проблемам с не-ASCII символами; вручную собирать multipart-запрос без корректного boundary.

**Пример / кейс**
```python
import requests
import json

# Намеренная ошибка: тело JSON, но заголовок не указан
resp = requests.post(
    "https://api.example.com/items",
    data=json.dumps({"name": "test"})  # без headers={"Content-Type": "application/json"}
)
print(resp.status_code)  # многие строгие серверы вернут 415 или 400

# Исправленный вариант
resp_ok = requests.post(
    "https://api.example.com/items",
    json={"name": "test"}  # requests сам выставит Content-Type: application/json
)
```
Проверка: сравнить заголовки исходящего запроса в обоих случаях (`resp.request.headers`) и статус-коды ответов.

### 196. [Q-03-04-0196] Что такое идемпотентность HTTP-метода и какие методы идемпотентны по спецификации?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Идемпотентный метод — такой, что повторное выполнение одного и того же запроса приводит к тому же результату на сервере, что и один вызов. GET, PUT, DELETE, HEAD, OPTIONS идемпотентны по спецификации; POST и PATCH — нет.

**Разбор**
- **Как это работает:** идемпотентность касается состояния ресурса на сервере, а не кода ответа — повторный DELETE уже удалённого ресурса может вернуть 404 вместо 204, но состояние ("ресурса нет") не меняется, поэтому метод остаётся идемпотентным.
- **На практике:** идемпотентность важна при повторных попытках (retries) на нестабильной сети — HTTP-клиенты и прокси могут безопасно повторить идемпотентный запрос при таймауте, не опасаясь побочных эффектов. Для неидемпотентных операций (POST) повторную отправку нужно защищать явно, например ключом идемпотентности.
- **Частые ошибки:** считать PUT идемпотентным автоматически, даже если обработчик добавляет побочные эффекты (например, инкрементирует счётчик версии при каждом вызове — это нарушает идемпотентность); путать идемпотентность с безопасностью (safe) — GET безопасен (не меняет состояние вовсе), а PUT идемпотентен, но может менять состояние при первом вызове.

**Пример / кейс**
```python
# Нарушение идемпотентности PUT: намеренная ошибка — счётчик обновлений растёт при каждом вызове
@app.put("/items/{item_id}")
def replace_item(item_id: int, item: Item):
    db[item_id] = item.dict()
    db[item_id]["update_count"] = db[item_id].get("update_count", 0) + 1  # нарушает идемпотентность
    return db[item_id]
```
Проверка: вызвать PUT дважды с одинаковым телом и сравнить весь ответ — поле `update_count` изменится, хотя при корректной идемпотентной реализации результат должен быть идентичен при повторных вызовах.

### 197. [Q-03-04-0197] Как в Python сериализовать объект в JSON для ответа API и что делать с типами, которые `json` не умеет кодировать напрямую (например, datetime)?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Модуль `json` сериализует только базовые типы (dict, list, str, int, float, bool, None); для datetime, Decimal, UUID и подобных нужно либо привести их к строке/числу вручную, либо передать кастомный `default`-обработчик в `json.dumps`, либо использовать библиотеку с готовой поддержкой (например, Pydantic в FastAPI).

**Разбор**
- **Как это работает:** `json.dumps` рекурсивно обходит структуру и для каждого значения ищет соответствие в таблице типов; при встрече неизвестного типа вызывается функция `default`, если она передана, иначе выбрасывается `TypeError`.
- **На практике:** в большинстве backend-фреймворков эта проблема решена за вас (FastAPI/Pydantic сами знают, как сериализовать datetime в ISO 8601), но при ручной работе с `json` или при сериализации нестандартных объектов нужно явно описывать преобразование.
- **Частые ошибки:** пытаться сериализовать `datetime` напрямую без обработчика и получать необработанное исключение в проде; сериализовывать datetime без таймзоны, из-за чего клиент не может корректно интерпретировать время; вручную конвертировать Decimal в float, теряя точность для денежных величин.

**Пример / кейс**
```python
import json
from datetime import datetime, timezone

def default_serializer(obj):
    if isinstance(obj, datetime):
        return obj.astimezone(timezone.utc).isoformat()
    raise TypeError(f"Object of type {type(obj)} is not JSON serializable")

payload = {"created_at": datetime.now(timezone.utc), "name": "order-1"}
result = json.dumps(payload, default=default_serializer)
print(result)  # {"created_at": "2024-05-01T12:00:00+00:00", "name": "order-1"}
```
Проверка: юнит-тест вызывает `json.dumps` без `default` и ожидает `TypeError`; с `default_serializer` — ожидает валидную JSON-строку с ISO-датой, которую можно распарсить обратно через `datetime.fromisoformat`.

### 198. [Q-03-04-0198] Чем различаются path-параметры и query-параметры в REST API и когда что использовать?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Path-параметры — часть URL, идентифицирующая конкретный ресурс (`/users/42`); query-параметры — необязательные модификаторы запроса после `?` (`?page=2&status=active`), используемые для фильтрации, сортировки, пагинации.

**Разбор**
- **Как это работает:** path-параметр обычно обязателен и однозначно определяет ресурс в иерархии URL; query-параметры опциональны и не меняют "адрес" ресурса, а уточняют, какую выборку или представление вернуть.
- **На практике:** если без параметра запрос не имеет смысла (например, ID пользователя) — это path-параметр; если параметр можно не указывать и получить разумный результат по умолчанию (фильтр, лимит) — это query-параметр. Такое разделение упрощает кэширование и генерацию документации (OpenAPI).
- **Частые ошибки:** засовывать в path опциональные фильтры (`/users/active/42`), что усложняет маршрутизацию и делает URL негибким; передавать идентификатор ресурса как query-параметр (`/users?id=42`), когда это должен быть path-параметр, что путает смысл "коллекция + фильтр" с "конкретный ресурс".

**Пример / кейс**
```python
from fastapi import FastAPI, Query

app = FastAPI()

@app.get("/users/{user_id}/orders")
def list_orders(
    user_id: int,
    status: str | None = Query(default=None),
    page: int = Query(default=1, ge=1),
):
    # user_id — path-параметр, обязателен; status и page — query-параметры, опциональны
    return {"user_id": user_id, "status": status, "page": page}
```
Проверка: вызов `GET /users/42/orders` без query — возвращает `status=None, page=1`; вызов `GET /users/42/orders?status=paid&page=2` — возвращает переданные значения; оба запроса адресуют одного и того же пользователя через один и тот же path.

### 199. [Q-03-04-0199] Как передать Bearer-токен для аутентификации запроса и почему его не стоит передавать в query-параметре?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Токен передают в заголовке `Authorization: Bearer <token>`; передача в query-параметре рискованна, так как URL часто логируется серверами, прокси и попадает в историю браузера, в отличие от заголовков.

**Разбор**
- **Как это работает:** HTTP-заголовки, в отличие от URL, как правило не попадают в access-логи веб-серверов и кэши промежуточных прокси по умолчанию (хотя сами заголовки тоже могут логироваться, если это явно настроено); сервер при каждом запросе читает заголовок `Authorization` и проверяет/декодирует токен (например, JWT) перед обработкой бизнес-логики.
- **На практике:** в Python такие проверки обычно реализуют через middleware или dependency (в FastAPI — `Depends`), чтобы не дублировать код проверки токена в каждом эндпоинте. Токен стоит передавать только по HTTPS, иначе заголовок можно перехватить в открытом виде.
- **Частые ошибки:** передавать токен в query-параметре "для простоты тестирования" и забывать убрать это в production-коде; хранить токен в логах при логировании полного запроса целиком, включая заголовки; не проверять срок действия (`exp`) токена на сервере.

**Пример / кейс**
```python
from fastapi import FastAPI, Depends, HTTPException, Header

app = FastAPI()

def verify_token(authorization: str = Header(default=None)):
    if not authorization or not authorization.startswith("Bearer "):
        raise HTTPException(status_code=401, detail="Missing or invalid token")
    token = authorization.removeprefix("Bearer ")
    if not is_token_valid(token):
        raise HTTPException(status_code=401, detail="Token expired or invalid")
    return token

@app.get("/profile")
def get_profile(token: str = Depends(verify_token)):
    return {"ok": True}
```
Проверка: запрос без заголовка `Authorization` возвращает 401; запрос с заголовком `Authorization: Bearer <валидный_токен>` возвращает 200; грепом по логам веб-сервера подтверждают отсутствие токена в записанных URL.

### 200. [Q-03-04-0200] Что такое CORS и почему браузер может блокировать запрос к API даже при корректном ответе сервера?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
CORS (Cross-Origin Resource Sharing) — механизм браузера, разрешающий или запрещающий JS-коду с одного origin делать запросы к API на другом origin; браузер блокирует ответ на стороне клиента, если сервер не вернул правильные заголовки `Access-Control-Allow-*`, даже если сам HTTP-запрос дошёл и обработался успешно.

**Разбор**
- **Как это работает:** для "небезопасных" запросов (например, с кастомными заголовками или методом PUT/DELETE) браузер сначала отправляет предварительный `OPTIONS`-запрос (preflight), и только если сервер ответит разрешающими заголовками, выполняется основной запрос. Для простых GET/POST без специальных заголовков preflight не нужен, но ответ всё равно будет скрыт от JS без `Access-Control-Allow-Origin`.
- **На практике:** сервер должен явно указать разрешённые origin, методы и заголовки; `Access-Control-Allow-Origin: *` подходит для публичных API без авторизации через cookie, но несовместим с `Access-Control-Allow-Credentials: true`. Настройку обычно делают через middleware фреймворка, а не руками в каждом эндпоинте.
- **Частые ошибки:** считать CORS защитой самого API от несанкционированных запросов (на самом деле это защита браузерного пользователя, серверные-к-серверным запросам CORS не мешает); ставить `Access-Control-Allow-Origin: *` вместе с передачей cookie/credentials, что браузер прямо запретит; забывать обрабатывать метод `OPTIONS` на сервере, из-за чего preflight возвращает 404/405.

**Пример / кейс**
```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://frontend.example.com"],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
)
```
Проверка: запрос с `curl` напрямую (без браузера) с тем же токеном успешно получает данные, несмотря на отсутствие заголовков CORS; тот же запрос из консоли браузера с другого origin без настроенного middleware будет виден в Network как успешный (200), но JS получит ошибку CORS в консоли.

### 201. [Q-03-04-0201] Как корректно обработать и вернуть ошибку валидации входных данных в API?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Нужно вернуть статус 400 или 422 с машиночитаемым телом ответа, описывающим, какое поле невалидно и почему, не выбрасывая необработанное исключение и не возвращая 500.

**Разбор**
- **Как это работает:** 422 Unprocessable Entity означает, что запрос синтаксически верен, но данные не прошли бизнес-валидацию (например, email в неверном формате); 400 Bad Request — более общий код для некорректного запроса в целом. Многие фреймворки (FastAPI с Pydantic) автоматически возвращают 422 при ошибке валидации схемы.
- **На практике:** тело ответа об ошибке стоит делать консистентным по структуре для всего API (например, `{"detail": [...]}` или `{"errors": [{"field": ..., "message": ...}]}`), чтобы клиент мог программно обрабатывать ошибки, а не парсить произвольный текст.
- **Частые ошибки:** возвращать 500 при ошибке валидации, из-за необработанного исключения типа `ValueError` внутри обработчика; возвращать 200 с полем `"success": false` вместо честного кода ошибки; не указывать, какое именно поле невалидно, вынуждая клиента угадывать причину.

**Пример / кейс**
```python
from pydantic import BaseModel, EmailStr, field_validator
from fastapi import FastAPI
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

app = FastAPI()

class CreateUser(BaseModel):
    email: EmailStr
    age: int

    @field_validator("age")
    @classmethod
    def age_must_be_positive(cls, v):
        if v <= 0:
            raise ValueError("age must be positive")
        return v

@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request, exc):
    return JSONResponse(status_code=422, content={"errors": exc.errors()})

@app.post("/users")
def create_user(payload: CreateUser):
    return {"ok": True}
```
Проверка: POST с `{"email": "not-an-email", "age": -1}` возвращает 422 и тело со списком ошибок по полям `email` и `age`, а не 500.

### 202. [Q-03-04-0202] Что такое пагинация в API и зачем она нужна при работе со списками ресурсов?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Пагинация — разбиение большого списка ресурсов на меньшие порции (страницы), которые клиент запрашивает по очереди; она нужна, чтобы не возвращать весь набор данных за один запрос, что перегружает память сервера, сеть и клиента.

**Разбор**
- **Как это работает:** клиент передаёт параметры (например, `page`/`per_page` или `limit`/`offset`), сервер ограничивает выборку с помощью `LIMIT`/`OFFSET` в SQL (или аналога в ORM) и возвращает только часть данных плюс метаданные (общее количество, наличие следующей страницы).
- **На практике:** без пагинации по умолчанию эндпоинт списка легко превращается в "выгрузить всю таблицу", что при росте данных рано или поздно приведёт к деградации производительности и таймаутам. Лимит страницы стоит ограничивать сверху (например, максимум 100), чтобы клиент не мог запросить миллион записей одним вызовом.
- **Частые ошибки:** не задавать значение по умолчанию и максимум для размера страницы, из-за чего один клиент может перегрузить сервис; возвращать общее количество через `COUNT(*)` по всей таблице при каждом запросе страницы без необходимости, что само по себе может быть дорогим на больших таблицах.

**Пример / кейс**
```python
from fastapi import FastAPI, Query

app = FastAPI()

@app.get("/items")
def list_items(page: int = Query(1, ge=1), per_page: int = Query(20, ge=1, le=100)):
    offset = (page - 1) * per_page
    rows = db_session.execute(
        "SELECT id, name FROM items ORDER BY id LIMIT :limit OFFSET :offset",
        {"limit": per_page, "offset": offset},
    ).fetchall()
    return {"page": page, "per_page": per_page, "items": [dict(r) for r in rows]}
```
Проверка: запрос `GET /items?page=1&per_page=2` возвращает ровно 2 записи; запрос с `per_page=1000` обрезается до максимума 100 (или возвращает 422, если лимит жёсткий) — проверяется тестом на длину возвращённого списка.

### 203. [Q-03-04-0203] Когда для ошибки нужно вернуть 400, когда 404, а когда 422?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
400 — запрос в принципе некорректен (например, невалидный JSON или отсутствует обязательный параметр); 404 — запрошенный ресурс не найден по указанному адресу; 422 — запрос синтаксически корректен, но данные не проходят бизнес-валидацию (например, нарушено правило или формат поля).

**Разбор**
- **Как это работает:** различие между этими кодами — в том, на каком этапе обработки запрос "отваливается": парсинг синтаксиса (400), поиск ресурса по идентификатору (404), проверка семантики данных относительно бизнес-правил (422). Некоторые команды используют 400 универсально вместо 422 — это допустимо, если так зафиксировано в контракте API и единообразно применяется.
- **На практике:** важно согласовать выбор кодов в команде и описать в OpenAPI-схеме, чтобы клиенты могли предсказуемо обрабатывать разные типы ошибок (например, повторный запрос при 400 не поможет, а при временной недоступности зависимости — другой код).
- **Частые ошибки:** возвращать 404 для "доступ запрещён" вместо 403, чтобы "скрыть" существование ресурса, без явного решения команды об этом как о политике безопасности; возвращать 400 при отсутствии ресурса по ID, путая синтаксическую ошибку запроса с отсутствием данных.

**Пример / кейс**
```python
@app.get("/orders/{order_id}")
def get_order(order_id: int):
    order = orders_repo.find(order_id)
    if order is None:
        return JSONResponse(status_code=404, content={"detail": "Order not found"})
    return order

@app.post("/orders")
def create_order(payload: dict):
    if "items" not in payload:
        return JSONResponse(status_code=400, content={"detail": "items field is required"})
    if len(payload["items"]) == 0:
        return JSONResponse(status_code=422, content={"detail": "order must contain at least one item"})
    return {"ok": True}
```
Проверка: тест с несуществующим `order_id` получает 404; тест без поля `items` получает 400; тест с пустым списком `items` получает 422 — три разных сценария различимы по коду ответа.

### 204. [Q-03-04-0204] Что такое HTTP keep-alive (постоянное соединение) и зачем он нужен при работе с API?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Keep-alive позволяет повторно использовать одно и то же TCP-соединение для нескольких HTTP-запросов подряд, избегая накладных расходов на установку нового соединения (и TLS-хендшейка) для каждого запроса.

**Разбор**
- **Как это работает:** в HTTP/1.1 keep-alive включён по умолчанию (в отличие от HTTP/1.0), соединение остаётся открытым после ответа, пока клиент или сервер не закроют его явно (заголовком `Connection: close`) или по таймауту неактивности.
- **На практике:** при множестве вызовов к одному и тому же внешнему сервису стоит использовать переиспользуемую сессию клиента (например, `requests.Session()` или пул соединений в `httpx`/`aiohttp`), а не создавать новое соединение на каждый запрос — это заметно снижает латентность при частых вызовах.
- **Частые ошибки:** создавать новый `requests.Session()` или новое TCP-соединение на каждый вызов функции, обрабатывающей запрос, что увеличивает нагрузку и задержку при частых обращениях к внешнему API; не закрывать сессии/пулы соединений, что может приводить к утечке файловых дескрипторов при долгой работе процесса.

**Пример / кейс**
```python
import requests

# Неэффективно: новое соединение на каждый вызов
def fetch_bad(url):
    return requests.get(url).json()

# Эффективно: одно переиспользуемое соединение (keep-alive) для серии запросов
session = requests.Session()

def fetch_good(url):
    return session.get(url).json()

for i in range(100):
    fetch_good(f"https://api.example.com/items/{i}")
```
Проверка: профилирование (например, через `time.perf_counter` вокруг цикла из 100 запросов к одному хосту) показывает заметно меньшее суммарное время у варианта с `Session`, чем без неё, за счёт переиспользования TCP/TLS-соединения.

### 205. [Q-03-04-0205] Чем webhook отличается от polling при интеграции с внешним сервисом?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Polling — это когда ваш сервис сам периодически опрашивает внешний API, чтобы узнать об изменениях; webhook — это когда внешний сервис сам отправляет HTTP-запрос на ваш URL в момент события, без необходимости постоянно спрашивать.

**Разбор**
- **Как это работает:** при polling клиент шлёт запросы с интервалом (например, раз в минуту) и сравнивает состояние с предыдущим; при webhook сторонний сервис заранее настраивается на отправку POST-запроса на указанный URL при возникновении события (оплата прошла, статус изменился).
- **На практике:** webhook снижает задержку реакции на событие и нагрузку по сравнению с частым polling, но требует, чтобы ваш сервис был доступен из интернета по HTTPS и мог обработать повторную доставку одного и того же события (внешние сервисы обычно не гарантируют доставку ровно один раз). Polling проще реализовать и тестировать, но создаёт либо задержку, либо лишнюю нагрузку при частом опросе.
- **Частые ошибки:** не проверять подлинность входящего webhook-запроса (его может отправить кто угодно, кто знает URL), не обрабатывать повторную доставку одного и того же webhook как идемпотентную операцию, использовать слишком частый polling "на всякий случай", создавая лишнюю нагрузку на внешний API и риск упереться в rate limit.

**Пример / кейс**
```python
from fastapi import FastAPI, Request

app = FastAPI()

@app.post("/webhooks/payment")
async def payment_webhook(request: Request):
    payload = await request.json()
    event_id = payload["event_id"]
    if already_processed(event_id):
        return {"status": "duplicate_ignored"}
    process_payment_event(payload)
    mark_processed(event_id)
    return {"status": "ok"}
```
Проверка: тест отправляет один и тот же payload два раза подряд — убеждается, что бизнес-логика (`process_payment_event`) выполнилась только один раз, а второй вызов вернул `duplicate_ignored`.

### 206. [Q-03-04-0206] Как вызвать внешний API через библиотеку requests и корректно обработать таймаут?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Нужно явно передавать параметр `timeout` в вызов `requests.get`/`requests.post` и оборачивать вызов в `try/except`, обрабатывая `requests.exceptions.Timeout` и `requests.exceptions.RequestException` отдельно от бизнес-логики успешного ответа.

**Разбор**
- **Как это работает:** без явного `timeout` запрос может "висеть" бесконечно, если внешний сервис не отвечает, занимая поток/соединение и потенциально истощая пул ресурсов приложения. `timeout` можно задать как одно число (на соединение и чтение вместе) или tuple `(connect_timeout, read_timeout)`.
- **На практике:** таймаут стоит выбирать исходя из SLA внешнего сервиса и допустимой задержки для вашего пользователя, а не ставить "на глаз" — слишком маленький таймаут даст ложные обрывы под нагрузкой, слишком большой — удержит ресурсы при реальном отказе внешнего сервиса. При таймауте нужно решить: вернуть пользователю ошибку, попробовать retry, или отдать fallback-данные — выбор зависит от критичности операции.
- **Частые ошибки:** вызывать `requests.get(url)` без `timeout` вообще — по умолчанию библиотека будет ждать бесконечно; ловить общий `Exception` без различения таймаута, ошибки соединения и ошибки HTTP-статуса, что мешает принимать разные решения для разных сбоев.

**Пример / кейс**
```python
import requests

def call_external_service(order_id: int) -> dict | None:
    try:
        resp = requests.get(
            f"https://partner.example.com/orders/{order_id}",
            timeout=(2, 5),  # 2с на соединение, 5с на чтение ответа
        )
        resp.raise_for_status()
        return resp.json()
    except requests.exceptions.Timeout:
        log.warning("partner service timed out", order_id=order_id)
        return None
    except requests.exceptions.RequestException as exc:
        log.error("partner service call failed", order_id=order_id, error=str(exc))
        return None
```
Проверка: юнит-тест с замоканным медленным ответом (`responses`/`requests-mock` с задержкой больше таймаута) проверяет, что функция вернёт `None`, а не зависнет и не выбросит необработанное исключение наружу.

### 207. [Q-03-04-0207] Зачем в URL API указывают версию (например, `/v1/`) и что это даёт?

**Направление:** Python Backend Developer

**Короткий ответ**<br>
Версия в URL позволяет вносить несовместимые изменения в API, продолжая обслуживать старых клиентов на прежней версии, пока они не перейдут на новую — это один из простых способов версионирования контракта.

**Разбор**
- **Как это работает:** при изменении формата ответа, удалении поля или смене поведения эндпоинта несовместимым образом создаётся новая версия (`/v2/...`), а старая версия продолжает работать без изменений для существующих интеграций.
- **На практике:** версионирование в URL — не единственный способ (есть версия через заголовок или content negotiation), но он самый явный и простой для отладки (видно прямо в адресе, легко тестировать curl'ом). Важно заранее договориться о политике поддержки старых версий (сколько версий поддерживается одновременно, срок депрекации).
- **Частые ошибки:** менять поведение существующего эндпоинта без увеличения версии, молча ломая всех текущих клиентов; увеличивать версию при любом, даже совместимом изменении (например, добавлении нового опционального поля), что создаёт ненужную фрагментацию и нагрузку на поддержку нескольких версий.

**Пример / кейс**
```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/v1/users/{user_id}")
def get_user_v1(user_id: int):
    return {"id": user_id, "full_name": "Иван Иванов"}  # одно строковое поле

@app.get("/v2/users/{user_id}")
def get_user_v2(user_id: int):
    return {"id": user_id, "first_name": "Иван", "last_name": "Иванов"}  # разбито на два поля — несовместимое изменение
```
Проверка: существующие тесты/клиенты, завязанные на `/v1/` и поле `full_name`, продолжают проходить без изменений; новые клиенты осознанно переходят на `/v2/` и поля `first_name`/`last_name`.

### 208. [Q-03-04-0208] Зачем нужен заголовок Content-Length и что может пойти не так, если он указан неверно?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Content-Length сообщает получателю точный размер тела сообщения в байтах, чтобы он знал, когда тело полностью получено; если значение указано неверно (меньше или больше фактического размера), получатель может обрезать данные или зависнуть, ожидая оставшиеся байты.

**Разбор**
- **Как это работает:** при использовании keep-alive заголовок Content-Length критичен, чтобы сервер/клиент понимал, где заканчивается текущий ответ и начинается следующий в рамках одного TCP-соединения; альтернатива — `Transfer-Encoding: chunked`, когда размер неизвестен заранее (например, при потоковой передаче).
- **На практике:** в большинстве backend-фреймворков этот заголовок выставляется автоматически на основе фактического тела ответа, и разработчику не нужно считать его руками. Вручную считать длину нужно, если тело собирается в несколько этапов или идёт стриминг с явным указанием размера.
- **Частые ошибки:** вручную выставлять Content-Length при прокси/модификации тела ответа (например, в middleware, которое меняет текст), забывая пересчитать длину после изменения — это приводит к обрезанному или "зависшему" ответу на стороне клиента; путать Content-Length с количеством символов в строке без учёта многобайтовой кодировки UTF-8 для не-ASCII текста.

**Пример / кейс**
```python
# Намеренная ошибка: длина считается по символам, а не по байтам UTF-8
text = "Привет"  # 6 символов, но 12 байт в UTF-8
wrong_length = len(text)  # 6 — неверно для Content-Length
correct_length = len(text.encode("utf-8"))  # 12 — корректно
```
Проверка: HTTP-клиент, получивший ответ с `Content-Length: 6`, но телом из 12 байт UTF-8, либо обрежет текст до 6 байт (сломав кодировку), либо зависнет, ожидая данные, которых не будет, — это легко увидеть в curl с `-v` и сравнением длины вывода.

### 209. [Q-03-04-0209] Как выглядит простой REST-эндпоинт для получения списка ресурсов и что должен содержать хороший ответ списка?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Эндпоинт списка должен принимать параметры фильтрации/сортировки/пагинации через query-параметры и возвращать сами элементы вместе с метаданными (общее количество или признак следующей страницы), а не только "голый" массив.

**Разбор**
- **Как это работает:** клиент вызывает `GET /resource?...`, сервер применяет фильтры к запросу к БД, ограничивает выборку пагинацией и формирует структурированный ответ. Возврат "голого" массива усложняет добавление метаданных в будущем без breaking change (так как корневой элемент JSON уже занят массивом).
- **На практике:** оборачивание списка в объект (`{"items": [...], "total": N, "page": P}`) с самого начала облегчает последующее добавление полей без изменения структуры верхнего уровня — это пример продуманного контракта на будущее.
- **Частые ошибки:** возвращать просто `[...]` на верхнем уровне ответа, из-за чего позже невозможно добавить метаданные без нарушения совместимости для всех текущих клиентов; не документировать, какие query-параметры поддерживаются и какие у них значения по умолчанию.

**Пример / кейс**
```python
from fastapi import FastAPI, Query

app = FastAPI()

@app.get("/articles")
def list_articles(
    author: str | None = Query(default=None),
    page: int = Query(default=1, ge=1),
    per_page: int = Query(default=20, ge=1, le=100),
):
    query = build_query(author=author)
    total = count_articles(query)
    items = fetch_articles(query, page=page, per_page=per_page)
    return {
        "items": items,
        "page": page,
        "per_page": per_page,
        "total": total,
    }
```
Проверка: тест проверяет, что ответ — объект с ключами `items`, `page`, `per_page`, `total`, а не массив напрямую; и что `len(items) <= per_page`.

### 210. [Q-03-04-0210] Что такое middleware в веб-фреймворке и для каких задач его обычно используют?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Junior

**Короткий ответ**<br>
Middleware — это слой кода, который выполняется для каждого (или группы) HTTP-запроса до и/или после основного обработчика; его используют для сквозной функциональности — логирования, аутентификации, CORS, обработки ошибок, замера времени запроса.

**Разбор**
- **Как это работает:** запрос проходит цепочку middleware по порядку их регистрации перед тем, как попасть в обработчик маршрута, а ответ проходит ту же цепочку в обратном порядке — так middleware может модифицировать и запрос, и ответ.
- **На практике:** middleware удобно для логики, общей для всех (или многих) эндпоинтов — не нужно дублировать код проверки токена или логирования в каждом обработчике отдельно. Но не всякая сквозная логика должна быть middleware — если проверка специфична для конкретного эндпоинта (например, доступ к конкретному ресурсу), лучше использовать dependency/декоратор на уровне обработчика.
- **Частые ошибки:** помещать в middleware тяжёлую бизнес-логику, которая должна зависеть от параметров конкретного запроса/маршрута, что усложняет тестирование и переиспользование; забывать обрабатывать исключения внутри middleware, из-за чего ошибка в middleware "роняет" обработку запроса до того, как сработает глобальный обработчик ошибок.

**Пример / кейс**
```python
import time
from fastapi import FastAPI, Request

app = FastAPI()

@app.middleware("http")
async def add_process_time_header(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    duration = time.perf_counter() - start
    response.headers["X-Process-Time"] = str(duration)
    return response
```
Проверка: любой запрос к приложению в ответе содержит заголовок `X-Process-Time`; тест проверяет его наличие и что значение — валидное число.

### 211. [Q-03-04-0211] Как спроектировать REST API для вложенных ресурсов (например, заказы пользователя) и когда использовать вложенный путь, а когда — плоский с фильтром?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Вложенный путь (`/users/{id}/orders`) уместен, когда ресурс логически не существует без родителя и к нему всегда обращаются в его контексте; плоский путь с фильтром (`/orders?user_id={id}`) лучше, когда ресурс самостоятелен и нужно выбирать его по разным критериям, не только по родителю.

**Разбор**
- **Как это работает:** вложенность пути отражает владение (ownership) — заказ существует только в контексте пользователя, который его создал. Но если нужно искать заказы одновременно по пользователю, статусу и дате — чисто вложенный путь усложняет комбинирование фильтров, а плоский с query-параметрами делает это естественно.
- **На практике:** глубокую вложенность (`/users/{id}/orders/{oid}/items/{iid}`) стоит ограничивать одним-двумя уровнями — иначе URL становятся громоздкими и ломкими при реорганизации модели данных. Часто практичнее делать `GET /orders/{oid}` без родителя в пути (ресурс сам по себе уникален по ID), используя вложенность только для создания (`POST /users/{id}/orders`) или списков в контексте родителя.
- **Частые ошибки:** требовать родительский ID в пути для операций с конкретным дочерним ресурсом, когда дочерний ID уже глобально уникален (это заставляет клиента хранить лишний контекст); смешивать вложенный путь и отдельный плоский эндпоинт для одного и того же ресурса без единого источника истины, что увеличивает поверхность API и путает клиентов.

**Пример / кейс**
```python
from fastapi import FastAPI

app = FastAPI()

# Создание в контексте родителя — вложенность оправдана
@app.post("/users/{user_id}/orders")
def create_order(user_id: int, payload: dict):
    return create_order_for_user(user_id, payload)

# Доступ к конкретному заказу — по глобально уникальному ID, без родителя в пути
@app.get("/orders/{order_id}")
def get_order(order_id: int):
    return find_order(order_id)

# Поиск по нескольким критериям — плоский путь с фильтрами
@app.get("/orders")
def list_orders(user_id: int | None = None, status: str | None = None):
    return search_orders(user_id=user_id, status=status)
```
Проверка: тест подтверждает, что `GET /orders/{order_id}` работает независимо от того, под каким пользователем был создан заказ, и что `GET /orders?user_id=1&status=paid` корректно комбинирует фильтры, которые было бы неудобно выразить через чистую вложенность.

### 212. [Q-03-04-0212] Сравните offset-based и cursor-based пагинацию: какие проблемы решает каждая и когда предпочесть cursor-based?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Offset-пагинация (`LIMIT/OFFSET`) проста, но даёт сдвиги и дубликаты/пропуски при параллельных вставках/удалениях и деградирует по производительности на больших смещениях; cursor-based пагинация (по последнему увиденному значению ключа) устойчива к изменениям данных между запросами страниц и быстрее на больших датасетах, но не позволяет прыгать на произвольную страницу по номеру.

**Разбор**
- **Как это работает:** offset-пагинация просит БД пропустить N строк и вернуть следующие M — при больших N база всё равно сканирует/сортирует пропущенные строки, что линейно растёт по стоимости. Cursor-пагинация использует значение (обычно ID или комбинацию полей сортировки) последней полученной записи как отправную точку для следующего запроса (`WHERE id > :last_id ORDER BY id LIMIT :limit`), что позволяет БД использовать индекс для быстрого поиска стартовой точки без сканирования пропущенных строк.
- **На практике:** если пользователю нужно показать номера страниц и дать переход "на страницу 5" — offset удобнее и привычнее для UI, несмотря на риск нестабильности при параллельных изменениях. Для бесконечной прокрутки, API с большими объёмами данных или высокой частотой изменений (лента событий, список логов) cursor-based предпочтительнее. Выбор зависит от объёма данных, частоты изменений и требований UX — универсального правильного ответа нет.
- **Частые ошибки:** использовать offset-пагинацию для API с высокочастотными вставками и удивляться дубликатам/пропускам записей между страницами у клиента; реализовывать cursor как просто "предыдущий offset в base64", что не решает проблему нестабильности, а лишь маскирует её; не добавлять уникальный tie-breaker (например, ID) к курсору при сортировке по неуникальному полю (дата), что может приводить к зацикливанию или пропуску записей с одинаковым значением сортировки.

**Пример / кейс**
```sql
-- Offset-пагинация: стоимость растёт с ростом OFFSET
SELECT id, name FROM events ORDER BY created_at DESC LIMIT 20 OFFSET 100000;

-- Cursor-пагинация: использует индекс по (created_at, id) напрямую
SELECT id, name, created_at FROM events
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```
Проверка: нагрузочный тест сравнивает время ответа offset-запроса при `OFFSET=0` и `OFFSET=100000` (второй заметно медленнее без покрывающего индекса), тогда как время cursor-запроса остаётся примерно одинаковым независимо от "глубины" пагинации при наличии подходящего индекса.

### 213. [Q-03-04-0213] Как обеспечить идемпотентность POST-запроса создания ресурса при повторной доставке (например, из-за retry на стороне клиента)?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Клиент передаёт уникальный ключ идемпотентности (например, в заголовке `Idempotency-Key`), сервер сохраняет связь "ключ → результат" и при повторном запросе с тем же ключом возвращает сохранённый результат, не выполняя операцию повторно.

**Разбор**
- **Как это работает:** при первом запросе с ключом сервер атомарно (например, через уникальный индекс в БД) резервирует этот ключ, выполняет операцию и сохраняет результат (включая статус-код и тело ответа) привязанным к ключу; при повторном запросе с тем же ключом сервер находит существующую запись и возвращает тот же результат без повторного выполнения бизнес-логики.
- **На практике:** ключ должен генерировать клиент (а не сервер) до первой попытки отправки, чтобы повторная отправка при таймауте использовала тот же ключ. Время жизни записи об идемпотентности нужно ограничивать (например, 24 часа), чтобы не накапливать их бесконечно. Важно защититься от гонки: если два запроса с одинаковым ключом приходят почти одновременно, нужна атомарная операция "вставить, если не существует", а не read-then-write.
- **Частые ошибки:** генерировать ключ идемпотентности на сервере или выводить его из содержимого запроса без согласия клиента — тогда клиент не может переиспользовать его при реальном retry; проверять наличие ключа и сохранять результат в два отдельных, не атомарных шага, что создаёт окно для двойного выполнения операции при параллельных повторных запросах.

**Пример / кейс**
```python
from fastapi import FastAPI, Header, HTTPException

app = FastAPI()

@app.post("/payments")
def create_payment(payload: dict, idempotency_key: str = Header(...)):
    existing = idempotency_store.get_if_exists(idempotency_key)  # атомарная проверка/резервирование
    if existing is not None:
        return existing["response_body"]
    result = process_payment(payload)
    idempotency_store.save(idempotency_key, result)
    return result
```
Проверка: интеграционный тест отправляет один и тот же запрос с одинаковым `Idempotency-Key` дважды подряд (в том числе параллельно) и убеждается, что платёж в системе создан ровно один раз, а оба ответа идентичны.

### 214. [Q-03-04-0214] Как диагностировать проблему N+1 запросов при сериализации вложенных объектов в API-ответе и как её устранить?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
N+1 проявляется, когда для одного списка из N объектов сериализатор выполняет по отдельному запросу на связанные данные для каждого элемента; диагностируют по логам SQL-запросов (один запрос на список + N похожих запросов), а устраняют через предварительную загрузку связанных данных одним batched-запросом (eager loading / join / `IN`-запрос).

**Разбор**
- **Как это работает:** если эндпоинт возвращает список заказов с полем "имя клиента", а код наивно обращается к `order.customer.name` для каждого заказа в цикле, при ленивой загрузке ORM это превращается в отдельный SQL-запрос на каждого клиента — при 100 заказах это 1 + 100 запросов вместо одного-двух.
- **На практике:** включить в логи или `EXPLAIN` количество выполненных запросов на один вызов эндпоинта, сравнить его с ожидаемым (константным, не зависящим от размера списка); в SQLAlchemy использовать `joinedload`/`selectinload`, в Django ORM — `select_related`/`prefetch_related`, либо вручную собрать все нужные ID и одним запросом с `IN` подтянуть связанные записи в словарь перед сериализацией.
- **Частые ошибки:** обнаруживать проблему только в production под нагрузкой, а не на этапе код-ревью или тестов с логированием SQL; "решать" N+1 кэшированием отдельных запросов вместо устранения причины, что скрывает проблему лишь частично и не помогает при холодном кэше; использовать eager loading "на всякий случай" для всех связей, включая те, что не нужны в конкретном ответе, что увеличивает объём данных, перекачиваемых из БД, без необходимости.

**Пример / кейс**
```python
# Намеренная проблема N+1 (SQLAlchemy, lazy loading по умолчанию)
orders = session.query(Order).filter(Order.status == "paid").all()
result = [{"id": o.id, "customer_name": o.customer.name} for o in orders]  # отдельный запрос на каждый o.customer

# Исправление: eager loading одним запросом
from sqlalchemy.orm import joinedload
orders = (
    session.query(Order)
    .options(joinedload(Order.customer))
    .filter(Order.status == "paid")
    .all()
)
result = [{"id": o.id, "customer_name": o.customer.name} for o in orders]  # customer уже подгружен
```
Проверка: включить `echo=True` в SQLAlchemy (или аналогичное логирование SQL) и сравнить количество выполненных запросов до и после исправления при 50 заказах — должно упасть с ~51 до 1–2 независимо от размера списка.

### 215. [Q-03-04-0215] Какие есть подходы к версионированию API (URL, заголовок, content negotiation) и в чём их практические плюсы и минусы?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Версионирование через URL (`/v1/...`) — самое явное и простое для отладки, но "захватывает" версию во всех ссылках; через заголовок (`Api-Version: 2`) или content negotiation (`Accept: application/vnd.myapi.v2+json`) — чище с точки зрения REST (URL остаётся постоянным идентификатором ресурса), но менее заметно и сложнее для отладки curl'ом и кэширования прокси.

**Разбор**
- **Как это работает:** при версионировании через URL маршрутизация выбирает обработчик сразу по префиксу пути; при версионировании через заголовок один и тот же путь обслуживается разной логикой в зависимости от значения заголовка, что требует дополнительной диспетчеризации внутри приложения или на уровне API-гейтвея.
- **На практике:** выбор зависит от аудитории API: для публичного API с внешними интеграторами версия в URL снижает порог входа (видно в документации, легко протестировать вручную); для внутреннего API, тесно интегрированного с API-гейтвеем и кэшированием по URL, версия в заголовке может быть предпочтительнее, чтобы не размножать записи кэша на каждую версию одного и того же логического ресурса.
- **Частые ошибки:** смешивать подходы в рамках одного API без единой политики (часть эндпоинтов версионируется в URL, часть — в заголовке), что усложняет документацию и клиентские SDK; не определять явного поведения при отсутствии заголовка версии (нужно решить — использовать последнюю версию по умолчанию или отвечать ошибкой, и задокументировать это решение).

**Пример / кейс**
```http
# Версионирование через URL
GET /v2/orders/42 HTTP/1.1
Host: api.example.com

# Версионирование через заголовок
GET /orders/42 HTTP/1.1
Host: api.example.com
Api-Version: 2

# Content negotiation
GET /orders/42 HTTP/1.1
Host: api.example.com
Accept: application/vnd.example.v2+json
```
Проверка: для каждого подхода пишется тест, что запрос без указания версии (или со старой версией) получает ответ в формате v1, а с явным указанием v2 — в формате v2; дополнительно проверяется поведение кэширующего прокси перед сервисом для варианта с заголовком (не "путает" ли он ответы разных версий при одинаковом URL).

### 216. [Q-03-04-0216] Как спроектировать обработку сбоев при вызове внешнего сервиса: retry, timeout и circuit breaker — зачем нужен каждый механизм?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Timeout ограничивает, сколько вы готовы ждать один вызов; retry повторяет вызов при временном сбое (обычно с экспоненциальной задержкой); circuit breaker временно прекращает попытки вызова сервиса, который стабильно отказывает, чтобы не тратить ресурсы и не усугублять его перегрузку.

**Разбор**
- **Как это работает:** эти три механизма решают разные проблемы и обычно применяются вместе: timeout защищает от бесконечного ожидания одного вызова, retry сглаживает кратковременные сетевые сбои, circuit breaker защищает систему от продолжительной недоступности зависимости, переводя вызовы в "открытое" состояние (быстрый отказ без реального запроса) на время восстановления.
- **На практике:** retry стоит применять только к идемпотентным операциям или операциям с защитой идемпотентности (см. idempotency key), иначе повтор может продублировать побочный эффект; задержку между попытками стоит увеличивать экспоненциально с джиттером, чтобы не создавать синхронизированный всплеск нагрузки ("thundering herd") на восстанавливающийся сервис. Количество попыток и пороги circuit breaker должны быть основаны на реальных SLA зависимости и критичности операции для пользователя — универсальных "правильных" чисел нет.
- **Частые ошибки:** делать retry для неидемпотентных операций без ключа идемпотентности, создавая дубликаты; ставить retry без ограничения общего времени (суммарный backoff может растянуться на минуты, пока пользователь ждёт ответа); не логировать переходы circuit breaker между состояниями, из-за чего невозможно понять в production, почему сервис вдруг стал быстро отказывать без реальных попыток вызова.

**Пример / кейс**
```python
import time
import random
import requests

def call_with_retry(url, max_attempts=3, base_delay=0.5):
    for attempt in range(1, max_attempts + 1):
        try:
            resp = requests.get(url, timeout=3)
            resp.raise_for_status()
            return resp.json()
        except requests.exceptions.RequestException as exc:
            if attempt == max_attempts:
                raise
            delay = base_delay * (2 ** (attempt - 1)) + random.uniform(0, 0.1)
            time.sleep(delay)  # экспоненциальный backoff с джиттером
```
Проверка: тест с замоканным сервисом, который отказывает 2 раза и отвечает успешно на 3-й попытке, подтверждает, что функция вернёт корректный результат; отдельный тест с сервисом, который отказывает все 3 раза, подтверждает, что исключение выбрасывается после ровно `max_attempts` попыток.

### 217. [Q-03-04-0217] В чём ключевое отличие GraphQL от REST и как в GraphQL проявляется проблема, аналогичная N+1 в REST?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
GraphQL позволяет клиенту одним запросом запросить произвольный набор полей и связанных сущностей через единый эндпоинт, в отличие от REST с фиксированной формой ответа на фиксированном URL; при этом резолверы для вложенных полей часто вызываются отдельно для каждого элемента списка, что создаёт классический N+1 на уровне резолверов, если не использовать batching (например, DataLoader).

**Разбор**
- **Как это работает:** в REST сервер решает, какие данные вернуть на конкретный путь; в GraphQL клиент описывает нужную форму ответа в запросе (query), а сервер исполняет граф резолверов, где каждое поле может иметь собственную функцию получения данных, независимо вызываемую для каждого родительского объекта.
- **На практике:** GraphQL решает проблему "недостаточности данных за один запрос" (undersetching) и "избыточности данных" (overfetching), характерные для жёстких REST-ответов, но добавляет сложность на стороне сервера: без батчинга резолвер для поля `author` у списка из 50 постов выполнит 50 отдельных запросов к БД. Выбор между REST и GraphQL зависит от разнообразия клиентов и их потребностей в данных, а не является универсально "более современным" решением.
- **Частые ошибки:** внедрять GraphQL, рассчитывая, что он "сам" решит проблемы производительности REST, и не предусматривать batching резолверов с самого начала; не ограничивать глубину/сложность запроса на стороне сервера, что позволяет клиенту сформировать чрезмерно дорогой вложенный запрос (query complexity attack).

**Пример / кейс**
```python
# Псевдокод резолвера на Python (Graphene/Strawberry-подобный стиль)
# Намеренная проблема N+1: отдельный запрос на автора для каждого поста
def resolve_author(post, info):
    return db.query(Author).get(post.author_id)  # вызывается отдельно для каждого post в списке

# Исправление через batching (DataLoader-подобный паттерн)
def resolve_author_batched(post, info):
    return info.context["author_loader"].load(post.author_id)  # накапливает ID и делает один IN-запрос
```
Проверка: включить логирование SQL-запросов при выполнении GraphQL-запроса со списком из 50 постов и полем `author` у каждого — без batching видно 50+ запросов к таблице авторов, с `DataLoader` — один запрос с `WHERE id IN (...)`.

### 218. [Q-03-04-0218] Как обеспечить обратную совместимость API при изменении структуры ответа, не повышая major-версию?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Совместимые изменения — это добавление новых опциональных полей в ответ и новых опциональных параметров запроса; несовместимые — удаление или переименование существующих полей, изменение их типа/семантики, добавление нового обязательного параметра запроса. Чтобы остаться совместимым, нужно только добавлять, не ломая то, что уже используют клиенты.

**Разбор**
- **Как это работает:** клиенты, написанные по принципу "игнорировать неизвестные поля" (что является хорошей практикой десериализации), не заметят появления нового поля в ответе; но они точно заметят исчезновение поля, на которое опирались, или смену его типа (например, число стало строкой).
- **На практике:** перед изменением контракта стоит явно classif­ицировать изменение как совместимое/несовместимое, опираясь на контракт (OpenAPI-схему), а не "на глаз"; для потенциально несовместимых изменений — использовать стратегию расширения (добавить новое поле рядом со старым, период параллельной поддержки обоих, затем депрекация старого с предупреждением в документации/заголовке `Deprecation`).
- **Частые ошибки:** переименовывать поле "для ясности" без сохранения старого имени как алиаса хотя бы на переходный период, молча ломая клиентов, которые не следят за changelog; менять тип существующего поля (например, `"id": 123` на `"id": "123"`) без версионирования, рассчитывая, что это "мелочь", хотя строго типизированные клиенты (например, сгенерированные из OpenAPI) могут упасть при десериализации.

**Пример / кейс**
```json
// Было (v1, используется клиентами)
{"id": 42, "total": 150.0}

// Совместимое изменение: добавлено новое опциональное поле
{"id": 42, "total": 150.0, "currency": "USD"}

// Несовместимое изменение: поле удалено/переименовано без алиаса — ломает текущих клиентов
{"id": 42, "amount": 150.0}
```
Проверка: contract-тест (например, на основе зафиксированной OpenAPI-схемы или snapshot предыдущего ответа) проверяет, что все поля из предыдущей версии контракта присутствуют в новом ответе с тем же типом — такой тест должен падать именно на несовместимом варианте и проходить на совместимом.

### 219. [Q-03-04-0219] Как спроектировать rate limiting для публичного API и как сообщить клиенту об ограничениях через HTTP-заголовки?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Rate limiting ограничивает число запросов от одного клиента (по API-ключу, пользователю или IP) за промежуток времени; при превышении лимита сервер возвращает 429 Too Many Requests, а информацию о лимите и остатке передаёт через заголовки типа `X-RateLimit-Limit`, `X-RateLimit-Remaining` и `Retry-After`.

**Разбор**
- **Как это работает:** распространённые алгоритмы — fixed window (счётчик на фиксированный интервал, прост, но даёт всплески на границе окна), sliding window и token bucket (более равномерное распределение, сложнее реализовать). Состояние счётчиков обычно хранят в быстром внешнем хранилище (Redis) с TTL, а не в памяти процесса, иначе лимит будет считаться отдельно на каждом инстансе приложения при горизонтальном масштабировании.
- **На практике:** лимиты стоит делить по уровню доступа клиента (бесплатный/платный тариф) и по типу операции (чтение обычно лимитируют мягче, чем дорогие операции записи); заголовок `Retry-After` в ответе 429 подсказывает клиенту, через сколько секунд повторить попытку, что снижает бессмысленные повторные запросы.
- **Частые ошибки:** хранить счётчики лимита в памяти одного процесса при наличии нескольких инстансов сервиса за балансировщиком, что фактически умножает реальный лимит на количество инстансов; не возвращать 429 с понятными заголовками, из-за чего клиенты просто получают "500-подобное" поведение и не могут адаптировать частоту запросов программно.

**Пример / кейс**
```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()

@app.middleware("http")
async def rate_limit_middleware(request: Request, call_next):
    api_key = request.headers.get("X-Api-Key", "anonymous")
    allowed, remaining, retry_after = rate_limiter.check(api_key)  # например, через Redis token bucket
    if not allowed:
        return JSONResponse(
            status_code=429,
            content={"detail": "Too many requests"},
            headers={"Retry-After": str(retry_after), "X-RateLimit-Remaining": "0"},
        )
    response = await call_next(request)
    response.headers["X-RateLimit-Remaining"] = str(remaining)
    return response
```
Проверка: тест отправляет запросы сверх лимита в быстром цикле и проверяет, что начиная с определённого запроса приходит 429 с заголовком `Retry-After`; после ожидания указанного времени повторный запрос снова проходит.

### 220. [Q-03-04-0220] Как обработать ситуацию, когда backend должен агрегировать данные из нескольких внешних сервисов, и один из них временно недоступен?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Нужно заранее решить и явно документировать стратегию для частичного отказа: либо вернуть частичный результат с явным указанием, какие данные недоступны, либо вернуть ошибку целиком — выбор зависит от того, критичны ли данные недоступного сервиса для корректности ответа.

**Разбор**
- **Как это работает:** при параллельном вызове нескольких внешних сервисов (например, через `asyncio.gather` с `return_exceptions=True`) можно получить смесь успешных результатов и исключений; дальше нужно решить для каждого источника данных, является ли он обязательным (и его отказ должен провалить весь запрос) или опциональным (и его отказ допускает деградацию функциональности).
- **На практике:** для некритичных дополнений (например, "рекомендованные товары" на странице заказа) разумно вернуть основной ответ без этого блока и залогировать/замониторить отказ; для критичных данных (например, актуальная цена перед оплатой) лучше вернуть ошибку, чем показать неполную или потенциально устаревшую информацию. Ответ должен явно сигнализировать клиенту о частичности данных (например, полем `partial: true` или списком недоступных источников), а не маскировать проблему.
- **Частые ошибки:** возвращать частичный ответ без явного индикатора, что часть данных отсутствует из-за сбоя, из-за чего клиент/пользователь принимает неполные данные за полные; не задавать таймаут на каждый из параллельных вызовов, из-за чего медленный ответ одного сервиса задерживает весь агрегированный ответ вместо того, чтобы считаться отказом по таймауту.

**Пример / кейс**
```python
import asyncio

async def get_order_summary(order_id: int) -> dict:
    results = await asyncio.gather(
        fetch_order_core(order_id),       # критично: при отказе — ошибка всего запроса
        fetch_recommendations(order_id),  # некритично: при отказе — пропускаем блок
        return_exceptions=True,
    )
    core, recommendations = results
    if isinstance(core, Exception):
        raise core  # основные данные обязательны
    response = {"order": core, "partial": False}
    if isinstance(recommendations, Exception):
        response["recommendations"] = None
        response["partial"] = True
    else:
        response["recommendations"] = recommendations
    return response
```
Проверка: тест с замоканным падением сервиса рекомендаций подтверждает, что эндпоинт всё равно возвращает 200 с `"partial": true` и `"recommendations": null`; тест с падением сервиса ядра заказа подтверждает, что эндпоинт возвращает ошибку, а не частичные данные о заказе.

### 221. [Q-03-04-0221] Как спроектировать валидацию входных данных API с помощью Pydantic и какую структуру ошибок возвращать клиенту при нескольких невалидных полях?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Pydantic описывает схему входных данных декларативно (типы, ограничения, кастомные валидаторы) и собирает все ошибки валидации за один проход; клиенту стоит вернуть единый ответ со списком всех невалидных полей и причин, а не только первую найденную ошибку.

**Разбор**
- **Как это работает:** Pydantic проверяет каждое поле по отдельности и аккумулирует список ошибок (`ValidationError.errors()`), а не останавливается на первой — это позволяет клиенту исправить все проблемы за одну итерацию, а не отправлять запрос заново после каждой отдельной ошибки.
- **На практике:** кастомные бизнес-правила (например, "дата окончания должна быть позже даты начала") реализуются через `model_validator`/`field_validator`, а не проверяются вручную после десериализации — это сохраняет единый формат ошибок для всех видов невалидности. Важно решить, насколько подробным должно быть сообщение об ошибке для внешнего API (не раскрывать внутренние детали реализации) против внутреннего API (можно быть более техническим).
- **Частые ошибки:** проверять только первое невалидное поле и прерывать проверку остальных, вынуждая клиента отправлять запрос несколько раз для нахождения всех проблем; возвращать текст ошибки Pydantic "как есть" без преобразования в клиентский формат, из-за чего структура ответа об ошибке становится нестабильной между версиями библиотеки.

**Пример / кейс**
```python
from pydantic import BaseModel, field_validator, model_validator
from datetime import date

class CreateBooking(BaseModel):
    start_date: date
    end_date: date
    guests: int

    @field_validator("guests")
    @classmethod
    def guests_positive(cls, v):
        if v < 1:
            raise ValueError("guests must be at least 1")
        return v

    @model_validator(mode="after")
    def check_dates(self):
        if self.end_date <= self.start_date:
            raise ValueError("end_date must be after start_date")
        return self
```
Проверка: передать `{"start_date": "2024-05-10", "end_date": "2024-05-01", "guests": 0}` — `ValidationError.errors()` должен содержать сразу две ошибки (по `guests` и по датам), что проверяется тестом на длину списка ошибок, а не только на факт исключения.

### 222. [Q-03-04-0222] Как реализовать приёмник webhook с проверкой подписи (HMAC), чтобы защититься от поддельных запросов?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Отправитель подписывает тело запроса общим секретом через HMAC и передаёт подпись в заголовке; приёмник независимо вычисляет HMAC от полученного тела с тем же секретом и сравнивает подписи константным по времени способом, отклоняя запрос при несовпадении.

**Разбор**
- **Как это работает:** HMAC (например, HMAC-SHA256) строится так, что вычислить корректную подпись без знания секрета вычислительно нецелесообразно; сравнение подписей нужно делать функцией, устойчивой к атакам по времени ответа (`hmac.compare_digest` в Python), а не обычным `==`, который может завершаться раньше при первом несовпадающем байте.
- **На практике:** подпись обычно считается от сырого байтового тела запроса "как получено", а не от повторно сериализованного JSON — если фреймворк уже распарсил тело в объект и вы заново сериализуете его перед проверкой подписи, различия в форматировании (порядок ключей, пробелы) сломают проверку. Поэтому подпись нужно проверять до или независимо от парсинга JSON, на основе точных байт тела.
- **Частые ошибки:** сравнивать подписи через обычный оператор сравнения строк вместо `hmac.compare_digest`, что потенциально уязвимо к timing-атакам; вычислять подпись от пересериализованного объекта вместо исходных байт тела, из-за чего легитимные запросы иногда ложно отклоняются при отличиях в форматировании; хранить секрет в коде или логировать его при отладке.

**Пример / кейс**
```python
import hmac
import hashlib
from fastapi import FastAPI, Request, HTTPException

app = FastAPI()
WEBHOOK_SECRET = b"shared-secret-for-example"  # учебный пример, не реальный секрет

@app.post("/webhooks/partner")
async def receive_webhook(request: Request):
    raw_body = await request.body()
    signature = request.headers.get("X-Signature", "")
    expected = hmac.new(WEBHOOK_SECRET, raw_body, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, signature):
        raise HTTPException(status_code=401, detail="Invalid signature")
    payload = await request.json()
    process_webhook_event(payload)
    return {"status": "ok"}
```
Проверка: тест с корректно подписанным телом возвращает 200; тест с изменённым телом, но старой подписью (или произвольной строкой вместо подписи) возвращает 401 — симулируя попытку подделки запроса.

### 223. [Q-03-04-0223] Как применить HTTP-кэширование (ETag, Cache-Control, Last-Modified) к эндпоинту чтения ресурса и какую проблему это решает?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
`Cache-Control` задаёт политику кэширования (сколько времени ответ можно считать свежим), `ETag`/`Last-Modified` позволяют клиенту делать условный запрос и получать 304 Not Modified вместо полного тела, если ресурс не изменился, — это снижает нагрузку на сервер и сеть при повторных запросах к не изменившимся данным.

**Разбор**
- **Как это работает:** сервер при первом ответе отдаёт `ETag` (хэш или версию содержимого) или `Last-Modified` (время последнего изменения); при следующем запросе клиент передаёт `If-None-Match`/`If-Modified-Since`, и сервер, если данные не изменились, отвечает 304 с пустым телом, экономя трафик на передаче неизменного содержимого.
- **На практике:** кэширование подходит для GET-эндпоинтов с относительно редко меняющимися данными (каталог товаров, настройки) и требует, чтобы ETag/Last-Modified надёжно отражали фактическое изменение данных — например, ETag можно построить как хэш от содержимого записи или использовать поле `updated_at` из БД. Для часто меняющихся или персонализированных данных (баланс счёта в реальном времени) агрессивное кэширование может привести к показу устаревших данных — нужно явно выбирать `Cache-Control: no-store`/`private` или короткий `max-age`.
- **Частые ошибки:** выставлять ETag, не завязанный на реальное содержимое (например, случайную строку при каждом ответе), из-за чего условные запросы никогда не совпадают и выгода от кэширования теряется; кэшировать ответы, содержащие данные конкретного авторизованного пользователя, с публичным `Cache-Control: public`, что может привести к утечке данных одного пользователя другому через общий (shared) кэш/CDN.

**Пример / кейс**
```python
import hashlib
from fastapi import FastAPI, Request, Response

app = FastAPI()

@app.get("/catalog/{item_id}")
def get_item(item_id: int, request: Request, response: Response):
    item = fetch_item(item_id)
    etag = hashlib.sha256(str(item).encode()).hexdigest()
    if request.headers.get("if-none-match") == etag:
        return Response(status_code=304)
    response.headers["ETag"] = etag
    response.headers["Cache-Control"] = "private, max-age=60"
    return item
```
Проверка: первый запрос возвращает 200 с заголовком `ETag`; повторный запрос с `If-None-Match`, равным полученному ETag, возвращает 304 с пустым телом; после изменения `item` в хранилище повторный запрос с тем же (старым) ETag возвращает 200 с новым содержимым и новым ETag.

### 224. [Q-03-04-0224] Как спроектировать API-эндпоинт для запуска долгой асинхронной операции (например, генерация отчёта) так, чтобы клиент мог узнать её результат?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Эндпоинт запуска операции должен немедленно отвечать 202 Accepted с идентификатором задачи и ссылкой на статус, а не ждать завершения в рамках HTTP-запроса; клиент далее опрашивает отдельный эндпоинт статуса (или получает webhook по завершении).

**Разбор**
- **Как это работает:** 202 означает "запрос принят к обработке, но результат пока не готов" — в отличие от синхронных операций, где финальный статус известен сразу. Обработка переносится в фоновую задачу (воркер, очередь задач, например Celery/RQ/встроенный `BackgroundTasks`), а API-слой лишь регистрирует задачу и возвращает идентификатор.
- **На практике:** эндпоинт статуса должен возвращать состояние (`pending`/`running`/`done`/`failed`) и, при завершении, либо сам результат, либо ссылку на него (например, URL для скачивания отчёта); если ожидаемое время выполнения велико и известно заранее, можно дополнительно поддержать webhook-уведомление вместо постоянного polling клиентом. Выбор между частым коротким polling и webhook зависит от того, насколько клиент терпим к задержке узнавания результата и насколько он способен принимать входящие запросы.
- **Частые ошибки:** держать HTTP-соединение открытым на время всей долгой операции (синхронный эндпоинт с длинным таймаутом), что хрупко при сбоях сети и не масштабируется при множестве одновременных долгих операций; не предусматривать способ узнать, что задача зависла или провалилась — клиент должен получать явный статус `failed` с причиной, а не вечно видеть `pending`.

**Пример / кейс**
```python
from fastapi import FastAPI, BackgroundTasks
import uuid

app = FastAPI()
tasks = {}

def generate_report(task_id: str, params: dict):
    tasks[task_id]["status"] = "running"
    try:
        result = build_report(params)  # потенциально долгая операция
        tasks[task_id] = {"status": "done", "result_url": result}
    except Exception as exc:
        tasks[task_id] = {"status": "failed", "error": str(exc)}

@app.post("/reports", status_code=202)
def start_report(params: dict, background_tasks: BackgroundTasks):
    task_id = str(uuid.uuid4())
    tasks[task_id] = {"status": "pending"}
    background_tasks.add_task(generate_report, task_id, params)
    return {"task_id": task_id, "status_url": f"/reports/{task_id}"}

@app.get("/reports/{task_id}")
def get_report_status(task_id: str):
    return tasks.get(task_id, {"status": "not_found"})
```
Проверка: тест вызывает `POST /reports` и получает 202 с `task_id`; немедленный `GET /reports/{task_id}` возвращает `pending`/`running`; после ожидания завершения фоновой задачи повторный `GET` возвращает `done` с результатом.

### 225. [Q-03-04-0225] Как протестировать код, который вызывает внешний API, без реальных обращений к сети во время unit-тестов?

Нужно замокать HTTP-слой (через `unittest.mock`, библиотеки `responses`/`respx`/`requests-mock` или тестовый HTTP-сервер), чтобы тест проверял логику обработки ответа и ошибок, не выполняя реальных сетевых запросов, и отдельно — через contract-тесты или интеграционные тесты против тестового окружения внешнего сервиса — проверять, что реальный контракт не разошёлся с ожиданиями.

### 226. [Q-03-04-0226] Клиент жалуется, что при повторных попытках (retry) из-за таймаута операция создания заказа выполнилась дважды. Как диагностировать и предотвратить дублирование?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Диагностика: нужно проверить логи/трейсы на наличие двух запросов с близкими временными метками и одинаковыми (или очень похожими) данными от одного клиента; предотвращение — требовать от клиента ключ идемпотентности для таких операций, либо выводить детерминированный ключ дедупликации из бизнес-данных запроса (если клиент не может передать явный ключ).

**Разбор**
- **Как это работает:** таймаут на стороне клиента не означает, что сервер не обработал запрос — ответ может быть потерян в сети уже после того, как операция выполнилась. Поэтому клиент, не получивший ответ, не может различить "запрос не дошёл" и "ответ не дошёл", и при retry без идемпотентности рискует продублировать операцию.
- **На практике:** если изменить протокол клиента (добавить ключ идемпотентности) быстро невозможно, можно на короткое время дедуплицировать по комбинации полей запроса (например, `user_id + cart_hash` в пределах нескольких минут) — это менее надёжно, чем явный ключ, но может быть временным решением. Долгосрочно правильнее явно согласовать с клиентами использование `Idempotency-Key` для всех операций создания с потенциальными повторами.
- **Частые ошибки:** считать, что увеличение таймаута "решает" проблему — оно лишь снижает частоту повторов, не устраняя саму возможность дублирования при реальном сетевом сбое; реализовывать дедупликацию только в памяти процесса без персистентного хранилища, из-за чего повторный запрос, обработанный другим инстансом сервиса (за балансировщиком), не распознаётся как дубликат.

**Пример / кейс**
```python
from fastapi import FastAPI, Header, HTTPException

app = FastAPI()

@app.post("/orders")
def create_order(payload: dict, idempotency_key: str | None = Header(default=None)):
    if idempotency_key is None:
        raise HTTPException(status_code=400, detail="Idempotency-Key header is required")
    existing = idempotency_store.get_if_exists(idempotency_key)
    if existing is not None:
        return existing
    order = orders_service.create(payload)
    idempotency_store.save(idempotency_key, order)
    return order
```
Проверка: воспроизвести сценарий — отправить запрос, искусственно "потерять" ответ (например, оборвать соединение на стороне тестового клиента после отправки), затем повторить запрос с тем же `Idempotency-Key`; в БД должен остаться ровно один заказ, а не два.

### 227. [Q-03-04-0227] Как выбрать схему аутентификации для backend-to-backend интеграции: статический API-ключ, OAuth2 client credentials или подписанный JWT?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Статический API-ключ прост, но сложно ротируется и не несёт встроенного срока жизни; OAuth2 client credentials даёт короткоживущие токены с возможностью централизованной ротации и отзыва через сервер авторизации; подписанный JWT, выпущенный доверенной стороной, подходит, когда нужна самодостаточная проверка без обращения к центральному серверу при каждом запросе — выбор зависит от требований к ротации, отзыву доступа и инфраструктурной сложности, которую команда готова поддерживать.

**Разбор**
- **Как это работает:** статический ключ сравнивается напрямую на сервере (обычно хранится как хэш); OAuth2 client credentials flow требует отдельного запроса за access-токеном к серверу авторизации перед обращением к ресурсному серверу, токен имеет TTL и подлежит обновлению; JWT содержит подписанные claims (кем выпущен, для кого, срок действия), которые ресурсный сервер может проверить локально по публичному ключу без похода к серверу авторизации на каждый запрос.
- **На практике:** для простых внутренних интеграций в контролируемой сети статический ключ с механизмом ротации (поддержка двух активных ключей на время перехода) может быть достаточным и самым простым в поддержке решением. Для интеграций с множеством внешних партнёров и требованием оперативного отзыва доступа OAuth2 даёт централизованный контроль. JWT предпочтителен при высокой частоте запросов и желании избежать дополнительного сетевого вызова на каждую проверку, но отзыв конкретного токена до истечения его срока действия сложнее (требует черного списка или короткого TTL).
- **Частые ошибки:** использовать статический ключ без возможности ротации без даунтайма (нет поддержки одновременно двух валидных ключей на переходный период); выдавать JWT с неограниченно долгим сроком действия, теряя смысл его срочности и усложняя отзыв компрометированного токена; не проверять `aud`/`iss`/`exp` claims JWT на стороне получателя, принимая токен, выпущенный для другого сервиса или уже просроченный.

**Пример / кейс**
```python
import jwt
from datetime import datetime, timedelta, timezone

def issue_service_token(service_name: str, private_key: str) -> str:
    now = datetime.now(timezone.utc)
    payload = {
        "iss": "internal-auth",
        "aud": "orders-service",
        "sub": service_name,
        "iat": now,
        "exp": now + timedelta(minutes=10),  # короткий TTL снижает риск долгоживущей компрометации
    }
    return jwt.encode(payload, private_key, algorithm="RS256")

def verify_service_token(token: str, public_key: str) -> dict:
    return jwt.decode(token, public_key, algorithms=["RS256"], audience="orders-service")
```
Проверка: тест с токеном, у которого `exp` в прошлом, должен вызывать исключение `ExpiredSignatureError` при проверке; тест с токеном, выпущенным для другого `aud`, должен быть отклонён — оба сценария проверяют, что проверка claims реально работает, а не только подпись.

### 228. [Q-03-04-0228] Как спроектировать эндпоинт загрузки файлов (multipart/form-data) в REST API и на что обратить внимание при больших файлах?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Файлы передаются через `multipart/form-data`, где каждая часть тела запроса имеет свои заголовки (включая `Content-Disposition` с именем файла); для больших файлов нужно читать и сохранять данные потоково, не загружая весь файл в память целиком, и ограничивать максимальный размер запроса явно на уровне сервера/прокси.

**Разбор**
- **Как это работает:** `multipart/form-data` разбивает тело на части с разделителем (boundary), каждая часть может быть обычным полем формы или файлом с указанным именем и типом содержимого; сервер должен распарсить это построчно/по частям, а не как единый JSON.
- **На практике:** веб-фреймворки (FastAPI через Starlette) поддерживают потоковую обработку загружаемых файлов (`UploadFile`), что позволяет сразу писать содержимое во временный файл или напрямую в объектное хранилище (S3-совместимое), не держа весь файл в оперативной памяти. Лимит на размер файла стоит задавать и на уровне приложения, и на уровне обратного прокси/балансировщика, чтобы отклонять слишком большие запросы до того, как они нагрузят процесс приложения.
- **Частые ошибки:** читать файл целиком в память (`await file.read()` для файлов произвольного размера) без ограничения, что при больших файлах или параллельных загрузках может привести к исчерпанию памяти процесса; не проверять реальный тип содержимого файла (доверять только расширению или заявленному Content-Type от клиента), что создаёт риск загрузки вредоносного содержимого под видом безопасного типа.

**Пример / кейс**
```python
from fastapi import FastAPI, UploadFile, File, HTTPException

app = FastAPI()
MAX_SIZE = 10 * 1024 * 1024  # 10 МБ

@app.post("/uploads")
async def upload_file(file: UploadFile = File(...)):
    total = 0
    with open(f"/tmp/{file.filename}", "wb") as out:
        while chunk := await file.read(1024 * 1024):  # читаем потоково по 1 МБ
            total += len(chunk)
            if total > MAX_SIZE:
                raise HTTPException(status_code=413, detail="File too large")
            out.write(chunk)
    return {"filename": file.filename, "size": total}
```
Проверка: тест загружает файл чуть больше `MAX_SIZE` и ожидает 413, при этом мониторинг памяти процесса во время теста подтверждает, что потребление не растёт пропорционально размеру файла (потоковая обработка, а не загрузка целиком в память).

### 229. [Q-03-04-0229] Как обеспечить согласованность между синхронным REST-ответом на создание ресурса и асинхронной обработкой этого ресурса через очередь сообщений?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
Ресурс нужно сначала надёжно сохранить в основном хранилище (БД) и только после этого (в идеале — в той же транзакции или через надёжный механизм вроде transactional outbox) публиковать сообщение в очередь; клиенту возвращается ответ на основе состояния в БД, а не на основе факта отправки сообщения.

**Разбор**
- **Как это работает:** если сначала отправить сообщение в очередь и только потом попытаться сохранить запись в БД, при сбое сохранения в очереди уже будет "висеть" сообщение о ресурсе, которого на самом деле нет; если сделать в обратном порядке без гарантий — можно сохранить запись, но не успеть отправить сообщение из-за сбоя (например, падения процесса между двумя операциями), и дальнейшая асинхронная обработка не запустится.
- **На практике:** паттерн transactional outbox решает эту проблему: запись о ресурсе и запись о "сообщении для отправки" сохраняются в одной транзакции БД, а отдельный процесс (relay) читает несохранённые исходящие сообщения из таблицы outbox и публикует их в очередь, помечая как отправленные — тем самым публикация становится согласованной с сохранением данных на уровне "по крайней мере один раз". Потребитель сообщения должен быть готов к повторной доставке (идемпотентная обработка), так как outbox-релей обычно не гарантирует ровно один раз.
- **Частые ошибки:** публиковать сообщение в очередь до подтверждения коммита транзакции в БД, из-за чего потребитель может начать обработку ресурса, которого в итоге не окажется при откате транзакции; считать, что "просто вызвать send() после commit()" достаточно надёжно — между этими двумя операциями возможен сбой процесса, и тогда сообщение не будет отправлено вовсе без outbox-механизма.

**Пример / кейс**
```python
def create_order_with_outbox(session, payload: dict):
    with session.begin():
        order = Order(**payload)
        session.add(order)
        session.flush()  # order.id уже доступен внутри транзакции
        outbox_event = OutboxEvent(
            event_type="order_created",
            payload={"order_id": order.id},
        )
        session.add(outbox_event)
    # relay-процесс отдельно читает неотправленные OutboxEvent и публикует их в очередь,
    # помечая отправленными после подтверждения брокером
    return order
```
Проверка: интеграционный тест имитирует сбой между сохранением заказа и публикацией в очередь (например, останавливает relay-процесс сразу после commit) и проверяет, что запись в таблице outbox остаётся неотправленной и будет доставлена при следующем запуске relay, а не теряется безвозвратно.

### 230. [Q-03-04-0230] Что такое HATEOAS и стоит ли реализовывать его в типичном внутреннем REST API?

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Middle

**Короткий ответ**<br>
HATEOAS (Hypermedia as the Engine of Application State) — принцип, при котором ответ API включает ссылки на доступные дальнейшие действия/ресурсы, позволяя клиенту "навигировать" по API динамически, а не хардкодить все URL заранее; для большинства внутренних и даже публичных API практическая польза ограничена по сравнению с ростом сложности, и решение внедрять его зависит от того, насколько клиентам нужна такая динамическая навигация.

**Разбор**
- **Как это работает:** вместо того чтобы клиент заранее знал, что после получения заказа со статусом "ожидает оплаты" нужно обратиться к `/orders/{id}/pay`, сервер включает в ответ ссылку с этим URL (и, возможно, только если действие действительно доступно в текущем состоянии) — клиент просто следует ссылкам, а не хардкодит бизнес-логику переходов.
- **На практике:** HATEOAS добавляет реальную ценность, когда переходы между состояниями ресурса действительно сложны и часто меняются, а разные клиенты (в том числе написанные не вами) должны адаптироваться к этим изменениям без пересборки — например, в API с богатым workflow заказов. Для большинства внутренних API, где клиент и сервер разрабатываются и деплоятся одной командой с полным контролем над обеими сторонами, выгода от динамической навигации не оправдывает дополнительную сложность реализации и тестирования — такие решения принимаются исходя из реального числа независимых клиентов и частоты изменения workflow, а не "потому что это настоящий REST".
- **Частые ошибки:** внедрять HATEOAS "для соответствия стандарту REST" без реальных клиентов, которые бы использовали эти ссылки динамически, что добавляет сложность без практической выгоды; либо наоборот — полностью игнорировать идею и хардкодить в клиенте бизнес-правила о допустимых переходах состояний, которые было бы правильнее получать от сервера, если они часто меняются.

**Пример / кейс**
```json
{
  "id": 42,
  "status": "awaiting_payment",
  "links": {
    "self": "/orders/42",
    "pay": "/orders/42/pay",
    "cancel": "/orders/42/cancel"
  }
}
```
```json
{
  "id": 42,
  "status": "paid",
  "links": {
    "self": "/orders/42",
    "refund": "/orders/42/refund"
  }
}
```
Проверка: тест проверяет, что набор `links` в ответе меняется в зависимости от `status` заказа (например, после оплаты ссылка `pay` исчезает, а появляется `refund`) — это демонстрирует, что клиент может ориентироваться на `links`, а не хардкодить логику допустимых переходов самостоятельно.

### 231. [Q-03-04-0231] Как спроектировать политику версионирования публичного API, который используют десятки внешних интеграторов с разным темпом обновления своих клиентов? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Senior

**Короткий ответ**<br>
Нужна явная политика: сколько версий поддерживается параллельно, какой минимальный срок уведомления перед выключением старой версии, и строгое разделение изменений на совместимые (вносятся без версии) и несовместимые (требуют новой major-версии) — конкретные числа и механизм выбираются исходя из состава клиентов, их готовности обновляться и бизнес-рисков простоя интеграций.

**Разбор**
- **Как это работает:** внешние интеграторы обновляют свои клиенты с разной скоростью и часто не read ваш changelog внимательно; политика версионирования должна балансировать между скоростью эволюции продукта (частые новые версии = меньше технического долга в поддержке старых контрактов) и стабильностью для партнёров (редкие версии = проще интегрироваться и поддерживать).
- **На практике:** типичные элементы политики — фиксированный период поддержки предыдущей major-версии (например, 6–12 месяцев после выпуска новой, в зависимости от контрактных обязательств перед партнёрами), заголовок `Deprecation`/`Sunset` в ответах устаревающей версии, мониторинг реального трафика по версиям перед отключением старой (нельзя выключать версию, которую активно используют, несмотря на формально прошедший срок уведомления), и явный канал коммуникации с интеграторами (email, панель разработчика, changelog).
- **Частые ошибки:** выключать старую версию строго по календарной дате без проверки реального трафика, ломая интеграции партнёров, которые не успели обновиться; вносить несовместимые изменения "по мелочи" в рамках той же версии, считая их незначительными, что подрывает доверие к гарантии совместимости внутри версии.
- **Компромисс:** частое выпускание новых major-версий снижает накопление технического долга от поддержки старых контрактов, но увеличивает нагрузку на партнёров и команду поддержки (нужно одновременно поддерживать больше версий дольше, пока идёт миграция); редкое версионирование снижает нагрузку на партнёров, но рискует накоплением крупных, сложных для миграции изменений за один раз. Выбор конкретного срока поддержки и порога "что считается breaking change" зависит от контрактных обязательств (SLA) перед ключевыми партнёрами, размера команды поддержки и терпимости бизнеса к потере интеграций при принудительном отключении старой версии.

**Пример / кейс**
```http
GET /v1/orders/42 HTTP/1.1
Host: api.example.com

HTTP/1.1 200 OK
Deprecation: true
Sunset: Wed, 01 Jan 2025 00:00:00 GMT
Link: <https://api.example.com/v2/orders/42>; rel="successor-version"
```
Проверка: дашборд мониторинга показывает долю трафика по версиям API во времени; решение об отключении `/v1/` принимается на основе наблюдаемого снижения трафика ниже порога (например, менее 1% за последние 30 дней) в сочетании с истечением заявленного срока поддержки, а не только по дате из `Sunset`.

### 232. [Q-03-04-0232] Для нового внутреннего сервиса с высокой нагрузкой команда выбирает между REST, GraphQL и gRPC. Как подойти к этому выбору? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Senior

**Короткий ответ**<br>
Выбор зависит от состава клиентов (браузер/мобильный клиент против внутреннего сервиса), требований к производительности и строгой типизации контракта, а не от того, какой подход считается "современнее"; REST проще для внешних и разнородных клиентов, GraphQL — когда клиентам нужна гибкая форма ответа, gRPC — для внутренних высоконагруженных сервис-сервис взаимодействий с строгим контрактом и минимальными накладными расходами.

**Разбор**
- **Как это работает:** REST поверх HTTP/1.1 или HTTP/2 с JSON — универсален, легко отлаживается curl'ом/браузером, широко поддержан инструментами; GraphQL даёт клиенту контроль над формой ответа через единый эндпоинт, но требует продуманного батчинга резолверов и защиты от дорогих запросов; gRPC поверх HTTP/2 с Protobuf даёт компактную бинарную сериализацию, строгую типизацию по `.proto`-схеме, встроенную поддержку стриминга, но хуже отлаживается вручную (нужны специальные инструменты вместо curl) и менее дружелюбен к браузерным клиентам без дополнительного прокси (grpc-web).
- **На практике:** для внутреннего высоконагруженного сервис-сервис взаимодействия gRPC часто даёт заметный выигрыш в задержке и объёме трафика за счёт бинарной сериализации и мультиплексирования HTTP/2, но накладывает инфраструктурные требования (генерация кода из `.proto`, поддержка версии схемы, инструменты наблюдаемости, адаптированные под gRPC). Если команда без опыта с gRPC внедряет его "потому что он быстрее", риски операционной сложности и кривой обучения могут превысить выгоду, особенно если реальная нагрузка далека от узкого места производительности.
- **Частые ошибки:** выбирать gRPC только из соображений "производительности" без фактического профилирования, где реально узкое место (часто бутылочное горлышко — не сериализация, а БД или внешние зависимости); внедрять GraphQL для внутреннего сервис-сервис API, где нужен фиксированный простой контракт, а не гибкая форма ответа для разнородных UI-клиентов — это добавляет сложность без соответствующей выгоды.
- **Компромисс:** gRPC даёт производительность и строгую типизацию, но стоит дороже в операционной сложности, обучении команды и интеграции с браузерными/внешними клиентами; REST даёт простоту, универсальность и низкий порог входа, но менее эффективен по трафику/CPU на сериализацию при очень высокой нагрузке; GraphQL решает проблему гибкости формы ответа для разнородных клиентов, но добавляет сложность на сервере (батчинг, защита от дорогих запросов) и не имеет смысла там, где форма ответа фиксирована. Критерии выбора: реальный профиль нагрузки и узкое место, состав клиентов (внутренние/внешние, браузер/сервис), готовность команды поддерживать выбранную технологию, и то, насколько критична задержка/трафик именно на уровне сериализации протокола, а не в другом месте системы.

**Пример / кейс**
```protobuf
// orders.proto — пример контракта gRPC для внутреннего сервиса
syntax = "proto3";

service OrdersService {
  rpc GetOrder (GetOrderRequest) returns (Order);
}

message GetOrderRequest {
  int64 order_id = 1;
}

message Order {
  int64 id = 1;
  string status = 2;
  double total = 3;
}
```
Проверка: нагрузочное тестирование (например, с помощью `ghz` для gRPC и `locust`/`wrk` для REST-эквивалента того же сервиса) на одинаковой инфраструктуре сравнивает latency p99 и использование CPU/сети при равной нагрузке — решение принимается на основе фактических цифр для конкретной системы, а не общих утверждений о производительности протокола.

### 233. [Q-03-04-0233] Платёжный API должен гарантировать, что повторная доставка одного и того же запроса на оплату (из-за retry клиента или сетевого сбоя) не приведёт к двойному списанию средств. Как спроектировать такую гарантию на уровне API и обработки? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Senior

**Короткий ответ**<br>
Нужен обязательный клиентский ключ идемпотентности, атомарно привязанный к результату операции на уровне БД (уникальный индекс + транзакция), плюс идемпотентная обработка на стороне интеграции с платёжным провайдером (который сам может повторно доставить уведомление); "exactly-once" в строгом смысле недостижимо в распределённой системе, поэтому цель — эффективно-однократное выполнение (effectively-once) через идемпотентность на каждом шаге цепочки.

**Разбор**
- **Как это работает:** клиент генерирует `Idempotency-Key` перед первой попыткой; сервер должен атомарно "зарезервировать" ключ (например, `INSERT ... ON CONFLICT DO NOTHING` с уникальным индексом по ключу) до начала фактического списания, чтобы параллельные повторные запросы с тем же ключом не прошли через бизнес-логику параллельно. Отдельно — вызов самого платёжного провайдера также должен быть идемпотентным (большинство провайдеров поддерживают свой idempotency key), потому что retry может произойти и на этом уровне, независимо от вашего API.
- **На практике:** нужно явно продумать все точки, где может произойти дублирование: клиент → ваш API, ваш API → платёжный провайдер, провайдер → ваш webhook-приёмник уведомлений о результате. Каждая из этих точек нуждается в своей защите идемпотентности; пропуск хотя бы одной (например, обработка webhook без проверки, что событие уже обработано) оставляет лазейку для дублирования. Решение требует согласования с выбранным платёжным провайдером, так как конкретный механизм (их idempotency key, формат уведомлений) зависит от его API.
- **Частые ошибки:** защищать идемпотентность только на входе вашего API, но не на вызове платёжного провайдера, из-за чего retry именно этого внутреннего вызова (например, после таймаута у провайдера) создаёт два реальных платежа при одном входящем запросе клиента; обрабатывать webhook от провайдера без дедупликации по его `event_id`, из-за чего повторная доставка уведомления (которую провайдеры прямо документируют как возможную) приводит к повторному зачислению/обработке.
- **Компромисс:** строгая идемпотентность на каждом уровне (клиент-API, API-провайдер, webhook) даёт максимальную защиту от дублирования, но увеличивает сложность реализации, требует дополнительного хранилища состояния операций и aккуратной обработки гонок (что в свою очередь добавляет латентность из-за блокировок/транзакций). Более простая реализация только на уровне клиент-API экономит время разработки, но оставляет риск дублирования на уровне интеграции с провайдером и обработки webhook — критерий выбора глубины защиты зависит от финансовой критичности операции, объёма трафика и того, насколько платёжный провайдер сам гарантирует идемпотентность на своей стороне.

**Пример / кейс**
```python
def charge_payment(idempotency_key: str, amount: float, user_id: int):
    with db.begin():
        inserted = db.execute(
            """INSERT INTO payment_attempts (idempotency_key, status)
               VALUES (:key, 'processing')
               ON CONFLICT (idempotency_key) DO NOTHING
               RETURNING id""",
            {"key": idempotency_key},
        ).fetchone()
        if inserted is None:
            # ключ уже существует — возвращаем предыдущий результат, не выполняя списание повторно
            return get_existing_result(idempotency_key)

    provider_result = payment_provider.charge(
        amount=amount,
        user_id=user_id,
        idempotency_key=idempotency_key,  # идемпотентность и на уровне провайдера
    )
    save_result(idempotency_key, provider_result)
    return provider_result
```
Проверка: нагрузочный тест отправляет 10 параллельных запросов с одинаковым `idempotency_key` и проверяет, что у платёжного провайдера (в тестовом/sandbox-режиме) зафиксирован ровно один реальный платёж, а не до десяти; отдельный тест имитирует повторную доставку webhook с одним `event_id` и проверяет, что баланс пользователя изменился один раз.

### 234. [Q-03-04-0234] Нужно спроектировать систему рассылки webhook-уведомлений внешним подписчикам (десятки сторонних сервисов), устойчивую к их временной недоступности и дублирующим доставкам. Как подойти к архитектуре retry, очереди недоставленных сообщений (DLQ) и порядку доставки? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Senior

**Короткий ответ**<br>
Доставку нужно делать асинхронно через очередь с повторными попытками и экспоненциальным backoff, подписывать каждое событие уникальным `event_id` для дедупликации на стороне подписчика, перемещать сообщения, исчерпавшие попытки, в DLQ с возможностью ручного/автоматического переразбора, и явно документировать подписчикам, что строгий порядок доставки между разными событиями не гарантируется, если это не было отдельно спроектировано.

**Разбор**
- **Как это работает:** отправка webhook — это по сути ненадёжный HTTP-вызов к стороннему сервису, который может быть недоступен, медленным или отвечать ошибкой; каждая попытка доставки должна иметь таймаут, ограниченное число повторов с нарастающей задержкой, и фиксацию результата (успех/ошибка) для наблюдаемости. Подписчик должен получать подписанный payload (HMAC) с уникальным идентификатором события, чтобы мог идемпотентно обработать повторную доставку — гарантия "ровно один раз" на уровне HTTP между двумя независимыми системами недостижима, поэтому стандарт — "как минимум один раз" плюс идемпотентность на приёмнике.
- **На практике:** нужно решить, сохранять ли строгий порядок доставки событий одного подписчика (например, через последовательную обработку на партицию по ID получателя) или допускать параллельную доставку разных событий с возможным нарушением порядка ради меньшей задержки и большей throughput — для событий типа "статус заказа изменился" порядок может быть критичен, для "новый лог записан" — не обязательно. DLQ должен быть снабжён алертингом (чтобы команда знала о накоплении недоставленных сообщений) и инструментом ручного replay после восстановления подписчика.
- **Частые ошибки:** делать синхронную доставку webhook внутри обработки основного бизнес-события (без очереди), из-за чего недоступность одного подписчика замедляет или ломает основной поток обработки события; не предусматривать дедупликацию на стороне подписчика через `event_id`, полагаясь, что "обычно" повторов не бывает; игнорировать упорядочивание там, где оно критично для бизнес-логики подписчика (например, доставить "заказ отменён" раньше "заказ создан" из-за параллельной обработки).
- **Компромисс:** гарантия строгого порядка доставки (например, через партиционирование очереди по получателю и последовательную обработку) снижает throughput и усложняет масштабирование обработки по сравнению с полностью параллельной доставкой, но устраняет риски бизнес-ошибок из-за рассинхронизации порядка событий у подписчика; неограниченные повторные попытки снижают потерю сообщений, но могут надолго занимать ресурсы на недоступного подписчика и задерживать видимость проблемы, тогда как агрессивный DLQ с малым числом попыток быстрее освобождает ресурсы, но требует механизма ручного/автоматического переразбора и мониторинга накопления в DLQ. Конкретный выбор числа попыток, необходимости упорядочивания и SLA по задержке доставки зависит от бизнес-критичности события для конкретных подписчиков и договорённостей с ними.

**Пример / кейс**
```python
import time
import hmac
import hashlib
import requests

def deliver_webhook(subscriber_url: str, secret: bytes, event: dict, max_attempts: int = 5) -> bool:
    body = json.dumps(event).encode()
    signature = hmac.new(secret, body, hashlib.sha256).hexdigest()
    for attempt in range(1, max_attempts + 1):
        try:
            resp = requests.post(
                subscriber_url,
                data=body,
                headers={"Content-Type": "application/json", "X-Signature": signature, "X-Event-Id": event["event_id"]},
                timeout=5,
            )
            if resp.status_code < 300:
                return True
        except requests.exceptions.RequestException:
            pass
        time.sleep(min(2 ** attempt, 60))
    return False  # после max_attempts — сообщение уходит в DLQ для ручного/отложенного переразбора
```
Проверка: интеграционный тест с намеренно недоступным (моковым) эндпоинтом подписчика проверяет, что после `max_attempts` неудачных попыток событие попадает в DLQ, а не теряется бесследно и не повторяется бесконечно; отдельный тест подтверждает, что подписчик, получивший одно событие дважды (один и тот же `event_id`), может распознать дубликат по этому полю.

### 235. [Q-03-04-0235] Backend-сервис интегрируется с внешним API, который периодически отвечает медленно или падает целиком, и это начинает каскадно влиять на доступность вашего сервиса. Как спроектировать отказоустойчивость интеграции (timeout, circuit breaker, fallback, изоляция ресурсов)? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Senior

**Короткий ответ**<br>
Нужно сочетание нескольких механизмов: жёсткий timeout на каждый вызов, circuit breaker, быстро прекращающий попытки при устойчивом отказе, изоляция ресурсов (отдельный пул соединений/потоков на эту интеграцию, чтобы её деградация не исчерпывала общие ресурсы сервиса), и заранее определённое поведение fallback (деградированный ответ или честная ошибка) — конкретные параметры и выбор fallback зависят от критичности зависимости для основной функциональности сервиса.

**Разбор**
- **Как это работает:** без изоляции ресурсов (паттерн bulkhead) медленные вызовы к одному внешнему сервису могут занять все доступные потоки/соединения пула, из-за чего даже запросы, не связанные с этим внешним сервисом, начинают отказывать — это классический каскадный отказ. Circuit breaker, отслеживая долю/количество ошибок за окно времени, переходит в "открытое" состояние и быстро отказывает новым вызовам без реальной попытки, давая внешнему сервису время восстановиться и защищая собственные ресурсы от трат на заведомо обречённые вызовы.
- **На практике:** параметры (порог ошибок для открытия circuit breaker, время до перехода в half-open для пробного вызова, размер изолированного пула) должны подбираться на основе реального профиля трафика и наблюдаемого поведения зависимости под нагрузкой, а не копироваться "по умолчанию" из библиотеки — слишком чувствительный breaker будет открываться на кратковременные всплески задержки, слишком нечувствительный не защитит вовремя. Fallback-поведение нужно решать для каждой интеграции отдельно: для некритичной зависимости — вернуть кэшированные/дефолтные данные с явной пометкой деградации; для критичной (например, проверка остатка средств перед списанием) — вернуть честную ошибку, а не рискованное приближение.
- **Частые ошибки:** использовать общий пул соединений/поток-пул для всех внешних интеграций сервиса, из-за чего отказ одной зависимости исчерпывает ресурсы для всех остальных; настраивать circuit breaker только по количеству подряд идущих ошибок без учёта окна времени, из-за чего он слишком медленно реагирует при низкой частоте запросов или слишком резко — при единичных всплесках; не тестировать поведение системы при реальном отказе зависимости (chaos-тестирование/fault injection), полагаясь, что механизмы "должны сработать" без проверки.
- **Компромисс:** более агрессивная изоляция и более чувствительный circuit breaker снижают риск каскадного отказа, но увеличивают операционную сложность (больше настроек для мониторинга и подстройки, больше ложных срабатываний при кратковременных всплесках) и могут излишне часто показывать деградированный fallback пользователям даже при частичных, восстановимых сбоях; менее агрессивная защита проще в эксплуатации, но оставляет риск, что единичный медленный внешний сервис обрушит доступность всего backend. Выбор конкретных порогов и того, использовать ли fallback или честную ошибку, зависит от критичности зависимости, SLA перед собственными пользователями и готовности команды поддерживать более сложную конфигурацию отказоустойчивости.

**Пример / кейс**
```python
import time
from concurrent.futures import ThreadPoolExecutor

# Bulkhead: отдельный пул ресурсов на конкретную внешнюю интеграцию
partner_pool = ThreadPoolExecutor(max_workers=10)

class CircuitBreaker:
    def __init__(self, failure_threshold=5, reset_timeout=30):
        self.failure_count = 0
        self.failure_threshold = failure_threshold
        self.reset_timeout = reset_timeout
        self.opened_at = None

    def call(self, func, *args, **kwargs):
        if self.opened_at is not None:
            if time.time() - self.opened_at < self.reset_timeout:
                raise RuntimeError("circuit open: fast-failing without calling dependency")
            self.opened_at = None  # half-open: пробуем снова
        try:
            result = func(*args, **kwargs)
            self.failure_count = 0
            return result
        except Exception:
            self.failure_count += 1
            if self.failure_count >= self.failure_threshold:
                self.opened_at = time.time()
            raise
```
Проверка: fault-injection тест заставляет внешний сервис отвечать ошибкой/таймаутом много раз подряд и проверяет, что после `failure_threshold` ошибок breaker переходит в открытое состояние и дальнейшие вызовы быстро завершаются без реального сетевого вызова (замеряется по времени ответа и счётчику обращений к моку); отдельно нагрузочный тест подтверждает, что запросы к другим, независимым внешним сервисам не замедляются во время деградации этой конкретной зависимости (изоляция пула сработала).

Как спроектировать процесс контрактов между командами (schema-first через OpenAPI/Protobuf, contract-тесты), чтобы независимые релизы не ломали друг друга? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Senior

**Короткий ответ**<br>
Нужен единый источник истины для контракта (OpenAPI/Protobuf-схема), версионируемый в репозитории и проверяемый автоматически (линтинг на breaking changes, contract-тесты типа consumer-driven contracts), который команда-провайдер не может изменить несовместимым образом без согласования с командами-потребителями; конкретный уровень строгости процесса зависит от числа потребителей и частоты релизов.

**Разбор**
- **Как это работает:** schema-first подход означает, что изменения в API сначала описываются в схеме (и проходят ревью/автоматическую проверку на совместимость), и только после этого реализуются в коде — это даёт явную точку контроля перед тем, как несовместимое изменение попадёт в production. Contract-тесты (например, по модели consumer-driven contracts) позволяют потребителю зафиксировать ожидания от API провайдера в виде тестов, которые провайдер прогоняет в своём CI перед релизом, узнавая о поломке контракта до деплоя, а не после.
- **На практике:** автоматическая проверка схемы на breaking changes (например, сравнение текущей и предыдущей версии OpenAPI-спеки в CI) эффективна для явных нарушений (удалённое поле, изменённый тип), но не ловит все семантические несовместимости (например, изменение бизнес-смысла поля при сохранении типа) — для этого нужны дополнительные contract-тесты с реальными сценариями использования. Процесс нужно соразмерять с реальным масштабом: для двух команд с редкими релизами формальный consumer-driven contract framework может быть избыточен, для десятков команд с частыми независимыми деплоями — обязателен.
- **Частые ошибки:** вести схему API "неофициально" в виде устной договорённости или устаревающей вики-страницы вместо версионируемого артефакта, который реально проверяется в CI; разрешать провайдеру мержить изменения в контракт без явного шага оповещения/проверки совместимости для известных потребителей, полагаясь только на "ревью кода" без автоматизации.
- **Компромисс:** строгий процесс (consumer-driven contract-тесты для каждого потребителя, обязательный gate в CI провайдера) даёт сильную защиту от поломок между релизами, но требует инфраструктурных инвестиций (поддержка framework для контрактных тестов, договорённости о том, кто их пишет и поддерживает) и может замедлять релизы провайдера, если потребители медленно обновляют свои контрактные тесты; более лёгкий процесс (только линтинг схемы на явные breaking changes без полноценных contract-тестов) быстрее внедряется и не замедляет релизы так сильно, но не ловит все классы несовместимостей, особенно семантические. Критерий выбора — число и критичность потребителей, частота изменений контракта и готовность команд инвестировать в тестовую инфраструктуру.

**Пример / кейс**
```yaml
# Фрагмент OpenAPI-схемы, версионируемой в репозитории и проверяемой в CI на breaking changes
paths:
  /orders/{orderId}:
    get:
      operationId: getOrder
      responses:
        "200":
          content:
            application/json:
              schema:
                type: object
                required: [id, status, total]
                properties:
                  id: { type: integer }
                  status: { type: string }
                  total: { type: number }
```
Проверка: CI-шаг (например, на основе `oasdiff` или аналогичного инструмента сравнения OpenAPI-спек) сравнивает новую версию схемы с предыдущей и падает, если из `required` удалено поле или изменён тип существующего поля; дополнительно запускаются contract-тесты потребителя против реального провайдера в тестовом окружении перед релизом провайдера.

### 237. [Q-03-04-0237] Публичный API компании используется тысячами клиентов с разной интенсивностью запросов, и один крупный клиент своей нагрузкой периодически деградирует сервис для остальных. Как спроектировать многоуровневый rate limiting (per-user, per-IP, глобальный) в распределённой системе? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Senior

**Короткий ответ**<br>
Нужны лимиты на нескольких уровнях одновременно — per-user/per-API-key (справедливое распределение между клиентами), per-IP (защита от анонимных/нелегитимных источников) и глобальный лимит на уровне всего сервиса (защита инфраструктуры в целом) — с централизованным хранилищем счётчиков (например, Redis) для корректной работы при множестве инстансов сервиса; конкретные пороги и алгоритм (token bucket, sliding window) выбираются исходя из реальной емкости системы и бизнес-тарифов.

**Разбор**
- **Как это работает:** в распределённой системе за балансировщиком счётчики лимитов не могут храниться в памяти одного процесса — нужно общее атомарное хранилище, иначе реальный лимит клиента фактически умножается на число инстансов, через которые пройдут его запросы. Per-user лимит защищает от того, чтобы один клиент "съел" ресурсы, предназначенные для всех; глобальный лимит защищает от ситуации, когда суммарная легитимная нагрузка от множества клиентов (каждый в рамках своего лимита) всё равно превышает реальную ёмкость инфраструктуры.
- **На практике:** разные уровни лимитов должны быть согласованы между собой и с реальной capacity системы, определённой через нагрузочное тестирование, а не подобраны произвольно; крупным клиентам с легитимно высокой нагрузкой стоит предлагать отдельные более высокие лимиты по договорённости (tiered rate limiting) или выделенную инфраструктуру, а не одинаковый лимит для всех. При исчерпании лимита важно возвращать информативный 429 с `Retry-After`, чтобы клиенты могли адаптивно снижать частоту запросов, а не "стучаться" агрессивнее.
- **Частые ошибки:** внедрять только per-IP лимит, который легко обходится через множество IP (NAT, облачные провайдеры с большим пулом адресов) и несправедливо наказывает многих легитимных пользователей за одним IP (например, офис за одним NAT); не предусматривать глобальный "предохранитель" уровня инфраструктуры, полагаясь только на сумму индивидуальных лимитов, что не защищает от ситуации одновременного пика у многих клиентов сразу.
- **Компромисс:** более тонкая многоуровневая схема (per-user + per-IP + глобальный, с разными тарифами для разных клиентов) лучше защищает инфраструктуру и справедливее распределяет ресурсы, но требует заметно более сложной инфраструктуры (централизованное хранилище счётчиков с низкой задержкой, согласование порогов между уровнями, мониторинг срабатываний) и усложняет диагностику при отладке ("почему именно этот запрос получил 429"); простая единая схема (один лимит на всех) проще эксплуатировать, но не защищает от описанных в вопросе сценариев и может быть одновременно слишком строгой для мелких клиентов и слишком мягкой для агрессивных крупных. Критерий выбора — распределение клиентов по объёму трафика, коммерческая модель (есть ли смысл в платных тарифах с разными лимитами) и реальная наблюдаемая ёмкость инфраструктуры.

**Пример / кейс**
```python
# Схематичный пример многоуровневой проверки лимита с Redis (token bucket через INCR + EXPIRE)
def check_rate_limits(redis_client, user_id: str, ip: str) -> tuple[bool, str]:
    checks = [
        (f"rl:user:{user_id}", 1000, 60, "per-user limit exceeded"),
        (f"rl:ip:{ip}", 2000, 60, "per-ip limit exceeded"),
        ("rl:global", 500_000, 60, "global capacity limit exceeded"),
    ]
    for key, limit, window, message in checks:
        current = redis_client.incr(key)
        if current == 1:
            redis_client.expire(key, window)
        if current > limit:
            return False, message
    return True, ""
```
Проверка: нагрузочный тест с одним "агрессивным" клиентом, превышающим per-user лимит, подтверждает, что он получает 429, не влияя на латентность запросов других клиентов (замеряется p99 latency остальных клиентов во время теста); отдельный тест с равномерной нагрузкой от множества клиентов, суммарно превышающей глобальный лимит, подтверждает срабатывание именно глобального предохранителя.

### 238. [Q-03-04-0238] Команда выбирает между stateless JWT-аутентификацией и session-based подходом с хранением сессии на сервере для API с требованием возможности немедленного отзыва доступа (например, при компрометации аккаунта). Как подойти к этому выбору? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Senior

**Короткий ответ**<br>
Чисто stateless JWT (проверяемый только по подписи, без обращения к хранилищу) плохо совместим с требованием немедленного отзыва, так как токен остаётся валидным до истечения `exp`, независимо от действий на сервере; session-based подход или JWT с централизованной проверкой отзыва (blacklist/короткий TTL с refresh) решает эту проблему за счёт частичного отказа от stateless-преимуществ — выбор зависит от того, насколько критично немедленное отключение доступа против стоимости дополнительного состояния и задержки от централизованной проверки.

**Разбор**
- **Как это работает:** stateless JWT проверяется локально ресурсным сервером по подписи без сетевого вызова — это даёт низкую латентность и горизонтальную масштабируемость без общего хранилища сессий, но означает, что отозвать конкретный токен до истечения срока действия невозможно без дополнительного механизма (например, списка отозванных токенов, который сам по себе требует централизованного, проверяемого на каждый запрос хранилища — что сводит на нет чистую stateless-природу). Session-based подход хранит состояние на сервере (в Redis/БД) и проверяет его при каждом запросе, что даёт немедленный отзыв (удалить запись сессии), но требует сетевого вызова к общему хранилищу на каждый запрос и делает систему зависимой от доступности этого хранилища.
- **На практике:** распространённый компромисс — короткоживущий access-токен (JWT, проверяется локально, минуты) в сочетании с более долгоживущим refresh-токеном, отзыв которого проверяется централизованно; это ограничивает "окно уязвимости" после компрометации временем жизни access-токена, не требуя централизованной проверки на каждый обычный запрос. Выбор конкретного TTL access-токена — это прямой trade-off между задержкой реакции на компрометацию и частотой обращений к центральному хранилищу для обновления токена.
- **Частые ошибки:** выдавать JWT с длительным сроком действия (часы/дни) без механизма отзыва, что делает компрометацию токена опасной на весь этот срок независимо от действий администратора; реализовывать "отзыв" JWT через проверку централизованного blacklist на каждый запрос, но при этом рекламировать решение как "stateless", не признавая, что оно уже несёт основные издержки session-based подхода (сетевой вызов на каждый запрос).
- **Компромисс:** полностью stateless JWT даёт максимальную производительность и простоту масштабирования, но жертвует возможностью немедленного отзыва — приемлемо, если токены короткоживущие и риск от компрометации в течение этого короткого окна приемлем для бизнеса. Session-based (или JWT с централизованной проверкой отзыва) даёт контроль и немедленный отзыв, но добавляет сетевую зависимость от общего хранилища на каждый запрос, точку отказа и дополнительную инфраструктуру. Критерий выбора — чувствительность данных/операций, защищаемых API, требования регуляторов или контрактов безопасности к скорости отзыва доступа, и готовность системы нести издержки централизованной проверки состояния на каждый запрос.

**Пример / кейс**
```python
# Компромиссный вариант: короткий access-токен (JWT) + централизованная проверка отзыва refresh-токена
from datetime import datetime, timedelta, timezone

def issue_tokens(user_id: int, private_key: str):
    now = datetime.now(timezone.utc)
    access_token = jwt.encode(
        {"sub": user_id, "exp": now + timedelta(minutes=5)},  # короткое окно уязвимости
        private_key, algorithm="RS256",
    )
    refresh_token = create_refresh_token(user_id)  # хранится в БД, может быть немедленно отозван
    return access_token, refresh_token

def revoke_user_access(user_id: int):
    revoke_all_refresh_tokens(user_id)  # немедленный эффект: новые access-токены не выдать
    # существующие access-токены останутся валидны до истечения exp (до 5 минут) — осознанный trade-off
```
Проверка: тест на отзыв моделирует компрометацию — вызывает `revoke_user_access`, затем проверяет, что попытка обновить access-токен через отозванный refresh-токен получает 401, а уже выданный (не истёкший) access-токен остаётся валидным до истечения `exp`, что явно демонстрирует границы немедленности отзыва при выбранном TTL.

### 239. [Q-03-04-0239] Для API со списком из десятков миллионов записей, которые часто изменяются (вставки, удаления) в реальном времени, нужно спроектировать пагинацию, устойчивую к большому объёму данных и приемлемую по согласованности для пользователя. Как подойти к этому выбору? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Senior

**Короткий ответ**<br>
Cursor-based пагинация с устойчивым tie-breaker (например, `(sort_field, id)`) обычно нужна для производительности на больших объёмах, но нужно явно решить и задокументировать модель согласованности для пользователя при одновременных изменениях данных — показывать ли "снимок" на момент начала пролистывания (может уже не отражать последние изменения) или живые данные (может приводить к пропуску/дублированию записей при параллельных вставках/удалениях).

**Разбор**
- **Как это работает:** на десятках миллионов строк offset-пагинация деградирует по производительности пропорционально глубине смещения, так как БД должна пропустить все предыдущие строки даже с индексом; cursor-based подход с индексированным составным ключом сортировки избегает этой деградации, обращаясь напрямую к позиции по значению курсора. Но при живых данных курсор, зафиксированный на "последней увиденной записи", не защищает от того, что новые записи, вставленные перед текущей позицией сортировки, никогда не будут показаны в текущем пролистывании, а удалённые — вызовут видимый "пропуск" в ощущении пользователя.
- **На практике:** для сценариев, где пользователь ожидает стабильный список за время своей сессии пролистывания (например, экспорт отчёта), можно явно зафиксировать снимок на момент первого запроса (через выборку по `created_at <= snapshot_time` или через версионированную отдельную таблицу/snapshot), жертвуя "живостью" данных ради предсказуемости. Для сценариев вроде бесконечной ленты, где пользователь и ожидает, что новые события могут появляться сверху, живой cursor без снимка вполне приемлем. Выбор зависит от ожиданий пользователя и от того, критична ли полнота/отсутствие дублей больше, чем свежесть данных.
- **Частые ошибки:** использовать cursor по неуникальному полю (только `created_at`) без tie-breaker, что приводит к пропуску или дублированию записей с одинаковым значением сортировки на границе страницы; обещать пользователю одновременно и "актуальные данные в реальном времени", и "стабильный список без дублей/пропусков при пролистывании" без снимка — это взаимоисключающие гарантии при активно изменяющихся данных, и попытка дать оба без явного компромисса приведёт к скрытым дефектам.
- **Компромисс:** фиксация снимка на момент начала пролистывания даёт предсказуемость и отсутствие дублей/пропусков, но увеличивает затраты на хранение (нужно либо версионирование строк, либо отдельная snapshot-таблица) и показывает пользователю данные, устаревающие по мере пролистывания; живой cursor без снимка проще и не требует дополнительного хранения, но даёт пользователю ощутимо "нестабильный" список при высокой частоте изменений исходных данных. Критерий выбора — бизнес-требования к точности списка (отчётность и финансовые выгрузки обычно требуют снимок), частота изменений данных и стоимость дополнительной инфраструктуры снимков.

**Пример / кейс**
```sql
-- Cursor-пагинация с корректным tie-breaker по неуникальному полю сортировки
SELECT id, name, created_at
FROM events
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```
```sql
-- Вариант со снимком для стабильной выгрузки при активно изменяющихся данных
SELECT id, name, created_at
FROM events
WHERE created_at <= :snapshot_time
  AND (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```
Проверка: тест параллельно вставляет новые записи во время пролистывания cursor-пагинации без снимка и фиксирует наблюдаемые дубли/пропуски (ожидаемое поведение для этого режима); тест с зафиксированным `snapshot_time` при тех же параллельных вставках подтверждает, что итоговый список стабилен и не содержит записей, вставленных после `snapshot_time`.

### 240. [Q-03-04-0240] Компания должна перевести публичный REST API на новую несовместимую major-версию (изменение структуры ответов и обязательных полей), при этом у сотен внешних интеграторов нет жёсткого SLA на скорость обновления своих клиентов, а полная остановка старой версии недопустима без длительного переходного периода. Как спроектировать миграцию без простоя? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer  
**Тема:** HTTP, API и интеграции: HTTP-семантика, REST, GraphQL, контракты, версионирование, пагинация, webhooks и взаимодействие с внешними сервисами  
**Уровень:** Senior

**Короткий ответ**<br>
Нужен длительный период параллельной работы старой и новой версии за одним бэкендом с общей бизнес-логикой (новая версия — это, как правило, другой слой трансляции данных, а не полностью отдельный сервис), прозрачный мониторинг реального трафика по версиям, явная коммуникация и поэтапное отключение старой версии только на основе наблюдаемого снижения трафика, а не фиксированной даты — конкретная длительность периода и критерии отключения зависят от состава и договорных обязательств перед интеграторами.

**Разбор**
- **Как это работает:** параллельная поддержка двух версий не должна означать дублирование бизнес-логики — обычно практичнее иметь единый внутренний слой данных/логики и два "адаптера" представления (сериализации) для v1 и v2 поверх него, чтобы изменения в бизнес-правилах не нужно было вносить в двух местах. Миграция данных схемы (если затронута структура БД) должна быть спроектирована так, чтобы оба адаптера могли корректно работать с одной и той же актуальной моделью данных одновременно (expand-and-contract подход: сначала расширить схему данных совместимо, перевести всех потребителей, затем убрать старые поля/структуры).
- **На практике:** нужно заранее инструментировать API метриками по версии и по конкретному клиенту (API-ключу), чтобы видеть, кто ещё использует старую версию, и иметь возможность целенаправленно связаться с оставшимися интеграторами перед финальным отключением, а не ориентироваться только на общий агрегированный трафик. Решение об отключении старой версии должно приниматься на основе данных (доля/абсолютное число активных ключей на v1 ниже порога и стабильно снижается), а не только по формально прошедшему сроку уведомления — принудительное отключение при значимом остаточном трафике создаёт риск массовых инцидентов у партнёров и репутационный риск для компании.
- **Частые ошибки:** реализовывать v1 и v2 как полностью независимые кодовые пути с дублированием бизнес-логики, из-за чего последующие изменения правил нужно синхронизировать вручную в двух местах и легко допустить рассинхронизацию поведения между версиями; устанавливать жёсткую дату отключения без мониторинга реального остаточного трафика и без возможности её сдвинуть при обнаружении значимого числа всё ещё активных интеграторов.
- **Компромисс:** длительный период параллельной поддержки с общим внутренним слоем логики и адаптерами представления снижает риск инцидентов у партнёров и даёт время на плавную миграцию, но увеличивает затраты на поддержку (два набора контрактных тестов, более сложная схема данных на переходный период, дольше живёт технический долг старой версии); агрессивное отключение по жёсткому сроку быстрее снижает этот технический долг и издержки поддержки, но переносит риск простоя и репутационного ущерба на внешних интеграторов, которые не успели мигрировать, и на саму компанию через поток инцидентов и обращений в поддержку. Критерий выбора — коммерческая значимость оставшихся интеграторов на старой версии, контрактные обязательства по срокам поддержки и готовность компании нести стоимость длительной параллельной поддержки против риска принудительного отключения.

**Пример / кейс**
```python
# Единый внутренний слой данных + два адаптера представления для v1 и v2
def get_order_internal(order_id: int) -> OrderData:
    return orders_repo.fetch(order_id)  # единая бизнес-логика и модель данных

def serialize_order_v1(order: OrderData) -> dict:
    return {"id": order.id, "full_name": f"{order.first_name} {order.last_name}", "total": order.total}

def serialize_order_v2(order: OrderData) -> dict:
    return {"id": order.id, "first_name": order.first_name, "last_name": order.last_name, "total": order.total, "currency": order.currency}

@app.get("/v1/orders/{order_id}")
def get_order_v1(order_id: int):
    return serialize_order_v1(get_order_internal(order_id))

@app.get("/v2/orders/{order_id}")
def get_order_v2(order_id: int):
    return serialize_order_v2(get_order_internal(order_id))
```
Проверка: дашборд метрик по API-ключу и версии показывает долю и абсолютное число активных интеграторов на `/v1/` во времени; решение об отключении `/v1/` принимается, когда их число падает ниже заранее согласованного порога и/или истекает контрактный срок поддержки, а не по единому формальному дедлайну без учёта фактического трафика; изменение бизнес-правила (например, формулы расчёта `total`) тестом проверяется на то, что оно одинаково отражается в ответах обеих версий, подтверждая отсутствие дублирования логики.
