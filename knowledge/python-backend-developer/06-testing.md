## Тема 6. Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных

### 291. [Q-03-06-0291] Что такое unit-тест и чем он принципиально отличается от интеграционного теста?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Unit-тест проверяет изолированный фрагмент логики (функцию, метод, класс) без реальных внешних зависимостей, а интеграционный тест проверяет совместную работу нескольких реальных компонентов — например, кода и тестовой БД.

**Разбор**
- **Как это работает:** Unit-тест подменяет окружение (БД, сеть, файловую систему) моками или заглушками и проверяет поведение одной единицы кода на заданных входных данных, изолируя её от остальной системы. Интеграционный тест запускает несколько компонентов вместе — приложение и реальную тестовую БД, приложение и очередь сообщений, — проверяя их фактическое взаимодействие, включая сериализацию данных и реальные сетевые или протокольные детали.
- **На практике:** Unit-тесты быстрые и дешёвые, их должно быть больше всего — это нижний уровень тестовой пирамиды, и их стоит запускать при каждом сохранении файла или коммите. Интеграционные тесты медленнее и дороже в поддержке, но ловят ошибки на границах компонентов: несовпадение типов колонок в SQL, неверный формат ответа внешнего API, которые мок не заметит, поэтому их обычно держат в отдельном, более редком этапе CI.
- **Частые ошибки:** Называть unit-тестом тест, который фактически стучится в реальную БД или сеть — это интеграционный тест, просто маленький, и его стоит запускать и учитывать отдельно. Считать, что большое число unit-тестов с моками само по себе гарантирует работоспособность системы в целом, хотя взаимодействие реальных компонентов — форматы запросов, транзакции, сетевые тайм-ауты — нигде не проверено.

**Пример / кейс**
```python
def calculate_discount(price: float, is_vip: bool) -> float:
    return price * 0.8 if is_vip else price

def test_calculate_discount_for_vip_user():
    # unit-тест: нет обращений к БД, сети или файловой системе
    assert calculate_discount(100.0, True) == 80.0

# Интеграционный тест (другой уровень) обращался бы к тестовой БД,
# чтобы получить is_vip из реальной таблицы пользователей.
```

### 292. [Q-03-06-0292] Как устроен простейший тест в pytest и как pytest находит тесты в проекте?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Pytest автоматически находит файлы вида test_*.py или *_test.py и функции с префиксом test_, а проверки внутри теста делаются обычным оператором assert без дополнительных методов.

**Разбор**
- **Как это работает:** При запуске команды pytest рекурсивно обходит каталоги, собирает файлы и функции по соглашению об именовании (test_*.py, функции test_*, классы Test* без __init__), не требуя явной регистрации тестов где-либо ещё. Внутри теста используется встроенный assert — pytest переписывает его байткод (assertion rewriting), чтобы при падении показать подробную разницу значений (например, конкретные различающиеся элементы списков или словарей), а не просто AssertionError.
- **На практике:** Для изменения правил поиска используют testpaths, python_files, python_functions в pytest.ini или pyproject.toml, например, если в проекте используются другие соглашения именования. Тесты обычно кладут в отдельную директорию tests/, зеркалирующую структуру пакета приложения, чтобы было понятно, какой тестовый файл относится к какому модулю исходного кода.
- **Частые ошибки:** Забывать префикс test_ у функции — тогда pytest её просто не запустит и это не будет ошибкой; разработчик решит, что тест прошёл, хотя он вообще не выполнялся при прогоне. Также путают return значения в тесте с assert — return True ничего не проверяет, тест будет зелёным при любом поведении кода, что создаёт ложное чувство покрытости.

**Пример / кейс**
```python
# test_math_utils.py
def add(a, b):
    return a + b

def test_add_returns_sum_of_two_numbers():
    result = add(2, 3)
    assert result == 5  # при падении pytest покажет: assert 4 == 5
```

### 293. [Q-03-06-0293] Что такое фикстура в pytest и для каких задач она используется?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Фикстура — это функция с декоратором @pytest.fixture, которая подготавливает данные или ресурс для теста (объект, соединение, тестовые данные) и может сама освобождать его после выполнения теста.

**Разбор**
- **Как это работает:** Тест получает фикстуру, просто указав её имя как аргумент функции; pytest по этому имени находит соответствующую фикстуру и вызывает её перед тестом, передавая возвращённое (или yield-нутое) значение автоматически, без явного вызова разработчиком. Если фикстура использует yield, код после yield выполняется как teardown после завершения теста, даже если сам тест упал с ошибкой.
- **На практике:** Фикстуры удобны для переиспользуемой подготовки: тестовый клиент API, тестовое соединение с БД, тестовые пользователи — вместо копирования одного и того же кода подготовки в каждый тест. Их можно объявлять в conftest.py, чтобы они были доступны во всех тестах каталога без явного импорта, а также комбинировать одну фикстуру внутри другой для построения более сложного состояния.
- **Частые ошибки:** Класть в фикстуру слишком много логики и неявных побочных эффектов, из-за чего тест становится непрозрачным — непонятно, что именно подготовлено и почему тест вообще проходит или падает. Забывать про teardown (освобождение ресурса) при использовании return вместо yield, когда ресурс нужно закрывать явно, что приводит к утечке соединений между тестами.

**Пример / кейс**
```python
import pytest

@pytest.fixture
def db_connection():
    conn = create_test_connection()
    yield conn          # вот тут тест получает соединение
    conn.close()         # выполнится после теста — teardown

def test_insert_user(db_connection):
    db_connection.execute("INSERT INTO users (name) VALUES ('Ann')")
    assert db_connection.execute("SELECT COUNT(*) FROM users").scalar() == 1
```

### 294. [Q-03-06-0294] В чём разница между тестами в стиле unittest.TestCase и тестами в стиле pytest?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
unittest.TestCase требует наследования от базового класса и использует методы assertEqual/assertTrue и т.п., а pytest позволяет писать обычные функции с простым assert и подключать зависимости через фикстуры вместо setUp/tearDown.

**Разбор**
- **Как это работает:** unittest — часть стандартной библиотеки, тесты оформляются как методы класса, унаследованного от unittest.TestCase, с методами setUp/tearDown для подготовки и очистки состояния класса. Pytest не требует наследования: тест — это обычная функция, а подготовка данных делается через фикстуры, которые можно комбинировать, переиспользовать между разными модулями и параметризовать гибче, чем атрибуты класса в unittest.
- **На практике:** Pytest умеет запускать и обычные unittest-тесты, поэтому миграция возможна постепенно, модуль за модулем, без необходимости переписывать весь проект сразу. Многие команды выбирают pytest из-за более читаемых сообщений об ошибках assert, параметризации (@pytest.mark.parametrize) и богатой экосистемы плагинов (pytest-cov, pytest-asyncio, pytest-mock), которых у чистого unittest нет из коробки.
- **Частые ошибки:** Смешивать стили непоследовательно в одном модуле без причины, что усложняет чтение и ревью кода новым участникам команды. Использовать assertEqual в pytest-тестах по привычке, теряя преимущество подробного вывода обычного assert, который сразу показывает конкретное расхождение значений.

**Пример / кейс**
```python
import unittest

class TestMath(unittest.TestCase):
    def setUp(self):
        self.value = 10

    def test_double(self):
        self.assertEqual(self.value * 2, 20)

# Эквивалент в стиле pytest:
def test_double_pytest():
    value = 10
    assert value * 2 == 20
```

### 295. [Q-03-06-0295] Как с помощью pytest.mark.parametrize проверить функцию на нескольких наборах входных данных без дублирования кода теста?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Декоратор @pytest.mark.parametrize позволяет один раз описать тело теста и список пар (входные данные, ожидаемый результат), и pytest запустит тест отдельно для каждого набора.

**Разбор**
- **Как это работает:** В decorator передаются имена параметров строкой и список кортежей со значениями; pytest на их основе генерирует отдельный тест-кейс для каждой комбинации данных, видимый в отчёте как отдельный пункт. При падении одного набора остальные продолжают выполняться независимо, не блокируя проверку других значений.
- **На практике:** Параметризация особенно полезна для граничных значений и edge cases: пустая строка, отрицательное число, None, очень большое значение, которые иначе пришлось бы дублировать в отдельных функциях. Каждому кейсу можно задать понятный id через параметр ids, чтобы в отчёте CI сразу было видно, какой именно набор данных упал, не читая тело теста.
- **Частые ошибки:** Запихивать в один параметризованный тест слишком разные сценарии с разной логикой проверки — тест становится нечитаемым и сложным для отладки при падении. Забывать, что параметризация не заменяет отдельные тесты для принципиально разных веток кода (например, успех и исключение), где сам assert и его смысл отличаются.

**Пример / кейс**
```python
import pytest

def is_valid_age(age: int) -> bool:
    return 0 <= age <= 120

@pytest.mark.parametrize("age,expected", [
    (0, True),
    (120, True),
    (-1, False),
    (121, False),
])
def test_is_valid_age(age, expected):
    assert is_valid_age(age) is expected
```

### 296. [Q-03-06-0296] Что такое mock-объект и для чего он применяется в тестах?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Mock — это объект-заменитель реальной зависимости (например, внешнего сервиса или БД), который имитирует её поведение и позволяет проверить, как тестируемый код взаимодействовал с этой зависимостью, без реального вызова.

**Разбор**
- **Как это работает:** Библиотека unittest.mock предоставляет класс Mock/MagicMock, у которого любой атрибут или вызов метода автоматически создаёт новый мок и записывает факт вызова вместе с аргументами, не требуя заранее описывать интерфейс заменяемого объекта. Это позволяет позже проверить, был ли вызван нужный метод, с какими параметрами и сколько раз.
- **На практике:** Моки используют там, где реальный вызов дорог, медленен, недетерминирован или недоступен в тестовом окружении: отправка email, обращение к платёжному шлюзу, системные часы, запись в внешний лог-сервис. patch() из unittest.mock подменяет объект на мок только на время теста и автоматически возвращает исходный объект после его завершения.
- **Частые ошибки:** Мокать слишком много, из-за чего тест перестаёт проверять реальную логику и превращается в проверку того, что мок вызвали — это ложное чувство безопасности без реальной пользы. Забывать, что мок по умолчанию принимает любые аргументы и не проверяет сигнатуру реальной функции, из-за чего тест не замечает несовместимые изменения интерфейса после рефакторинга кода.

**Пример / кейс**
```python
from unittest.mock import Mock

def send_welcome_email(mailer, address):
    mailer.send(address, subject="Welcome")

def test_send_welcome_email_calls_mailer():
    mailer = Mock()
    send_welcome_email(mailer, "user@example.com")
    mailer.send.assert_called_once_with("user@example.com", subject="Welcome")
```

### 297. [Q-03-06-0297] Как проверить в тесте, что функция выбрасывает ожидаемое исключение?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Нужно использовать контекстный менеджер pytest.raises(ИсключениеТип), внутри которого вызывается код, и pytest проверит, что исключение действительно возникло и имеет нужный тип.

**Разбор**
- **Как это работает:** pytest.raises перехватывает исключение внутри блока with; если исключение заданного типа не возникло вообще или возник другой тип, тест падает с ошибкой, явно сигнализируя, что ожидаемого поведения не произошло. Через атрибут .value можно получить сам объект исключения и проверить его сообщение или дополнительные атрибуты.
- **На практике:** Такой тест важен для проверки валидации входных данных и граничных условий — например, что деление на ноль или передача отрицательного возраста действительно приводит к понятной, явной ошибке, а не к тихому неверному результату или падению в неожиданном месте кода позже.
- **Частые ошибки:** Проверять только факт исключения, но не его тип или сообщение, из-за чего тест пройдёт даже при неправильном, не относящемся к делу исключении (например, TypeError вместо ожидаемого ValueError). Оборачивать в pytest.raises слишком большой блок кода из нескольких вызовов, из-за чего непонятно, какая именно строка должна была бросить исключение, если тест упадёт.

**Пример / кейс**
```python
import pytest

def withdraw(balance: float, amount: float) -> float:
    if amount > balance:
        raise ValueError("insufficient funds")
    return balance - amount

def test_withdraw_raises_when_amount_exceeds_balance():
    with pytest.raises(ValueError, match="insufficient funds"):
        withdraw(balance=100, amount=150)
```

### 298. [Q-03-06-0298] Что такое паттерн Arrange-Act-Assert (AAA) и зачем ему следовать при написании тестов?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
AAA — это структура теста из трёх частей: подготовка данных и окружения (Arrange), вызов проверяемого кода (Act) и проверка результата (Assert); она делает тесты читаемыми и предсказуемыми по структуре.

**Разбор**
- **Как это работает:** В Arrange создаются входные данные, моки и зависимые объекты, необходимые именно для этого сценария. В Act вызывается ровно та функция или метод, поведение которых проверяется, и больше ничего. В Assert сравнивается фактический результат с ожидаемым, обычно одним или несколькими логически связанными утверждениями об одном и том же поведении.
- **На практике:** Явное разделение частей (даже просто пустой строкой или комментарием) облегчает чтение теста спустя время и ревью — сразу видно, что именно подготовлено, что вызывается и что именно проверяется. Это особенно важно в длинных тестах с несколькими моками или сложной подготовкой данных, где легко потерять нить повествования.
- **Частые ошибки:** Перемешивать Act и Assert, вызывая функцию несколько раз с разными проверками внутри одного теста, что усложняет диагностику того, какой именно вызов привёл к падению. Делать Arrange слишком большим и непрозрачным, пряча в фикстурах важные для понимания сути теста детали, из-за чего читателю приходится переходить по нескольким файлам.

**Пример / кейс**
```python
def test_apply_discount_to_order():
    # Arrange
    order = Order(items=[Item(price=100)], coupon="SALE10")

    # Act
    total = order.calculate_total()

    # Assert
    assert total == 90
```

### 299. [Q-03-06-0299] Зачем для тестов нужна отдельная тестовая база данных и как её обычно подключают в проекте?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Отдельная тестовая БД нужна, чтобы тесты не изменяли и не зависели от данных production или окружения разработки; её обычно поднимают через фикстуру, которая создаёт схему перед тестами и удаляет данные после них.

**Разбор**
- **Как это работает:** Тестовая БД может быть отдельной базой в том же СУБД-инстансе, временным SQLite-файлом или контейнером, поднятым специально для тестового прогона (например, через testcontainers или docker-compose), и полностью независима от БД разработки. Фикстура уровня сессии обычно применяет миграции один раз в начале прогона, а фикстура уровня функции очищает или откатывает данные между тестами.
- **На практике:** Важно, чтобы тестовая БД максимально соответствовала production по диалекту СУБД — если в проде PostgreSQL, тесты на SQLite могут не заметить несовместимые особенности SQL (например, работу с JSON-полями, регистрозависимость строк или ограничениями внешних ключей), которые проявятся только в production.
- **Частые ошибки:** Использовать production БД для тестов «по привычке» или из экономии времени — это прямой риск порчи или удаления реальных данных пользователей. Не изолировать тесты друг от друга: один тест оставляет данные в таблице, которые влияют на результат следующего, из-за чего тесты начинают зависеть от порядка запуска и ломаются непредсказуемо.

**Пример / кейс**
```python
import pytest

@pytest.fixture
def test_db():
    engine = create_engine("postgresql://test_user@localhost/test_db")
    Base.metadata.create_all(engine)
    yield engine
    Base.metadata.drop_all(engine)  # очистка после теста
```

### 300. [Q-03-06-0300] Для чего в unittest используются методы setUp и tearDown и когда они вызываются?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
setUp выполняется перед каждым тестовым методом класса и готовит общее состояние (объекты, соединения), а tearDown выполняется после каждого теста и освобождает ресурсы, независимо от того, прошёл тест или упал.

**Разбор**
- **Как это работает:** unittest вызывает setUp перед вызовом каждого test_* метода этого класса, а tearDown — сразу после, даже если тест завершился исключением или неудачным assert, а не только при успешном завершении. Это гарантирует, что ресурсы (файлы, соединения, временные директории), открытые в setUp, не утекают между тестами и не накапливаются при большом наборе тестов.
- **На практике:** setUp/tearDown удобны для простых повторяющихся приготовлений в рамках одного класса тестов, но при более сложной иерархии зависимостей pytest-фикстуры с разным scope часто оказываются гибче, позволяя переиспользовать подготовку между разными классами и модулями без дублирования кода.
- **Частые ошибки:** Делать tearDown зависимым от того, что setUp отработал полностью — если setUp упал на середине, часть ресурсов могла не создаться, и tearDown попытается закрыть несуществующий объект, порождая новую, маскирующую ошибку. Класть в setUp тяжёлые операции (например, реальный сетевой вызов или полную пересборку схемы БД), что сильно замедляет весь набор тестов.

**Пример / кейс**
```python
import unittest

class TestFileWriter(unittest.TestCase):
    def setUp(self):
        self.tmp_file = open("test_output.txt", "w")

    def tearDown(self):
        self.tmp_file.close()

    def test_write_line(self):
        self.tmp_file.write("hello")
        self.assertTrue(self.tmp_file.writable())
```

### 301. [Q-03-06-0301] Как проверить с помощью Mock, что функция была вызвана с определёнными аргументами, и чем это отличается от простой проверки факта вызова?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Для проверки аргументов используют mock.assert_called_with(...) или assert_called_once_with(...), которые сравнивают переданные аргументы с ожидаемыми, а не просто факт вызова, который проверяется методом assert_called().

**Разбор**
- **Как это работает:** Каждый Mock записывает историю вызовов в атрибуте call_args_list, включая позиционные и именованные аргументы каждого вызова, а не только факт его наличия. assert_called_with сравнивает последний вызов с переданными значениями и бросает AssertionError с понятной разницей, показывая и ожидаемые, и фактические аргументы.
- **На практике:** Такая проверка важна, когда важно не только что метод вызвали, но и что ему передали правильные данные — например, что уведомление отправлено именно на адрес текущего пользователя, а не на пустую строку или адрес по умолчанию, оставшийся от предыдущей итерации кода.
- **Частые ошибки:** Использовать assert_called() вместо assert_called_with(), когда на самом деле важны конкретные аргументы — тест пройдёт даже при передаче совершенно неверных данных. Не учитывать, что assert_called_once_with ещё и проверяет количество вызовов равное единице, и упадёт, если метод по ошибке вызвали дважды, даже с правильными аргументами в обоих случаях.

**Пример / кейс**
```python
from unittest.mock import Mock

def notify_user(notifier, user_id, message):
    notifier.send(user_id, message)

def test_notify_user_passes_correct_arguments():
    notifier = Mock()
    notify_user(notifier, user_id=42, message="Hi")
    notifier.send.assert_called_once_with(42, "Hi")
```

### 302. [Q-03-06-0302] Что показывает метрика покрытия тестами (code coverage) и почему высокий процент покрытия сам по себе не гарантирует качество тестов?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Покрытие показывает, какая доля строк или веток кода была выполнена хотя бы одним тестом, но не проверяет, что тест действительно содержит осмысленные проверки (assert) ожидаемого поведения на этих строках.

**Разбор**
- **Как это работает:** Инструмент вроде pytest-cov инструментирует код во время прогона тестов и фиксирует, какие строки (line coverage) или ветки условий (branch coverage) были выполнены хотя бы один раз, формируя отчёт в процентах по отдельным файлам, модулям и проекту в целом, с подсветкой непокрытых строк.
- **На практике:** Покрытие полезно, чтобы найти явно непротестированный код — функции или ветки обработки ошибок, которые вообще ни разу не вызывались в тестах. Но тест, который просто вызывает функцию без содержательного assert, засчитает строки как покрытые, хотя фактически ничего не проверил о корректности поведения.
- **Частые ошибки:** Ставить цель «100% покрытия» как самоцель, что приводит к формальным тестам без содержательных проверок, написанным только ради зелёной метрики. Делать выводы о качестве кода только по общему проценту покрытия проекта, не глядя на то, какие именно критичные ветки (обработка ошибок, граничные значения, редкие сценарии) остались непокрытыми.

**Пример / кейс**
```python
# плохой пример: строка покрыта, но ничего не проверяется
def test_process_order_runs_without_errors():
    process_order(Order(items=[]))  # нет ни одного assert

# лучше:
def test_process_order_returns_zero_total_for_empty_order():
    result = process_order(Order(items=[]))
    assert result.total == 0
```

### 303. [Q-03-06-0303] Как протестировать простой REST-эндпоинт с помощью тестового клиента фреймворка (например, TestClient в FastAPI)?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Тестовый клиент позволяет отправить HTTP-запрос к приложению прямо в процессе теста, без поднятия реального сервера и сети, и проверить код ответа и тело в формате JSON.

**Разбор**
- **Как это работает:** TestClient (на базе httpx/requests) оборачивает ASGI/WSGI-приложение и вызывает его напрямую через интерфейс приложения, эмулируя полный цикл обработки запроса: маршрутизацию, middleware, валидацию входных данных, сериализацию ответа — но без реального сетевого сокета и реального порта, что делает такие тесты быстрыми и стабильными.

from fastapi.testclient import TestClient

### 304. [Q-03-06-0304] Какие бывают основные виды тестовых дублеров (test doubles) — mock, stub, fake — и чем они отличаются друг от друга на простом уровне?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>
Stub возвращает заранее заданные данные без проверки вызовов, mock дополнительно проверяет, как именно его вызывали, а fake — это упрощённая, но рабочая реализация зависимости (например, БД в памяти вместо настоящей).

**Разбор**
- **Как это работает:** Stub используют, когда важно только получить предсказуемый результат от зависимости, не интересуясь деталями вызова или тем, сколько раз его вызвали. Mock добавляет к этому проверку поведения теста — какие методы вызваны, с какими аргументами, сколько раз именно. Fake — это отдельная, часто самописная реализация с реальной, пусть и упрощённой логикой, например словарь вместо таблицы в БД, который действительно хранит и возвращает данные.
- **На практике:** В Python чаще всего используют unittest.mock, который фактически совмещает возможности stub и mock в одном объекте — можно и задать возвращаемое значение (return_value), и проверить вызовы. Fake полезен, когда нужна более реалистичная имитация поведения, чем просто фиксированный ответ, например in-memory репозиторий для unit-тестов бизнес-логики.
- **Частые ошибки:** Путать термины и называть любой тестовый дублер «моком», что затрудняет общение в команде о том, что именно проверяет конкретный тест. Использовать слишком примитивный stub там, где нужна fake-реализация с реальной логикой хранения и выборки данных, из-за чего тест не замечает ошибки в работе с этими данными.

**Пример / кейс**
```python
class FakeUserRepository:
    def __init__(self):
        self._users = {}

    def save(self, user):
        self._users[user.id] = user

    def get(self, user_id):
        return self._users.get(user_id)

def test_user_service_saves_and_returns_user():
    repo = FakeUserRepository()  # fake вместо реальной БД
    service = UserService(repo)
    service.register(User(id=1, name="Ann"))
    assert service.get_user(1).name == "Ann"
```

**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Junior

**Короткий ответ**<br>

- **Как это работает:** Структура tests/unit, tests/integration, tests/e2e (или похожая) явно разделяет тесты по скорости и типу зависимостей, что позволяет запускать их выборочно: например, только быстрые unit-тесты при каждом коммите, а интеграционные — реже, в CI перед мержем, не блокируя разработчика долгим ожиданием.

Смешивать в одном каталоге быстрые unit-тесты и медленные интеграционные без явного разделения, из-за чего разработчики начинают игнорировать запуск всего набора тестов локально перед коммитом.

### 307. [Q-03-06-0307] Чем отличаются scope фикстур в pytest (function, class, module, session) и как выбрать подходящий scope для фикстуры с тестовой БД?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Middle

**Короткий ответ**<br>
Scope определяет, как часто пересоздаётся фикстура: function — перед каждым тестом, session — один раз за весь прогон; для тестовой БД обычно создают соединение/схему на уровне session, а очистку данных — на уровне function, чтобы не терять изоляцию тестов.

**Разбор**
- **Как это работает:** pytest кеширует результат фикстуры в рамках её scope и переиспользует его для всех подходящих тестов, пока scope не завершится, вызывая фикстуру заново только при смене области видимости. Более широкий scope (session, module) снижает накладные расходы на дорогие операции (поднятие контейнера с БД, подключение к сети), а узкий scope (function) обеспечивает полную изоляцию между тестами ценой повторной инициализации.
- **На практике:** Частый паттерн: фикстура session-уровня поднимает engine и применяет миграции один раз за весь прогон, а фикстура function-уровня оборачивает каждый тест в транзакцию и откатывает её после теста (через savepoint или rollback), совмещая скорость дорогой подготовки с полной изоляцией данных между тестами.
- **Частые ошибки:** Использовать session-scope для фикстуры, которая мутирует общее состояние (например, вставляет строки в таблицу), без последующей очистки — тесты начинают зависеть от порядка выполнения и ломаются при параллельном запуске через pytest-xdist. Делать всё function-scope без необходимости, из-за чего дорогие операции (поднятие контейнера) повторяются на каждый тест и сильно замедляют весь прогон без пользы для изоляции.

**Пример / кейс**
```python
import pytest

@pytest.fixture(scope="session")
def db_engine():
    engine = create_engine(TEST_DATABASE_URL)
    run_migrations(engine)
    yield engine
    engine.dispose()

@pytest.fixture
def db_session(db_engine):
    connection = db_engine.connect()
    transaction = connection.begin()
    session = Session(bind=connection)
    yield session
    session.close()
    transaction.rollback()  # откат изменений конкретного теста
    connection.close()
```

### 308. [Q-03-06-0308] Как правильно замокать внешний HTTP-вызов в тестах и почему важно патчить объект именно там, где он используется, а не там, где он определён?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Middle

**Короткий ответ**<br>
Нужно патчить имя функции/клиента в пространстве имён модуля, который его импортировал и использует, а не в модуле, где он изначально объявлен — иначе патч не подействует на реально выполняемый вызов.

**Разбор**
- **Как это работает:** unittest.mock.patch подменяет атрибут объекта в конкретном пространстве имён (модуле) на время теста. Если модуль a делает `from b import call_api` и вызывает `call_api(...)`, имя call_api существует и используется в пространстве имён модуля a — патчить нужно `a.call_api`, а не `b.call_api`, иначе ссылка в модуле a останется на оригинальную функцию.
- **На практике:** Для HTTP-вызовов часто удобнее использовать специализированные библиотеки (responses, httpx-mock, requests-mock), которые перехватывают запросы на уровне транспорта и позволяют описывать ожидаемые URL, метод, заголовки и тело ответа, а не мокать внутренние детали реализации конкретного клиента, что делает тест устойчивее к смене библиотеки.
- **Частые ошибки:** Патчить модуль, где функция определена, вместо модуля, где она используется — классическая ошибка, из-за которой мок «не срабатывает», и тест либо падает с реальной сетевой ошибкой, либо незаметно делает реальный запрос во внешний сервис. Мокать слишком низкоуровневые детали (например, внутренний сокет или TCP-соединение), из-за чего тест становится хрупким к любому рефакторингу реализации клиента.

**Пример / кейс**
```python
# service.py
from external_client import call_api

def get_price(product_id):
    return call_api(f"/price/{product_id}")["price"]

# test_service.py
from unittest.mock import patch

def test_get_price_uses_api_response():
    with patch("service.call_api") as mocked_call:  # патчим там, где используется
        mocked_call.return_value = {"price": 100}
        assert get_price(42) == 100
```

**Короткий ответ**<br>

**Разбор**
- **Как это работает:** freezegun подменяет вызовы datetime.now()/date.today() на уровне интерпретатора на время теста, фиксируя указанную дату для всего кода, выполняемого внутри декоратора или контекстного менеджера. Альтернативный, более явный подход — архитектурно внедрять функцию или объект clock в код вместо прямого вызова datetime.now(), что не требует монкипатчинга стандартной библиотеки и прозрачнее в чтении.
- **На практике:** Выбор между freezegun и внедрением зависимости clock зависит от размера кодовой базы и готовности к рефакторингу: freezegun быстрее внедрить в уже существующий код без изменения сигнатур функций, явный clock даёт более предсказуемое и read-only поведение без побочных эффектов монкипатчинга на весь процесс выполнения теста.
- **Частые ошибки:** Писать тесты, которые неявно зависят от реального текущего времени (например, `assert created_at.date() == date.today()`), что иногда ломается в полночь или при разнице часовых поясов CI-машины. Не учитывать часовой пояс при подмене времени, из-за чего тест проходит локально, но падает в CI с другим TZ.

**Пример / кейс**
```python
from freezegun import freeze_time

def days_until_expiry(expiry_date: date) -> int:
    return (expiry_date - date.today()).days

@freeze_time("2024-01-01")
def test_days_until_expiry():
    assert days_until_expiry(date(2024, 1, 10)) == 9
```

### 310. [Q-03-06-0310] Как организовать тестовую БД с транзакционным откатом между тестами, чтобы тесты были изолированы и быстро выполнялись?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Middle

**Короткий ответ**<br>
Каждый тест оборачивают в транзакцию (или savepoint) на реальном соединении с тестовой БД, а после теста транзакцию откатывают вместо того, чтобы пересоздавать схему или удалять данные вручную.

**Разбор**
- **Как это работает:** Фикстура открывает соединение, начинает транзакцию и создаёт сессию ORM, привязанную к этому соединению; все операции теста выполняются в её рамках. После теста fixture делает rollback — все изменения, включая вставки и обновления, отменяются, а схема и исходные данные (если были) остаются нетронутыми для следующего теста.
- **На практике:** Такой подход значительно быстрее, чем пересоздание всей схемы БД между тестами, и хорошо работает с большинством тестов, но ломается, если тестируемый код сам управляет транзакциями (commit/rollback) — вложенные savepoint нужно настраивать аккуратно, либо использовать отдельный engine для такого кода.
- **Частые ошибки:** Не учитывать, что некоторые операции (например, DDL в части СУБД, или явный commit внутри тестируемого кода) автоматически завершают внешнюю транзакцию, из-за чего откат не срабатывает так, как ожидалось, и данные остаются в БД. Переиспользовать одну и ту же сессию между несвязанными тестами без отката, что приводит к накоплению «мусорных» данных и падениям, зависящим от порядка запуска.

**Пример / кейс**
```python
@pytest.fixture
def db_session(db_engine):
    connection = db_engine.connect()
    trans = connection.begin()
    session = Session(bind=connection, join_transaction_mode="create_savepoint")
    yield session
    session.close()
    trans.rollback()
    connection.close()

def test_create_order_is_rolled_back(db_session):
    db_session.add(Order(total=100))
    db_session.flush()
    assert db_session.query(Order).count() == 1
    # после теста fixture откатит транзакцию, и следующий тест увидит 0 заказов
```

**Уровень:** Middle

**Короткий ответ**<br>
Нужно использовать плагин pytest-asyncio (или pytest-anyio) и помечать тестовую функцию как async def с декоратором @pytest.mark.asyncio, чтобы pytest запустил её внутри event loop, а не просто вызвал как обычную функцию.

**Разбор**
- **Как это работает:** Без специального плагина pytest не умеет ожидать корутины — async def тест без правильной настройки просто вернёт объект корутины, а не выполнит его, из-за чего тест формально «пройдёт», ничего не проверив. pytest-asyncio оборачивает такие тесты в event loop и дожидается их завершения через await.

Смешивать блокирующие вызовы (например, обычный requests.get) внутри асинхронного теста, что не отражает реальное поведение production-кода в event loop и маскирует проблему блокировки цикла событий.

**Пример / кейс**
```python
import pytest

    assert response.json()["id"] == 1
```

**Разбор**
- **Как это работает:** Flaky-тест обычно связан со скрытой зависимостью от внешнего или разделяемого состояния: случайных данных без фиксированного seed, реального времени, порядка выполнения тестов (если один тест оставляет данные для следующего), таймаутов в CI с ограниченными ресурсами, гонок между потоками или корутинами, которые не всегда успевают пересечься по времени.

Временная карантинная маркировка (@pytest.mark.flaky или skip с тикетом) допустима, но не должна становиться постоянным решением.
- **Частые ошибки:** Просто перезапускать упавший тест до зелёного результата в CI без расследования причины — это маскирует реальную проблему, которая может быть и в production-коде (например, настоящая гонка данных). Списывать нестабильность на «медленный CI» без проверки гипотезы через воспроизведение локально.

**Пример / кейс**
```text

```

Это особенно важно для сервисов с частичными отказами внешних зависимостей.

**Уровень:** Middle

**Короткий ответ**<br>
Для unit-тестирования логики задачи её можно вызвать напрямую как обычную функцию (task.run(...) или task(...)) либо включить режим task_always_eager=True, при котором Celery выполняет задачу синхронно в том же процессе без реального брокера.

**Разбор**
- **Как это работает:** При task_always_eager=True вызов task.delay()/apply_async() выполняет тело задачи немедленно и синхронно в текущем процессе, возвращая EagerResult, что позволяет проверить результат без Redis/RabbitMQ. Альтернативно можно тестировать саму функцию задачи напрямую, игнорируя декоратор Celery, если вся логика вынесена в обычную функцию, а задача — лишь тонкая обёртка.
- **На практике:** Eager-режим хорош для unit-тестирования бизнес-логики задачи, но не проверяет поведение, специфичное для реальной очереди: retry-политики, маршрутизацию по очередям, сериализацию аргументов, поведение при падении воркера. Для этого нужны отдельные интеграционные тесты с реальным (тестовым) брокером.
- **Частые ошибки:** Полагаться только на eager-тесты и считать, что retry/countdown/routing уже проверены — eager-режим их фактически обходит стороной и не выполняет реальную маршрутизацию. Не мокать побочные эффекты внутри задачи (отправку email, внешние вызовы), из-за чего unit-тест задачи превращается в полноценный, медленный и нестабильный интеграционный тест без явного на то намерения.

**Пример / кейс**
```python
from myapp.tasks import send_report

def test_send_report_task_runs_synchronously(celery_app, celery_worker):
    celery_app.conf.task_always_eager = True
    result = send_report.delay(user_id=1)
    assert result.get(timeout=5) == "sent"
```

### 317. [Q-03-06-0317] Как написать тесты для схемы валидации данных (например, Pydantic-модели) так, чтобы покрыть граничные и некорректные случаи, а не только happy path?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Middle

**Короткий ответ**<br>
Нужно отдельно проверить успешную валидацию корректных данных, явный отказ при невалидных данных (через pytest.raises(ValidationError)) и граничные значения — минимум/максимум допустимой длины, диапазона, пустые и None значения там, где они формально допустимы или недопустимы.

**Разбор**
- **Как это работает:** Pydantic при создании экземпляра модели с некорректными данными бросает ValidationError со списком конкретных ошибок по каждому полю отдельно; тест может проверить не только факт ошибки, но и то, что она относится к ожидаемому полю и имеет ожидаемый тип, через анализ e.value.errors().
- **На практике:** Параметризация (@pytest.mark.parametrize) хорошо подходит для перебора набора граничных и некорректных значений одного поля: пустая строка, строка ровно на границе max_length, отрицательное число для поля с ge=0, неверный формат email. Это системно покрывает значимые классы эквивалентности входных данных.
- **Частые ошибки:** Тестировать только один успешный пример и считать схему полностью проверенной, упуская граничные условия, где чаще всего и возникают реальные баги в production. Проверять сообщение об ошибке дословно вместо факта и места ошибки, из-за чего тест становится хрупким к любым правкам текста сообщения.

**Пример / кейс**
```python
from pydantic import BaseModel, Field, ValidationError
import pytest

class CreateUserRequest(BaseModel):
    name: str = Field(min_length=1, max_length=50)
    age: int = Field(ge=0, le=120)

@pytest.mark.parametrize("age", [-1, 121])
def test_create_user_request_rejects_invalid_age(age):
    with pytest.raises(ValidationError) as exc_info:
        CreateUserRequest(name="Ann", age=age)
    assert exc_info.value.errors()[0]["loc"] == ("age",)
```

### 318. [Q-03-06-0318] Почему тесты иногда начинают зависеть от порядка запуска, и как обеспечить их независимость друг от друга?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Middle

**Короткий ответ**<br>
Тесты начинают зависеть от порядка, когда делят общее изменяемое состояние — глобальные переменные, данные в тестовой БД без отката, кеш, файлы на диске — и один тест неявно опирается на состояние, оставленное предыдущим; решение — явная изоляция через фикстуры с очисткой/откатом перед или после каждого теста.

**Разбор**
- **Как это работает:** Если тест A создаёт запись в БД и не удаляет её, а тест B неявно рассчитывает на пустую таблицу (например, проверяет count() == 0), результат теста B зависит от того, выполнялся ли тест A раньше. Запуск тестов в случайном порядке (pytest-randomly) — хороший способ быстро выявить такие скрытые зависимости.
- **На практике:** Надёжная изоляция обычно достигается транзакционным откатом БД между тестами, пересозданием моков в каждой фикстуре function-уровня вместо модульных глобальных моков, и избеганием мутируемых global/module-level переменных в тестируемом коде либо их явным сбросом в фикстуре.
- **Частые ошибки:** Использовать module-scope или session-scope фикстуры для объектов, которые тест изменяет, без последующей очистки состояния между тестами. Полагаться на то, что тесты в файле всегда будут запускаться в порядке их объявления — pytest формально это обычно делает, но параллельные раннеры (pytest-xdist) и переупорядочивание плагинами этого не гарантируют.

**Пример / кейс**
```python
# Плохо: тесты неявно зависят от порядка
_counter = {"value": 0}

def test_increment():
    _counter["value"] += 1
    assert _counter["value"] == 1  # упадёт, если запустить после другого теста

# Хорошо: состояние изолировано фикстурой на каждый тест
@pytest.fixture
def counter():
    return {"value": 0}

def test_increment_isolated(counter):
    counter["value"] += 1
    assert counter["value"] == 1
```

### 319. [Q-03-06-0319] Что такое контрактное (schema/contract) тестирование API и зачем оно нужно в дополнение к обычным функциональным тестам эндпоинтов?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Middle

**Короткий ответ**<br>
Контрактное тестирование проверяет, что фактический формат запроса/ответа API соответствует согласованной схеме (например, OpenAPI-спецификации), что позволяет заранее обнаружить несовместимые изменения API для клиентов, которые сами по себе не ломают функциональные тесты сервера.

**Разбор**
- **Как это работает:** Схема (OpenAPI/JSON Schema) описывает ожидаемую структуру полей, их типы и обязательность. Тест может валидировать реальный ответ сервера против этой схемы (например, через schemathesis или jsonschema), либо, в подходе consumer-driven contracts, клиент фиксирует свои ожидания в контракте, а сервер в CI проверяет, что продолжает ему соответствовать.
- **На практике:** Такое тестирование особенно полезно в системах с несколькими независимо развивающимися сервисами или внешними потребителями API, где обычный функциональный тест на сервере может быть зелёным (данные корректны по бизнес-логике), но формат ответа изменился и сломал клиента, которого разработчик сервера не видит в своём репозитории.
- **Частые ошибки:** Полагаться только на функциональные тесты конкретных значений ответа и не проверять саму структуру схемы, из-за чего переименование или удаление поля остаётся незамеченным до жалобы интеграционного партнёра в production. Поддерживать схему OpenAPI вручную отдельно от кода, что быстро приводит к расхождению схемы и реального поведения сервиса.

**Пример / кейс**
```python
import schemathesis

schema = schemathesis.openapi.from_url("http://localhost:8000/openapi.json")

@schema.parametrize()
def test_api_matches_openapi_schema(case):
    response = case.call()
    case.validate_response(response)  # проверка структуры и статусов по схеме
```

### 320. [Q-03-06-0320] Как настроить прогон тестов в CI так, чтобы он был быстрым и давал надёжный сигнал (например, за счёт параллелизации и разделения на этапы)?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Middle

**Короткий ответ**<br>
Тесты стоит разделить на быстрый этап (unit-тесты, линтеры) и более медленный этап (интеграционные тесты с реальной БД), запускать их параллельно по нескольким воркерам (pytest-xdist) и настраивать кеширование зависимостей, чтобы обратная связь разработчику приходила как можно быстрее при сохранении достаточного покрытия перед мержем.

**Разбор**
- **Как это работает:** pytest-xdist распределяет тесты по нескольким процессам/ядрам (pytest -n auto), сокращая общее время прогона на многоядерных раннерах. Разделение на job'ы в CI-пайплайне (unit → integration → e2e) с ранним завершением (fail fast) на первом же упавшем быстром этапе экономит время и вычислительные ресурсы.
- **На практике:** Важно учитывать изоляцию при параллельном запуске: каждая параллельная группа тестов с реальной БД должна использовать собственную схему/базу или уникальный namespace, иначе параллельные воркеры будут конфликтовать за одни и те же данные. Кеширование зависимостей (pip/poetry) и Docker-слоёв ускоряет повторные прогоны.
- **Частые ошибки:** Запускать все тесты, включая медленные e2e, на каждый push без разделения на этапы, из-за чего обратная связь занимает слишком много времени и разработчики реже проверяют CI перед мержем в основную ветку. Включать параллелизацию без обеспечения изоляции данных между воркерами, что проявляется как случайные, труднообъяснимые падения именно в CI, но не локально.

**Пример / кейс**
```yaml
jobs:
  unit-tests:
    steps:
      - run: pytest tests/unit -n auto --maxfail=1

  integration-tests:
    needs: unit-tests
    services:
      postgres:
        image: postgres:16
    steps:
      - run: pytest tests/integration -n 4
```

### 321. [Q-03-06-0321] Как протестировать, что миграция базы данных применяется и откатывается корректно, не ломая существующие данные?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Middle

**Короткий ответ**<br>
Нужен тест, который на тестовой БД применяет миграции до нужной ревизии, проверяет итоговую схему (и, при изменении данных миграцией, их корректность), а затем откатывает миграцию назад и проверяет, что схема вернулась в исходное состояние без потери важных данных.

**Разбор**
- **Как это работает:** Инструменты миграций (Alembic для SQLAlchemy, стандартные миграции Django) предоставляют программный интерфейс для апгрейда и даунгрейда до конкретной ревизии; тест может вызвать upgrade('head') и downgrade('-1') на изолированной тестовой БД и после каждого шага интроспектировать структуру таблиц (через information_schema или метаданные ORM).
- **На практике:** Особенно важно тестировать миграции, которые переносят или трансформируют данные (а не только меняют схему) — например, разбивают одно поле на два. Такой тест должен заранее засеять БД репрезентативными данными перед апгрейдом и проверить, что после миграции данные преобразованы верно, а после отката не потеряны безвозвратно, если это возможно по природе миграции.
- **Частые ошибки:** Тестировать миграции только на пустой БД, из-за чего проблемы с реальными данными (NULL в новом NOT NULL поле, конфликт уникальности после трансформации) обнаруживаются только в production на реальных строках. Не тестировать downgrade вообще, полагаясь, что откат никогда не понадобится, хотя именно он часто нужен при экстренном rollback релиза.

**Пример / кейс**
```python
def test_migration_adds_not_null_column_with_default(alembic_config, db_connection):
    seed_users_table(db_connection, rows=[{"id": 1, "name": "Ann"}])

    run_migration(alembic_config, revision="+1")  # применяем следующую миграцию
    row = db_connection.execute("SELECT status FROM users WHERE id=1").fetchone()
    assert row.status == "active"  # новое поле заполнено дефолтом

    run_migration(alembic_config, revision="-1")  # откат
    columns = get_table_columns(db_connection, "users")
    assert "status" not in columns
```

### 322. [Q-03-06-0322] Как спроектировать код так, чтобы его было проще покрывать unit-тестами, и какие практические приёмы внедрения зависимостей (dependency injection) для этого применяют в Python-проекте?

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Middle

**Короткий ответ**<br>
Нужно передавать внешние зависимости (репозиторий БД, HTTP-клиент, почтовый отправитель) в конструктор или аргументы функции явно, а не создавать их внутри тела функции или импортировать как глобальный singleton, — тогда в тесте можно подставить тестовую реализацию или мок вместо реальной зависимости.

**Разбор**
- **Как это работает:** Если функция сама создаёт клиент БД или HTTP-сессию внутри себя (`def process(): client = RealApiClient()`), тест не может подменить эту зависимость без патчинга импортов, что более хрупко и неявно. Если зависимость передаётся параметром (`def process(client): ...`), тест просто передаёт тестовый двойник напрямую, без монкипатчинга модулей.
- **На практике:** В Python для этого не обязателен сложный DI-фреймворк — обычно достаточно явных конструкторов классов, принимающих интерфейс/протокол зависимости, и фабричной функции или контейнера на уровне входной точки приложения (main, обработчик запроса), которая один раз собирает реальные зависимости. Это также упрощает переиспользование одной и той же бизнес-логики с разными реализациями хранилища (например, в тестах — in-memory, в проде — PostgreSQL).
- **Частые ошибки:** Злоупотреблять patch() как заменой нормального проектирования — патчинг глубоко вложенных импортов работает, но делает тесты хрупкими к рефакторингу структуры модулей. Вводить DI-контейнер и избыточную абстракцию там, где у функции всего одна простая зависимость и явного параметра конструктора было бы достаточно.

**Пример / кейс**
```python
# Плохо для тестирования: зависимость создаётся внутри функции
def send_report(user_id):
    mailer = SmtpMailer()  # нельзя подменить без патчинга модуля
    mailer.send(user_id, "report ready")

# Лучше: зависимость передаётся явно
def send_report(user_id, mailer):
    mailer.send(user_id, "report ready")

def test_send_report_calls_mailer():
    fake_mailer = Mock()
    send_report(user_id=1, mailer=fake_mailer)
    fake_mailer.send.assert_called_once_with(1, "report ready")
```

### 323. [Q-03-06-0323] Как спроектировать тестовую стратегию (соотношение unit/интеграционных/e2e-тестов) для крупного backend-сервиса с множеством внешних интеграций, учитывая скорость обратной связи и надёжность сигнала? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Senior

**Короткий ответ**<br>
Стратегию стоит строить как пирамиду с основанием из быстрых unit-тестов бизнес-логики, средним слоем интеграционных тестов на границах с БД и внешними сервисами, и тонким верхним слоем e2e-тестов критичных пользовательских сценариев — конкретные пропорции и границы между слоями зависят от критичности сервиса, зрелости команды и стоимости инцидентов.

**Разбор**
- **Как это работает:** Каждый уровень тестовой пирамиды ловит свой класс ошибок: unit-тесты — ошибки в логике при минимальной стоимости и максимальной скорости; интеграционные — несовместимость с реальной БД, сериализацией, внешними контрактами; e2e — поломки в связке всех компонентов и инфраструктуры, но ценой медленного и более хрупкого прогона.
- **На практике:** Для сервисов с множеством внешних интеграций стоит дополнительно инвестировать в контрактные тесты (consumer-driven contracts) на границах с партнёрами, чтобы не превращать каждую интеграцию в дорогой e2e-сценарий. Критичные денежные или безопасность-чувствительные пути оправдывают больше e2e-покрытия, несмотря на их стоимость.
- **Частые ошибки:** Строить «перевёрнутую пирамиду» с преобладанием медленных e2e-тестов, из-за чего CI занимает часы, а разработчики начинают игнорировать падения. Или наоборот — полагаться почти исключительно на unit-тесты с моками, упуская целый класс ошибок интеграции, который проявляется только в production.
- **Компромисс:** Больше unit-тестов — быстрая обратная связь и низкая стоимость поддержки, но риск пропустить ошибки интеграции. Больше интеграционных/e2e — выше уверенность в реальном поведении системы, но дороже в поддержке, медленнее CI и больше flaky-тестов. Критерий выбора: критичность сценария (деньги, безопасность, SLA), частота изменений в этой части системы и фактическая история инцидентов — там, где инциденты повторяются, стоит добавлять тесты именно того уровня, который их бы поймал, а не слепо увеличивать долю одного типа тестов.

**Пример / кейс**
```text
Пример распределения для платёжного сервиса с 5 внешними интеграциями:
- 70% unit-тестов бизнес-логики расчёта и валидации (мс на тест)
- 20% интеграционных тестов с тестовой БД и контрактных тестов на внешние API
- 10% e2e-сценариев: "оплата прошла и зачислена", "возврат средств"
Критерий ревью: каждый найденный в production баг должен добавлять тест
на том уровне, где он дешевле всего обнаруживается повторно.
```

### 324. [Q-03-06-0324] Как протестировать идемпотентность обработчика сообщений в системе с возможной повторной доставкой (at-least-once), и какие подходы к такому тестированию стоит обсудить? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Senior

**Короткий ответ**<br>
Нужен тест, который явно эмулирует повторную доставку одного и того же сообщения (с тем же ключом идемпотентности) и проверяет, что повторная обработка не приводит к повторному побочному эффекту — например, списание средств или отправка уведомления происходит ровно один раз, в зависимости от того, какую гарантию реализует конкретный обработчик.

**Разбор**
- **Как это работает:** Идемпотентность обычно реализуется через хранение уже обработанных ключей сообщений (идентификатор сообщения, бизнес-ключ операции) в БД или кеше с уникальным ограничением, и обработчик перед выполнением проверяет, не обработано ли уже такое сообщение. Тест должен вызвать обработчик дважды с одинаковым сообщением и проверить состояние системы после каждого вызова.
- **На практике:** Важно тестировать не только «повтор подряд», но и конкурентный повтор (два почти одновременных вызова с одним и тем же ключом) — это требует теста с реальной или близкой к реальной БД с уникальным ограничением или блокировкой, так как чисто моковый unit-тест не проверит гонку на уровне СУБД.
- **Частые ошибки:** Проверять идемпотентность только последовательным повторным вызовом в одном потоке, упуская конкурентный сценарий, который на практике и приводит к дублированию при повторной доставке почти одновременно двумя воркерами. Считать операцию идемпотентной только потому, что код выглядит так, будто проверяет дубликат, без теста, подтверждающего это на реальном хранилище с конкурентным доступом.
- **Компромисс:** Полный тест с реальной БД и конкурентными вызовами даёт высокую уверенность, но дороже в поддержке и медленнее; unit-тест с моком хранилища дешевле, но не ловит гонки на уровне БД (отсутствие или неправильное использование уникального ограничения). Критерий выбора: для критичных операций (платежи, списания) оправдан хотя бы один интеграционный тест с конкурентным вызовом на реальной тестовой БД, а для менее критичных операций может быть достаточно unit-теста, проверяющего логику проверки дубликата.

**Пример / кейс**
```python
import threading

def test_payment_handler_is_idempotent_under_concurrent_retry(db_session, payment_handler):
    message = {"idempotency_key": "order-42", "amount": 100}

    results = []
    def process():
        results.append(payment_handler.handle(message, session=db_session))

    threads = [threading.Thread(target=process) for _ in range(2)]
    for t in threads: t.start()
    for t in threads: t.join()

    charges = db_session.query(Charge).filter_by(idempotency_key="order-42").count()
    assert charges == 1  # ровно одно списание, несмотря на два почти одновременных вызова
```

### 325. [Q-03-06-0325] Стоит ли внедрять property-based тестирование (например, через hypothesis) в проект с уже сложившейся практикой классических example-based тестов, и как выбрать, для какого кода это оправдано? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Senior

**Короткий ответ**<br>
Property-based тестирование полезно для кода с чёткими инвариантами и большим пространством входных данных (парсеры, сериализация/десериализация, математические операции), но не должно полностью заменять example-based тесты, которые лучше документируют конкретные бизнес-сценарии и граничные случаи, понятные человеку.

**Разбор**
- **Как это работает:** Вместо фиксированных примеров hypothesis генерирует множество случайных входных данных по описанной стратегии и проверяет, что заданное свойство (инвариант) выполняется для всех них — например, что `decode(encode(x)) == x` для любого x из определённого диапазона. При падении hypothesis автоматически минимизирует (shrinking) контрпример до простейшего воспроизводимого случая.
- **На практике:** Хорошие кандидаты — чистые функции с математическими или структурными инвариантами: сериализация, нормализация данных, арифметика с деньгами, сортировки. Плохие кандидаты — код с тяжёлыми побочными эффектами (реальные сетевые вызовы, запись в БД), где случайная генерация большого числа запусков дорога и малоинформативна без дополнительной инфраструктуры.
- **Частые ошибки:** Пытаться описать property-тестом код, у которого нет чёткого формулируемого инварианта, и в итоге писать сложную, малопонятную стратегию генерации данных ради сомнительной пользы. Выбрасывать существующие example-based тесты важных бизнес-кейсов в пользу property-тестов, теряя читаемую документацию конкретных сценариев для новых членов команды.
- **Компромисс:** Property-based тесты находят неочевидные граничные случаи, которые человек не всегда придумает вручную, но требуют больше времени на формулировку инвариантов и могут давать более медленные и иногда недетерминированные (по времени выполнения) прогоны. Критерий выбора: внедрять точечно для модулей с высокой ценой ошибки и чёткими инвариантами, сохраняя example-based тесты для документирования конкретных бизнес-правил и регрессионных случаев, найденных в production.

**Пример / кейс**
```python
from hypothesis import given, strategies as st

def normalize_phone(raw: str) -> str:
    digits = "".join(ch for ch in raw if ch.isdigit())
    return digits[-10:]

@given(st.text(alphabet="0123456789 -()", min_size=10, max_size=20))
def test_normalize_phone_always_returns_exactly_10_digits(raw):
    result = normalize_phone(raw)
    assert len(result) <= 10
    assert result.isdigit() or result == ""
```

### 326. [Q-03-06-0326] Как организовать тестирование конкурентного доступа к данным (гонки, потерянные обновления) в backend-сервисе, учитывая, что такие баги плохо воспроизводятся обычными последовательными тестами? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Senior

**Короткий ответ**<br>
Нужно сочетать явные тесты конкурентного сценария на реальной тестовой БД (запуск нескольких параллельных операций над одной записью и проверка итогового состояния) с осознанным выбором механизма защиты (оптимистичная блокировка через version-поле, пессимистичная блокировка SELECT ... FOR UPDATE, сериализуемый уровень изоляции транзакций) — тест должен проверять именно тот механизм, который реализован, а не абстрактную «защищённость от гонок».

**Разбор**
- **Как это работает:** Тест запускает несколько потоков или процессов (или два отдельных соединения/сессии к одной тестовой БД), которые одновременно читают одну запись, изменяют её и пытаются сохранить, затем проверяет, что итоговое значение соответствует ожидаемому при выбранной стратегии защиты — например, что при оптимистичной блокировке один из конкурентных апдейтов явно завершается ошибкой конфликта версии, а не молча перезаписывает чужие изменения.
- **На практике:** Такие тесты по своей природе недетерминированы по времени выполнения гонки, поэтому часто используют искусственную синхронизацию (barriers, явные паузы в определённых точках через монкипатчинг или специальные hooks) — иначе гонка может просто не успеть произойти в большинстве прогонов, и тест будет ложно-зелёным, создавая иллюзию защищённости.
- **Частые ошибки:** Писать «тест на гонку» без принудительной синхронизации потоков, который в 99% прогонов проходит просто потому, что операции физически не пересеклись по времени — такой тест не доказывает отсутствие проблемы. Путать уровень защиты в тесте с уровнем, реально используемым в production-коде (например, тестировать с SERIALIZABLE, когда в проде используется READ COMMITTED по умолчанию).
- **Компромисс:** Тесты с принудительной синхронизацией гонки дают высокую уверенность, но сложны в реализации и поддержке, специфичны к конкретной СУБД и уровню изоляции. Более простой вариант — полагаться на статический анализ и ревью кода критичных секций плюс мониторинг конфликтов в production — дешевле, но не даёт автоматической регрессионной защиты. Критерий выбора: для операций с прямой денежной или юридической ценой (списания, бронирования ограниченного ресурса) оправдан явный тест на гонку с синхронизацией; для менее критичных операций может быть достаточно явного ревью кода и мониторинга.

**Пример / кейс**
```python
def test_optimistic_locking_detects_concurrent_update_conflict(db_engine):
    conn_a = db_engine.connect()
    conn_b = db_engine.connect()

    account_a = load_account(conn_a, account_id=1)  # version=1
    account_b = load_account(conn_b, account_id=1)  # version=1

    save_account(conn_a, account_a, new_balance=90)   # успешно, version становится 2
    with pytest.raises(StaleDataError):
        save_account(conn_b, account_b, new_balance=80)  # version устарела -> конфликт, а не тихая перезапись
```

### 327. [Q-03-06-0327] Как спроектировать подход к тестированию эволюции контракта API (обратная совместимость, consumer-driven contracts) в системе с несколькими независимыми потребителями? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Senior

**Короткий ответ**<br>
Для изменений, затрагивающих внешний контракт, стоит сочетать тесты обратной совместимости на стороне сервера (старые поля и форматы продолжают поддерживаться в переходный период) с consumer-driven contract тестами, где каждый значимый потребитель фиксирует свои реальные ожидания от API, и сервер в CI проверяет, что эти ожидания не нарушены — конкретный баланс между строгостью контрактов и скоростью эволюции API зависит от числа потребителей и их возможности быстро обновляться.

**Разбор**
- **Как это работает:** Consumer-driven contract подход (например, Pact) фиксирует для каждого потребителя набор ожидаемых запросов и ответов как отдельный контракт-файл; сервер в своём CI воспроизводит эти запросы против текущей реализации и падает, если ответ перестал соответствовать зафиксированным ожиданиям — это обнаруживает breaking change до релиза, а не после жалобы потребителя.
- **На практике:** Для изменений, которые объективно ломают совместимость (переименование обязательного поля, смена типа), практикуют версионирование API или параллельную поддержку старого и нового формата на переходный период с планом и сроком депрекации, доносимым до потребителей заранее, а не как технический сюрприз.
- **Частые ошибки:** Полагаться только на внутренние функциональные тесты сервера и не учитывать реальные контракты потребителей, из-за чего несовместимые изменения обнаруживаются только в production у внешнего партнёра. Вводить строгий consumer-driven contract процесс для всех без исключения внутренних эндпоинтов, что создаёт чрезмерные накладные расходы там, где сервис и потребитель меняются синхронно одной командой.
- **Компромисс:** Строгие contract-тесты для всех потребителей дают максимальную защиту от breaking changes, но замедляют эволюцию API и требуют дисциплины от всех команд-потребителей поддерживать свои контракты актуальными. Более лёгкий подход — версионирование API и ручной чеклист при изменениях — быстрее внедрить, но полагается на дисциплину разработчиков и даёт менее автоматизированную защиту. Критерий выбора: число и критичность внешних потребителей, их способность быстро адаптироваться, и фактическая история breaking changes в истории сервиса — там, где такие инциденты уже случались, инвестиция в contract-тесты окупается быстрее.

**Пример / кейс**
```text
Контракт потребителя "billing-service" к "orders-api" (Pact, упрощённо):
Given: заказ с id=42 существует
When: GET /orders/42
Then: ответ 200, тело содержит поля {id: number, total: number, status: string}

CI сервера orders-api перед релизом проигрывает этот контракт против текущей
реализации; удаление поля "total" или смена его типа на строку = явный провал
контрактного теста до релиза, а не инцидент у billing-service в production.
```

### 328. [Q-03-06-0328] Как найти баланс между использованием моков/тестовых дублеров и тестированием против реальных зависимостей в CI по мере роста сервиса и числа интеграций? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Senior

**Короткий ответ**<br>
Решение зависит от стоимости и стабильности реальной зависимости: для быстрых и детерминированных зависимостей (своя тестовая БД, внутренний сервис с тестовым окружением) стоит тестировать против реальных инстансов в интеграционных тестах, а для медленных, дорогих, нестабильных или сторонних зависимостей (внешние платёжные шлюзы, сторонние API с лимитами) оправданы моки и контрактные тесты вместо постоянных реальных вызовов в CI.

**Разбор**
- **Как это работает:** Моки дают скорость, детерминированность и независимость от доступности внешней системы, но верны ровно настолько, насколько верны предположения разработчика о поведении реальной зависимости — если реальный сервис изменит поведение, мок этого не заметит. Реальные зависимости в CI (через контейнеры или тестовые окружения) дают более высокую уверенность, но увеличивают время прогона, хрупкость (сетевые сбои, лимиты) и инфраструктурную сложность пайплайна.
- **На практике:** Распространённый компромисс — трёхуровневая стратегия: unit-тесты с моками для быстрой обратной связи по логике, контрактные тесты против записанных или согласованных реальных ответов (VCR-кассеты, Pact) для проверки формата без постоянных реальных вызовов, и небольшое число настоящих end-to-end smoke-тестов против реальной (тестовой) внешней системы, запускаемых реже — например, по расписанию, а не на каждый коммит.
- **Частые ошибки:** Мокать внешнюю зависимость один раз на старте проекта и никогда не обновлять мок при изменении реального API, из-за чего моки медленно расходятся с реальностью и тесты теряют ценность, оставаясь зелёными при реально сломанной интеграции. Либо обратная крайность — тестировать абсолютно всё против реальных внешних сервисов в каждом CI-прогоне, что делает пайплайн медленным, дорогим и зависимым от доступности третьих сторон.
- **Компромисс:** Больше моков — быстрый и стабильный CI, но риск расхождения мока с реальным поведением зависимости со временем. Больше реальных вызовов — выше доверие к результату, но дороже, медленнее и менее предсказуемо (зависимость от сети и SLA третьей стороны). Критерий выбора: стоимость ложного отрицательного результата (пропущенной поломки интеграции) против стоимости медленного и нестабильного CI — для критичных денежных интеграций стоит инвестировать в периодические реальные smoke-тесты вдобавок к мокам, даже если они не гоняются на каждый коммит.

**Пример / кейс**
```text
Стратегия для интеграции с внешним платёжным шлюзом:
- unit-тесты бизнес-логики: мок платёжного клиента (каждый коммит, секунды)
- контрактные тесты: записанные реальные ответы шлюза через VCR-кассеты (каждый коммит)
- smoke-тест в песочнице шлюза: один реальный платёж в тестовом режиме
  (по расписанию раз в сутки, не блокирует обычный релиз)
```

### 329. [Q-03-06-0329] Как тестировать деградацию производительности системы под нагрузкой, не полагаясь на единственное число RPS или результат одного микробенчмарка как доказательство качества? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Senior

**Короткий ответ**<br>
Нужно тестировать поведение системы на реалистичном профиле нагрузки (смесь типов запросов, распределение по времени, постепенный рост) и смотреть на набор метрик — задержку по перцентилям (p50/p95/p99), частоту ошибок, использование ресурсов, поведение под пиковой и длительной нагрузкой, — а не только на пиковый RPS, который сильно зависит от окружения теста и конкретной конфигурации.

**Разбор**
- **Как это работает:** Нагрузочный тест (например, через locust или k6) эмулирует параллельных пользователей по сценарию, близкому к реальному трафику, и собирает распределение времени ответа, а не только среднее значение — среднее легко маскирует то, что часть запросов (например, p99) отвечает на порядок медленнее из-за блокировок, N+1-запросов или исчерпания пула соединений с БД под нагрузкой.
- **На практике:** Важно тестировать не только пиковую нагрузку, но и длительную (soak-тест), чтобы заметить деградацию, которая проявляется только со временем — утечки памяти, рост фрагментации соединений, накопление данных, не удаляемых фоновыми задачами. Результаты одного прогона на нестабильном или нерепрезентативном окружении (другая конфигурация железа, другая версия зависимостей) нельзя напрямую сравнивать с production без воспроизведения сопоставимых условий.
- **Частые ошибки:** Сообщать результат одного короткого прогона («система держит 5000 RPS») без указания условий (размер данных, профиль запросов, конфигурация окружения, перцентили задержки) как универсальный факт о производительности системы. Оптимизировать исключительно под синтетический бенчмарк, не отражающий реальный профиль трафика (например, тестировать только одинаковые лёгкие запросы, когда в production преобладают тяжёлые отчётные запросы).
- **Компромисс:** Подробное многометриковое нагрузочное тестирование с реалистичным профилем трафика даёт более достоверную картину, но требует значительных усилий на подготовку сценариев и инфраструктуры, а также времени на прогон (особенно soak-тесты). Быстрый микробенчмарк дешевле и даёт сигнал быстрее, но легко вводит в заблуждение относительно реального поведения под production-нагрузкой. Критерий выбора: для критичных по SLA систем оправдано регулярное, а не разовое нагрузочное тестирование с фиксацией условий прогона, чтобы результаты были сравнимы во времени и отражали реальные регрессии, а не шум окружения.

**Пример / кейс**
```python
from locust import HttpUser, task, between

class ApiUser(HttpUser):
    wait_time = between(0.1, 0.5)

    @task(3)
    def get_order(self):
        self.client.get("/orders/42")

    @task(1)
    def create_order(self):
        self.client.post("/orders", json={"items": [{"sku": "A1", "qty": 2}]})

# Отчёт locust фиксирует p50/p95/p99 задержки и % ошибок под заданным
# числом одновременных пользователей — это и есть предмет анализа,
# а не единственное число RPS.
```

### 330. [Q-03-06-0330] Как организовать тестовую инфраструктуру для multi-tenant backend-системы так, чтобы тесты были изолированы по данным разных клиентов (tenant) и не давали ложной уверенности из-за случайного совпадения тестовых данных между тенантами? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Тестирование backend-приложений: pytest, unittest, unit- и интеграционные тесты, фикстуры, моки, тестирование API и работа с тестовой базой данных<br>
**Уровень:** Senior

**Короткий ответ**<br>
Нужно явно моделировать multi-tenant изоляцию в тестах — создавать как минимум два разных тестовых тенанта в большинстве интеграционных тестов на чувствительных к изоляции путях и явно проверять, что данные/действия одного тенанта не видны и не влияют на другой, а не полагаться на то, что тестовые данные случайно не пересекаются из-за разных ID.

**Разбор**
- **Как это работает:** В зависимости от архитектуры multi-tenancy (общая БД с tenant_id в каждой таблице, отдельная схема на тенанта, или отдельная БД на тенанта) тест должен воспроизводить именно тот механизм разделения, который используется в production — если изоляция держится на фильтрации по tenant_id в каждом запросе, тест обязан проверить, что забытый фильтр в одном из запросов действительно приводит к падению теста, а не остаётся незамеченным.
- **На практике:** Эффективный паттерн — обязательный тестовый кейс «утечка между тенантами» для каждого нового эндпоинта, читающего данные по идентификатору: создать сущность у тенанта A, попытаться прочитать её с токеном/контекстом тенанта B и явно проверить отказ (404/403), а не просто успешный ответ для тенанта A в изоляции. Для схем/БД на тенанта тестовая инфраструктура должна уметь поднимать и мигрировать несколько тестовых тенантов параллельно без значительного роста времени прогона.
- **Частые ошибки:** Писать интеграционные тесты только с одним тестовым тенантом «по умолчанию», из-за чего баг отсутствия фильтрации по tenant_id в одном из запросов остаётся незамеченным, пока не проявится в production как утечка данных между клиентами. Использовать предсказуемые, одинаковые для всех тестов ID тенантов и сущностей, из-за чего тесты могут случайно «совпасть» по данным и скрыть реальную проблему изоляции.
- **Компромисс:** Полная изоляция с отдельной БД/схемой на тестовый тенант в каждом прогоне даёт самую высокую уверенность и ближе всего к production-архитектуре, но увеличивает время и сложность тестовой инфраструктуры, особенно при модели «отдельная БД на тенанта» в большом масштабе. Более лёгкая модель — общая тестовая БД с tenant_id и обязательными cross-tenant проверками в тестах — дешевле поддерживать, но зависит от дисциплины обязательно включать такие проверки в каждый новый тест. Критерий выбора: модель изоляции должна в тестах соответствовать реальной production-модели multi-tenancy, а объём обязательных cross-tenant тестов — зависеть от цены утечки данных между клиентами для конкретного продукта (например, выше для медицинских/финансовых данных).

**Пример / кейс**
```python
def test_user_cannot_read_order_from_another_tenant(api_client, tenant_a, tenant_b):
    order = create_order(tenant=tenant_a, total=100)

    response = api_client.get(
        f"/orders/{order.id}",
        headers={"X-Tenant-Id": tenant_b.id},  # запрос от имени другого тенанта
    )

    assert response.status_code == 404  # данные тенанта A не должны быть видны тенанту B
```
