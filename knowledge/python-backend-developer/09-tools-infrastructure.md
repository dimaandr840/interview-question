## Тема 9. Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка

### 441. [Q-03-09-0441] Объясните, что такое ветка (branch) в Git и зачем она нужна в повседневной работе команды. Чем отличается `git merge` от `git rebase` при объединении изменений?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
Ветка — это указатель на цепочку коммитов, позволяющий разрабатывать функциональность изолированно от основной линии; `merge` создаёт коммит слияния и сохраняет историю обеих веток, а `rebase` переносит коммиты поверх новой базы, делая историю линейной.

**Разбор**
- **Как это работает:** branch — лёгкий указатель (хеш последнего коммита), а не копия файлов; HEAD переключается между ветками. `merge` делает трёхстороннее слияние с общим предком; `rebase` переигрывает коммиты один за другим на новую базу.
- **На практике:** rebase используют для приватных feature-веток перед открытием PR, чтобы история была чистой; merge — для объединения в основную ветку, чтобы не терять контекст. Публичную ветку, от которой уже ответвились другие, rebase'ить нельзя.
- **Частые ошибки:** rebase общей ветки после того, как её запушили и другие от неё ответвились, — ломает историю у коллег; путают `git merge --squash` с обычным merge.

**Пример / кейс**
```bash
git checkout feature/orders
git fetch origin
git rebase origin/main          # переносит коммиты feature поверх актуального main
git push --force-with-lease

git checkout main
git merge --no-ff feature/orders   # сохраняет отдельный merge-коммит для истории
```

### 442. [Q-03-09-0442] Как вы обнаруживаете и разрешаете конфликт слияния в Git? Опишите шаги на примере текстового конфликта в файле.

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
Конфликт возникает, когда Git не может автоматически объединить изменения в одном и том же участке файла из двух веток; разрешение — открыть файл, выбрать нужные строки между маркерами `<<<<<<<`/`=======`/`>>>>>>>`, убрать маркеры, протестировать результат и закоммитить его.

**Разбор**
- **Как это работает:** при merge/rebase Git построчно сравнивает версии файла относительно общего предка; если один и тот же диапазон строк изменён в обеих ветках по-разному, автоматическое слияние невозможно, и Git вставляет конфликтные маркеры.
- **На практике:** нужно открыть файл, понять смысл обеих версий, собрать корректный итоговый код, удалить все маркеры, прогнать тесты/линтер, затем `git add <file>` и `git commit` (для merge) или `git rebase --continue`. `git status` подсказывает, какие файлы ещё в конфликте.
- **Частые ошибки:** закоммитить файл, не удалив маркеры конфликта; слепо брать «свою» или «чужую» версию через `git checkout --ours/--theirs` без проверки смысла; не запускать тесты после разрешения.

**Пример / кейс**
```text
<<<<<<< HEAD
def get_discount(user):
    return 0.1 if user.is_premium else 0
=======
def get_discount(user):
    return 0.15 if user.is_premium else 0.05
>>>>>>> feature/discounts
```
Нужно согласовать корректную бизнес-логику, оставить один вариант без маркеров, прогнать `pytest tests/test_discount.py`, затем `git add pricing.py && git commit`.

### 443. [Q-03-09-0443] Что такое виртуальное окружение в Python и почему не стоит устанавливать все зависимости проекта глобально?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
Виртуальное окружение — изолированный набор интерпретатора и пакетов для конкретного проекта, который не затрагивает системный Python и другие проекты; без него проекты с конфликтующими версиями одной библиотеки не могут нормально сосуществовать на одной машине.

**Разбор**
- **Как это работает:** `python -m venv .venv` создаёт отдельную директорию с собственным `site-packages`; при активации `PATH` и `sys.prefix` переключаются на этот каталог, поэтому `pip install` ставит пакеты именно туда.
- **На практике:** venv создают отдельно для каждого проекта, коммитят только список зависимостей, а сам каталог `.venv` добавляют в `.gitignore`. Для воспроизводимости на других машинах окружение пересоздают из файла зависимостей.
- **Частые ошибки:** установка пакетов глобально через `sudo pip install` — ломает системный Python и создаёт конфликты версий между проектами; забывают активировать venv и ставят пакет не туда.

**Пример / кейс**
```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -c "import sys; print(sys.prefix)"   # путь внутри .venv
deactivate
```

### 444. [Q-03-09-0444] Чем отличается `pip install flask` от записи `flask==2.3.3` в requirements.txt? Почему важно фиксировать версии зависимостей?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
`pip install flask` ставит последнюю доступную версию без гарантии, что завтра или на другой машине будет установлена та же версия, а `flask==2.3.3` фиксирует точную версию — это нужно для воспроизводимости сборок и предсказуемого поведения приложения в разных средах.

**Разбор**
- **Как это работает:** pip по умолчанию разрешает диапазон версий, совместимый с окружением, и может подтянуть новый релиз с изменённым поведением. Точная фиксация убирает эту неопределённость.
- **На практике:** в requirements.txt для приложений фиксируют точные версии всех зависимостей (через `pip freeze` или `pip-compile`), чтобы установка давала одинаковый набор пакетов в dev, CI и production. Для библиотек задают более широкие диапазоны.
- **Частые ошибки:** фиксировать только верхнеуровневые пакеты, не учитывая транзитивные зависимости; не обновлять версии годами, накапливая неисправленные уязвимости; путать назначение зависимостей приложения и переиспользуемой библиотеки.

**Пример / кейс**
```text
# без фиксации — риск несовпадения версий между машинами
flask

# с фиксацией — воспроизводимая сборка
flask==2.3.3
sqlalchemy==2.0.23
```

### 445. [Q-03-09-0445] Объясните разницу между Docker-образом (image) и контейнером (container). Как это соотносится с классами и объектами в программировании?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
Docker-образ — неизменяемый «шаблон» с файловой системой и метаданными приложения, а контейнер — запущенный экземпляр этого образа с собственным изолированным процессом; это похоже на отношение класса и объекта — образ — класс, контейнер — конкретный объект.

**Разбор**
- **Как это работает:** образ состоит из read-only слоёв, объединённых union-filesystem; при `docker run` Docker добавляет сверху записываемый слой и создаёт изолированный процесс с собственными namespace и cgroups.
- **На практике:** из одного образа можно запустить сколько угодно независимых контейнеров; изменения внутри контейнера не влияют на образ и теряются при удалении контейнера, если не вынесены в volume. Образ хранится в registry, контейнер — эфемерная рантайм-единица.
- **Частые ошибки:** хранить важные данные только в писаемом слое контейнера — при пересоздании они пропадают; путать `docker build` (создание образа) и `docker run` (создание и запуск контейнера).

**Пример / кейс**
```bash
docker build -t myapp:1.0 .
docker run -d --name app1 myapp:1.0
docker run -d --name app2 myapp:1.0
docker ps     # два независимых процесса на базе одного образа
```

### 446. [Q-03-09-0446] Зачем в Dockerfile сначала копируют requirements.txt и устанавливают зависимости, а потом копируют остальной код приложения? Что происходит, если сделать наоборот?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
Такой порядок позволяет Docker кэшировать слой с зависимостями и переустанавливать их только при изменении requirements.txt, а не при каждом изменении кода; если скопировать весь код сразу, любое изменение файла инвалидирует кэш и зависимости переустанавливаются заново.

**Разбор**
- **Как это работает:** Docker строит образ послойно и кэширует каждый слой по хешу инструкции и входных данных; если слой не изменился, Docker берёт его из кэша, иначе пересобирает его и все последующие слои.
- **На практике:** правильный порядок — `COPY requirements.txt .`, затем `RUN pip install`, и только потом `COPY . .`; тогда при правке `.py`-файла пересобирается только быстрый слой копирования кода.
- **Частые ошибки:** `COPY . .` одной командой в начале Dockerfile — любое изменение в коде инвалидирует кэш pip install и заставляет переустанавливать все пакеты при каждой сборке.

**Пример / кейс**
```dockerfile
FROM python:3.12-slim
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .
CMD ["gunicorn", "app:app", "--bind", "0.0.0.0:8000"]
```

### 447. [Q-03-09-0447] Что такое Continuous Integration и Continuous Delivery/Deployment? Какие шаги обычно входят в простой CI-пайплайн для Python-проекта?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
Continuous Integration — практика частого слияния изменений в общую ветку с автоматической проверкой на каждый коммит/PR; Continuous Delivery/Deployment — автоматизация доставки проверенного кода до staging (Delivery) или прямо до production (Deployment) без ручных шагов.

**Разбор**
- **Как это работает:** при пуше или открытии PR CI-система запускает pipeline — набор стадий, которые выполняются в изолированном окружении по описанию из YAML-файла конфигурации.
- **На практике:** типичный пайплайн: установка зависимостей → линтинг/типизация → тесты с покрытием → сборка Docker-образа → публикация образа и автодеплой. Каждая стадия должна давать понятный отчёт об ошибке.
- **Частые ошибки:** называть «непрерывным деплоем» процесс с обязательным ручным подтверждением (это Delivery, а не Deployment); не разделять быстрые и медленные проверки, из-за чего разработчики начинают игнорировать долгий пайплайн.

**Пример / кейс**
```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt
      - run: ruff check .
      - run: pytest --cov=app
```

### 448. [Q-03-09-0448] Приложение не может прочитать файл конфигурации на сервере и падает с PermissionError. Какие команды Linux вы используете, чтобы продиагностировать и исправить права доступа?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
Нужно сначала посмотреть владельца, группу и права файла командой `ls -l`, узнать, под каким пользователем запущен процесс, а затем выдать минимально необходимые права через `chmod`/`chown`, а не открывать файл «всем на запись».

**Разбор**
- **Как это работает:** у каждого файла есть владелец, группа и биты прав rwx для владельца, группы и остальных; процесс читает файл с правами того UID, от имени которого он запущен — это может быть не тот пользователь, что создавал файл.
- **На практике:** `ls -l config.yaml` покажет владельца и права, `ps -o user= -p <pid>` покажет, от чьего имени работает процесс; дальше либо `chown`, либо `chmod 640` (владелец читает/пишет, группа читает).
- **Частые ошибки:** «лечить» PermissionError через `chmod 777` — даёт запись и чтение всем пользователям системы, включая потенциально скомпрометированные процессы, что является дырой безопасности для файлов с секретами.

**Пример / кейс**
```bash
ls -l /etc/app/config.yaml
# -rw------- 1 root root 512 ... config.yaml

chown root:app_group /etc/app/config.yaml
chmod 640 /etc/app/config.yaml
usermod -aG app_group app_user
```

### 449. [Q-03-09-0449] Что такое WSGI и почему Flask/Django-приложение само по себе не запускают напрямую в production без дополнительного сервера типа Gunicorn?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
WSGI — стандартный синхронный интерфейс между Python-приложением и веб-сервером; встроенный dev-сервер однопоточен и не выдерживает нагрузку, поэтому перед приложением ставят WSGI-сервер (Gunicorn, uWSGI), умеющий управлять несколькими рабочими процессами и таймаутами.

**Разбор**
- **Как это работает:** WSGI описывает простой контракт — приложение это вызываемый объект `application(environ, start_response)`; любой WSGI-совместимый сервер может обслуживать любое WSGI-совместимое приложение.
- **На практике:** `flask run` удобен только для локальной разработки; в production запускают `gunicorn app:app --workers 4` — несколько процессов-воркеров обрабатывают запросы через WSGI-интерфейс приложения.
- **Частые ошибки:** запускать встроенный dev-сервер в production, игнорируя предупреждение «development server»; думать, что WSGI сам ускоряет приложение — он просто определяет интерфейс.

**Пример / кейс**
```bash
# НЕ для production:
flask run --host=0.0.0.0

# production:
gunicorn --workers 4 --bind 0.0.0.0:8000 app:app
```

### 450. [Q-03-09-0450] В чём принципиальная разница между WSGI и ASGI? Какой тип приложений требует ASGI-сервер?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
WSGI поддерживает только синхронную модель «один запрос — один вызов приложения», а ASGI поддерживает `async`/`await`, WebSocket и долгоживущие соединения, что необходимо для приложений на FastAPI, Starlette или Django Channels.

**Разбор**
- **Как это работает:** WSGI-приложение — синхронная функция, вызываемая один раз на запрос; ASGI-приложение — корутина с интерфейсом `scope`, `receive`, `send`, способная обрабатывать несколько сообщений за «соединение» без блокировки потока.
- **На практике:** ASGI нужен для WebSocket, Server-Sent Events или когда хочется обслуживать много I/O-bound соединений одним процессом. Для обычного CRUD-приложения выигрыш зависит от того, насколько код реально асинхронный.
- **Частые ошибки:** считать ASGI «быстрее WSGI» по умолчанию без учёта профиля нагрузки; пытаться запустить WSGI-приложение через ASGI-сервер без адаптера.

**Пример / кейс**
```python
# WSGI
def application(environ, start_response):
    start_response("200 OK", [("Content-Type", "text/plain")])
    return [b"Hello"]

# ASGI
async def app(scope, receive, send):
    await send({"type": "http.response.start", "status": 200,
                "headers": [(b"content-type", b"text/plain")]})
    await send({"type": "http.response.body", "body": b"Hello"})
```

### 451. [Q-03-09-0451] Зачем использовать модуль logging вместо print() для диагностики приложения в production? Какие уровни логирования вы знаете и когда их применять?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
`print()` всегда пишет в stdout без уровней и фильтрации, а `logging` поддерживает уровни важности (DEBUG, INFO, WARNING, ERROR, CRITICAL) и может отправлять сообщения сразу в несколько мест без изменения кода приложения.

**Разбор**
- **Как это работает:** logging построен на логгерах, обработчиках и уровнях; логгер фильтрует сообщения по уровню, а обработчики решают, куда их направить и в каком формате.
- **На практике:** DEBUG — подробности разработки; INFO — обычные события; WARNING — отклонение от штатного режима; ERROR — операция не выполнена; CRITICAL — сервис нерабочий. Настройку делают один раз в точке входа.
- **Частые ошибки:** разбрасывать `print()` по коду вместо logging — такие сообщения невозможно централизованно фильтровать, а в Gunicorn они перемешиваются в stdout; логировать как ERROR ожидаемую бизнес-ситуацию, создавая шум в алертах.

**Пример / кейс**
```python
import logging
logger = logging.getLogger(__name__)

def process_order(order_id):
    logger.info("Processing order %s", order_id)
    try:
        ...
    except PaymentError as exc:
        logger.error("Payment failed for order %s: %s", order_id, exc)
        raise
```

### 452. [Q-03-09-0452] Для чего нужен файл .gitignore? Что может пойти не так, если в репозиторий случайно закоммитить файл .env с паролями?

**Направление:** Python Backend Developer<br>

*.pyc
.env
*.log
dist/

### 453. [Q-03-09-0453] Почему секреты (пароли, API-ключи) не стоит хранить в коде или конфигурационных файлах, закоммиченных в репозиторий? Как обычно передают такие значения в приложение?

**Уровень:** Junior

**Короткий ответ**<br>
Секреты в коде, закоммиченном в репозиторий, доступны всем, у кого есть доступ к истории Git, и их почти невозможно надёжно удалить задним числом; поэтому значения передают через переменные окружения или секрет-хранилища (Vault, AWS Secrets Manager), которые приложение читает в runtime.

- **Частые ошибки:** хранить `.env` с продовыми секретами в репозитории «для удобства»; хардкодить пароль в settings.py «временно»; логировать переменные окружения целиком при дебаге.

**Пример / кейс**
```python
import os
DATABASE_URL = os.environ["DATABASE_URL"]
DEBUG = os.environ.get("DEBUG", "false").lower() == "true"
```

### 454. [Q-03-09-0454] Что такое docker-compose и для чего он используется при локальной разработке backend-приложения, которому нужна база данных?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Junior

**Короткий ответ**<br>
docker-compose — инструмент для описания и запуска нескольких связанных контейнеров (приложение, PostgreSQL, Redis) одной командой из единого YAML-файла; он решает проблему локальной разработки, когда приложению нужна инфраструктура, которую неудобно поднимать вручную.

**Разбор**
- **Как это работает:** `docker-compose.yml` описывает набор сервисов, их образы, переменные окружения, порты и volume, а также сеть, в которой контейнеры видят друг друга по имени сервиса; `docker compose up` строит и запускает все сервисы с учётом зависимостей.

**Пример / кейс**
```yaml
services:
  web:
    build: .
    ports: ["8000:8000"]
    environment:
      DATABASE_URL: postgresql://app:app@db:5432/app
    depends_on: [db]
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```

### 455. [Q-03-09-0455] В команде из 6 разработчиков часто возникают конфликты и запутанная история в Git. Как бы вы организовали стратегию работы с ветками и правила rebase/merge, чтобы снизить количество конфликтов и сохранить читаемую историю?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
Помогает модель с короткоживущими feature-ветками от общей main, обязательным rebase перед PR для чистой истории и squash-merge при приёме PR, чтобы в основной ветке был один логический коммит на фичу; конкретная модель зависит от частоты релизов и числа параллельно поддерживаемых версий.

**Разбор**
- **Как это работает:** короткоживущие ветки снижают вероятность конфликтов, потому что меньше расхождение с main накапливается за время их жизни; squash-merge убирает «шумные» промежуточные коммиты и упрощает `git bisect`/revert на уровне фич.
- **На практике:** вводят правило «ветка живёт не больше N дней», требуют rebase на актуальный main перед ревью, фиксируют чеклист в PR-шаблоне; для команд с частыми релизами предпочтительнее trunk-based с feature flags вместо долгоживущих release-веток.
- **Частые ошибки:** вводить сложную модель (GitFlow с develop/release/hotfix) для команды с частыми мелкими релизами — добавляет накладные расходы без выгоды; разрешать прямые push в main без ревью, обесценивая саму стратегию.

**Пример / кейс**
```text
main (защищённая, только через PR)
 ├─ feature/order-refunds   (живёт 1-2 дня, rebase на main перед PR)
 ├─ feature/rate-limiting
 └─ fix/null-pointer-checkout

Правило репозитория: branch protection на main —
обязательный зелёный CI + минимум 1 approve + squash merge.
```

### 456. [Q-03-09-0456] После релиза обнаружился баг, который появился где-то в последних 50 коммитах, но непонятно в каком именно. Как использовать `git bisect` для поиска проблемного коммита? Когда уместно применять `git cherry-pick`?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
`git bisect` автоматизирует бинарный поиск: вы помечаете известный «хороший» и «плохой» коммит, а Git последовательно предлагает промежуточные коммиты для тестирования, сужая диапазон за логарифмическое число шагов; `git cherry-pick` уместен, когда нужно перенести один конкретный коммит (например, hotfix) в другую ветку без слияния всей истории.

**Разбор**
- **Как это работает:** `git bisect start`, затем `bad`/`good` на границах диапазона; Git чекаутит средний коммит, вы отмечаете результат — за ~log2(50)≈6 итераций находится первый плохой коммит. `git bisect run <script>` автоматизирует это при наличии автоматического теста.
- **На практике:** перед bisect нужен надёжный тест, однозначно отличающий «баг есть» от «бага нет»; cherry-pick удобен для hotfix в несколько веток, но при частом использовании на много коммитов лучше рассмотреть merge/rebase.
- **Частые ошибки:** bisect без чистого критерия (баг то воспроизводится, то нет из-за флакующего теста) даёт неверный результат; cherry-pick коммита, зависящего от других неперенесённых коммитов — ведёт к ошибкам сборки.

**Пример / кейс**
```bash
git bisect start
git bisect bad HEAD
git bisect good v1.4.0
git bisect run pytest tests/test_regression.py::test_order_total
git bisect reset

git checkout release/1.5
git cherry-pick a1b2c3d
```

### 457. [Q-03-09-0457] Чем lock-файл (poetry.lock, Pipfile.lock или requirements.txt, сгенерированный pip-compile) отличается от файла с верхнеуровневыми зависимостями (pyproject.toml)? Как воспроизводимость сборки связана с этими файлами?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
pyproject.toml описывает желаемые, часто диапазонные версии прямых зависимостей, а lock-файл фиксирует точный, полностью разрешённый набор версий всех зависимостей, включая транзитивные, вместе с хешами — это гарантирует, что установка на любой машине даёт одинаковое окружение.

**Разбор**
- **Как это работает:** при добавлении зависимости resolver решает задачу совместимости версий по всему дереву и записывает результат в lock-файл; при установке по lock-файлу resolver уже не нужен — пакеты ставятся по зафиксированным версиям и хешам.
- **На практике:** в репозиторий коммитят оба файла: pyproject.toml читают люди, lock-файл перегенерируют командой и тоже коммитят, чтобы CI и прод использовали именно его. Конфликт версий resolver обнаруживает на этапе lock.
- **Частые ошибки:** редактировать lock-файл руками — при следующей регенерации изменения потеряются; не коммитить lock-файл, полагаясь на диапазоны в pyproject.toml — разные установки могут получить разные версии транзитивных пакетов.

**Пример / кейс**
```toml
[tool.poetry.dependencies]
python = "^3.12"
fastapi = "^0.110"
```
```bash
poetry lock
poetry install --sync
```

### 458. [Q-03-09-0458] Образ Python-приложения получился 1.5 ГБ и долго собирается/деплоится. Как с помощью multi-stage build и выбора базового образа уменьшить размер итогового Docker-образа?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
Multi-stage build позволяет использовать «тяжёлый» этап с компиляторами для сборки зависимостей, а в финальный образ скопировать только готовые артефакты на «тонкий» базовый образ, не включая инструменты сборки и кэш pip, которые не нужны в runtime.

**Разбор**
- **Как это работает:** в Dockerfile можно объявить несколько стадий `FROM ... AS builder`, а в финальной стадии командой `COPY --from=builder` забрать только нужные файлы; промежуточные слои не попадают в итоговый образ.
- **На практике:** особенно полезно для зависимостей с C-расширениями, требующих компилятор — он нужен только на этапе установки; финальный образ на базе `slim`/`alpine` получается значительно меньше и с меньшей поверхностью атаки.
- **Частые ошибки:** копировать в финальную стадию весь `/usr`; выбирать alpine без проверки совместимости — musl libc может конфликтовать с пакетами, собранными под glibc.

**Пример / кейс**
```dockerfile
FROM python:3.12 AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --target=/install -r requirements.txt

FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /install /usr/local/lib/python3.12/site-packages
COPY . .
CMD ["gunicorn", "app:app", "--bind", "0.0.0.0:8000"]
```

### 459. [Q-03-09-0459] При обновлении деплоя контейнеры с приложением убиваются по SIGKILL, и часть HTTP-запросов обрывается с ошибками у клиентов. Как правильно организовать graceful shutdown процесса в контейнере по сигналу SIGTERM?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
Нужно обрабатывать SIGTERM, дожидаясь завершения уже принятых запросов и закрывая соединения с БД/брокером, прежде чем процесс завершится, а оркестратор должен давать приложению достаточный grace period перед принудительным SIGKILL.

- **Как это работает:** при остановке контейнера Docker/Kubernetes сначала отправляет SIGTERM и ждёт grace period, затем присылает SIGKILL; Gunicorn/Uvicorn по умолчанию умеют корректно обрабатывать SIGTERM, переставая принимать новые соединения и ожидая завершения текущих.

**Пример / кейс**
```yaml
services:
  web:
    build: .
    stop_grace_period: 30s
```
```bash
gunicorn app:app --workers 4 --graceful-timeout 25 --timeout 30
```

**Уровень:** Middle

**Короткий ответ**<br>
Разумный пайплайн: установка зависимостей (с кэшем) → линтинг/типизация и unit-тесты параллельно → сборка Docker-образа с кэшированием слоёв → сканирование образа на уязвимости → публикация в registry; кэширование экономит минуты на каждом запуске.

**Разбор**
- **Как это работает:** CI-системы кэшируют директории между запусками по ключу (хеш lock-файла); для Docker используют registry cache или BuildKit cache mount, чтобы не пересобирать неизменившиеся слои на «холодном» раннере.
- **На практике:** линтинг и тесты не зависят друг от друга и могут идти параллельно, сокращая общее время; сборку образа логично запускать после прохождения тестов, но можно параллелить со сканированием, если образ собирается долго.

**Пример / кейс**
```yaml
jobs:
  test:
    steps:
      - uses: actions/cache@v4
        with:
          path: ~/.cache/pip
          key: pip-${{ hashFiles('requirements.txt') }}
      - run: pip install -r requirements.txt
      - run: pytest
  build:
    needs: test
    steps:
      - uses: docker/build-push-action@v5
        with:
          cache-from: type=registry,ref=myrepo/app:cache
          cache-to: type=registry,ref=myrepo/app:cache,mode=max
```

### 461. [Q-03-09-0461] Чем canary-развёртывание отличается от blue-green? В каком случае вы выберете один подход, а в каком — другой, для backend-сервиса с базой данных?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
Blue-green разворачивает новую версию параллельно со старой и переключает весь трафик одним разом с быстрым откатом переключением обратно, а canary постепенно направляет небольшую долю трафика на новую версию; canary выбирают, когда важно обнаружить проблему на малой доле пользователей, blue-green — когда нужен быстрый простой откат «всё или ничего».

**Разбор**
- **Как это работает:** blue-green требует двух полных независимых окружений и механизма переключения на уровне роутинга; canary требует более тонкого контроля трафика и системы мониторинга, способной сравнить метрики с baseline.
- **На практике:** для сервиса с БД нужно продумать обратную совместимость схемы между старой и новой версией в обоих подходах, так как они одновременно читают/пишут одни таблицы; canary лучше ограничивает blast radius для рискованных изменений, blue-green подходит для хорошо протестированных изменений с важной скоростью релиза.
- **Частые ошибки:** считать canary автоматически «безопаснее» без настроенных метрик и критериев остановки; забывать, что blue-green не защищает от проблем, вызванных несовместимой миграцией БД, применённой до переключения.

**Пример / кейс**
```text
Blue-green:
  blue (v1, 100%) ── green (v2, 0%, прогрет)
  → переключение роутера: blue 0% / green 100%
  → откат за секунды

Canary:
  v1: 95%, v2: 5%
  → мониторинг error rate/latency v2 относительно v1 15 минут
  → 5% → 25% → 100%
```

Сначала находят проблемный процесс и его потоки через `top -H`/`htop`, смотрят, что делает процесс на уровне системных вызовов через `strace -p <pid>`, или профилируют код через `py-spy dump`/`py-spy top`, которые показывают стек вызовов работающего процесса без его остановки.

- **Как это работает:** `top -H` показывает загрузку CPU по отдельным потокам; `strace` трассирует системные вызовы, показывая, не крутится ли процесс в busy-loop без I/O (признак чистого CPU-bound цикла в коде). `py-spy` — внешний сэмплирующий профилировщик, читающий стек CPython-процесса из памяти.
- **На практике:** если `strace` не показывает системных вызовов продолжительное время — проблема скорее в самом коде (бесконечный цикл, неэффективный алгоритм, regex с катастрофическим backtracking); `py-spy dump -p <pid>` сразу укажет конкретную функцию.
- **Частые ошибки:** пытаться подключить обычный debugger, требующий перезапуска процесса, к упавшему в 100% CPU production-процессу; смотреть только агрегированный CPU процесса без разбивки по потокам.

**Пример / кейс**
```bash
top -H -p <pid>
strace -f -p <pid> -c -T
py-spy dump --pid <pid>
```

### 463. [Q-03-09-0463] Сервис приложения запущен как systemd unit и периодически перезапускается. Как посмотреть причину перезапуска и настроить unit-файл, чтобы сервис корректно перезапускался при сбое, но не попадал в бесконечный restart loop?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
Причину смотрят через `journalctl -u <service> --since "1 hour ago"` и `systemctl status <service>`; чтобы не попасть в бесконечный restart loop, настраивают `Restart=on-failure` вместе с `StartLimitBurst`/`StartLimitIntervalSec`, которые останавливают попытки после N неудач за интервал.

**Пример / кейс**
```ini

StartLimitIntervalSec=60
StartLimitBurst=5
```

### 464. [Q-03-09-0464] Как вы выбираете количество worker-процессов и их тип при запуске FastAPI-приложения через `gunicorn -k uvicorn.workers.UvicornWorker`? От чего зависит это число для CPU-bound и I/O-bound нагрузки?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
Для CPU-bound нагрузки число воркеров выбирают близким к числу ядер (формула `2*CPU+1` как отправная точка), а для I/O-bound асинхронного приложения важнее, что один event loop может обслуживать много соединений без блокировки, поэтому большое число воркеров не ускоряет ожидание внешних сервисов.

**Разбор**
- **Как это работает:** каждый UvicornWorker — отдельный процесс с собственным event loop; GIL не даёт параллельно исполнять байткод Python в потоках одного процесса, поэтому параллелизм для CPU-bound ограничен числом процессов.
- **На практике:** начинают с `workers = CPU_cores` и нагрузочно тестируют с реалистичным профилем; для смешанной нагрузки тяжёлые вычисления выносят в отдельные процессы (Celery), а не раздувают число ASGI-воркеров.
- **Частые ошибки:** ставить огромное число воркеров на машине с малым числом ядер — приводит к избыточному потреблению памяти и конкуренции за CPU; не учитывать, что блокирующий вызов внутри async-обработчика блокирует весь event loop одного воркера независимо от общего числа воркеров.

**Пример / кейс**
```bash
gunicorn app:app -k uvicorn.workers.UvicornWorker --workers 5 --bind 0.0.0.0:8000
# для 4-ядерной машины: 2*4+1 = 9 как отправная точка для CPU-bound
```

### 465. [Q-03-09-0465] Чем отличаются типы worker'ов Gunicorn sync, gthread и gevent? В каком случае синхронный Django-сервис с медленными внешними HTTP-вызовами выиграет от перехода на gevent-воркеры, а в каком — нет?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
`sync` — один запрос на воркер, блокируется на любом I/O; `gthread` — несколько потоков на воркер; `gevent` — кооперативная многозадачность через monkey-patching блокирующих вызовов, позволяющая держать тысячи ожидающих соединений, но требующая совместимости всех используемых библиотек.

**Разбор**
- **Как это работает:** sync блокируется до завершения запроса; gthread позволяет другому потоку работать, пока один ждёт I/O (отпуская GIL); gevent патчит стандартную библиотеку так, что блокирующие вызовы становятся неблокирующими greenlet-переключениями.
- **На практике:** переход на gevent/gthread выгоден, когда узкое место — ожидание сети; выигрыша не будет, если узкое место — CPU-bound вычисления (GIL всё равно не даёт параллельно исполнять Python-код), и возможны баги, если используются C-расширения, не совместимые с monkey-patching.
- **Частые ошибки:** включить gevent без проверки совместимости зависимостей — получают труднодиагностируемые «подвисания»; считать, что gevent решит проблему CPU-bound нагрузки.

**Пример / кейс**
```bash
gunicorn app:app --workers 4 --worker-class sync

pip install gevent
gunicorn app:app --workers 4 --worker-class gevent --worker-connections 1000
```

### 466. [Q-03-09-0466] Как организовать структурированное логирование (JSON-логи) с correlation id/request id, чтобы можно было сквозно проследить один запрос через несколько сервисов и слоёв приложения?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
На входе генерируют или подхватывают request id, кладут его в контекст логирования (`contextvars`) и передают дальше в заголовках при межсервисных вызовах; каждая запись лога формируется в JSON с этим id, что позволяет в системе агрегации отфильтровать все записи одного запроса по всем сервисам.

**Разбор**
- **Как это работает:** middleware на входе проверяет заголовок или генерирует UUID, сохраняет в `contextvars.ContextVar`, доступный во всех корутинах обработки запроса; фильтр логирования добавляет значение из контекста в каждую запись.
- **На практике:** JSON-формат даёт возможность индексировать поля (request_id, user_id, duration_ms) и строить дашборды/алерты по ним; при вызове другого сервиса request id передают в заголовке, чтобы его подхватил downstream-сервис.
- **Частые ошибки:** генерировать request id на каждом сервисе независимо, не передавая его дальше; использовать `threading.local` в асинхронном коде вместо `contextvars` — один поток обслуживает множество конкурентных задач, и `threading.local` не изолирует их корректно.

**Пример / кейс**
```python
import contextvars, logging, uuid

request_id_var = contextvars.ContextVar("request_id", default="-")

class RequestIdFilter(logging.Filter):
    def filter(self, record):
        record.request_id = request_id_var.get()
        return True

async def request_id_middleware(request, call_next):
    rid = request.headers.get("X-Request-ID", str(uuid.uuid4()))
    request_id_var.set(rid)
    response = await call_next(request)
    response.headers["X-Request-ID"] = rid
    return response
```

### 467. [Q-03-09-0467] Какие вы добавите метрики Prometheus (counter, gauge, histogram) в Python backend-сервис, чтобы отслеживать его здоровье и производительность? Приведите конкретные примеры метрик.

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
Типичный набор: counter `http_requests_total` для количества запросов и ошибок, histogram `http_request_duration_seconds` для latency с перцентилями, gauge `db_connection_pool_in_use` для занятости пула соединений, и бизнес-метрики типа counter `orders_created_total`.

**Разбор**
- **Как это работает:** counter — монотонно растущее значение, удобно для вычисления rate() за интервал; gauge — произвольно растущее/убывающее текущее значение; histogram распределяет наблюдения по бакетам и позволяет вычислять перцентили через `histogram_quantile`.
- **На практике:** latency лучше измерять histogram, а не average — среднее скрывает длинный хвост медленных запросов; по counter с лейблом status считают error rate для алертов SLO; gauge пула соединений помогает заметить приближение к исчерпанию до таймаутов.

**Пример / кейс**
```python
from prometheus_client import Counter, Histogram, Gauge

REQUESTS = Counter("http_requests_total", "Total HTTP requests", ["method", "path", "status"])
LATENCY = Histogram("http_request_duration_seconds", "Request latency", ["path"])
POOL_IN_USE = Gauge("db_connection_pool_in_use", "Connections currently in use")

@LATENCY.labels(path="/orders").time()
def handle_orders_request():
    REQUESTS.labels(method="GET", path="/orders", status="200").inc()
```

### 468. [Q-03-09-0468] При rolling deployment старая и новая версия приложения работают одновременно некоторое время, а вам нужно также применить миграцию базы данных, которая переименовывает колонку. Как спланировать порядок деплоя кода и миграции, чтобы не было downtime и ошибок?

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Middle

**Короткий ответ**<br>
Нужно разбить изменение на обратно совместимые шаги: сначала миграция, добавляющая новую колонку без удаления старой, затем код, пишущий в обе колонки, затем полный rollout нового кода, использующего новую колонку, и только позже отдельная миграция, удаляющая старую — подход expand-contract.

**Разбор**
- **Как это работает:** при rolling deploy одновременно работают старая и новая версия, обращаясь к одной БД; прямое переименование одной атомарной миграцией сломает либо старые, либо новые инстансы, поэтому изменение схемы и кода разносят по времени.
- **На практике:** шаги: 1) миграция добавляет новую колонку; 2) код пишет в обе колонки; 3) полный rollout кода, читающего только новую; 4) отдельная более поздняя миграция удаляет старую колонку, когда откат на предыдущий код уже не понадобится.
- **Частые ошибки:** переименование одной миграцией одновременно с новым кодом — часть реплик упадёт с ошибками о несуществующей колонке; слишком быстро удалять старую колонку, не оставив времени на экстренный откат.

**Пример / кейс**
```sql
ALTER TABLE orders ADD COLUMN customer_email_new VARCHAR(255);
-- новый код пишет в обе колонки, старый код продолжает работать с customer_email
-- после полного rollout и подтверждения стабильности, отдельным релизом:
ALTER TABLE orders DROP COLUMN customer_email;
```

Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Senior

**Короткий ответ**<br>
Для 40 инженеров с несколькими параллельными релизами жизнеспособны и trunk-based с feature flags (минимизирует merge-боль, требует зрелой CI/CD), и схема с release-ветками на каждую поддерживаемую версию плюс строгий процесс cherry-pick hotfix'ов (даёт изоляцию релизов, но увеличивает нагрузку на слияние); выбор зависит от числа одновременно поддерживаемых в production версий.

**Разбор**
- **Как это работает:** trunk-based держит одну главную ветку, в которую непрерывно мержатся маленькие изменения, скрытые за feature flags; это требует сильного автоматического тестирования, так как main должен быть постоянно готов к релизу. - **Частые ошибки:** внедрять trunk-based без зрелой культуры feature flags и быстрого CI — получают нестабильный main; выбирать классический GitFlow для команды с ежедневными релизами «по традиции», не оценивая, что модель создавалась для редких дискретных релизов.
- **Компромисс:** trunk-based снижает merge-overhead, но перекладывает риск на дисциплину тестирования и управление feature flags (технический долг от забытых флагов); release-ветки дают предсказуемую изоляцию версий, но создают операционную нагрузку на синхронизацию фиксов. Критерий выбора — число одновременно поддерживаемых версий и зрелость автоматизированного тестирования.

**Пример / кейс**

hotfix: обычный PR в main + ускоренный деплой

### 470. [Q-03-09-0470] Вы переносите набор Python backend-сервисов в Kubernetes и должны задать requests/limits по CPU/памяти и настроить horizontal pod autoscaling. Какие риски несёт как недооценка, так и переоценка лимитов, и как выбрать политику автоскейлинга для сервиса с неравномерной нагрузкой? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Senior

**Короткий ответ**<br>
Недооценка лимитов приводит к OOMKill или CPU throttling под нагрузкой, переоценка — к неэффективному использованию кластера и более высоким затратам; для неравномерной нагрузки разумно сочетать консервативные requests под реальный baseline с запасом в limits и настраивать HPA с учётом времени прогрева новых подов, возможно с кастомными метриками, а не только CPU.

**Разбор**
- **Как это работает:** `requests` резервируется планировщиком при размещении пода, `limits` — верхняя граница, при превышении которой по памяти под получает OOMKill, по CPU — throttling через cgroups; HPA по умолчанию масштабируется по доле использования CPU относительно requests.cpu, поэтому неверный requests искажает решения автоскейлера.
- **На практике:** requests задают на основе измерений под реалистичной нагрузкой; для скачкообразной нагрузки учитывают время холодного старта новых подов в поведении HPA, иначе всплеск обгонит скорость автоскейлинга; для сервисов с внешним ограничением (пул соединений к БД) масштабирование по CPU может упереться в лимит БД раньше, чем в лимит CPU.
- **Частые ошибки:** ставить limits сильно выше requests «на всякий случай» — даёт поду захватить много ресурсов ноды и вызвать noisy neighbor; настраивать HPA только по CPU для сервиса, узкое место которого — память или внешние соединения.
- **Компромисс:** точная настройка требует профилирования и может быстро устареть при изменении трафика — операционные издержки против риска инцидентов от грубой оценки; выбор между CPU-based HPA и кастомными метриками зависит от того, какая метрика реально коррелирует с перегрузкой, и от сложности внедрения адаптера метрик.

**Пример / кейс**
```yaml
resources:
  requests: { cpu: "250m", memory: "256Mi" }
  limits:   { cpu: "500m", memory: "512Mi" }
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
  behavior:
    scaleUp: { stabilizationWindowSeconds: 30 }
```

**Разбор**

- **Частые ошибки:** хранить продовые секреты как обычные переменные, доступные любому workflow, включая PR внешних контрибьюторов; использовать сторонние Actions по мутируемому тегу; логировать переменные окружения целиком при дебаге.

Критерий выбора — чувствительность данных, нормативные требования и зрелость команды безопасности.

### 472. [Q-03-09-0472] Система из 12 микросервисов на Python должна получить распределённую трассировку запросов через OpenTelemetry. Как вы спроектируете схему трассировки (propagation, context, sampling rate) с учётом объёма данных и стоимости хранения трасс? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Senior

**Короткий ответ**<br>
Схема должна передавать context через W3C Trace Context заголовки между всеми сервисами и применять sampling — например, 100% для ошибок и медленных запросов, но лишь небольшой процент для обычных успешных; точный процент зависит от объёма трафика и бюджета на хранение.

**Разбор**
- **Как это работает:** OpenTelemetry SDK создаёт spans в каждом сервисе; context propagation передаёт trace id и флаг сэмплирования в заголовках следующего вызова — решение принимается либо один раз на входе (head-based), либо коллектором после сбора всех spans (tail-based, требующий буферизации).
- **На практике:** head-based проще и дешевле, но может не засэмплировать редкую важную ошибку; tail-based через Collector с политикой «сохранить трассу при ошибке или высокой latency» даёт лучшую видимость, но требует дополнительной инфраструктуры.
- **Частые ошибки:** включить 100% сэмплирование «чтобы видеть всё» без расчёта объёма хранения — быстро становится неподъёмным; не передавать context через асинхронные брокеры сообщений, разрывая трассировку на границе очереди.
- **Компромисс:** высокий процент сэмплирования даёт полную видимость, но дорог в хранении; низкий процент дешевле, но рискует упустить редкие инциденты без tail-based правил. Выбор между head- и tail-based зависит от готовности держать отдельный Collector-слой и бюджета на инфраструктуру.

**Пример / кейс**
```yaml
processors:
  tail_sampling:
    policies:
      - name: errors-always
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow-requests
        type: latency
        latency: { threshold_ms: 500 }
      - name: baseline-rate
        type: probabilistic
        probabilistic: { sampling_percentage: 5 }
```

### 473. [Q-03-09-0473] Команда предлагает перевести крупное синхронное Django-приложение на ASGI и асинхронные view, ожидая кратного роста производительности. Какие риски и скрытые ограничения (блокирующие вызовы ORM, сторонние синхронные библиотеки, смешанный код) нужно оценить перед таким переходом? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Senior

**Короткий ответ**<br>
Главный риск — скрытые блокирующие вызовы (синхронный ORM, сторонние SDK без async-версии), которые при наивном переносе блокируют весь event loop и снижают, а не повышают производительность; реальный выигрыш появляется только если весь путь запроса действительно асинхронный, а нагрузка преимущественно I/O-bound.

**Разбор**
- **Как это работает:** Django с 3.1+ поддерживает async view и ASGI, но исторический ORM синхронный — вызов внутри `async def view` без `sync_to_async` выбросит ошибку либо, при обёртке, выполнится в отдельном потоке, что добавляет overhead переключения, а не даёт истинного ускорения.
- **На практике:** нужен аудит всех внешних вызовов на пути запроса — для каждого найти async-альтернативу или вынести в `sync_to_async`; миграцию делают постепенно, view за view, с нагрузочным тестированием каждого изменённого участка.
- **Частые ошибки:** переводить view в `async def`, оставляя внутри синхронные блокирующие вызовы без оборачивания — замедляет обработку для всех одновременных запросов; ожидать кратного роста для CPU-bound логики, где async не даёт параллелизма вычислений.
- **Компромисс:** полный переход с переписыванием критического пути даёт потенциальный выигрыш при высокой I/O-bound конкурентности, но требует значительных трудозатрат и риска регрессий; выборочный переход самых нагруженных I/O-bound эндпоинтов снижает риск, но не даёт системного выигрыша. Критерий выбора — доля I/O-bound нагрузки и ресурсы на полноценное async-покрытие пути запроса.

**Пример / кейс**
```python
# Намеренно показан антипаттерн при наивном переносе:
async def get_order(request, order_id):
    order = Order.objects.get(id=order_id)   # ОШИБКА: блокирующий вызов в event loop
    return JsonResponse({"id": order.id})

# Корректный промежуточный вариант:
from asgiref.sync import sync_to_async

async def get_order(request, order_id):
    order = await sync_to_async(Order.objects.get)(id=order_id)
    return JsonResponse({"id": order.id})
```

### 474. [Q-03-09-0474] Production-сервис начал отдавать 50% ошибок 504 Gateway Timeout в течение 20 минут, затем сам восстановился. У вас есть логи приложения, метрики Prometheus и трассировки запросов. Как вы по шагам восстановите хронологию инцидента и напишете постмортем с конкретными action items? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Senior

**Короткий ответ**<br>
Восстановление начинают с метрик (когда начался рост latency/error rate и что предшествовало), сужают через логи ошибок за этот период и трассировки конкретных запросов, затем формулируют точную последовательность событий, корневую причину и конкретные action items с владельцами и сроками.

- **Как это работает:** метрики дают общую картину «что» и «когда»; логи дают «что конкретно пошло не так» на уровне исключений; трассировки показывают «где в цепочке вызовов» возникла задержка — вместе они восстанавливают причинно-следственную цепочку, а не только симптом.

- **Частые ошибки:** писать постмортем с причиной, указывающей на человека, а не на процесс; ограничиваться action item без конкретики; не фиксировать точный интервал инцидента и показатели.
- **Компромисс:** глубокое расследование с привлечением нескольких команд даёт точную корневую причину, но занимает больше времени; быстрый поверхностный разбор даёт результат быстро, но рискует повторением по той же скрытой причине. Критерий выбора глубины — тяжесть и частота повторения инцидентов и доступность данных.

### 475. [Q-03-09-0475] Релизное окно ограничено двумя часами, а изменение включает несовместимую миграцию схемы БД (удаление колонки) вместе с новой версией кода. Как спроектировать процесс деплоя и план откатa (rollback), чтобы минимизировать риск необратимых проблем в этом окне? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Инструменты и инфраструктура: Git, зависимости, Docker, CI/CD, Linux, ASGI/WSGI, развёртывание, логи, метрики и трассировка<br>
**Уровень:** Senior

**Короткий ответ**<br>
Безопаснее разделить изменение на expand-contract и отложить физическое удаление колонки за пределы окна, либо, если удаление необходимо сейчас, заранее подготовить явный план откатa с восстановлением колонки из бэкапа — откат кода без откатa данных не восстанавливает удалённые данные.

**Разбор**
- **Как это работает:** откат кода не откатывает миграцию схемы автоматически; если миграция уже удалила колонку, откат на версию, которая её ожидает, приведёт к ошибкам на уровне БД, а не к восстановлению работоспособности — rollback кода и rollback схемы нужно синхронизировать явно.
- **На практике:** для жёсткого окна разумно не выполнять удаление в это же окно — только добавление нового и перенос чтения/записи; если удаление обязательно сейчас, заранее делают бэкап таблицы и готовят протестированный на staging скрипт восстановления с измеренным временем, укладывающимся в окно.
- **Частые ошибки:** полагаться только на `git revert` и повторный деплой как на «план Б» для несовместимой миграции без проверки совместимости данных; не тестировать сам процесс восстановления заранее на staging.
- **Компромисс:** expand-contract резко снижает риск потери данных, но не выполняет удаление в заявленный срок; немедленное удаление с подготовленным восстановлением выполняет задачу в срок, но требует подготовительной работы и несёт остаточный риск, если restore займёт больше времени, чем на staging. Критерий выбора — жёсткость дедлайна, объём данных и наличие протестированного процесса восстановления.

**Пример / кейс**
```sql
-- Безопасный для окна вариант: только расширение, без удаления
ALTER TABLE users ADD COLUMN email_normalized VARCHAR(255);
-- удаление старой колонки переносится на отдельный релиз после стабильности

-- Если удаление обязательно в это окно — заранее:
-- 1) pg_dump --table=users перед миграцией
-- 2) протестированный на staging скрипт восстановления колонки из бэкапа
-- 3) чеклист: "если за 40 минут после деплоя error rate не стабилизировался — restore из бэкапа"
```
