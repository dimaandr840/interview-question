### 401. [Q-03-08-0401] Что такое профилирование кода и чем оно отличается от точечных замеров времени через time.time()?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Профилирование — это автоматизированный сбор статистики по всей программе (сколько раз вызвана каждая функция и сколько времени она заняла), а ручные замеры time.time() показывают время только в тех местах, где их явно расставили.

**Разбор**
- **Как это работает:** Профилировщик (например, cProfile) инструментирует вызовы функций на лету и строит таблицу: число вызовов, суммарное время внутри функции (tottime), время с учётом вложенных вызовов (cumtime). Это даёт полную картину без ручной разметки кода.
- **На практике:** Профилирование запускают перед оптимизацией, чтобы не тратить время на ускорение кода, который и так быстрый. Для коротких скриптов достаточно cProfile, для долгоживущих сервисов — сэмплирующие профилировщики с меньшим overhead.
- **Частые ошибки:** Начинают оптимизировать код по интуиции, не измерив, где реально тратится время; забывают, что профилирование само по себе замедляет выполнение и искажает абсолютные цифры (относительные пропорции обычно показательны).

**Пример / кейс**
```python
import cProfile

def slow_function():
    total = sum(i * i for i in range(10**6))
    return total

cProfile.run("slow_function()")
# Вывод содержит столбцы ncalls, tottime, cumtime для каждой функции —
# по ним видно, где реально тратится время, а не только итоговую длительность.
```
### 402. [Q-03-08-0402] Почему проверка `x in collection` может быть быстрой или медленной в зависимости от типа коллекции, и как это связано со сложностью алгоритма?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Проверка вхождения в list выполняется за O(n), потому что требует последовательного перебора, а в set или dict — в среднем за O(1) благодаря хеш-таблице, поэтому для больших коллекций set значительно быстрее.

**Разбор**
- **Как это работает:** list хранит элементы последовательно, и `in` сравнивает искомое значение с каждым элементом по очереди, пока не найдёт совпадение или не дойдёт до конца. set и dict используют хеш-таблицу: по хешу значения сразу вычисляется бакет, где оно должно лежать.
- **На практике:** Если в коде есть цикл с проверкой `if x in big_list`, суммарная сложность становится O(n*m), что на больших объёмах данных приводит к заметным замедлениям; замена list на set для таких проверок — одна из самых дешёвых оптимизаций.
- **Частые ошибки:** Используют list для частых проверок вхождения просто потому, что порядок элементов кажется важным, не замечая, что для самой проверки порядок не нужен; путают сложность списка и множества, считая обе структуры одинаково быстрыми «потому что обе встроенные».

**Пример / кейс**
```python
import timeit

big_list = list(range(100_000))
big_set = set(big_list)

t_list = timeit.timeit(lambda: 99_999 in big_list, number=1000)
t_set = timeit.timeit(lambda: 99_999 in big_set, number=1000)
print(t_list, t_set)
# t_list на несколько порядков больше t_set — наглядное подтверждение O(n) vs O(1)
```
### 403. [Q-03-08-0403] Как работает functools.lru_cache и в каких случаях его применение может навредить?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
lru_cache запоминает результаты вызовов функции по её аргументам и возвращает сохранённый результат при повторном вызове с теми же аргументами, но подходит только для чистых функций с хешируемыми аргументами и ограниченным набором входных значений.

**Разбор**
- **Как это работает:** Декоратор хранит словарь «аргументы → результат» и вытесняет записи по принципу LRU после достижения maxsize; повторный вызов с уже виденными аргументами возвращает значение из кэша без выполнения тела функции.
- **На практике:** Полезен для дорогих детерминированных вычислений (например, парсинг конфигурации, построение неизменяемых структур) с небольшим количеством уникальных комбинаций аргументов; maxsize нужно подбирать осознанно, а не оставлять unbounded.
- **Частые ошибки:** Применяют lru_cache к функциям с побочными эффектами или недетерминированным результатом (текущее время, случайные числа, сетевые вызовы с изменяющимися данными); забывают, что аргументы должны быть хешируемыми (list или dict как аргумент вызовет ошибку); кэш на уровне модуля в веб-приложении может расти неограниченно и утекать память при maxsize=None.

**Пример / кейс**
```python
from functools import lru_cache

@lru_cache(maxsize=256)
def parse_config_section(section_name: str) -> dict:
    # дорогая, но детерминированная операция
    return {"section": section_name, "parsed": True}

parse_config_section("db")      # выполнится и закэшируется
parse_config_section("db")      # вернётся мгновенно из кэша
# parse_config_section({"a": 1})  # TypeError: unhashable type: dict
```
### 404. [Q-03-08-0404] Чем генератор отличается от списка с точки зрения потребления памяти, и когда стоит выбрать генератор?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Генератор вычисляет и отдаёт элементы по одному лениво, не храня всю последовательность в памяти, тогда как список сразу материализует все элементы; генератор предпочтителен, когда данные обрабатываются последовательно и целиком в памяти не нужны.

**Разбор**
- **Как это работает:** Generator expression или функция с yield создают итератор, который на каждом шаге вычисляет следующее значение и сохраняет только текущее состояние, а не весь набор данных.
- **На практике:** При построчной обработке большого файла или потоковой выдаче результатов из API генератор позволяет не загружать весь датасет в память; но если нужно несколько проходов по данным или индексированный доступ, список подходит лучше.
- **Частые ошибки:** Используют list comprehension там, где данные читаются один раз и сразу суммируются/фильтруются, из-за чего программа упирается в память на больших объёмах; пытаются повторно итерироваться по уже исчерпанному генератору, получая пустой результат без ошибки.

**Пример / кейс**
```python
# Список: все 10**8 значений материализуются в памяти сразу
total_list = sum([x * x for x in range(10**8)])

# Генератор: значения вычисляются и отбрасываются по одному
total_gen = sum(x * x for x in range(10**8))
# Оба варианта дают одинаковый результат, но первый расходует
# на порядки больше памяти — проверяется через tracemalloc или resource.getrusage
```
### 405. [Q-03-08-0405] Почему пароли нельзя хранить в базе данных в открытом виде, и чем хеширование с солью лучше простого MD5/SHA-256 от пароля?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Хранение пароля в открытом виде или через быстрый хеш без соли делает базу уязвимой к мгновенной компрометации всех учётных записей при утечке; специализированные алгоритмы (bcrypt, argon2) с солью и настраиваемой стоимостью вычислений делают подбор пароля экономически невыгодным.

**Разбор**
- **Как это работает:** Соль — случайная строка, уникальная для каждого пользователя, добавляемая к паролю перед хешированием, что делает бесполезными заранее посчитанные радужные таблицы. bcrypt/argon2 дополнительно намеренно медленные и настраиваемые по «cost factor», в отличие от MD5/SHA-256, которые проектировались быстрыми.
- **На практике:** В Python для этого используют библиотеки passlib, bcrypt или встроенные механизмы фреймворка (Django использует PBKDF2/argon2 по умолчанию); соль генерируется автоматически и хранится вместе с хешем в одной строке.
- **Частые ошибки:** Пишут собственную схему хеширования «для скорости»; сравнивают хеши через обычный `==` вместо constant-time сравнения, что теоретически открывает timing-атаку; хранят пароли в логах при отладке.

**Пример / кейс**
```python
import bcrypt

password = b"super-secret-password"
hashed = bcrypt.hashpw(password, bcrypt.gensalt())
# hashed уже содержит соль внутри строки, отдельно хранить её не нужно

assert bcrypt.checkpw(b"super-secret-password", hashed) is True
assert bcrypt.checkpw(b"wrong-password", hashed) is False
```
### 406. [Q-03-08-0406] Чем аутентификация отличается от авторизации, и можно ли считать, что успешный логин автоматически даёт доступ ко всем ресурсам?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Аутентификация отвечает на вопрос «кто ты» (подтверждение личности), авторизация — «что тебе разрешено» (права доступа к конкретным действиям и данным); успешный логин сам по себе не гарантирует доступ ни к одному защищённому ресурсу без отдельной проверки прав.

**Разбор**
- **Как это работает:** Аутентификация проверяет учётные данные (пароль, токен, сертификат) и подтверждает, что пользователь — тот, за кого себя выдаёт. Авторизация выполняется отдельно на каждом защищённом эндпоинте и сверяет роль/права аутентифицированного пользователя с требуемыми для операции.
- **На практике:** В веб-API это обычно два отдельных слоя middleware: один декодирует и проверяет токен (authn), другой проверяет, например, что пользователь — владелец ресурса или имеет нужную роль (authz); пропуск второго слоя — частая причина уязвимостей вроде IDOR.
- **Частые ошибки:** Проверяют только валидность токена и забывают проверить, что именно этому пользователю разрешено запрошенное действие (например, изменить чужой заказ по ID из URL); путают HTTP-коды 401 (не аутентифицирован) и 403 (аутентифицирован, но не авторизован).

**Пример / кейс**
```http
GET /orders/777 HTTP/1.1
Authorization: Bearer <валидный токен пользователя A>

HTTP/1.1 403 Forbidden
Content-Type: application/json

{"error": "Токен валиден (authn пройден), но заказ 777 принадлежит другому пользователю (authz отклонён)"}
```
### 407. [Q-03-08-0407] Из каких частей состоит JWT-токен, и что произойдёт, если изменить payload токена, не зная секретного ключа подписи?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
JWT состоит из трёх частей — header, payload и signature, закодированных в base64url и разделённых точками; изменение payload без пересчёта подписи корректным секретным ключом приведёт к несовпадению подписи, и сервер должен отклонить такой токен как невалидный.

**Разбор**
- **Как это работает:** Header описывает алгоритм подписи, payload содержит claims (например, user_id, роль, срок действия exp), signature — это HMAC или цифровая подпись от header+payload с использованием секретного (или приватного) ключа. Любой может декодировать base64 и прочитать payload — JWT не шифрует данные, а только подписывает.
- **На практике:** На сервере обязательна проверка подписи и срока действия при каждом запросе; в payload нельзя класть секретные данные (пароли, полные номера карт), так как они читаемы без ключа; важно также не допускать алгоритм «none» в заголовке — это известная уязвимость некоторых библиотек.
- **Частые ошибки:** Путают подпись с шифрованием и кладут чувствительные данные в payload; не проверяют exp и alg на сервере; хранят JWT в localStorage без понимания риска XSS-кражи токена.

**Пример / кейс**
```python
import base64, json

token = "eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyX2lkIjo0Mn0.sign_here"
header_b64, payload_b64, signature = token.split(".")

def pad(s):
    return s + "=" * (-len(s) % 4)

payload = json.loads(base64.urlsafe_b64decode(pad(payload_b64)))
print(payload)  # {'user_id': 42} — читается без секретного ключа и без проверки подписи
# Подмена payload без пересчёта подписи правильным секретом даст сигнатуру,
# не совпадающую при проверке на сервере -> токен отклоняется
```
### 408. [Q-03-08-0408] Что такое SQL-инъекция и почему приведённый ниже код уязвим?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
SQL-инъекция — это внедрение произвольного SQL-кода через непроверенный пользовательский ввод, который подставляется в запрос как часть текста; код уязвим, потому что формирует SQL-строку через f-string вместо параметризованного запроса.

**Разбор**
- **Как это работает:** Если ввод пользователя напрямую вставляется в текст SQL-запроса, атакующий может передать фрагмент, который изменит логику запроса (например, добавит `OR 1=1` или завершит запрос и начнёт новый).
- **На практике:** Защита — параметризованные запросы (placeholders), где драйвер БД сам экранирует значения и никогда не интерпретирует их как часть SQL-синтаксиса; ORM вроде SQLAlchemy/Django ORM по умолчанию параметризует запросы, но raw SQL и `text()` всё ещё можно использовать небезопасно.
- **Частые ошибки:** Считают, что экранирование кавычек вручную достаточно безопасно; доверяют «внутренним» данным без параметризации; используют f-строки/`%`-форматирование для построения SQL с пользовательским вводом.

**Пример / кейс**
```python
# Пример намеренно уязвимого кода:
username = request.args["username"]
query = f"SELECT * FROM users WHERE username = '{username}'"
cursor.execute(query)
# username = "' OR '1'='1" вернёт всех пользователей вместо одного

# Безопасный вариант — параметризованный запрос:
query = "SELECT * FROM users WHERE username = %s"
cursor.execute(query, (username,))
```
### 409. [Q-03-08-0409] Что такое XSS-атака, и как шаблонизатор вроде Jinja2 помогает защититься от неё по умолчанию?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
XSS (межсайтовый скриптинг) — внедрение вредоносного JavaScript в страницу через непроверенный пользовательский ввод, который браузер жертвы затем выполняет; Jinja2 по умолчанию автоматически экранирует HTML-спецсимволы при выводе переменных в шаблон, превращая потенциальный тег `<script>` в безопасный текст.

**Разбор**
- **Как это работает:** Автоэкранирование заменяет символы `<`, `>`, `&`, `\"` на HTML-сущности перед вставкой в разметку, поэтому введённая пользователем строка отображается как текст, а не исполняется как HTML/JS.
- **На практике:** Автоэкранирование защищает только вывод непосредственно в HTML-тело; при выводе в атрибуты, JavaScript-блоки или через `|safe`/`Markup` защита отключается, и такие места нужно проверять особенно внимательно; дополнительно помогает заголовок Content-Security-Policy.
- **Частые ошибки:** Отключают автоэкранирование (`|safe`) для пользовательского контента «чтобы форматирование работало»; считают, что XSS актуален только для фронтенда, хотя backend отвечает за корректный рендеринг шаблонов и заголовки безопасности; не экранируют данные, вставляемые в JSON, встроенный в HTML.

**Пример / кейс**
```text
{# comment содержит: <script>alert(1)</script> #}

Безопасно (автоэкранирование включено):
{{ comment }}
--> &lt;script&gt;alert(1)&lt;/script&gt;  (отображается как текст, не выполняется)

Уязвимо (защита намеренно отключена):
{{ comment | safe }}
--> <script>alert(1)</script>  (выполнится в браузере жертвы)
```
### 410. [Q-03-08-0410] Почему секреты (пароли от БД, API-ключи) принято хранить в переменных окружения, а не прямо в коде приложения?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>

**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
CORS (Cross-Origin Resource Sharing) — это механизм браузера, который по умолчанию запрещает JavaScript на одном домене читать ответ от сервера на другом домене, если сервер явно не разрешил это через заголовки Access-Control-Allow-*.

**Разбор**
- **Как это работает:** Браузер сравнивает origin (схема+домен+порт) страницы и запрашиваемого ресурса; если они различаются, для «небезопасных» запросов сначала отправляется preflight-запрос методом OPTIONS, и только при наличии правильных CORS-заголовков в ответе браузер разрешает JS-коду получить доступ к телу ответа.
- **На практике:** Сам факт блокировки CORS не защищает сервер от прямых запросов (curl, другой сервер) — это защита именно браузерных сценариев от чтения чужих данных чужим JS-кодом; backend должен явно настроить разрешённые origin, методы и заголовки, а не использовать `*` вместе с credentials.
- **Частые ошибки:** Путают CORS с общей защитой API и считают, что настройка CORS защищает от неавторизованных вызовов; ставят Access-Control-Allow-Origin: * вместе с Access-Control-Allow-Credentials: true, что браузеры вообще запрещают.

**Пример / кейс**
```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Authorization, Content-Type
# Preflight OPTIONS-запрос браузер отправит автоматически перед основным
# запросом с методом PUT/DELETE или нестандартными заголовками
```
### 412. [Q-03-08-0412] Что такое rate limiting и как клиент должен понять, что превысил допустимую частоту запросов к API?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Rate limiting — это ограничение количества запросов от одного клиента за промежуток времени для защиты сервиса от перегрузки и злоупотреблений; при превышении лимита сервер обычно отвечает статусом 429 Too Many Requests с заголовком Retry-After.

**Разбор**
- **Как это работает:** Сервер (или прокси/API-gateway перед ним) считает количество запросов от идентификатора клиента (IP, API-ключ, user id) за окно времени и отклоняет запросы сверх установленного порога, не передавая их в основную бизнес-логику.
- **На практике:** Лимиты стоит делать отдельными для разных типов операций (например, чтение и создание ресурсов) и возвращать клиенту заголовки с текущим состоянием лимита (X-RateLimit-Remaining, Retry-After), чтобы клиент мог корректно повторить запрос позже.
- **Частые ошибки:** Ограничивают только по IP, что ломается за NAT или CDN (много пользователей — один IP) и обходится через множество IP у атакующего; не возвращают понятный статус и заголовки, из-за чего клиенты не понимают, что делать при отказе.

**Пример / кейс**
```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0

{"error": "rate limit exceeded, retry after 30 seconds"}
```
### 413. [Q-03-08-0413] Зачем backend-приложению использовать HTTPS вместо обычного HTTP, если данные и так передаются во внутренней сети?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
HTTPS (HTTP поверх TLS) шифрует трафик между клиентом и сервером и подтверждает подлинность сервера через сертификат, защищая от перехвата и подмены данных (man-in-the-middle), включая пароли, токены и cookie, которые при обычном HTTP передаются открытым текстом.

**Разбор**
- **Как это работает:** При установке соединения TLS стороны согласуют алгоритмы шифрования и обмениваются ключами с проверкой сертификата сервера через цепочку доверия (CA), после чего весь последующий трафик шифруется симметричным ключом сессии.
- **На практике:** Даже во «внутренней» сети компании устройства могут быть скомпрометированы, а трафик может проходить через промежуточные прокси или общую облачную инфраструктуру, поэтому TLS применяют и для внутренних сервисов (mTLS между микросервисами); для внешнего API HTTPS обязателен без исключений.
- **Частые ошибки:** Считают, что HTTPS нужен только для публичных сайтов с формами оплаты; оставляют редирект с HTTP на HTTPS единственной защитой, забывая заголовок HSTS, который запрещает браузеру вообще обращаться по HTTP повторно.

**Пример / кейс**
```yaml
# nginx (упрощённо)
server:
  listen: 80
  return: 301 https://$host$request_uri
---
server:
  listen: 443 ssl
  add_header: "Strict-Transport-Security: max-age=63072000; includeSubDomains"
```
### 414. [Q-03-08-0414] Зачем приложению пул соединений с базой данных вместо открытия нового соединения на каждый запрос?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Установка соединения с БД — относительно дорогая операция (TCP-хендшейк, аутентификация, настройка сессии), и открытие нового соединения на каждый запрос резко увеличивает задержку и нагрузку на БД; пул поддерживает заранее открытые соединения и переиспользует их между запросами.

**Разбор**
- **Как это работает:** Пул создаёт и хранит ограниченное число живых соединений; при обращении из кода соединение берётся из пула, используется и возвращается обратно, а не закрывается физически, что устраняет повторные затраты на установку соединения.
- **На практике:** Размер пула подбирают с учётом числа воркеров приложения и лимитов самой БД на одновременные соединения (max_connections в PostgreSQL); слишком большой пул может исчерпать лимиты БД при масштабировании нескольких инстансов приложения.
- **Частые ошибки:** Забывают возвращать соединение в пул (не закрывают курсор/сессию в блоке finally или контекстном менеджере), из-за чего пул исчерпывается под нагрузкой; создают новый пул на каждый запрос вместо одного общего на процесс/приложение.

**Пример / кейс**
```python
from sqlalchemy import create_engine

engine = create_engine(
    "postgresql://user:pass@localhost/db",
    pool_size=10,
    max_overflow=5,
)

with engine.connect() as conn:  # соединение берётся из пула и возвращается автоматически
    conn.execute(text("SELECT 1"))
```
### 415. [Q-03-08-0415] Что произойдёт, если выполнить HTTP-запрос к внешнему сервису через библиотеку requests без указания timeout, и почему это опасно?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Без явного timeout запрос через requests может ждать ответа неограниченно долго, если внешний сервис завис или сеть деградировала, что приводит к зависанию обрабатывающего потока/воркера и, при повторении у многих запросов, к исчерпанию ресурсов приложения.

**Разбор**
- **Как это работает:** По умолчанию у requests нет таймаута на соединение и чтение ответа, поэтому запрос физически может висеть до разрыва соединения операционной системой, что происходит далеко не сразу и не гарантированно.
- **На практике:** Timeout стоит задавать явно и раздельно для connect и read (`timeout=(3, 10)`), а поведение при истечении таймаута — оборачивать в обработку исключения requests.Timeout и, при необходимости, повторные попытки с ограниченным числом ретраев и экспоненциальной задержкой.

**Пример / кейс**
```python
import requests

try:
    response = requests.get(
        "https://external-service.example.com/api",
        timeout=(3, 10),  # 3с на коннект, 10с на чтение ответа
    )
    response.raise_for_status()
except requests.exceptions.Timeout:
    logger.warning("external service timed out")
    raise
```

**Уровень:** Junior

**Короткий ответ**<br>
Принцип наименьших привилегий требует выдавать приложению только права, необходимые для его работы (SELECT/INSERT/UPDATE/DELETE на нужных таблицах), чтобы при компрометации приложения ущерб был ограничен, а не распространялся на всю базу данных, включая возможность удалять таблицы или читать чужие схемы.

**Разбор**
- **Как это работает:** В большинстве СУБД можно создать отдельного пользователя/роль с ограниченным набором грантов на конкретные таблицы и операции, отдельно от учётной записи администратора, используемой для миграций и обслуживания.

**Пример / кейс**
```sql
-- учётная запись для приложения: только нужные операции на нужных таблицах
GRANT SELECT, INSERT, UPDATE, DELETE ON orders, order_items TO app_user;

-- отдельная учётная запись для миграций, не используемая самим приложением
GRANT ALL PRIVILEGES ON SCHEMA public TO migration_user;
```
### 417. [Q-03-08-0417] Как профилировать производительность Python-сервиса прямо в production, не перезапуская процесс и не внося заметных задержек в обработку запросов?

**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Для production используют сэмплирующие профилировщики, которые подключаются к уже запущенному процессу извне и периодически снимают стек вызовов (например, py-spy), а не инструментирующие профилировщики вроде cProfile, которые перехватывают каждый вызов функции и создают существенный overhead.

- **Как это работает:** Сэмплирующий профилировщик с заданной частотой (например, 100 Гц) читает текущий стек вызовов процесса, не изменяя байткод и не добавляя накладных расходов на каждый вызов; статистически по множеству сэмплов восстанавливается, где процесс проводит больше всего времени.

- **Частые ошибки:** Включают cProfile в production без ограничения по времени и трафику, что заметно замедляет обработку запросов; делают выводы по одному короткому снятому профилю, не учитывая, что нагрузка и узкие места могут отличаться в разное время суток.

**Пример / кейс**
```bash

# результат — флейм-график (SVG), где ширина блока функции
# пропорциональна доле времени, которое процесс провёл в ней за 30 секунд
```

### 418. [Q-03-08-0418] В логах ORM-приложения на эндпоинт, отдающий список из 50 заказов с товарами, уходит более 150 SQL-запросов. Как диагностировать и исправить такую проблему?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Это классическая проблема N+1: один запрос получает список заказов, а затем для каждого заказа отдельно выполняется запрос на связанные товары; решение — заранее подгрузить связанные данные одним или несколькими запросами через select_related/prefetch_related (Django) или joinedload/selectinload (SQLAlchemy).

**Разбор**
- **Как это работает:** ORM по умолчанию делает ленивую загрузку связей — обращение к order.items внутри цикла инициирует отдельный запрос к БД на каждой итерации, вместо того чтобы получить все нужные данные заранее.
- **На практике:** Для диагностики включают логирование SQL-запросов ORM или инструмент вроде django-debug-toolbar/SQLAlchemy echo, видят повторяющийся однотипный запрос с разными ID; для связей «один ко многим» уместнее prefetch_related/selectinload (отдельный запрос с IN), для «многие к одному» — select_related/joinedload (JOIN в одном запросе).
- **Частые ошибки:** Добавляют select_related ко всем связям без разбора, что увеличивает объём одного запроса и может создать декартово произведение при нескольких связях «многие»; исправляют проблему точечно в одном месте кода, не проверяя, что та же модель используется в других эндпоинтах с тем же паттерном доступа.

**Пример / кейс**
```python
# Проблема: N+1 запрос
orders = Order.objects.all()
for order in orders:
    print(order.customer.name)   # отдельный SELECT на каждой итерации
    for item in order.items.all():  # ещё по одному SELECT на заказ
        print(item.name)

# Исправление: JOIN для связи "многие к одному" + отдельный IN-запрос для "один ко многим"
orders = Order.objects.select_related("customer").prefetch_related("items")
```

**Уровень:** Middle

**Короткий ответ**<br>
RBAC реализуют через явную модель данных «пользователь → роль → разрешения», где проверка прав на каждом защищённом эндпоинте сверяет набор разрешений текущей роли пользователя с разрешением, требуемым для конкретного действия, а не хардкодит список ролей внутри каждого обработчика.

**Разбор**
- **Как это работает:** В БД хранятся роли (admin, manager, viewer) и связанные с ними разрешения (create_order, delete_user и т.д.), пользователь может иметь одну или несколько ролей; при запросе middleware или декоратор проверяет, есть ли у набора разрешений пользователя нужное разрешение для запрошенной операции.
- **На практике:** Разрешения стоит делать достаточно гранулярными для реальных бизнес-сценариев, но не чрезмерно детальными; для сложных случаев, когда доступ зависит ещё и от владения ресурсом, RBAC дополняют проверкой на уровне объекта (object-level permission), а не только роли.
- **Частые ошибки:** Хардкодят проверки вида `if user.role == "admin"` в десятках мест кода, из-за чего добавление новой роли требует правок по всему коду; путают роль с разрешением, выдавая слишком широкую роль там, где нужно одно конкретное действие; забывают проверить права на уровне API при наличии проверки только в UI.

```python
            if permission_name not in request.user.role.permissions:
                return Response(status=403)
            return view_func(request, *args, **kwargs)
        return wrapper
    return decorator

@require_permission("delete_order")

    ...
```

**Короткий ответ**<br>
Логируют структурированные события с явным списком полей, а не произвольные объекты целиком, применяют маскирование известных чувствительных полей (пароль, токен, номер карты) на уровне логирующего слоя, и исключают из логов сырые тела запросов с персональными данными или маскируют идентифицирующую часть.

- **Как это работает:** В логирующий pipeline добавляют фильтр или процессор, который проходит по словарю логируемых полей и заменяет значения по списку ключей-паттернов (password, token, authorization, card_number) на маску вроде ***, прежде чем запись попадёт в обработчик вывода.
- **На практике:** Удобно логировать структурированные события (structlog, python-json-logger) с заранее определённым набором полей вместо logger.info(str(request_object)), что снижает риск случайно залогировать весь объект запроса целиком вместе с заголовком Authorization; для персональных данных email/телефон можно частично маскировать.

```python
SENSITIVE_KEYS = {"password", "token", "authorization", "card_number"}

                k: "***" if k.lower() in SENSITIVE_KEYS else v
                for k, v in record.args.items()
            }
        return True
```

**Короткий ответ**<br>
Клиент передаёт уникальный идемпотентный ключ (idempotency key) на операцию, а сервер при получении запроса с уже обработанным ключом возвращает сохранённый результат первой обработки вместо повторного выполнения бизнес-логики.

- **Как это работает:** Сервер хранит таблицу «idempotency_key → статус и результат операции»; при поступлении запроса сначала атомарно проверяется и резервируется ключ (например, через уникальный индекс в БД с транзакцией), и если ключ уже существует и операция завершена — возвращается сохранённый ответ без повторного списания.

- **Частые ошибки:** Реализуют идемпотентность только «по смыслу» (проверяют, нет ли уже такого заказа по сумме и времени), что ненадёжно при параллельных запросах; не защищают саму проверку и резервирование ключа от гонки между двумя одновременными запросами с одним ключом, из-за чего обе обработки всё равно проходят.

- **Как это работает:** requests задаёт гарантированные ресурсы для планирования пода, а limits — жёсткий потолок; при превышении лимита памяти ядро Linux (через cgroups) убивает процесс немедленно, без возможности корректно освободить ресурсы, в отличие от превышения лимита CPU, которое приводит к троттлингу, а не к убийству процесса.
- **На практике:** Лимит памяти стоит выставлять с запасом поверх наблюдаемого p95/p99 потребления под реальной нагрузкой, а не «на глаз»; для многопроцессных серверов (несколько воркеров Gunicorn в одном контейнере) суммарное потребление растёт с числом воркеров, и лимит должен учитывать их все.
- **Частые ошибки:** Ставят limits.memory равным requests без запаса, из-за чего любой временный всплеск нагрузки вызывает перезапуск; не отличают OOMKilled контейнера от обычного исключения MemoryError внутри Python — это разные механизмы (первый уровня ОС/cgroups, второй — уровня интерпретатора).

**Пример / кейс**
```yaml

    memory: "256Mi"
    cpu: "250m"
  limits:
    memory: "512Mi"   # запас над наблюдаемым p99 потребления под нагрузкой
    cpu: "500m"
# kubectl describe pod <name> покажет:
# Last State: Terminated, Reason: OOMKilled
```
### 429. [Q-03-08-0429] Как спроектировать безопасную загрузку файлов, которые пользователи прикрепляют к своим профилям, если backend сохраняет их на диск сервера?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Нужно проверять реальный тип содержимого файла по сигнатуре (а не доверять расширению или Content-Type из запроса), ограничивать максимальный размер, генерировать собственное безопасное имя файла на сервере вместо использования присланного имени, и хранить файлы вне корня веб-сервера с ограниченными правами исполнения.

**Разбор**
- **Как это работает:** Расширение и Content-Type в запросе полностью контролируются клиентом и могут быть подделаны, поэтому тип файла стоит дополнительно проверять по сигнатуре содержимого (magic bytes); присланное имя файла может содержать ../ для path traversal, поэтому сервер генерирует собственное уникальное имя (UUID), а оригинальное имя сохраняет отдельно только как метаданные.
- **На практике:** Для изображений дополнительно полезно перекодировать файл через библиотеку обработки изображений, что уничтожает потенциально вредоносный полезный код, встроенный не по спецификации формата; каталог с загруженными файлами не должен давать право на исполнение.
- **Частые ошибки:** Проверяют только расширение файла (.jpg, .png), пропуская файл с вредоносным содержимым и переименованным расширением; сохраняют файл по оригинальному имени без санитизации, допуская перезапись системных файлов через path traversal; не ограничивают размер загрузки.

**Пример / кейс**
```python
import uuid, imghdr

MAX_SIZE = 5 * 1024 * 1024  # 5 MB

def save_uploaded_avatar(file_bytes: bytes) -> str:
    if len(file_bytes) > MAX_SIZE:
        raise ValueError("file too large")
    kind = imghdr.what(None, h=file_bytes)  # проверка по сигнатуре, не по расширению
    if kind not in ("jpeg", "png"):
        raise ValueError("unsupported file type")
    safe_name = f"{uuid.uuid4().hex}.{kind}"
    with open(f"/var/app/uploads/{safe_name}", "wb") as f:
        f.write(file_bytes)
    return safe_name  # оригинальное имя пользователя не используется как путь
```
### 430. [Q-03-08-0430] Как реализовать вход через стороннего провайдера (например, Google) по протоколу OAuth2/OpenID Connect, и зачем нужен параметр state в этом потоке?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Middle

**Короткий ответ**<br>
В Authorization Code Flow backend перенаправляет пользователя на провайдера, получает обратно одноразовый код авторизации на заранее зарегистрированный redirect_uri и обменивает его на токены на сервере; параметр state — случайное значение, которое backend генерирует перед редиректом и проверяет при возврате, что защищает от CSRF-атаки на сам процесс логина.

**Разбор**
- **Как это работает:** Backend сохраняет сгенерированный state (например, в сессии пользователя), отправляет пользователя на провайдера с этим state, провайдер возвращает его без изменений вместе с кодом авторизации на redirect_uri, и backend сверяет полученный state с сохранённым, прежде чем продолжить обмен кода на токены.
- **На практике:** Обмен authorization code на access/id-токен должен происходить на backend напрямую с провайдером (server-to-server) с использованием client_secret, а не в браузере; для публичных клиентов (SPA, мобильные приложения) без возможности хранить secret используют PKCE вместо client_secret.
- **Частые ошибки:** Пропускают проверку state, что открывает возможность login CSRF; доверяют данным из id_token без проверки его подписи, издателя (iss), аудитории (aud) и срока действия; хранят client_secret на фронтенде вместо backend.

**Пример / кейс**
```text
1. Backend генерирует state=random_abc, сохраняет в сессии
2. Редирект пользователя:
   GET https://accounts.google.com/o/oauth2/v2/auth?client_id=...&redirect_uri=...&state=random_abc
3. Провайдер возвращает:
   GET /callback?code=auth_code_xyz&state=random_abc
4. Backend сверяет state из запроса со state из сессии -> совпадает -> продолжает
5. Backend обменивает code на access_token/id_token напрямую с провайдером (server-to-server)
```

### 432. [Q-03-08-0432] Приложение использует cookie-based сессии для аутентификации. Как защититься от CSRF-атаки, когда сторонний сайт отправляет запрос от имени залогиненного пользователя?

**Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Основная защита — CSRF-токен, уникальный для сессии пользователя, который сервер требует в теле или заголовке каждого изменяющего состояние запроса (POST/PUT/DELETE) и сверяет с токеном, привязанным к сессии; дополнительно cookie сессии стоит выставлять с атрибутом SameSite=Lax или Strict.

**Разбор**
- **Как это работает:** Браузер автоматически прикладывает cookie к любому запросу на домен сессии, даже инициированному со стороннего сайта, поэтому один факт наличия валидной cookie не доказывает, что запрос инициирован самим пользователем через легитимный интерфейс; CSRF-токен передаётся не через cookie, а отдельно (скрытое поле формы, заголовок), и сторонний сайт не может его узнать из-за политики same-origin.

- **Частые ошибки:** Защищают CSRF-токеном только часть изменяющих эндпоинтов, оставляя «забытые» POST-формы уязвимыми; полагаются только на SameSite cookie, не учитывая, что Lax всё ещё пропускает top-level GET-навигацию; путают CSRF-защиту с CORS, хотя это разные механизмы для разных сценариев атак.

**Пример / кейс**
```http
<form method="POST" action="/transfer">
  <input type="hidden" name="csrf_token" value="a1b2c3...">
  ...
</form>

```

**Уровень:** Senior

**Короткий ответ**<br>
Выбор зависит от того, что важнее для конкретной системы — простота масштабирования без разделяемого состояния (JWT), возможность мгновенного отзыва доступа и единая точка контроля (серверные сессии), или защита самого межсервисного взаимодействия от скомпрометированной сети (mTLS); на практике для внешних клиентов и внутреннего трафика часто используют разные механизмы одновременно.

**Разбор**
- **Как это работает:** Stateless JWT проверяется каждым сервисом локально по подписи без обращения к центральному хранилищу, что снижает задержку, но отзыв конкретного токена до истечения срока требует дополнительного механизма. - **На практике:** Внешним клиентам обычно выдают короткоживущий JWT (access token) плюс серверный refresh-токен, что сочетает низкую задержку для частых запросов и возможность отзыва через инвалидацию refresh-токена; между внутренними сервисами поверх уже аутентифицированного пользовательского запроса добавляют mTLS или service mesh для защиты от бокового перемещения при компрометации одного сервиса.

- **Компромисс:** Stateless JWT даёт низкую задержку и независимость от доступности центрального сервиса, но усложняет немедленный отзыв доступа и увеличивает риск при утечке долгоживущего токена; серверные сессии дают мгновенный контроль ценой дополнительной задержки и единой точки отказа; выбор зависит от требований к скорости отзыва доступа (регуляторные требования), ожидаемой нагрузки на сервис сессий и готовности команды поддерживать инфраструктуру PKI для mTLS.

**Пример / кейс**
```text

Gateway проверяет подпись JWT и пробрасывает запрос дальше.

  сертификат сервиса A подтверждает, что запрос пришёл именно от сервиса A,
  даже если сеть между подами потенциально доступна другим нагрузкам в кластере.

```

Нужно выбрать алгоритм и уровень ограничения (per-IP, per-account, per-API-key, поведенческий анализ) под конкретный профиль трафика: простые алгоритмы (fixed window) дёшевы, но грубы и дают всплески на границах окна; скользящее окно или token bucket точнее, но дороже по вычислениям и состоянию при высокой нагрузке; одного универсального порога часто недостаточно против распределённой атаки.

**Разбор**
- **Как это работает:** Fixed window считает запросы в фиксированных интервалах и обнуляет счётчик на границе, что даёт эффект всплеска (burst) на стыке окон; sliding window и token bucket сглаживают эту проблему ценой необходимости хранить больше состояния (временные метки запросов или текущее число токенов) в быстром хранилище вроде Redis, что увеличивает нагрузку при очень высоком трафике.
- **На практике:** Для защиты от распределённых атак per-IP недостаточно — добавляют лимиты по API-ключу/аккаунту и поведенческий анализ (резкий рост необычных паттернов запросов, нетипичная география), а для легитимных пользователей вводят более мягкие меры при первом превышении (задержка, капча) вместо немедленной блокировки.
- **Частые ошибки:** Усиливают лимиты только по одному измерению (IP), не замечая, что это бьёт по легитимным пользователям за NAT/VPN и не останавливает атаку с множества IP; выбирают дорогой точный алгоритм без оценки его стоимости на масштабе; не разделяют лимиты по критичности эндпоинтов.
- **Компромисс:** Более точные алгоритмы (sliding window, token bucket с детальным состоянием) снижают ложные блокировки легитимных пользователей, но увеличивают нагрузку на инфраструктуру лимитирования при росте трафика; грубые алгоритмы дёшевы, но создают всплески и легко обходятся распределённой атакой. Выбор зависит от того, что дороже для бизнеса — потерянные легитимные запросы или риск недостаточной защиты, а также от реальной архитектуры трафика (доля пользователей за общим IP/NAT).

**Пример / кейс**
```text

  00:01:00 -- окно сброшено, ещё 100 запросов проходят сразу

```

- **Компромисс:** Более частое и широкое сэмплирование даёт точнее данные и быстрее ловит редкие регрессии, но пропорционально увеличивает overhead и риск самому стать причиной деградации под пиковой нагрузкой; редкое и выборочное профилирование безопаснее для продакшена, но может пропустить кратковременные проблемы. Решение зависит от чувствительности бизнеса к дополнительной задержке, зрелости observability-инфраструктуры и от того, насколько критична скорость обнаружения регрессий.

Критерии выбора — число и размер тенантов, регуляторные требования конкретных клиентов и зрелость автоматизации управления множеством инстансов БД в команде.

### 440. [Q-03-08-0440] Продукт должен соответствовать требованиям по защите персональных данных (включая право пользователя на удаление своих данных и ограничение срока хранения), но часть этих данных активно используется в аналитике и кэшируется для производительности горячих запросов. **Направление:** Python Backend Developer<br>
**Тема:** Производительность, безопасность и надёжность: профилирование, оптимизация, аутентификация, авторизация, управление секретами, защита приложения и контроль ресурсов<br>
**Уровень:** Senior

**Короткий ответ**<br>
Нужно заранее спроектировать модель данных так, чтобы персональные данные были локализованы в ограниченном числе мест, а не размножены по кэшам, логам и аналитическим витринам без учёта этого, и предусмотреть явный процесс каскадного удаления/анонимизации по запросу пользователя, даже если это усложняет схему кэширования и снижает часть оптимизаций.

**Разбор**
- **Как это работает:** Право на удаление требует, чтобы при запросе пользователя система могла достоверно найти все места хранения его персональных данных — основную БД, резервные копии, кэши, аналитические агрегаты, логи — и либо удалить, либо анонимизировать данные там, где физическое удаление невозможно в разумный срок (например, в неизменяемых бэкапах) согласно политике хранения.
- **На практике:** Распространённый подход — хранить персональные данные в одном выделенном месте с жёстким контролем доступа и ссылаться на них по псевдонимизированному идентификатору из остальных систем (аналитика, кэши), чтобы удаление в одном месте автоматически «обесценивало» данные во всех производных системах; для горячих данных в кэше можно использовать TTL, не превышающий политику хранения.
- **Частые ошибки:** Проектируют аналитику и кэши так, будто персональные данные можно свободно копировать между системами «для удобства», не оставляя способа отследить и удалить все копии; реализуют «мягкое» удаление (флаг is_deleted) без реальной очистки данных из активно используемых мест; не определяют явно срок хранения в бэкапах, оставляя его «как получится» по умолчанию инструмента резервного копирования.
- **Компромисс:** Псевдонимизация и жёсткая локализация персональных данных снижают риск при compliance-аудите и упрощают удаление, но усложняют аналитические запросы (приходится джойнить данные через дополнительный слой) и могут снизить производительность некоторых горячих путей, оптимизированных на денормализованные данные; более свободное копирование данных между системами ради производительности увеличивает операционный риск при аудите и запросах на удаление. Критерии выбора — юрисдикция и строгость применимого регулирования, чувствительность конкретных данных и стоимость переработки уже существующей аналитической инфраструктуры.

**Пример / кейс**
```text
core_users (PII: email, phone, address) -- доступ строго ограничен, аудит обращений
analytics_events (user_pseudo_id, event_type, ts) -- без прямых PII, ссылка через псевдоним
cache:user_profile:{pseudo_id} TTL=1h -- не переживает политику хранения

Запрос на удаление пользователя:
  1. удалить/анонимизировать запись в core_users
  2. разорвать связь pseudo_id -> user_id (таблица маппинга)
  3. дождаться истечения TTL кэша и ближайшей ротации бэкапов согласно политике
```
