### 1. [Q-03-01-0001] В чём разница между list и tuple в Python и когда вы выберете каждый из них в реальном коде?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
list — изменяемая последовательность для данных, которые меняются по ходу работы программы; tuple — неизменяемая последовательность, подходящая для фиксированных наборов значений и в качестве ключей словаря.

**Разбор**
- **Как это работает:** list реализован как динамический массив ссылок, поддерживающий append, insert, удаление элементов — объект можно изменять после создания. tuple хранит тот же набор ссылок, но без методов изменения состава; после создания кортеж нельзя дополнить или сократить.
- **На практике:** tuple удобен для возврата нескольких значений из функции (координаты, пара ключ-значение), для неизменяемых записей и как элемент set/ключ dict, поскольку он хешируем (если хешируемы все его элементы). list используют для коллекций, которые растут, сортируются или фильтруются в процессе работы.
- **Частые ошибки:** Путают неизменяемость кортежа с неизменяемостью его содержимого: tuple с вложенным list внутри всё равно позволяет изменить этот list, хотя сам кортеж "не меняется". Также забывают, что tuple из одного элемента требует запятой: (1) — это просто число 1, а не кортеж.

**Пример / кейс**
```python
point = (10, 20)          # tuple: фиксированная пара координат
# point[0] = 11            # TypeError: 'tuple' object does not support item assignment

history = []              # list: будет расти по ходу работы
history.append(point)
history.append((11, 21))
print(history)             # [(10, 20), (11, 21)]

mixed = (1, [2, 3])        # кортеж неизменяем, но вложенный список — да
mixed[1].append(4)
print(mixed)                # (1, [2, 3, 4])
```
### 2. [Q-03-01-0002] Как в Python определить, что тип данных изменяемый (mutable) или неизменяемый (immutable), и почему это важно при передаче аргументов в функцию?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Изменяемость — это способность объекта менять своё содержимое по тому же id() без создания нового объекта; list, dict, set изменяемы, а int, float, str, tuple, frozenset — неизменяемы, и это определяет, увидит ли вызывающий код изменения, сделанные внутри функции.

**Разбор**
- **Как это работает:** В Python аргументы передаются как ссылки на объекты (passing the object, не "по значению" и не классическое "по ссылке"). Если функция вызывает у переданного объекта метод, меняющий его содержимое in-place (append, pop, обновление по индексу), изменения видны снаружи, потому что это тот же объект. Если функция делает `x = x + [1]` или переприсваивает параметр, снаружи создаётся новый объект, и внешняя переменная не меняется.
- **На практике:** Проверить изменяемость можно через id(): если id(obj) до и после операции совпадает — объект изменили in-place, если изменился — создали новый. При проектировании функций явно документируют, мутирует ли функция входные данные, либо возвращают новый объект, чтобы не создавать скрытые побочные эффекты.
- **Частые ошибки:** Ожидают, что `def f(n): n += 1` изменит переданное число — не изменит, так как int неизменяем и `+=` для него создаёт новый объект. И наоборот, не ожидают, что `def f(lst): lst.append(1)` изменит список вызывающего кода — а он изменится, так как list изменяем.

**Пример / кейс**
```python
def add_item(container, item):
    container.append(item)      # мутирует переданный list по месту

def increment(number):
    number += 1                 # создаёт новый int, не трогает исходный

data = [1, 2]
add_item(data, 3)
print(data)                     # [1, 2, 3] — изменения видны снаружи

n = 5
increment(n)
print(n)                        # 5 — не изменилось, int неизменяем
```
### 3. [Q-03-01-0003] Что выведет этот код и в чём классическая ошибка с изменяемым значением по умолчанию у функции?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Значение-аргумент по умолчанию вычисляется один раз при определении функции, а не при каждом вызове, поэтому изменяемый default (список, словарь) переживает между вызовами и накапливает данные — правильное решение: использовать None как default и создавать новый объект внутри функции.

**Разбор**
- **Как это работает:** Python создаёт объект для значения по умолчанию один раз, в момент выполнения `def`, и хранит его в `__defaults__` функции. Каждый вызов без явного аргумента получает ссылку на этот же самый объект, а не на свежую копию.
- **На практике:** Безопасный паттерн — `def f(items=None): items = items if items is not None else []`. Это гарантирует новый список на каждый вызов без явного аргумента. Такой же баг возникает с default-словарями и default-множествами, а не только со списками.
- **Частые ошибки:** Разработчики ожидают, что каждый вызов "начинает с чистого листа", и удивляются, когда данные из предыдущих вызовов появляются в текущем. Баг особенно незаметен в тестах, если тесты выполняются в порядке, который случайно маскирует накопление состояния.

**Пример / кейс**
```python
def append_item(item, bucket=[]):   # баг: один и тот же список на все вызовы
    bucket.append(item)
    return bucket

print(append_item(1))   # [1]
print(append_item(2))   # [1, 2]  — неожиданно, старое значение осталось

def append_item_fixed(item, bucket=None):
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

print(append_item_fixed(1))  # [1]
print(append_item_fixed(2))  # [2]  — независимые вызовы
```
### 4. [Q-03-01-0004] Чем оператор is отличается от ==, и почему `a == b`, но `a is not b` — это нормальная и частая ситуация?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
== сравнивает значения объектов через метод __eq__, а is сравнивает идентичность — указывают ли переменные на один и тот же объект в памяти (совпадает ли id()); два разных объекта могут быть равны по значению, но не быть одним и тем же объектом.

**Разбор**
- **Как это работает:** `a == b` вызывает `a.__eq__(b)` (с запасным вариантом `b.__eq__(a)`), и поведение зависит от того, как класс объекта определяет равенство. `a is b` — это сравнение `id(a) == id(b)`, то есть равенство адресов/идентификаторов объектов, которое ни один класс переопределить не может.
- **На практике:** `is` используют для сравнения с синглтонами: `is None`, `is True/False` (хотя для bool обычно пишут просто `if flag:`), и иногда для проверки "это тот же самый объект, а не его копия". Для сравнения значений — чисел, строк, списков, собственных объектов — всегда используют `==`.
- **Частые ошибки:** Пишут `if x == None` вместо `if x is None` (работает, но не идиоматично и может дать неожиданный результат, если у объекта переопределён `__eq__`). Другая ошибка — полагаться на `is` для сравнения небольших чисел или коротких строк из-за того, что CPython кеширует маленькие int (-5..256) и некоторые строковые литералы: такое поведение является деталью реализации CPython, а не гарантией языка, и ломается, например, для чисел вне диапазона кеша.

**Пример / кейс**
```python
a = [1, 2, 3]
b = [1, 2, 3]
print(a == b)   # True  — одинаковое содержимое
print(a is b)   # False — это два разных объекта в памяти

c = a
print(a is c)   # True  — c ссылается на тот же объект

x = 256
y = 256
print(x is y)   # True на CPython (кеш маленьких int) — деталь реализации
x2 = 1000
y2 = 1000
print(x2 is y2) # не гарантировано True — нельзя полагаться на это в коде
```
### 5. [Q-03-01-0005] Как работают срезы (slicing) списков и строк в Python? Объясните на примерах с отрицательными индексами и шагом.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Срез `seq[start:stop:step]` возвращает новую последовательность того же типа с элементами от индекса start (включительно) до stop (не включая), с заданным шагом; отрицательные индексы отсчитываются с конца, а отрицательный шаг разворачивает порядок.

**Разбор**
- **Как это работает:** Python вычисляет границы среза, нормализуя отрицательные индексы (прибавляя длину последовательности) и подставляя значения по умолчанию: start=0, stop=len(seq) для положительного шага (и наоборот для отрицательного), step=1. Результат — всегда новый объект-копия выбранных элементов, исходная последовательность не меняется.
- **На практике:** Частые идиомы: `seq[::-1]` — разворот последовательности, `seq[:n]` — первые n элементов, `seq[-n:]` — последние n элементов, `seq[::2]` — каждый второй элемент. Для списков срез можно использовать и в левой части присваивания: `lst[1:3] = [10, 20, 30]` заменит два элемента тремя.
- **Частые ошибки:** Путают, что stop не включается в результат (off-by-one ошибки). Также забывают, что срез списка — это поверхностная (shallow) копия: вложенные изменяемые объекты внутри остаются общими для исходного списка и срезанной копии.

**Пример / кейс**
```python
s = "Backend"
print(s[1:4])     # "ack"
print(s[-3:])     # "end"
print(s[::-1])    # "dnekcaB" — разворот строки

nums = [0, 1, 2, 3, 4, 5]
print(nums[::2])    # [0, 2, 4]
print(nums[1:4])    # [1, 2, 3], индекс 4 не включён

copy_nums = nums[:]   # полная поверхностная копия списка
copy_nums.append(99)
print(nums)           # [0, 1, 2, 3, 4, 5] — исходный список не изменился
```
### 6. [Q-03-01-0006] В чём разница между list comprehension и generator expression, и когда вы предпочтёте одно другому?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
List comprehension `[x for x in it]` сразу вычисляет и хранит в памяти весь список, а generator expression `(x for x in it)` создаёт ленивый итератор, который вычисляет элементы по одному при обращении — выбор зависит от того, нужен ли полный список сразу или достаточно пройти по данным один раз.

**Разбор**
- **Как это работает:** List comprehension выполняет цикл немедленно и собирает результаты в новый объект list в памяти. Generator expression возвращает объект-генератор без вычислений "внутри"; каждое значение вычисляется лениво при вызове `next()` (явном или через for/sum/list и т.п.), и после одного полного прохода генератор исчерпывается.
- **На практике:** Для больших или потенциально бесконечных источников данных (построчное чтение файла, поток записей из БД) генератор экономит память, так как не держит все элементы одновременно. Если результат нужно индексировать, проходить несколько раз, получить len() или передать как JSON — нужен конкретный список, то есть list comprehension или `list(generator)`.
- **Частые ошибки:** Пытаются повторно проитерироваться по уже исчерпанному генератору и получают пустой результат без ошибки. Также создают list comprehension там, где нужен только один проход по большим данным (например, суммирование), и получают лишний расход памяти на промежуточный список.

**Пример / кейс**
```python
numbers = range(1_000_000)

squares_list = [n * n for n in numbers]        # весь список сразу в памяти
squares_gen = (n * n for n in numbers)         # ленивый генератор, почти без памяти

total = sum(n * n for n in numbers)            # эффективно: без промежуточного списка

gen = (x for x in [1, 2, 3])
print(list(gen))   # [1, 2, 3]
print(list(gen))   # [] — генератор уже исчерпан, повторный проход невозможен
```
### 7. [Q-03-01-0007] Какими способами можно объединить два словаря в Python, и как разрешается конфликт ключей?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Словари объединяют через метод `dict.update()`, распаковку `{**d1, **d2}` или оператор `|` (Python 3.9+); во всех способах при совпадении ключей выигрывает значение из словаря, указанного позже (правее / последним применённым).

**Разбор**
- **Как это работает:** `d1.update(d2)` изменяет `d1` на месте, перезаписывая совпадающие ключи значениями из `d2`. `{**d1, **d2}` и `d1 | d2` создают новый словарь, не изменяя исходные; порядок распаковки или операндов определяет, чьё значение "побеждает" при одинаковых ключах — побеждает тот, что применён позже.
- **На практике:** Если нужно сохранить оба исходных словаря без изменений — используют `|` или распаковку. Если исходный словарь можно мутировать и важна скорость для большого числа обновлений — `update()` эффективнее, так как не создаёт новый объект. Начиная с 3.9 есть также `|=` для обновления на месте в стиле, похожем на `update`.
- **Частые ошибки:** Думают, что `update()` возвращает новый словарь — метод возвращает `None`, результат нужно смотреть в изменённом исходном объекте. Также не учитывают порядок операндов в `|`/распаковке и получают не то значение при пересекающихся ключах.

**Пример / кейс**
```python
defaults = {"timeout": 30, "retries": 3}
overrides = {"retries": 5, "debug": True}

merged = {**defaults, **overrides}
print(merged)                 # {'timeout': 30, 'retries': 5, 'debug': True}

merged2 = defaults | overrides
print(merged2 == merged)      # True, тот же результат другим синтаксисом

defaults.update(overrides)    # изменяет defaults на месте, возвращает None
print(defaults)               # {'timeout': 30, 'retries': 5, 'debug': True}
```
### 8. [Q-03-01-0008] Для чего используются *args и **kwargs в сигнатуре функции? Приведите пример функции, которая их применяет осмысленно.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
*args собирает произвольное количество позиционных аргументов в tuple, а **kwargs собирает произвольные именованные аргументы в dict — это позволяет писать функции с гибким числом параметров и универсальные обёртки, прозрачно передающие аргументы дальше.

**Разбор**
- **Как это работает:** При определении функции `*args` должен идти после обычных позиционных параметров, `**kwargs` — последним. При вызове все "лишние" позиционные аргументы попадают в `args` как кортеж, все лишние именованные — в `kwargs` как словарь. При вызове другой функции `func(*args, **kwargs)` происходит обратная операция — распаковка.
- **На практике:** Типичное применение — декораторы и обёртки (`logging_wrapper(*args, **kwargs)`), которые не знают заранее сигнатуру оборачиваемой функции, но должны передать в неё все аргументы как есть. Также используется для функций с опциональными параметрами конфигурации, где явный список был бы слишком длинным.
- **Частые ошибки:** Злоупотребляют `**kwargs` там, где нужны явные, задокументированные именованные параметры — это ухудшает читаемость и подсказки IDE/статическую типизацию. Также путают порядок: позиционные параметры, затем `*args`, затем параметры только по имени (keyword-only), затем `**kwargs`.

**Пример / кейс**
```python
def call_and_log(func, *args, **kwargs):
    print(f"Вызов {func.__name__} с args={args}, kwargs={kwargs}")
    return func(*args, **kwargs)

def create_user(name, age, role="user"):
    return {"name": name, "age": age, "role": role}

result = call_and_log(create_user, "Alice", age=30, role="admin")
print(result)  # {'name': 'Alice', 'age': 30, 'role': 'admin'}
```
### 9. [Q-03-01-0009] Чем метод экземпляра класса отличается от обычной функции, и зачем нужен параметр self?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Метод экземпляра — это функция, определённая внутри класса, которая автоматически получает первым аргументом сам объект, на котором её вызвали (`self`), что даёт методу доступ к атрибутам и другим методам этого конкретного экземпляра.

**Разбор**
- **Как это работает:** Когда вы пишете `obj.method(arg)`, Python фактически вызывает `ClassName.method(obj, arg)` — `self` связывается с объектом автоматически через механизм дескрипторов функций (bound method). Внутри метода `self.attr` обращается к атрибуту именно этого экземпляра.
- **На практике:** `self` — это просто соглашение об имени (можно назвать иначе, но так не делают), и он обязателен как первый параметр любого обычного метода, не являющегося `staticmethod`. Через `self` методы читают и изменяют состояние объекта, вызывают другие методы того же объекта (`self.other_method()`).

```python
        return self.value
```

### 10. [Q-03-01-0010] В каком порядке выполняются блоки try/except/else/finally, и зачем нужен блок else в этой конструкции?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Сначала выполняется try; если исключения не было — выполняется else, затем всегда выполняется finally; если исключение возникло и было перехвачено — выполняется соответствующий except, затем finally; finally выполняется в любом случае, даже при исключении, return или необработанной ошибке.

**Разбор**
- **Как это работает:** Блок `else` в try/except — это код, который должен запуститься только тогда, когда try полностью завершился без исключений; он не выполнится, если исключение было поймано except'ом. `finally` гарантированно выполняется после try/except/else независимо от исхода: нормального завершения, перехваченного исключения или даже необработанного исключения, которое прокидывается дальше после finally.
- **На практике:** `else` используют, чтобы не прятать код, зависящий от успеха операции, внутрь try — это снижает риск случайно перехватить исключение, брошенное уже в коде "после успеха". `finally` применяют для гарантированного освобождения ресурсов (закрытие файлов, соединений), хотя для этого чаще используют контекстные менеджеры (`with`).
- **Частые ошибки:** Кладут в try слишком много кода, из-за чего except неожиданно перехватывает ошибки из логики, не связанной с рискованной операцией. Не замечают, что `return` внутри try всё равно не отменяет выполнение `finally` — finally выполнится перед фактическим возвратом значения.

**Пример / кейс**
```python
def read_config(path):
    try:
        f = open(path)
    except FileNotFoundError:
        print("Файл не найден, используем значения по умолчанию")
        return {}
    else:
        print("Файл успешно открыт")   # выполнится только без исключения
        data = f.read()
        f.close()
        return {"raw": data}
    finally:
        print("Попытка чтения конфигурации завершена")  # выполнится всегда

read_config("missing.cfg")
```

```python

        return "количество не указано"
    if qty:
        return f"в наличии: {qty}"
    return "товар закончился"            # qty == 0, но это не None

print(describe_quantity(None))  # количество не указано
```

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
str — это последовательность текстовых символов (Unicode code points), а bytes — последовательность байтов (чисел 0–255), представляющих закодированные данные; UnicodeDecodeError возникает при попытке декодировать bytes в str с кодировкой, которая не соответствует тому, как данные были закодированы на самом деле.

**Разбор**
- **Как это работает:** Текст в памяти Python 3 всегда хранится как `str` в абстрактном Unicode-представлении. Чтобы отправить текст по сети, записать в файл в бинарном режиме или передать в протокол, str кодируют в bytes через `.encode("кодировка")`; обратное преобразование — `.decode("кодировка")`. Если байты были получены в одной кодировке (например, UTF-8 с кириллицей), а decode вызывается с другой (например, ASCII или неправильной cp1251), часть байтовых последовательностей не соответствует ни одному валидному символу — возникает `UnicodeDecodeError`.
- **На практике:** По умолчанию большинство Python API (файлы, HTTP-библиотеки) используют UTF-8, и явно указывать кодировку стоит всегда, когда источник данных может быть в другой кодировке (легаси-файлы, экспорт из Excel на Windows в cp1251). Для чтения файла в бинарном режиме используют `open(path, "rb")`, в текстовом — `open(path, "r", encoding="utf-8")`.
- **Частые ошибки:** Смешивают str и bytes в одной операции (`"text" + b"bytes"`) и получают `TypeError`. Также читают файл без указания encoding, из-за чего на разных ОС (разные encoding по умолчанию) один и тот же файл читается по-разному или падает с ошибкой декодирования.

**Пример / кейс**
```python
text = "Привет, backend!"
encoded = text.encode("utf-8")
print(encoded)                 # b'\xd0\x9f\xd1\x80\xd0\xb8...'

decoded = encoded.decode("utf-8")
print(decoded == text)         # True

try:
    encoded.decode("ascii")    # кириллица не кодируется в ASCII
except UnicodeDecodeError as e:
    print("Ошибка декодирования:", e)
```

**Короткий ответ**<br>
__init__ — это метод-инициализатор, который вызывается автоматически сразу после создания нового объекта класса и используется для присвоения начальных значений атрибутам этого экземпляра; он не создаёт сам объект, а только настраивает уже созданный.

```python
        self.is_active = True      # значение по умолчанию при создании
```

### 14. [Q-03-01-0014] В чём разница между staticmethod, classmethod и обычным методом экземпляра в Python?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Обычный метод получает первым аргументом экземпляр (self) и обращается к его состоянию; classmethod получает первым аргументом сам класс (cls) и обычно используется для альтернативных конструкторов; staticmethod не получает ни self, ни cls и ведёт себя как обычная функция, просто логически связанная с классом по смыслу.

**Разбор**
- **Как это работает:** Декоратор `@classmethod` превращает первый параметр в ссылку на класс, через который метод был вызван (это важно при наследовании — `cls` будет указывать на класс-наследник, если метод вызван через него). `@staticmethod` убирает автоматическую передачу чего-либо — метод просто помещён в namespace класса для группировки, без доступа к `self`/`cls`.
- **На практике:** classmethod часто используют для фабричных методов, создающих объект по-другому (`User.from_dict(data)`), которые должны уметь работать и для подклассов. staticmethod применяют для вспомогательных функций, логически относящихся к классу (например, валидация формата email), но не нуждающихся ни в состоянии объекта, ни в самом классе.
- **Частые ошибки:** Делают staticmethod там, где фактически нужен classmethod (и наоборот), из-за чего, например, фабричный метод в подклассе продолжает создавать объект родительского класса вместо подкласса. Также пытаются обратиться к `self` внутри staticmethod и получают ошибку, так как он туда не передаётся.

**Пример / кейс**
```python
class User:
    def __init__(self, name):
        self.name = name

    @classmethod
    def from_dict(cls, data):
        return cls(data["name"])      # cls — правильный класс даже для наследников

    @staticmethod
    def is_valid_name(name):
        return bool(name) and name.isalpha()

class AdminUser(User):
    pass

admin = AdminUser.from_dict({"name": "Boss"})
print(type(admin))                  # <class '__main__.AdminUser'>
print(User.is_valid_name("Alice"))  # True
```

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Наследование позволяет классу-потомку переиспользовать и переопределять атрибуты и методы родительского класса; `super()` даёт доступ к методам родителя из переопределённого метода потомка, что позволяет дополнить, а не полностью заменить родительскую логику.

**Разбор**
- **Как это работает:** При определении `class Child(Parent):` потомок автоматически получает все методы и атрибуты родителя, которые не переопределены явно. Вызов `super().method(...)` внутри потомка ищет реализацию `method` выше по цепочке наследования (согласно порядку MRO) и вызывает её с текущим `self`.
- **На практике:** Чаще всего `super().__init__(...)` вызывают в начале `__init__` потомка, чтобы родительский класс корректно инициализировал свою часть состояния, а потомок — только добавил своё. Это избавляет от дублирования кода инициализации и сохраняет правильное поведение при изменении родительского класса.
- **Частые ошибки:** Полностью переопределяют метод потомка без вызова `super()`, из-за чего теряется важная логика родителя (например, не выполняется обязательная валидация из базового класса). Также обращаются к родителю напрямую по имени класса (`Parent.method(self)`) вместо `super()`, что усложняет поддержку при изменении иерархии наследования.

**Пример / кейс**
```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

    def describe(self):
        return f"{self.name}, зарплата {self.salary}"

class Manager(Employee):
    def __init__(self, name, salary, team_size):
        super().__init__(name, salary)     # инициализация родительской части
        self.team_size = team_size

    def describe(self):
        base = super().describe()          # дополняем, а не заменяем
        return f"{base}, команда из {self.team_size} человек"

m = Manager("Анна", 150000, 5)
print(m.describe())  # Анна, зарплата 150000, команда из 5 человек
```

set — это неупорядоченная коллекция уникальных хешируемых элементов, автоматически отбрасывающая дубликаты, в отличие от list, который допускает повторяющиеся элементы и сохраняет порядок их добавления.

**Пример / кейс**
```python
raw_ids = [1, 2, 2, 3, 1, 4]
unique_ids = set(raw_ids)
print(unique_ids)              # {1, 2, 3, 4}, порядок не гарантирован
```

### 17. [Q-03-01-0017] Как создать и возбудить собственное исключение в Python, и зачем наследоваться от Exception, а не использовать стандартные исключения для всего?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Собственное исключение создаётся как класс, наследующийся от Exception (или более конкретного встроенного исключения), и возбуждается через `raise MyError("сообщение")`; это позволяет вызывающему коду отличать именно вашу ошибку от остальных и обрабатывать её целенаправленно через `except MyError`.

- **Как это работает:** Класс исключения обычно не требует собственной логики — достаточно унаследоваться от `Exception` или подходящего встроенного класса (например, `ValueError`), чтобы получить стандартное поведение хранения сообщения и трассировки стека. При `raise` Python прерывает обычный поток выполнения и ищет подходящий `except` выше по стеку вызовов.
- **На практике:** Собственные исключения делают код читаемым и позволяют вызывающей стороне принимать решения в зависимости от конкретной ошибки (`except InsufficientFundsError`), а не парсить текст сообщения общего `ValueError`. - **Частые ошибки:** Используют общий `Exception` для всех ошибок без разделения на типы, из-за чего вызывающий код вынужден либо ловить всё подряд, либо парсить текст сообщения. Также забывают вызвать `super().__init__(message)`, из-за чего у исключения отсутствует читаемое текстовое представление.

**Пример / кейс**
```python
class InsufficientFundsError(Exception):
    def __init__(self, balance, amount):
        super().__init__(f"Недостаточно средств: баланс {balance}, нужно {amount}")
        self.balance = balance
        self.amount = amount

def withdraw(balance, amount):
    if amount > balance:
        raise InsufficientFundsError(balance, amount)
    return balance - amount

try:
    withdraw(100, 150)
except InsufficientFundsError as exc:
    print("Операция отклонена:", exc)
    print("Не хватает:", exc.amount - exc.balance)
```
### 18. [Q-03-01-0018] Что означает ключевое слово global в функции, и как Python определяет, локальная переменная или глобальная?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Python по умолчанию считает переменную, которой присваивается значение внутри функции, локальной для этой функции; ключевое слово `global` явно говорит интерпретатору, что присваивание должно изменить переменную в глобальной области видимости модуля, а не создавать новую локальную.

**Разбор**
- **Как это работает:** Интерпретатор анализирует тело функции целиком перед выполнением: если переменной где-либо внутри функции присваивается значение (без `global`/`nonlocal`), она считается локальной во всей функции, даже в строчках до присваивания — это может привести к `UnboundLocalError`, если переменную с тем же именем сначала читают, а потом присваивают. `global name` отменяет это поведение для конкретного имени внутри функции.
- **На практике:** Читать глобальную переменную внутри функции можно без `global` — он нужен только для её изменения (присваивания нового значения) внутри функции. На практике частое изменение глобальных переменных через `global` считается плохой практикой — предпочтительнее передавать данные через аргументы и возвращаемые значения или хранить состояние в объекте.
- **Частые ошибки:** Пытаются изменить глобальную переменную внутри функции без `global` и неожиданно создают новую локальную переменную, из-за чего изменение "пропадает" за пределами функции. Также путают `global` (для модульной области) с `nonlocal` (для области видимости объемлющей функции).

**Пример / кейс**
```python
counter = 0

def increment_broken():
    counter += 1          # UnboundLocalError: присваивание делает counter локальным

def increment_fixed():
    global counter
    counter += 1

increment_fixed()
increment_fixed()
print(counter)             # 2

try:
    increment_broken()
except UnboundLocalError as e:
    print("Ошибка:", e)
```
### 19. [Q-03-01-0019] Какими способами можно итерироваться по словарю в Python, чтобы получить ключи, значения или пары ключ-значение?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Для перебора словаря используют сам словарь или `.keys()` для ключей, `.values()` для значений и `.items()` для пар (ключ, значение) — во всех случаях начиная с Python 3.7 порядок перебора соответствует порядку вставки ключей.

**Разбор**
- **Как это работает:** `for key in d:` и `for key in d.keys():` эквивалентны и дают ключи. `for value in d.values():` даёт значения без привязки к ключам. `for key, value in d.items():` возвращает пары, которые удобно распаковывать прямо в заголовке цикла. Все три представления — "живые" view-объекты: они отражают изменения словаря, если словарь меняется во время итерации по отдельному, не связанному с ней коду.
- **На практике:** `.items()` — самый частый выбор, когда внутри цикла нужны и ключ, и значение. Если нужен словарь, отфильтрованный или преобразованный, часто используют dict comprehension: `{k: v for k, v in d.items() if condition}`.
- **Частые ошибки:** Изменяют словарь (добавляют/удаляют ключи) прямо во время итерации по нему — это вызывает `RuntimeError: dictionary changed size during iteration`. Чтобы безопасно изменять словарь во время обхода, итерируются по копии ключей: `for key in list(d.keys()):`.

**Пример / кейс**
```python
prices = {"apple": 100, "banana": 50, "cherry": 300}

for name, price in prices.items():
    print(f"{name}: {price} руб.")

expensive = {name: price for name, price in prices.items() if price > 60}
print(expensive)          # {'apple': 100, 'cherry': 300}

for name in list(prices.keys()):   # копия ключей — безопасно удалять во время обхода
    if prices[name] < 60:
        del prices[name]
print(prices)              # {'apple': 100, 'cherry': 300}
```
### 20. [Q-03-01-0020] Чем отличаются методы list.append(), list.extend() и list.insert()? Что выведет код, где их перепутали?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
append() добавляет один элемент в конец списка (даже если этот элемент сам является списком), extend() добавляет все элементы из переданного итерируемого объекта по отдельности в конец, а insert(index, value) вставляет один элемент по конкретному индексу, сдвигая остальные.

**Разбор**
- **Как это работает:** `lst.append(x)` увеличивает длину списка на 1, добавляя сам объект `x` целиком как один элемент. `lst.extend(iterable)` проходит по `iterable` и добавляет каждый его элемент как отдельный элемент `lst`, то есть длина увеличивается на количество элементов в `iterable`. `lst.insert(i, x)` сдвигает элементы, начиная с индекса `i`, вправо и помещает `x` на позицию `i`.
- **На практике:** Частая путаница — попытка "добавить список элементов" через `append()`: `lst.append([1, 2, 3])` добавит один элемент — сам список `[1, 2, 3]` — а не три числа; для этого нужен `extend([1, 2, 3])` или `lst += [1, 2, 3]`. `insert()` используют редко в горячих циклах, так как вставка в середину списка требует сдвига элементов и имеет линейную стоимость от размера списка.
- **Частые ошибки:** Используют `append()` вместо `extend()` при объединении списков и получают список списков вместо плоского списка. Также не замечают, что `extend()` принимает любой итерируемый объект, а не только list — например, строку, которая будет разбита на отдельные символы.

**Пример / кейс**
```python
numbers = [1, 2, 3]

numbers_wrong = numbers.copy()
numbers_wrong.append([4, 5])
print(numbers_wrong)         # [1, 2, 3, [4, 5]]  — вложенный список, не то, что ожидали

numbers_right = numbers.copy()
numbers_right.extend([4, 5])
print(numbers_right)         # [1, 2, 3, 4, 5]

numbers_right.insert(0, 0)
print(numbers_right)         # [0, 1, 2, 3, 4, 5]
```
### 21. [Q-03-01-0021] Какие есть способы форматирования строк в Python (f-строки, .format(), оператор %), и какой из них предпочтителен в современном коде?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
В современном Python 3 предпочтительны f-строки (`f"{value}"`) как наиболее читаемый и быстрый способ; метод `.format()` остаётся полезен, когда шаблон строки определяется динамически или отдельно от значений, а оператор `%` считается устаревшим стилем, доставшимся от Python 2.

**Разбор**
- **Как это работает:** f-строка вычисляет выражения внутри `{}` непосредственно в месте использования и вставляет их строковое представление (с учётом опциональных спецификаторов формата после `:`). `.format()` подставляет аргументы в именованные или позиционные `{}`-плейсхолдеры шаблонной строки, которую можно хранить отдельно от значений. `%` использует printf-подобный синтаксис (`%s`, `%d`) и требует соответствия типов плейсхолдерам.
- **На практике:** f-строки предпочтительны почти везде, где шаблон и значения известны в одном месте кода — они короче и быстрее на выполнение. `.format()` удобен, когда шаблон читается из конфигурации или файла локализации и заранее не содержит реальных переменных Python. Спецификаторы формата (`{value:.2f}`, `{num:,}`) работают одинаково и в f-строках, и в `.format()`.
- **Частые ошибки:** Используют конкатенацию строк (`"Привет, " + name + "!"`) для сложных сообщений вместо f-строк, что менее читаемо и подвержено ошибкам с типами (нельзя конкатенировать str и int без явного приведения). Также забывают, что в f-строках нельзя использовать обратный слэш внутри выражения в `{}` (ограничение зависит от версии Python).

**Пример / кейс**
```python
name = "Мария"
balance = 1234.5

print(f"Пользователь {name}, баланс: {balance:.2f} руб.")
print("Пользователь {}, баланс: {:.2f} руб.".format(name, balance))

template = "Привет, {user}! У вас {count} новых сообщений."
print(template.format(user=name, count=3))
```
### 22. [Q-03-01-0022] Чем отличаются del, list.remove() и list.pop() при удалении элементов списка?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
del lst[i] удаляет элемент по индексу и ничего не возвращает (а del lst целиком удаляет саму переменную), remove(value) удаляет первое вхождение конкретного значения (ищет по содержимому, не по индексу), а pop(i) удаляет элемент по индексу и возвращает его значение.

**Разбор**
- **Как это работает:** `del` — это оператор языка, а не метод списка: `del lst[2]` убирает элемент с индексом 2, `del lst[1:3]` убирает срез, `del lst` удаляет саму переменную `lst` из текущей области видимости. `remove(value)` линейно ищет первое совпадение по значению и удаляет его, бросая `ValueError`, если значение не найдено. `pop()` без аргумента удаляет и возвращает последний элемент (эффективно, O(1)), `pop(i)` — элемент по индексу (может требовать сдвига остальных, если i не последний).
- **На практике:** `pop()` без аргументов — стандартный способ реализовать стек (LIFO). `remove()` удобен, когда известно значение, но не известен его индекс, но на больших списках он медленный из-за линейного поиска. `del` по срезу — удобный способ очистить часть списка сразу.
- **Частые ошибки:** Вызывают `remove()`, ожидая удаления по индексу (путая его с `pop`), и удаляют неверный элемент, если в списке есть совпадающее значение раньше нужной позиции. Также не оборачивают `remove()`/`pop(i)` в try/except там, где значение или индекс могут отсутствовать, и получают необработанные `ValueError`/`IndexError`.

**Пример / кейс**
```python
queue = ["a", "b", "c", "b"]

queue.remove("b")        # удаляет первое вхождение "b" (по значению, не по индексу)
print(queue)              # ['a', 'c', 'b']

last = queue.pop()        # удаляет и возвращает последний элемент
print(last, queue)        # b ['a', 'c']

del queue[0]
print(queue)               # ['c']
```
### 23. [Q-03-01-0023] Как работает множественное присваивание и распаковка последовательностей в Python? Как с помощью неё поменять значения двух переменных местами без временной переменной?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Python поддерживает одновременное присваивание нескольких переменных из любой последовательности подходящей длины (`a, b = 1, 2`), а также распаковку "остатка" через `*rest`; обмен значений двух переменных делается прямо через `a, b = b, a`, так как правая часть полностью вычисляется перед присваиванием.

**Разбор**
- **Как это работает:** При `a, b = b, a` Python сначала строит временный tuple `(b, a)` из текущих значений, затем распаковывает его в `a` и `b` — поэтому не нужна отдельная переменная для хранения промежуточного значения. При распаковке с `*rest` одна переменная помечается звёздочкой и забирает все элементы, которые не достались остальным переменным, в виде списка.
- **На практике:** Такой способ обмена делает код короче и нагляднее, чем классический `tmp = a; a = b; b = tmp`. Распаковка с `*` удобна для разбора "первый + остальные" или "первый, последний, середина": `first, *middle, last = items`.
- **Частые ошибки:** Пытаются распаковать последовательность с несовпадающим количеством элементов без `*` и получают `ValueError: too many values to unpack` (или наоборот — not enough values). Также забывают, что при распаковке с `*rest` результат — всегда list, даже если исходная последовательность была tuple или строкой.

**Пример / кейс**
```python
a, b = 1, 2
a, b = b, a
print(a, b)          # 2 1 — обмен без временной переменной

first, *middle, last = [10, 20, 30, 40, 50]
print(first, middle, last)   # 10 [20, 30, 40] 50

try:
    x, y = [1, 2, 3]       # несовпадение количества без *
except ValueError as e:
    print("Ошибка:", e)
```
### 24. [Q-03-01-0024] Прочитайте код ниже: функция должна возвращать отфильтрованный список чётных чисел, но тест падает. В чём ошибка и как её исправить?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Junior

**Короткий ответ**<br>
Функция не содержит инструкции return после цикла, поэтому она всегда неявно возвращает None, хотя внутри корректно строит список result — исправление: добавить явный `return result` после цикла.

**Разбор**
- **Как это работает:** Если функция доходит до конца тела без явного `return value`, Python автоматически завершает её, возвращая `None`. Это не вызывает ошибку интерпретатора — код "работает" в смысле не падает, но вызывающая сторона получает `None` вместо ожидаемого значения, и ошибка обнаруживается только там, где это `None` пытаются использовать как список.
- **На практике:** Отлавливают такие баги через unit-тесты, проверяющие именно возвращаемое значение (`assert result == [2, 4]`), а не только отсутствие исключений. Также полезно включить проверку типов (type hints + статический анализатор типа mypy), который подскажет несоответствие аннотированного `-> list[int]` и фактического `None` в некоторых путях выполнения.
- **Частые ошибки:** Забывают return при рефакторинге, когда переносят логику из цикла, который раньше печатал результат, в функцию, которая должна его возвращать. Также кладут `return` внутрь цикла по ошибке, из-за чего функция возвращает результат после обработки только первого элемента, а не всего списка.

**Пример / кейс**
```python
def filter_even_broken(numbers):
    result = []
    for n in numbers:
        if n % 2 == 0:
            result.append(n)
    # забыли return result — функция всегда отдаёт None

def filter_even_fixed(numbers):
    result = []
    for n in numbers:
        if n % 2 == 0:
            result.append(n)
    return result

print(filter_even_broken([1, 2, 3, 4]))   # None — баг
print(filter_even_fixed([1, 2, 3, 4]))    # [2, 4] — исправлено
```
### 25. [Q-03-01-0025] Что такое замыкание (closure) в Python? Объясните на примере, почему создание функций в цикле с использованием переменной цикла часто приводит к неожиданному результату.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Замыкание — это функция, которая запоминает переменные из окружающей (объемлющей) области видимости даже после завершения выполнения этой области; при создании нескольких замыканий в цикле они обычно ссылаются на одну и ту же переменную цикла по имени, а не на её значение на момент создания, поэтому все замыкания видят её финальное значение.

**Разбор**
- **Как это работает:** Внутренняя функция хранит ссылку на ячейку переменной (cell) во внешней функции, а не копию значения на момент определения. Переменная цикла `for i in range(n)` — это одна и та же переменная на всех итерациях, поэтому все замыкания, созданные в цикле и ссылающиеся на `i`, после завершения цикла видят её последнее значение.
- **На практике:** Проблема решается "захватом" текущего значения через параметр по умолчанию (`def f(i=i): ...`) или через `functools.partial`, который фиксирует значение аргумента в момент создания. Замыкания широко используют для фабрик функций, мемоизации и для реализации декораторов с параметрами.
- **Частые ошибки:** Создают список обработчиков/лямбд в цикле без захвата текущего значения переменной и получают одинаковое поведение у всех, хотя ожидали разное. Также не осознают, что это не баг Python, а последствие того, как работают области видимости и позднее связывание (late binding) имён.

**Пример / кейс**
```python
handlers = []
for i in range(3):
    handlers.append(lambda: i)     # все лямбды делят одну переменную i

print([h() for h in handlers])      # [2, 2, 2] — неожиданно одинаково

handlers_fixed = []
for i in range(3):
    handlers_fixed.append(lambda i=i: i)   # захватываем текущее значение i

print([h() for h in handlers_fixed])        # [0, 1, 2] — как и ожидалось
```

Декоратор оборачивает исходную функцию во внутреннюю функцию-обёртку, которая выполняет замер времени до и после вызова оригинала; без functools.wraps обёрнутая функция теряет своё имя, docstring и другие метаданные, так как снаружи видна только функция-обёртка, а не оригинал.

**Разбор**
- **Как это работает:** Декоратор `@my_decorator` синтаксически эквивалентен `func = my_decorator(func)` — имя `func` в месте использования начинает указывать на объект, который вернул декоратор (обычно это wrapper-функция). `functools.wraps(func)` — это сам декоратор, применяемый к wrapper, который копирует `__name__`, `__doc__`, `__module__` и прочие атрибуты оригинальной функции на wrapper, чтобы снаружи decorated-функция выглядела как исходная.
- **На практике:** Без `functools.wraps` инструменты автодокументации, отладчики, логирование стектрейсов и `help(func)` показывают имя `wrapper` вместо реального имени функции, что затрудняет диагностику в продакшене. Это особенно критично, если декораторы применяются массово (логирование, кеширование, авторизация) на многих функциях API.
- **Частые ошибки:** Забывают `*args, **kwargs` в сигнатуре wrapper, из-за чего декоратор перестаёт работать с функциями, принимающими аргументы. Также забывают вернуть результат вызова оригинальной функции из wrapper, из-за чего декорированная функция всегда возвращает None.

**Пример / кейс**
```python
import time
import functools

def timed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} выполнена за {elapsed:.4f} с")
        return result
    return wrapper

@timed
def compute_sum(n):
    """Считает сумму чисел от 0 до n."""
    return sum(range(n))

compute_sum(1_000_000)
print(compute_sum.__name__, "-", compute_sum.__doc__)  # compute_sum - Считает сумму...
```

Также не осознают, что при построении цепочки генераторов ошибка в коде-потребителе может "молча" остановить обработку на середине, если не предусмотрена явная обработка исключений внутри цикла.

### 28. [Q-03-01-0028] Как реализовать собственный контекстный менеджер в Python двумя способами: через класс с __enter__/__exit__ и через contextlib.contextmanager? В чём разница их поведения при исключении внутри блока with?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Класс-менеджер определяет методы __enter__ (код настройки, возвращаемое значение становится переменной after as) и __exit__ (код очистки, получает информацию об исключении и может его подавить, вернув True); contextlib.contextmanager превращает функцию-генератор с одним yield в контекстный менеджер, где код до yield — это __enter__, а код после yield (обычно в try/finally) — это __exit__.

**Разбор**
- **Как это работает:** Блок `with cm:` вызывает `cm.__enter__()` и привязывает его результат к переменной после `as`. При выходе из блока (нормально или из-за исключения) вызывается `cm.__exit__(exc_type, exc_value, traceback)`; если исключение было, но `__exit__` возвращает truthy-значение, исключение считается обработанным и не распространяется дальше. У генератора с `@contextmanager` исключение из блока `with` "прорастает" в точку `yield` внутри генератора, поэтому код очистки обычно оборачивают в try/finally вокруг yield.
- **На практике:** Класс выбирают, когда менеджеру нужно хранить сложное состояние или предоставлять дополнительные методы. `@contextmanager` — более короткий способ для простых случаев (временная подмена настройки, блокировка, замер времени), особенно когда логика естественно описывается как "код до" / `yield` / "код после".
- **Частые ошибки:** Забывают try/finally вокруг yield в генераторной версии, из-за чего код очистки не выполняется при исключении внутри with. В классовой версии забывают, что `__exit__`, возвращающий `True`, подавляет исключение — иногда это делают случайно и теряют важную ошибку.

**Пример / кейс**
```python
from contextlib import contextmanager

class Timer:
    def __enter__(self):
        import time
        self._start = time.perf_counter()
        return self

    def __exit__(self, exc_type, exc_value, tb):
        import time
        print(f"Прошло: {time.perf_counter() - self._start:.4f} с")
        return False          # не подавляем исключение

@contextmanager
def timer_gen():
    import time
    start = time.perf_counter()
    try:
        yield
    finally:
        print(f"Прошло: {time.perf_counter() - start:.4f} с")

with Timer():
    sum(range(100_000))

with timer_gen():
    sum(range(100_000))
```
### 29. [Q-03-01-0029] Что такое MRO (Method Resolution Order) при множественном наследовании в Python, и как узнать порядок, в котором будут искаться методы?

**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
MRO — это детерминированный порядок, в котором Python ищет метод или атрибут по цепочке классов при множественном наследовании, вычисляемый по алгоритму C3-линеаризации; узнать точный порядок для конкретного класса можно через `ClassName.__mro__` или `ClassName.mro()`.

**Разбор**
- **Как это работает:** C3-линеаризация строит порядок так, чтобы класс всегда шёл раньше своих родителей, а относительный порядок родителей, указанных в определении класса, сохранялся — это даёт единый непротиворечивый порядок обхода даже для сложных диаграмм наследования. `super()` внутри метода использует именно этот порядок, переходя к следующему классу в MRO текущего экземпляра, а не напрямую к "родителю" в обычном понимании.
- **На практике:** Понимание MRO важно для классов-миксинов (mixin), где функциональность собирается из нескольких небольших классов: порядок перечисления родителей в `class Combined(MixinA, MixinB, Base):` определяет, какая реализация метода будет вызвана первой. При конфликтных иерархиях Python может поднять `TypeError: Cannot create a consistent method resolution order`, если линеаризация невозможна.
- **Частые ошибки:** Предполагают, что методы ищутся строго "слева направо" без учёта общих базовых классов, и не понимают, почему вызов через `super()` в миксине неожиданно попадает не в прямого родителя, а в другой класс по MRO. Также злоупотребляют глубоким множественным наследованием, из-за чего реальный порядок вызовов становится трудно предсказать без явной проверки `__mro__`.

**Пример / кейс**
```python
class Base:
    def greet(self):
        return "Base"

class MixinA(Base):
    def greet(self):
        return "A->" + super().greet()

class MixinB(Base):
    def greet(self):
        return "B->" + super().greet()

class Combined(MixinA, MixinB):
    pass

print([c.__name__ for c in Combined.__mro__])
# ['Combined', 'MixinA', 'MixinB', 'Base', 'object']
print(Combined().greet())   # A->B->Base — порядок строго по MRO
```
### 30. [Q-03-01-0030] Почему при переопределении метода __eq__ в классе часто также нужно переопределить __hash__, и что произойдёт, если это не сделать?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Python требует, чтобы равные по __eq__ объекты имели одинаковый хеш (__hash__) для корректной работы в set и как ключи dict; если переопределить __eq__ и не переопределить __hash__, Python по умолчанию делает объект нехешируемым (__hash__ становится None), и попытка положить его в set/словарь приведёт к TypeError.

**Разбор**
- **Как это работает:** Контракт хеш-таблиц: если `a == b`, то должно быть `hash(a) == hash(b)` — иначе два "равных" объекта могут попасть в разные корзины хеш-таблицы, и словарь/множество перестанет находить уже добавленный эквивалентный элемент. Как только класс явно определяет `__eq__`, Python автоматически отключает унаследованный `__hash__` (устанавливает его в `None`), чтобы не нарушить этот контракт случайно, — хеш нужно либо переопределить согласованно с `__eq__`, либо явно оставить класс нехешируемым.
- **На практике:** Хеш обычно строят из тех же полей, которые участвуют в сравнении равенства, оборачивая их в `hash((self.field1, self.field2))`. Для изменяемых объектов (чьи поля, участвующие в равенстве, могут меняться после создания) переопределять `__hash__` обычно не стоит — такие объекты логично оставить нехешируемыми, чтобы не ломать инварианты множеств/словарей при изменении объекта после вставки.
- **Частые ошибки:** Переопределяют только `__eq__` для сравнения "по значению" (например, по id сущности) и удивляются `TypeError: unhashable type`, пытаясь положить объекты в set. Другая ошибка — переопределить `__hash__` на основе изменяемых полей и затем мутировать объект после того, как он уже лежит в set/dict, из-за чего объект "теряется" (его больше невозможно найти по новому значению хеша в старой корзине).

**Пример / кейс**
```python
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __eq__(self, other):
        return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y)

    def __hash__(self):
        return hash((self.x, self.y))   # согласован с полями из __eq__

p1, p2 = Point(1, 2), Point(1, 2)
print(p1 == p2)              # True
print({p1, p2})              # {<Point ...>} — один элемент, хеши совпали
print(len({p1, p2}))         # 1
```

### 32. [Q-03-01-0032] Что делает __slots__ в классе Python, какую память он экономит, и какие ограничения накладывает на класс?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
__slots__ объявляет фиксированный, заранее известный набор атрибутов экземпляра и запрещает Python создавать для каждого объекта отдельный __dict__ для произвольных атрибутов — это уменьшает потребление памяти на больших количествах экземпляров, но не позволяет добавлять атрибуты, не перечисленные в __slots__, и требует аккуратности при множественном наследовании.

- **Как это работает:** Без `__slots__` каждый экземпляр хранит свой словарь атрибутов `__dict__`, который сам по себе занимает заметный объём памяти, особенно при создании миллионов небольших объектов. `__slots__ = ("x", "y")` заставляет Python выделить для каждого атрибута компактный дескриптор на уровне класса (slot), а у экземпляров не создаётся `__dict__` вообще, что экономит память и немного ускоряет доступ к атрибутам.
- **На практике:** __slots__ имеет смысл применять к классам, которые создаются в больших количествах (элементы кэша, узлы структур данных, DTO в горячем пути), и для которых набор атрибутов точно фиксирован. Если нужно наследование от класса без __slots__ (например, от стандартного Exception без явного slots) или динамическое добавление атрибутов — экономия частично или полностью теряется.
- **Частые ошибки:** Пытаются присвоить атрибут, не указанный в `__slots__`, и получают `AttributeError`. Также забывают, что при множественном наследовании нескольких классов с непустыми и несовместимыми `__slots__` Python может поднять `TypeError` из-за конфликта layout памяти, а при наследовании от класса без `__slots__` потомок всё равно получает `__dict__`, и экономия памяти исчезает.

**Пример / кейс**
```python
class PointSlots:
    __slots__ = ("x", "y")

    def __init__(self, x, y):
        self.x = x
        self.y = y

p = PointSlots(1, 2)
print(p.x, p.y)        # 1 2
try:
    p.z = 3             # нет в __slots__
except AttributeError as e:
    print("Ошибка:", e)

import sys
class PointDict:
    def __init__(self, x, y):
        self.x = x
        self.y = y

print(sys.getsizeof(PointSlots(1, 2)) <= sys.getsizeof(PointDict(1, 2)))  # True (обычно)
```
### 33. [Q-03-01-0033] В чём разница между поверхностным (copy) и глубоким (deepcopy) копированием объекта, и на каком примере с вложенными структурами это становится заметно?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>

**Разбор**
- **Как это работает:** `copy.copy(obj)` (или `list(obj)`, `dict(obj)`, срез `obj[:]`) создаёт новый контейнер верхнего уровня, но копирует в него те же самые ссылки на вложенные объекты, а не их содержимое. `copy.deepcopy(obj)` рекурсивно обходит структуру и создаёт новые копии на каждом уровне вложенности, используя memo-словарь, чтобы корректно обрабатывать циклические ссылки без бесконечной рекурсии.
- **На практике:** Для "плоских" структур (список чисел или строк) поверхностная копия и глубокая дают одинаковый практический результат, так как элементы неизменяемы. Для структур с вложенными list/dict/объектами выбор критичен: если нужна полностью независимая копия для безопасной модификации — нужен deepcopy, который дороже по времени и памяти, поэтому его не стоит использовать там, где достаточно поверхностной копии.
- **Частые ошибки:** Используют `list(nested_list)` или `dict.copy()`, ожидая полностью независимую структуру, и затем случайно изменяют вложенные списки/словари как в оригинале, так и в "копии". Также применяют `deepcopy` без необходимости в горячем пути, что создаёт заметные накладные расходы на больших структурах.

**Пример / кейс**
```python
import copy

original = {"items": [1, 2, 3], "meta": {"owner": "team-a"}}

shallow = copy.copy(original)
shallow["items"].append(4)
print(original["items"])          # [1, 2, 3, 4] — изменилось и в оригинале!

deep = copy.deepcopy(original)
deep["items"].append(99)
print(original["items"])           # [1, 2, 3, 4] — оригинал не затронут deepcopy
```
### 34. [Q-03-01-0034] Для чего используется синтаксис raise NewError(...) from original_error, и чем он отличается от обычного raise NewError(...) внутри блока except?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
`raise ... from original_error` явно связывает новое исключение с исходным через атрибут __cause__, фиксируя в трассировке осознанную причину "одна ошибка вызвала другую"; без `from` при повторном raise внутри except исходное исключение всё равно попадает в трассировку через неявный __context__, но как побочный эффект обработки, а не как явно задокументированная причина.

**Разбор**
- **Как это работает:** Когда внутри `except OriginalError:` возбуждают новое исключение, Python автоматически сохраняет текущее исключение в атрибуте `__context__` нового — это видно в трассировке как "During handling of the above exception, another exception occurred". `raise New(...) from original` дополнительно устанавливает `__cause__ = original` и меняет текст в трассировке на явное "The above exception was the direct cause of the following exception", что сигнализирует намеренную трансформацию ошибки, а не случайную.
- **На практике:** Такой паттерн используют, когда низкоуровневая ошибка (например, ошибка драйвера БД) должна быть представлена вызывающему коду как ошибка более высокого уровня (например, `RepositoryError`), но важно не терять оригинальную причину для логов и отладки. `raise New(...) from None` явно подавляет отображение цепочки, когда исходная ошибка не несёт полезной информации для внешнего наблюдателя.
- **Частые ошибки:** Перехватывают исключение и поднимают новое без `from`, теряя для читателя трассировки явную связь, хотя неявный `__context__` технически присутствует — это усложняет диагностику в логах, где печатают только `str(exc)` без полного traceback. Также путают `raise` без аргументов (повторно возбуждает текущее перехваченное исключение) с `raise NewException() from current`.

**Пример / кейс**
```python
class RepositoryError(Exception):
    pass

def load_user(user_id):
    try:
        raise ConnectionError("Соединение с БД потеряно")
    except ConnectionError as exc:
        raise RepositoryError(f"Не удалось загрузить пользователя {user_id}") from exc

try:
    load_user(42)
except RepositoryError as exc:
    print("Поймано:", exc)
    print("Причина:", exc.__cause__)   # ConnectionError('Соединение с БД потеряно')
```
### 35. [Q-03-01-0035] В production-сервисе обработчик, формирующий отчёт, стал заметно медленнее при росте числа строк. В коде конкатенация строк в цикле через +=. Как диагностировать и исправить эту проблему?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Повторная конкатенация строк через += в цикле на больших объёмах данных квадратично деградирует по времени, так как строки в Python неизменяемы и каждая конкатенация создаёт новую строку, копируя все предыдущие символы; решение — собирать части в список и объединить один раз через ''.join(parts) в конце.

**Разбор**
- **Как это работает:** Строка — неизменяемый объект, поэтому `result += chunk` не дополняет существующую строку "по месту", а создаёт новый объект, копируя все символы старой строки плюс новый фрагмент. При N итерациях суммарный объём скопированных символов растёт квадратично (1+2+...+N), хотя CPython в некоторых случаях оптимизирует этот паттерн для простых локальных переменных, такая оптимизация не гарантирована языком и не работает надёжно, например, при накоплении в атрибуте объекта или списке.
- **На практике:** Профилировать такую проблему можно через `cProfile`/`timeit` на реальном объёме данных, сравнивая время при росте N: квадратичная деградация видна по тому, что время растёт быстрее, чем линейно с увеличением N. Исправление — копить фрагменты в list и один раз вызвать `"".join(parts)`, что имеет линейную сложность от суммарной длины.
- **Частые ошибки:** Оптимизируют "на глаз" без замера на реалистичном объёме данных и упускают случаи, когда проблема проявляется только при достаточно больших N (в тестах с маленькими данными деградация не заметна). Также путают эту проблему с более общим советом "всегда используйте join", не объясняя, почему конкретно += в цикле проблематичен именно для больших N.

**Пример / кейс**
```python
def build_report_slow(rows):
    report = ""
    for row in rows:
        report += f"{row}\n"     # на больших N — квадратичная деградация
    return report

def build_report_fast(rows):
    parts = [f"{row}\n" for row in rows]
    return "".join(parts)          # линейная сложность

import timeit
rows = list(range(20000))
# timeit.timeit(lambda: build_report_slow(rows), number=5)
# timeit.timeit(lambda: build_report_fast(rows), number=5)
# на реальном прогоне build_report_fast заметно быстрее при росте len(rows)
```
### 36. [Q-03-01-0036] Что такое nonlocal, и чем он отличается от global? Приведите пример вложенной функции, которой он нужен.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
nonlocal позволяет функции, вложенной в другую функцию, изменять переменную из области видимости объемлющей (не глобальной) функции, тогда как global всегда ссылается на переменную модульного уровня — без nonlocal попытка присвоить значение внешней переменной внутри вложенной функции создаёт новую локальную переменную во вложенной функции.

**Разбор**
- **Как это работает:** Python следует правилу LEGB (Local, Enclosing, Global, Built-in) при поиске имени для чтения, но для присваивания переменной по умолчанию выбирается самая внутренняя (Local) область видимости. `nonlocal name` явно указывает интерпретатору искать и изменять `name` в ближайшей объемлющей функции (Enclosing), а не создавать новую локальную переменную во вложенной функции.
- **На практике:** Типичный случай — функция-фабрика, создающая счётчик, аккумулятор или кэш внутри замыкания: внутренняя функция должна изменять состояние, "принадлежащее" внешней функции, между вызовами. Это распространённый паттерн до появления (или как альтернатива) классов для простого хранения состояния.
- **Частые ошибки:** Забывают `nonlocal` и получают `UnboundLocalError` при попытке изменить переменную объемлющей функции внутри вложенной. Также пытаются использовать `nonlocal` для переменной модульного уровня, что вызывает `SyntaxError: no binding for nonlocal found`, если подходящей объемлющей функции нет — в этом случае нужен `global`.

**Пример / кейс**
```python
def make_counter():
    count = 0

    def increment():
        nonlocal count     # без этого — UnboundLocalError при count += 1
        count += 1
        return count

    return increment

counter = make_counter()
print(counter())   # 1
print(counter())   # 2
print(counter())   # 3 — состояние сохраняется между вызовами замыкания
```
### 37. [Q-03-01-0037] Зачем в Python использовать абстрактные базовые классы (abc.ABC, @abstractmethod), если утиная типизация (duck typing) и так позволяет вызывать любой метод, который есть у объекта?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
ABC формализует контракт: класс с абстрактным методом нельзя инстанцировать напрямую, пока все абстрактные методы не переопределены в подклассе, что даёт явную, проверяемую на этапе создания объекта гарантию реализации интерфейса, а не только соглашение по документации, на которое полагается чистая утиная типизация.

**Разбор**
- **Как это работает:** Класс, наследующийся от `abc.ABC` и помечающий методы `@abstractmethod`, не может быть создан через `ClassName()`, если хотя бы один абстрактный метод не переопределён в конкретном подклассе — Python поднимает `TypeError` прямо в момент попытки создания объекта, а не позже, когда отсутствующий метод впервые понадобится. Это сдвигает обнаружение ошибки "забыли реализовать метод" на самое раннее возможное время.
- **На практике:** ABC полезны, когда в команде/библиотеке определён набор обязательных методов для расширяемого компонента (например, разные реализации хранилища данных, разные стратегии оплаты), и важно сразу получить понятную ошибку при неполной реализации, а не падение в продакшене на вызове отсутствующего метода. Утиная типизация без ABC остаётся нормальной практикой для более гибких, неформальных интерфейсов, где избыточная формализация не оправдана.
- **Частые ошибки:** Добавляют ABC "на всякий случай" почти для всех классов, превращая простой код в избыточно формализованную иерархию. Также забывают, что абстрактный метод может иметь реализацию по умолчанию (вызываемую через `super()`), а не только пустое тело — ABC не запрещает частичную реализацию в базовом классе.

**Пример / кейс**
```python
from abc import ABC, abstractmethod

class PaymentProvider(ABC):
    @abstractmethod
    def charge(self, amount: float) -> bool:
        ...

class CardProvider(PaymentProvider):
    def charge(self, amount: float) -> bool:
        print(f"Списано {amount} с карты")
        return True

try:
    PaymentProvider()        # TypeError: нельзя создать экземпляр абстрактного класса
except TypeError as e:
    print("Ошибка:", e)

CardProvider().charge(100.0)   # работает, все абстрактные методы реализованы
```
### 38. [Q-03-01-0038] Как работает декоратор @dataclass, и как настроить сравнение (__eq__), строковое представление (__repr__) и неизменяемость (frozen) у класса, описывающего данные?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
@dataclass автоматически генерирует __init__, __repr__ и __eq__ на основе аннотированных полей класса; поведение можно настроить параметрами декоратора — eq=False отключает сравнение по значению, repr=False отключает автогенерацию строкового представления, а frozen=True делает экземпляры неизменяемыми после создания (присваивание полям вызывает исключение).

**Разбор**
- **Как это работает:** По умолчанию `@dataclass` читает аннотации типов на уровне класса и генерирует `__init__`, который присваивает каждому аргументу соответствующее поле, `__repr__`, печатающий все поля в читаемом виде, и `__eq__`, сравнивающий объекты как tuple из значений полей в порядке объявления. `frozen=True` переопределяет `__setattr__`/`__delattr__`, чтобы бросать `FrozenInstanceError` на попытку изменить поле после `__init__`, что также делает экземпляр потенциально хешируемым (при согласованных условиях), в отличие от обычного изменяемого dataclass.
- **На практике:** dataclass обычно выбирают для DTO, объектов-значений и простых структур конфигурации, где не нужна сложная бизнес-логика, но важны автоматическое сравнение по значению и читаемый `repr` для логов/отладки. Поля с изменяемым значением по умолчанию (list, dict) нельзя указывать напрямую — для них используют `field(default_factory=list)`, чтобы повторить защиту от общего mutable default, о которой говорилось для обычных функций.
- **Частые ошибки:** Указывают `field: list = []` вместо `field: list = field(default_factory=list)` и получают тот же классический баг общего изменяемого default между экземплярами, что и в обычных функциях. Также ожидают, что `frozen=True` делает неизменяемыми и вложенные объекты (списки/словари внутри полей) — это не так, frozen запрещает только переприсваивание самих полей объекта.

**Пример / кейс**
```python
from dataclasses import dataclass, field

@dataclass(frozen=True)
class Money:
    amount: float
    currency: str = "RUB"

m1 = Money(100.0)
m2 = Money(100.0)
print(m1 == m2)        # True — сравнение по значению полей
print(m1)               # Money(amount=100.0, currency='RUB')
try:
    m1.amount = 200.0   # FrozenInstanceError: экземпляр неизменяем
except Exception as e:
    print("Ошибка:", type(e).__name__)

@dataclass
class Basket:
    items: list = field(default_factory=list)   # безопасный default для list
```
### 39. [Q-03-01-0039] Как Python собирает мусор для объектов с циклическими ссылками (например, когда два объекта ссылаются друг на друга), и зачем в таких случаях может понадобиться weakref?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Для объектов без циклов CPython освобождает память сразу, когда счётчик ссылок (refcount) падает до нуля; для объектов, образующих цикл ссылок друг на друга, счётчик ссылок никогда не достигнет нуля сам по себе, поэтому отдельный циклический сборщик мусора (generational garbage collector) периодически находит такие группы объектов и освобождает их — а weakref позволяет держать ссылку на объект, не увеличивая его refcount и не создавая цикл, который мешал бы освобождению памяти.

**Разбор**
- **Как это работает:** Каждый объект в CPython хранит счётчик ссылок; когда он достигает нуля, память освобождается немедленно, детерминированно. Если объект A ссылается на B, а B ссылается на A, их взаимные ссылки держат refcount каждого минимум на 1, даже если снаружи на них больше никто не ссылается — обычный refcounting эту группу никогда не освободит. Модуль `gc` периодически запускает алгоритм поиска таких недостижимых извне циклов и освобождает их; `weakref.ref(obj)` создаёт ссылку, которая не увеличивает refcount и становится "мёртвой" (возвращает None), если на объект больше нет обычных (strong) ссылок.
- **На практике:** weakref часто применяют в кэшах (чтобы закешированный объект не продлевал жизнь другому объекту искусственно), в наблюдателях/подписках (listener не должен мешать уборке объекта-источника события) и в структурах с обратными ссылками "родитель-потомок", где потомок хранит ссылку на родителя. Это снижает риск утечек памяти в долгоживущих процессах backend-сервиса, где циклические структуры создаются часто, но зависимость от цикличного GC нежелательна (например, если объекты держат нетривиальные внешние ресурсы, для которых важно освобождение сразу, а не "когда-нибудь" через цикл gc).
- **Частые ошибки:** Полагают, что в Python утечки памяти в принципе невозможны благодаря автоматическому GC — циклы с объектами, у которых определён кастомный `__del__`, в некоторых версиях/ситуациях усложняют и замедляют сборку, а если в сборке участвуют внешние ресурсы (файлы, соединения), их высвобождение может откладываться до срабатывания циклического сборщика. Также путают `weakref` с обычным удалением ссылки — слабая ссылка не продлевает жизнь объекту, но и не удаляет его сама.

**Пример / кейс**
```python
import weakref

class Node:
    def __init__(self, name):
        self.name = name
        self.parent = None

class ParentNode:
    def __init__(self, name):
        self.name = name
        self.children = []

    def add_child(self, child):
        self.children.append(child)
        child.parent = weakref.ref(self)   # слабая ссылка — без цикла refcount

p = ParentNode("root")
c = Node("child")
p.add_child(c)
print(c.parent().name)    # 'root' — вызываем weakref как функцию, чтобы получить объект
del p
print(c.parent())          # None — родитель уже собран, слабая ссылка это отражает
```

**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Класс-итератор реализует __iter__ (обычно возвращает self) и __next__ (вычисляет и возвращает следующее значение при каждом вызове); об окончании последовательности он сигнализирует, возбуждая исключение StopIteration внутри __next__, которое цикл for автоматически перехватывает и завершает итерацию.

**Разбор**
- **Как это работает:** Протокол итератора требует двух методов: `__iter__(self)`, возвращающий объект-итератор (часто `self`, если класс одновременно итерируемый и итератор), и `__next__(self)`, возвращающий очередное значение или возбуждающий `StopIteration`, когда значений больше нет. Конструкция `for x in obj:` под капотом вызывает `iter(obj)` один раз, затем повторяет `next(it)` в цикле, автоматически останавливаясь при перехвате `StopIteration` без вывода ошибки пользователю.
- **На практике:** Такой подход используют, когда нужен контроль над состоянием итерации (например, итератор с ленивой подгрузкой страниц из API или БД), а не просто требуется перебрать готовую коллекцию, для которой было бы достаточно генератора с `yield`. Часто разделяют класс-контейнер (реализует только `__iter__`, создающий новый итератор на каждый вызов) и отдельный класс-итератор (хранит текущую позицию) — это позволяет проходить по одному контейнеру несколько раз параллельно.
- **Частые ошибки:** Делают контейнер и итератор одним и тем же объектом без разделения состояния, из-за чего повторный `for` по уже пройденному объекту не выдаёт ничего (итератор уже исчерпан) — для повторной итерации нужен новый объект-итератор. Также забывают возбуждать `StopIteration` и получают бесконечный цикл `for`.

**Пример / кейс**
```python
class Squares:
    def __init__(self, n):
        self.n = n

    def __iter__(self):
        return SquaresIterator(self.n)

class SquaresIterator:
    def __init__(self, n):
        self.n = n
        self.current = 1

    def __iter__(self):
        return self

    def __next__(self):
        if self.current > self.n:
            raise StopIteration
        value = self.current ** 2
        self.current += 1
        return value

squares = Squares(4)
print(list(squares))   # [1, 4, 9, 16]
print(list(squares))   # [1, 4, 9, 16] — можно пройти снова, т.к. __iter__ создаёт новый итератор
```
### 41. [Q-03-01-0041] В production-коде два экземпляра класса Order неожиданно делят один и тот же список товаров: добавление товара в один заказ появляется и в другом. В коде список объявлен как атрибут класса, а не как атрибут экземпляра в __init__. Как диагностировать и исправить эту ошибку?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Атрибут, объявленный прямо в теле класса (а не внутри __init__ через self.attr), принадлежит самому классу и является общим для всех экземпляров; если это изменяемый объект (список, словарь) и к нему обращаются через self.attr.append(...), все экземпляры мутируют один и тот же общий объект — исправление: инициализировать список индивидуально для каждого экземпляра внутри __init__.

**Разбор**
- **Как это работает:** Атрибут класса (`class Order: items = []`) создаётся один раз при определении класса и хранится в namespace самого класса, а не в `__dict__` каждого экземпляра. Чтение `self.items` находит этот общий атрибут (Python сначала ищет в `__dict__` экземпляра, не находит и поднимается к классу), но `self.items.append(x)` не создаёт новый атрибут экземпляра — он мутирует тот самый общий объект класса, поэтому изменение видно через любой экземпляр.
- **На практике:** Диагностируют такую проблему, сравнивая `id(order1.items)` и `id(order2.items)` — совпадающий id подтверждает, что это один и тот же объект. Исправление — перенести инициализацию в `__init__`: `self.items = []`, что создаёт новый список для каждого экземпляра при его создании, присваивая атрибут экземпляра, который перекрывает (shadow) атрибут класса при последующих обращениях через `self`.
- **Частые ошибки:** Используют изменяемые атрибуты класса для "значений по умолчанию", полагая, что это аналог параметра по умолчанию в функции — поведение здесь похоже на классическую ошибку с mutable default arguments, но проявляется на уровне всего класса, а не отдельного вызова функции. Эта ошибка особенно опасна в коде, где такие объекты используются как кэш или аккумулятор состояния на уровне запроса/сессии.

**Пример / кейс**
```python
class OrderBroken:
    items = []                 # общий для ВСЕХ экземпляров атрибут класса

    def add_item(self, item):
        self.items.append(item)

o1 = OrderBroken()
o2 = OrderBroken()
o1.add_item("book")
print(o2.items)                 # ['book'] — утечка через общий атрибут класса!
print(o1.items is o2.items)     # True — это один и тот же объект

class OrderFixed:
    def __init__(self):
        self.items = []         # отдельный список для каждого экземпляра

    def add_item(self, item):
        self.items.append(item)

f1, f2 = OrderFixed(), OrderFixed()
f1.add_item("book")
print(f2.items)                  # [] — изолировано корректно
```
### 42. [Q-03-01-0042] Как работает functools.lru_cache, и в каких ситуациях его применение опасно или неэффективно?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
lru_cache сохраняет результаты вызовов функции по кортежу её аргументов и возвращает закешированный результат при повторном вызове с теми же аргументами, вытесняя наименее недавно использованные записи при превышении лимита maxsize; он опасен для функций с нехешируемыми или изменяемыми аргументами, для функций с побочными эффектами или зависимостью от внешнего состояния, а также может привести к удержанию в памяти больших объектов дольше, чем ожидается, особенно если декорировать метод экземпляра.

**Разбор**
- **Как это работает:** lru_cache строит внутренний словарь, где ключ — это представление позиционных и именованных аргументов вызова, а значение — результат функции; при повторном вызове с таким же ключом функция не выполняется повторно, а сразу возвращается сохранённый результат. Поскольку ключ строится на основе хеша аргументов, все аргументы должны быть хешируемыми (immutable), иначе будет `TypeError`.
- **На практике:** lru_cache хорошо подходит для чистых функций (детерминированных, без побочных эффектов), зависящих только от своих аргументов — классический пример, вычисление чего-то дорогого по небольшому диапазону входных значений. Декорирование метода экземпляра (`self.method`) опасно: `self` становится частью ключа кеша, и кеш неявно держит ссылку на сам объект `self`, продлевая его жизнь дольше, чем ожидалось (утечка памяти), пока кеш не очищен явно (`cache_clear()`) или объект не исчезнет из всех ключей кеша.
- **Частые ошибки:** Кешируют функцию, которая обращается к изменяемому внешнему состоянию (конфигурации, текущему времени, данным из БД), и получают устаревшие результаты после изменения этого состояния, так как кеш не инвалидируется автоматически. Также применяют `lru_cache` без ограничения `maxsize` (бесконечный кеш) для функции с большим или неограниченным количеством уникальных аргументов, что приводит к неконтролируемому росту потребления памяти.

**Пример / кейс**
```python
from functools import lru_cache

@lru_cache(maxsize=256)
def fib(n: int) -> int:
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

print(fib(30))            # быстро за счёт кеша повторных подвызовов
print(fib.cache_info())    # CacheInfo(hits=..., misses=..., maxsize=256, currsize=...)

try:
    @lru_cache
    def total(items):     # list — нехешируемый аргумент
        return sum(items)
    total([1, 2, 3])
except TypeError as e:
    print("Ошибка:", e)
```
### 43. [Q-03-01-0043] Что такое diamond problem (проблема ромбовидного наследования) при множественном наследовании, и как Python разрешает её при помощи super() и MRO?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Diamond problem возникает, когда класс наследуется от двух классов, у которых есть общий предок, и возникает неоднозначность, какую версию метода общего предка должен получить итоговый класс; Python решает это не "напрямую к родителю", а через единый порядок MRO (C3-линеаризацию), благодаря чему super() в каждом классе переходит к следующему классу по этому общему порядку, и общий предок вызывается ровно один раз, а не дважды.

**Разбор**
- **Как это работает:** Если `ClassD(ClassB, ClassC)`, а `ClassB` и `ClassC` оба наследуются от `ClassA`, наивная реализация (вызов родителя "в лоб" по имени класса) привела бы к тому, что метод `ClassA` может быть вызван дважды — один раз через цепочку B, второй раз через C. MRO выстраивает единый линейный порядок `[D, B, C, A, object]`, и каждый `super().method()` в B и C переходит не прямо к A, а к следующему классу в этом общем порядке, поэтому A вызывается один раз, независимо от того, сколько путей к нему ведёт.
- **На практике:** Это особенно важно для классов-миксинов, где несколько миксинов совместно дополняют базовое поведение (например, миксин логирования и миксин кеширования, оба модифицирующие один и тот же метод через super()) — именно единый MRO гарантирует, что цепочка вызовов `super()` пройдёт по всем миксинам ровно один раз в согласованном порядке.
- **Частые ошибки:** Вызывают родительский метод напрямую через имя класса (`ClassA.method(self)`) вместо `super().method()`, что обходит MRO и может привести к повторному вызову общего предка или пропуску промежуточных классов в цепочке. Также строят глубокие и сложные деревья множественного наследования, не проверяя `__mro__`, из-за чего итоговое поведение становится трудно предсказать при добавлении нового миксина.

**Пример / кейс**
```python
class A:
    def action(self):
        print("A.action")

class B(A):
    def action(self):
        print("B.action")
        super().action()

class C(A):
    def action(self):
        print("C.action")
        super().action()

class D(B, C):
    def action(self):
        print("D.action")
        super().action()

D().action()
# D.action -> B.action -> C.action -> A.action
# A вызван ровно один раз благодаря единому MRO, а не наивному вызову по дереву
```
### 44. [Q-03-01-0044] Чем должны отличаться реализации __repr__ и __str__ у класса, и какую из них использует print(obj), а какую — вывод объекта в интерактивной консоли без print?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
__str__ предназначен для читаемого, ориентированного на человека представления объекта и используется функцией print() и str(obj); __repr__ предназначен для однозначного, по возможности воссоздаваемого (eval-able) представления, полезного для отладки и логов, и используется интерактивной консолью при выводе значения без print, а также как резервный вариант, если __str__ не определён.

**Разбор**
- **Как это работает:** `str(obj)` вызывает `obj.__str__()`, а если класс его не определяет — падает обратно на `obj.__repr__()`. `repr(obj)` всегда вызывает именно `obj.__repr__()`. Интерактивная консоль и Jupyter при выводе значения ячейки без явного print используют `repr()`, что объясняет, почему объект может "выглядеть по-разному" при print(obj) и при простом вводе obj в REPL, если оба метода переопределены по-разному.
- **На практике:** Хорошей практикой считается всегда реализовывать `__repr__` так, чтобы по нему можно было понять точное состояние объекта для отладки — по соглашению, в идеале в форме, похожей на код, который воссоздаёт объект (`Point(x=1, y=2)`). `__str__` реализуют отдельно только тогда, когда пользовательское, более "человеческое" представление действительно отличается от технического (например, для форматированной денежной суммы в UI).
- **Частые ошибки:** Определяют только `__str__`, а объекты в логах/debugger'е (которые обычно используют repr) выводятся в неинформативном виде по умолчанию (`<MyClass object at 0x...>`). Также путают их роли и помещают в `__repr__` сложное, многострочное "человеческое" сообщение, что затрудняет чтение логов и отладочного вывода списков таких объектов.

**Пример / кейс**
```python
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):
        return f"Point(x={self.x}, y={self.y})"   # для отладки и логов

    def __str__(self):
        return f"({self.x}, {self.y})"             # для вывода пользователю

p = Point(1, 2)
print(p)                 # (1, 2)            -> использует __str__
print([p, p])             # [Point(x=1, y=2), Point(x=1, y=2)] -> список использует __repr__ элементов
```
### 45. [Q-03-01-0045] Почему для представления ограниченного набора статусов (например, статус заказа) в Python предпочтительнее использовать enum.Enum, а не обычные строки или числа-константы?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Enum даёт именованный, замкнутый набор допустимых значений с проверкой на этапе использования через идентичность/принадлежность классу, тогда как обычные строки или числа-константы не защищают от опечаток, произвольных "левых" значений и не группируют связанные значения в единый, самодокументируемый тип.

**Разбор**
- **Как это работает:** `class Status(Enum): PENDING = "pending"; PAID = "paid"` создаёт класс, где `Status.PENDING` — это единственный объект-член с заданным значением; сравнение `status == Status.PENDING` явное и проверяется статическими анализаторами типов, а перечисление всех возможных значений доступно через `list(Status)`. Числовые/строковые "магические" константы (`STATUS_PENDING = "pending"`) синтаксически остаются обычными строками — ничто не мешает присвоить переменной произвольную строку, не входящую в предполагаемый набор.
- **На практике:** Enum улучшает читаемость (`order.status = Status.PAID` нагляднее, чем `order.status = "paid"`), позволяет IDE подсказывать все доступные варианты и упрощает рефакторинг (переименование члена enum найдёт все использования). При сериализации в JSON/БД обычно сохраняют `.value` (например, строку), а при чтении — явно конвертируют обратно в enum через `Status(value)`, обрабатывая случай недопустимого значения.
- **Частые ошибки:** Сравнивают enum-член напрямую со строкой (`status == "paid"`) вместо `status == Status.PAID` — для обычного `Enum` это обычно `False`, даже если `.value` совпадает (если явно не используется `StrEnum` или `(str, Enum)` в качестве базовых классов). Также забывают, что добавление нового члена enum в растущей системе — это изменение контракта, которое должно быть согласовано со всеми потребителями значения (БД, другие сервисы), а не только с кодом, где enum объявлен.

**Пример / кейс**
```python
from enum import Enum

class OrderStatus(Enum):
    PENDING = "pending"
    PAID = "paid"
    CANCELLED = "cancelled"

def can_cancel(status: OrderStatus) -> bool:
    return status in (OrderStatus.PENDING, OrderStatus.PAID)

print(can_cancel(OrderStatus.PENDING))   # True
print(OrderStatus.PAID == "paid")          # False — enum-член не равен обычной строке
print(OrderStatus.PAID.value == "paid")    # True — сравнение по значению явное
print(list(OrderStatus))                    # [<OrderStatus.PENDING: 'pending'>, ...]
```
### 46. [Q-03-01-0046] Как перехватить и обработать сразу несколько разных типов исключений в одном блоке except, и чем это отличается от использования нескольких отдельных except-блоков?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Один `except (TypeA, TypeB):` перехватывает любое исключение из перечисленных типов и обрабатывает его одним и тем же кодом, тогда как несколько отдельных `except TypeA:` / `except TypeB:` позволяют обработать каждый тип исключения своей отдельной, различающейся логикой.

**Разбор**
- **Как это работает:** `except (ValueError, KeyError) as exc:` проверяет, является ли возникшее исключение экземпляром любого из перечисленных классов (включая их подклассы), и если да — выполняет общий блок кода с одной и той же переменной `exc`, независимо от того, какой конкретно тип сработал. Порядок проверки except-блоков в try важен: Python проверяет их сверху вниз и выполняет первый подходящий, остальные блоки для этого исключения не рассматриваются.
- **На практике:** Группировку в один except используют, когда реакция на разные ошибки действительно одинакова (например, "залогировать и вернуть обобщённую ошибку клиенту"). Если же разным типам ошибок требуется разная реакция (повторить запрос при таймауте, но не повторять при ошибке валидации) — предпочтительнее отдельные except-блоки, расположенные от более специфичных типов к более общим, чтобы не "затенить" специфичную обработку более общим перехватом, стоящим раньше.
- **Частые ошибки:** Ставят `except Exception:` первым, из-за чего более специфичные except-блоки ниже становятся недостижимым кодом (многие линтеры это подсвечивают). Также группируют в один except типы ошибок, которые на самом деле требуют разной обработки, из-за чего теряется важная информация о причине сбоя при логировании или ответе клиенту API.

**Пример / кейс**

```python
def parse_amount(raw):
    try:
        data = {"amount": raw}

```
### 47. [Q-03-01-0047] В обработчике очереди сообщений, зарегистрированном как callback, через несколько часов работы сервиса растёт потребление памяти, хотя сами сообщения небольшие. В коде callback — это замыкание, созданное внутри функции настройки, которая также создаёт большой объект конфигурации. Как диагностировать и устранить такую утечку?

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
Замыкание захватывает не только нужные ему переменные, но неявно удерживает ссылки на весь объект объемлющей области видимости, если он на него ссылается хоть одним атрибутом; если большой объект конфигурации доступен в той же функции, где создаётся callback, он может держаться в памяти через ячейку замыкания даже тогда, когда реально callback'у нужен только один маленький параметр из него — решение: явно скопировать нужное значение в отдельную переменную перед созданием замыкания, не ссылаясь на весь большой объект.

**Разбор**
- **Как это работает:** Замыкание хранит ссылки на переменные объемлющей функции, к которым оно обращается по имени в своём теле — если тело callback обращается, например, к `config.retry_limit`, то замыкание держит ссылку на весь объект `config`, а не только на число `retry_limit`, потому что Python разрешает имя `config` динамически при каждом вызове, а не копирует значение атрибута заранее. Пока существует хотя бы один живой callback, созданный в этой функции, весь объект `config` (и всё, что он в себе держит) не может быть собран сборщиком мусора.
- **На практике:** Диагностируют такие утечки через профилировщики памяти (`tracemalloc`, `objgraph`), которые показывают, что объекты конфигурации продолжают жить дольше, чем ожидалось, и находят цепочку ссылок до объекта-замыкания. Исправление — скопировать только нужное значение в локальную переменную перед определением callback (`retry_limit = config.retry_limit`, и использовать в теле именно `retry_limit`), чтобы замыкание держало ссылку на маленькое неизменяемое значение, а не на весь большой объект.
- **Частые ошибки:** Создают много callback'ов в цикле настройки, каждый из которых неявно захватывает один и тот же большой объект "на всякий случай" через обращение к его атрибутам внутри тела функции. Также путают эту причину утечки с утечкой из-за циклических ссылок — здесь проблема не в цикле, а в том, что обычная (strong) ссылка из активного callback искусственно продлевает жизнь большому объекту, который давно не нужен целиком.

**Пример / кейс**
```python
class HeavyConfig:
    def __init__(self):
        self.retry_limit = 3
        self.cache = {}   # представим, что здесь много данных

def register_callback_leaky(config):
    def on_message(msg):
        if config.retry_limit > 0:   # держит ссылку на ВЕСЬ config
            process(msg)
    return on_message

def register_callback_fixed(config):
    retry_limit = config.retry_limit    # копируем только нужное значение
    def on_message(msg):
        if retry_limit > 0:              # замыкание держит только int, не весь config
            process(msg)
    return on_message

def process(msg):
    pass
```
### 48. [Q-03-01-0048] Прочитайте тест: assertEqual сравнивает два словаря с вложенными списками и неожиданно проходит, хотя разработчик ожидал, что тест должен падать из-за "разных объектов". Объясните, почему это ожидаемое поведение, и в каком случае тест действительно должен использовать проверку идентичности.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Middle

**Короткий ответ**<br>
assertEqual (как и обычный оператор ==) сравнивает структуры по значению рекурсивно, а не по идентичности объектов, поэтому два разных объекта dict/list с одинаковым содержимым считаются равными — это и есть правильное, ожидаемое поведение теста на корректность данных; проверка идентичности (assertIs / is) нужна только в особом случае, когда тест специально проверяет, что функция вернула именно тот же самый объект (например, из кэша), а не его копию.

**Разбор**
- **Как это работает:** `==` для list и dict определён так, что он рекурсивно сравнивает элементы/значения по их собственному `==`, независимо от того, являются ли контейнеры одним и тем же объектом в памяти. `assertEqual` в unittest внутри вызывает именно `==`, поэтому для словарей и списков он фактически проверяет совпадение содержимого, а не адреса в памяти.
- **На практике:** Такое поведение — то, что обычно и нужно в тестах на бизнес-логику: "функция должна вернуть структуру данных с такими-то полями и значениями", а не "функция должна вернуть именно тот объект, что был создан где-то внутри". Проверка идентичности через `assertIs(a, b)` оправдана, например, при тестировании кэширующего декоратора, где важно убедиться, что повторный вызов вернул именно закешированный объект, а не пересчитанную копию с таким же содержимым.
- **Частые ошибки:** Ожидают от `==`/`assertEqual` поведения идентичности и удивляются, что "тест не ловит баг", хотя баг на самом деле не в равенстве значений. Также путают это с проблемой мутируемости: если тест сравнивает объект с самим собой после его последующей мутации в другом месте теста, он может "пройти" не из-за корректности логики, а из-за того, что сравниваются два имени, указывающих на один и тот же изменённый объект.

**Пример / кейс**
```python
def build_payload():
    return {"ids": [1, 2, 3], "meta": {"source": "api"}}

result = build_payload()
expected = {"ids": [1, 2, 3], "meta": {"source": "api"}}

print(result == expected)       # True — сравнение по значению, разные объекты
print(result is expected)        # False — это действительно два разных объекта

cache = {}
def cached_build():
    if "payload" not in cache:
        cache["payload"] = build_payload()
    return cache["payload"]

a = cached_build()
b = cached_build()
print(a is b)   # True — здесь важно именно это: один и тот же объект из кэша
```
### 49. [Q-03-01-0049] Иерархия классов сервиса обработки заказов выросла до пяти уровней наследования с переопределением поведения на каждом уровне, и команда жалуется, что изменение базового класса непредсказуемо ломает подклассы. Как бы вы решали вопрос наследования против композиции в этой ситуации? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
Глубокое наследование создаёт жёсткую связанность между уровнями иерархии и делает локальные изменения базового класса потенциально опасными для всех потомков (fragile base class problem); переход к композиции — сборке поведения из небольших, независимо тестируемых объектов-стратегий/сервисов, внедряемых через конструктор — обычно снижает эту связанность, но требует более явного проектирования интерфейсов и не бесплатен в смысле читаемости и количества объектов.

**Разбор**
- **Как это работает:** При наследовании подкласс неявно зависит от внутренней реализации родителя (какие методы вызывают друг друга, в каком порядке, какие инварианты поддерживаются), а не только от его публичного контракта — изменение этой внутренней механики в базовом классе может незаметно для автора изменения сломать логику в далёких потомках. Композиция заменяет "является" (is-a) на "использует" (has-a): объект работы с заказом получает нужное поведение (расчёт скидки, уведомление, валидацию) как отдельные объекты-коллаборанты через явные интерфейсы, и изменение одного коллаборанта не затрагивает остальных, пока контракт интерфейса не меняется.
- **На практике:** Перенос с наследования на композицию — это рефакторинг, который стоит делать постепенно: выделить нестабильные, часто переопределяемые участки поведения в отдельные протоколы/классы-стратегии, оставив неглубокое наследование там, где оно действительно отражает устойчивую иерархию типов (например, разные варианты одного интерфейса с минимальной переопределённой логикой). Критерий выбора — частота и характер изменений: если поведение на разных уровнях меняется независимо и часто, композиция снижает риск регрессий; если иерархия стабильна и уровни меняются синхронно, глубина наследования может быть приемлема.
- **Частые ошибки:** Механически заменяют всё наследование композицией без оценки реальной стоимости рефакторинга (миграция существующих подклассов, тесты, время команды) и рискуют получить избыточно многословный код с большим количеством мелких интерфейсов там, где простая иерархия из двух уровней работала бы прекрасно. Также путают "глубина наследования — это плохо" с "наследование — это плохо": проблема не в наследовании как инструменте, а в его неограниченной глубине и смешении уровней абстракции внутри одной иерархии.
- **Компромисс:** Композиция обычно снижает хрупкость и улучшает тестируемость по отдельности, но увеличивает количество объектов, интерфейсов и мест, где нужно явно связать зависимости (вручную или через DI-контейнер), что может замедлить онбординг новых разработчиков и усложнить навигацию по коду. Решение зависит от реальной частоты изменений в каждом уровне иерархии, размера команды и того, насколько критично для бизнеса минимизировать регрессии при доработке заказа.

**Пример / кейс**
```python
# Было: пятиуровневая иерархия, где каждый подкласс переопределяет шаги обработки
class Order: ...
class DiscountedOrder(Order): ...
class DiscountedInternationalOrder(DiscountedOrder): ...
# ломается непредсказуемо при изменении Order.process()

# Альтернатива: композиция стратегий, внедряемых явно
class Order:
    def __init__(self, discount_strategy, shipping_strategy):
        self.discount_strategy = discount_strategy
        self.shipping_strategy = shipping_strategy

    def total(self, base_amount):
        discounted = self.discount_strategy.apply(base_amount)
        return self.shipping_strategy.add_cost(discounted)

# Изменение одной стратегии не затрагивает Order и другие стратегии напрямую
```
### 50. [Q-03-01-0050] В библиотеке команда предлагает использовать метакласс для автоматической регистрации всех подклассов плагинов в общем реестре. Когда метаклассы действительно оправданы по сравнению с альтернативами (__init_subclass__, декоратор класса), и какие риски несёт их использование в командном коде? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
Метакласс оправдан, когда нужно контролировать сам процесс создания класса (изменить namespace до создания, проверить структуру нескольких классов согласованно, вмешаться в наследование на уровне, недоступном для __init_subclass__), но для большинства задач регистрации подклассов или простой валидации достаточно более простых и предсказуемых механизмов — __init_subclass__ (хук, вызываемый при создании любого подкласса) или декоратора класса — которые не меняют семантику наследования для всей иерархии и легче понимаются командой.

**Разбор**
- **Как это работает:** Метакласс — это "класс класса": он управляет вызовом `type(name, bases, namespace)` и может переопределить `__new__`/`__init__` на уровне создания самого класса, то есть видит весь процесс до того, как класс полностью сформирован, включая возможность менять набор атрибутов, список базовых классов и порядок MRO. `__init_subclass__(cls, **kwargs)` — это обычный classmethod-хук, который Python вызывает автоматически на базовом классе при создании любого его подкласса, уже после того как подкласс создан — этого достаточно для большинства сценариев "сделать что-то при наследовании", включая регистрацию в реестре, без необходимости писать полноценный метакласс.
- **На практике:** Для задачи "автоматически регистрировать каждый подкласс Plugin в словаре реестра" `__init_subclass__` решает её напрямую, прозрачно для читателя (логика находится в самом базовом классе Plugin, а не в отдельном, менее очевидном объекте-метаклассе) и не создаёт конфликтов, если позже понадобится использовать другой метакласс (например, из ORM-библиотеки) в той же иерархии — совмещать два разных метакласса в одной иерархии классов сложно или невозможно без явного объединения, тогда как `__init_subclass__` совместим почти всегда.
- **Частые ошибки:** Берутся за метакласс как за "мощный и интересный" инструмент без явной необходимости в контроле над самим процессом создания класса, из-за чего команда получает малопонятный, трудный для дебага код (ошибки в метаклассе проявляются загадочно, на этапе импорта модуля, а не вызова). Также не учитывают, что сторонние библиотеки (ORM, сериализаторы), уже использующие свой метакласс для базового класса, могут конфликтовать с добавлением второго, несовместимого метакласса в той же иерархии.
- **Компромисс:** Метаклассы дают максимальный контроль и могут решить задачи, недоступные другим механизмам (например, динамическая генерация атрибутов на основе анализа всего namespace класса до его создания), но платят за это сложностью, трудной отлаживаемостью и риском конфликта с метаклассами сторонних библиотек; `__init_subclass__` и декораторы класса покрывают подавляющее большинство практических случаев с меньшим когнитивным весом, и выбор метакласса должен быть осознанным исключением, а не стандартным инструментом команды.

**Пример / кейс**
```python
class Plugin:
    registry = {}

    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        Plugin.registry[cls.__name__] = cls   # автоматическая регистрация без метакласса

class CsvExporter(Plugin):
    pass

class JsonExporter(Plugin):
    pass

print(Plugin.registry)
# {'CsvExporter': <class '...CsvExporter'>, 'JsonExporter': <class '...JsonExporter'>}
```
### 51. [Q-03-01-0051] Команда предлагает использовать дескрипторы (descriptor protocol) для реализации полей с валидацией в собственном ORM-подобном слое вместо property на каждом поле. Какие преимущества и риски несёт этот подход на уровне архитектуры и поддержки кода? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
Дескриптор позволяет один раз описать логику валидации/преобразования и переиспользовать её декларативно на множестве полей многих классов без повторения кода property для каждого поля, но переносит часть логики на менее очевидный уровень протокола __get__/__set__, что увеличивает порог входа для разработчиков, не знакомых с этим механизмом, и усложняет отладку по сравнению с явным property на каждом поле.

**Разбор**
- **Как это работает:** Дескриптор — объект, определяющий `__get__`, `__set__` и/или `__delete__`, который при присвоении атрибуту класса (не экземпляра) перехватывает доступ к этому имени у всех экземпляров класса: `instance.field` фактически вызывает `Field.__get__(descriptor, instance, owner)`, а `instance.field = value` — `Field.__set__(descriptor, instance, value)`. В отличие от property, которая создаётся заново для каждого атрибута через декоратор прямо в классе, дескриптор — это отдельный переиспользуемый класс, который можно параметризовать (тип, диапазон значений, обязательность) и применять к множеству полей разных классов одной и той же реализацией.
- **На практике:** Дескрипторы оправданы, когда одинаковая логика валидации/преобразования повторяется на множестве полей (например, `PositiveNumber`, `NonEmptyString`, `ForeignKeyField` в ORM) — это именно тот сценарий, которым пользуются настоящие ORM и сериализаторы (Django ORM, SQLAlchemy, Pydantic во многом построены на похожих идеях). Если валидация специфична для одного-двух полей конкретного класса, property остаётся проще для чтения и сопровождения, так как логика видна прямо в месте использования, а не в отдельном переиспользуемом классе дескриптора.
- **Частые ошибки:** Забывают разницу между дескриптором данных (определяет `__set__`, имеет приоритет над `__dict__` экземпляра) и недескриптором/дескриптором не-данных (только `__get__`), из-за чего получают неожиданное поведение при попытке переопределить значение атрибута на уровне экземпляра. Также хранят состояние поля непосредственно в самом объекте-дескрипторе (который один на класс, а не на экземпляр) вместо `instance.__dict__` — это приводит к тому, что значение поля становится общим для всех экземпляров класса, повторяя классическую ошибку общего mutable-состояния, но на уровне протокола дескрипторов, что сложнее диагностировать.
- **Компромисс:** Выигрыш в переиспользуемости и декларативности достаётся по цене дополнительного уровня абстракции, который часть команды может плохо понимать, что увеличивает время онбординга и риск тонких багов (особенно с хранением состояния по экземплярам, а не по классу). Решение должно учитывать, сколько полей и классов реально выигрывают от переиспользования логики, и готова ли команда инвестировать в обучение и документирование этого внутреннего слоя — для небольшого числа полей цена абстракции может не оправдаться.

**Пример / кейс**
```python
class PositiveNumber:
    def __set_name__(self, owner, name):
        self.private_name = f"_{name}"

    def __get__(self, instance, owner):
        return getattr(instance, self.private_name, None)

    def __set__(self, instance, value):
        if value <= 0:
            raise ValueError(f"Значение должно быть положительным, получено {value}")
        setattr(instance, self.private_name, value)   # хранится в __dict__ экземпляра!

class Product:
    price = PositiveNumber()
    stock = PositiveNumber()

    def __init__(self, price, stock):
        self.price = price
        self.stock = stock

p1 = Product(100, 5)
p2 = Product(200, 10)
print(p1.price, p2.price)   # 100 200 — значения независимы по экземплярам
```
### 52. [Q-03-01-0052] Вы проектируете иерархию исключений для библиотеки доступа к данным, которую используют несколько независимых команд в компании. Как определить гранулярность исключений (один общий класс ошибки против десятков узкоспециализированных) с учётом обратной совместимости публичного контракта библиотеки? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
Гранулярность иерархии исключений должна отражать реальные различия в том, как вызывающий код должен реагировать на ошибку (повторить операцию, прервать транзакцию, показать пользователю конкретное сообщение), а не внутреннюю детализацию реализации библиотеки; устойчивый подход — ограниченное число стабильных публичных базовых классов исключений с возможностью добавлять более специфичные подклассы без слома уже написанного кода, который перехватывает базовые классы.

**Разбор**
- **Как это работает:** Если библиотека предоставляет только один общий `DataAccessError`, вызывающий код не может различить "временная сетевая проблема, стоит повторить" и "данные нарушают ограничение целостности, повторять бессмысленно" без парсинга текста ошибки, что хрупко и ломается при изменении формулировок. Если библиотека рассыпает десятки узких классов ошибок без общей структуры, внешний код вынужден либо перехватывать каждый класс по отдельности, либо ловить общий `Exception`, теряя весь смысл специализации; правильная практика — выстроить неглубокую иерархию (`DataAccessError` → `TransientError` / `IntegrityError` / `NotFoundError` и т.п.), где подклассы можно продолжать добавлять, не трогая уже объявленные базовые классы.
- **На практике:** Публичный контракт исключений library-кода стоит рассматривать как часть API наравне с сигнатурами функций: добавление нового более специфичного подкласса обычно безопасно (код, перехватывающий родителя, продолжит работать), а удаление или переименование существующего класса, или изменение его места в иерархии — это breaking change, требующий отдельного major-релиза или периода депрекации. Разные команды-потребители с разными требованиями (одним нужна гранулярная обработка retry-логики, другим достаточно "упало — залогировали и вернули 500") обе могут быть обслужены одной и той же неглубокой, но продуманной иерархией, если верхнеуровневые классы выбраны по осям, релевантным именно реакции на ошибку.
- **Частые ошибки:** Проектируют иерархию исключений исходя из внутренней структуры реализации (отдельный класс ошибки на каждый внутренний модуль или драйвер БД) вместо того, чтобы отразить различия, важные для вызывающей стороны — в результате при внутреннем рефакторинге библиотеки приходится либо менять публичные классы исключений (breaking change), либо множить дублирующие классы. Также не документируют и не тестируют, какие именно классы исключений являются частью публичного контракта, из-за чего случайное изменение внутреннего исключения, от которого ничего не наследуется явно, тихо ломает код потребителей, перехватывавших его по имени.
- **Компромисс:** Более гранулярная иерархия даёт потребителям точный контроль над обработкой разных сценариев отказа, но увеличивает площадь публичного API, которую нужно поддерживать стабильной годами и документировать; слишком общая иерархия проще поддерживать автору библиотеки, но перекладывает сложность различения причин ошибки на всех потребителей. Критерий выбора — ожидаемое число различных стратегий обработки ошибок у реальных потребителей и готовность команды библиотеки поддерживать совместимость каждого публичного класса отдельно.

**Пример / кейс**

```python
class TransientError(DataAccessError):

class IntegrityError(DataAccessError):

class NotFoundError(DataAccessError):
    """Запрошенная запись не найдена."""

def fetch_user(user_id):
```

### 53. [Q-03-01-0053] При выборе между потоками, процессами и asyncio для сервиса, который одновременно выполняет CPU-интенсивный парсинг и много сетевых запросов к внешним API, как GIL влияет на это архитектурное решение, и какие компромиссы возникают при каждом варианте? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
GIL (Global Interpreter Lock) в CPython разрешает только одному потоку выполнять Python-байткод в любой момент времени, поэтому потоки (threading) не ускоряют CPU-bound вычисления, но хорошо подходят для I/O-bound ожидания (сеть, диск), где GIL освобождается во время блокирующего вызова; процессы (multiprocessing) дают реальный параллелизм для CPU-bound кода за счёт отдельных интерпретаторов и памяти на каждый процесс, а asyncio даёт высокую конкурентность для I/O-bound задач в одном потоке без накладных расходов на переключение ОС-потоков, но не распараллеливает CPU-bound вычисления и требует неблокирующих (async-совместимых) библиотек на всём пути выполнения.

**Разбор**
- **Как это работает:** GIL — это механизм CPython (не свойство языка Python как спецификации), гарантирующий потокобезопасность интерпретатора за счёт того, что байткод одного потока выполняется, пока другие ждут; большинство операций блокирующего I/O (сетевой сокет, чтение файла) реализованы так, что GIL временно освобождается на время ожидания ОС, поэтому несколько потоков могут параллельно "ждать" ответ от разных внешних сервисов, даже не выполняя Python-код параллельно. CPU-интенсивный парсинг (регулярные выражения на больших данных, числовые вычисления на чистом Python) выполняется байткодом, который держит GIL почти всё время, поэтому добавление потоков для такой работы не даёт ускорения на многоядерной машине — для реального параллелизма вычислений нужны отдельные процессы (каждый со своим интерпретатором и GIL) или C-расширения, освобождающие GIL на время вычислений (например, некоторые операции NumPy).
- **На практике:** Для сервиса с сочетанием CPU-bound парсинга и I/O-bound сетевых вызовов разумный подход часто комбинированный: asyncio (или много лёгких потоков) для конкурентных сетевых запросов к внешним API, и выделение CPU-тяжёлого парсинга в отдельный пул процессов (`concurrent.futures.ProcessPoolExecutor`) или отдельный сервис/воркер, чтобы не блокировать event loop и не держать GIL во время тяжёлых вычислений. Выбор зависит от объёма CPU-работы относительно I/O-работы, доступного числа ядер, накладных расходов на межпроцессное взаимодействие (сериализация данных между процессами) и от того, насколько библиотеки, нужные для сетевых вызовов, имеют async-совместимые версии.
- **Частые ошибки:** Добавляют потоки, ожидая ускорения CPU-bound кода, и не видят прироста производительности на многоядерной машине, не понимая, что причина — GIL, а не плохая реализация потоков. Также переносят CPU-тяжёлую функцию внутрь async-обработчика без вынесения в отдельный процесс/executor, из-за чего она блокирует единственный поток event loop и замораживает обработку всех остальных конкурентных запросов на время её выполнения — это частая и опасная для продакшена ошибка "блокирующий код внутри асинхронного приложения".
- **Компромисс:** asyncio даёт лучшую масштабируемость по числу одновременных I/O-ожиданий при низких накладных расходах, но требует переписывания или оборачивания блокирующих вызовов и усложняет код (async/await всюду по цепочке вызовов). Процессы дают честный параллелизм для CPU-bound работы, но стоят дороже по памяти (отдельный интерпретатор на процесс) и требуют сериализации данных между процессами, что добавляет накладные расходы и ограничивает типы передаваемых объектов. Выбор правильной комбинации зависит от профиля нагрузки конкретного сервиса, а не от универсального правила "asyncio всегда быстрее" или "многопроцессность всегда лучше для надёжности".

**Пример / кейс**
```python
import asyncio
from concurrent.futures import ProcessPoolExecutor

def cpu_heavy_parse(raw_text: str) -> dict:
    # представим затратный CPU-bound парсинг на чистом Python
    return {"length": len(raw_text)}

async def fetch_external(url: str) -> str:
    await asyncio.sleep(0.1)   # условная имитация сетевого I/O без блокировки GIL
    return f"data from {url}"

async def handle_request(url: str, raw_text: str, pool: ProcessPoolExecutor):
    loop = asyncio.get_running_loop()
    # CPU-bound работа уходит в отдельный процесс, не блокируя event loop
    parse_task = loop.run_in_executor(pool, cpu_heavy_parse, raw_text)
    fetch_task = fetch_external(url)
    parsed, fetched = await asyncio.gather(parse_task, fetch_task)
    return parsed, fetched
```
### 54. [Q-03-01-0054] Публичный dataclass из вашей библиотеки используется десятками внутренних сервисов и сериализуется в JSON. Нужно добавить новое обязательное на бизнес-уровне поле. Как спроектировать это изменение, чтобы не сломать существующих потребителей, и какие варианты эволюции контракта вы рассмотрите? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
Немедленно сделать поле обязательным в коде и в сериализованном формате — это breaking change для всех, кто создаёт объект без нового поля или десериализует старые сообщения без него; безопасная эволюция обычно идёт через добровольный (optional) этап: поле добавляется с безопасным значением по умолчанию или как Optional, старые данные продолжают десериализоваться, а переход к реально обязательному полю выполняется отдельным скоординированным этапом с поддержкой потребителей и периодом депрекации.

**Разбор**
- **Как это работает:** Если поле добавлено как `field: NewType` без значения по умолчанию в существующий `@dataclass`, любой код, создающий объект позиционными/именованными аргументами без этого поля, немедленно перестанет работать (`TypeError: missing required argument`), а код, десериализующий старые JSON-сообщения без этого поля в словарь и передающий его как `**data` в конструктор, упадёт точно так же. Добавление поля со значением по умолчанию (`field: NewType = default` или `Optional[NewType] = None`) сохраняет обратную совместимость конструктора и десериализации, позволяя постепенно обновлять потребителей, которые должны начать заполнять это поле осмысленным значением.
- **На практике:** Типичная последовательность: (1) добавить поле как Optional с безопасным default и задеплоить библиотеку — старые потребители не ломаются; (2) обновить и задеплоить сервисы-производители данных, чтобы они начали заполнять новое поле; (3) добавить мониторинг/алерты на случаи, когда поле всё ещё приходит пустым от каких-то потребителей; (4) только после того, как все знаемые продюсеры подтверждённо заполняют поле, рассмотреть перевод его в по-настоящему обязательное в следующей major-версии библиотеки, задокументированной как breaking change с периодом депрекации. Для JSON-сериализации дополнительно стоит явно решить, как десериализатор обрабатывает отсутствие поля в входящих данных старых версий — это отдельная ось совместимости от конструктора класса на Python-уровне.
- **Частые ошибки:** Добавляют обязательное поле и тестируют только "счастливый путь" с новым кодом на обоих концах, не проверяя обратную совместимость при встрече новой библиотеки со старыми сообщениями/вызовами, которые неизбежно существуют в проде при постепенном деплое. Также путают совместимость конструктора Python-объекта с совместимостью формата сериализации — поле может быть безопасным при создании объекта (есть default), но его отсутствие в JSON может по-прежнему вызывать ошибку в кастомной логике десериализации, если она не обработана отдельно.
- **Компромисс:** Поэтапный подход с default/Optional безопаснее, но требует больше календарного времени, координации между командами-потребителями и временного существования "неполных" данных без нового поля, которые нужно явно обрабатывать в бизнес-логике (что делать, если поле всё ещё отсутствует). Резкое немедленное изменение быстрее для автора библиотеки, но переносит всю стоимость и риск поломки на множество внешних команд одновременно, что при десятках потребителей обычно неприемлемо по операционным рискам.

**Пример / кейс**
```python
from dataclasses import dataclass
from typing import Optional

# Шаг 1: безопасное добавление поля, старые вызовы и JSON без поля продолжают работать
@dataclass
class OrderEvent:
    order_id: str
    amount: float
    currency: str = "RUB"            # уже существующее поле с default
    risk_score: Optional[float] = None  # новое поле — Optional на переходный период

# Старый вызывающий код и старые сообщения без risk_score не ломаются:
old_style = OrderEvent(order_id="o-1", amount=100.0)
print(old_style.risk_score)   # None — потребитель должен уметь обработать этот случай
```

**Уровень:** Senior

**Короткий ответ**<br>
__slots__ может заметно снизить потребление памяти и немного ускорить доступ к атрибутам при массовом создании однотипных мелких объектов, но ограничивает динамичность класса (нельзя произвольно добавлять атрибуты, сложнее совмещается с множественным наследованием и некоторыми библиотеками, ожидающими __dict__), поэтому повсеместное применение без разбора рискует сломать совместимость с существующим кодом и сторонними библиотеками, которые полагаются на динамические атрибуты, monkey-patching или сериализацию через __dict__.

**Разбор**
- **Как это работает:** Экономия памяти от `__slots__` пропорциональна количеству экземпляров и разнице между размером `__dict__` экземпляра (который выделяется для каждого объекта индивидуально и имеет заметный базовый оверхед) и компактным slot-хранилищем на уровне дескрипторов класса; выигрыш особенно заметен именно на больших количествах мелких объектов, что соответствует описанному сценарию кэша. Однако любой код, который сериализует объект через `obj.__dict__` (некоторые реализации pickle, кастомные сериализаторы, debug-инструменты), или который ожидает возможности динамически добавить атрибут объекту (некоторые паттерны мокирования в тестах, декораторы, добавляющие служебные поля), перестанет работать без изменений, если у объекта нет `__dict__`.
- **На практике:** Внедрение стоит начинать с классов, которые действительно создаются в больших количествах и имеют стабильный, точно известный набор полей (записи кэша, узлы структур данных), измеряя реальный эффект на памяти через профилирование (`sys.getsizeof`, `tracemalloc`) в условиях, близких к продакшн-нагрузке, а не на синтетическом микробенчмарке. Для классов с наследованием важно либо применять `__slots__` на всех уровнях иерархии согласованно, либо явно принять, что часть экономии потеряется там, где какой-то уровень иерархии не задаёт `__slots__` (и тогда у потомков появляется `__dict__` в любом случае).
- **Частые ошибки:** Внедряют `__slots__` массово по всей кодовой базе одним большим изменением без оценки, какие классы реально выигрывают по памяти, и получают неожиданные `AttributeError` в местах, где код (возможно, в сторонней библиотеке или тестах) динамически добавлял атрибуты. Также не проверяют поведение сериализации/копирования таких объектов (pickle по умолчанию работает с `__slots__`, но требует, чтобы класс определил нужные методы корректно в более сложных случаях наследования), из-за чего ломаются существующие механизмы сохранения состояния.
- **Компромисс:** Выигрыш в памяти и небольшой выигрыш в скорости доступа к атрибутам стоит потери гибкости класса и риска несовместимости с кодом/библиотеками, ожидающими `__dict__`; решение должно быть точечным — применяться к конкретным классам с измеримым профитом на реальной нагрузке, а не как универсальная практика "для всех классов сразу", особенно в кодовой базе, где не весь код и не все зависимости находятся под полным контролем команды.

**Пример / кейс**
```python
import sys

class CacheEntrySlots:
    __slots__ = ("key", "value", "expires_at")
    def __init__(self, key, value, expires_at):
        self.key, self.value, self.expires_at = key, value, expires_at

class CacheEntryDict:
    def __init__(self, key, value, expires_at):
        self.key, self.value, self.expires_at = key, value, expires_at

e1 = CacheEntrySlots("k", "v", 123)
e2 = CacheEntryDict("k", "v", 123)
print(sys.getsizeof(e1), sys.getsizeof(e2))   # slots-версия заметно компактнее

try:
    e1.extra = "x"     # нельзя добавить произвольный атрибут
except AttributeError as e:
    print("Ошибка:", e)
```
### 56. [Q-03-01-0056] Статусы сущности в вашей системе (например, состояние обработки платежа) хранятся в БД как строка и используются множеством сервисов через общую библиотеку. Команда обсуждает, представлять ли их в Python как enum.Enum, typing.Literal или просто строковые константы, учитывая, что набор статусов будет расширяться со временем разными командами. Какие компромиссы вы рассмотрите? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
enum.Enum даёт самый строгий контроль и единый источник истины в runtime, но каждое добавление нового статуса требует релиза общей библиотеки и обновления всех её потребителей; typing.Literal даёт схожую строгость только на уровне статической проверки типов (mypy/pyright) без runtime-гарантий и без накладных расходов на объект enum; простые строковые константы самые гибкие и дешёвые для расширения, но не защищают ни во время выполнения, ни статически от опечаток и несогласованных значений между сервисами.

**Разбор**
- **Как это работает:** `Enum` — это настоящий класс с конечным, явно перечисленным в коде набором членов; проверка принадлежности (`status in OrderStatus`) и исчерпывающий перебор (`list(OrderStatus)`) работают в runtime, но любое новое значение статуса должно появиться как новый член enum именно в этом коде, то есть требует релиза библиотеки, где enum объявлен, и обновления зависимости везде, где он используется. `Literal["pending", "paid", ...]` существует только для статических анализаторов типов — в runtime это обычная строка без каких-либо проверок, поэтому неверное значение не будет отловлено во время выполнения, только при статической проверке типов (и только там, где такая проверка реально подключена в CI). Обычные строковые константы (`STATUS_PENDING = "pending"`) — это просто более читаемые имена для строковых литералов без какой-либо встроенной защиты ни на одном из уровней.
- **На практике:** Если разные команды должны самостоятельно и часто добавлять новые статусы без скоординированного релиза общей библиотеки у всех потребителей, строгий `Enum` в общей библиотеке становится операционным узким местом — каждое добавление статуса блокируется на релиз и обновление зависимости у всех. В этом случае практичным компромиссом может быть менее строгая runtime-модель (строка + документированный, но не являющийся исчерчерпывающим enum список "известных на этот момент" значений для автодополнения и статической проверки через `Literal` там, где это осмысленно) в сочетании с явной валидацией на границах системы (при записи в БД, при приёме запроса), а не полной enum-защитой во всех внутренних точках кода.
- **Частые ошибки:** Выбирают `Enum` "потому что он самый правильный" без учёта операционной стоимости релизов общей библиотеки при каждом новом статусе, что на практике приводит либо к задержкам в поставке фич командами-потребителями, либо к обходным путям (хранению статуса как произвольной строки "временно", что убивает весь смысл enum). Также полагаются только на `Literal` и статическую проверку типов как единственную защиту, забывая, что любые данные, пришедшие из внешнего источника (БД, HTTP-запрос, сообщение из очереди) не проверяются типизатором в runtime и могут содержать произвольное значение, если нет отдельной явной валидации.
- **Компромисс:** Чем строже механизм (Enum), тем выше гарантии согласованности, но выше стоимость изменения набора значений и координации между командами; чем мягче механизм (строка/Literal), тем быстрее и дешевле расширение, но выше риск расхождения значений между сервисами и отсутствие runtime-защиты. Выбор зависит от того, как часто ожидается добавление новых статусов, сколько команд должно иметь возможность делать это независимо, и насколько критичны последствия рассинхронизации значений статуса между сервисами для бизнес-процесса (например, для платежей ошибка в статусе намного дороже, чем для внутреннего технического лейбла).

**Пример / кейс**
```python
from enum import Enum
from typing import Literal

class PaymentStatus(Enum):    # строгий runtime-контроль, но требует релиза при расширении
    PENDING = "pending"
    PAID = "paid"
    FAILED = "failed"

KnownStatus = Literal["pending", "paid", "failed"]   # только статическая подсказка, без runtime-проверки

def validate_status_from_db(raw: str) -> str:
    # явная граница системы: валидация независимо от того, какой подход выбран для типов
    known = {s.value for s in PaymentStatus}
    if raw not in known:
        raise ValueError(f"Неизвестный статус платежа из БД: {raw!r}")
    return raw
```
### 57. [Q-03-01-0057] В сервисе обработки заказов команда спорит между "богатой" объектной моделью (методы бизнес-логики на самом объекте Order) и анемичной моделью (Order как простой контейнер данных, вся логика — в отдельных сервисных функциях/классах). Как бы вы выбирали подход для конкретной части системы, и какие риски несёт каждый вариант в Python backend? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
Богатая модель инкапсулирует инварианты и поведение рядом с данными, что облегчает их защиту от нарушения и тестирование объекта в изоляции, но рискует разрастись до объекта с слишком многими ответственностями и скрытыми зависимостями; анемичная модель с отдельными сервисами проще комбинировать и переиспользовать для разных сценариев обработки, но легко приводит к размытой логике, дублирующейся в нескольких сервисах, и к данным, которые можно привести в несогласованное состояние, если не все пути проходят через нужные проверки.

**Разбор**
- **Как это работает:** В богатой модели методы, изменяющие состояние объекта (`order.cancel()`, `order.add_item(item)`), сами проверяют инварианты (нельзя отменить уже отправленный заказ, нельзя добавить товар в оплаченный заказ) — любой код, вызывающий эти методы, автоматически получает защиту от некорректных переходов состояния, потому что проверка находится в одном месте, а не размазана по вызывающему коду. В анемичной модели `Order` — это, по сути, dataclass с полями, а проверки и переходы состояния реализованы в отдельных функциях/сервисах (`OrderService.cancel(order)`), которые сами решают, что можно, а что нет — если появляется второй сервис, изменяющий тот же объект без тех же проверок, инвариант можно случайно нарушить в обход первого сервиса.
- **На практике:** Богатая модель хорошо подходит для core-домена с устойчивыми, явными бизнес-правилами, которые должны соблюдаться всегда и везде, независимо от вызывающего кода (это соответствует идеям domain-driven design об агрегатах, защищающих свои инварианты). Анемичная модель с сервисами часто удобнее на границах системы (API-слой, интеграции, ETL), где объекты по сути являются DTO для передачи данных между слоями/сервисами, а бизнес-правила либо отсутствуют, либо принадлежат другому слою (например, правила валидации на уровне HTTP-запроса, а не домена).
- **Частые ошибки:** Делают Order богатым объектом, но одновременно позволяют внешнему коду напрямую изменять его поля, минуя методы с проверками (`order.status = "cancelled"` напрямую вместо `order.cancel()`), из-за чего инкапсуляция инвариантов становится фиктивной. В анемичной модели — размещают схожую логику валидации в нескольких независимых сервисах, которые постепенно расходятся в поведении при изменениях одной из копий, что порождает трудно диагностируемые несоответствия между частями системы.
- **Компромисс:** Богатая модель повышает согласованность данных и локальность бизнес-правил, но увеличивает размер и ответственность объекта и может затруднить переиспользование отдельных операций в контекстах, где нужна лишь часть логики. Анемичная модель облегчает компоновку и переиспользование сервисов, но требует дисциплины, чтобы не дублировать и не расходовать логику валидации по разным местам — выбор зависит от того, насколько критичны инварианты конкретной сущности для бизнеса и сколько независимых путей изменения этой сущности существует в системе.

**Пример / кейс**
```python
# Богатая модель: инвариант защищён внутри объекта
class RichOrder:
    def __init__(self, status="new"):
        self.status = status

    def cancel(self):
        if self.status == "shipped":
            raise ValueError("Нельзя отменить уже отправленный заказ")
        self.status = "cancelled"

# Анемичная модель: данные отдельно, логика — в сервисе
class AnemicOrder:
    def __init__(self, status="new"):
        self.status = status

class OrderService:
    @staticmethod
    def cancel(order: AnemicOrder):
        if order.status == "shipped":
            raise ValueError("Нельзя отменить уже отправленный заказ")
        order.status = "cancelled"
        # риск: другой сервис может присвоить order.status напрямую, минуя эту проверку
```
### 58. [Q-03-01-0058] В коде сервиса встречается сравнение статусов через is вместо == для строковых значений, и один из разработчиков утверждает, что это безопасно, ссылаясь на кеширование маленьких строк и чисел в CPython. Почему такая аргументация рискованна для продакшен-кода, и как бы вы отнеслись к такому паттерну при код-ревью? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
Кеширование маленьких целых чисел (-5..256) и интернирование некоторых строковых литералов — это деталь реализации конкретной версии CPython, а не гарантия языка Python, поэтому код, зависящий от `is` для сравнения значений, может работать случайно на одной версии/сборке интерпретатора и давать иной результат на другой, в другом окружении выполнения или при значениях, пришедших не как литералы (например, построенных конкатенацией в runtime); правильная практика — всегда использовать `==` для сравнения значений и оставлять `is` только для сравнения идентичности объектов и синглтонов (`None`, `True`, `False`).

**Разбор**
- **Как это работает:** CPython по соображениям производительности кеширует небольшие целые числа и интернирует некоторые строки (в основном короткие идентификатор-подобные литералы, определяемые во время компиляции), поэтому два отдельных литерала с одинаковым маленьким значением иногда действительно оказываются одним и тем же объектом в памяти, и `is` между ними возвращает `True`. Но это оптимизация реализации, не являющаяся частью языковой спецификации: она не гарантирована для строк, полученных во время выполнения (например, через `str(x)`, конкатенацию, `.format()`, чтение из файла/сети/БД), и может отличаться между версиями CPython или вообще не выполняться в альтернативных реализациях (PyPy и другие).
- **На практике:** На код-ревью такой паттерн стоит трактовать как потенциальный баг, а не как "преждевременную оптимизацию, которая просто странно выглядит": строка статуса, прочитанная из БД, десериализованная из JSON или полученная из внешнего API, почти никогда не будет тем же самым интернированным объектом, что строковый литерал в коде, даже если их текстовое значение совпадает — `is` в этом случае может молча вернуть `False` там, где `==` вернул бы ожидаемый `True`, и приложение примет неверную бизнес-логику без явной ошибки, что особенно опасно, так как баг проявляется не всегда, а в зависимости от того, как именно строка была создана.
- **Частые ошибки:** Пишут код, который "работает на машине разработчика" именно из-за совпадения деталей реализации интернирования для конкретных литералов, и не замечают проблему до тех пор, пока то же сравнение не столкнётся со строкой иного происхождения (из БД, после сериализации) в продакшене. Также путают `is` для `None`/`True`/`False` (где это действительно правильная и идиоматичная практика, так как это настоящие синглтоны, гарантированные языком) с `is` для произвольных строк/чисел, где такой гарантии нет.
- **Компромисс:** Строгого компромисса здесь по сути нет — для сравнения значений правильный инструмент почти всегда `==`, и отступать от этого правила в пользу `is` оправдано только в узких, явно документированных случаях работы с действительно синглтон-подобными объектами на уровне самого приложения (например, собственный sentinel-объект `_UNSET = object()`, созданный и используемый ровно как один объект). Обсуждение на ревью должно смещаться не к "может сработать", а к тому, что корректность кода не должна зависеть от деталей реализации интерпретатора, которые явно не документированы как гарантия.

**Пример / кейс**
```python
a = "pending"
b = "pending"
print(a is b)         # True на CPython для таких литералов — деталь реализации

c = "pend" + "ing"      # собрано в runtime из частей
print(a is c)           # не гарантировано True, часто False

status_from_db = str("pending")   # смоделируем значение, пришедшее не как литерал
print(a == status_from_db)   # True — корректно работает всегда
print(a is status_from_db)   # ненадёжно, не гарантировано

SENTINEL = object()   # для настоящих синглтонов приложения is — правильный инструмент
def get(value=SENTINEL):
    return value is SENTINEL
```
### 59. [Q-03-01-0059] Класс в вашем многопоточном backend-сервисе хранит счётчик обработанных запросов как обычный атрибут int, инкрементируемый из нескольких потоков через self.counter += 1. Коллеги утверждают, что GIL делает это безопасным. Разберите, насколько это верно, и как бы вы спроектировали потокобезопасный доступ к общему состоянию в такой ситуации. Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
GIL гарантирует, что в любой момент выполняется только один поток байткода, но составная операция `self.counter += 1` на уровне байткода разбивается на несколько шагов (прочитать текущее значение, вычислить новое, записать обратно), и между этими шагами GIL может быть передан другому потоку, который успеет выполнить такую же составную операцию над тем же значением — в результате возможна потеря обновлений (race condition) даже при наличии GIL; надёжное решение — явная синхронизация (threading.Lock) вокруг составной операции или использование атомарных примитивов, спроектированных для конкурентного доступа.

**Разбор**
- **Как это работает:** GIL защищает внутреннюю целостность самого интерпретатора (например, от повреждения внутренних структур CPython при одновременном выполнении байткода двумя потоками), но не превращает составные операции над объектами Python в атомарные с точки зрения бизнес-логики. `counter += 1` компилируется в несколько байткод-инструкций (загрузка текущего значения атрибута, сложение, сохранение нового значения), и GIL может переключиться на другой поток между любыми двумя байткод-инструкциями (например, при превышении лимита переключения потоков или при любой операции, явно/неявно отпускающей GIL) — если второй поток в этот момент тоже читает старое значение counter и увеличивает его, одно из двух увеличений будет потеряно при записи.
- **На практике:** Надёжный способ защитить составную операцию — обернуть её в `threading.Lock` (`with self._lock: self.counter += 1`), что гарантирует, что чтение-изменение-запись выполняется как единый, не прерываемый другими потоками блок относительно этого конкретного лока. Альтернативы: использовать потокобезопасные примитивы из модуля `queue`/`collections` там, где они покрывают нужный сценарий, либо вообще избегать общего mutable-состояния между потоками, агрегируя локальные счётчики каждого потока и суммируя их в конце (если бизнес-логика это допускает), что убирает необходимость в синхронизации вовсе.
- **Частые ошибки:** Полагаются на "GIL делает код потокобезопасным" как на общее правило, не проверяя, что конкретная операция действительно атомарна на уровне байткода (простые перестановки/присваивания отдельных неизменяемых значений часто действительно атомарны, но составные read-modify-write операции — нет). Также добавляют блокировку на каждую отдельную простую операцию без анализа, не приводит ли это к избыточной конкуренции за лок и падению производительности в горячем пути, вместо того чтобы спроектировать более крупную единицу синхронизации или вовсе другую модель состояния.
- **Компромисс:** Блокировки гарантируют корректность, но вносят конкуренцию за лок, что может стать узким местом при высокой частоте обращений из многих потоков, и требует дисциплины, чтобы не создать deadlock при использовании нескольких локов одновременно. Более радикальная альтернатива — вынести такие счётчики в асинхронную модель с одним потоком (устранить многопоточность для этого состояния целиком) или в отдельное хранилище, спроектированное для конкурентных атомарных операций (например, атомарный счётчик в Redis) — выбор зависит от того, насколько критична точность счётчика, частота операций и общая архитектура сервиса.

**Пример / кейс**
```python
import threading

class RequestCounterUnsafe:
    def __init__(self):
        self.counter = 0

    def increment(self):
        self.counter += 1     # read-modify-write — не атомарно, возможна потеря обновлений

class RequestCounterSafe:
    def __init__(self):
        self.counter = 0
        self._lock = threading.Lock()

    def increment(self):
        with self._lock:          # гарантирует атомарность составной операции
            self.counter += 1

def run_many_threads(counter_obj, n_threads=20, n_increments=5000):
    def worker():
        for _ in range(n_increments):
            counter_obj.increment()
    threads = [threading.Thread(target=worker) for _ in range(n_threads)]
    for t in threads: t.start()
    for t in threads: t.join()
    return counter_obj.counter   # у Unsafe-версии итог часто < n_threads * n_increments
```
### 60. [Q-03-01-0060] Широко используемая внутренняя библиотека поднимает один общий DataError для всех ошибок слоя данных. Для мажорной версии 2.0 команда решает разделить его на несколько более специфичных подклассов, сохранив DataError как общий родитель. Как спроектировать этот рефакторинг и его выпуск, чтобы минимизировать риск для десятков потребителей библиотеки? Обсудите компромиссы, риски и критерии выбора — единственного правильного решения может не быть.

**Направление:** Python Backend Developer<br>
**Тема:** Основы Python: типы данных, коллекции, функции, области видимости, исключения, ООП и модель объектов<br>
**Уровень:** Senior

**Короткий ответ**<br>
Если новые специфичные классы становятся настоящими подклассами существующего DataError и возбуждаются вместо него (а не вместе с полной заменой типа в местах, где raise возбуждал ровно DataError), весь код потребителей, перехватывающий `except DataError`, продолжает работать без изменений благодаря полиморфизму исключений, а потребители, которым нужна более точная обработка, могут постепенно переходить на перехват конкретных подклассов — риск сохраняется там, где потребители делают более узкие и хрупкие проверки (например, `type(exc) is DataError`, сравнение типа без учёта наследования) или полагаются на текст сообщения ошибки.

**Разбор**
- **Как это работает:** Механизм перехвата исключений в Python проверяет принадлежность классу через `isinstance`, который учитывает всю цепочку наследования — поэтому `except DataError:` продолжит перехватывать `ConnectionDataError(DataError)` и `ValidationDataError(DataError)` ровно так же, как раньше перехватывал голый `DataError`, если структура наследования правильно построена и библиотека просто начинает возбуждать более специфичные подклассы вместо родителя в тех же самых точках кода, где раньше возбуждался только родитель. Ломается именно тот код, который либо проверяет точный тип исключения без учёта наследования (`type(exc) is DataError`, а не `isinstance(exc, DataError)`), либо парсит текст сообщения ошибки как часть своей логики, либо зависит от того, что `DataError` — финальный, не расширяемый класс (например, через паттерн-матчинг по множеству атрибутов, специфичных только для старой версии).
- **На практике:** Безопасный план релиза 2.0: ввести новые подклассы и начать возбуждать именно их (сохраняя наследование от `DataError`) без удаления и без изменения смысла самого `DataError`; задокументировать в changelog, что `DataError` остаётся валидным способом перехвата "любой ошибки данных", а новые подклассы — опциональное уточнение; при необходимости предоставить период, когда и старое, и новое поведение видимы одновременно (например, отдельный флаг или минорная версия 1.x, которая уже возбуждает подклассы, прежде чем 2.0 удалит что-либо ещё). Важно заранее опросить или иным образом оценить, какие потребители используют хрупкие паттерны проверки типа или парсинга сообщений, и явно предупредить их перед релизом, а не полагаться только на формальную корректность наследования.
- **Частые ошибки:** Разработчики библиотеки предполагают, что раз наследование формально корректно, миграция автоматически безопасна для всех, и не учитывают реальные паттерны использования исключений у потребителей (сравнение точного типа, парсинг сообщения, сериализация типа исключения в лог/метрику, которая теперь покажет другое имя класса и может сломать алерты, настроенные на конкретную строку). Также полностью убирают возможность возбуждать именно `DataError` напрямую, вместо того чтобы на переходный период оставить его доступным как fallback для случаев, не покрытых новыми специфичными подклассами.
- **Компромисс:** Более гранулярная иерархия исключений даёт потребителям точный контроль, но увеличивает площадь поверхности изменений при каждом релизе библиотеки и требует явной коммуникации и версионирования; сохранение единственного общего исключения проще поддерживать, но оставляет всех потребителей без возможности различать сценарии ошибок программно. Риск и объём работы на стороне библиотеки и потребителей нужно сопоставить с реальной потребностью в более точной обработке ошибок у большинства из десятков команд, а не проектировать иерархию исходя только из внутреннего удобства авторов библиотеки.

**Пример / кейс**
```python
# До 2.0: один общий класс для всех ошибок слоя данных
class DataError(Exception):
    pass

# В 2.0: добавляем специализированные подклассы, НЕ убирая DataError
class ConnectionDataError(DataError):
    pass

class ValidationDataError(DataError):
    pass

def fetch(record_id):
    raise ConnectionDataError(f"Не удалось получить запись {record_id}")

# Старый код потребителя продолжает работать без изменений благодаря наследованию:
try:
    fetch(42)
except DataError as exc:            # перехватывает и новый ConnectionDataError
    print("Обработано как и раньше:", type(exc).__name__, exc)

# Новый код потребителя может уточнять обработку:
try:
    fetch(42)
except ConnectionDataError:
    print("Специфичная обработка: повторить позже")
except DataError:
    print("Общая обработка прочих ошибок данных")
```
