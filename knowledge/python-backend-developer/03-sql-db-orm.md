### 131. [Q-03-03-0131] Что такое первичный ключ и внешний ключ в реляционной БД и зачем они нужны?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
Первичный ключ (PRIMARY KEY) однозначно идентифицирует строку таблицы и не допускает NULL/дублей, а внешний ключ (FOREIGN KEY) ссылается на первичный (или уникальный) ключ другой таблицы и обеспечивает ссылочную целостность между ними.

**Разбор**
- **Как это работает:** PK создаёт уникальный индекс и ограничение NOT NULL+UNIQUE на одну или несколько колонок; FK добавляет ограничение, что значение колонки должно существовать среди значений PK/UNIQUE родительской таблицы, иначе вставка/обновление отклоняется.
- **На практике:** PK выбирают либо естественный (например, email, если он реально уникален и стабилен), либо суррогатный (SERIAL/UUID); FK настраивают с ON DELETE/ON UPDATE (CASCADE, RESTRICT, SET NULL) в зависимости от бизнес-логики удаления связанных записей.
- **Частые ошибки:** Забывают добавить ON DELETE поведение и получают ошибку при удалении родителя; используют естественный ключ, который со временем меняется (например, email после смены пользователем), что требует болезненной миграции FK.

**Пример / кейс**
```sql
CREATE TABLE authors (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE books (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    author_id INTEGER NOT NULL REFERENCES authors(id) ON DELETE CASCADE
);
-- Удаление автора автоматически удалит все его книги
-- (проверяется: DELETE FROM authors WHERE id = 1; затем SELECT * FROM books;)
```
### 132. [Q-03-03-0132] В чём разница между INNER JOIN и LEFT JOIN? Приведите пример, где результат отличается.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
INNER JOIN возвращает только строки, для которых есть совпадение в обеих таблицах, а LEFT JOIN возвращает все строки левой таблицы, подставляя NULL в колонки правой таблицы, если совпадения нет.

**Разбор**
- **Как это работает:** INNER JOIN выполняет пересечение по условию ON — строка попадает в результат только при наличии совпадения с другой стороны. LEFT JOIN сохраняет все строки левой таблицы независимо от совпадения, дополняя отсутствующие значения NULL.
- **На практике:** LEFT JOIN используют, когда нужно показать все записи «главной» сущности, даже без связанных данных — например, всех пользователей, включая тех, у кого пока нет заказов. INNER JOIN применяют, когда связанные данные обязательны для смысла строки.
- **Частые ошибки:** Добавляют условие на колонку правой таблицы в WHERE вместо ON при LEFT JOIN (например WHERE orders.status = 'paid'), что превращает LEFT JOIN обратно в INNER JOIN, отфильтровывая пользователей без заказов.

**Пример / кейс**
```sql
SELECT u.id, u.name, COUNT(o.id) AS orders_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;
-- Пользователь без заказов попадёт в результат с orders_count = 0
-- При INNER JOIN вместо LEFT JOIN такой пользователь исчезнет из результата
```
### 133. [Q-03-03-0133] Как работают GROUP BY и агрегатные функции (COUNT, SUM, AVG)? Почему в запросе с GROUP BY нельзя просто добавить любую колонку в SELECT?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
GROUP BY группирует строки по значениям указанных колонок, а агрегатные функции считают значение по каждой группе; в SELECT можно использовать только колонки из GROUP BY или результаты агрегатных функций, иначе непонятно, какое значение негруппированной колонки показывать для группы из нескольких строк.

**Разбор**
- **Как это работает:** СУБД сначала логически разбивает результат на группы по значениям указанных колонок, затем применяет агрегатную функцию к каждой группе отдельно, возвращая одну строку на группу.
- **На практике:** Типичная ошибка — попытка вывести негруппированную колонку «для примера»; PostgreSQL в этом случае выдаст ошибку компиляции запроса, в отличие от некоторых других СУБД, которые могут вернуть произвольное значение.
- **Частые ошибки:** Путают HAVING и WHERE, забывают, что WHERE фильтрует строки до группировки и не может ссылаться на результат агрегатной функции.

**Пример / кейс**
```sql
SELECT department_id, COUNT(*) AS employees, AVG(salary) AS avg_salary
FROM employees
GROUP BY department_id;
-- Ошибка в PostgreSQL, если добавить employees.name в SELECT без агрегатной функции и без GROUP BY по ней:
-- ERROR: column "employees.name" must appear in the GROUP BY clause or be used in an aggregate function
```
### 134. [Q-03-03-0134] Чем HAVING отличается от WHERE и когда каждое из них применяется?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
WHERE фильтрует отдельные строки до группировки, а HAVING фильтрует уже готовые группы после агрегации — то есть HAVING может ссылаться на результат агрегатной функции, а WHERE нет.

**Разбор**
- **Как это работает:** Порядок логического выполнения запроса: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. WHERE отбрасывает строки до группировки, снижая объём данных для агрегации; HAVING применяется уже к результатам COUNT/SUM/AVG по каждой группе.
- **На практике:** Если условие можно сформулировать на уровне отдельной строки (например, status = 'active'), его стоит вынести в WHERE — это эффективнее. HAVING используют только для условий на агрегат, например HAVING COUNT(*) > 5.
- **Частые ошибки:** Пытаются написать WHERE COUNT(*) > 5 — это синтаксическая ошибка, так как на момент WHERE агрегат ещё не вычислен; либо необоснованно переносят в HAVING условия, которые можно и нужно проверить в WHERE.

**Пример / кейс**
```sql
SELECT customer_id, COUNT(*) AS orders_count
FROM orders
WHERE status = 'completed'
GROUP BY customer_id
HAVING COUNT(*) > 3;
-- Отбирает только завершённые заказы (WHERE), затем только клиентов с более чем 3 такими заказами (HAVING)
```
### 135. [Q-03-03-0135] Чем ограничение UNIQUE отличается от PRIMARY KEY? Может ли в таблице быть несколько ограничений UNIQUE?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
PRIMARY KEY — это единственное на таблицу ограничение, идентифицирующее строку, автоматически NOT NULL; UNIQUE гарантирует отсутствие дублей в колонке(ах), но допускает NULL (в PostgreSQL несколько NULL допустимы), и таких ограничений может быть сколько угодно.

**Разбор**
- **Как это работает:** Оба ограничения реализуются через уникальный индекс. Разница в семантике: PK один на таблицу и используется как основной идентификатор для внешних ключей, UNIQUE может быть добавлен на любые колонки для бизнес-правил (например, email должен быть уникален).
- **На практике:** Типичный паттерн — SERIAL/UUID как PK для внутренней идентификации плюс UNIQUE на email или на связке колонок (например, (user_id, role_id) для предотвращения дублирования связи).
- **Частые ошибки:** Думают, что UNIQUE запрещает NULL — в PostgreSQL несколько строк с NULL в UNIQUE-колонке допустимы, так как NULL не равен NULL; если нужно запретить больше одной «пустой» записи, нужен отдельный partial unique index.

**Пример / кейс**
```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email TEXT UNIQUE NOT NULL,
    phone TEXT UNIQUE
);
-- INSERT с одинаковым email -> ошибка unique violation
-- INSERT двух строк с phone = NULL -> успешно, так как NULL != NULL
```
### 136. [Q-03-03-0136] Чем отличаются DELETE, TRUNCATE и DROP при работе с таблицей?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
DELETE удаляет строки по условию и может быть отменён в транзакции, TRUNCATE мгновенно очищает всю таблицу без построчной обработки (и в PostgreSQL тоже транзакционен), а DROP полностью удаляет объект таблицы вместе со схемой.

**Разбор**
- **Как это работает:** DELETE построчно проверяет условие WHERE и может вызывать триггеры ON DELETE. TRUNCATE не сканирует строки, быстро освобождает страницы таблицы и по умолчанию сбрасывает SERIAL/IDENTITY, если не указано CONTINUE IDENTITY. DROP удаляет саму структуру таблицы, включая индексы и ограничения.
- **На практике:** DELETE используют, когда нужно удалить часть данных по условию или нужны триггеры; TRUNCATE — для быстрой очистки всей таблицы в тестах/ETL; DROP — при удалении таблицы из схемы, например при откате миграции.
- **Частые ошибки:** Используют DELETE FROM table; без WHERE для очистки большой таблицы — это медленнее TRUNCATE и сильнее нагружает WAL и автовакуум; забывают, что TRUNCATE требует ACCESS EXCLUSIVE lock и блокирует параллельные чтения.

**Пример / кейс**
```sql
BEGIN;
TRUNCATE TABLE sessions RESTART IDENTITY;
-- В PostgreSQL TRUNCATE тоже транзакционен, можно сделать ROLLBACK
ROLLBACK; -- таблица sessions останется нетронутой
```
### 137. [Q-03-03-0137] Что такое индекс в базе данных и как он ускоряет выполнение запросов?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
Индекс — это дополнительная структура данных (обычно B-tree), хранящая упорядоченные значения колонки(ок) со ссылками на строки, что позволяет находить нужные строки за O(log n) вместо полного перебора таблицы (Seq Scan).

**Разбор**
- **Как это работает:** Без индекса СУБД читает все строки таблицы (Sequential Scan), проверяя условие у каждой. Индекс позволяет быстро найти диапазон или точное значение через обход дерева и затем обратиться только к нужным строкам таблицы.
- **На практике:** Индексы ускоряют SELECT с фильтрацией/сортировкой/джойнами по индексируемой колонке, но замедляют INSERT/UPDATE/DELETE, так как индекс нужно поддерживать в актуальном состоянии; план выполнения проверяют через EXPLAIN.
- **Частые ошибки:** Создают индекс «на всякий случай» на каждую колонку, не оценивая рост времени записи и объёма на диске; забывают, что индекс не всегда используется планировщиком при низкой избирательности условия.

**Пример / кейс**
```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- До индекса: Seq Scan on orders (cost=...)
-- После индекса: Index Scan using idx_orders_user_id on orders (cost=...)
```
### 138. [Q-03-03-0138] Как NULL ведёт себя в сравнениях и агрегатных функциях SQL? Почему условие column = NULL никогда не сработает?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
NULL обозначает отсутствие значения, а не конкретное значение, поэтому любое сравнение с NULL через =, !=, <, > возвращает NULL (не true/false), и строка не попадает в результат WHERE; проверять нужно через IS NULL / IS NOT NULL.

**Разбор**
- **Как это работает:** SQL использует трёхзначную логику (TRUE/FALSE/UNKNOWN); WHERE оставляет только строки, где условие дало TRUE, а UNKNOWN отбрасывается так же, как FALSE. Агрегатные функции COUNT(column), SUM, AVG игнорируют NULL-значения.
- **На практике:** Для замены NULL на значение по умолчанию используют COALESCE(column, 'default'); для подсчёта всех строк включая NULL используют COUNT(*), а не COUNT(column).
- **Частые ошибки:** Пишут WHERE column = NULL вместо WHERE column IS NULL и получают пустой результат без ошибки; не учитывают, что NOT IN с подзапросом, содержащим NULL, возвращает пустой результат для всех строк.

**Пример / кейс**
```sql
SELECT COUNT(*) AS total_rows, COUNT(phone) AS rows_with_phone FROM users;
-- COUNT(*) считает все строки, COUNT(phone) пропускает строки где phone IS NULL

SELECT * FROM users WHERE phone = NULL; -- всегда 0 строк, это ошибка в логике
SELECT * FROM users WHERE phone IS NULL; -- корректный способ найти пользователей без телефона
```
### 139. [Q-03-03-0139] Что такое транзакция в БД и что означает аббревиатура ACID?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
Транзакция — это последовательность операций, выполняемая как единое неделимое целое; ACID (Atomicity, Consistency, Isolation, Durability) описывает гарантии, которые СУБД даёт для транзакций: атомарность, согласованность, изолированность и устойчивость к сбоям.

**Разбор**
- **Как это работает:** Atomicity — все операции применяются целиком или не применяются вовсе (ROLLBACK при ошибке); Consistency — после транзакции данные остаются согласованными с ограничениями БД; Isolation — конкурентные транзакции не видят промежуточных незафиксированных изменений друг друга; Durability — после COMMIT данные гарантированно сохранены даже при сбое благодаря WAL.
- **На практике:** Оборачивать в транзакцию нужно логически связанные операции — например, списание денег с одного счёта и зачисление на другой, чтобы при сбое после первой операции вторая не «потерялась».
- **Частые ошибки:** Держат транзакцию открытой слишком долго (например, ждут ответа внешнего API внутри транзакции), удерживая блокировки; забывают явный ROLLBACK при обработке исключения, из-за чего соединение остаётся в состоянии прерванной транзакции.

**Пример / кейс**
```python
with connection.cursor() as cur:
    try:
        cur.execute("BEGIN")
        cur.execute("UPDATE accounts SET balance = balance - 100 WHERE id = 1")
        cur.execute("UPDATE accounts SET balance = balance + 100 WHERE id = 2")
        cur.execute("COMMIT")
    except Exception:
        cur.execute("ROLLBACK")
        raise
```
### 140. [Q-03-03-0140] В каких ситуациях нужно явно использовать COMMIT и ROLLBACK при работе с БД из приложения?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
COMMIT фиксирует все изменения текущей транзакции безвозвратно, а ROLLBACK отменяет их полностью; явный контроль над ними нужен там, где несколько операций должны либо выполниться все вместе, либо не выполниться вообще, и где нужно корректно обработать ошибку.

**Разбор**
- **Как это работает:** При открытии транзакции все последующие изменения видны только внутри неё до COMMIT; при ROLLBACK СУБД откатывает их, используя MVCC-версии строк в PostgreSQL.
- **На практике:** В веб-приложении типичный паттерн — одна транзакция на HTTP-запрос или бизнес-операцию: если все шаги успешны — commit в конце, если возникло исключение — rollback. ORM (Django, SQLAlchemy) предоставляют контекстные менеджеры atomic()/begin(), делающие это автоматически.
- **Частые ошибки:** Забывают явный rollback после исключения, оставляя соединение в состоянии «aborted transaction»; делают commit после каждой отдельной операции там, где нужна атомарность нескольких операций вместе.

**Пример / кейс**
```python
from django.db import transaction

def transfer_money(from_id, to_id, amount):
    with transaction.atomic():
        Account.objects.filter(id=from_id).update(balance=F("balance") - amount)
        Account.objects.filter(id=to_id).update(balance=F("balance") + amount)
    # При исключении внутри блока Django сделает ROLLBACK автоматически
```
### 141. [Q-03-03-0141] Чем отличаются типы VARCHAR(n), TEXT и CHAR(n) в PostgreSQL?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
В PostgreSQL VARCHAR(n) и TEXT хранятся одинаково и не имеют разницы в производительности — VARCHAR(n) лишь добавляет ограничение максимальной длины, TEXT не ограничивает длину вовсе, а CHAR(n) дополняет строку пробелами до фиксированной длины n и почти никогда не нужен в современных приложениях.

**Разбор**
- **Как это работает:** Внутри PostgreSQL все три типа используют один и тот же механизм хранения переменной длины (varlena); VARCHAR(n) добавляет проверку длины при вставке/обновлении, CHAR(n) всегда дополняет строку до n символов пробелами справа.
- **На практике:** Для большинства полей (имена, описания, email) рекомендуется TEXT без ограничения длины на уровне БД, валидацию делать на уровне приложения/ORM; VARCHAR(n) оправдан, когда ограничение длины — реальное бизнес-правило.
- **Частые ошибки:** Выбирают CHAR(n) по привычке из других СУБД, не замечая паддинг пробелами, что ломает сравнение строк; жёстко ограничивают VARCHAR(255) «по умолчанию» без анализа требований.

**Пример / кейс**
```sql

-- b и c хранят ровно 'ab', length(b) = 2
```
### 142. [Q-03-03-0142] Что такое нормализация базы данных? Покажите на примере, как денормализованную таблицу привести к 3NF.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
Нормализация — это процесс структурирования таблиц так, чтобы устранить избыточное дублирование данных и функциональные зависимости, не относящиеся напрямую к первичному ключу; на практике чаще всего ориентируются на 3-ю нормальную форму (3NF), где неключевые атрибуты зависят только от первичного ключа.

**Разбор**
- **Как это работает:** Денормализованная таблица часто хранит повторяющиеся группы атрибутов (например, название и адрес компании в каждой строке заказа); нормализация выносит такие данные в отдельную таблицу со своим PK, а исходная ссылается на неё через FK.
- **На практике:** Нормализация снижает избыточность и риск рассинхронизации данных при обновлении, но увеличивает число JOIN на чтение; в реальных системах иногда сознательно идут на частичную денормализацию для производительности, документируя это решение.
- **Частые ошибки:** Нормализуют «до упора» без учёта паттернов доступа, получая схему с 8-10 JOIN на типовой запрос; либо оставляют дублирование атрибутов компании/клиента в каждой таблице, что приводит к рассинхронизации при обновлении одной копии.

**Пример / кейс**
```sql
-- Денормализовано: company_name и company_address повторяются в каждом заказе
-- orders(id, customer_name, company_name, company_address, amount)

-- После нормализации (3NF):
CREATE TABLE companies (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    address TEXT
);
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    customer_name TEXT NOT NULL,
    company_id INTEGER REFERENCES companies(id),
    amount NUMERIC(12,2) NOT NULL
);
-- Изменение адреса компании теперь требует UPDATE одной строки в companies, а не N строк в orders
```
### 143. [Q-03-03-0143] Как работает автоинкремент первичного ключа в PostgreSQL — через SERIAL и через GENERATED ... AS IDENTITY? Какой вариант предпочтительнее в новом коде?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
SERIAL — «синтаксический сахар», создающий отдельную sequence и DEFAULT на колонку, а GENERATED ... AS IDENTITY (стандарт SQL, PostgreSQL 10+) — более современный и строгий способ, явно привязывающий генерацию значения к колонке; в новом коде предпочтительнее IDENTITY.

**Разбор**
- **Как это работает:** Оба механизма используют один и тот же объект sequence, но SERIAL реализован через DEFAULT nextval('seq_name'), который можно случайно переопределить обычным INSERT с явным значением, тогда как GENERATED ALWAYS AS IDENTITY по умолчанию запрещает указывать значение вручную.
- **На практике:** IDENTITY ближе к стандарту SQL:2003, лучше защищает от случайной перезаписи id и чище выглядит в DDL; SERIAL остаётся широко распространён в legacy-коде и старых примерах.
- **Частые ошибки:** Вручную вставляют id без учёта текущего значения sequence (например, при миграции данных), из-за чего последующий автоинкремент пытается вставить уже занятый id и падает с unique violation — нужно вызвать setval() для синхронизации.

**Пример / кейс**
```sql
-- Старый подход
CREATE TABLE t1 (id SERIAL PRIMARY KEY, name TEXT);

-- Современный подход (PostgreSQL 10+)
CREATE TABLE t2 (id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name TEXT);

-- После ручной вставки с явным id нужно синхронизировать sequence:
SELECT setval(pg_get_serial_sequence('t1', 'id'), (SELECT MAX(id) FROM t1));
```
### 144. [Q-03-03-0144] Как определить простую модель данных в SQLAlchemy с помощью Declarative API?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
Модель описывается как Python-класс, наследующий от общей декларативной базы (Base), с атрибутами класса типа Mapped[...]/mapped_column, задающими колонки таблицы, их типы и ограничения; SQLAlchemy связывает класс с таблицей через атрибут __tablename__.

**Разбор**
- **Как это работает:** При объявлении класса SQLAlchemy регистрирует его в метаданных (MetaData), связывая имя таблицы, колонки и их типы; это описание используется и для генерации DDL (Base.metadata.create_all), и для построения SQL-запросов через ORM.
- **На практике:** В современных версиях SQLAlchemy (2.0+) рекомендуется типизированный стиль Mapped[int]/mapped_column вместо старого Column, что даёт подсказки типов в IDE и явную поддержку Optional для nullable-колонок.

**Пример / кейс**
```python
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

class Base(DeclarativeBase):
    pass

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(unique=True)
    name: Mapped[str | None] = mapped_column(nullable=True)

# Base.metadata.create_all(engine) создаст таблицу users в БД
```
### 145. [Q-03-03-0145] Как открыть сессию SQLAlchemy и выполнить простой запрос на выборку данных?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
Сессия создаётся через sessionmaker(bind=engine)() или контекстный менеджер Session(engine), а запрос строится через select(Model) и выполняется методом session.execute()/session.scalars(), после чего результат извлекается методами .all()/.first().

**Разбор**
- **Как это работает:** Сессия — рабочая единица, отслеживающая загруженные объекты (identity map) и накопленные изменения до flush/commit; в SQLAlchemy 2.0 единый стиль select(...) работает и для ORM-объектов, и для Core-выражений, в отличие от устаревшего session.query(...).
- **На практике:** Сессию обычно открывают на время одного логического юнита работы (например, одного HTTP-запроса) и закрывают/коммитят в конце; удобно использовать with Session(engine) as session: — сессия закроется даже при исключении.
- **Частые ошибки:** Держат сессию открытой на всё время жизни приложения как глобальный singleton, что приводит к устаревшим данным в identity map и утечкам соединений; забывают обработать исключение и оставляют сессию в «грязном» состоянии без rollback.

**Пример / кейс**
```python
from sqlalchemy import select
from sqlalchemy.orm import Session

with Session(engine) as session:
    stmt = select(User).where(User.email == "alice@example.com")
    user = session.scalars(stmt).first()
    if user is None:
        raise ValueError("User not found")
    print(user.name)
```

### 147. [Q-03-03-0147] В чём разница между QuerySet.get() и QuerySet.filter().first() в Django ORM? Какие исключения может вызвать get()?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
get() ожидает ровно одну подходящую строку и возвращает сам объект, выбрасывая DoesNotExist, если строк нет, или MultipleObjectsReturned, если найдено больше одной; filter().first() возвращает первый объект из QuerySet или None, без исключений при отсутствии совпадений.

**Разбор**
- **Как это работает:** get() выполняет тот же SQL-запрос, что и filter(), но проверяет количество строк и возвращает объект либо поднимает исключение; filter() всегда возвращает QuerySet, а .first()/.last() материализуют один объект или None.
- **На практике:** get() удобен, когда ожидается ровно одна запись (поиск по уникальному email); отсутствие/дублирование — ошибочная ситуация, которую стоит обработать явно. filter().first() уместен, когда отсутствие результата — нормальный случай.
- **Частые ошибки:** Используют get() без обработки исключений в коде, который должен штатно работать с «не найдено», получая необработанный 500 вместо 404; забывают, что MultipleObjectsReturned возможен, если на уровне БД отсутствует реальное unique-ограничение.

**Пример / кейс**
```python
from django.core.exceptions import ObjectDoesNotExist

try:
    user = User.objects.get(email="alice@example.com")
except User.DoesNotExist:
    user = None
except User.MultipleObjectsReturned:
    raise RuntimeError("Email должен быть уникальным, но найдено несколько пользователей")

# Эквивалент без исключений:
user = User.objects.filter(email="alice@example.com").first()
```

```sql
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.amount > 100;

-- Исправленный вариант, сохраняющий всех клиентов:
```

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
Ошибку нужно перехватывать явным except на конкретный тип исключения (например, IntegrityError в Django/SQLAlchemy), откатывать текущую транзакцию и возвращать понятный ответ или бизнес-исключение, а не «проглатывать» любое исключение широким except.

**Разбор**
- **Как это работает:** При нарушении constraint СУБД отклоняет операцию и возвращает ошибку с конкретным кодом (например, SQLSTATE 23505 для unique_violation в PostgreSQL), которую драйвер оборачивает в своё исключение; транзакция переходит в состояние «aborted» до ROLLBACK.
- **На практике:** В веб-приложении типичный паттерн — перехватить конкретное исключение и преобразовать его в понятный ответ пользователю (например, HTTP 409 Conflict «email уже занят»), вместо падения с 500 ошибкой.

**Пример / кейс**
```python
from django.db import IntegrityError, transaction

def create_user(email: str, name: str) -> "User | None":
    try:
        with transaction.atomic():
            return User.objects.create(email=email, name=name)
    except IntegrityError:
        # unique-ограничение на email нарушено, транзакция уже откатана Django
        return None  # вызывающий код превращает это в HTTP 409
```

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Junior

**Короткий ответ**<br>
psycopg2 — синхронный драйвер, каждый вызов блокирует текущий поток/процесс до получения ответа от БД, а asyncpg — асинхронный драйвер, работающий через event loop asyncio и позволяющий не блокировать поток на время ожидания ответа от сети/БД.

**Разбор**
- **Как это работает:** psycopg2 выполняет сетевой I/O синхронно, поэтому внутри асинхронного приложения (например, FastAPI с async def) вызов psycopg2 заблокирует весь event loop, если не выполнить его в отдельном потоке. asyncpg встраивается в event loop через await, уступая управление другим задачам на время ожидания сети.
- **На практике:** Для асинхронных фреймворков (FastAPI, aiohttp) выбирают asyncpg или async-обёртки SQLAlchemy/Django ORM; для классических WSGI-приложений (Flask, обычный Django) psycopg2 остаётся стандартным выбором.
- **Частые ошибки:** Вызывают синхронный psycopg2 напрямую внутри async def обработчика без выноса в threadpool, убирая выигрыш от асинхронности — один медленный запрос блокирует event loop для всех остальных.

**Пример / кейс**
```python
import asyncio
import asyncpg

async def get_user(email: str):
    conn = await asyncpg.connect("postgresql://user:pass@localhost/db")
    try:
        row = await conn.fetchrow("SELECT id, name FROM users WHERE email = $1", email)
        return dict(row) if row else None
    finally:
        await conn.close()

# asyncio.run(get_user("alice@example.com")) — вызов не блокирует другие корутины на время ожидания БД
```

Миграция — это версионированный, воспроизводимый набор инструкций, который переводит схему БД из одного состояния в другое; миграции нужны, чтобы изменения моделей в коде синхронизированно и повторяемо применялись к реальной БД на всех окружениях и у всех разработчиков.

**Разбор**
- **Как это работает:** Инструмент миграций (Alembic для SQLAlchemy, встроенный механизм Django) сравнивает текущее состояние моделей с историей уже применённых миграций и генерирует/хранит файлы с операциями; каждая миграция применяется по порядку и помечается как выполненная в специальной таблице в БД.
- **На практике:** Миграции хранят в репозитории рядом с кодом и применяют как часть процесса деплоя; важно, чтобы миграция была воспроизводима на чистой БД и откатываема (downgrade), когда это возможно.
- **Частые ошибки:** Правят схему БД руками напрямую в production, минуя миграции, из-за чего состояние БД расходится с историей миграций; коммитят модель без соответствующей миграции, из-за чего ORM и реальная БД не совпадают.

**Пример / кейс**
```text
# Django
python manage.py makemigrations  # генерирует файл миграции на основе изменений моделей
python manage.py migrate          # применяет непримененные миграции к БД

# Alembic (SQLAlchemy)
alembic revision --autogenerate -m "add phone to users"
alembic upgrade head
```

### 155. [Q-03-03-0155] Что такое проблема N+1 запросов в ORM, как её обнаружить и как исправить в Django/SQLAlchemy?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Проблема N+1 возникает, когда для получения связанных данных по N строкам основного запроса ORM выполняет один дополнительный SQL-запрос на каждую строку (всего N+1 запросов) вместо одного объединённого запроса; решается через явную загрузку связей — select_related/prefetch_related в Django или joinedload/selectinload в SQLAlchemy.

**Разбор**
- **Как это работает:** Ленивая загрузка связанных объектов по умолчанию откладывает запрос к связанной таблице до момента обращения к атрибуту; в цикле по списку объектов это превращается в отдельный запрос на каждую итерацию.
- **На практике:** Проблему обнаруживают через логирование SQL (django-debug-toolbar, echo=True в SQLAlchemy) или APM; select_related (JOIN, для ForeignKey) и prefetch_related (отдельный IN-запрос, для ManyToMany) в Django, joinedload/selectinload в SQLAlchemy решают проблему заранее указанной стратегией.
- **Частые ошибки:** Добавляют select_related на ManyToMany-связь — не работает, для таких связей нужен prefetch_related; забывают, что prefetch_related всё равно выполняет отдельный запрос, который для очень больших выборок нужно ограничивать.

**Пример / кейс**
```python
# Плохо: N+1 запрос — по одному SELECT authors на каждую книгу
books = Book.objects.all()
for book in books:
    print(book.author.name)

# Хорошо: один дополнительный JOIN
books = Book.objects.select_related("author").all()
for book in books:
    print(book.author.name)
# Проверка: django-debug-toolbar покажет 1 запрос вместо N+1
```
### 156. [Q-03-03-0156] Чем отличаются уровни изоляции Read Committed и Repeatable Read в PostgreSQL? Какой уровень используется по умолчанию?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
По умолчанию PostgreSQL использует Read Committed, при котором каждый отдельный запрос внутри транзакции видит только данные, зафиксированные к моменту его начала; Repeatable Read фиксирует единый снимок данных на момент начала всей транзакции, поэтому повторный такой же запрос внутри неё всегда возвращает одинаковый результат.

**Разбор**
- **Как это работает:** Оба уровня в PostgreSQL реализованы через MVCC без блокировки читающих транзакций записывающими; разница в моменте фиксации «снимка» — на уровне отдельного оператора или на уровне всей транзакции. Repeatable Read защищает от non-repeatable read и phantom read, но не от всех serialization anomalies, в отличие от Serializable.
- **На практике:** Read Committed подходит для большинства обычных CRUD-операций; Repeatable Read выбирают для отчётов/аналитики, где важно видеть консистентный снимок на момент начала транзакции.
- **Частые ошибки:** Предполагают, что Read Committed защищает от lost update между чтением и последующим обновлением — на самом деле для этого нужны явные блокировки (SELECT FOR UPDATE) или более строгий уровень изоляции.

**Пример / кейс**
```sql
-- Сессия A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1; -- видит 100

-- Сессия B (в это время, в другой транзакции)
UPDATE accounts SET balance = 200 WHERE id = 1;
COMMIT;

-- Сессия A, тот же SELECT повторно в той же транзакции
SELECT balance FROM accounts WHERE id = 1; -- всё ещё видит 100, снимок зафиксирован на начало транзакции
COMMIT;
```
### 157. [Q-03-03-0157] Что такое deadlock в БД, как его диагностировать в PostgreSQL и как минимизировать риск его возникновения?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Deadlock возникает, когда две (или более) транзакции удерживают блокировки и одновременно ждут блокировку, удерживаемую друг другом, образуя цикл ожидания; PostgreSQL автоматически обнаруживает цикл и прерывает одну из транзакций с ошибкой deadlock detected, которую нужно перехватить и повторить операцию.

**Разбор**
- **Как это работает:** PostgreSQL периодически проверяет граф ожидания блокировок; при обнаружении цикла выбирается «жертва» — её запрос завершается ошибкой, а остальные участники продолжают работу.
- **На практике:** Диагностируют через лог PostgreSQL (сообщения «deadlock detected» содержат оба конфликтующих запроса) или pg_stat_activity/pg_locks; снижают риск, блокируя строки в одном и том же порядке во всех частях кода (например, по возрастанию id) и держа транзакции короткими.
- **Частые ошибки:** Не оборачивают операцию в retry-логику после перехваченной ошибки deadlock, хотя это ожидаемая ситуация; обновляют несколько строк в разном порядке в разных частях кода, создавая классические условия для deadlock.

**Пример / кейс**
```python
from django.db import transaction, OperationalError
import time

def transfer_with_retry(from_id, to_id, amount, attempts=3):
    for attempt in range(attempts):
        try:
            with transaction.atomic():
                first, second = sorted([from_id, to_id])
                # блокируем строки в фиксированном порядке, чтобы избежать deadlock
                Account.objects.select_for_update().filter(id__in=[first, second])
                Account.objects.filter(id=from_id).update(balance=F("balance") - amount)
                Account.objects.filter(id=to_id).update(balance=F("balance") + amount)
            return
        except OperationalError as e:
            if "deadlock detected" in str(e) and attempt < attempts - 1:
                time.sleep(0.1 * (attempt + 1))
                continue
            raise
```
### 158. [Q-03-03-0158] Как читать план выполнения запроса из EXPLAIN ANALYZE в PostgreSQL? В чём разница между Seq Scan и Index Scan?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
EXPLAIN ANALYZE реально выполняет запрос и показывает дерево операций с оценённой и фактической стоимостью/временем/числом строк для каждого узла; Seq Scan читает всю таблицу страницами подряд, а Index Scan использует индекс, чтобы обратиться только к нужным строкам.

**Разбор**
- **Как это работает:** План строится снизу вверх — листовые узлы (сканы) передают строки родительским узлам (Join, Sort, Aggregate); планировщик выбирает стратегию на основе статистики (ANALYZE таблицы). Расхождение между estimated и actual rows часто сигнализирует об устаревшей статистике.
- **На практике:** При анализе медленного запроса смотрят на узлы с наибольшим actual time и на то, совпадает ли план с ожиданием; BUFFERS в EXPLAIN (ANALYZE, BUFFERS) дополнительно показывает хиты/промахи кэша страниц.
- **Частые ошибки:** Смотрят только на EXPLAIN без ANALYZE и путают оценочную стоимость с реальным временем; не замечают, что планировщик иногда осознанно выбирает Seq Scan вместо Index Scan для низкой избирательности условия.

**Пример / кейс**
```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 42;
-- Seq Scan on orders (cost=0.00..2500.00 rows=50000 width=64) (actual time=0.015..35.201 rows=12 loops=1)
--   Filter: (user_id = 42)
--   Rows Removed by Filter: 49988
-- Вывод: нужен индекс на user_id, так как фильтр отбрасывает почти все строки при полном сканировании
```
### 159. [Q-03-03-0159] Как выбрать порядок колонок в составном индексе (multi-column index)? Почему индекс (a, b) не всегда помогает запросу с условием только по b?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Составной B-tree индекс упорядочен лексикографически — сначала по первой колонке, затем по второй внутри одинаковых значений первой, поэтому он эффективно используется для условий по первой колонке (или по обеим), но обычно бесполезен для запроса, фильтрующего только по второй колонке без первой.

**Разбор**
- **Как это работает:** Структура похожа на отсортированный список пар (a, b) — найти диапазон по a быстро, а внутри найденного диапазона дополнительно быстро сузить по b; без фиксации a СУБД не может перейти сразу к нужным b, они «разбросаны» по дереву.
- **На практике:** Общее правило — ставить первой колонку с более высокой избирательностью или ту, по которой чаще фильтруют в равенстве (=), а колонку с диапазонным условием (<, >, BETWEEN) обычно ставят последней.
- **Частые ошибки:** Создают отдельные индексы на a и на b по отдельности, думая, что это эквивалентно составному индексу (a, b) для запросов с условием на оба поля; меняют порядок колонок «для красоты», не проверяя профиль запросов через pg_stat_statements.

**Пример / кейс**
```sql
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at);

-- Эффективно использует индекс: равенство по первой колонке + диапазон по второй
EXPLAIN SELECT * FROM orders WHERE user_id = 42 AND created_at > now() - interval '7 days';

-- Индекс почти не поможет: нет условия на первую колонку user_id
EXPLAIN SELECT * FROM orders WHERE created_at > now() - interval '7 days';
```
### 160. [Q-03-03-0160] Что такое partial index (частичный индекс) в PostgreSQL и в каких сценариях его применяют?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Partial index — это индекс, построенный только для строк, удовлетворяющих условию WHERE, указанному при его создании; его применяют, когда запросы почти всегда фильтруют по одному и тому же подмножеству строк (например, только активные записи), чтобы индекс был меньше и быстрее полного.

**Разбор**
- **Как это работает:** При создании CREATE INDEX ... WHERE condition PostgreSQL включает в индекс только строки, удовлетворяющие condition, и поддерживает это условие при последующих INSERT/UPDATE; планировщик использует такой индекс только для запросов, чьё условие WHERE логически покрывается условием индекса.
- **На практике:** Типичный кейс — таблица задач с большинством завершённых записей: CREATE INDEX ... WHERE status != 'done' резко уменьшает размер индекса по сравнению с полным индексом на всю таблицу.
- **Частые ошибки:** Пишут запрос с условием, которое СУБД не может сопоставить с условием partial-индекса буквально (например, индекс WHERE status = 'active', а запрос использует WHERE status IN ('active')), из-за чего планировщик может не применить индекс.

**Пример / кейс**
```sql
CREATE INDEX idx_tasks_active ON tasks(assignee_id) WHERE status = 'active';

-- Использует partial index
EXPLAIN SELECT * FROM tasks WHERE status = 'active' AND assignee_id = 10;

-- Не использует этот индекс (условие не совпадает)
EXPLAIN SELECT * FROM tasks WHERE status = 'in_progress' AND assignee_id = 10;
```
### 161. [Q-03-03-0161] Как реализовать optimistic locking (оптимистичную блокировку) для предотвращения конкурентного перезатирания данных без постоянных блокировок строк?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Optimistic locking добавляет в таблицу колонку версии (version/updated_at), и при обновлении запрос проверяет, что версия в БД совпадает с версией, прочитанной приложением ранее (UPDATE ... WHERE id = ? AND version = ?); если ни одна строка не обновилась — данные изменились параллельно, и приложение должно повторить операцию или сообщить о конфликте.

**Разбор**
- **Как это работает:** В отличие от пессимистичной блокировки (SELECT ... FOR UPDATE), здесь не удерживается блокировка строки на время «размышления» приложения — конфликт обнаруживается только в момент самой записи по несовпадению версии.
- **На практике:** Подходит для сценариев с низкой частотой конкурентных изменений одной строки (например, редактирование профиля); при обнаружении конфликта обычно показывают пользователю актуальные данные и просят повторить изменение.
- **Частые ошибки:** Забывают увеличивать version при каждом обновлении; не проверяют количество затронутых строк после UPDATE, из-за чего «тихий» конфликт остаётся незамеченным и одно из изменений просто теряется.

**Пример / кейс**
```python
def update_profile(user_id: int, new_name: str, expected_version: int) -> bool:
    updated = (
        User.objects
        .filter(id=user_id, version=expected_version)
        .update(name=new_name, version=F("version") + 1)
    )
    return updated == 1  # False означает конфликт версий — данные изменились параллельно
```

**Уровень:** Middle

**Короткий ответ**<br>
Оконные функции вычисляют значение для каждой строки на основе «окна» связанных строк (OVER (PARTITION BY ... ORDER BY ...)), не сворачивая результат в одну строку на группу, в отличие от обычных агрегатных функций с GROUP BY; ROW_NUMBER() нумерует строки внутри партиции, RANK() делает то же самое, но учитывает повторы значений при сортировке.

**Разбор**
- **Как это работает:** PARTITION BY делит результат на логические группы без потери отдельных строк, ORDER BY внутри OVER определяет порядок для вычисления ранга/номера/смещения; функция вычисляется для каждой исходной строки.
- **На практике:** Типичные задачи — выбор «последней записи на пользователя» (ROW_NUMBER() + фильтр = 1), топ-N в каждой категории, скользящие суммы/средние — это часто проще и быстрее, чем аналогичная логика через self-join.
- **Частые ошибки:** Путают RANK() и ROW_NUMBER() — при одинаковых значениях ORDER BY RANK() присвоит одинаковый ранг нескольким строкам и «пропустит» следующие номера, а ROW_NUMBER() всегда даёт уникальный последовательный номер.

**Пример / кейс**
```sql
SELECT id, user_id, amount, created_at,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
FROM orders;

-- Выбрать только последний заказ каждого пользователя:
SELECT * FROM (
    SELECT id, user_id, amount,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
    FROM orders
) t WHERE rn = 1;
```
### 163. [Q-03-03-0163] Что такое CTE (Common Table Expression) в SQL? Чем рекурсивный CTE отличается от обычного?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
CTE (конструкция WITH name AS (...)) — это временный именованный результат подзапроса, который можно использовать в основном запросе как обычную таблицу, что улучшает читаемость сложных запросов; рекурсивный CTE (WITH RECURSIVE) ссылается сам на себя, что позволяет обходить иерархические структуры произвольной глубины.

**Разбор**
- **Как это работает:** Обычный CTE — способ разбить сложный запрос на именованные шаги (в PostgreSQL 12+ может инлайниться или материализоваться, в зависимости от оптимизатора). Рекурсивный CTE состоит из «базовой» части и «рекурсивной» части, присоединяемой к результату предыдущей итерации, пока не перестанут появляться новые строки.
- **На практике:** Рекурсивные CTE используют для обхода деревьев категорий, графов зависимостей, иерархии сотрудников; важно предусмотреть условие остановки и ограничивать глубину явным счётчиком для защиты от циклов.
- **Частые ошибки:** Забывают про возможность циклов в данных — без ограничения глубины рекурсивный CTE уйдёт в бесконечный цикл; используют обычный CTE там, где нужен проход по произвольной глубине иерархии, дублируя логику через код приложения.

**Пример / кейс**
```sql
WITH RECURSIVE category_tree AS (
    SELECT id, name, parent_id, 1 AS depth
    FROM categories WHERE parent_id IS NULL
    UNION ALL
    SELECT c.id, c.name, c.parent_id, ct.depth + 1
    FROM categories c
    JOIN category_tree ct ON c.parent_id = ct.id
    WHERE ct.depth < 20  -- защита от бесконечной рекурсии на испорченных данных
)
SELECT * FROM category_tree ORDER BY depth, id;
```
### 164. [Q-03-03-0164] Когда стоит использовать колонку типа JSONB в PostgreSQL вместо отдельных реляционных колонок/таблиц, и как ускорить поиск по значениям внутри JSONB?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
JSONB уместен для действительно полуструктурированных или часто меняющихся по составу данных, когда заранее неизвестна или нестабильна схема, а не как универсальная замена нормализованных таблиц; для ускорения поиска по ключам/значениям внутри JSONB создают GIN-индекс.

**Разбор**
- **Как это работает:** JSONB хранит данные в бинарном разложенном виде, что ускоряет выборочный доступ к ключам и позволяет строить GIN-индекс, поддерживающий операторы @>, ?, ?& и поиск по пути jsonb_path_ops.
- **На практике:** Типичный баланс — вынести стабильные, часто фильтруемые атрибуты в обычные колонки/таблицы, а вариативные или редко запрашиваемые — в JSONB; злоупотребление JSONB усложняет валидацию, JOIN и миграции данных внутри самого JSON.
- **Частые ошибки:** Хранят в JSONB данные, которые по сути реляционные и регулярно участвуют в JOIN/агрегации, что затрудняет аналитические запросы; создают обычный B-tree индекс на JSONB-колонку целиком вместо GIN-индекса.

**Пример / кейс**
```sql
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    attributes JSONB NOT NULL DEFAULT '{}'::jsonb
);
CREATE INDEX idx_products_attributes ON products USING GIN (attributes);

-- Найти товары с атрибутом color = "red"
SELECT * FROM products WHERE attributes @> '{"color": "red"}';
EXPLAIN SELECT * FROM products WHERE attributes @> '{"color": "red"}';
-- При наличии GIN-индекса план покажет Bitmap Index Scan вместо полного Seq Scan
```
### 165. [Q-03-03-0165] Чем отличаются стратегии загрузки связей lazy='select', 'joined', 'subquery' и 'selectin' в SQLAlchemy ORM? Когда предпочтительна selectin?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
'select' (по умолчанию) делает отдельный запрос на каждый доступ к связи; 'joined' добавляет LEFT OUTER JOIN в основной запрос; 'subquery' выполняет отдельный подзапрос для всех связанных объектов сразу; 'selectin' выполняет отдельный SELECT ... WHERE id IN (...) для всех родительских id сразу — обычно это предпочтительный вариант для коллекций.

**Разбор**
- **Как это работает:** 'joined' увеличивает размер результата основного запроса (дублирование строк родителя при JOIN к коллекции); 'subquery' и 'selectin' выполняют единственный дополнительный запрос для всех объектов партии, но 'selectin' эффективнее за счёт простого IN-списка и лучше работает с LIMIT/OFFSET.
- **На практике:** 'joined' хорошо подходит для связей «один-к-одному»/«многие-к-одному» с небольшим числом строк; 'selectin' — предпочтительный выбор для коллекций в современных версиях SQLAlchemy, переопределяется через options(selectinload(...)).
- **Частые ошибки:** Используют 'joined' для коллекций с большим количеством связанных строк, получая умножение строк результата; не указывают стратегию загрузки вовсе, получая N+1 при итерации по объектам в цикле.

**Пример / кейс**
```python
from sqlalchemy.orm import selectinload

stmt = select(Author).options(selectinload(Author.books))
authors = session.scalars(stmt).all()
for author in authors:
    print(author.name, len(author.books))
# SQLAlchemy выполнит ровно 2 запроса: один по authors, один SELECT ... WHERE author_id IN (...) по books
```
### 166. [Q-03-03-0166] В чём разница между session.flush() и session.commit() в SQLAlchemy?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
flush() отправляет накопленные изменения в БД в рамках текущей транзакции, делая их видимыми для последующих запросов этой же транзакции (например, чтобы получить сгенерированный id), но не фиксирует их навсегда; commit() выполняет flush неявно и затем фиксирует транзакцию, делая изменения постоянными и видимыми другим транзакциям.

**Разбор**
- **Как это работает:** SQLAlchemy Session накапливает изменения объектов в памяти (unit of work) и не отправляет их в БД немедленно при каждом session.add(); flush синхронизирует состояние объектов с БД, но до commit всё это можно откатить через rollback().
- **На практике:** Явный flush() нужен, когда в рамках одной транзакции нужно получить автоматически сгенерированный PK нового объекта до завершения всей бизнес-операции; в большинстве сценариев достаточно одного commit() в конце.
- **Частые ошибки:** Вызывают commit() слишком часто внутри одной логической операции, фиксируя промежуточные состояния, которые должны быть атомарны вместе с последующими шагами; путают flush с commit, считая, что после flush rollback уже не отменит изменения — это не так.

**Пример / кейс**
```python
with Session(engine) as session:
    author = Author(name="Jane Doe")
    session.add(author)
    session.flush()  # author.id уже доступен, но транзакция ещё не зафиксирована
    book = Book(title="New Book", author_id=author.id)
    session.add(book)
    session.commit()  # фиксирует и author, и book одной транзакцией
```
### 167. [Q-03-03-0167] Зачем в Django ORM используют bulk_create() и bulk_update() вместо обычного цикла с save()? Какие у них ограничения?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
bulk_create()/bulk_update() формируют один (или несколько батчами) SQL-запрос на вставку/обновление множества объектов сразу вместо отдельного INSERT/UPDATE на каждый объект в цикле, что резко снижает число round-trip'ов к БД; ограничения — они не вызывают save()/сигналы Django для каждого объекта.

**Разбор**
- **Как это работает:** Обычный цикл for obj in objects: obj.save() выполняет отдельный запрос на каждый объект; bulk_create собирает один многострочный INSERT (батчами, управляется batch_size), bulk_update формирует CASE WHEN-конструкцию или несколько UPDATE одним проходом.
- **На практике:** bulk_* операции применяют при массовом импорте/синхронизации данных; pre_save/post_save сигналы не вызываются, поэтому побочная логика, завязанная на сигналы, должна быть продублирована явно при необходимости.
- **Частые ошибки:** Ожидают, что bulk_create выполнит кастомную логику переопределённого save() — это не так; не указывают batch_size для очень большого количества объектов, что может создать один гигантский SQL-запрос.

**Пример / кейс**
```python
# Плохо: N отдельных INSERT
for row in import_rows:
    Product.objects.create(sku=row["sku"], price=row["price"])

# Хорошо: один (или несколько батчами) INSERT
products = [Product(sku=row["sku"], price=row["price"]) for row in import_rows]
Product.objects.bulk_create(products, batch_size=500)
# Сигналы post_save НЕ будут вызваны для каждого объекта — это нужно учитывать явно
```
### 168. [Q-03-03-0168] Как с помощью Alembic безопасно добавить NOT NULL колонку в таблицу, где уже есть данные?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Нельзя просто добавить колонку с NOT NULL без DEFAULT в таблицу с существующими строками — PostgreSQL попытается применить ограничение ко всем текущим строкам и упадёт, так как для них значения не определены; правильный путь — добавить колонку nullable, заполнить существующие строки значениями, затем отдельным шагом добавить ограничение NOT NULL.

**Разбор**
- **Как это работает:** ALTER TABLE ... ADD COLUMN col TYPE NOT NULL без DEFAULT требует значения для каждой существующей строки — его взять неоткуда, поэтому PostgreSQL отклоняет миграцию; добавление с DEFAULT в PostgreSQL 11+ для большинства типов быстро, но столбец всё ещё нужно сначала сделать nullable, прежде чем включать NOT NULL.
- **На практике:** Безопасная последовательность: (1) добавить колонку nullable; (2) выполнить backfill существующих строк батчами; (3) добавить ограничение NOT NULL отдельной миграцией после подтверждения завершения backfill — это минимизирует блокировки на большой таблице.
- **Частые ошибки:** Пытаются сделать всё одной миграцией на большой production-таблице, вызывая долгую блокировку ACCESS EXCLUSIVE; забывают, что старый код приложения во время rolling deploy может создавать новые строки без новой колонки, если не предусмотрен DEFAULT.

**Пример / кейс**
```python
# Миграция 1: добавить nullable колонку с default
def upgrade():
    op.add_column("users", sa.Column("country", sa.String(length=2), nullable=True))

# Отдельный backfill-скрипт/миграция данных батчами
# UPDATE users SET country = 'US' WHERE country IS NULL AND id BETWEEN 1 AND 10000;

# Миграция 2 (после подтверждения, что backfill завершён): включить NOT NULL
def upgrade():
    op.alter_column("users", "country", nullable=False)
```
### 169. [Q-03-03-0169] Как сделать data migration в Django (миграцию, изменяющую не схему, а сами данные)?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Data migration создаётся через manage.py makemigrations --empty appname и содержит операцию RunPython с функцией, которая читает/изменяет данные через исторические версии моделей (apps.get_model), а не через прямой импорт текущих моделей приложения.

**Разбор**
- **Как это работает:** Django передаёт в функцию RunPython специальный объект apps, содержащий историческую версию моделей на момент именно этой миграции — это защищает от падения старых миграций, если метод модели в будущем изменится или исчезнет.
- **На практике:** Data migration используют для заполнения новой колонки вычисленными значениями, нормализации данных; для больших таблиц такую миграцию стоит писать с батчингом (iterator() с chunk_size), чтобы не держать долгую транзакцию.
- **Частые ошибки:** Импортируют модель напрямую (from myapp.models import User) вместо apps.get_model("myapp", "User") — миграция может сломаться в будущем; не добавляют reverse_code, оставляя RunPython.noop, хотя откат данных был бы ожидаем.

**Пример / кейс**
```python
from django.db import migrations

def set_default_country(apps, schema_editor):
    User = apps.get_model("myapp", "User")
    User.objects.filter(country__isnull=True).update(country="US")

def reverse_default_country(apps, schema_editor):
    pass  # осознанно noop: восстановить исходные NULL невозможно без дополнительных данных

class Migration(migrations.Migration):
    dependencies = [("myapp", "0005_add_country_field")]
    operations = [migrations.RunPython(set_default_country, reverse_default_country)]
```
### 170. [Q-03-03-0170] Что такое проблема lost update (потерянное обновление) при конкурентном изменении данных? Покажите сценарий и способ решения.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Lost update возникает, когда две параллельные транзакции читают одно и то же значение, затем каждая вычисляет новое значение на основе прочитанного и записывает его обратно — одно из обновлений «теряется»; решение — атомарное обновление на уровне SQL (UPDATE ... SET x = x + 1) или явная блокировка строки (SELECT ... FOR UPDATE).

**Разбор**
- **Как это работает:** Проблема возникает из-за паттерна «прочитать в приложении → изменить в памяти → записать обратно» между двумя отдельными SQL-командами, в промежутке между которыми другая транзакция успевает сделать то же самое с тем же исходным значением.
- **На практике:** Если логика обновления простая арифметика, надёжнее выразить её прямо в одном SQL-запросе (balance = balance - 100), который СУБД выполнит атомарно; если нужна сложная проверка перед записью, используют SELECT ... FOR UPDATE или optimistic locking.
- **Частые ошибки:** Читают значение через ORM (obj = Model.objects.get(...)), изменяют атрибут в Python и сохраняют через save() — именно этот паттерн подвержен lost update, даже если каждая SQL-операция сама по себе использует Read Committed.

**Пример / кейс**
```python
# Подвержено lost update: два параллельных запроса читают balance=100, оба пишут 100-30=70
account = Account.objects.get(id=1)
account.balance -= 30
account.save()

# Безопасно: атомарное выражение на уровне SQL, выполняется БД как единая операция
Account.objects.filter(id=1).update(balance=F("balance") - 30)
```
### 171. [Q-03-03-0171] Что такое connection pool при работе с БД из приложения и что происходит, если пул соединений исчерпан?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Connection pool — это заранее созданный и переиспользуемый набор открытых соединений к БД, который избегает дорогостоящего создания нового TCP/TLS-соединения на каждый запрос; если все соединения в пуле заняты и достигнут лимит, новые запросы либо ждут освобождения соединения с таймаутом, либо сразу получают ошибку.

**Разбор**
- **Как это работает:** Пул выдаёт соединение по запросу (checkout), приложение выполняет запросы и возвращает соединение в пул (checkin) по завершении работы; при превышении лимита без доступных соединений вызывающий код блокируется до pool_timeout или получает исключение пула.
- **На практике:** Размер пула подбирают с учётом числа воркеров приложения, ограничения max_connections на стороне PostgreSQL и реального профиля конкурентности; для большого числа коротких подключений часто ставят внешний пулер (PgBouncer) перед PostgreSQL.
- **Частые ошибки:** Забывают возвращать соединение/сессию в пул (не закрывают сессию в finally), из-за чего пул постепенно «утекает»; ставят слишком большой pool_size на каждый инстанс при множестве инстансов, в сумме превышая max_connections БД.

**Пример / кейс**
```python
from sqlalchemy import create_engine

engine = create_engine(
    "postgresql+psycopg2://user:pass@localhost/db",
    pool_size=10,
    max_overflow=5,
```

### 172. [Q-03-03-0172] Как организовать чтение с реплики (read replica) в приложении и какие проблемы это создаёт из-за replication lag?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Запросы на чтение (отчёты, листинги) направляют на отдельное read-only соединение к реплике, а запросы на запись и критичные к свежести чтения — на primary; главная проблема — replication lag, когда реплика ещё не применила недавние изменения с primary, и пользователь может не увидеть собственное только что сохранённое изменение.

**Разбор**
- **Как это работает:** Физическая/логическая репликация PostgreSQL асинхронно передаёт WAL с primary на реплику; величина задержки зависит от нагрузки и сети (синхронная репликация устраняет эту проблему ценой задержки записи на primary).
- **На практике:** Типичный паттерн — маршрутизация запросов по признаку «это SELECT без требования строгой консистентности»; для сценария «показать сразу после записи» читают с primary в течение короткого окна.
- **Частые ошибки:** Отправляют на реплику запрос сразу после записи в рамках того же пользовательского действия, получая «заказ не найден» из-за лага; не мониторят сам лаг (pg_stat_replication), из-за чего деградация реплики остаётся незамеченной.

**Пример / кейс**
```python
def get_order_for_display(order_id):
    return Order.objects.using("replica").get(id=order_id)  # для обычного просмотра

def create_order_and_show(data):
    order = Order.objects.using("default").create(**data)  # запись на primary
    return Order.objects.using("default").get(id=order.id)  # читаем тоже с primary, чтобы не попасть в лаг
```
### 173. [Q-03-03-0173] Что такое паттерн soft delete (мягкое удаление) записей в БД? Какие у него плюсы и минусы по сравнению с реальным DELETE?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Soft delete — это помечание записи как удалённой через флаг (is_deleted) или метку времени (deleted_at) вместо физического удаления строки; это сохраняет историю и возможность восстановления, но требует, чтобы вся логика приложения и все запросы явно учитывали этот флаг, иначе «удалённые» записи будут неожиданно появляться в выборках.

**Разбор**
- **Как это работает:** Вместо DELETE FROM table WHERE id = ... выполняется UPDATE table SET deleted_at = now() WHERE id = ...; все последующие SELECT-запросы обязаны добавлять условие WHERE deleted_at IS NULL, либо это делает кастомный менеджер ORM.
- **На практике:** Soft delete уместен там, где важна аудируемость и возможность восстановления, или где на удалённую запись продолжают физически ссылаться другие таблицы; индексы нужно проектировать с учётом фильтра (partial index WHERE deleted_at IS NULL).
- **Частые ошибки:** Забывают добавить фильтр по deleted_at в одном из мест кода (прямой SQL, отдельный отчёт); не продумывают UNIQUE-ограничения — повторная регистрация с тем же email после soft delete может упереться в unique-constraint без partial unique index.

**Пример / кейс**
```python
class ActiveUserManager(models.Manager):
    def get_queryset(self):
        return super().get_queryset().filter(deleted_at__isnull=True)

class User(models.Model):
    email = models.EmailField()
    deleted_at = models.DateTimeField(null=True, blank=True)

    objects = ActiveUserManager()
    all_objects = models.Manager()

    def soft_delete(self):
        self.deleted_at = timezone.now()
        self.save(update_fields=["deleted_at"])
```
### 174. [Q-03-03-0174] Что такое функциональный (expression) индекс в PostgreSQL? Приведите пример индекса по lower(email) и объясните, когда он нужен.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Функциональный индекс строится не по значению колонки напрямую, а по результату выражения/функции от неё (например, lower(email)); он нужен, когда запросы фильтруют по результату такого выражения, а не по исходному значению — обычный индекс на email в этом случае не используется планировщиком для условия с lower(email).

**Разбор**
- **Как это работает:** PostgreSQL может строить B-tree индекс по любому детерминированному выражению, вычисляя и храня в индексе результат для каждой строки; планировщик использует индекс только при точном совпадении формы выражения в условии WHERE.
- **На практике:** Типичный пример — регистронезависимый поиск по email: вместо LOWER(email) = LOWER(:input) с полным сканированием строят CREATE INDEX ON users (lower(email)) и фильтруют по WHERE lower(email) = lower(:input); альтернатива — тип citext.
- **Частые ошибки:** Создают обычный индекс на email, а в запросах используют LOWER(email), из-за чего индекс не применяется; рассинхронизируют выражение в запросе и в индексе (например, индекс по lower(trim(email)), а запрос фильтрует только по lower(email)).

**Пример / кейс**
```sql
CREATE INDEX idx_users_lower_email ON users (lower(email));

EXPLAIN SELECT * FROM users WHERE lower(email) = lower('Alice@Example.com');
-- Index Scan using idx_users_lower_email вместо Seq Scan по всей таблице
```

```sql
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

### 176. [Q-03-03-0176] Как выполнить миграцию схемы без простоя (zero-downtime), например переименование колонки, при rolling deploy, когда старая и новая версия приложения работают одновременно?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
Прямое переименование колонки одной миграцией несовместимо с rolling deploy, так как старая версия кода ещё обращается к старому имени; безопасный подход — паттерн expand/contract: добавить новую колонку, синхронизировать данные со старой, переключить код на новую, и только после полной раскатки удалить старую колонку отдельной миграцией.

**Разбор**
- **Как это работает:** Во время rolling deploy одновременно работают как минимум две версии кода, обращающиеся к одной БД — любое несовместимое изменение схемы должно оставаться совместимым с обеими версиями кода на протяжении переходного периода.
- **На практике:** Для переименования: expand (добавить колонку) → dual write (приложение пишет в обе колонки) → backfill исторических данных → переключение кода на чтение новой колонки → contract (удаление старой колонки отдельным релизом).
- **Частые ошибки:** Выполняют ALTER TABLE RENAME COLUMN в одной миграции одновременно с деплоем нового кода, полагая, что деплой происходит мгновенно — старые инстансы тут же начинают падать с ошибкой «колонка не существует».

**Пример / кейс**
```sql
-- Шаг 1 (релиз N): добавить новую колонку
ALTER TABLE users ADD COLUMN full_name TEXT;
-- Приложение версии N пишет в обе колонки: name и full_name

-- Backfill исторических данных батчами
UPDATE users SET full_name = name WHERE full_name IS NULL AND id BETWEEN 1 AND 50000;

-- Шаг 2 (релиз N+1, после полной раскатки N): код читает только full_name
-- Шаг 3 (релиз N+2, после подтверждения): удалить старую колонку
ALTER TABLE users DROP COLUMN name;
```
### 177. [Q-03-03-0177] Зачем в PostgreSQL использовать UPDATE ... RETURNING вместо отдельного SELECT после UPDATE?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
RETURNING позволяет получить значения изменённых (или вставленных/удалённых) строк в одном запросе вместе с самой операцией изменения, без отдельного round-trip на SELECT, и без риска, что между UPDATE и последующим SELECT другая транзакция успеет снова изменить эти же строки.

**Разбор**
- **Как это работает:** RETURNING добавляется к INSERT/UPDATE/DELETE и возвращает результирующий набор строк так же, как обычный SELECT, но строки берутся непосредственно из только что изменённых версий — одна атомарная операция клиент-сервер.
- **На практике:** Удобно применять, когда нужно сразу получить вычисленное на стороне БД значение (например, обновлённый balance после F("balance") - amount) или id после INSERT, без дополнительного запроса; это также устраняет гонку между UPDATE и следующим SELECT.
- **Частые ошибки:** Продолжают писать UPDATE, а затем отдельный SELECT для получения результата по тому же условию — лишний round-trip и потенциальная рассинхронизация, если между запросами произошло ещё одно изменение той же строки.

**Пример / кейс**
```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = 1 AND balance >= 100
RETURNING id, balance;
-- Если строки не было (например, balance < 100), запрос вернёт 0 строк —
-- это сразу и результат проверки условия, и получение нового значения одним запросом
```
### 178. [Q-03-03-0178] Как работают cascade-настройки и параметр back_populates в relationship SQLAlchemy? Что случится при удалении родительского объекта с cascade='all, delete-orphan'?

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Middle

**Короткий ответ**<br>
back_populates связывает два атрибута relationship на обеих сторонах связи, чтобы изменение одной стороны в памяти Python автоматически синхронизировало другую; cascade="all, delete-orphan" на стороне "один" означает, что при удалении родителя все связанные дочерние объекты будут автоматически удалены СУБД, а дочерний объект, у которого убрали ссылку на родителя, будет считаться «осиротевшим» и также удалён при flush.

**Разбор**
- **Как это работает:** back_populates — это Python-уровневая синхронизация объектов в памяти сессии (в отличие от backref, который создаёт обратный атрибут автоматически); cascade управляет тем, какие операции SQLAlchemy ORM применяет к связанным объектам при соответствующей операции с родителем.
- **На практике:** cascade="all, delete-orphan" типичен для составных сущностей, где дочерний объект не имеет смысла без родителя; важно не путать ORM-уровень cascade (срабатывает только через сессию) с ON DELETE CASCADE на уровне БД (срабатывает при прямом SQL в обход ORM).
- **Частые ошибки:** Настраивают только cascade на уровне ORM без ON DELETE на уровне FK в БД, и прямое удаление через raw SQL оставляет «осиротевшие» строки; используют одновременно backref и back_populates на той же паре атрибутов, вызывая конфликт конфигурации.

**Пример / кейс**
```python
class Author(Base):
    __tablename__ = "authors"
    id: Mapped[int] = mapped_column(primary_key=True)
    books: Mapped[list["Book"]] = relationship(back_populates="author", cascade="all, delete-orphan")

class Book(Base):
    __tablename__ = "books"
    id: Mapped[int] = mapped_column(primary_key=True)
    author_id: Mapped[int] = mapped_column(ForeignKey("authors.id"))
    author: Mapped["Author"] = relationship(back_populates="books")

# session.delete(author); session.commit() -> удалит author и все его books автоматически
```
### 179. [Q-03-03-0179] В сервисе обработки платежей нужно гарантировать, что при конкурентных операциях со счётом баланс не станет отрицательным и не возникнет двойного списания. Как выбрать между уровнем изоляции Serializable и Repeatable Read с явными блокировками, учитывая нагрузку и необходимость retry-логики? Обсудите компромиссы, риски и критерии выбора: единственного правильного решения нет.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Senior

**Короткий ответ**<br>
Serializable даёт самую строгую гарантию без необходимости вручную расставлять блокировки, но требует обязательной retry-логики на serialization failure и может снижать пропускную способность под высокой конкуренцией; Repeatable Read/Read Committed с явным SELECT ... FOR UPDATE или атомарными UPDATE-выражениями даёт больше контроля и обычно выше производительность, но требует аккуратного ручного проектирования каждого критичного пути.

**Разбор**
- **Как это работает:** Serializable в PostgreSQL реализован через SSI (Serializable Snapshot Isolation) — он детектирует потенциальные аномалии между конкурентными транзакциями и прерывает одну из них с ошибкой serialization failure; при Repeatable Read/Read Committed корректность операции обеспечивается явно — через атомарный UPDATE с условием (WHERE balance >= amount) или SELECT ... FOR UPDATE, блокирующий строку до конца транзакции.
- **На практике:** Для систем с умеренной конкуренцией и сложной бизнес-логикой Serializable снижает риск пропустить неочевидную аномалию, но требует retry-цикла, так как откат под Serializable — штатная ситуация; для высокочастотных простых операций часто выгоднее явный атомарный UPDATE или FOR UPDATE, так как это предсказуемо по производительности.
- **Частые ошибки:** Включают Serializable глобально «на всякий случай», не реализовав retry-логику, из-за чего под нагрузкой пользователи получают случайные ошибки; реализуют FOR UPDATE в одних частях кода и обычные UPDATE без условий в других, создавая непоследовательную защиту.
- **Компромисс:** Выбор зависит от частоты конкурентных обращений к одним и тем же счетам, сложности бизнес-логики внутри транзакции, терпимости к retry на стороне клиента и готовности команды поддерживать явные блокировки против декларативного Serializable; критерий — профилирование реальной конкуренции и нагрузочное тестирование обоих вариантов перед продакшеном, а не выбор «по умолчанию».

**Пример / кейс**
```python
from django.db import transaction, DatabaseError, connection
import time

def debit_serializable(account_id, amount, attempts=5):
    for attempt in range(attempts):
        try:
            with transaction.atomic():
                connection.cursor().execute("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE")
                account = Account.objects.get(id=account_id)
                if account.balance < amount:
                    raise ValueError("Insufficient funds")
                account.balance -= amount
                account.save()
            return
        except DatabaseError as e:
            if "could not serialize access" in str(e) and attempt < attempts - 1:
                time.sleep(0.05 * (attempt + 1))
                continue
            raise
```
### 180. [Q-03-03-0180] Growing-продукт перерастает один инстанс PostgreSQL по объёму записи и данных. Как подойти к выбору стратегии шардирования (по ключу, диапазону) и какие проблемы с транзакциями и JOIN между шардами это создаёт? Обсудите компромиссы, риски и критерии выбора: единственного правильного решения нет.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Senior

**Короткий ответ**<br>
Шардирование по ключу (hash) даёт равномерное распределение нагрузки записи, но делает диапазонные запросы и перебалансировку сложнее; шардирование по диапазону (range) упрощает диапазонные запросы и добавление новых шардов, но рискует создавать «горячие» шарды при неравномерном распределении ключей; в обоих случаях транзакции и JOIN между шардами перестают быть атомарными и эффективными на уровне одной СУБД.

- **Как это работает:** При шардировании данные одной логической таблицы физически распределяются по нескольким независимым базам на основе ключа шардирования; обычная транзакция и JOIN работают только внутри одного шарда — операции между шардами требуют распределённой транзакции или перепроектирования логики так, чтобы связанные данные оказывались в одном шарде (co-location).
- **На практике:** Ключ шардирования выбирают так, чтобы большинство транзакционных операций и JOIN укладывались в один шард — например, шардировать по tenant_id, если почти все запросы скоуплены одним клиентом; для агрегации по всем шардам обычно используют отдельный путь — ETL в аналитическое хранилище, а не прямые cross-shard JOIN в OLTP-пути.
- **Частые ошибки:** Выбирают ключ шардирования по техническому удобству, не учитывая реальные паттерны запросов, что приводит к постоянным cross-shard операциям; откладывают проектирование шардирования до момента, когда миграция требует болезненного простоя или сложного дуального write.
- **Компромисс:** Решение зависит от того, какие запросы доминируют (точечные по ключу или диапазонные/аналитические), темпа роста и приемлемости сложности перебалансировки; hash-шардирование проще держать равномерным, но диапазонные запросы и resharding обычно дороже, чем при range-шардировании — нужно явно обсуждать, какие cross-shard сценарии бизнес готов обслуживать отдельным (более медленным/асинхронным) путём.

**Пример / кейс**
```text
Сценарий: мультитенантный SaaS, 10 000 клиентов, данные растут неравномерно.
Вариант A (hash по tenant_id): равномерная нагрузка записи, но отчёт "все платежи за месяц по всем клиентам"
требует запроса ко всем шардам и слияния на стороне приложения.
Вариант B (range по дате регистрации клиента): новые клиенты концентрируются в последнем шарде
("горячий" шард), но поддержка старых клиентов стабильна.
Решение команды: hash по tenant_id + co-location всех таблиц клиента в одном шарде,
аналитика — через отдельный ETL в DWH, а не прямые cross-shard JOIN.
```

[Q-03-03-0181] Как спроектировать эволюцию схемы БД и контрактов API так, чтобы изменения можно было деплоить и откатывать без несовместимости между версиями сервиса и структурой данных при частых релизах? Обсудите компромиссы, риски и критерии выбора: единственного правильного решения нет.

**Направление:** Python Backend Developer<br>

**Уровень:** Senior

**Короткий ответ**<br>
Основной принцип — любое изменение схемы должно оставаться совместимым как минимум с предыдущей версией кода на протяжении переходного периода (backward-compatible), что достигается аддитивными изменениями (новые nullable-колонки/таблицы вместо немедленного удаления/переименования старых) и явным разделением «расширения» схемы от «сжатия» (expand/contract) на отдельные релизы.

**Разбор**
- **Как это работает:** При rolling deploy и при необходимости откатить релиз одновременно могут работать как минимум две версии кода с одной и той же БД; совместимость означает, что старая версия кода не должна падать на новой схеме, а новая версия должна корректно работать даже при откате кода.
- **На практике:** Безопасные паттерны — добавление новых nullable-колонок/таблиц, отдельные релизы на «удаление» только после полной уверенности, что старый код больше не используется; версионирование контрактов API позволяет потребителям переходить постепенно.
- **Частые ошибки:** Совмещают несовместимое изменение схемы и деплой кода в один шаг, рассчитывая на «мгновенность» деплоя; не тестируют сценарий отката релиза отдельно от сценария «вперёд» — откат кода на старую версию при уже применённой новой миграции может оказаться невозможным.
- **Компромисс:** Полностью безопасная эволюция (expand/contract, многоэтапные релизы) требует больше времени и дисциплины по сравнению с «быстрым» прямым изменением схемы; критерий выбора — насколько критичен сервис к простою и как часто требуется откат, и готова ли команда поддерживать временно двойственный код на переходный период.

**Пример / кейс**
```text
Запрос на изменение: переименовать "status" в "order_status" и поменять набор допустимых значений.
Безопасный план:
1) Добавить новую колонку order_status, дублировать запись в обе колонки на уровне приложения.
2) Выпустить новую версию API с полем order_status как optional, старое поле status помечено
   deprecated, но ещё отдаётся.
3) После миграции всех потребителей API на новое поле — прекратить запись в старую колонку
   и удалить её отдельным релизом.
Риск при пропуске шагов: клиент API, который не обновился, получит неожиданное отсутствие поля
status и сломается без предупреждения.
```

[Q-03-03-0182] Для операции, затрагивающей несколько независимых сервисов с отдельными БД (например, резервирование товара и списание оплаты), нужно обеспечить согласованность без единой распределённой транзакции. **Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Senior

**Короткий ответ**<br>
2PC даёт строгую атомарность между несколькими БД за счёт координатора, который синхронно удерживает блокировки на всех участниках до commit, но плохо масштабируется и уязвим к недоступности координатора/участника; Saga разбивает операцию на последовательность локальных транзакций с компенсирующими действиями на случай неудачи, что масштабируется лучше, но требует продумывания каждой компенсации и временного окна промежуточной неконсистентности.

**Разбор**
- **Как это работает:** 2PC проходит через фазу подготовки (каждый участник резервирует изменения и сообщает «готов») и фазу коммита — пока не пройдена вторая фаза, ресурсы у всех участников заблокированы; Saga выполняет шаги последовательно как независимые локальные транзакции, и при ошибке запускает заранее определённые компенсирующие операции для уже выполненных шагов.
- **На практике:** 2PC применим, когда все участники поддерживают протокол и объём операций не слишком высок; Saga — типичный выбор для микросервисной архитектуры с разными технологиями хранения и высокой частотой операций, но требует идемпотентных шагов и компенсаций.
- **Частые ошибки:** Реализуют Saga без идемпотентности шагов, из-за чего повторная доставка сообщения приводит к двойному списанию/резервированию; не предусматривают, что компенсирующая операция сама может завершиться с ошибкой, оставляя систему в неопределённом состоянии без алертинга.
- **Компромисс:** Выбор зависит от требуемой строгости согласованности (мгновенная vs eventual), числа и разнородности участников, частоты операций и готовности команды поддерживать компенсирующую логику; для низкочастотных критичных операций в контролируемой инфраструктуре 2PC может быть оправдан, для высоконагруженной распределённой системы почти всегда предпочтительнее Saga с явным учётом окна неконсистентности.

**Пример / кейс**
```text

Saga:
1) OrderService: создать заказ в статусе "pending".
2) InventoryService: зарезервировать товар (локальная транзакция) -> событие "reserved".
3) PaymentService: списать оплату (локальная транзакция).
   - Если оплата не прошла -> компенсация: InventoryService отменяет резерв -> "reservation_cancelled".
4) OrderService: перевести заказ в "confirmed" или "cancelled" по итогам шагов.

Риск: между шагом 2 и 3 товар зарезервирован, но заказ ещё не оплачен — нужно явно решить,
сколько времени держать резерв и что считать таймаутом для запуска компенсации.
```
### 183. [Q-03-03-0183] Таблица событий/логов выросла до сотен миллионов строк, запросы и обслуживание (VACUUM, индексы) стали медленными. Как спроектировать партиционирование этой таблицы в PostgreSQL (по диапазону дат, по списку, по хешу) и какие риски и ограничения нужно учесть? Обсудите компромиссы, риски и критерии выбора: единственного правильного решения нет.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Senior

**Короткий ответ**<br>
Партиционирование по диапазону дат обычно лучший выбор для таблиц событий/логов, так как совпадает с паттерном доступа (чаще читают/пишут свежие данные) и позволяет дешёво удалять старые данные целыми партициями (DROP PARTITION) вместо построчного DELETE; партиционирование по хешу даёт равномерное распределение без «горячего» диапазона, но не даёт дешёвого способа избавляться от старых данных и не ускоряет диапазонные запросы по времени.

**Разбор**
- **Как это работает:** PostgreSQL Declarative Partitioning создаёт родительскую таблицу и набор физических партиций-наследников; планировщик использует partition pruning, чтобы при запросе с условием на партиционирующий ключ сканировать только нужные партиции, что также уменьшает объём данных для VACUUM/ANALYZE.
- **На практике:** Для таблицы событий типична схема «партиция на день/неделю/месяц» по created_at, автоматическое создание новых партиций заранее (pg_partman) и DROP/detach старых партиций вместо DELETE; партиционирующий ключ должен входить в большинство «горячих» запросов и в PRIMARY KEY/UNIQUE-ограничения.
- **Частые ошибки:** Выбирают ключ партиционирования, не используемый в фильтрах реальных запросов, из-за чего partition pruning не работает; создают слишком много мелких партиций, увеличивая накладные расходы планировщика.
- **Компромисс:** Range-партиционирование по дате даёт удобное устаревание данных, но требует дисциплины по созданию новых партиций вовремя и миграции существующей большой таблицы на партиционированную структуру (обычно через создание новой таблицы и постепенный перенос данных); критерий выбора — доминирующий паттерн доступа (по времени vs равномерно по ключу) и необходимость быстрого устаревания старых данных.

**Пример / кейс**
```sql
CREATE TABLE events (
    id BIGSERIAL,
    user_id BIGINT NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE events_2026_02 PARTITION OF events
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

-- Запрос за январь сканирует только одну партицию (partition pruning)
EXPLAIN SELECT * FROM events WHERE created_at >= '2026-01-10' AND created_at < '2026-01-20';

-- Удаление старых данных почти мгновенно вместо DELETE с полным сканом:
DROP TABLE events_2026_01;
```

**Уровень:** Senior

ORM даёт единообразие, безопасность от SQL-инъекций «из коробки», переносимость и скорость разработки типовых CRUD-операций, но на сложных аналитических запросах может генерировать неоптимальный SQL; raw SQL (или материализованное представление/хранимая процедура) даёт полный контроль над производительностью, но жертвует переносимостью и типобезопасностью ORM и требует отдельного процесса тестирования SQL-кода.

### 185. [Q-03-03-0185] Сервис обрабатывает события из очереди сообщений с гарантией доставки at-least-once, поэтому одно и то же сообщение может быть обработано дважды. Как спроектировать запись в БД так, чтобы повторная обработка не приводила к дублированию операции (например, двойному списанию)? Обсудите компромиссы, риски и критерии выбора: единственного правильного решения нет.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Senior

**Короткий ответ**<br>
Идемпотентность достигается явным uniqueness-ограничением на идентификатор операции (idempotency key/event id) в таблице, где фиксируется факт обработки, в сочетании с атомарной записью результата и факта обработки в одной транзакции — повторная обработка того же события натыкается на уже существующую запись и безопасно пропускается вместо повторного выполнения эффекта.

**Разбор**
- **Как это работает:** Перед выполнением бизнес-эффекта приложение пытается вставить строку с уникальным event_id в таблицу processed_events в той же транзакции, где выполняется сам эффект; если вставка нарушает unique-ограничение — событие уже обработано, транзакция откатывается без повторного эффекта.
- **На практике:** Ключ идемпотентности должен однозначно идентифицировать именно бизнес-операцию, а не технический id сообщения в очереди (который может отличаться при ретрае брокера); для внешнего side effect (вызов платёжного API) идемпотентность нужно обеспечивать и на уровне самого внешнего вызова.
- **Частые ошибки:** Проверяют «не обработано ли уже событие» отдельным SELECT, а запись выполняют отдельной операцией позже — между шагами возможна гонка при параллельной обработке; используют как ключ идемпотентности значение, меняющееся при каждой повторной доставке.
- **Компромисс:** Хранение полной истории обработанных event_id бессрочно требует места и обслуживания (архивация/партиционирование), а слишком агрессивная очистка рискует «забыть» о событии при очень отложенном ретрае брокера; критерий выбора срока хранения — максимально возможная задержка повторной доставки в конкретном брокере против стоимости хранения большого объёма идентификаторов.

**Пример / кейс**
```python
from django.db import transaction, IntegrityError

def handle_payment_event(event_id: str, account_id: int, amount: int) -> bool:
    try:
        with transaction.atomic():
            ProcessedEvent.objects.create(event_id=event_id)  # unique constraint на event_id
            Account.objects.filter(id=account_id).update(balance=F("balance") - amount)
        return True  # можно делать ack сообщения брокеру
    except IntegrityError:
        # event_id уже обработан ранее — эффект не повторяем, но ack всё равно делаем
        return False
```

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Senior

**Короткий ответ**<br>
Основная причина, при которой autovacuum не может очистить устаревшие версии строк, — долго открытые транзакции (включая «зависшие» idle in transaction соединения) или не продвигающиеся replication slots, которые удерживают старый снимок MVCC; решение — контроль длительности транзакций на уровне приложения/пула (таймауты), мониторинг age транзакций и слотов, и более агрессивная настройка autovacuum для горячих таблиц.

**Разбор**
- **Как это работает:** PostgreSQL использует MVCC — каждое UPDATE/DELETE создаёт новую версию строки, старая остаётся, пока активная транзакция потенциально может её видеть; autovacuum не может продвинуться дальше самой старой активной транзакции или replication slot — отсюда bloat даже при формально работающем autovacuum.
- **На практике:** Для диагностики смотрят на pg_stat_activity (state = 'idle in transaction'), pg_stat_replication/pg_replication_slots, pg_stat_user_tables (n_dead_tup); меры — idle_in_transaction_session_timeout, более агрессивные настройки autovacuum для «горячих» таблиц, мониторинг возраста самой старой открытой транзакции.
- **Частые ошибки:** Держат транзакцию открытой во время ожидания ответа от внешнего API; игнорируют неиспользуемые replication slots (например, от удалённого consumer логической репликации), которые бесконечно удерживают WAL.
- **Компромисс:** Слишком агрессивные настройки autovacuum снижают bloat, но увеличивают фоновую нагрузку на I/O/CPU, заметную на пиковой нагрузке; слишком редкий vacuum экономит ресурсы в моменте, но накапливает bloat, замедляющий Seq Scan и индексы — решение требует баланса, основанного на профиле нагрузки конкретной таблицы, а не единой настройки «по умолчанию» для всей БД.

**Пример / кейс**
```sql
-- Найти долгие/зависшие транзакции
SELECT pid, state, now() - xact_start AS duration, query
FROM pg_stat_activity
WHERE state != 'idle' AND xact_start IS NOT NULL
ORDER BY duration DESC;

-- Найти таблицы с большим числом "мёртвых" строк
SELECT relname, n_dead_tup, n_live_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;
```
### 187. [Q-03-03-0187] Релиз включает миграцию БД (например, изменение структуры таблицы) вместе с новым кодом. Как спроектировать процесс деплоя так, чтобы в случае проблем можно было безопасно и быстро откатить релиз без потери и повреждения данных? Обсудите компромиссы, риски и критерии выбора: единственного правильного решения нет.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Senior

**Короткий ответ**<br>
Безопасный откат обеспечивается, когда миграция и код спроектированы так, что предыдущая версия кода продолжает корректно работать и после применения новой миграции (backward-compatible migration) — тогда откат кода не требует отдельного откат миграции «на лету»; миграции, которые физически удаляют данные/колонки или делают их несовместимыми для старого кода, нужно разносить на отдельные более поздние релизы.

**Разбор**
- **Как это работает:** При обнаружении проблемы после релиза самый быстрый способ восстановления — откатить деплой кода до предыдущей версии; если миграция уже физически изменила несовместимым образом структуру (удалила колонку), откат кода сам по себе не восстановит работоспособность без восстановления колонки и данных.
- **На практике:** Стратегия — разделять рискованные структурные изменения на несколько релизов (expand → перенести код на новую структуру → contract), держать миграции обратимыми, тестировать сценарий rollback на стейджинге; для необратимых операций заранее делать резервную копию или снапшот.
- **Частые ошибки:** Пишут функцию downgrade() формально, но никогда не тестируют её — на реальном откате выясняется, что она не работает или теряет данные; считают, что блокировка на пару секунд при ALTER TABLE — это нормально, без проверки на реальном объёме production-таблицы.
- **Компромисс:** Многоэтапный безопасный процесс требует больше времени и дисциплины релизного процесса, чем прямое изменение схемы одним релизом; команда должна явно решить, какой уровень риска приемлем — для некритичных внутренних сервисов можно допустить более быстрый, но менее безопасный путь, тогда как для платёжных/учётных систем обязательна многоэтапная стратегия с протестированным откатом.

**Пример / кейс**
```text
План релиза с рискованной миграцией:
1) Снять логический снапшот/бэкап перед миграцией (point-in-time recovery доступен на N часов назад).
2) Выполнить только backward-compatible часть миграции (expand): добавить новую колонку nullable.
3) Деплой кода, который пишет в обе колонки.
4) Наблюдение (canary/мониторинг ошибок) в течение оговорённого окна.
5) Contract-миграция (удаление старой колонки) — отдельным релизом, только после подтверждения
   стабильности и явного решения, что откат к состоянию "до шага 2" больше не рассматривается.
```
### 188. [Q-03-03-0188] Для финансово значимой таблицы нужно вести аудит всех изменений (кто, когда и что изменил, включая старые и новые значения) для последующих расследований и соответствия требованиям комплаенса. Как спроектировать такой аудит — через триггеры БД, через приложение (outbox/явный лог) или через событийный подход (event sourcing-lite), и какие риски несёт каждый вариант? Обсудите компромиссы, риски и критерии выбора: единственного правильного решения нет.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Senior

**Короткий ответ**<br>
Триггеры БД гарантируют, что ни одно изменение не пройдёт мимо аудита независимо от того, через какой код/сервис оно сделано (включая ручные правки через psql), но усложняют миграции и могут быть «невидимы» для разработчиков, читающих только код приложения; аудит на уровне приложения более прозрачен и прост в сопровождении, но не защищает от изменений в обход этого кода.

**Разбор**
- **Как это работает:** Триггер AFTER INSERT/UPDATE/DELETE может автоматически писать старые/новые значения строки (через OLD/NEW) в таблицу аудита в той же транзакции, что и само изменение; приложение-уровневый подход явно формирует запись аудита в коде обработчика, часто вместе с бизнес-семантикой изменения.
- **На практике:** Триггерный подход предпочтителен, когда к таблице обращаются разные сервисы/скрипты не через единый слой приложения; приложение-уровневый — когда важен бизнес-контекст изменения. Event sourcing-lite даёт наиболее полную историю «почему», но требует серьёзного пересмотра архитектуры хранения.
- **Частые ошибки:** Реализуют аудит только в коде приложения, не замечая, что администратор БД или скрипт миграции данных может менять данные напрямую, минуя аудит; переkладывают объём аудита в ту же БД без партиционирования и политики хранения, из-за чего таблица аудита сама становится проблемой.
- **Компромисс:** Наиболее надёжный по полноте вариант — комбинация триггеров (или CDC/Debezium в отдельное хранилище) для гарантии «ничего не прошло мимо» и приложения для обогащения бизнес-контекстом; выбор зависит от строгости требований комплаенса, объёма изменений (триггеры добавляют накладные расходы на каждую запись) и готовности команды поддерживать более сложную инфраструктуру.

**Пример / кейс**
```sql
CREATE TABLE account_audit (
    id BIGSERIAL PRIMARY KEY,
    account_id INTEGER NOT NULL,
    changed_by TEXT,
    changed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    old_balance NUMERIC(14,2),
    new_balance NUMERIC(14,2)
);

CREATE OR REPLACE FUNCTION audit_account_balance() RETURNS TRIGGER AS $$
BEGIN
    IF NEW.balance IS DISTINCT FROM OLD.balance THEN
        INSERT INTO account_audit(account_id, changed_by, old_balance, new_balance)
        VALUES (NEW.id, current_setting('app.current_user', true), OLD.balance, NEW.balance);
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_audit_account_balance
AFTER UPDATE ON accounts
FOR EACH ROW EXECUTE FUNCTION audit_account_balance();
-- Срабатывает независимо от того, через ORM или прямой SQL было изменение
```
### 189. [Q-03-03-0189] Раздел каталога товаров читается в сотни раз чаще, чем обновляется, и нагрузка на чтение растёт. Как выбрать между кэшированием на уровне приложения, добавлением read replica и материализованными представлениями (materialized view) в PostgreSQL для масштабирования чтения? Обсудите компромиссы, риски и критерии выбора: единственного правильного решения нет.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Senior

**Короткий ответ**<br>
Кэш на уровне приложения даёт наибольшее снижение нагрузки на БД и самую низкую латентность, но добавляет слой инвалидации, за которым нужно следить; read replica снимает нагрузку на чтение без изменения логики кэша, но стоит дополнительной инфраструктуры и несёт риск replication lag; материализованное представление ускоряет конкретные дорогие агрегирующие запросы, но данные в нём устаревают до следующего REFRESH.

**Разбор**
- **Как это работает:** Кэш хранит готовый результат вне БД и отдаёт его без обращения к БД до инвалидации/TTL; read replica — полноценная копия БД для SELECT-запросов, не трогающая primary; materialized view — заранее вычисленный результат сложного запроса, обновляемый командой REFRESH, а не пересчитываемый на каждый SELECT.
- **На практике:** Для данных, которые меняются редко и читаются по понятному ключу, кэш даёт наибольший выигрыш при разумной инвалидации по событию обновления; для разнородных запросов (поиск, фильтрация) часто проще read replica; materialized view хорошо подходит для тяжёлых агрегаций, не обязанных быть в реальном времени.
- **Частые ошибки:** Добавляют кэш без продуманной стратегии инвалидации, получая устаревшие цены/наличие товара; используют read replica и считают проблему производительности полностью решённой, не замечая, что сама primary продолжает деградировать из-за записи.
- **Компромисс:** Можно комбинировать все три подхода на разных частях каталога, но каждый добавленный слой — это дополнительная операционная сложность и ещё одна точка, где данные могут временно расходиться; критерий выбора — приемлемая для бизнеса степень устаревания данных (секунды для кэша с коротким TTL, секунды-минуты для replica lag, минуты-часы для materialized view) и готовность команды поддерживать соответствующую инфраструктуру.

**Пример / кейс**
```python

import redis

r = redis.Redis()

def get_product(product_id: int) -> dict:
    cache_key = f"product:{product_id}"
    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)
    product = Product.objects.values().get(id=product_id)
    r.setex(cache_key, 300, json.dumps(product, default=str))  # TTL 5 минут
    return product

def on_product_updated(product_id: int):
    r.delete(f"product:{product_id}")  # явная инвалидация при изменении товара
```

### 190. [Q-03-03-0190] Таблица пользователей содержит чувствительные персональные данные (например, номер документа), которые должны быть защищены шифрованием на уровне колонки. Как выбрать между column-level шифрованием через pgcrypto и шифрованием на уровне всего хранилища (TDE/дискового тома), и как это решение влияет на возможность индексации и производительность запросов? Обсудите компромиссы, риски и критерии выбора: единственного правильного решения нет.

**Направление:** Python Backend Developer<br>
**Тема:** SQL, базы данных и ORM: PostgreSQL, моделирование данных, индексы, транзакции, уровни изоляции, SQLAlchemy, Django ORM и миграции<br>
**Уровень:** Senior

**Короткий ответ**<br>
Шифрование на уровне диска/тома защищает данные только «в покое» и полностью прозрачно для SQL-слоя — индексы и запросы работают как обычно, но не защищает от доступа через скомпрометированную учётную запись БД; column-level шифрование через pgcrypto защищает конкретное поле даже от доступа с правами на таблицу, если ключ хранится отдельно от БД, но делает обычный поиск/сравнение/сортировку по этому полю в зашифрованном виде невозможными без расшифровки.

**Разбор**
- **Как это работает:** pgcrypto предоставляет функции pgp_sym_encrypt/pgp_sym_decrypt, которые шифруют значение перед записью и расшифровывают при чтении с передачей ключа как параметра запроса; хранимое значение — бинарные зашифрованные байты, поэтому обычный индекс на этой колонке бесполезен для поиска по исходному значению.
- **На практике:** Для полей, по которым нужен точный поиск, применяют детерминированное шифрование или дополнительно хранят отдельный HMAC/хеш от значения в отдельной индексируемой колонке; управление ключами выносят за пределы самой БД (KMS/Vault), так как хранение ключа рядом с данными снижает защиту почти до нуля при компрометации БД.
- **Частые ошибки:** Шифруют колонку и одновременно ожидают от неё эффективного LIKE/диапазонного поиска — это невозможно без расшифровки каждой строки; хранят ключ шифрования в той же БД или в конфиге рядом с connection string, что не даёт защиты сверх обычного шифрования диска.
- **Компромисс:** TDE/шифрование диска проще внедрить и не влияет на производительность и индексацию, но защищает от более узкого набора угроз; column-level шифрование защищает от более широкого класса угроз, но требует отказа от обычной индексации по этому полю и инфраструктуры управления ключами — критерий выбора — модель угроз, регуляторные требования и реальная потребность в поиске/сортировке по защищаемому полю.

**Пример / кейс**
```sql
-- Учебный пример (без реальных секретов и ключей): шифрование номера документа
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- Запись: ключ передаётся из приложения как параметр запроса, не хранится в БД
INSERT INTO users (id, document_number_encrypted, document_hmac)
VALUES (
    1,
    pgp_sym_encrypt('1234567890', :encryption_key),
    encode(hmac('1234567890', :hmac_key, 'sha256'), 'hex')
);

-- Поиск по точному значению через отдельный индексируемый HMAC, а не через расшифровку каждой строки
CREATE INDEX idx_users_document_hmac ON users(document_hmac);
SELECT id FROM users WHERE document_hmac = encode(hmac('1234567890', :hmac_key, 'sha256'), 'hex');
```
