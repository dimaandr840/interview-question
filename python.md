## 1. Что выведет код и как исправить ошибку: изменяемое значение по умолчанию?

Направление: Python Backend Developer
Тема: Основы Python
Уровень: Junior

### Короткий ответ
Значение по умолчанию вычисляется один раз при определении функции, поэтому изменяемый объект (`[]`, `{}`) разделяется между вызовами. Используйте `None` и создавайте объект внутри функции.

### Разбор
**Как это работает:** при выполнении `def` Python создаёт объект функции и сразу вычисляет значения по умолчанию, сохраняя их в `func.__defaults__`. Каждый вызов без аргумента получает ссылку на тот же объект. Если функция его мутирует, изменения видны всем следующим вызовам.

**На практике:**
- Шаблон `def f(x, items=None): items = [] if items is None else items`.
- Различайте `None` и «пустой список, переданный явно»: проверяйте `is None`, а не `not items`, если пустое значение осмысленно.
- Для неизменяемых значений (`int`, `str`, `tuple`, `None`) проблемы нет.
- Проверка: тест, который вызывает функцию дважды и проверяет, что второй результат не содержит данных первого вызова. Линтеры (например, ruff, правило B006) тоже ловят этот паттерн.

**Частые ошибки:**
- Считать, что список создаётся заново при каждом вызове.
- «Лечить» проблему копированием в конце функции, а не заменой значения по умолчанию.
- Использовать `if not items`, из-за чего переданный вызывающим пустой список молча подменяется новым, и вызывающий не видит изменений в своём объекте.

### Пример / кейс
```python
def add_tag(tag, tags=[]):  # ОШИБКА намеренно: общий список
    tags.append(tag)
    return tags

print(add_tag("a"))  # ['a']
print(add_tag("b"))  # ['a', 'b']  <- неожиданно

def add_tag_fixed(tag, tags=None):
    if tags is None:
        tags = []
    tags.append(tag)
    return tags

assert add_tag_fixed("a") == ["a"]
assert add_tag_fixed("b") == ["b"]
```
Ожидание: у исправленной версии второй вызов не видит данных первого. Проверка — assert-ы выше или `add_tag.__defaults__`.

## 2. Почему `{[1, 2]: "x"}` вызывает ошибку, а `{(1, 2): "x"}` нет, и когда для проверки вхождения лучше `set`, чем `list`?

Направление: Python Backend Developer
Тема: Основы Python
Уровень: Junior

### Короткий ответ
Ключи словаря и элементы множества должны быть хешируемыми: у `list` нет стабильного хеша, у `tuple` из хешируемых элементов есть. `set` даёт проверку `in` в среднем за O(1) против O(n) у списка, но не хранит порядок вставки как последовательность и не допускает дубликаты.

### Разбор
**Как это работает:** `dict` и `set` — хеш-таблицы. Объект кладётся в корзину по `hash(obj)`, а равенство проверяется через `__eq__`. Если объект изменяем и его содержимое влияет на `==`, хеш мог бы измениться после вставки, и объект «потерялся» бы. Поэтому `list`, `dict`, `set` не хешируемы. Кортеж хешируем, только если хешируемы все его элементы: `(1, [2])` вызовет `TypeError`.

**На практике:**
- Проверка прав `if role in ALLOWED_ROLES` при большом наборе значений — кандидат на `set`/`frozenset`.
- Для 5–10 элементов разница несущественна; решение должно опираться на размер данных и профилирование, а не на привычку.
- Среднее O(1) не гарантирует худший случай: коллизии возможны.
- Проверка: `timeit` на реалистичных объёмах и типах ключей.

**Частые ошибки:**
- Говорить, что `set` всегда быстрее для любых операций (создание `set` из списка стоит O(n)).
- Рассчитывать на порядок элементов `set` (у `dict` порядок вставки гарантирован с Python 3.7, у `set` — нет).
- Использовать изменяемый объект с собственным `__hash__`, зависящим от изменяемых полей.

### Пример / кейс
```python
ok = {(1, 2): "x"}
try:
    bad = {[1, 2]: "x"}
except TypeError as e:
    print(e)  # unhashable type: 'list'

try:
    {(1, [2])}
except TypeError as e:
    print(e)  # unhashable type: 'list'

ALLOWED = frozenset({"admin", "editor", "viewer"})
print("editor" in ALLOWED)  # True, среднее O(1)
```
Проверка: перехваченные `TypeError` и результат `in` для `frozenset`.

## 3. Почему этот код падает с `UnboundLocalError` и как его исправить?

Направление: Python Backend Developer
Тема: Основы Python
Уровень: Junior

### Короткий ответ
Присваивание внутри функции делает имя локальным для всей функции, поэтому чтение до присваивания обращается к ещё не созданной локальной переменной. Решение — передавать и возвращать значение, использовать объект-состояние, а `global`/`nonlocal` применять осознанно.

### Разбор
**Как это работает:** область видимости имени определяется на этапе компиляции функции по правилу LEGB (Local → Enclosing → Global → Built-in). Если в теле есть `counter += 1`, то `counter` — локальная, и чтение до первого присваивания даёт `UnboundLocalError`. Чтение глобальной переменной без присваивания работает.

**На практике:**
- Для вложенной функции, меняющей переменную внешней функции, нужен `nonlocal`.
- `global` для изменяемого состояния в backend-приложении — плохая идея: при нескольких процессах (gunicorn/uvicorn workers) каждый процесс получит свою копию счётчика, а в потоках возможны гонки.
- Состояние лучше хранить в объекте, БД или внешнем хранилище (например, Redis), а не в модульной переменной.
- Проверка: юнит-тест на функцию без побочных эффектов.

**Частые ошибки:**
- Считать, что ошибка возникает «только при выполнении `+=`», а не из-за правил компиляции.
- Использовать `global` как универсальное решение.
- Мутировать глобальный `dict`/`list` и думать, что это решает проблему многопроцессности.

### Пример / кейс
```python
counter = 0

def inc_broken():  # ОШИБКА намеренно
    counter += 1   # UnboundLocalError при вызове

def inc(value: int) -> int:
    return value + 1

def make_counter():
    count = 0
    def inc_inner():
        nonlocal count
        count += 1
        return count
    return inc_inner

c = make_counter()
assert (c(), c()) == (1, 2)
assert inc(counter) == 1
```
Ожидание: `inc_broken()` падает с `UnboundLocalError`, остальные примеры проходят assert-ы.

## 4. В чём разница между `is` и `==`, и когда `is` использовать корректно?

Направление: Python Backend Developer
Тема: Основы Python
Уровень: Junior

### Короткий ответ
`==` сравнивает значения через `__eq__`, `is` проверяет, что это один и тот же объект. `is` корректен для синглтонов (`None`, `True`, `False`) и сентинелов; для чисел и строк результат зависит от реализации.

### Разбор
**Как это работает:** `is` сравнивает идентичность объектов (в CPython — это совпадение адреса, `id(a) == id(b)`). `==` вызывает `a.__eq__(b)`, и класс сам определяет, что значит «равно».

**На практике:**
- Проверка на `None`: `if value is None` — стандарт (PEP 8), `__eq__` можно переопределить, и `== None` даст сюрприз.
- Сентинел: `_MISSING = object()` и `if x is _MISSING` позволяет отличить «не передано» от `None`.
- Кэширование небольших `int` и интернирование строк — деталь CPython, она может меняться между версиями и контекстами компиляции. Писать код, зависящий от этого, нельзя.
- Проверка: тесты на значения, а не на идентичность.

**Частые ошибки:**
- Использовать `is` для сравнения строк и чисел («работает у меня в REPL»).
- Использовать `== True` / `is True` для проверки истинности, когда нужна просто truthiness (но если API различает `True` и `1`, проверка `is True` осмысленна).
- Думать, что `float("nan") == float("nan")` истинно: это `False`, при этом `nan is nan` для одного объекта — `True`.

### Пример / кейс
```python
a = [1, 2]
b = [1, 2]
assert a == b
assert a is not b

_MISSING = object()

def get_limit(limit=_MISSING):
    if limit is _MISSING:
        return 100      # не передан
    return limit        # в т.ч. None = «без лимита»

assert get_limit() == 100
assert get_limit(None) is None
```
Проверка: assert-ы; поведение `None` и «не передано» различается.

## 5. Что вернёт функция и в каком порядке выполнятся `try`, `else` и `finally`?

Направление: Python Backend Developer
Тема: Основы Python
Уровень: Junior

### Короткий ответ
`else` выполняется, если в `try` не было исключения, `finally` — всегда. `return` внутри `finally` перекрывает возврат и подавляет исключение, поэтому так писать не следует.

### Разбор
**Как это работает:** при `return` в `try` значение вычисляется, затем выполняется `finally`, и только потом происходит возврат. Если `finally` сам делает `return` или `raise`, он заменяет результат или исключение. Блок `else` стоит между `try` и `finally` и выполняется только при отсутствии исключения.

**На практике:**
- `finally` — для освобождения ресурсов (закрыть соединение, снять блокировку), но чаще лучше `with`.
- `else` помогает сузить зону `try`: в `try` только код, который может бросить ожидаемое исключение.
- В новых версиях Python (3.14, PEP 765) `return`/`break`/`continue`, выходящие из `finally`, вызывают предупреждение компилятора; свою версию проверьте в документации.
- Проверка: тесты с принудительным исключением и проверкой побочных эффектов.

**Частые ошибки:**
- Ловить слишком широкий блок `try`, скрывая ошибки в коде, которые не должны перехватываться.
- `return` в `finally`, молча проглатывающий исключение.
- Забывать, что `finally` выполняется и при `return`, и при необработанном исключении.

### Пример / кейс
```python
def f(flag):
    log = []
    try:
        log.append("try")
        if flag:
            raise ValueError("boom")
    except ValueError:
        log.append("except")
    else:
        log.append("else")
    finally:
        log.append("finally")
    return log

assert f(False) == ["try", "else", "finally"]
assert f(True) == ["try", "except", "finally"]
```
Проверка: assert-ы показывают порядок блоков для обеих веток.

## 6. Чем отличаются поверхностная и глубокая копия, и почему изменение копии «ломает» оригинал?

Направление: Python Backend Developer
Тема: Основы Python
Уровень: Junior

### Короткий ответ
Поверхностная копия (`copy.copy`, `list.copy()`, `dict.copy()`) создаёт новый внешний контейнер, но элементы остаются теми же объектами. `copy.deepcopy` рекурсивно копирует вложенные объекты.

### Разбор
**Как это работает:** переменные в Python — ссылки на объекты. Копия списка списков содержит те же внутренние списки. Изменение внутреннего списка видно через обе ссылки. `deepcopy` обходит граф объектов и запоминает уже скопированные, поэтому справляется и с циклами.

**На практике:**
- Для простых конфигов с вложенностью `deepcopy` безопасен, но может быть дорогим на больших структурах.
- Часто лучше не копировать, а использовать неизменяемые структуры (`tuple`, `frozenset`, frozen dataclass) или строить новый объект явно.
- Объекты с ресурсами (соединения, файлы, блокировки) копировать глубоко нельзя или бессмысленно.
- Проверка: тест, меняющий вложенный элемент копии и сравнивающий оригинал.

**Частые ошибки:**
- Думать, что `new = old` — это копия (это вторая ссылка).
- Считать, что `[[0] * 3] * 3` создаёт независимые строки (нет, одна и та же строка трижды).
- Применять `deepcopy` «на всякий случай» в горячем пути запроса.

### Пример / кейс
```python
import copy

a = [[1], [2]]
b = a.copy()
b[0].append(9)
assert a == [[1, 9], [2]]  # оригинал изменился

c = copy.deepcopy(a)
c[0].append(7)
assert a == [[1, 9], [2]]  # не изменился

grid = [[0] * 3] * 3       # ОШИБКА намеренно: одна строка трижды
grid[0][0] = 1
assert grid == [[1, 0, 0]] * 3
```
Проверка: assert-ы показывают разделение вложенных объектов и работу `deepcopy`.

## 7. Почему после определения `__eq__` экземпляры класса перестают быть хешируемыми и что с этим делать?

Направление: Python Backend Developer
Тема: Основы Python
Уровень: Junior

### Короткий ответ
Если класс определяет `__eq__` и не определяет `__hash__`, Python устанавливает `__hash__ = None`. Нужно согласованно определить оба метода или использовать `@dataclass(frozen=True)`.

### Разбор
**Как это работает:** контракт: равные объекты должны иметь равный хеш. Определив `__eq__`, вы изменили понятие равенства, и унаследованный от `object` хеш (по идентичности) перестаёт соответствовать контракту, поэтому Python отключает его.

**На практике:**
- Хешировать нужно по тем же полям, что участвуют в `__eq__`, и только по неизменяемым.
- `@dataclass(eq=True)` без `frozen=True` и без `unsafe_hash` устанавливает `__hash__ = None`; `frozen=True` генерирует хеш.
- Для сущностей с идентификатором (ORM-модели) равенство часто строят по первичному ключу, но у несохранённых объектов ключа ещё нет — учитывайте это.
- Проверка: тесты, что равные объекты дают одинаковый хеш и работают в `set`/`dict`.

**Частые ошибки:**
- Определить `__hash__` по изменяемым полям: объект «теряется» в `set` после изменения.
- Определить `__hash__` без `__eq__` (или наоборот) и нарушить контракт.
- Возвращать `hash(id(self))` вместе с `__eq__` по значению.

### Пример / кейс
```python
from dataclasses import dataclass

class Money:
    def __init__(self, amount: int, currency: str):
        self.amount, self.currency = amount, currency
    def __eq__(self, other):
        return (self.amount, self.currency) == (other.amount, other.currency)

try:
    {Money(1, "USD")}
except TypeError as e:
    print(e)  # unhashable type: 'Money'

@dataclass(frozen=True)
class Price:
    amount: int
    currency: str

assert len({Price(1, "USD"), Price(1, "USD")}) == 1
```
Проверка: первый пример падает с `TypeError`, второй схлопывает равные значения в один элемент множества.

## 8. Как работают `*args`, `**kwargs` и аргументы только по ключу, и зачем они в публичных функциях?

Направление: Python Backend Developer
Тема: Основы Python
Уровень: Junior

### Короткий ответ
`*args` собирает лишние позиционные аргументы в кортеж, `**kwargs` — именованные в словарь, параметры после `*` можно передать только по имени. Это делает сигнатуры явными и защищает от перепутанных позиционных аргументов.

### Разбор
**Как это работает:** при вызове Python сопоставляет аргументы с параметрами слева направо, затем собирает остаток в `*args`/`**kwargs`. Параметры после голого `*` — keyword-only. Параметры до `/` — positional-only (Python 3.8+).

**На практике:**
- Булевы флаги и необязательные настройки лучше делать keyword-only: `create_user("Ann", is_admin=True)` читается однозначно.
- Не используйте `**kwargs` там, где набор параметров известен: IDE и type checker перестают помогать, опечатки в именах не ловятся.
- Обёртки и декораторы прозрачно передают `*args, **kwargs` дальше.
- Проверка: тест, что вызов с позиционным флагом даёт `TypeError`.

**Частые ошибки:**
- `def f(**kwargs)` вместо явных параметров.
- Забыть распаковку при передаче: `g(args)` вместо `g(*args)`.
- Менять сигнатуру публичной функции, вставляя новый позиционный параметр в середину: ломаются существующие вызовы.

### Пример / кейс
```python
def create_user(name: str, *, is_admin: bool = False, **extra):
    return {"name": name, "is_admin": is_admin, "extra": extra}

assert create_user("Ann", is_admin=True, team="core") == {
    "name": "Ann", "is_admin": True, "extra": {"team": "core"}
}

try:
    create_user("Ann", True)  # позиционный флаг запрещён
except TypeError as e:
    print(e)
```
Проверка: assert проходит, второй вызов вызывает `TypeError`.

## 9. Как правильно обернуть низкоуровневую ошибку в доменное исключение, не потеряв причину?

Направление: Python Backend Developer
Тема: Основы Python
Уровень: Junior

### Короткий ответ
Определите собственный класс исключения и бросайте его через `raise DomainError(...) from exc`. Так сохраняется цепочка причин (`__cause__`), и в трейсбэке видно исходную ошибку.

### Разбор
**Как это работает:** при `raise ... from exc` Python записывает `exc` в `__cause__` нового исключения и выводит обе ошибки. Без `from` внутри `except` исключение тоже связывается (`__context__`), но сообщение сформулировано как «во время обработки произошло другое исключение». `from None` намеренно скрывает контекст.

**На практике:**
- Ловите конкретные исключения (`KeyError`, `ConnectionError`), а не `except Exception` и тем более голый `except:` (он перехватывает `KeyboardInterrupt` и `SystemExit`).
- Слой API превращает доменные исключения в HTTP-статусы; детали внутренних ошибок клиенту не раскрываются, но пишутся в лог.
- Логируйте через `logger.exception(...)` или `exc_info=True`, чтобы сохранить трейсбэк.
- Проверка: тест через `pytest.raises` с проверкой `__cause__`.

**Частые ошибки:**
- `except Exception: pass` — молчаливое проглатывание.
- Потеря трейсбэка при `raise Exception(str(e))`.
- Логирование и повторный `raise` на каждом уровне: одна ошибка дублируется в логах многократно.

### Пример / кейс
```python
class ConfigError(Exception):
    pass

def get_port(cfg: dict) -> int:
    try:
        return int(cfg["port"])
    except KeyError as exc:
        raise ConfigError("Не задан параметр port") from exc
    except ValueError as exc:
        raise ConfigError("port должен быть числом") from exc

try:
    get_port({})
except ConfigError as e:
    assert isinstance(e.__cause__, KeyError)
```
Проверка: `__cause__` содержит исходный `KeyError`; в трейсбэке видны обе ошибки.

## 10. Почему два экземпляра класса «делят» список и как этого избежать?

Направление: Python Backend Developer
Тема: Основы Python
Уровень: Junior

### Короткий ответ
Атрибут, объявленный в теле класса, принадлежит классу и разделяется всеми экземплярами. Изменяемые данные экземпляра нужно создавать в `__init__` (или через `field(default_factory=...)` в dataclass).

### Разбор
**Как это работает:** поиск атрибута идёт сначала в `instance.__dict__`, затем в классе и его предках. Если в `__init__` атрибута нет, `self.items` найдётся в классе. Метод `self.items.append(x)` мутирует общий объект. А присваивание `self.items = [...]` создаёт атрибут экземпляра и «затеняет» атрибут класса.

**На практике:**
- Состояние экземпляра — в `__init__`; константы и значения по умолчанию неизменяемых типов — на уровне класса.
- В dataclass изменяемое значение по умолчанию запрещено напрямую (`ValueError`), нужен `field(default_factory=list)`.
- Проверка: тест, создающий два экземпляра и меняющий один.
- В коде с потоками общий изменяемый атрибут класса — источник гонок.

**Частые ошибки:**
- Путать присваивание (`self.x = ...`, создаёт атрибут экземпляра) и мутацию (`self.x.append(...)`, меняет общий объект).
- Использовать атрибут класса как «кэш по умолчанию» без осознания, что он общий для процесса.
- Ожидать, что `Cart.items` и `cart.items` — разные объекты.

### Пример / кейс
```python
from dataclasses import dataclass, field

class CartBroken:
    items = []  # ОШИБКА намеренно: общий для всех экземпляров
    def add(self, x):
        self.items.append(x)

a, b = CartBroken(), CartBroken()
a.add("milk")
assert b.items == ["milk"]  # неожиданно

@dataclass
class Cart:
    items: list = field(default_factory=list)

c, d = Cart(), Cart()
c.items.append("milk")
assert d.items == []
```
Проверка: assert-ы; у исправленной версии экземпляры независимы.
